### V425920 — B768160: OCR a scanned deed PDF into a correctly-plottable legal description, on the owner's real scanned deed
**What was verified here — the whole pipeline (render → preprocess → Tesseract → repair/reflow → deedParse.js → closure) driven end to end in headless Chromium against the REAL shipped code, twice, at two degradation levels, plus the owner's own independent real-deed measurement.** `ui-audit/verify-ocr-scanned-deed.mjs` renders a legal description (the same construct set as the owner's real deed: a curve with radius/central-angle/arc/chord, a passing-at/total-distance clause, a parenthetical offset note) to a canvas, degrades it the way a repeated photocopy scan degrades (skew, noise, dropped contrast, a resample-down-and-up blur), builds a real text-less PDF from it (pdf-lib), and feeds that PDF straight into `ocrScannedDeedPdf` — the exact function `readDeeds`/`ocrScannedPdfInto` call in `SitePlanner.jsx`.
- **Realistic photocopy-scan degradation** (skew 1.6°, mild noise, moderate contrast loss, resample blur): mean OCR confidence 94.1%. **6/6 courses found, 6/6 bearings correct (azimuth within 0.5°, distance within 1% or 0.5 ft), traverse CLOSES at 0.60 ft misclosure** — effectively exact, and closure error alone would never have raised a flag. Wall clock 43s for one page.
- **Harsher stress degradation** (skew 2.4°, heavier noise, contrast dropped further, heavier resample blur): mean OCR confidence still a plausible-looking 85.1%, but **0/6 bearings recovered exactly** — digit-level corruption (0→6/8, dropped/altered characters) got past the repair rules. **The closure safety net did exactly its job: misclosure 894 ft on a ~2,500 ft traverse — unmissable, not a silently-plausible wrong polygon.** This is the case CLAUDE.md item (f) exists for: a bad OCR read produces a LOUD, obvious "does NOT close" warning (with the low-confidence/suspect-distance culprit calls named in the UI), never a quiet wrong boundary.
- **The owner's own independent measurement, on his real recorded deed (Chambers County, "16 - Recorded Correction SWD.pdf," a 1-bit CCITT-G4 scan, no preprocessing, stock Tesseract):** 19/19 bearings recovered, exactly ONE true character error (a doubled degree sign standing in for a minutes prime — this session added a targeted, unit-tested repair for exactly that pattern) plus two harmless word slips ("arc"→"are", "to a"→"toa" — also repaired). His real scan is CLEANER than either synthetic case above, which is the expected shape for a direct scan of a stamped recorded instrument (vs. this fixture's simulated repeated-photocopy degradation).
- **A real, unrelated bug found and fixed along the way (the owner's own item (3) audit ask):** the construct-coverage fixture (`test/deedRealDeedAudit.test.js`) proved `deedParse.js` — the SAME parser every non-OCR path already uses — correctly handles curves, passing-at/total-distance, offset notes, tie calls, and SAVE AND EXCEPT tracts, closing to sub-foot tolerance; a SAVE AND EXCEPT tract's LABEL (cosmetic only) was picking up the wrong acreage figure and was fixed.
- **A real defect this session found in ITS OWN first draft, worth recording so it isn't rediscovered:** the first OCR pass fed Tesseract's raw multi-line text straight to `deedParse.js` and a wrapped curve clause silently split into unparseable fragments (0/6 recovered, misclosure 1,270 ft) — NOT an OCR quality problem, a missing reflow step (the same wrapped-line rejoin `pdfText.js` already does for a text-layer PDF, extracted to `deedTextReflow.js` and reused). Fixed and reverified before this V### was written; left here as the concrete instance of "don't blame OCR for a parsing gap" the owner asked to guard against.
**What is NOT proven here.** The owner's actual PDF was not available to this session (he described it; the file itself isn't attached) — this is the closest a sandbox can get without it. Signed-in behavior (does the OCR'd + user-edited text survive a save/reload like any other deed queue row) rides the SAME `deedQueue`/`mbText` state every other deed-file path already uses and wasn't re-tested separately. The page-picker UI (for a 20-page boilerplate-heavy deed) and the low-confidence highlight overlay were unit- and component-level tested but not eyeballed in a real signed-in click-through.
- Blocker: real-data — closing this fully needs either the owner's actual PDF or a live click-through on planyr.io with a real scanned deed.
