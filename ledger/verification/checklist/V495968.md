That table has **not been applied to production** — this session's production access was read-only/SELECT-only, so the migration file was handed to the owner rather than run. This is the **exact same shape** V480816 above uses for its own cloud round-trip, and the same reasoning: local behaviour is fully proven in sandbox; the network round trip through real Supabase, on a real account, cannot be.

**What was verified here, extensively, without a real signed-in pass:** the guarded-write code itself is UNCHANGED from what `doc_reviews`/`sites` already use in production (no new concurrency logic was written — see `modelStore.js`'s header), so its correctness is inherited from those tables' own live history, not re-argued from scratch; the local-only path (read/write/reload) is proven in `e2e/model-spreadsheet.spec.js`; the SQL itself mirrors `doc_reviews.sql` byte-for-shape (same RLS policies, same `(user_id, id)` primary key, same `version` column) and was reviewed, not merely written.
