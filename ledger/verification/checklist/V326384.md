### V326384 — B851 (×2): the schedule grid no longer diverges from the route, and the false "newer version" reload banner stops firing from browsing projects `Blocker: real-data` `Blocker: auth`
**What was verified here — root cause reproduced by simulation, fix mutation-proven, not just plausible.** The recurrence (route "Goose Creek", grid showing Grand Port's tasks, plus a false "a newer version was saved on another device" reload prompt) traces to `public/sequence/index.html`'s `window.storage.set()` having no serialization: every `data` change fires an un-debounced `attemptCloudSave`, and the Scheduler's carry-in effect posts a real project-switch into the always-kept-alive Scheduler iframe on every app-wide routed-project change (even while Schedule isn't the visible tab, by design — B1342). Browsing a few Site Planner projects before landing on Schedule can put two or more real saves to `hs-v1` in flight at once; the optimistic-concurrency guard (`cloudRev > knownRev[k]`) is a plain read-then-write check with no server-side compare-and-swap, so overlapping same-tab saves that complete OUT OF ORDER let the LAST one to finish win outright, even when it was issued first and is now stale — with no conflict ever detected. A forced-ordering simulation using the REAL Layer-0 guard logic and the real `mergeCloudDoc` (the verbatim mirror already in `ui-audit/stress/scheduler-engine.mjs`) reproduced this: 2 of 3 realistic network-timing interleavings silently clobbered the correct value. The fix serializes `window.storage.set()` per key (coalescing adjacent AUTO saves, never coalescing an explicit checkpoint save); the same simulation converges correctly in all 3 interleavings after the fix. `test/schedulerSaveQueue.test.js` (8 tests, new) extracts the real queue wrapper from the shipped file (drift-proof) and proves both the pre-fix reproduction and the post-fix convergence.
