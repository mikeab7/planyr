### V408192 — B742369: at real browser page zoom (Ctrl+/Ctrl−), a footprint corner drag still tracks the cursor 1:1
**What was verified here — the pointer→world transform audited and found to carry no zoom/devicePixelRatio term, and the DAMAGE this class of bug can do closed and proven regardless of the answer.** `p2f`/`screenToWorld` (`shared/viewport/viewportTransform.js`) is `world = (screen − t) / scale`, fed only by `MouseEvent.clientX/clientY` and `Element.getBoundingClientRect()` — both defined by the CSSOM View spec in the same "visual CSS pixel" space at any zoom level, so a uniform page zoom scales both together and their difference is invariant by construction; a repo-wide search of the drag path found no `devicePixelRatio`/`movementX`/`movementY` reference anywhere in it. Separately, and independent of that question: the self-crossing/degenerate guard that used to run only at pointer-up now runs on every drag frame, so an oversized pointer delta — whatever its cause — can no longer write an invalid polygon to state at all; it holds the vertex at the last valid position and warns. That half is proven live, headless, this session (`ui-audit/verify-b872-round2.mjs`, 4/4 checks).
**What is NOT proven, and why it parks here rather than closing on the audit alone:** whether the specific production observation — a corner drag overshooting ~5× at ~160% browser zoom — was actually CAUSED by zoom, or by something else that happened to coincide with it. This sandbox cannot drive Chrome's real Ctrl+/Ctrl− page zoom, which changes `window.devicePixelRatio` proportionally; the one proxy tried (`document.body.style.zoom`) was confirmed NOT equivalent — it changes `getBoundingClientRect()` numbers but leaves `devicePixelRatio` and `visualViewport.scale` at 1, unlike real page zoom. So the audit is strong evidence against zoom being the cause, not a live-machine proof.
**Steps, each with a named expected result:**
1. On a real machine (not this sandbox), open any plan and set the browser's page zoom (Ctrl+ / Ctrl− on Windows/Linux, ⌘+ / ⌘− on Mac) to roughly 150–175%. **Expect:** the app still renders and is usable at this zoom (a baseline sanity check, not the point of the test).
2. Select a building, "✎ Edit footprint (reshape)" (or via the right-click menu), and drag one corner a modest, ordinary distance — a few inches of mouse travel, nothing extreme. **Expect:** the corner tracks the cursor 1:1, the same feel as at 100% zoom — NOT a multi-times overshoot.
3. Repeat step 2 at 100% zoom on the same building for a direct comparison. **Expect:** identical tracking behavior between the two zoom levels.
4. If step 2 DOES still overshoot: note the exact zoom %, OS, browser, and whether a HiDPI/Retina display is involved, and file a fresh, narrower repro — but confirm first that the corner still refuses to cross the outline and holds with a "⚠ Reshape held…" toast rather than corrupting the saved plan (the fix this item shipped). A live failure of step 2 downgrades this from a data-integrity bug back to an input-tracking one; it does not reopen the data-integrity question, which the frame-by-frame guard closes independent of root cause.
**Result:** ⏳ pending — needs a real machine with real browser page zoom, which this sandbox cannot faithfully emulate.
