- **❌ What the live run found (Cowork, 2026-07-03):** on the live signed-in map, **3 independent Fort Bend clicks all showed the amber "Statewide backup — Fort Bend county's server is unavailable; shown from TxGIO" notice** — including a plain residential rooftop. Decisive evidence it was a code bug, not FBCAD being down: a direct in-page `fetch()` of the FBCAD Esri endpoint for the exact clicked point returned **HTTP 200, featureCount = 1** with the full FBCAD schema, and the network tab showed **the app itself calling that same FBCAD URL and getting 200 on every click** — so FBCAD's primary was up and answering, yet the app labeled it unavailable.
- **🔧 Root cause (B630) — NOT the circuit breaker (the live report's hypothesis was close but off).** The breaker correctly ignores "200 + 0 features" (B245), and it was CLOSED (FBCAD was being queried, per the 200s). The real culprit: the click path (`identifyParcelEager`) races the county CAD and the statewide TxGIO layer **in parallel and takes the first to answer** — and FBCAD's Esri layer is a hair slower than TxGIO's identify, so **TxGIO kept WINNING THE RACE**. The old `viaBackup = STATEWIDE_KEYS.includes(hit.county) && realPrimaries.length > 0` then read "the statewide source answered" as "the county server is down" — a false alarm on every healthy click.
- **✅ Fix shipped (B630, this branch):** new pure `isStatewideBackup()` in `lib/sourceHealth.js` — a statewide answer is flagged a "backup" **only when the county's own CAD was genuinely unavailable this click** (its breaker was open → it was dropped from the query), never when a healthy CAD was queried but merely lost the parallel race. Wired into both the map-click (`handleClick`) and the search-select (`selectParcelAt`) paths in `MapFinder.jsx`. Proven here: lint 0 · full suite **2281 green** (incl. 6 new B630 cases: race-lost ⇒ no notice, breaker-open ⇒ real backup, statewide-only area, border straddle) · build green.
- **🔧 Follow-on fix (B643, this branch) — the eager RACE itself, so FBCAD's OWN data shows (V194 step 3):** B630 made the *notice* honest, but TxGIO still won the parallel race, so a Fort Bend click could select TxGIO's coarser copy (missing FBCAD's appraisal values). B643 tags identify candidates with `statewide` and has `identifyParcelEager` (`lib/arcgis.js`) **prefer a healthy real CAD** — a real-CAD hit resolves immediately; a statewide hit waits a bounded ~1.2s `BACKUP_GRACE_MS` for an in-flight CAD before being accepted — so a healthy FBCAD wins the race and its own parcel/appraisal data shows, while a genuinely-hung CAD still can't stall the click past the grace (the B244 eager guarantee holds). With the CAD winning, `hit.county` is the CAD (not statewide), so `isStatewideBackup` is doubly false. Proven here: lint 0 · **2429 tests green** (post `origin/main` merge; incl. my 3 new eager-preference/grace cases in `test/arcgis.test.js`) · build green. If a healthy FBCAD still loses the race in the field, the grace is a one-line tune.
