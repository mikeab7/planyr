**What was verified here, without a signed-in browser.** The four new pure functions (`coreChanged`, `stripViewState`, `persistViewState`, `resolveViewState`) were extracted directly from the shipped `public/sequence/index.html` (never a reimplementation) and exercised against the EXACT production repro: a simulated sequence of `aPid` switches (2→3→1→3) with the rest of the document held at identical object references, matching how the real `setData` updaters build their result — `coreChanged` reports `false` at every step, meaning `attemptCloudSave` (and therefore a `__rev` bump) would not fire for any of them; a genuine task/settings edit in the same harness correctly reports `true`. `stripViewState` was proven to remove exactly the 13 keys measured on the real production row (`jsonb_object_keys`) and nothing else, confirmed against a doc shaped like the real one (`projects`/`nPid`/`nTid`/`settings`/`__rev`/`_v6`–`_v8` present and untouched). `resolveViewState` was proven to migrate a doc's baked-in values into `sessionStorage`/`localStorage` on a synthetic "first load," to prefer already-saved tab/browser state over a freshly-imported/restored doc's stale snapshot on a synthetic "later load," to never resurrect `editProjId`, and to never return an `aPid` that doesn't resolve to a real project even when the saved one is stale/deleted. Source-guard checks confirm `attemptCloudSave` and all four explicit checkpoint saves (`pre-restore`/`pre-delete-project`/`pre-import`/`pre-recascade`) actually call `stripViewState` before writing, and that the main data-change effect actually gates `attemptCloudSave` on `coreChanged`'s result rather than firing unconditionally. `node ui-audit/verify-sequence.mjs` (a real, unmocked Chromium session against the built app) was run before and after this change and produced byte-identical output — 0 real console/page errors either way — so this diff introduces no observable runtime regression to the embedded app's boot path; its pre-existing "RENDERED: false" is this sandbox's CDN egress block (reproduces identically on unmodified `main`), not something this change caused.
