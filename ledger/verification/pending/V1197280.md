### V1197280 — B1675104: two signed-in windows editing different paragraphs of the same note merge silently; the same paragraph still asks `Blocker: auth`

**Why this needs a live pass, and what it is NOT.** This is not asking anyone to re-diagnose whether the merge algorithm is correct — that half is fully proven in sandbox: two real `notesStore` module instances (not mocks) talking to an in-memory fake server that enforces the exact same `rev`-guard the production trigger does (`test/notesTwoClientConflict.test.js`'s new "the per-paragraph merge (NEW-1)" describe block, 2 tests), plus 16 pure-function cases covering independent edits, same-block conflicts, delete-vs-edit, indent-only edits, and a real toggle's open/closed state (`test/notesBlockMerge.test.js`). What sandbox genuinely cannot reach: the actual cloud sync engine (`notesCloud.js`'s `judgeConflict`/`settleQuietly`/`resolveDivergence`) only runs for a SIGNED-IN account — a signed-out (`local` scope) two-tab test cannot exercise this feature at all, since there is no server round-trip to diverge against. Signing in is CORS-blocked in this sandbox (the same wall every other `Blocker: auth` item on this list names).

**What was verified here (sandbox).** The RED-PROOF: `judgeConflict` (unchanged) calls two independently-edited paragraphs "diverged" — the pre-existing whole-document banner, with no way to land both edits — and `mergeNoteDocs` resolves the identical three documents with both edits present and nothing flagged. The two-client test drives the real `seed()`/`pushPending()`/`resolveDivergence()` code path end to end: window A edits paragraph 1, window B edits paragraph 3, both push, B's push is refused (server moved), and B's copy silently gains BOTH edits with `notesConflicts()` reading `[]` throughout — then a further sync converges A onto the identical merged document. A second case proves the safety net: both windows touch the SAME paragraph differently (plus each also makes an independent, non-conflicting edit elsewhere) — a real conflict IS still raised, `resolveNotesConflict("theirs")` still resolves it exactly as before, and neither candidate is missing the other side's non-conflicting edit. A pre-merge snapshot is confirmed to land in Version History (`reason: "before-merge"`) in the clean-merge case.

**Steps, each with a named expected result:**
1. On a Cowork session (or Michael himself) with real signed-in access, open the same note in two browser windows/tabs of the same account (or two devices). **Expect:** both windows show the note; no conflict banner yet.
2. In window A, edit one paragraph (e.g. the first) and wait for "Synced" in the footer. In window B — WITHOUT having refreshed since step 1 — edit a DIFFERENT paragraph (e.g. a paragraph well below A's) and wait for a sync attempt (switch tabs, wait ~60s, or trigger a manual sync if one exists). **Expect:** window B's edit lands with NO conflict banner appearing, and reloading window B shows BOTH edits present in the one document.
3. Reload window A. **Expect:** window A now also shows both edits, converged with window B.
4. Repeat steps 1–2 but have BOTH windows edit the SAME paragraph, each to different text. **Expect:** this time the existing "also changed in another window" notice DOES appear in the window that synced second, and Review shows only that one paragraph in dispute (not the whole document) — any OTHER paragraph either window separately edited in the same test should already be present in BOTH the "keep mine" and "keep theirs" choices shown by Review.
5. Pick either choice in step 4's Review screen. **Expect:** the note updates to the picked version, the banner clears, and Version History (the toolbar's History control) shows a row for the copy that was NOT picked, reachable and restorable.
- Stopping rule: closes when steps 2–3 confirm a genuine silent merge on real signed-in accounts, AND step 4–5 confirm the same-paragraph case still asks and still resolves non-destructively. A step that fails is filed as its own bug referencing this item and `notesBlockMerge.js`, not folded back into this item's own text.
