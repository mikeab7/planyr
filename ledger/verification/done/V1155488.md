### V1155488 — B1626528: `sites_enforce_version_monotonic` refuses a stale/unconditional write to `public.sites` and cannot be reached by a well-behaved CAS write

**Why this is a database-level check, not a browser one, stated precisely.** The defect and its fix live entirely in the schema — a BEFORE UPDATE trigger comparing `old.version`/`new.version` — with no UI surface: the CLIENT side of this (the conditional `WHERE version=expected` write) was already built and already working (`shared/cloud/optimisticUpsert.js`, B314/B672), so there is nothing new to click through in the app. The only thing that can actually prove a database trigger works is the database, driven directly, which is what this record is.

**Method.** Every step below ran against `planyr_production` (Supabase project `lyeqzkuiwngunutlkkmi`) via the Supabase MCP tools available in this session, inside `BEGIN; … ROLLBACK;` transactions on throwaway ids (`repro_new1_*`, `zzvmg-*`) that borrowed an existing user's `user_id` only to satisfy the row's own constraints — no existing row was read for its content, written to, or left modified; confirmed after every run with `select count(*) from public.sites where id like 'zzvmg-%' or id like 'repro_new1_%'` → **0**, and the same for `public.client_errors` telemetry rows.

**1. Reproduced the bug live, before any fix, on the unmodified pre-fix schema.**
```
0 initial insert                                            version=1  els=3
1 window A draws something — a real, WHERE-guarded CAS save  version=2  els=4  (1 row matched)
2 window B is stale, sends the SAME well-behaved CAS shape   version=2  els=4  (0 rows matched — correctly refused)
3 window B / an old bundle sends an UNCONDITIONAL update     version=1  els=3  (1 row matched — THE BUG)
```
Step 2 proves the client-side conditional filter already works when both sides honor it. Step 3 proves it buys nothing against a writer that doesn't: the counter moved backwards (2→1) and window A's 4th element vanished.

**2. Shipped `db/sites_version_monotonic_guard.sql`** (`sites_enforce_version_monotonic`, a BEFORE UPDATE trigger requiring a content-changing write to carry a strictly-greater `version`) via `mcp__Supabase__apply_migration`, and re-ran the identical step 3 write: **0 rows matched, version/els stayed at 2/4 — the exploit is now refused.** Re-ran a legitimate CAS save (step 1's shape) on a fresh row: **still succeeds.** Re-ran a soft delete then a restore (`deleted_at` only, no version bump — the path `cloudDelete`/`cloudRestore` depend on): **both still succeed, unbumped.** Confirmed exactly one `public.client_errors` row (`event:version-guard-refused`) logged for the refused write (LOUD-FAILURE).

**3. Ran the formal, repo-committed test, `db/test/sites_version_monotonic_guard.test.sql`, against the shipped trigger — self-rolling-back, 10 cases: ALL 10 PASSED.**

**4. Mutation-proved it.** `DROP TRIGGER sites_enforce_version_monotonic ON public.sites;`, re-ran the identical test file: **5 of 10 FAILED — exactly cases 2 (the exploit), 3 (the production "44→43" shape), 4 (an equal/non-advancing version), 5 (LOUD-FAILURE — nothing was logged, because nothing was refused) and 6 (a site-column-only stale write).** Cases 0 (known-good arm), 1 (well-behaved CAS), 7 (soft delete), 8 (restore) and 9 (a version jump of more than 1) **stayed green** — the guard's absence breaks only what it exists to guard, nothing else. Recreated the trigger via `apply_migration` and re-ran: **ALL 10 PASSED again.**

**5. Confirmed trigger ordering.** `select tgname from pg_trigger where tgrelid='public.sites'::regclass and not tgisinternal order by tgname` — `sites_enforce_version_monotonic` sorts first among the table's BEFORE UPDATE set (ahead of `sites_normalize_county`, `sites_preserve_rename_stamp`, `sites_team_share_guard`), matching the file's own stated design (it evaluates the caller's proposed `new.data`/`new.site`/`new.version` before any sibling trigger's own narrow correction can run).

**What this does NOT cover, said plainly:** the client's own reconcile-and-retry-once behavior on a genuine CAS conflict (B672's architecture) is unchanged by this item and was not re-verified here — it predates this fix and is out of scope; nothing in this item's own analysis found it interacting with the new trigger (a well-behaved CAS write's matched `old.version` is always exactly `expected`, so `new.version = expected+1 > old.version` holds by construction — the refuse branch is unreachable from that path). NEW-2 (the four other tables with no `version` column at all) is untouched, filed as a separate dispatch.
