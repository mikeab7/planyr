- **WHAT IT DOES.** When the flag is on and the plan's county has a baked archive, the FEMA row renders from `public/flood/flood-<state>-<county>.pmtiles` — range-read off the same Cloudflare Pages origin that already serves the app — instead of calling FEMA's `/export` on every pan and zoom. **Same panel row, not a second one:** a second row would double-paint and would ask the owner a question about our plumbing.
- **⛔ THE FAIL-SOFT GUARANTEE IS THE LOAD-BEARING PART, AND IT IS A PROPERTY OF A PURE FUNCTION.** `floodTiles.resolveFloodSource` answers `live` for EVERY way the fast path can be unavailable — flag off · no county on the plan · county with no archive · an archive that failed earlier this session · called with nothing at all — each with a stated `reason` on the status channel. The runtime half is one terminal `_die()` in the layer: a 404 or an unparsable header disarms it ONCE, tears the slot down through `layers.js`'s existing shared `release` helper, and re-enters `syncOverlayLayers`, which then takes the raster branch exactly as it does today. A per-TILE miss is deliberately NOT that — most of a county has no polygon in it, and an empty tile is the ordinary case.
- **⛔ PARCEL-SCALE AUTHORITY IS UNCHANGED, AND THAT LINE DOES NOT MOVE.** A tile is generalised — simplified per zoom, quantised to a tile grid — so it is the right source for the FAST PICTURE and the wrong source for any number a user acts on. The screening / mitigation math still queries live FEMA; every tile identify card carries *"the parcel's authoritative zone and acreage still come from the live FEMA query."* Fast picture from tiles, exact number from FEMA.
- **⛔ AND THE ABSENCE RULE IS NOT THE SAME ON BOTH SOURCES, which is a trap worth naming.** The build DROPS unshaded Zone X, so on tiles "no polygon here" means **outside the mapped floodplain** — a real finding. On the LIVE layer it means **no effective flood map at this point** (the honest gap `layers.js` opts into with `identifyGap: "flood"`), which is the opposite risk position. `floodAbsenceKindFor(source)` is the one place that decides which wording applies; showing the live layer's absence wording over a tile answer would turn a clean result into a scare.
- **BUNDLE, MEASURED RATHER THAN ASSUMED.** The vector-tile stack (`pmtiles` + `@mapbox/vector-tile` + `pbf`) is reached ONLY by a dynamic `import()` at layer-switch-on, so it lands in its own **38.1 KB** chunk (`floodTileLayer-*.js`) and no visitor downloads it unless the flag is on AND their county has an archive. The site route pays **+5.0 KB** for the pure decision / manifest / normaliser code — measured by running the bundle audit against this branch's base with the tree stashed (site route 2387.1 KB → 2392.1 KB; largest chunk 1495.3 → 1499.6 KB). The four "above baseline" warnings the audit prints are inherited from main and reproduce identically on the stashed build.
- **⛔ WHAT IS DELIBERATELY NOT WIRED, so it is not read as an oversight.** The **map finder** stays on live FEMA: it has no plan county, and the county under the viewport changes on every pan, which would rebuild the layer mid-gesture. Phase 2 can pass `countyForView` if the fast path is wanted there; the fail-soft path makes that a one-line change with no new risk.

The full harness is `ui-audit/verify-flood-tiles.mjs`.
- **⛔ THE PLAN'S CENTRAL MECHANISM WAS REFUTED BY MEASUREMENT AFTER THIS PR OPENED, AND THE FIX IS IN THE SAME BRANCH: CLOUDFLARE PAGES DOES NOT DO HTTP BYTE SERVING.** The brief's design is *"read by the browser with HTTP range requests."* Measured against a REAL Pages deployment of this branch (`claude-planyr-floodplain-pha.planyr.pages.dev`, `server: cloudflare`, `cf-ray` present): a ranged GET returns **`HTTP 200` with `content-length: 6246238`, no `accept-ranges`, no `content-range`.** Repeated (not a cold-cache artifact) and reproduced on the 665 KB Adams archive, on `manifest.json`, and on a plain `/assets/index-*.js` — so it is a property of the HOST, not of these files. **The control rules out the sandbox's egress proxy:** the identical ranged request through the same proxy returns `206` + `content-range` from `raw.githubusercontent.com` and `registry.npmjs.org`.
- **⛔ AND IT WOULD HAVE SHIPPED GREEN.** `pmtiles`' own `FetchSource` REFUSES a 200-with-full-body — *"Server returned no content-length header or content-length exceeding request. Check that your storage backend supports HTTP Byte Serving."* — so the layer would have thrown on its FIRST read in production and fallen back to live FEMA, permanently and silently. Nothing here would have caught it: **the Vite dev server DOES honour Range** (verified: 206, 127 bytes), so `verify-flood-tiles` 10/10, every unit test and every local run stay green over a feature that cannot work where it ships. That is the "green on a build that cannot work" class this repo keeps naming, and it was found only because the Cloudflare preview URL made a real host reachable.
- **THE FIX — ADAPTIVE, NOT A SWAP** (`lib/floodArchiveSource.js`). The first read asks for a range like any other client: a **206** keeps the cheap path (a few KB per tile, nothing held); a **200 with the whole body** means the host ignored the range, so that body is KEPT and every later read is a memory slice — the archive is fetched exactly **once**. No host detection, no configuration, a future Cloudflare that enables byte serving is picked up for free, and the dev server keeps its ranged path. Concurrent cold-viewport reads are deduped, so N tiles do not become N whole-file downloads.
- **⛔ AND THE WHOLE-FILE PATH IS NOT A CONSOLATION PRIZE AT THIS SIZE.** The largest archive is 5.96 MiB and measured **0.65 s** to fetch complete from Pages; after that every tile in the county is a memory slice with zero network, and static assets on Pages are **unmetered**. What it costs is one held ArrayBuffer per open county (dropped by `forgetArchive`) and a slower FIRST paint on a cold cache — which is why `public/_headers` now gives `/flood/*` `max-age=3600, stale-while-revalidate=86400`, and gives the MANIFEST the same policy so a refreshed vintage can never appear over stale tiles.
- **✅ AND THE FIX IS PROVEN ON THE REAL HOST, not only in a simulation of it.** The shipped reader was driven from Node against the live Cloudflare Pages deployment of this branch: **Harris — header + 5 z13 tiles decoded (38 / 70 / 19 / 60 / 52 features) in ONE request, 5.96 MiB, 1,094 ms total**; **Waller — 1 request, 0.69 MiB, 231 ms.** That is the same code path the browser takes, against the same host the app is served from, so the whole-file behaviour is measured end to end rather than inferred from the header dump that found it.
- **GUARD.** `test/floodArchiveSource.test.js` (9) drives the REAL committed Harris archive through BOTH measured host behaviours and requires them to decode the **same tile, feature for feature** — plus: exactly one whole-file fetch however many tiles are read · the held buffer is released · a short read and an error status both throw LOUDLY rather than feeding an error page to the tile decoder · three concurrent cold reads produce ONE request.
- **⛔ THE GAP, STATED PLAINLY — this is why the item parks.** Every `hazards.fema.gov` request **from Chromium** in this sandbox dies with `ERR_CONNECTION_RESET` (Node reaches the same host fine — that is how the archives were built). So the harness can prove the live path is ENGAGED and can NEVER prove it PAINTS, which means the tiles-vs-live first-paint comparison — the number the owner actually asked for — has no live half here. The harness DETECTS the block and says so rather than reporting the sandbox's egress policy as a defect in the app. V96960 owns the remaining steps.
