- **WHERE THE ~24 ms/call actually went, profiled in Node against the real 8-tile cover B800848 measured:** `joinSeams`'s per-level seam-stitch is ~90% of `composeContourPaint`'s own cost, and within it the dominant waste was `rank(ln)` (the canonical-order sort key, needed so a saddle where 3+ endpoints meet resolves the same way regardless of tile-arrival order) being rebuilt from scratch on EVERY comparator call inside `.sort()` — an O(n log n) quantity of string builds for a value that only needs to exist once per item. `pickLabels`'s `id(l)` has the identical shape at smaller scale.
- **THE FIX — precompute each item's sort key once (a Schwartzian transform), and fuse the seam-stitch lookup-and-match into one pass instead of collecting a `hits` array first.** `joinSeams`/`pickLabels` in `contours.js` now build `[key, item]` pairs once, sort by the cached key, and drop the key — mathematically the identical total order to recomputing on every comparison, since both approaches compare the exact same key values pairwise. The seam-stitch `near()`+scan (which built an array of every candidate across the 9 neighboring buckets, then scanned it) is now one `findMatch()` that returns the first usable candidate directly, in the same dx/dy and bucket-insertion order, without ever allocating the intermediate array.
- **⛔ CONSTRAINT HONORED — byte-identical output, proven directly, not just implied.** `test/terrainLattice.test.js` gained a new describe block: `joinSeamsReference`/`pickLabelsReference`/`composeContourPaintReference` are LITERAL copies of the pre-fix algorithm (same re-derive-in-comparator pattern, same collect-then-scan seam search), run against the real captured tile spread over a NEW 8-tile grid (more seams/junctions than the 2-tile fixture elsewhere in the file, to stress saddle-point ties) and compared field-for-field to the shipped functions — `lines`, `labels`, and `joinSeams`/`pickLabels` individually per level all match exactly. Every pre-existing test in the file (order-independence, no re-roll, seam-joined halves, B800848's incremental-diff guarantees) still passes unmodified — `composeContourPaint`'s callers see no behavior change, only its own internal cost changed. Same guarantee, same method B800848 used ("prove byte-identical, or say exactly what changed"), applied to a change that — unlike B800848's — does touch the pure engine's internals.
- **MEASURED — Node microbenchmark, real captured DEM data, median of 50 calls:** `composeContourPaint` over a real 8-tile cover (888 composed lines, 128 raw labels) went **4.02 ms/call → 2.12 ms/call, a 47% reduction** — from removing algorithmic waste alone, no caching, no incremental recomposition, no change to what is computed.
- **BROWSER-LEVEL BEFORE/AFTER — same harness, same method as B800848 (two real builds, CDP `Performance.getMetrics`, median of 14 pan steps) — and a harness defect found and fixed along the way (see below).** With `ui-audit/diagnose-contour-pan-perf.mjs`'s served fixture corrected to the tile's real requested size, a real 14-step continuous pan at zoom 18: **before 78.0 ms/step → after 74.8 ms/step, a further −4.1%** on top of B800848's own −3.5%. **Reported honestly, not rounded up:** this is smaller than the 47% per-call reduction because at this harness's step size, `composeContourPaint` only re-runs on the steps where the lattice tile SET actually changes (4 of the 14 measured steps — `terrainLayers.js`'s `refresh()` correctly bails out before calling it at all when the tile set is unchanged, which is itself correct, desired behavior and not a gap this item should touch). A real mouse-driven pan crossing more tile boundaries per second than this synthetic step would fire the per-call saving more often; this harness's own honest number is what's reported, not an extrapolation.
- **⛔ HARNESS DEFECT FOUND AND FIXED, LOUDLY, because it silently invalidated the very measurement this item exists to produce.** `ui-audit/diagnose-contour-pan-perf.mjs` served the SAME 463×400 fixture (`test/fixtures/dep-katy-463x400.lerc`, sized for the unrelated Node-level unit tests, which build their own matching `req`) for every `exportImage` request — but a real lattice tile always requests `TILE_CELLS + 2*MARGIN_CELLS` = 528×528 px, and `decodeGrid()` in `lercGrid.js` correctly, loudly refuses a size mismatch (`grid size mismatch: got 463x400, asked 528x528` — the right LOUD-FAILURE behavior; a silently-resized export would georeference wrong everywhere). So EVERY tile fetch in the harness rejected at decode time, on both builds, in both this item's run and B800848's own: `composeContourPaint` was never actually called with real geometry, and B800848's reported "1 label at rest" was a stray `.leaflet-marker-icon` from something else on the map, not a contour label — the harness was silently timing a layer that fails to paint. **This is also the root cause of B800850**, filed the same session as a suspected re-fetch bug — see that item, now refuted, for the full trace. Fixed with a new, correctly-sized, still-100%-real fixture: `test/fixtures/dep-katy-528x528.lerc` (the same real captured USGS 3DEP elevation values from the original fixture, edge-padded out to 528×528 with real data extended flat at the margins — never fabricated noise — and re-encoded with Esri's `lerc` codec at the oldest codec sub-version the app's JS `lerc` reader can parse; `scripts/gen-terrain-pan-fixture.py` regenerates and self-verifies it). With the fix the harness genuinely paints (37 labels at rest, real geometry, zero decode rejections).
