- **THE CORRECTION, which is the whole item.** B1205/B1206 shipped saying per-layer OPACITY was "the one escape hatch" in the fixed stacking model. That is false for the case it was offered for: **opacity cannot fix OCCLUSION for a layer that draws UNDER the site elements.** Turning a buried floodplain fill down changes nothing on screen — the building still covers it, and all the slider does is fade the parts that were already visible. Opacity only helps a layer that is already ON TOP and too loud. **Occlusion order can only be fixed by order.**
- **⛔ THE DEFAULT IS UNTOUCHED, deliberately, and that is asserted rather than assumed.** Area fills still draw under the elements and line/point layers still draw over them, so the owner's ORIGINAL complaint — contours vanishing behind his buildings — still needs **zero interaction**. A toggle you never have to touch beats a toggle you always have to touch, so the lift is opt-in and defaults OFF on every layer. `test/layerAbovePlan.test.js` fails the build if any registered layer ever defaults to lifted.
- **Shipped: a two-state, semantically-named control on every toggleable row — "Show above plan".** One `abovePlanControl` implementation and ONE `aboveRow` call site driving all three row shapes (solo · the pairwise City-limits & ETJ composite · the N-ary merge groups), which is the B1206 discipline applied to the new control. It is **not** a free-form z-order picker: no front/back, no up/down, no per-layer number. Planner surface only — the map finder has no plan for a layer to be above.
- **The already-on state is SHOWN, not hidden — and this was the one open question on the item.** A line or symbol layer is over the plan already, so the control has nothing to do on that row. It renders **checked and inert**, with a hover saying why. Chosen over hiding it because **an absent control cannot be told apart from a control that was not offered**: the user would have to interpret the row's silence ("already above?" vs "this layer can't?"), and being able to READ where a layer sits is the point of adding the control at all. It also teaches the fixed model, which is what makes the default comprehensible. One place, one meaning, on every row.
- **WHERE THE LIFT STOPS, and the architectural decision that cost the most.** A lifted layer clears the site elements and stops **below the labels/chips and below B1197's always-on-top handle layer**. The cheap implementation — drop the lifted pane into the map-top host beside B1205's line band — is one line, and it was **refused**: that host sits above the whole plan SVG, so it would have inherited **B1208**'s deviation. That deviation is tolerable for a HAIRLINE (a contour may cross a handle but can never make one unreachable) and **intolerable for a FILL** (a floodplain wash over the handle layer hides the grip you are dragging — strictly worse than the occlusion the lift exists to fix). So the lifted band is hosted **inside the plan SVG**, in a screen-space `<foreignObject>` at a new `data-gis-front-band` anchor rendered after the elements and before the labels. **B1208 is neither closed nor widened by this.**
- **The model: `lib/mapStack.js` gains ONE tier, `gisAreaFront` (z 660).** Only an AREA role is liftable, because it is the only role the default puts underneath. A role-SPLIT source (FEMA zone polygons + hazard boundaries) lifts its **fill half only** and leaves its stroke half where it already was — one row, one toggle, still two export requests.
- **The mechanism, and the trap.** Leaflet fixes a layer's pane at CONSTRUCTION — there is no `setPane` — so flipping the toggle is a tear-down-and-re-add, executed in the SAME sync pass so the layer never blinks out. `bandKey` compares the **resolved pane names**, not the flag, which is what lets the map finder collapse both bands onto one pane and rebuild **nothing**. The teardown goes through the ONE `release` helper the toggle-off path already used, so the role-split resurrection trap (releasing only `refs[k]` and leaving the other half's tiles + in-flight request alive) cannot reappear on the new path.
- **VIEWPORT-STABLE.** The in-SVG host is a THIRD mirror of the wrap's gesture transform, written in the same statement as the original (`setWrapTransform`) and in a LAYOUT effect, plus Leaflet's map-pane translate — and it additionally counter-translates the SVG's own registration shift, because a map pane inside the SVG must not be nudged onto the imagery twice. `pointer-events: none` throughout, so it can neither take a click nor steal a handle.
- **PDF-PARITY.** The sheet now composites **three** bands: `under` at the backdrop anchor, `front` **into the plan SVG's own `data-gis-front-band` group**, and `over` after the plan. So a lifted fill prints above the buildings and still under the printed labels — the same place it reads on screen. LOUD-FAILURE if a sheet has no front anchor: the layer prints over the plan **with a named warning**, never silently underneath.
- **Persisted per plan.** A new sparse `layerAbove` map on the site model — the `layerOverrides` twin, its own field so no existing record, merge or undo frame changes meaning — restored on open, saved on toggle, with its own undo signature so a lift is its own undoable frame. Only layers the lift can actually MOVE are stored; a stale or nonsensical key self-prunes.
- **The copy that claimed otherwise is fixed**, in `mapStack.js`, `LayerPanel.jsx` and this folder's `CLAUDE.md`. Opacity keeps its "See through this layer" hover — still true — and no longer claims to answer "I can't see through my plan". A guard test fails the build if the word "escape hatch" reappears in the opacity control.
