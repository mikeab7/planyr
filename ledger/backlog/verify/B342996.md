- **⛔ THE OWNER'S DECISION (×3), VERBATIM, AND IT OVERRULES THE ONE BELOW: *"stamp renames with their OWN timestamp, separate from the edit timestamp… 'Last edited' keeps meaning what it says: the text changed. A rename must not move it, and the label he sees must not change because someone renamed a note."*** He was right and the ×2 argument was wrong: it reasoned that renaming a note IS editing it, which is defensible in the abstract and false on screen — the page header renders `updatedAt` as **Last edited**, so a note nobody had written a word in for months began claiming it was edited today because somebody fixed its title.
- **WHAT SHIPPED FOR IT.** Three independent stamps, each answering exactly one question: `updatedAt` (the TEXT changed — rendered, moved only by `touchPage`), **`renamedAt`** (the TITLE changed) and **`filedAt`** (the PROJECT changed). The last two are never rendered and are read only to settle their own conflict, in `mergeTrees` rule 3. His other constraints, each as a case: **newest rename wins**; **absent is OLDEST, never newest**, so a machine that has never renamed anything cannot win by default; **when NEITHER side has a stamp the old rule stands (local wins) and the code says so.**
- **⛔ AND THE DEFECT THIS FOUND, which was nowhere near the merge and is the reusable lesson.** `migratePageNode` rebuilds every node from a **named field list**, and every read of the tree goes through it. It did not name the two new fields — so they were written correctly, **destroyed on the next read**, and the merge then compared two absent stamps, called it a tie and kept local: **indistinguishable from the old behaviour, in total silence.** Seven cases went red at the merge; the cause was in the reader. A per-node field must be added to `migratePageNode` in the same commit.
- **GUARDS (×3).** Eight new cases in `test/notesTreeWriteThrough.test.js`: a rename does not move Last edited · a re-file does not either · both stamps survive `migrate` · an older node reads back with no stamps rather than zeros · **his test — two clients, one stale, A renames and B pushes an older tree, in BOTH directions** · a machine with no stamp cannot win by default · **and the mutation check he asked for.** Mutation-proven twice against the real source: restoring `updatedAt` stamping turns **8 red**; making an absent stamp read as *newest* turns **9 red**.
- **THE DECISION THE ×2 PASS TOOK, KEPT AS THE RECORD BECAUSE IT WAS OVERRULED.** The filing named a real either/or: stamp renames (which changes what `updatedAt` means) or add a per-field revision. Stamping `updatedAt` was chosen, on the argument that renaming a note IS editing it. See above for why that was wrong.
- **THE MERGE RULE, AMENDED.** `mergeTrees` rule 3 was an unconditional "the local title wins", justified by the merge only running when this device owes an edit. That does not survive contact with a second page: owing an edit on page X says nothing about page Y's name, and even for X the account may hold a NEWER name typed elsewhere since this device last synced. **The name now comes from whichever side was edited LAST**; a tie or a missing stamp still resolves to LOCAL — the conservative answer, because the copy in front of someone is the one they can see is wrong.
- **THE PROJECT BINDING — was open after ×2, closed by B421493 and given its own `filedAt` stamp here.** The 2026-08-10 filing correctly noted rule 3 covers a page's `projectId` too; ×2 left it deliberately unchanged. Where a page SITS — its parent, its order and its project — stays on rule 4 (local placement wins), which the reachability fuzz (`notesReachability`), `notesProjectIntegrity` and `notesTwoClientConflict` are all built around. Recency is the right rule for a VALUE; it is not obviously the right rule for a STRUCTURE, and changing both in one pass is how a merge's hard-won rules get quietly re-litigated. So: re-filing a note on one computer still does not reach the other. That is the remaining work on this number.
- **GUARDS.** Three cases in `test/notesTreeWriteThrough.test.js` — a rename reaching the other computer and not being undone by it; the LATER of two rival renames winning whichever machine typed it; a tie resolving to the copy in front of you. Mutation-proven: restoring "local always wins" turns three red.

- **THE MEASUREMENT.** His LOCAL tree is at rev **812** with `treeDirty: true` while the CLOUD tree is at rev **910**. Local is 98 revisions behind AND owes the cloud a push at the same time.
- **IS THAT STATE REACHABLE? YES, AND LEGITIMATELY.** `sync.treeRev` records the server rev the last completed seed saw; `treeDirty` records that this device has unpushed structural edits. A device that edits while offline — or whose pushes keep losing the guard — sits in exactly this state. It is not corruption.
- **DOES IT "PUSH BACKWARDS"? NO — AND THAT PART IS REFUTED.** With `treeDirty` set, the seed MERGES rather than adopting (`seed()` → `mergeTrees`), and the merge is a union: nothing on the server side is dropped. The push that follows carries the merged tree guarded on the server's own rev. So the structure cannot regress.
- **WHAT IS GENUINELY AT RISK IS THE TITLE.** `mergeTrees` rule 3 says *"for a node on both sides, the LOCAL title wins"* — reasonable when local is a few seconds stale, wrong when it is 98 revisions stale: a rename made on another device is silently reverted by a device that has not caught up. Same for a page's project binding, which rule 3 also covers.
- **WHY IT WAS NOT FIXED IN THE FIRST PASS (2026-08-10), kept as the record.** The obvious repair — take the LATER edit — could not be done with what the model stored: `renameNode` did not stamp `updatedAt` (only body saves did, through `touchPage`), so there was no timestamp to arbitrate a title with. That diagnosis was exactly right, and the decision it was waiting on is taken above.
- **THE HAZARD IT ACTUALLY CAUSED IS ALREADY CLOSED.** The stale-merge condition is what made B342992's two holes reachable in practice; both are fixed and property-tested. This item is the remaining, narrower risk.
