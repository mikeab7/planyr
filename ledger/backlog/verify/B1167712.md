- **(c) Both already exist independently.** A placed, unattached plan gets ONE resolve attempt per overlay per app session, on every reload — "the owner never does anything," but see the correction below for what "attach" now means.
- **⛔ THE MATCH RULE IS NOT THE COMP'S RADIUS — a NEW, plan-specific rule, justified in `overlaySiteMatch.js`'s own header.** A comp is a point; a plan is a drawing that covers area, and a fixed centroid-distance radius calibrated for a point gets WORSE (more false positives) the bigger the plan. The rule instead asks whether an existing site's own recorded point falls **inside the plan's own drawn, placed rectangle** (its real center/scale/rotation — reusing `overlayGeoref.js`'s existing `latLonToImagePoint`, no new projection math), padded by a small **fixed** 300 ft buffer (`SITE_MATCH_BUFFER_FT`) that does NOT scale with the plan's own size — a bigger plan's footprint reaches further because it genuinely covers more ground, never because of a size-scaled fudge factor. Falls back to the same exact normalized-title match `compSiteMatch.js` uses when no site's point falls inside the drawing at all.
- **⛔ NOTHING STICKS SILENTLY.** A resolved/attached plan shows a persistent, always-visible, always-editable **"Site"** dropdown right on the plan itself — reassign it to any other known site, or pick "No site (detached)" to unlink it entirely. Detaching never deletes the plan and never unpins a comp already pinned to it (unchanged `comps_site_plan_overlay_delete_reverts_to_pin.sql` machinery only fires on an actual delete). A new `site_link_declined` column (`site_plan_overlays_site_link.sql`, applied to production) records a deliberate detach so the reload-sweep resolver never re-attaches the SAME plan behind the owner's back — "once he has separated them, they stay separated." A detached (or never-yet-attached) plan is never stranded: the empty "no plan yet" state on any comp's card lists every unattached plan with a one-click "Attach here."
