- **THE HYPOTHESIS, CONFIRMED AGAINST REAL SOURCE, not assumed.** (a) The baseline cannot become available before `baselineSkipMs` (5 s) and typically not before `baselineSkipMs + baselineWindowMs` (50 s) — `perfTrigger.js`'s `feedFrame`: `if (s.baseline === null) { … return false; }` is unconditional. (b) No capture path can fire before that: `feedFrame` returns `false` on every call while `s.baseline === null`, full stop — there is no code path that reaches `fire()` pre-baseline. (c) The frames are NOT lost: `perfRecorder.js`'s `onFrame` calls `pushFrame(_frames, t, dt)` **before** it calls `feedFrame`, unconditionally — so the ring already held boot-window frames whenever the loop ran, merely unjudged. Per (c), the fix is a boot-window judgment path, not new instrumentation — exactly as the hypothesis predicted.
- **THE ADJACENT QUESTION THE BRIEF ASKED FOR, ANSWERED, AND IT WIDENS THE FINDING RATHER THAN NARROWING IT.** "Does the ring even run during boot given the interaction-gated rAF loop" — **yes, this is a second, independent blind spot, confirmed by reading `noteActivity`/`loop`/`schedule`**: the frame loop only starts on a real `pointerdown`/`pointermove`/`wheel`/`keydown`/`touchstart`/`touchmove` event, and a resumed plan can open on a hard reload with **zero** prior interaction at all (`bootResume.js`'s `pickResumeTarget`/`bootActiveId`) — so a genuinely idle boot (the owner watching the screen load without touching anything) recorded **no frames whatsoever**, independent of the baseline issue. Fixed by free-running the frame loop for a bounded window at install (`RECORDER_DEFAULTS.bootRunMs`, 10 s), regardless of interaction — proven live: the headless CONTROL arm below collected 150 frames with the mouse never moving at all.
- **A THIRD BLIND SPOT, FOUND WHILE READING `main.jsx` RATHER THAN ASKED FOR, AND IT IS THE SHARPEST ONE.** `installPerfRecorder` is itself deferred: `if (typeof requestIdleCallback === "function") requestIdleCallback(armRec, { timeout: 9000 }); else setTimeout(armRec, 4500);` — deliberately, so the recorder's own arrival never competes with "the four busy seconds B1431 attributed to the boot." This is an anti-correlation by construction: the busier the boot, the LATER `requestIdleCallback` fires (up to its 9 s timeout), so the sessions most worth observing are the ones the recorder is least likely to have installed for yet. This sounds like it defeats the whole fix — except `observeTasks()`'s `PerformanceObserver` subscribes with `{buffered: true}`, which retroactively delivers every matching long-task/LoAF entry recorded since navigation start, however late the observer itself is created. **Proven, not assumed:** the headless EARLY-BURN arm below burns the main thread from an `addInitScript` — before the page's own first script runs, long before any idle callback could fire — and the resulting boot capture still landed once the recorder eventually installed.
- **THE AUTOMATION-SUPPRESSION QUESTION, ANSWERED DIRECTLY.** `networkReportSuppression` (keyed on `navigator.webdriver`, `clientErrors.js`) gates only the NETWORK SEND — the in-memory ring, `pfTelemetry.recent()` and `window.pfRec.state()`/`captures()` all still work under automation (several existing harnesses assert against exactly those). So it is not "double-blind" for the mechanism itself, but it DOES mean a harness relying on a `client_errors` row landing in Supabase (rather than reading `window.pfRec` directly) would see nothing under Chromium's default `navigator.webdriver === true` — a real, if narrower, contributor to "two harnesses never reproduced it."
- **THE FIX.** `perfTrigger.js` gains `feedBootTask(s, t, dur)` — a boot-only judgment, structurally different from the steady-state test (no self-relative baseline exists yet to compare against), keyed on long-task/LoAF duration: fires once (sharing the SAME `fires`/`cooldownMs`/`maxAuto` budget the steady-state trigger uses) on either one task ≥ `bootSingleTaskMs` (250 ms) or cumulative boot-window task time ≥ `bootTaskBudgetMs` (400 ms), only while `t < bootWindowMs` (10 s, matching the owner's own "5 to 10 seconds") and only pre-baseline. Both bars sit well above B1448's own measured NORMAL 1×-CPU boot cost (195 ms busy total, largest phase 44.8 ms) — a first cut, to revisit once real boot captures start arriving. `perfRecorder.js` wires it into the EXISTING, already-unconditional `observeTasks()` callback (no new listener — "do not ship a second always-on instrument if an existing one can be judged differently," per the brief) and free-runs the frame loop for `bootRunMs` at install so the resulting capture carries real frame deltas rather than an empty "no-frames" track (`noteActivity` also changed to `Math.max` its `_activeUntil` rather than overwrite it, so an early interaction can't cut the free-run short). `perfCapture.js`'s allowlist gains `bootTaskMs`/`bootTaskCount`/`bootTrigger` (fixed vocabulary `""|"single"|"cumulative"`, `BOOT_TRIGGER_VOCAB`) — present only on a boot capture, proven via `assertCaptureClean`.
- **Tests.** `test/perfRecorder.test.js` (+8) — an ordinary boot's short tasks never trip either bar; a single task at the bar fires with `trigger:"single"`; cumulative time crossing the budget fires with `trigger:"cumulative"` even with no single task near the bar; nothing fires past `bootWindowMs`; nothing fires once a baseline has sealed (the two judgments never overlap); the boot judgment shares the steady-state `maxAuto`/cooldown budget; a non-positive/NaN duration is ignored; `bootTrigger` values stay on `BOOT_TRIGGER_VOCAB`.
