- **STRUCTURE, decided and built exactly as specified.** A comp (`public.comps`) is its own entity, owned by the user who entered it — never a project type. `project_id` is a nullable FK to `public.sites`; a comp with no project at all is fully valid and equally visible ("I don't need to build on it to place a lease comp on it"). Every comp a viewer can access (their own + their team's, via `team_id`) is a map candidate regardless of which project it names or whether it names one.
- **ANCHOR: pin drop OR real parcel selection, never a drawn rectangle.** Built by REUSING `MapFinder.jsx`'s existing parcel-select flow rather than a second identify pipeline: the `+ Comp` button arms a small one-shot pin-drop mode (its own `placingCompPin` state/ref, mutually exclusive with `selectMode`); a `Comp here` button rides the EXISTING "+ Select parcels" selection bar, so a parcel anchor is exactly the parcel `selectMode` already resolved (its lon/lat `rings`, snapshotted into `parcel_geom` for the map layer — no re-derivation, no second query). `comps_parcel_anchor_has_identity` is a DB check constraint: a `parcel` anchor with no APN and no geometry is refused at the database, not just the UI.
- **SHARING — narrower than a shared site plan, DELIBERATELY, per the owner's own precedent for why: "that default cost this owner 57 elements off a live plan on 2026-08-21."** `public.comps` RLS composes two EXISTING precedents rather than inventing a third shape: the SELECT half is `team_sharing.sql`'s "own row OR a team you're in" verbatim; UPDATE/DELETE are `profiles.sql`'s plain owner-only shape (`user_id = auth.uid()`), with **no team-admin override** — not even a team admin can edit or delete a teammate's comp. Proven against the REAL production database (`lyeqzkuiwngunutlkkmi`), not just argued: a self-rolling-back RLS proof (`src/shared/comps/db/test/comps_rls.test.sql`) ran live via the Supabase MCP inside a `DO`/`RAISE EXCEPTION` block (nothing committed — confirmed after with a direct row-count read) and reported **9/9 PASS**, including the two negative controls that matter most — a teammate's UPDATE and DELETE against another member's team-shared comp both affect 0 rows.
- **THREE COMP TYPES, empty fields never render.** `compFieldRows(comp)` (`lib/comps.js`) is the ONE place that decision is made — a field with no value is simply absent from the returned row array, never an empty row or an em-dash, and the list, the detail view and (implicitly) the map tooltip all read the same function rather than re-deriving which fields apply per type. LAND's and BUILDING SALE's $/SF headline is DERIVED from price + size (`landPricePerSf`/`buildingPricePerSf`), never entered or stored twice — building SF, not land SF, for the building-sale figure. `comp_date` is the one field the database itself requires on all three (`not null`), matching the brief's "date REQUIRED" stated three times.
- **LEASE BASIS — stored as quoted, normalized only where the math is honest.** `lease_rate_period` (annual/monthly) and `lease_rate_expense` (NNN/gross) are both stored per comp, as quoted. `annualLeaseRate` converts period to annual with EXACT math (×12) and returns `null` — never a guessed default — when the period is unknown, because assuming annual on a comp quoted monthly would silently misstate it 12x in any aggregate. **NNN and gross are never blended into one number**: there is no honest conversion between them without the underlying expense figures this app doesn't have (an op-ex load), so `summarizeLeaseComps` keeps them as SEPARATE averages, defaults the headline to annual NNN (falling back to gross only when no NNN comps exist), and always NAMES the basis it's showing — a comp missing its rate or basis counts toward a reported `unknownCount`, never silently toward either average. This is the honest reading of "normalise to one display basis (annual NNN by default) and state which basis it is showing" — blending NNN and gross into one figure would itself be the "table that silently mixes monthly and annual figures" the brief explicitly ruled out, just on the other axis.
