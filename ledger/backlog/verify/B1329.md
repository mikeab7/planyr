Net-new.)*
`[x]` *(implemented 2026-07-31; parked for a live zoom on a heavy signed-in plan — see **V650**.)* Owner: *"I scroll out, and it takes probably a whole second to scroll out, and it does it in like two scrolls or two zooms."*
- Verify: live — **V650**
- Origin: filed 2026-07-31 from chat (NEW-3)

**(a) THE HARNESS LANDED FIRST, AND IT HAD TO BE CORRECTED TWICE BEFORE IT MEANT ANYTHING.** There was no zoom frame-time instrument anywhere: `perf-harness.mjs` measured a scripted DRAG only, and `zoomout-frames.mjs` measures dark-pixel fraction on a one-element scene. `perf-harness.mjs --gesture wheel` now reports `zoomFrameMedianMs` / `zoomFrameP90Ms` **and a canvas-commit count per wheel event**, reusing `lib/frameSampling.mjs`'s guards unchanged so a hidden tab or a starved sample is refused rather than reported. Commits are counted off the planner's own published `data-view-*` / `data-reg-*` attributes through a `MutationObserver` — no React internals, no instrumented build.
**Both corrections are recorded in the source, because each one produced a confident, wrong number first.** (1) `page.mouse.wheel()` awaits a CDP round-trip per notch and so delivers roughly one event per frame: against that input a coalescing handler and an uncoalesced one are indistinguishable, and the harness duly reported an identical `1.00 commits/wheel` on both builds. (2) Dispatching the burst inside ONE task is equally useless — React 18 auto-batches every `setView` in a single task into a single commit, and four runs per build came back at an identical 16.7 ms median. Real wheel input arrives one event per TASK, and auto-batching does not span tasks. The driver is now a MessageChannel pump: one event per task, five per burst.
**MEASURED, same machine, same build otherwise, three runs each:** canvas commits per wheel event **1.00 / 1.00 / 1.00 → 0.45 / 0.60 / 0.75** (mean 1.00 → 0.60). Frame median is 16.7 ms on both, because the committed stand-in scenario is not render-bound — which is precisely why V650 exists and why no ceiling was recorded off these numbers.

**(b) THE WHEEL IS rAF-COALESCED.** `SitePlanner.jsx`'s wheel handler called `setView` directly, once per raw event, with no rAF and no throttle — while the pointer path (`scheduleFrameJob`/`flushFrameJobs`) and the pinch path (`flushPinch`) both coalesce. The pinch path's own comment calls itself "the other half of the jank"; the wheel WAS that other half. Zoom factors now accumulate in a ref and commit once per animation frame. **The math is unchanged, not approximated:** an anchored zoom about a fixed screen point composes, so f₁ then f₂ about the same anchor is one zoom by f₁·f₂ about it; the latest cursor position is the anchor (which is where the user is pointing by the time the frame paints) and the clamp is applied once at the end. A capture-phase `pointerdown` on the wrapper flushes synchronously, so no gesture starts against a view with a zoom queued behind it.

**(c) THE SECOND RENDER PER VIEW CHANGE IS GONE.** `setRegShift`'s guard used a `1e-4` px epsilon against a continuously-varying sub-pixel residual, so it essentially never held; `regShift` is component state consumed as the SVG's transform, so every zoom AND pan step committed a second full render of the ~4,600-node tree. The epsilon is now `REG_EPS_PX = 0.02` — an order of magnitude below the quarter-pixel placement accuracy `ui-audit/diagnose-pointer-accuracy.mjs` asserts, so the B1141/B1142 weld is untouched. **The bigger win was deliberately NOT taken:** moving `regShift` out of React state and writing both transforms through refs would also move `window.__plannerView.registration()` and the `data-reg-dx/dy` attributes the harnesses read. Ship the epsilon, measure, then decide — do not do both blind.

**B1122'S WELD IS UNTOUCHED.** The basemap transform is still written in the LAYOUT effect, same frame as the SVG, from the same view value. Nothing here moves that write, and `test/panLockInvariant.js` still passes.
