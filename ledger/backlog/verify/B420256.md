- **THE DEFECT.** `site_elements`' primary key is **(site_id, kind, id)** — deliberately, because legacy pre-salt ids are reused verbatim across collections. `elementSync.js` keyed a commit batch's per-op results by **`r.id` alone**, in two places (`processResults` and `onAtomicRollback`), under the comment *"ids are unique within a batch"*. **That comment is false in production.** With two ops for one id in a batch the second `byId.set()` overwrote the first, and every lookup for that id handed one element the OTHER's result — wrong rev, wrong status, silently. Every other lookup in the file goes through `skey(kind, id)`; these two forgot the kind.
- **THE REPRODUCER IS THE OWNER'S OWN DATA.** Site `smqh3au6aeb4` (Katz / Plan 1) holds `e6327` **twice, both LIVE** — kind `el` (a building, rev 2) and kind `markup` (rev 2) — and both rows carry the **identical `updated_at` of 2026-06-29 15:36:02.112**, i.e. they were written by ONE batch, which is exactly the collision condition. Confirmed against production this session. **The plan was NOT touched** and nothing was written to `public.site_elements`: `e6327` under two kinds is legitimate live data and the code must tolerate it (same reasoning as B384432 — make the ambiguity safe, do not destroy it). A sweep of the whole live table finds exactly one such pair, plus the ordinary `tombstone`-beside-a-real-kind pairs the schema has always produced.
- **⛔ THE OBVIOUS FIX IS NOT AVAILABLE, AND SHIPPING IT WOULD HAVE BROKEN EVERY WRITE.** The audit prescribed `skey(r.kind, r.id)`. **There is no `r.kind`.** `commit_elements` builds each result from `v_id` alone (`db/site_elements.sql`): `{id, status, rev}`, plus `row` on a miss. Keying by a field the server never sends misses on **every** op, so every op would fall to the `element-no-result` branch and be requeued forever. What the RPC **does** guarantee is ORDER — it loops over `p_ops` appending exactly one result per op — and `flush()` builds `ops = batch.map(opFor)`, so `results[i]` belongs to `batch[i]`; `elementApi`'s own contract already documents it ("same order as `ops`").
- **THE FIX.** One helper, `pairCommitResults`, used by both settle paths and nothing else. It pairs **positionally** and **VERIFIES** the pairing rather than trusting it: the ids must agree, and so must the kind whenever a returned `row` names one. A response failing that check falls back to a per-id **FIFO** that consumes each result once (preferring one whose row names this op's kind) and reports `element-results-unaligned` (LOUD-FAILURE — a pairing we cannot justify must never look like a clean one). An empty response is unchanged: it still reports `element-no-result` per op and requeues. The false comment is **deleted**, not reworded.
- **PROVEN RED BEFORE THE FIX.** `test/elementResultPairing.test.js` — 7 cases driving the real engine over the Katz collision: **5 failed, 2 passed** on the unfixed code (the two that passed are the deliberate controls — distinct ids, and a missing result — so the test is not simply asserting the new implementation). All 7 green after. The five that were red: a conflict on `el` beside an `ok` on `markup` (and its mirror), a `deleted` result tombstoning the wrong kind, the B1117 atomic rollback adopting the wrong fresh rev, and the out-of-order response.
- **THE SWEEP THE AUDIT ASKED FOR — every other id-alone lookup in the element-row path, and what it is.** These two were the only kindless lookups over the composite key. `elementRows.js`'s `rowsToModel` is already explicitly aware of this class (its comment names *"the legacy e6327 class"*) and subtracts live ids of ANY kind from `deletedIds`; `foldJournal`'s `find`/`filter` by id run **inside `out[field]`**, where the kind is already fixed by the field, so they are correct; `assemblyDigest.js` reasons only over `kind: "el"`. The other `byId` maps in the tree (Library files, Notes sketch boxes, folder rows) key domains whose real identity IS the id. No further change needed.
