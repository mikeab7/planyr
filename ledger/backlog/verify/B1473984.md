### B1473984 — A comp's rate period is never borrowed from another clause `[Site Planner]` (bug) #ui #testing  *(owner call, 2026-09-10 — "treat the Generation Park rate as a bug, not user error")*
`[x]` Four defects, one family: a monthly/annual period word being attributed to the RATE when it belongs to an escalation clause, or to an address. Shipped 2026-09-10.
- Verify: live · **V1069392**
- **(1)** `detectPeriod` read the ORIGINAL line rather than `working`. Escalation/cap/term/TI are all claimed and blanked BEFORE the rate block runs, so reading the raw line let "$0.64/SF NNN, 3% annual escalations" put `annual` on the rate — and, a period having been "found", the blocking "no monthly/annual period was given" flag never fired. The parser had already read that same clause as `escalationPct: 3`, so it knew the word belonged elsewhere. Now reads `working`.
- **(2)** `DOLLAR_ESCAL_RE`'s gap reached across `", 3% "` and claimed a genuine rate token as a dollar-step escalation — `"$0.64/SF/mo NNN, 3% escalations"` saved with **no rate at all**, the rate text landing in Notes. A correctly written comp silently lost its headline number. The gap may no longer cross a comma or a percent sign.
- **(3)** `PERIOD_RE` matched a bare `pa` as "per annum". PA is Pennsylvania, and parcels now resolve nationwide (VA/WV/CA/RI wired 2026-09-08/09), so an out-of-state address fabricated an annual period. `per annum` and `p.a.` still match.
- **(4)** An escalation clause with no percentage ("with annual escalation") is never claimed by `findEscalationPct`, so its period word survived into the rate. A bare period word adjacent to an escalation noun is now rejected; a slashed form (`/mo`, `/yr`) stays exempt — that shape only ever attaches to a rate.
- **Same family, reached through the EDIT path instead of the parser:** `compToDraft` defaulted a missing period to `"annual"`, so a comp whose period was genuinely unknown opened as annual and committed that guess on the next save; and `CompsPanel`'s period select had no unset option (which `CompDraftsPanel`'s identical control already had), so a blank period had no option to render and read as though a period had been chosen. Both closed.
- **Two existing test expectations were INVERTED, deliberately.** `test/compParse.test.js`'s "Michael's Tesla repro" asserted `rowHasBlockingFlags === false` — "ready to save with no correction needed" — on a row whose period had been fabricated from "increasing 3% annually". It encoded this very defect. It now asserts the period is unset and the blocking flag fires. The `period("pa")` corpus case likewise now asserts the bare form does NOT resolve.
- Mutation-checked: reverting any one of the four fixes turns the new tests red; restoring makes them green again.
- **No production data was touched** — the stored Generation Park row still reads annual, filed as **B1473985** for Michael to approve.
