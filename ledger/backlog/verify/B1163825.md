`[x]` **FIXED THIS SESSION.** Tesla - TGS DC4 stores `lease_rate = 0.645`; the detail view and list row both showed `$0.65/SF/mo NNN` (rounded to 2 decimals via `Number(comp.leaseRate).toFixed(2)`), while "Total annual rent (face)" (`$9,434,719`) and "Net effective" were both computed from the FULL `0.645` value — so a reader checking `0.65 × 12 × 1,218,956` by hand against the printed total found a real-looking `$73,138` gap that doesn't exist. New `fmtRate()` (`comps.js`) shows the rate at its STORED precision — extending past 2 decimals only when the value genuinely carries more, via `String(n)`'s own shortest round-tripping decimal string (safe here: `leaseRate` is read straight off a Postgres `numeric` column via `Number(r.lease_rate)` with no arithmetic in between, so there's no `0.1+0.2`-style float artifact to worry about) — capped at 6 decimals as a sanity ceiling, never fewer than 2 (matching every existing "$X.XX" comp figure). Chose showing the stored precision over rounding the totals to match, because rounding the TOTALS would misstate the deal's real annual rent — showing the rate honestly is the smaller, more honest change.
