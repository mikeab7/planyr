- Origin: found 2026-07-30 by the B1188 audit (not owner-reported). Fixed 2026-07-30.
- **REPRODUCED first, exactly as filed** (headless Chromium, production `vite preview`, logged out): draw a building → click the Properties rail tab → dispatch Escape in the SAME evaluated tick. The whole planner is replaced by the boundary's `Minified React error #185`. Screenshot captured.
- **⛔ THE PRIOR SESSION'S LEAD IS REFUTED — record it so nobody re-runs it.** Its trace showed `size` getting a new object every render and concluded the loop was a `setSize` feedback cycle, with "quantise `setSize`" as the next step. Instrumented both writers at full precision across the crash: **RO and the B962 layout effect never disagreed** — both reported 1058 exactly — and there were **FIVE `setSize` dispatches in the entire trace** while `size` was replaced ~50 times. The width was never oscillating. Quantising would have changed nothing, and would have put a whole pixel of slop into view maths that `diagnose-pointer-accuracy` asserts to a quarter of a pixel.
- **The actual root cause, from a sourcemapped crash frame** (`SitePlannerApp:7:334513` → `SitePlanner.jsx:2581 setRegShift`): the runaway writer is the **drawing↔basemap registration layout effect**, not `setSize`. Two individually-innocent pieces closed a cycle:
  1. **The effect depended on the `size` OBJECT** (`[view, size, origin, geoOverscan]`) while reading only numbers out of it. `setSize`'s updater ALLOCATES whenever the measured width differs from the state it is applied to, and React re-applies a retained updater against its base state on every subsequent render — so once the panel close left one retained, every render minted a fresh `{w:1058,h:640,…}` holding the SAME numbers, and the effect re-ran on identity alone.
  2. **The effect dispatched `setRegShift` unconditionally**, including on the `!origin` early return (a blank plan) where there is nothing to register against. A `setState` whose updater returns the same value is still a DISPATCH — React only skips scheduling via the eager-bailout path, which needs the fiber to have no other pending work, and during a panel close there always is some. So that dispatch scheduled another render, which minted another `size`, which re-ran the effect…
  Instrumented proof: ~50 consecutive runs with every dep VALUE identical (view `{0.35,60,60}`, 1058×640, overscan 213), one component instance (no remount), zero `setSize` dispatches in the loop. Fifty round trips is React's nested-update limit, and it aborts the subtree.
- **LAYER 1 — the loop.** The effect now depends on `size`'s NUMBERS (`[view, size.w, size.h, origin, geoOverscan]`), so an allocation-only change is invisible to it — correct, because nothing in the body can tell two `{w:1058,h:640}` objects apart. The `!origin` path now guards its dispatch instead of relying on a no-op updater. The B837 pan compensation already depended on `size.w` this way; the registration effect was the outlier. **Scoped to `size` deliberately:** the trace showed `view` and `origin` hold their identity across the loop and their writers replace them only on a real change, so they stay whole-object deps — listing their fields too was belt-and-braces against a churn nothing has exhibited, and it was not free (it cost enough bytes to push `largestChunkBytes` past its CI ceiling, which is how the over-reach was caught).
- **LAYER 2 — a measurement loop must never be able to take the planner down (the non-optional half).** React's "Maximum update depth exceeded" is a CIRCUIT BREAKER, not a diagnosis of corrupt state: the loop is already broken by the time a boundary sees it, and the plan lives in storage, not in the aborted render. Yet the boundary answered it with a terminal card that replaced the entire planner — the drawing, the rails, the session. New pure `src/app/recoverableError.js` classifies that error (dev text **and** minified `#185`, because production is where it fired and where a message-only match would be dead code), and `ErrorBoundary` now spends up to **two automatic remounts** before showing any card, holding a quiet "Redrawing…" placeholder for the frame it takes. The retries are **bounded** so a genuinely repeating crash still surfaces, and the budget resets after 30 s so an unrelated later blip is not held against an hours-old count. **LOUD-FAILURE is preserved on both paths** — every catch still logs and still reports to telemetry, tagged with whether it auto-recovered, so a silently-retried loop is data, not a swallowed error. If a recoverable error does exhaust its retries, the card now says the plan is saved rather than reading as lost work. Deliberately NARROW: an ordinary `TypeError` recurs identically on remount, so it is not recoverable and still goes straight to the card.
- **Verified here (the regression test was PROVEN RED on pre-fix code before it was accepted, as the item required).** New `e2e/panel-escape-race.spec.js` drives the exact race — the rail click and the Escape in ONE evaluated tick, strictly faster than two driver round trips and immune to machine speed — six times per run. **On the unmodified baseline build it fails with the planner replaced by the error boundary (screenshot attached to the run); on the fix it passes 6/6 with no update-depth error raised at all.** Layer 2 is asserted independently of the race in `test/errorBoundaryRecovery.test.js` (8 tests: the minified-code match, neighbouring-code false positives, non-recoverable classes, the bounded retry, the window reset).
- **No regression in what this effect exists to do**, which was the real risk of the dep change: `ui-audit/diagnose-map-lock.mjs` **PASS** (pure-pan round trip returns exactly; zoom re-snap 0.650 px lock / 0.493 px return, both inside the 1 px bound) and `ui-audit/diagnose-pointer-accuracy.mjs` **PASS** (120/120 readings within 0.25 px, compensation still applied) — both on a LOCATED site with a real basemap, so the `origin`-set path is exercised, not just the blank one. Plus e2e `panel-toggle-viewport` (B837), `panel-open-squish` (B962), `panel-toggle-flash` (B933) and `canvas-click-pan-jump` all green.
- **Bonus, measured:** `e2e/inspector-close.spec.js` — one of the three specs **B1179** records as RED on `main` — was red *because of this bug* and is now **3/3 green**. B1179's other two are untouched and stay open.
- **Gate:** lint 0 errors · full unit suite green · build green · bundle budgets within ceiling. **The first CI run FAILED on `largestChunkBytes` by 0.1 KB** — B1178's unreproducible baseline had already consumed the whole headroom band on `main`, so this change's +89 bytes tipped it. Paid back rather than ratcheted (raising the baseline would have baked in B1178's drift): the over-broad dep lists were narrowed to the measured churner, and the registration effect's two reference builders — which each spelled out the same three-call Leaflet "map frame" read, and which built the projection reference TWICE for one measurement — were de-duplicated.
