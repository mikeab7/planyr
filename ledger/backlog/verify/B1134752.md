`[x]` **ROOT-CAUSED AND FIXED THIS SESSION — candidate (3) from the task brief: "a rotation is applied at render time from something other than rotation_deg."** Ruled out (1) (the flyer artwork itself printed at an angle) as the PRIMARY explanation — it can't be confirmed or refuted without the actual file, but it isn't needed to explain the symptom, and the fix below is correct regardless of whether the artwork also carries some residual angle (which the rotate handle, B1134753, now makes trivial to dial out). Ruled out (2) (non-uniform aspect-ratio stretch) by inspection: `ftPerPx` is one scalar applied identically to width and height everywhere in `overlayGeoref.js` — there is no code path that could skew it.
- **The actual mechanism.** `overlayCornersFromPlacement`/`latLonToImagePoint`/`imagePointToLatLon` build the overlay's box axis-aligned in **State Plane GRID coordinates** (the projected x/y from `projectToZone`), then convert each corner back to lat/lon. State Plane grid north equals TRUE north only exactly on the zone's own central meridian (EPSG:2278's is 99°W). Away from it — which is everywhere a real site sits — the two differ by the grid **convergence angle**, so a box built axis-aligned to grid coordinates, once projected onto the true-north-up Leaflet map, reads as rotated even though `rotationDeg` never left 0. This is the exact fact `deedAlign.gridConvergenceDeg` already models for a different feature (correcting a plotted deed's basis of bearings) — it had simply never been wired into the overlay placement math.
- **Measured on the owner's own real row**, without touching it: `aa2d8163` sits at (29.9878°N, −95.3973°W) — Airtex, north Houston. Grid convergence there is **1.756°**. Across the plan's own ≈3,000 ft width that is roughly **92 ft of edge drift** — plainly enough to read as "it angled itself," and it did, silently, on every overlay ever placed anywhere off the central meridian.
- **The fix.** `gridConvergenceDeg` moved from `workspaces/site-planner/lib/deedAlign.js` into `shared/coordinates/statePlane.js` (beside its sibling `gridScaleFactor` — the same category of per-zone geodetic fact) — `deedAlign.js` re-exports it unchanged, so its own existing callers (the deed-align tool) are untouched. `shared/sitePlans/lib/overlayGeoref.js` gained one new function, `gridRotationDeg(placement)` = `rotationDeg − gridConvergenceDeg(centerLat, centerLon)`, used everywhere the old code fed `placement.rotationDeg` straight into the rotation math (the forward corner build, and BOTH inverse directions — `latLonToImagePoint`/`imagePointToLatLon`, kept in lock-step so a pinned comp's derived position stays exact). `rotationDeg: 0` now means "this overlay's top points at true north on screen" — which is also exactly what the rotate handle's own screen-pixel-angle math already assumed (its own header: "a screen-pixel rotation angle equals a true-north rotation") — so the fix makes reality match an intention that was already coded elsewhere, rather than introducing a new convention. Falls back to 0 correction (byte-identical old behavior) outside every modeled zone, same as every other zone-aware fallback in this module.
