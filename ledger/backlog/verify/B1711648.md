- **Root cause, confirmed against the actual (unminified) source, `src/workspaces/scheduler/Scheduler.jsx` + `lib/navState.js` — a ROUTE-WRITE RACE, not a logic error in B1614528's own fix.** `resolveReportRowNavigation` correctly resolves the click and records the pick (`explicitPickRef.current`), then calls `onProjectChange(linkedSiteId)` to carry the site into the outer route. But `onProjectChange` → `route.js`'s `navigate()` writes `window.location.hash`, and the resulting `projectId` PROP only updates once that hashchange event fires — a real, later browser task, never synchronous with and never batched into the SAME message handler's `setState` calls. So the very next render commits with `section` already `"projects"` but `projectId` still the OLD (null) value, `isPickShowing` reads "not showing" (it compared the pick's target project against the still-stale route), and `shouldNeutralizeToReports` — B1614528's own drift-correction gate — fires a real `planar:nav-dashboard` into that one-tick gap, exactly as it's supposed to for GENUINE ambient drift. The embed obediently reports back "reports"; the shell's carry-in effect then re-drives with `planar:nav-select-by-site`; the embed lands on "projects" again — a real, if brief, round trip the postMessage log confirms byte-for-byte: `nav-state projects → shell posts nav-dashboard → nav-state reports → shell posts nav-select-by-site → nav-state projects`. That round trip is what clobbers whatever selection the embed's own `goToTask` had already set correctly (confirmed by reading `public/sequence/index.html`'s `goToTask` and its `planar:nav-dashboard`/`planar:nav-select-by-site` handlers — neither explicitly reads as "safe," and B1614528's own postMessage capture already showed the loss happening, so removing the round trip is the fix rather than trying to make it lossless).
- **THE FIX IS CANDIDATE (a) FROM THE DISPATCH, NOT (b): the round trip is eliminated, not survived.** `isPickShowing` (`navState.js`) gains an optional 5th argument, `pendingProjectId`, defaulting to `null` (zero behavior change for every pre-existing caller, including the breadcrumb's `selectSchedule()`, left deliberately untouched — see its own header for why that path wasn't observed to share this race and why it's out of scope for this item). `Scheduler.jsx` adds `pendingRouteProjectIdRef`, set to the pick's own target `projectId` in the SAME synchronous tick `onProjectChange` is called (before the hashchange round trip lands) and threaded into the `pickShowing` computation — so the pick reads as "showing" on the very render it is recorded on, never waiting out the async route write. `shouldNeutralizeToReports` and the carry-in effect's `needsScheduleCarryIn` both already gate on `pickShowing` first, so bridging it this way suppresses BOTH the bounce and the redundant re-drive at the source, for both the linked-site case AND the unlinked/cross-cutting (Pursuits/Operations) case B1614528 also covers — verified unaffected. The ref is cleared the moment the real `projectId` prop next changes (confirmed or superseded either way) and defensively retired alongside `explicitPickRef` in `selectSchedule()`/`goDashboardWithinModule()`, so a stale bridge can never outlive its own navigation or leak into an unrelated later pick.
