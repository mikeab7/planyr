The background site link (`resolveOverlaySite`, which waits on a lookup), the debounced opacity write, rename, eye and lock all wrote the plan's OLD position / rotation / flags back over anything changed while they waited (`commitPlacement` records its new version before the stale save runs). Repro: open the Map panel with a placed, unlinked plan, drag / rotate it during the lookup → it snaps back and stays back after reload; a delayed opacity undoes a same-moment rotation; a rename undoes an eye toggle.
- **Fix — one write path, built at WRITE time:** `lib/overlayPatchWrite.js` `writeOverlayPatch` runs inside the per-plan queue and builds the row from the plan's LATEST copy (`getLatest`) with only the patch laid over it (re-read again for the conflict retry); the captured `o` is only the id and a fallback. `SitePlansSection` routes every row write through it: `patchAndReload` (rename, visibility, lock, opacity, share, crop, site link, background attach), the "Change page" write in `confirmPage`, and the raster-attach write (`overlayRasterAttach` now also queued and given the latest copy). Because React's `overlays` ref only catches up on the next render, every local list change now goes through one synchronous `commitOverlays` (ref first, then state), so a write queued in the same microtask chain as a drag / toggle / reload reads the newest copy. Grep: no `updateOverlay(` call and no `{ ...o, ...patch }` remain in the file (guarded).
