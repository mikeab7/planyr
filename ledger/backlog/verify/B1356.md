`[x]` **Shipped 2026-07-31. Parked in ⏳ Verify — `V667`.** Drag one end of a dock zone and only that end moves; the end you did not grab stays exactly where it was.
- **THE OWNER'S REPORT, verbatim:** *"fix the fact that when I shrink the trailer parking, it shrinks from both sides."*
- **ROOT CAUSE, confirmed against the code before a line was written (AUDIT-FIRST).** `dockZones.layoutZoneByKind` built the zone centre as `b.c + u·center + tan·alongShift`, and the ONLY along-wall term was `alongShift` — which exists to carry the B492 corner-bump-out trim and is non-zero only when a court is pulled in between bump-outs. The LENGTH came from the user (`alongLen` → `zoneAlongSpan`); the CENTRE did not. So the length changed and the centre did not, and both ends travelled inward by half the reduction. It is not an arithmetic error: the model stored a SPAN WITH NO ANCHOR, and there was no field in which "which end did you grab" could be written down.
- **REPRODUCED LIVE FIRST, on the owner's own geometry, before the fix** — his real "Concept D — Sylvestri Retail" rows (site `sms4zs8unbkg`), building `e1454698mwpaoj` (867.94 × 300, a 55 ft bump-out at each end, clear face 757.94) with court `e1454699mwpaoj` and trailer `e1454796yyuqqs`, seeded logged-out and driven in headless Chromium. Grabbing the row's east end and pulling it in: **the west end moved 59.95 px and the east end moved 59.95 px** — both ends, half the reduction each, exactly as reported. Note what this proves about the class: **not one element on that plan carries an `alongLen`.** This defect needs no poisoned data and no history — it is what a clean plan does the first time a zone is shrunk.
- **THE FIX — the override is an ANCHORED span.** Three fields, of which only the first already existed, so nothing migrates and an unstamped plan renders byte-identically: `alongLen` (the length, unchanged) · `alongAnchor` (`-1` the −along end held, `+1` the +along end, `0` centred — absent ⇒ 0 ⇒ the old behaviour) · `alongOff` (feet from the chain default's corresponding reference to the held one). `anchoredAlongSpan` resolves the three into a length and a centre shift; `layoutZoneByKind` folds that into the `tan` term it already had, **COMPOSING with the bump-out `alongShift` rather than replacing it**. Because the anchor is a REFERENCE and not a world position, it survives everything the zone is derived through: shrink the host and the held end tracks the wall it is bonded to, grow it back and the span springs out, add a bump-out and the whole chain slides together.
- **The gesture is read off the geometry, not off the handle.** An edge drag pins the opposite edge exactly and a corner drag pins the opposite corner, so `alongAnchorFromDrag` takes whichever end moved less; both ends moving (a re-centre) reads as centred, the conservative answer. **B1123's two intent gates are untouched and still decide WHETHER anything is pinned** — a depth-only drag, a host refit, a rotation, a relayout and the load-time heal all still pin nothing. This adds only WHERE.
- **A TYPED length keeps the current anchor** instead of silently re-centring; clearing the override clears the anchor with it (intent withdrawn is intent gone).
- **THE AUDIT, all four resizable bonded zones, as asked — and it was not only the trailer:**
  - **Trailer parking** — defective. Fixed.
  - **Buffer** (and any menu-appended outward layer) — defective by the identical mechanism, same `opts.alongs[i]` path. Fixed by the same rule.
  - **Truck court** — defective, and doubly so: its typed length re-centred on the clear face, AND its along-edge drag was discarded outright (`resized.truckCourt ? null : …`), so it could not be anchored at all. It now pins and anchors like every other zone, still capped to the clear bump-out face, so **B492 is unchanged** — an anchored court can never slide onto a bump-out, and its whole outward stack still tracks it.
  - **Side parking** — **already anchored correctly**, and needed no change: `dogEar.sideParkAlongRun` records `{ run, alongShift }`, so the along-CENTRE the drag produced is carried through beside the run instead of being re-derived to the middle of the wall. That is exactly the shape this item gives the dock zones. Asserted in the new suite so a future edit cannot quietly lose it.
  - **Wall strips** (sidewalk / landscape) — fully derived from the span rule, no user length at all, so there is no anchor to lose. Asserted too.
- **SEQUENCED AGAINST THE IN-FLIGHT ALONG-RUN WORK, deliberately, and it is the reason the shape is what it is.** That work (**B1123** ⏳ Verify — the Goose Creek trailers frozen at 708/707 against 712 ft courts; **B1124** + `normalizeHostRuns` — the Colorado court and parking carrying a different building's 708.58; **B1340 ×2** — the Sylvestri end parking stuck at 205/80 against 260/259 ft sidewalks) **has already landed on `main` and is the base this branch is cut from.** It made a bonded child's span DERIVED-unless-explicitly-stamped, and the anchor is therefore built INTO that override's shape from the start rather than bolted beside it: `alongAnchor` / `alongOff` live on the same element, are written by the same gesture gate, are dropped by the same heals that drop `alongLen`, and are re-clamped on every host change by the same rule. Nothing here re-opens or weakens any of the three.
- **The heals had to move in the same commit or they would have fought the canvas.** All three `layoutZoneByKind` call sites in `siteModel.js` (`normalizeStrandedZones` · `normalizeZoneAlongLen` · `normalizeHostRuns`) now carry `anchors`/`offs`, and `normalizeHostRuns` resolves the court head through the same `anchoredAlongSpan`. Because **B1340's tear detector IS the healer's own diff**, a heal that ignored the anchor would have reported a permanent tear against a canvas laying the zone correctly. A dropped length now drops its anchor with it.
- **Guards.** `test/zoneAlongAnchor.test.js` (47) drives the real `layoutZoneByKind` through a helper that mirrors `relayoutSide`/`courtBumpOpts` line for line, on the owner's flat building AND his rotated one (540 × 1041 at 33.959°): shrink from each end · grow from each end · a second drag from the OTHER end (the case a bare offset cannot express) · a typed length preserving the anchor · composition with a bump-out trim · a host resize · rotations at 0/17.5/90/178.543/269/359° · re-clamping instead of sliding off the wall · a pre-fix baseline proving the centred model moves both ends · the four-zone audit · the three heals leaving an anchored zone identical. **Mutation-checked: 15 of them go red with the anchor removed.** `e2e/dock-zone-anchor.spec.js` (4) drives the REAL render and the REAL drag on the owner's seeded rows; **3 of 4 go red on the pre-fix model, reproducing the 59.95 px double-shrink.** New fixture `ui-audit/fixtures/sylvestri-concept-d.json` (his 22 real elements, verbatim).
