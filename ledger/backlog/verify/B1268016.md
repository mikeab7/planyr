- **⛔ THE DEPENDENCY THE BRIEF ASKED TO BE SURFACED LOUDLY, SAID PLAINLY: this field did not exist before this item.** "Days since it entered the needs-attention state" cannot be read off anything already stored — a task's raw `.health` is a value the owner (or a health RULE) sets directly, and the rule-computed DISPLAY health (`computeDisplayHealth`, `public/sequence/index.html`) is a live, every-render derivation that the app's own code deliberately never writes back to `.health` (its own comment: "that computed color is never written back to `health`"). So there was no historical record of a health TRANSITION anywhere to read a date from. **Added `needsAttentionSince`**, a per-leaf-task ISO timestamp stamped the instant `computeDisplayHealth` first reads `"red"` and cleared the instant it stops, via a new reconciliation pass (`reconcileNeedsAttention`, called on every real data change AND on the existing day-rollover `refresh()` callback, so a pure midnight rollover with no edit still catches it). **Per the brief's own instruction, this does NOT fall back to days-past-due** — a task with no stamp is simply absent from the list, never estimated from its end date. **The one real consequence, stated rather than hidden:** on the first load of an existing account after this ships, every task already sitting in "Needs Attn." starts its clock at 0 days and grows correctly from there forward — the time it spent red *before* this shipped is not recoverable, by construction (there was nothing to read it from). This is exactly the trade the dispatch anticipated ("if you had to add the field, say so").
- **"N waiting"** = how many other tasks name this one as a predecessor (the Scheduler's own existing `succMap` derivation, replicated read-only in the Dashboard's pure lib rather than imported, to keep the Scheduler's health-rule engine out of the Dashboard's bundle).
- **Click-through reaches the exact task, not just the project** — a new `planar:nav-select-task` postMessage type (added beside the existing `planar:nav-select-by-site` etc. in the Scheduler's bridge) that resolves the routed site to its linked schedule and calls the Scheduler's own pre-existing internal `goToTask(pid, taskId)` (already used by its Master-view row jump and the successor-prompt modal — reused verbatim, not reinvented). `Shell.jsx` stashes the request as a token-stamped intent (`scheduleTaskIntent`, same shape as the existing `docIntent` the Doc-Review jump already uses) since the Dashboard unmounts before the Scheduler mounts; `Scheduler.jsx` posts the message once its iframe reports ready.
