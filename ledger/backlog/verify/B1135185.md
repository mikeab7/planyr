### B1135185 — "Someone else changed this site plan" fires for a single user editing alone, and can discard the user's own in-progress placement `[Site Planner]` (bug) #site-planner #persistence #sync  *(owner chat block, 2026-09-04, same block as B1135184 — filed and fixed same session. Minted **B1135185** from the same reserved block, code/tests/commit keep the provisional label NEW-18. DEDUPE-FIRST — searched Open/⏳Verify/Done for "someone else changed", "optimisticUpsert", "casUpsert" + site plan overlays: no prior item on this table's version-guard race. Net-new.)*
`[x]` **FIXED THIS SESSION.** Root cause, found by reading the code: the optimistic-concurrency "expected version" a write sends was read from a stale source, so a client's OWN rapid successive writes could race and defeat each other. `SitePlansSection.jsx`'s placement-commit handler (`commitPlacementRef`) and its simple-field handler (`patchAndReload`) both read `expected = existing.version` from `overlaysRef.current`/a component prop — both of which only advance when React actually re-renders and the ref-sync line re-runs, which lags a just-issued write's own `setOverlays` call by at least one render. Two writes fired close together (two finished-drag gestures back to back, or a fast double-click on "Editing on map" while nothing was rendering — see B1135184) therefore read the SAME stale `expected`; the first to reach the server won, the second was correctly rejected by the real DB-side CAS check (`commit_site_plan_overlay_placement`'s `version = p_expected_version` guard) as a genuine-looking conflict, surfaced as "Someone else changed this site plan — showing the latest version instead," and **the second write's change — sometimes the one that would have set a valid scale — was discarded with no retry.** Confirmed this is a real, independent bug (not solely dependent on B1135184's specific row): the evidence row's `version` climbed from 4 → 18 (14 more attempts) while its `ft_per_px` stayed null across several of them, matching "several rapid saves, each bumps version, and a save that left before the previous response landed comes back with a stale expected-version."

- **STRONG HYPOTHESIS TESTED, per the chat block's own instruction, and the result reported honestly: B1135184 and B1135185 are related but NOT purely one causal chain.** The evidence row's `ft_per_px` being null was directly and independently explained by B1135184 (the drop-placement bug wrote a real, literal `NULL` at insert time — no race required). What the race DOES explain is why fixing it via the self-heal took **14 attempts** instead of 1, and it is what produced the "someone else changed this" banner the owner actually saw while he is the only person on the account. Both bugs are real, both are now fixed, and they compound each other in exactly the reported way even though neither is solely the other's cause.
- **THE FIX — three parts, in `src/shared/sitePlans/components/SitePlansSection.jsx` (+ a new tested pure module):**
  1. **`src/shared/cloud/writeSerializer.js` (new, unit-tested — `test/writeSerializer.test.js`, 5 tests)** — a per-key async write queue (`createWriteSerializer().run(id, fn)`). Every write for the SAME overlay id now queues behind the previous one, so a second commit's body does not even START reading "what version do I expect" until the first has fully settled — this alone closes the two-calls-fired-back-to-back race.
  2. **`overlayVersionsRef`** — the last-known-good version per overlay id, updated SYNCHRONOUSLY (never through React state/props, which is what was stale) the instant a write settles. Combined with the queue above, a write's `expected` version is always the true one.
  3. **Retry-once-on-conflict, in both `commitPlacementRef` and `patchAndReload`** — a reported conflict (which should now be rare, since the race above is closed) triggers ONE refetch-and-retry with the fresh version before being believed. A conflict that survives the retry is treated as a genuine concurrent editor: the banner still fires (**a real foreign edit must still be detected — this does not touch or weaken the DB-side CAS check itself**, only the client's bookkeeping around it), but the user's own in-progress placement is **never silently discarded** — the optimistic local state (already applied before the write) is left on screen rather than overwritten by a `reload()`, so the user can simply move it again to retry.
- **What was explicitly NOT changed:** `commit_site_plan_overlay_placement`'s and `casUpsert`'s actual version-guard SQL/logic — the real concurrency check some other session's genuinely simultaneous edit needs is untouched; only the CLIENT's bookkeeping of what version to send was wrong.
- **Presence signal:** the chat block asked to "honour the existing presence signal" before reporting a conflict. `src/shared/presence/` (`multiTab.js`) is scoped to a single open SITE in the Site Planner canvas, not to a site-plan-overlay row inside the map finder, so wiring it in here would be a materially bigger, riskier change for this session. Functionally the retry-once fix achieves the same intent without it: after the race is closed, a conflict that still occurs after a fresh-version retry genuinely IS a second live write landing in that narrow window — which is the strongest form of "someone else is here" signal available, achieved without adding new cross-tab plumbing.
