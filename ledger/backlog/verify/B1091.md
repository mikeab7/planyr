- **Root cause (AUDIT-FIRST).** `scopeFloodEntries` suppressed a district row on ONE signal: `cfg.district !== governing`. `governing` comes from the drainage context (`resolveDrainageContext` → `drainageDistrict`), which is null until a drainage check has run and been remembered — and a snapshot saved before B1080 carries no district at all. Null `governing` → fail open → every district renders. Two further holes underneath it: `COUNTY_DISTRICT` was keyed `"fort bend"` while the panel's own county prop is `"fortbend"`, so the county fallback could never fire in Fort Bend; and `coh_storm` had no district at all, so the district gate could not reach it in any state.
- **Fix — ONE mechanism, four ordered signals** (`floodRowRelevance`, `lib/floodGroup.js`), reusing the coverage-scope machinery the Master Plan gate already uses rather than adding a second: (1) a district row that isn't the governing one; (2) a district row whose district does not REACH this county (`districtReaches`, off `DRAINAGE_DISTRICTS[].counties` — no network, no drainage check, so it works the moment the county is known); (3) a row whose agency's own service area is elsewhere (`cfg.areaCounties`, now declared on `coh_storm`); (4) the coverage engine's published-extent "out". County keys canonicalise (`countyKey`), so `"Fort Bend"` / `"fortbend"` / `"Fort Bend County"` can never miss again.
- **Demoted, never deleted.** A demoted row moves behind ONE collapsed line — "N sources that don't cover this site" — where it keeps its checkbox and carries its own reason ("Harris County Flood Control District doesn't cover Waller County — Brookshire–Katy Drainage District is shown instead."). That satisfies both branches the owner offered (not rendered in the default view / listed with the honest coverage note) and keeps a scoping call one click from being overridden. A layer the user has ALREADY turned on is never yanked away — it stays in its tier with the reason as a caption. - **Root cause (AUDIT-FIRST) — THREE distinct defects, all shipped together, each sufficient on its own.**
- **(a) A GUESS was given the authority of a FACT.** `floodRowRelevance` demoted a district row whenever `governing` was non-null and different — including a `governing` the COUNTY heuristic merely inferred. Districts overlap counties: BKDD spans Waller, Harris AND Fort Bend, so "this county's flood-control district is HCFCD" is no evidence whatsoever about BKDD. That single unqualified comparison is the inversion. `governingDistrict` now returns **`exclusive`** — true for a boundary containment, or for a county answer only once every rival district has been boundary-tested and CLEANLY excluded — and only an exclusive answer may say another district doesn't govern. A guess may still demote a district that cannot REACH this county (checkable), and otherwise **fails open**.
- **(b) The panel reasoned over the WRONG COUNTY.** The scoping consumed `LayerPanel`'s `county` prop, which is the parcel-lookup / jurisdiction-layer REGISTRY KEY — a UI selector that `useState`s to `"harris"` on every site and only ever names counties Planyr publishes local layers for. It is not a fact about where the site is. The panel now reasons over the **site identify county** (`floodContext.authority.jurisdiction.county` — the same value the header renders as "Waller County"), falling back to the site record's own county (new `siteCounty` prop); a straddle or an unresolved identify yields null, which fails open. `county` keeps its original job (which county's local layers to offer).
- **(c) A remembered check FORGOT the district the boundary test found — confirmed against the production row.** The Tsakiris snapshot in Supabase has **no `drainageDistrict` key at all** (it predates B1080) while its own `authority.flags` carry **`"bkdd-district-present"`** and its overlays carry the `drainage-district` / `bkdd` record — i.e. the boundary query had answered YES. `hydrateDrainageContext` read only the county-derived `channelAuthority`, so that fact was discarded on every reload and a county guess filled the vacuum. Hydration now reads the flag (and the stored overlay) FIRST and restores the district with `source: "boundary"`.
- **LOUD-FAILURE.** A FAILED district-membership query is no longer indistinguishable from a clean negative: `resolveDrainageContext` publishes `drainageDistrict.tested` — the district ids whose boundary query actually answered — and an outage (`bkdd-unverified`) leaves the id out, so it can never license an exclusion. Unknown stays unknown.
