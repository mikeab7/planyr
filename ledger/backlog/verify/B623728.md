- **THE FIX — `MIN_PIN_ZOOM` raised from 12 to 15, chosen by measurement, not by nudging a constant.** Three independent lines of evidence, all computed directly rather than guessed (full derivation in the code comment, `FoodMap.jsx`): **(a) ground scale is zoom-intrinsic** — at z12 one screen pixel covers ~33m at Houston's latitude, at z15 ~4m, the first zoom where a city block reads as more than a few pixels; **(b) miles-across a 1440px window** — z12 ≈29.7mi (the whole metro), z14 ≈7.4mi (several stitched-together neighbourhoods), z15 ≈3.7mi (one named neighbourhood, e.g. the Heights or Montrose); **(c) the decisive practical test, run directly against production** — at z15, even downtown/midtown (the single densest `food_places` cluster in the entire metro) returns only **1,251** places, under the reference-snapshot RPC's 2,000-row cap; at z14 the identical box already returns **2,641**, over the cap. So z15 is the tightest zoom at which the reference snapshot is unconditionally complete everywhere tested in the metro — nothing is ever sampled, so the proportional-share fairness question (B576001, below) becomes moot at the zoom people will actually reach it.
- **THE DISTRIBUTION CONCERN — measured, not assumed, and it is real density, not an algorithm bug.** Raw `food_places` counts for the areas the colleague named: Sharpstown 713, Spring Branch 710, Heights 498, Bellaire 161, Independence Heights 127, Kashmere Gardens 56. Spring Branch (reported "nearly empty") is in fact nearly as dense as Sharpstown (reported "dense") — 710 vs 713. Running the actual production RPC over a wide box containing both returned 71 rows in Sharpstown's footprint vs 65 in Spring Branch's — proportional to their true 713:710 ratio. The sparse areas really are sparse in the underlying data; this is not the proportional-cap algorithm failing. And at the corrected z15 threshold this is moot regardless: six real Houston locations checked directly against production (downtown/midtown 1,251, Sharpstown 574, Heights 483, Galleria 265, Spring Branch 197, Kashmere Gardens 58) all sit under the 2,000-row cap, so nothing is sampled at all at z15 anywhere tested — a distribution question about a sampling algorithm that never engages.

- **BASEMAP — CARTO Voyager, not Positron; checked the Site Planner's registry again first, same answer as before.** The first ship's Positron ("light_all") delivered "muted" so thoroughly it read as a flat grey wash — water, parks and built-up land all nearly one tone, nothing to orient by. `basemaps.cartocdn.com/rastertiles/voyager` is the SAME free, key-less CARTO service, same terms (https://carto.com/basemaps), same domain — just a different `style` parameter, confirmed against CARTO's own published URL scheme (`github.com/CartoDB/basemap-styles`) rather than guessed: real cartographic colour (green parks, blue water, warm building fill) with roads/labels still quiet. Esri/USGS (the Site Planner's own free sources) were re-checked and are still the wrong content type — aerial photography has no "muted" setting, it would reintroduce "too busy" in a different shape.
- **PINS — coloured by rating, not decoration.** `lib/ratingColor.js` is a 10-step warm ramp (cream → deep red-brown); a rated place/pin uses `colorForRating(avgRating)` (the mean of that place's rated visits), falling back to the flat logged/manual colour when visited-but-unrated. **Deliberately single-hue, never red/green** (this repo's own KEY DECISIONS already bans that confusion pair elsewhere) — verified by asserting the green channel never dominates red in any step. **Relative luminance falls STRICTLY step 1→10 (0.89→0.04, WCAG formula, computed not eyeballed)**, so the ramp still reads light-to-dark in grayscale or on a washed-out phone screen. Step 8 (`#BE3B22`) lands exactly on the module's own existing `--accent-food` token. Every step's paired label colour clears AA (≥4.5:1, the small-bold-text bar) — step 7 was nudged from a linear interpolation's `#D74A2A` (4.28:1, short of AA against either black or white) to `#CC4526` (4.72:1) specifically to close that gap.
