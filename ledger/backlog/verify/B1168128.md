`[x]` **IMPLEMENTED AND RED/GREEN-PROVEN THIS SESSION — the fix, and an honest account of what could and couldn't be proven against it.** AUDIT-FIRST re-read of `index.css` found the actual gap: `html, body, #root { overflow: hidden; height: 100dvh; }` stops the document from ever NEEDING to scroll (B168), but on iOS Safari that does not reliably stop the page from being DRAGGED — a one-finger touch that starts over content with nowhere to scroll can still hand the gesture to the browser's own top-level "rubber-band"/edge-bounce scroller, which is a native WKWebView behaviour CSS `overflow` alone doesn't fully govern. Fixed at the app-shell level, per the brief's own instruction, not patched for the Site module alone:
  1. **`src/index.css`** — `html, body` now also get `position: fixed; inset: 0; width: 100%; overscroll-behavior: none`. Pinning them takes the document OUT of the page's native scroll entirely — there is no top-level scroller left for a stray touch to hand a gesture to. `overscroll-behavior: none` is additive belt-and-suspenders for browsers that DO scroll-chain (Android Chrome); it is not the fix on its own, since Safari's edge-swipe/rubber-band gestures aren't fully governed by it. `#root` is untouched (still a normal block, fills the now-pinned body exactly as it filled the unpinned one) — this is app-shell-wide, covering every module and both map surfaces (the Site Planner canvas AND the account/site-picker map in `MapFinder.jsx`), not a Site-module-only patch.
  2. **`src/workspaces/site-planner/SitePlanner.jsx`** (the canvas wrap div) and **`MapFinder.jsx`** (the Leaflet host wrapper) both gained `touchAction: "none", overscrollBehavior: "none"` — defence in depth beyond the `<svg>`'s own pre-existing `touchAction: "none"`, so a touch landing on floating chrome stacked over either map (the scale bar, the calibration badge, the phone FABs) declares the same intent.
  3. **`src/shared/ui/pageContainmentGuard.js` (new) + wired into `main.jsx`** — a `clickDiag.js`-shaped, always-on, silent-by-construction runtime watcher (STANDING RULE #2 disposition 3, "instrument it so it captures itself"): since html/body are now pinned, `window.scrollX/scrollY` must always read (0,0) and `visualViewport.scale` must hold at 1 — a `scroll`/`visualViewport` event that ever finds otherwise IS the defect happening live. It self-heals (snaps scroll back to 0,0; nudges the viewport meta to force Safari to reset scale) and reports via `reportClientEvent` (the same `client_errors` channel B468/NEW-5 established) so a real-device recurrence produces a durable server-side record automatically instead of relying on him noticing and re-describing it. 15 new unit tests (`test/pageContainmentGuard.test.js`) prove the pure `detectDrift` logic and the installer's self-heal/report/throttle/idempotency/uninstall behaviour against an injected fake `window`.
