- **⛔ AUDIT-FIRST — the dispatch's own inference ("a stale window re-published its whole local store") was investigated and only PARTLY confirmed; the dominant mechanism is a different, more serious defect than either the dispatch or an initial read of the code suggested.**
  1. **Hypothesis A, checked and mostly ruled out: the empty-anchor litter sweep (`sweepEmptyAnchors`, runs on every Notes load) marking many pages dirty at once.** Queried the CURRENT content of all 11 pages for `noteAnchor` nodes: only 3 of the 11 contain one at all, so the litter sweep alone cannot explain the other 8 — it only rewrites a page that actually has litter to remove. **Real defect found anyway, independent of this incident**: `sweepEmptyAnchors`'s writes went through the exact same `writePage` path a live editor keystroke uses, so an automatic, no-user-intent cleanup pass COULD legitimately collide with a genuine edit made elsewhere and raise a conflict bar over content the user on this device never touched — which matches the owner's own confusion ("I didn't make this edit") more precisely than a 3-day-old real edit would. **Fixed below regardless.**
  2. **Hypothesis B, the one that actually explains the burst, found only by reproducing the shape end to end (no sibling window needed at all): a page, once ever written to via `writePage`, NEVER actually left the sync ledger's dirty set.** `pushPending()` updates `sync.pages[id]`/`sync.treeDirty` IN MEMORY the instant a push succeeds, but does not write that success to disk until its own trailing `saveSyncState()` call — which then merges the now-clean in-memory state against whatever is STILL on disk from the PRE-push moment (nothing else wrote disk in between). `mergeSyncState`'s blind `dirty: mine.dirty || disk.dirty` cannot tell "disk knows about a genuinely different window's still-pending edit" (the real B1391 case, which must keep working) from "disk is simply this same window's own now-superseded snapshot from a few lines earlier in the SAME call." **Reproduced with a throwaway repro test against the UNMODIFIED shipped code, one page, no sibling window, four `refreshNotesSync()` calls after the first successful sync**: the server row's `rev` climbed **1→2→3→4→5** — an unconditional, permanent, silent re-push, on every subsequent tab focus/visibility/online event AND the 60-second poll (`POLL_MS`) for as long as the tab stays open. **This is what actually produces "eleven pages committed in one second, with unrelated revs, from a client the burst-detector never suspected of an edit":** once ANY page has ever been typed into, it never leaves the dirty set, and a poll/focus tick re-pushes EVERY such page a device is holding in one `pushPending()` call.
- **⛔ THE URGENT QUESTION — DID ANY OF THE 11 PAGES LOSE CONTENT? NO, not from this mechanism, and here is the reasoning rather than a guess.** Every push (buggy re-push or genuine) sends whatever `readPage(id)` currently returns — the device's own CURRENT, correct local body — never a cached-from-before copy. - **THE RULE THIS SESSION IMPLEMENTS, one sentence:** a page is treated as "genuinely dirty and worth a conflict" only while its OWN unpushed edit has not yet been confirmed by a successful round trip to the server or is a live editor save nobody automated on the user's behalf — never because a stale on-disk snapshot or an automatic housekeeping rewrite says so.
- **FIX 1 — the self-resurrection bug (`mergeSyncState`, `notesCloud.js`).** Disk's `dirty` claim is now honoured only when disk's own `rev` is AT LEAST as current as what `mine` (the in-memory side) already confirmed — exactly the shape of a genuine sibling window's still-unpushed edit (same or newer base) — and ignored when disk's rev is OLDER than what `mine` has already moved past (this window's own stale pre-push snapshot). The B1391 guarantee this must not break — "an unpushed edit in EITHER window is still owed to the cloud" when both share the same confirmed base — is unit-tested unchanged. Same fix applied to `treeDirty`/`treeRev`, which resurrected identically.
- **FIX 2 — an automatic write can never itself raise a conflict (`writePage`/`writePageHousekeeping`/`commitPageWrite`, `notesStore.js`; `planPageSeed`, `notesCloud.js`).** The sync ledger's per-page entry grows a fourth fact, `auto` — true only for `sweepEmptyAnchors`'s one-time litter cleanup (any FUTURE non-interactive body rewrite belongs on the same path, never through `writePage`). `planPageSeed` and `pushPending`'s push-time race both now resolve an `auto`-dirty page whose base has moved by silently ADOPTING the server's row — never naming a conflict — because there is no per-document user intent behind that write to defend. A genuinely dirty (non-`auto`) page is completely unaffected and still raises a real conflict on a real divergence, per B1391.
- **THE DETECTOR, per the block's explicit ask.** `pushPending()` now calls `reportClientEvent("notes_bulk_page_push", …)` (the existing `client_errors` `event:` channel) whenever a single push cycle is about to commit **5 or more** page bodies at once, carrying the count, the ids (capped at 20), and the auto/editor-marked split — so a repeat of this incident shows up by name in telemetry instead of requiring another manual SQL query.
