`[x]` **FOUND AND FIXED, RED-PROOFED AGAINST UNMODIFIED CODE.** Two independent, pre-existing defects in `notesSketchEditor.js`, both invisible until a box's own `<g>` element could be reliably re-targeted twice in a row — confirmed present on unmodified `origin/main` (`git stash` round-trip, identical reproduction before either fix).
1. **A press that did not turn into a drag called the FULL redraw, `paint()`, instead of `paintSelection()` (`onPointerUp`).** `select()`'s own header already names exactly this trap — "a redraw would destroy the element that has DOM focus, which is exactly what happens when a keyboard user tabs onto a box" — `onPointerUp`'s no-op-drag fallback simply never followed it. Every plain click on an existing box tore down and rebuilt its `<g>` element, destroying whatever had focus and, separately, breaking the browser's OWN double-click recognition (element identity, not merely screen position, factors into whether two clicks form a native `dblclick`) — reproduced directly: `document.activeElement` after double-clicking a previously-selected box's center was `<body>`, and no `dblclick` event ever fired for the second press. Fixed: the no-op-drag branch now calls `paintSelection()` (already used elsewhere in this file for exactly this reason), which never replaces the DOM.
2. **`onDoubleClick` read `e.target` directly, which POINTER CAPTURE retargets.** `onPointerDown` arms a potential drag with `drawSlot.setPointerCapture(e.pointerId)` for any press on a node; a captured pointer's derived `click`/`dblclick` events report `e.target` as the CAPTURING element (`drawSlot`, a plain DIV) rather than whatever the cursor is actually over. `target.closest("[data-sketch-node]")` therefore always missed for a double-click on an existing box, and the gesture fell through to "empty spot," minting a brand-new box on top of the one just double-clicked — reproduced directly: box count 1 → 2, the original untouched, a fresh empty one at the same point. Fixed: `onDoubleClick` now resolves the real target via `document.elementFromPoint(e.clientX, e.clientY)` first, falling back to `e.target` only if that returns nothing — the standard remedy for this exact pointer-capture gotcha.
- **VERIFIED, real trusted browser input:** double-clicking an existing, previously-closed (Escape), already-committed box now correctly reopens its editor with the label field focused and its stored text intact, and creates no second box — reproduced fixed on both a freshly-created box and one that had already been through B1683296's own relocate path. Every other sketch-mode gesture re-verified unaffected: dragging a box, dragging an arrow between two boxes (both use the same `onPointerUp` path), the delete cascade, and a full reload.
- **Both mechanisms generalise beyond sketch mode** — see `docs/NOTES-CARRY-FORWARD.md` §1 entry 31 for the note filed against any future node view with the same shape (re-selectable content, or its own embedded controls).
