`[x]` **Root cause 1 — the keyboard measurement read zero on a real iPhone.** `keyboardInset = innerHeight − vv.height − vv.offsetTop`. WebKit's `LocalDOMWindow::innerHeight()` returns `unobscuredContentRectIncludingScrollbars().height()` — the VISIBLE rect, the same one `visualViewport` is built from — so with the keyboard up `innerHeight` shrinks with it and the difference cancels to ≈ 0: no lift, no full snap. (Read from WebKit's source, not observed on a device — no session can drive a real iPhone keyboard; V1497664 is the closure.) **Why 136/136 was green:** both earlier harnesses stubbed `visualViewport` but kept `innerHeight` at the full layout height — they tested their own model. Fix: `lib/keyboardInset.js` measures the layout viewport as the fixed-position containing block itself (a hidden `position:fixed;top:0;bottom:0` probe), `max`'d with innerHeight so desktop/Android are unchanged.
`[x]` **Root cause 2 — the reveal.** `BottomSheet` used `el.scrollIntoView`, which on iOS also scrolls the page/visual viewport (fighting the lift), and only ran on focus when the inset was ALREADY non-zero — never true for the dish editor's autoFocus name field (focus first, keyboard after).
