- **"Sometimes" WAS the diagnosis, and it was MEASURED before a line was written (AUDIT-FIRST).** Tab is the browser's own focus key, so any press the document declines falls through to the page chrome and then to the browser toolbar. Driven headless at desk width, the editor's existing extensions claimed Tab in exactly two situations and it escaped in every other one: **table cell** → handled (next cell) · **nested-able list item** → handled (indent) · **FIRST list item** → the list claims it and then declines (nothing to indent into) → **escaped** · **plain paragraph** → nobody claims it → **escaped** · **empty page** → **escaped**. Three of five presses left the document.
- **What shipped — a FALLBACK, not a blanket swallow.** `lib/notesTabKey.js` registers at a LOW PRIORITY, which puts its keymap after the table's and the list's: those still run first and still win whenever they can act, and this only ever sees the presses they turned down. In a plain paragraph or an empty page it inserts a real tab character (a real character, so the indent survives storage, Markdown export and the print sheet — an indent faked with margin on the DOM node would not). In a list item whose indent was declined it swallows the key rather than wedging a tab inside a bullet, which is a document you cannot outdent again. Shift+Tab takes the tab stop back and is swallowed either way, because focus-backward walks the caret out just as surely.
- **⛔ THE KEYBOARD-TRAP ESCAPE HATCH IS PART OF THE FIX, not an extra.** A key that can never leave seals a keyboard-only user inside the note. **Escape releases the next Tab** (or Shift+Tab) to the browser, and typing anything takes the release back so there is no mode to get stuck in. It is ANNOUNCED rather than folklore: the editor's accessible name reads "Note body. Tab indents; press Escape then Tab to leave the note.", with `aria-keyshortcuts` beside it.
- **PDF-PARITY:** a tab typed in a paragraph is a real character, so the print sheet honours it at the SAME width the screen does (`tab-size: 4` in both `EDITOR_CSS` and `notesPrint.js`) — a unit test compares the two numbers and fails if they drift.
- Guards: `verify-notes.mjs` §23 drives all five cases plus both halves of the hatch — paragraph and empty page indent and the caret stays; the first list item stays put with no stray tab in the bullet; a second list item still really nests; a table still steps to the next cell; Escape-then-Tab leaves; and typing re-arms. `test/notesModule.test.js` asserts the extension is in the one canonical list, that its priority is below every other extension's, that the hatch exists, and the print parity.
