`[x]` **FIXED THIS SESSION — two distinct causes, both real, found by reading the actual event wiring rather than guessing.**
- **Cause 1 — the click-to-arm gesture itself was ambiguous, exactly as reported.** Before arming (clicking "Move / resize", or clicking the plan on the map to select it), the overlay's raw `<img>` never stopped its own `pointerdown` — correct, so a real drag could still reach Leaflet's own map-pan handler underneath — but the browser's native trailing `click` event still fires afterward regardless (confirmed against the installed `leaflet-src.js`: `Draggable.finishDrag` fires only its own `dragend`; there is no document-level click-suppression trick anywhere in this Leaflet version). So the SAME gesture both panned the map (correctly) AND selected/armed the overlay (never intended) — which one "won" visibly depended on unrelated timing, which is precisely "sometimes… sometimes…, no clear way to tell which." Fixed in `rotatedImageLayer.js`: pointerdown is still never stopped (so a real drag still pans normally), but the click handler now tracks the pointerdown→pointerup travel distance and ignores the trailing click if it moved more than a small tap-slop — a real drag no longer ALSO arms the overlay.
- **Cause 2 — once armed, the interaction model already matched the task's own Google-Earth-Pro-style spec for the parts that don't risk distorting a scaled drawing, but was missing legibility.** `overlayPlacementHandles.js` already implements: a visible frame that exists ONLY while armed · a whole-frame move surface that stops propagation so a drag inside it can never reach the map underneath (was already correct — the reported ambiguity was Cause 1, at the point of ENTERING edit mode, not while already in it) · per-corner resize cursors · one commit per gesture, on release (never per mouse-move). Added: a **diamond** rotate marker (matching the reference model's own vocabulary, was a circle) · a **live numeric readout** during a gesture — degrees while rotating, feet× feet while corner-scaling · **Escape cancels and restores the exact pre-gesture placement** (was not implemented — a stray drag had no undo-in-place, only whatever the next commit happened to write) · a panel field to **type an exact rotation value** (Rotation °, in the expanded Site plans row, committed the same atomic way a drag is).
- **Deliberately NOT built: independent per-corner skew/stretch or free per-side resize (the task brief's literal Google Earth Pro reference).** This app's overlay model is one uniform `ftPerPx` for the whole image — by design, since a site plan is a SCALED DRAWING and non-uniform stretching would distort its dimensions, unlike Google Earth Pro's general photo-draping use case. Corner handles keep the EXISTING uniform-scale-about-center behavior (already correct and already the deliberate, stated convention this module mirrors from the Site Planner's own reference-image tool). The "trim it" want the side/edge handles would otherwise address is B1134754's crop tool instead — a more correct fit for "there's too much white space," not a resize.
- **The false-conflict race, named in this task's own sequencing note as a known blocker, was found to be REAL and CURRENT (no in-flight PR existed for it — confirmed via `list_pull_requests`/`search_pull_requests`, zero open PRs in the repo at session start) and is fixed as part of this same interaction-model work, since it directly undermines it.** `SitePlansSection.jsx`'s placement-commit handler read `existing.version` from a React ref that only updates on re-render — two commits fired close together (plausible with the improved, easier-to-use handles) could both read the SAME pre-commit version, so the second landed as a false "someone else changed this site plan" even though it was the same user's own very next gesture (matches the task's own note: row `aa2d8163` reached version 18 in four minutes of ordinary nudging). Fixed by serializing same-overlay commits through a promise chain and tracking each overlay's version in a plain ref updated synchronously within that chain — never through React's scheduled re-render — so a rapid second gesture always reads the version its predecessor's write actually produced.
