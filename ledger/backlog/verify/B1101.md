- **Why the old one was wrong (the owner's diagnosis, and the reason this is a redesign rather than a relabel).** `Project | All` and `Apply` look like one axis and are two: the segmented control chose **where the value is STORED**; Apply **pushed it onto objects already DRAWN**. Read left to right it parsed as "apply to this project or apply to all" — which it can never be, since nothing can retroactively restyle a plan you have not opened. Hierarchy was inverted on top of that: `All` was a loud filled accent chip while `Apply` was faint grey, so the least consequential control shouted the loudest.
- **What it is now — THREE buttons, each named outright, no scope toggle.** **Apply to this plan (N)** · **Save for this plan** · **Save for all projects**. Apply carries the live count of objects it would change and is the primary (filled); the two Saves are quiet outlined secondaries. Apply keeps its existing toast **with Undo** (it is the only action that touches drawn geometry); the two Saves get a brief non-blocking confirmation with **no Undo**, because there is nothing to take back.
- **THE CONSEQUENCE, HANDLED: Standards edits are now a PENDING DRAFT.** Once "Save for this plan" is an explicit button, a field edit can no longer silently commit as the plan default, or that button means nothing. So every Standards style edit lands in `stdDraft` and NOTHING is stored until a button commits it. The pure model is `lib/standardsApply.js` (`EMPTY_STD_DRAFT` / `withParcelDraft` / `withTypeDraft` / `draftParcelValue` / `draftTypeValue` / `draftDirty` / `mergeDraftIntoSettings`); `derivedPanelScope` and the whole per-key scope machinery (`parcelStdScope` / `typeStdScope` / `stdScopeKeys` / `settings.stdScope` / `promoteParcelStd` / `promoteTypeStd`) are DELETED, not left dead.
- **An unsaved-edit trap would be worse than the problem, so the draft is visible, reversible and durable.** The footer shows a quiet **● Unsaved changes** marker (in `--warn-text`, the AA amber this app uses for every saving / unsaved / offline label) with **Discard** beside it; Discard drops the draft, which restores the pre-edit values by construction since nothing was ever written. `draftDirty` compares against what is COMMITTED, so editing a value back to where it started clears the marker instead of leaving a permanent nag. The draft is persisted per PLAN in `sessionStorage` (`planyr:stdDraft:<siteId>`), so closing the panel, switching workspace or reloading cannot silently throw the edits away — **and a draft can never leak onto a different plan**, which plain component state would have allowed on a plan switch.
- **"Apply to this plan" commits AND pushes in ONE undo frame**, exactly as specified — applying implies keeping, so it does not take two clicks. Its toast's Undo takes back the WHOLE action: the drawn objects, the stored plan defaults, and the pending draft all come back.
- **"Save for all projects" writes the account-level defaults** through the existing `cloudReady` path (`public.profiles.prefs`, own-row RLS), then drops this plan's own copies so the plan keeps following the account default when it later changes — the old promote rule, generalised from one key to the panel. It touches nothing already drawn, and signed out it stays disabled with its existing explanatory tooltip rather than passing a per-computer value off as an account default.
- **A draft changes what you SEE, never what gets STORED.** Element type styles resolve at RENDER, so the canvas previews the draft live (`planStyle.setPreviewStyleDefaults`, a layer above the project setting and below a per-object override, where a `null` CLEARS back to the built-in rather than painting nothing). `parcelDefaultStyle` deliberately does NOT read it — it STAMPS a value into a new parcel, and an uncommitted value must never reach stored geometry. "Reset all to built-in" became a draft edit (a null per key) like everything else.
- **PLACEMENT — it is a real footer now, not a sticky bar inside the list.** The old bar was `position: sticky` INSIDE the scrolling settings container with a negative bottom margin, so it hovered over the content and cut whatever row sat at the bottom of the scrollport in half (the reported "Bay band (min / max)" slice) and did not span the panel. It is now rendered as a **sibling BELOW the scroll container** in both hosts — the docked panel and `FloatingPanel`, which gained a `footer` slot — with a hairline rule above and a subtle upward shadow so it reads as chrome. That is strictly stronger than the bottom-padding remedy the brief proposed: a sibling reserves its own space, so **no row can be occluded at ANY scroll position**, not just at the bottom, which is what the e2e asserts (`footer.top >= scroller.bottom`) at both a middle and a bottom scroll. The actions share a row when they fit and wrap into full-width rows when the panel is narrow — never overflowing or clipping.
