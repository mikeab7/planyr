**PART 1 — "Needs attention": where the `days` figure comes from, and why it's identical five weeks apart.** `needsAttentionSince` (public/sequence/index.html's `reconcileNeedsAttention`) stamps a leaf task the instant `computeDisplayHealth` first reads "red," using ONE `nowIso` computed per call — and that call fires not just on a real edit but on **the first load of an existing schedule** after this field shipped, which stamps EVERY already-red task at once with that single shared timestamp. **Confirmed against `planyr_production` (read-only, 2026-09-09):** of the owner's 31 currently-flagged tasks, 25 share one exact stamp (`2026-09-06T18:57:08.194Z`) and 6 share a second (`2026-09-09T05:00:21.887Z`) — zero organic, individually-observed transitions. The card's sort (`days` descending) is not itself broken — it correctly orders by the field it's given — but with the top 25 of 31 rows all reading the SAME `days` value, the visible top-8 window shows no variation at all, and there is **no other per-task timestamp anywhere in the document to backfill from** (re-confirmed 2026-09-08 by a different session, `dashboardScheduleFetch.js`'s own header). **Chosen: say plainly on the card what the figure is measured from, not backfill (no honest source to backfill from exists).** A row whose exact stamp is shared with another currently-flagged task account-wide — the bulk-stamp signature; an organic transition landing on the identical millisecond as another is not a real possibility — now renders `bulkStamped: true`, shown as a trailing **"+"** on its day count (a floor, not a claim of precision) with a hover tooltip naming the batch date, plus a one-line card footnote ("+ = flagged in a batch when tracking began — could be longer than shown.") that appears only when at least one visible row carries it. As his tasks naturally transition after this shipped, their stamps become unique and the "+" clears on its own — no future session needs to revisit this.
- **"0 waiting" — established it IS computed, correctly, and needed no code change.** `successorCounts`/`waiting` in `needsAttentionList.js` reads real predecessor links; confirmed against production that 413 of his 828 real tasks carry predecessor arrays, and 7 of his 31 currently-flagged tasks are genuinely named as a predecessor by another task (`waiting: 1` each). The reported "0 waiting on all 8" is the SAME root cause as the days tie, not a second defect: with 25 tasks tied at the top `days` value and the old comparator having no tie-break, the particular 8 rows that happened to land in the visible window (via arbitrary stable-sort insertion order) simply weren't among the 7 with a real waiting count. Fixed as a byproduct of the sort fix below, not by touching the (already-correct) `waiting` computation.
- **Sort now ties on `days` → `waiting` descending → task name ascending**, never plain insertion order — a task blocking more downstream work is a real, already-computed, non-fabricated signal (never `t.end`, per the existing anti-proxy rule; never quiet time, which doesn't exist on this card) to prefer among otherwise-indistinguishable rows.

**PART 2 — "Pursuits": genuinely absent, not unwired.** **Confirmed against `planyr_production` (read-only, 2026-09-09):** every one of the owner's 28 open (pursuit/active/onhold, non-tracked) pursuit projects — 44 underlying plan rows — has `data->>feasibilityExpiry`, `data->>loiDate` and `data->>closingDate` **all null** — `dashboardSitesFetch.js`'s query correctly reads the three jsonb fields (verified by direct read), and `pursuitsList.js`'s own header already documented this exact first-release state ("EVERY row reads 'Nothing scheduled'… until dates are entered"). Nobody has used the "Deal dates…" editor yet — this is real, not a read bug. With `next` null on every row, the old comparator's `ad==null && bd==null → return 0` left `Array.sort`'s stability to present raw insertion (fetch) order as if it meant something, which is exactly the defect: **"a sort keyed on a value no row has is arbitrary, and presenting an arbitrary order as a sort is the defect."**
- **Fix:** the undated↔undated tie-break is now **alphabetical by name** — a real, defensible, deterministic order, deliberately NOT quiet time (`quietDays`) or last-edited/recency, both of which this module's own header already rejects as a sort input, for a reason stated there (a stale pursuit must never outrank one with a real clock running on it) that still applies even when nobody currently has a clock running. New `allPursuitsUndated(rows)` helper; the card now shows a one-line banner — "No deal dates set yet — sorted alphabetically." — whenever every row is undated, so the alphabetical fallback is never presented as if it were the "soonest date" sort the card is built to be. The banner disappears the moment even one pursuit gets a real date.
