**ROOT CAUSE.** `az_pinal`'s bbox (Pinal's own measured data extent) and `az_maricopa`'s bbox overlap far more than the two counties' real boundaries do — exactly the shape this file's own B130/Sugar-Land comment already documents for harris/fortbend. `candidateCountiesForPoint` already asks the real county-polygon geometry for a confident answer (`resolveCounty`, B209502) once it's resident, but it only used that answer to reorder the bbox matches, never to narrow them — so a solidly-interior point still queried every bbox-overlapping neighbour, exactly as if it were a genuine boundary straddle. `identifyParcelEager` fires one query per candidate and, of two REAL-CAD (non-statewide) candidates, takes whichever answers first with a hit — there is no county-identity tiebreak between two real CADs, so a wrong-county answer is one race condition away every time two bboxes overlap and geometry has already decided which one is real.

**THE FIX (`counties.js`).** `geometryCountyAnswer(lat, lng)` now returns `{ key, nearEdge }` (was: key only). `candidateCountiesForPoint` uses it: when the geometry answer is confident (`nearEdge: false`) and resolves to a real, non-statewide county, that county is the ONLY real-CAD candidate returned — every other bbox match is dropped, not just demoted. A genuinely near-edge point (within ~150 m of the resolved county's own line, `nearEdge: true`) is unchanged: every bbox-overlapping neighbour is still returned, because THAT is the real straddle case the old "query both, let the answer decide" reasoning is actually for. The statewide fallback tier (TxGIO, the state OIT composites, …) is untouched either way — it's coverage-of-last-resort, not a rival county, and is still appended for the point's own state(s).

**Consequence for B1339920's own reasoning, corrected:** its "safe because whichever service answers owns the lot" line was true only for the Mesa-area straddle it was thinking of; Casa Grande — squarely inside Pinal, no straddle at all — is exactly the case that reasoning missed. No further action needed on B1339920 itself; its endpoint wiring is untouched by this fix.
