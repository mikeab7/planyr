- **ROOT CAUSE.** `deleteSiteGroup` (`storage.js`) is called by `ProjectBreadcrumb.jsx`'s `doDelete` (the project switcher's per-row kebab → Delete → confirm flow) via `shared/projects/projects.js`'s `deleteProject`. It resolves what to delete via `loadPlansOfGroup(groupId)`, which filters `loadSitesList()` — a read of THIS BROWSER's `localStorage` cache, never the cloud. When that comes back empty, the function historically assumed "nothing to delete" and returned success without ever calling `deleteSite`/`cloudDelete`. The three "reads of the deleted list" per attempt the owner measured are `purgeExpiredDeletedProjects` firing on every switcher-dropdown open (background noise from `ProjectBreadcrumb.jsx`'s own open handler, unrelated to the delete write itself) — confirming the switcher's OTHER cloud reads worked fine while the delete write specifically never fired.
- **#1519 CHECKED FIRST, PER THE BRIEF'S EXPLICIT INSTRUCTION, AND RULED OUT.** Commit `75b0877` (PR #1519, merged 20 minutes before the first reproduction) changed `cloudSync.cloudCheckDeleted` (the route-gate READ, called from `checkProjectDeletionStatus`/`ensureProjectRow`) and added a group-liveness guard to `purgeProjectFoldersFor` (called only from the 30-day expiry purge / "Delete forever" paths). Neither function is in the call graph of `deleteSiteGroup`/`deleteSite`/`cloudDelete` — confirmed by reading every call site of both (`storage.js` lines 1207 and 1371/1404/1425). A broken read in either would still have produced the ordinary delete WRITE traffic the owner's instrumentation would have caught, and it did not. **Ruled out, not merely suspected.**
- **IS THIS A REGRESSION? Stated honestly.** This container's shallow git history cannot audit further back than a few days. Nothing in the visible recent history touched `deleteSiteGroup`'s empty-plans-list branch — it reads the same today as the earliest version reachable in this clone. The two owner-reported stuck projects were both created "last night," i.e. very recently and by a path (an external session, not a normal draw-something-in-the-planner flow) that never happened to populate this device's local cache — so the honest read is that this defect has likely existed since `deleteSiteGroup` was written, and simply never manifested until a project was deleted from a device whose cache didn't have it. **Not calling it a recent regression** on the strength of a shallow-history absence of counter-evidence.
- **THE FIX — ask the cloud directly when the local cache has nothing.** `storage.js`'s `deleteSiteGroup` now falls back to a new `cloudSync.cloudDeleteGroup(uid, groupId)` whenever `loadPlansOfGroup` is empty (and the caller is signed in) instead of assuming there is nothing to do. `cloudDeleteGroup` mirrors `cloudCheckDeleted`'s two-query shape (`id = groupId` catches the anchor/a legacy pre-groupId row; `group_id = groupId` catches every sibling) and soft-deletes (`deleted_at`) every row it finds, aggregating the result the same way the ordinary per-plan path does. Signed OUT, the empty-cache case is unchanged (a clean `{ok:true, removed:0}` — there's no account to ask). The SAME class of silent no-op existed a second time in `SitePlannerApp.jsx`'s own `deleteSiteGroup` (wired to the map/site-list "Delete project…" entry point) — `if (!rec) return;` with **no error, no toast, no network call** — fixed the same way (fall back to treating the row's own id as the group id, then to the storage-layer cloud fallback), since it is the exact same bug family reached from a second entry point (see the adjacent-cases table below).
