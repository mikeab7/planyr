- **PROVEN IN THE PRODUCTION DB, WITH A SURVIVING VICTIM.** Group `smrp1wrgg6u5` — one project, five plans, TWO names, split for four days. The `.256/.307/.358` writes are ONE `loadPlansOfGroup` loop (the rename); `sms4zs8unbkg` was saved **seventeen minutes later**, after the rename, and still said "Sylvestri" — it was not in the local set when the rename ran, so it kept the old spelling and wrote it back to the cloud.
- **THE STRUCTURAL FIX, ARGUED.** The alternatives were (a) a real `projects` table, (b) a group-keyed name record, (c) an authoritative value per group reconciled on read. **(c) shipped**, because (a) and (b) both mean a new table, a new RLS surface, a migration of every existing group, and a second write path to keep in step with `sites` — a large blast radius to fix a rule that can be stated in one line. The invariant is what matters, not where the bytes live: **a project's name has ONE authoritative value per group, and every `site` field is a DERIVED MIRROR of it.** The per-plan `site` column stays (every read path uses it, and the cloud's slim-header row is keyed off it) — it is simply no longer a source of truth.
- **WHAT MAKES IT AN AUTHORITY RATHER THAN A GUESS: `siteRenamedAt` (schema v13, additive, null on every existing record).** A rename stamps the group; the name on the plan with the NEWEST stamp wins, unconditionally. **This field is the whole point, and the trap it closes is specific:** without it the only available tiebreak is "most recently updated", and on the owner's own data that answer is a coin flip — `sms9c5oc7jnt` (correct name) happens to be later than the straggler, but nothing made that true, and had Concept D been touched last the wrong name would have won. Do not "simplify" the authority back onto `updatedAt`.
- **`lib/projectName.js` is the pure decision** (`nameAuthority` / `reconcileGroupNames` / `resolveNameFor` / `maxStampOf`) — no storage, no network, no DOM. Three bases, and the third is the honest one: `stamp` (a real rename) → `majority` (LEGACY only, no stamp anywhere; this is the shape the bug produces — the loop writes N−1 copies and the straggler keeps the old one, which is how the owner's 4-vs-1 group recovers) → `ambiguous` (legacy, no majority, e.g. a 1-vs-1 split): **there is no honest winner, so nothing is changed and the group is REPORTED** (`project-name-ambiguous`, LOUD-FAILURE) rather than half-renamed. Once a group is stamped it always resolves — a same-instant two-name tie breaks deterministically on count, never back into `ambiguous`.
- **THE READ AND WRITE SEAMS, because a rule that lives in one of them is not an invariant.** `loadSitesList` resolves the authority on the way OUT (so a split group can never reach the map list, the switcher or an export under two names, even before anything is written back); `loadSite` does the same for the single-record read that `pushSiteToCloud` goes through; and **`saveSite` is the write choke point** — every local write passes through `resolveNameFor`, so a stale in-memory model can no longer be *written* with the old name and therefore can never be *pushed* with it. That last one is the exact move that undid the owner's rename.
- **The stamp is STRICTLY MONOTONIC — `max(now, groupMax + 1)`, not a bare `Date.now()`.** Two renames inside one millisecond would otherwise share a stamp and the SECOND could lose; and a device whose clock runs slow would stamp a genuinely later rename with an earlier number. The first case was caught by a test, not by inspection.
