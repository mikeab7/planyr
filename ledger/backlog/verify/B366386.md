### B366386 — Sharing a MULTI-PLAN project keyed on the drifting `group_id` COLUMN — the rename bug's shape, still latent `[Site Planner / teams]` (bug) #site-planner #auth #sync  *(arrived 2026-08-11 as provisional NEW-3 in the same owner chat block, filed there as "FLAG TO VERIFY (NOT PROVEN)". See B366384's provenance for the DEDUPE-FIRST sweep.)*
`[x]` **⏳ SHIPPED as a fix, not just a check — the defect is REAL in mechanism and was LATENT for his data. Both stated plainly below rather than one overclaimed as the other.**
- Verify: live — V161952 (`Blocker: auth`)
- Origin: owner chat block, 2026-08-11 — filed and shipped the same session.
- **WHAT THE BLOCK ASKED.** *"Confirm it sets team_id on EVERY plan row in the group AT THE SOURCE OF TRUTH… This is the same shape as the rename bug that half-landed and left stale rows in the cloud."* Correct instinct, and it was checkable statically.
- **THE DEFECT.** Both `set_project_team` and its pre-migration fallback matched `coalesce(group_id, id)` — the group_id **COLUMN**. `db/rename_site_group.sql` exists *because that column is a denormalised mirror known to drift from the jsonb*, and its header says outright: *"matching on it would rename the wrong set. Do not 'optimise' this onto the column."* Sharing was matching on exactly that column while the CLIENT passes a group id read out of the **jsonb** (`groupOf()` → `data->>'groupId'`). Wrong in both directions: a plan whose column disagrees is MISSED (a "shared" project only partly shared; on unshare, a collaborator keeps access the owner believes he revoked), and a foreign plan whose column names the group is swept IN.
- **THE DRIFT IS REAL IN THIS DATABASE TODAY** — row `e2e-fixture-testfit` has `group_id = 'e2e-fixture'` against `data->>'groupId' = 'e2e-fixture-testfit'`. So the mechanism is live, not theoretical.
- **AND THE HONEST LIMIT: it is LATENT for every one of the owner's real projects.** Measured across all 34 groups — Bain 2, Clay & Porter 2, Gessner 2, Goose Creek 4, Houston ColdPort 2, Silvestri 5 — **both keys select the identical row set**. The only disagreement in the whole database is that e2e fixture pair. So this fix is PREVENTIVE; it did not repair a currently-broken share, and it is not claimed to have.
- **THE FIX.** Both functions now key on `coalesce(data->>'groupId', id)` — byte-identical to `rename_site_group.sql` and to the client's own `groupOf()`, so all three read one grouping. Sharing already reached un-hydrated plans (it is ONE server-side UPDATE over the group, not a client loop — that is what half-landed the rename), so this changes WHICH rows that statement selects, never whether it is atomic.
- **PLUS A COMPLETENESS SELF-CHECK, both directions (LOUD-FAILURE).** The RPC re-counts its own group AFTER writing and returns `mismatched`; a non-zero value is surfaced as *"Only part of this project was shared — N of M plans didn't take"*, and on the unshare side as *"N of M plans are STILL shared"* — named rather than softened, because a half-unshare is the dangerous direction. A group holding a teammate's plan reports `foreign` and says so instead of claiming a clean success.
- Guards: repo-root `test/` suite **shareMirror** (a source guard on BOTH function bodies — the jsonb key required, `coalesce(group_id, id)` forbidden).
