- **⛔ THE FIRST FIX WAS INCOMPLETE, AND HE CAUGHT IT.** Generation 1 (below, for the record) partitioned the viewport into an 8×8 grid and gave every cell the SAME fixed cap (`p_cap / 64`). That fixed the ORIGINAL bug (a scan-order prefix bunched in one corner) but introduced a NEW, subtler one: **giving every cell an equal absolute count, regardless of how many places actually live there, systematically under-represents dense areas and over-represents sparse ones.** Measured on a real production viewport (a ~12mi box, 8,903 total matching places across a 4×4 analysis grid): the densest cell (1,959 real places) returned only **124 rows — 6.3% of its content**; the sparsest cell (114 real places) returned **100 rows — 87.7% of its content**. A >13x disparity in coverage fraction, cell to cell. That is a biased slice by any reasonable definition, and it is very likely what read as "focusing on the middle" — whichever part of his screen happened to be denser was proportionally the most under-filled.
- **THE FIX — weight each cell's share of the cap by its OWN true count** (`ceil(p_cap * cell_count / total_matched)`, both cheap window functions on the same scan). Re-measured on the identical viewport: coverage fraction flattened to a **near-constant ~22.6%–24.0% across 14 of 16 analysis cells** (the remaining two, at the extreme edge of the RPC's own grid, sit at 17.1% and 9.6% — a `width_bucket` edge-overflow artifact affecting only the very outermost sliver, not a "middle" bias). This is a genuinely representative sample now, not a shape that favors wherever a cell happens to be dense or centrally located.
- **⛔ AND THE MODEL ITSELF CHANGED — read the redesign entry below.** This query is now used ONLY once zoomed in past the threshold; below it, the reference snapshot doesn't draw at all (his own logged/rated places are the zoomed-out content instead, always visible, never sampled). So this fix matters for the "zoomed into a neighbourhood" case specifically, which is exactly where he observed it.
