`[x]` **Shipped; ⏳ Verify (V1765584).**
- Verify: live — pan/zoom-dependent rendering on a real phone → **V1765584**; sandbox harness `ui-audit/verify-click-ack-anchor.mjs` (14 checks) is green, and RED on the old wiring (ring stayed at 826,491 while the land moved to 469,573).
- **THE REAL CAUSE.** `shared/ui/clickAck.js` appends a plain-DOM `position: fixed` ring at the tap's `clientX/clientY` (deliberately outside React so it paints before the planner's ~150 ms render). Fixed means it holds a SCREEN pixel: nothing ever re-projected it. Not a touch-vs-mouse difference — one code path on both; the ring simply outlives the tap for as long as the county answers, and any pan/zoom in that window left it over the wrong ground. (`SitePlanner.jsx` `beginIdentifyPress` is the Land > Parcels canvas path; `MapFinder.jsx` has the same ring on the Map tab's select mode.)
- **Fix.** `startClickAck(x, y, track?)` takes an optional `{ project(), subscribe(reposition) }`. SitePlanner records the tapped GROUND point (`p2f`, feet) and projects it with the LIVE view (`viewRef`, not the frozen pan anchor), repositioned from a `useLayoutEffect` on `view` so it moves in the same frame as the land; MapFinder projects the tapped lat/lng with `latLngToContainerPoint` on Leaflet `move zoom viewreset`. Look, lifecycle, watchdog and supersede rules unchanged; no `track` = old behaviour.
