Read against the actual schema (`comps.project_id references sites(id)`, `resolveOrCreateTrackedSiteForComp`/`compSiteMatch.js`) and the owner's own words ("Comps are a part of the site records, and this is supposed to be geared more toward exporting the site records, not necessarily the plans") — the premise holds and is what shipped.
- **New pure module `src/shared/comps/lib/kmlExport.js`** (+ `test/kmlExport.test.js`, 24 tests) — a SECOND, independent hand-rolled KMZ writer from `site-planner/lib/kmzExport.js` (B684), deliberately NOT importing across the `shared/` ↔ workspace boundary (see `src/shared/CLAUDE.md`'s "shared/ code must not statically depend on a workspace module"); mirrors its ZIP/KML conventions (STORE-only zip, hand-rolled CRC32, no JSZip) rather than reinventing them. Reuses `kmlImport.js`'s `polygonCentroid` (never re-derives it) for the "every polygon exports as its polygon AND a pin at its centre" rule — the pin carries the placemark's balloon (an Earth polygon balloon is awkward to open), the polygon carries none.
- **Structure:** one KMZ, two folders — `Parcel` (the site record's own drawn boundary, via the SAME canonical parcel source the map pin/list already use — `siteBoundaryInfo`/`siteDrawParcels`, B849344 — reprojected through the map's own `feetToLatLng`, never a second projection path; falls back to a single pin at the site's origin when no boundary is drawn yet) and `Comps` (every comp sharing that site record's `project_id`, each rendered per its OWN anchor kind — a `parcel`-anchored comp's `parcelGeom` GeoJSON becomes its own polygon+pin pair, colored per `compMarkerColor`; a `pin`/`site_plan`-anchored comp is a bare pin).
- **Balloon contents — everything populated, no curation, per the owner's "all the info attached to the site."** Site record: name, role (Pursuit/Tracked), status, county, acreage (from the canonical parcel summary — reports "Unknown" rather than a fabricated 0 when the summary hasn't loaded, never "No boundary" misreported as 0 ac), origin coordinates, any map Notes pinned to the project (title + body), the sibling comp roster, and filed Documents — **listed by NAME only, never embedded** (per the owner: "except for the full PDF file of course"), read best-effort via a dynamic import of the Document Review workspace's `reviewStore.listReviews()` (never a static cross-workspace import — this stays off both workspaces' boot bundles) filtered to the site's `project_id`; a failed/signed-out read omits the Documents section rather than falsely claiming none exist. Each comp's balloon reuses `compFieldRows`/`compHeadline`/`compDateLabel` verbatim — the SAME field set the panel/detail view already renders, never a second derivation — plus its Location text via `compLocationText.js`'s existing three-anchor-kind functions (synchronous fallback only; the async reverse-geocode cache is deliberately not wired in here, since a KMZ's own lat/lon pin already carries the position — an address string is a bonus, not the geometry).
- **No owning site resolvable** (a comp saved before B1165441's auto-attach, or whose site isn't in the currently-loaded list) → exports the ONE clicked comp alone and says so via the existing map error banner, never a silent narrower file (never a bulk "export the whole database" path either — one right-click, one site record, per the owner's explicit scope: "I won't be trying to export the entire database by this method").
- **LOUD-FAILURE:** a site parcel vertex that reprojects to a non-finite lon/lat throws and aborts the export (mirrors B684's `siteToFeatures` exactly); an empty result (no boundary AND no located comps) is refused with a plain message, never an empty/corrupt file.
