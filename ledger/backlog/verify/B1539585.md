**THE MECHANISM, proven with a page-internal ordered log, not console-message ordering (CDP can reorder those across the wire).** `updateTask`'s roll-announcement toast (B816, reused unchanged by today's "Next meeting"/"Previous meeting" feature) was written as a closure-local flag checked immediately after the state update:
```
let _rollToast = null;
setData(d => { /* ...may set _rollToast inside here, based on the recomputed schedule... */ });
if (_rollToast) showToast(_rollToast);
```
This assumes React calls the `setData` updater function synchronously, inline with the dispatch, so `_rollToast` is already set by the time the `if` check runs. React 18's automatic batching only takes that synchronous "eager" path when the fiber has genuinely no other work pending at the moment of the call; the instant anything else is even lightly pending — close to constant in an interactive app; this scheduler runs a live realtime-reconnect loop in the background — React defers the actual updater call to the next render, which happens AFTER the `if` check already ran and found `_rollToast` still `null`. Measured directly: a debug array written from inside both the updater and the post-`setData` check, read back after the interaction, shows the true order is `["after setData call, _rollToast=null", "updater running, touchesSchedule=true", "set _rollToast inside updater"]` — the check runs BEFORE the write, every time, in a clean, otherwise-idle headless tab (100+ repeated attempts, 0 successes). The row's date still updates correctly (`recomputeSchedule` itself is unaffected by any of this) — only the CONFIRMATION is silently lost, with no error and nothing to show it happened. This is a LOUD-FAILURE violation wearing a UI-polish bug's clothes: the toast the owner screenshotted is real (it fired for him at least once, with the overflow bug visible on top of it), but the mechanism behind it is unreliable, not merely cosmetically broken — this repo's own headless environment shows it losing every single time.

**THE FIX.** Replaced the closure-local `let _rollToast` with a `useRef` (`rollToastRef`, declared once at the `App` component's top level), written ONLY from inside the `setData` updater (safe regardless of eager-vs-deferred timing, since mutating a ref has no React scheduling implications), and flushed by a new `useEffect(() => { if (rollToastRef.current) { showToast(rollToastRef.current); rollToastRef.current = null; } }, [data])` — guaranteed to run only after the render that incorporated the updater's write has committed, under either timing.

**PROOF.** The same page-internal ordered-log method, re-run against the fix, confirms the toast now fires correctly. `ui-audit/verify-schedule-toast-fit.mjs` §A — which needs this exact mechanism working to observe anything to measure at all — went from **0/9 on untouched `main`** (no toast ever appeared for either call site the harness drives) to **9/9** on the fix, reproduced across repeated runs. `test/schedulerEngine.test.js` gets a 3-test anti-drift `describe` pinning the ref declaration, the write-site inside the updater, and the flush effect, and asserting the OLD racy pattern (`if (_rollToast) showToast(_rollToast);`) is gone from the source.
