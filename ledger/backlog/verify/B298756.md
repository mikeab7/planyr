- **⛔ IT RIDES THE PICTURE TIER RATHER THAN A SECOND BLOB TIER, and that was the load-bearing choice.** The owner offered both — *"either a new bucket or a relaxed policy plus a row per file"* — and the second is what shipped. The picture tier already owns a sync plan, a purge cascade, an orphan sweep and a per-notebook ceiling; a parallel tier would have meant a second copy of every one of those, and a second way to leak bytes. An attachment is a picture that is not a picture, not a new subsystem.
- **THE MIGRATION, APPLIED — nothing on the owner's plate.** `notes_attachments_new5` on `planyr_production`, 2026-08-09, via the Supabase MCC: `notes_images` gains `name` and `kind` (`'image' | 'file'`, DEFAULT `'image'`, so every existing row is already correct and nothing is backfilled), plus a two-value check constraint; the private `notes-images` bucket stops refusing non-image types and its per-object ceiling goes to 50 MB. Verified after applying: both columns present, `allowed_mime_types` null, `file_size_limit` 52428800, security advisors show **no new findings**. Committed as a record at `src/workspaces/notes/db/notes_attachments.sql`.
- **⛔ THE BUCKET IS STILL CALLED `notes-images` AND MUST STAY THAT WAY.** Renaming it orphans every object already in it — every picture in every existing note — for the sake of a more accurate word. The table comment says what it really holds.
- **⛔ `assetIdsInDoc`, NOT `imageIdsInDoc`, IS WHAT EVERY DELETE PATH MUST NOW ASK.** The purge cascade and the orphan sweep both moved to it. A cascade that asked only for image ids would leave a deleted page's attachments on the device and in the account forever — bytes nothing can reach and nothing will ever free, which is the exact leak TOMBSTONE-DELETES exists to prevent, one layer down.
- **A MIXED DROP DOES NOT LOSE HALF OF ITSELF.** Two plugins watching one drop is a race the first to `return true` wins outright, so a screenshot dragged in beside a PDF would have landed the picture and dropped the PDF with no message anywhere. The attachment intake runs first, DECLINES a pictures-only drop (leaving the image path exactly as it was) and claims a mixed one whole, routing both halves.
- **EXPORT — named always, embedded when small.** Markdown embeds up to 2 MB and NAMES anything larger, reporting it as lossy; the print sheet carries name · type · size, because paper cannot carry bytes and a survey that vanishes silently out of a PDF is the worst class of export bug. Both are asserted against real downloads in the harness.
- **The ceiling is enforced at the STORE** (`MAX_FILE_BYTES`, 34 MB of stored data URL ≈ 25 MB of file), so no future intake path can slip past it, and an oversize file is a NAMED refusal in the app rather than an opaque 400 from storage (LOUD-FAILURE).
