- **⛔ ONE CORRECTION TO THE DIAGNOSIS, and it matters for where the fix goes.** The item's stated likely root was that the easement kind carries none of `labelSize` / `labelSpacing` / `labelPlace` / `labelInside` / `labelHalo`. **It carries all of them** — verified against the four real easement rows on that plan and against `inlineLabelEls`, which the easement render calls at `SitePlanner.jsx`. An easement has TWO labels: the repeating INLINE label (fully controlled, and not the reported one) and the CENTROID label built from `labelOverride`, which had no controls at all. **And no markup label anywhere is in world units** — the others ride a clamped zoom ramp. His five measured neighbour sizes are `base × 0.34` exactly (labelSize 7 → 2.38, 8 → 2.72, default 11 → 3.74, 12 → 4.08), which is what identified the ramp.
- **⛔ THE ANSWER TO "IS A SHARED LEGIBILITY GATE THE RIGHT ABSTRACTION": IT ALREADY EXISTED, BUILT THREE TIMES, AND THIS LABEL WAS USING NONE OF IT.** B149's `detailLabelVisible`, B911's `dimFontPx` and the pond-parameter tier each pair the same two defences — a VISIBILITY gate keyed on the measured feature's on-screen size, and a SIZE riding `dimFontScale`. So **no fourth threshold was introduced**: the floor IS `dimCalloutVisible`, the ramp IS `dimFontScale`, and nothing in the new code is tunable. B371360's `featureEditFloorPpf` was considered and is deliberately NOT reused — it answers "is an EDIT legible" from an absolute px/ft floor and a viewport cap, which is a different question from "is this label smaller than its feature".
- **WHAT IS GENUINELY NEW is the third question none of the three existing tiers asks: is the LABEL narrower than its FEATURE?** The others gate on the feature alone, which suffices for short generated numbers ("300′") and not for arbitrary user text: this 513 ft easement clears `detailLabelVisible` at ppf 0.0585, where 30 characters still measure ~64 px against 30 px of feature. A long name now waits longer than a short one on the same feature.
- **⛔ THE SELECTION BYPASS WAS PART OF THE DEFECT.** The label only drew when selected, via `(isSel || dimCalloutVisible(ppf))` — `isSel` short-circuited every gate, which is exactly why a 199 px label sat over a 21 px object. Selection no longer lifts it, and the predicate takes no `selected` option at all (asserted structurally).
- **THE CHARACTER-WIDTH RATIO IS MEASURED, NOT GUESSED.** A per-frame `getComputedTextLength` is a layout read per label per frame and is not affordable in the render body, so the width is estimated — and calibrated in Chromium against the app's own built stylesheet (Inter 700, `getBBox().width`, five font sizes): his own label 0.6250–0.6444 (**201 px at 10.5, against the 199 px he measured live**), the others 0.4531–0.6146. `LABEL_CHAR_W_RATIO` is **0.68**, above the widest realistic label, so the estimate over-predicts and errs toward hiding. ⚠ It is NOT an upper bound for a pathological all-caps run of the widest glyph (1.0125–1.0714, asserted so the bound is recorded); such a label reveals slightly early, bounded at ~1.6× the estimate, never 9.5×.
- **"the feature's length" is its GREATEST extent**, not its horizontal one — otherwise a vertical easement of the same length would wait far longer for its name, which is a size rule masquerading as an orientation rule.
