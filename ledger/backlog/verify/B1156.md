- **Report.** Michael: pressing `f` should go to true fullscreen. What it did was **chrome-hide, not fullscreen** — `setFullscreen(v => !v)` collapsed the header to nothing and rendered a floating exit button, while the browser tab strip, the address bar and the OS taskbar all stayed exactly where they were.
- **The fix.** The keypress is a user activation, so `requestFullscreen()` is called straight out of the key handler — on **`document.documentElement`**, deliberately never a sub-element: fullscreening a subtree hides every `position: fixed` overlay that lives outside it, the exit button included. The existing chrome-hide is KEPT on top, so the result is edge to edge.
- **The four things that make it hold:**
  - **A refused request still hides the chrome.** `requestFullscreen` returns a promise that can reject (no activation, a permissions policy, an iframe without `allow="fullscreen"`), and iOS Safari has no fullscreen for a non-video element at all. Both paths fall back to today's behaviour rather than leaving a keypress that appears to do nothing.
  - **The header is DERIVED from the document, never guessed.** A `fullscreenchange` listener (plus the webkit-prefixed spelling) drives the React state off `document.fullscreenElement`, so Esc, the browser's own exit affordance, or anything else that ends fullscreen brings the chrome back with it. Entering never sets the state directly — one owner, so it cannot race the event that reports it.
  - **Esc is not fought.** In real fullscreen the browser consumes it and exits; `fullscreenchange` then restores the header. The existing Escape handler now runs only in the fallback mode, where nothing else would.
  - **The exit button calls `document.exitFullscreen()`** in native mode, and only falls back to plain state in the refused/unsupported mode.
- **A regression this session's own harness caught, before it could ship.** `fullscreenchange` is a DOCUMENT event, so **every** mounted workspace header hears it — and with workspaces kept mounted-but-hidden, all of them collapsed and each rendered its own floating exit button (two, stacked). The listener now takes the SAME keep-alive gate the keyboard shortcut has (`headerRef.current.offsetParent === null` → ignore). The gate at the shortcut is untouched.
- **The viewport really does change size, so both surfaces were CHECKED rather than assumed.** Entering: the planner canvas grows into the reclaimed height (800 → 880 px tall) and the Leaflet basemap container re-fits with it (1334 → 1466); leaving, both return exactly. The drawing stays welded to the imagery through both transitions — the B1141 registration shift reads 0.103 / 0.528 px, inside the sub-pixel band, in and out — and the view transform is bit-identical across the round trip, so B1122's VIEWPORT-STABLE fix is not regressed. **Note for anyone re-checking:** the map container does NOT track the canvas by a fixed offset (it is the canvas plus twice the overscan, and the overscan follows the drawable element count), so asserting a constant difference is asserting a false invariant — assert the registration shift.
