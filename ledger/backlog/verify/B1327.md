**THE PANEL WAS NEVER THE PROBLEM — THE PRESS NEVER ARRIVED.** Audited before patching (AUDIT-FIRST) and the reported diagnosis held on every point: `openInspector` → `shouldInspectorTakeDock` → `setLeftPanel("properties")` is sound, the panel's render condition has no element-type gate, and `startMoveEl`'s double-tap branch is intact and unchanged. The parcel acreage badge renders `pointerEvents: auto` whenever the Select tool is up and paints AFTER `drawElsZ.above`. In SVG **paint order IS hit-test order**, so that solid pill won every press inside it. `startAcChip` stops propagation, sets no selection and never calls `isDoubleTap` — so the press produced no visible change, could not pair as a double-tap, and burnt an undo frame through a stray `pushHistory()`.

**WHY NOW.** B1186 moved the badge's anchor from `centroid()` — a vertex average that often floated clean off the lot — to `polylabel()`, the pole of inaccessibility, which is *guaranteed* inside the ring: the developed middle of the lot, where the buildings are. On the owner's own saved plan (`ui-audit/fixtures/goose-creek-plan1copy.json`) three badges moved several hundred feet and landed on two buildings and a road. Not only buildings.

**THE FIX IS THE RULE THE PARCEL'S OTHER CHROME ALREADY FOLLOWS.** The badge's hit target is gated on ITS OWN lot being selected — exactly what `setbackGrabNode` / `setbackChipNodes` do (`if (!selParcel) return null`). It still DRAWS at all times; only its press is gated, and a click on it now falls through to whatever is underneath (over the lot's own fill, that selects the lot and arms the drag). The stray undo frame goes with it.

**THE SAME BUG IN THREE MORE HATS, all fixed, because a fix that names one component protects one component — which is what B1174 already taught.**
- **The dimension grab band.** The fat transparent grab line renders only `if (dimSel)`, i.e. only once the element is selected — so press 2 of a real double-click lands on a layer press 1 just created, and `startDimMove` swallowed it. Double-click was dead in that band **by construction**, on buildings and on centerline roads alike. It now forwards to `isDoubleTap` keyed on the element's own id, the same key `startMoveEl` uses.
- **The `lastTapRef` poison.** `isDoubleTap` keeps ONE tap record, so chrome using a PRIVATE key over its own object destroys the pair AND clobbers the record. The dimension number (`eldim:${id}`) sits ON the footprint, so a body-press → number-press pair was the common case, not a corner; the pond map label (`${id}:label`) overhangs its basin the same way. Both are re-keyed onto the feature's own id. The ACTION still branches on which surface took the press — number → the inline length editor, body → Properties — so no affordance was lost; what is gone is a double-click that does nothing.
- **A reference promoted by "Draw above the plan" (B1198) — REFUTED, deliberately, and here is the reasoning.** It does take the press, but it is not the same defect and must not get the same treatment. The badge is chrome the user never asked to put there, cannot move off the building, cannot lock and cannot demote. A promoted reference is an **explicit per-reference opt-in** whose stated purpose is to sit over the plan, and it has TWO discoverable one-click ways out in the menu it was turned on from — **Lock** (pointer-transparent) and **Draw below the plan**. A markup with `behindEls: false` has behaved identically since it shipped. Making it click-through would make it unselectable on canvas, which is the regression B1198's handle-layer work exists to prevent. It is declared as a deliberate exception in the guard rather than silently unhandled.

**THE GUARD IS STRUCTURAL AND IT IS MUTATION-CHECKED, because the general rule is the deliverable.** `e2e/chrome-swallows-press.spec.js` drives the owner's real plan and asks two independent questions. **(1) STRUCTURAL:** with nothing selected, every element's own centre must answer to that element — asked of every element on the plan through `document.elementFromPoint`, the browser's real hit test, so ANY future late-painted pointer-enabled node that covers content fails here by construction, whatever it is called. **(2) BEHAVIOURAL:** a double-click opens something — driven at the element centre, and once more straight onto the dimension grab band (which the structural half cannot see, because the band lives inside the element's own group and only exists after press 1). The band was given a `data-testid="el-dim-grab"` so the repro addresses it exactly rather than guessing at an offset. **Proven red on the pre-fix code, three ways:** reverting the badge gate turns both structural tests red; reverting the grab-band forward turns the behavioural one red with the owner's exact symptom — `{"dock":"none","inline":false}`, a double-click that opened nothing.

**B1179 STAYS OPEN, and this item does not touch it.** Its inspector-close half is already explained and fixed (V562 / B1189, 3-of-3), and its module-keepalive half is stale. Its THIRD strand — "double-click a centerline road always opens Properties" — is **not** explained by this diagnosis: that spec runs on a blank site with no parcels, so no badge exists, and no handle or grab layer sits at its hit point. Do not close it on the strength of this work.

- **AMENDED 2026-08-06 by B50008–B50011 (this item is NOT re-opened; its fix stands and the CHROME-NEVER-EATS-A-PRESS rule is unchanged).** B1327's diagnosis was right about ITS cause — the acreage badge painted above the footprint and swallowed the press — but a double-click also dies when nothing eats it at all: the pair was measured on a WALL CLOCK read inside the handler (**B50008**), and the native `dblclick` never reaches the feature's node because press 1 re-renders it (**B50009**). Neither is a swallow, so neither was reachable from this item's framing. **B50011** is the audit that would have seen all three: it drives every element type and markup kind, and its `--labels` mode is what finds chrome that only EXISTS once selected — the case this item's corollary 2 names as invisible to a static reading.
