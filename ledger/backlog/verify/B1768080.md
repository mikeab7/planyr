- **AUDIT-FIRST, and it overturned B1696400's own conclusion.** That item read `Shell.jsx`'s comment ("the pairing is stored on the schedule project… a lightweight HINT is mirrored onto the site… the Schedule record stays the source of truth") and, from it, concluded `scheduleProjectName` is the linked Schedule's own, separately-editable name — a genuinely different fact from the site's name, never meant to agree. **Tracing the actual message payload says otherwise.** `Scheduler.jsx` posts `{ type: "planar:nav-link", ..., siteName: routedSiteName }` (the SITE's own current name) to the embedded schedule app; `public/sequence/index.html`'s handler calls `emitLinkChanged(siteId, scheduleId, m.siteName)` — **not** the schedule's own `name` field — straight back to the Shell, which writes it into `scheduleProjectName`. The value that lands on the site row is a **snapshot of the SITE's own name, taken once, at the instant the link was created or changed** — never the schedule's real name. And nothing ever refreshes it afterward: a later SITE rename has no write path into it, and a later SCHEDULE rename (`ScheduleOwnerList`'s rename, `nav-rename`) never calls `emitLinkChanged` either. It is a write-once cache that drifts from BOTH sides over time.

This is the exact bug, happening right now, not a hypothetical.
- **FIND THE FOUR READ SITES, as instructed — and what each renders.** `scheduleProjectName` is read in exactly four production code paths, all server-side (nothing in the client UI renders it at all — `groupProjects`/`listProjects` never carry it past `scheduleProjectId`, confirmed by grep): (1) `functions/api/mcp/_tools.js`'s `list_projects` tool → each project's `schedule.name`; (2) the SAME tool's `get_project`'s TOP-LEVEL `schedule` field (already partly correct pre-fix — it resolves the live schedule via `resolveScheduleProject`/`summarizeScheduleProject` when the backend is reachable, falling to `null` on failure); (3) `get_project`'s NESTED per-site `sites[].schedule`, via `_metrics.js`'s `summarizeSite` — this is where the internal inconsistency lived: the SAME response's outer `schedule.name` could read "MUD v PID" while the nested one read "Goose Creek"; (4) `get_site_layout`'s own `summarizeSite` call, no schedule context fetched at all pre-fix. All four are consumed by the read-only Planyr MCP connector (`/api/mcp/<token>`) — an LLM (Michael's assistant) asking "what's my Goose Creek project's construction schedule" reads straight off these.
- **THE DECISION BETWEEN (a) and (b), settled by what those four sites render.** Every one of them is displaying "what is this schedule CURRENTLY called" — never "what did the site used to be called at some past instant" — so (a) (derive at read time, from the schedule's own live record) is correct, and forcing `rename_site_group` to also write a fourth field (option (b)) would be WRONG: it would write the SITE's name into a slot that (2) above already proves is meant to hold the SCHEDULE's own, independently-choosable name once the backend is reachable — exactly the B1696400 audit's original, correct instinct, just wired to the wrong source (a stale snapshot instead of a live lookup). `functions/api/mcp/_tools.js` gained `liveScheduleNameMap(scheduleProjects)` (id → current name, from the already-fetched-or-fetchable `planar_data`); `_metrics.js`'s `summarizeSite(data, { liveScheduleNames })` now takes an optional live-name map and prefers it over the stored field. All three remaining read sites now build and pass this map: `list_projects` (it already fetches `scheduleProjects` for `schedulerOnlyProjects` — this just uses it a second way), `get_project` (the SAME fetch now feeds both the top-level and nested fields, closing the internal-inconsistency case), and `get_site_layout` (now conditionally fetches the scheduler backend when the site names a linked schedule at all). Falls back to the stored snapshot only when the scheduler backend is unreachable (`scheduleBackendError`) — a legitimate "offline read" reason to keep it, per option (b)'s own stated exception, not a reason to force-write it.
