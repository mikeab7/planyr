- **Root cause (measured):** the row hover outline is plain CSS `:hover` (`.drow:hover > [data-col-key]::before`). `:hover` follows the physical pointer, so with the mouse parked on row A and the keyboard walking the blue box to row B, both rows legitimately matched — row A by `:hover`, row B by `[data-row-sel]` — and read as two current rows. On main the harness reads `lit: 13,20` after ArrowDown with the pointer parked on 20.
- **Fix:** keyboard navigation hands the highlight to the keyboard. A document-level capture listener in `GridView` sets `data-kbnav` on the grid's scroll container the instant a navigation key goes down (ArrowUp/Down/Left/Right, Tab, Shift+Tab, PageUp/PageDown, Home, End, Enter — which covers shift+arrow range extension and Enter-to-move-down after an edit), and the hover rules are gated `[data-grid-scroll]:not([data-kbnav])` so the outline (and the grab handle's hover brightening) stops painting. **Only a REAL pointer move clears it**: `pointermove` coordinates must DIFFER from where the pointer sat when the key went down — a scroll or re-render under a parked pointer synthesises a move at the SAME coordinates, which is ignored, so a row sliding under a still mouse (keyboard scrolling) never re-lights. The attribute is set imperatively (a re-render per keystroke is not free) and nothing is stored. The selected-row outline (`data-row-sel`) is not hover and is unchanged; hover-driven interaction (the pointer actually moving) is unchanged.
- **Adjacent cases (harness, each by name):** ArrowDown/Up, Tab, Shift+Tab, Shift+ArrowDown, Home, End, PageDown, Enter-to-move-down after editing, a same-coordinate pointermove (stays unlit), a real move (hover returns), and a row slid under the pointer by keyboard scrolling; Split view uses the same GridView. Known-good arm: the hover outline must light on a plain pointer rest before any key is pressed.
