- **The report, measured not guessed.** Same plan, no edits between, export payload captured in-page (`URL.createObjectURL` hooked, anchor download blocked) rather than a PDF eyeballed. Corner zoom: `paths 44 · polygons 34 · rects 1,251 · texts 151 · images 6 · buildings 12`. Wide zoom: `paths 96 · polygons 34 · rects 1,251 · texts 118 · images 6 · buildings 11 — Building 12 absent`. Reproduced exactly on a repeat run, so not a race. **Silent**: the geometry was all there and nothing in the UI said a label had been dropped, so the sheet looked complete.
- **Root cause, confirmed against the source (the reporter explicitly asked that it be verified, not assumed — it was right).** `buildExportSvg` CLONES the live `<svg>`. B1047 flips culling off and flushes a full render first, so geometry survives; but every label decision — the `ls` size ramp, `fitLines`' LOD line-drop, `layoutLabels`' collision resolution, `dimCalloutVisible` / `detailLabelVisible` / `pondParamLabelVisible`, `dimFontPx` — reads `view.ppf`. At a wide zoom the on-screen declutter hides crowded labels and leaders the survivors out, and the clone carried that state onto the sheet. The reporter's "extra paths are leader lines" reading was correct.
- **The fix: the label tier gets its OWN frame.** New pure `lib/exportLabelScale.js`. On screen the frame IS the view (`k = 1`, so **screen output is byte-for-byte unchanged**). On an export pass it is the SHEET's own px-per-foot — the framed extent in feet against the plan box's physical size, in screen-equivalent px — so the sheet is a function of the plan and the frame only, exactly as `exportStyle.js` already claimed for strokes. Two numbers, because the units are the trap: `ppf` (what DECISIONS are made at) and `k` (label px → canvas px, so emitted sizes land at the right PHYSICAL size once the viewBox rescales the clone). Box overlap is invariant under a uniform scale + translation, so scaling every metric in the pool by `k` reproduces exactly the layout a screen render at the sheet's scale would have produced.
- **Calibrated, not re-tuned.** `SHEET_PX_PER_CENTI_INCH = 0.96` maps the sheet onto "how it reads at 100% on a 96-dpi monitor", which reproduces the ~4 pt body text the export already produced from a normal working zoom. It moves the WIDE-zoom sheet onto that reference; it does not move the reference.
- **Four more members of the same class, all found by the new harness and all fixed.** (1) The sheet FURNITURE sized itself with absolute-pixel floors (a 6-unit type floor, 0.4/0.35-unit hairlines) that only make sense when a user unit IS a screen pixel — on a wide-zoom frame the floor bit and the scale bar's numbers printed ~9× larger; `furnitureMetrics(refS, { unitIsPx: false })` on the export path. (2) `restyleExportClone` rounded retargeted stroke widths to 3 DECIMALS, which on a wide-zoom frame collapsed distinct drafting weights onto the same number and flattened the line hierarchy the retarget exists to preserve — significant figures now, same in `sheetFurniture`. (3) `strokeZoom` thickens line work with the live zoom, and the physical retarget reads the AUTHORED width through a CLAMPED map it cannot invert, so two exports printed at line weights differing by ~2× — an export pass now authors at `strokeZk = 1`. (4) Two sub-pixel visibility gates (`insetRingVisible` for the setback ring, the `FEAT_BTN_MIN_PX` reveal for the building column grid) dropped real drawn content from a zoomed-out sheet; both now measure at the sheet's scale.
- **A units rule this established, written down so it doesn't get re-litigated.** A FONT SIZE must be multiplied by `k`; a HALO / stroke width must NOT, because `printStrokeWidth` rewrites it from the authored number and its clamp would land differently per zoom. Both directions are commented at every site.
- **Guards.** `ui-audit/verify-export-label-parity.mjs` reproduces the reporter's own capture method against the REAL built app and asserts label content, label size, line weight and every geometry count (`rects` / `polygons` / `paths` / `lines` / `circles` / `images`) are identical across corner / wide / zoomed-in exports — each assertion failed before the corresponding fix, in the order they were found. `test/viewCull.test.js` gains the pure guard the reporter asked for: label CONTENT and per-label line count are view-independent, plus a case asserting the PRE-fix path fails it so the guard cannot go vacuous.
- **Why the existing guard missed it, in the reporter's own words and confirmed:** `test/viewCull.test.js` asserted "the export element count is INDEPENDENT of the viewport", which was TRUE for geometry and FALSE for text — it counted drawn geometry only. That is now closed.
