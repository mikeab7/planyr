#### Defect 1 — the feed derived schedule events and then always cut them

**MEASURED, not reasoned** (`probe-feed-month-away.mjs`, a one-month absence): 17 events derived, 12 shown, and **all 3 schedule events landed in the hidden 5 — 0 of 3 survived**. Not a tie-break, not a coincidence: a structural certainty.

**ROOT CAUSE.** `buildScheduleEvents` stamped both of its kinds — `schedule-slip` and `tasks-completed` — at `windowStartMs`. That is the OLDEST instant the change could possibly have occurred: a true lower bound, and a catastrophic sort key. The feed sorts newest-first and slices at 12, so a row stamped at the floor of the window sorts below every real-stamped event inside it. Any absence long enough to overflow the cap therefore loses 100% of its schedule rows. A date moving is the single most consequential thing that can happen while the owner is away, so this deleted exactly the rows worth keeping. The original comment argued the floor was "honest about the uncertainty" — it was honest about the INTERVAL and silent about what using it as a RANK would do.

**AUDIT-FIRST — what was checked before writing code**, since the fix depends on it. `public.planar_data` has **no `updated_at` column**, and no task object in the live document carries a temporal field of any kind (all 32 distinct task keys enumerated against production: `start`, `end`, `health`, `percentComplete`, … none records when a field last changed). So the module header's claim that nothing stamps a schedule change is CORRECT and stands. What it missed: **`public.planar_history` is an append-only ring of DATED writes of that same document** (the embedded Scheduler's own `_snapshot`, one row per save; 1,477 rows live). Its newest `created_at` is a real, observed moment.

**THE FIX, two independent halves — either alone still fails.**
1. **Stamp at a measured UPPER bound, never the floor.** `fetchScheduleLastWriteAt()` (new, in `dashboardScheduleFetch.js`) reads exactly one indexed timestamp — `select("created_at") … limit(1)`, **never `value`**, which is a ~216 KB jsonb copy of the whole schedule. A change detected by diff happened at or before that write, and after the last visit, so the row is stamped there, clamped into the window at both ends, and carries `tsApprox: true` with its real `tsEarliest`/`tsLatest` interval so no consumer can mistake the point for an exact stamp. Unavailable → the bound loosens to `now`; it never tightens to a guess (LOUD-FAILURE: degrade the precision, never fake it).
2. **Cap fairly across kinds.** Half 1 alone is not enough — a schedule last written early in a long window legitimately stamps old and would be cut again, for an honest reason this time. `capRowsFairlyByKind` reserves one slot per event kind present before any kind takes a second, then fills the rest by real recency, then re-sorts newest-first for display. With the cap at 12 against 7 kinds, **a kind present in the feed always reaches the card.** The cap may shorten the story; it may not delete it.

**THE OTHER KINDS — asked and answered, both directions.** `tasks-completed` has the **same defect** and is fixed in the same change (it is the second kind `buildScheduleEvents` emits, and was stamped `windowStartMs` identically). **No other kind has it.** `plan-created` (`sites.created_at`), `plan-renamed` (`siteRenamedAt`), `plan-edited` (`updated_at`), `comp-added` (`comps.createdAt`) and `note-written` (the synced page node's `createdAt`) every one reads a real recorded stamp off the record itself and is exact. Guarded, so the answer cannot rot: a test asserts no kind other than the two schedule ones is ever marked `tsApprox`.

**One UI consequence, handled.** The card prints `shortAge(row.ts)`, which would now read as a definite "3d" for a row whose time is an interval. Approximate rows get a `~` prefix and a hover naming the real bounds — one character and a `title`, no added copy (PANEL-BREVITY: nothing was added to the visible line).

#### Defect 2 — plan thumbnails had no ceiling, and interpolated values unescaped

**MEASURED** (`probe-thumbnail-size.mjs`): output grew linearly and without limit with how much is drawn — **185 KB at 300 elements × 40 vertices, 380 KB at 600 × 40** (503 KB as a data-URI). Four thumbnails load on every dashboard visit, so a busy account was fetching most of a megabyte for four ~180px pictures.

**THE CEILING.** `planThumbnailSvg` now bounds its own output at `MAX_SVG_BYTES` (24 KB) whatever the plan:
- **Ramer–Douglas–Peucker simplification in VIEW space** (`simplifyRing`), so the tolerance is stated in units of the picture actually shown, never in feet. It runs iteratively (explicit stack, never recursion — a surveyed ring carries thousands of vertices and this runs on the main thread right after a save) and splits each ring at its two extreme points, so closing a ring cannot collapse its far side.
- **The base tolerance is set BELOW the thumbnail's own visible resolution** (0.30 of a 400-unit viewBox against a ~180 px render, i.e. under half a rendered pixel), so an ordinary plan is simplified imperceptibly and the escalation ladder never runs at all. Coordinates also drop from 2 dp to 1 — still an order of magnitude finer than the tolerance above them, and roughly half the bytes.
- **Escalation, in the order it degrades:** raise the tolerance to a hard `MAX_DEVIATION_UNITS` ceiling; only then drop elements, smallest-area first, halving the survivor count each round so it terminates in log₂(n) passes. The boundary parcel is never dropped — a plan can degrade to its own outline, never to nothing, and with no boundary to fall back on a floor of elements is kept so a heavy plan can never render as `null`.
- **Result: 380 KB → 19.4 KB**, and a realistic plan (60 elements × 24 vertices) is not touched at all — all 61 paths still render.

**"STILL LOOKS LIKE ITSELF" IS MEASURED, not asserted by eye.** `test/planThumbnail.test.js` reconstructs each rendered ring from the emitted path data and computes the **maximum deviation from the original outline**, requiring it under `MAX_DEVIATION_UNITS`; a second test asserts the drawn content still fills the viewBox after the heaviest case. Per PERCEPTUAL-PARITY §4 the thresholds were fixed on the stated viewing reasoning BEFORE any of it was run, not tuned to make a run pass.

**THE ESCAPING.** `stroke` / `fill` / `fill-opacity` come off the user's own model and were interpolated raw into attributes, so one `"` closed its attribute early and everything after it parsed as markup — the probe's injected `"/><script>…` produced a genuinely corrupt document. It is a **rendering break, not a script-execution hole**: the result is displayed via `<img src="data:image/svg+xml,…">`, where SVG scripting does not run. Escaped anyway, because the fix is identical either way — `xmlAttr()` on every interpolation, no exceptions.

**GUARDS, and both were teeth-proved rather than assumed.** 22 tests in `test/planThumbnail.test.js` and 30 in `test/sinceLastHereFeed.test.js`. Reverting each fix in turn was confirmed to turn the right ones red: un-escaping → 3 red · removing the ceiling → 5 red · reverting both feed halves → 3 red · reverting only the stamp → 1 red. One existing test had to be **corrected rather than deleted**: `expect(row.ts).toBe(TWO_DAYS_AGO)` was pinning the defect in place, and the line now records that, so it is not re-introduced as a "fix".
