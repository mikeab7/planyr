- **Root cause #1 — `minMeetingsAfter` bypassed the existing fixed-point guard without supplying what the guard assumes it does.** `applyMeetingBinding`'s guard keeps a meeting-bound task's OWN previously-snapped start when there is no live predecessor and no driving meeting — because re-deriving from a date that is itself the search's own prior answer ratchets one meeting forward every time (a meeting's agenda deadline always precedes it, so the meeting is never "eligible" measured from its own date). The guard's condition additionally required `!minMeetingsAfter`, on the assumption that `minMeetingsAfter` always supplies an external anchor. It doesn't — `minMeetingsAfter` only ever tightens `afterDate` (a floor), never `readyDate` itself, so a bound task with no real predecessor and ONLY a `minMeetingsAfter` floor still fed its own prior `start` back into `nextEligibleMeeting`, self-referentially, and ratcheted forward one (or more) meetings every single cascade — with no bound, forever. Fixed by hoisting the `minMeetingsAfter` floor computation above the guard and folding it into the SAME early-return check (`(!minAfterFloor || packetReady > minAfterFloor) && meetingDatesInRange(...)`), so a still-eligible, still-on-calendar date is kept exactly as the pred-less case already was.
- **Root cause #2 — THE ACTUAL CAUSE ON MICHAEL'S REAL SCHEDULE, found by querying his production data directly (read-only, Supabase project `planyr_production` / `lyeqzkuiwngunutlkkmi`, table `planar_data`, the account's own `hs-v1` row).** Task 261 "HW Review" (project "Master Schedule") is a plain (non-meeting) child of summary row 259 "Contract", and its predecessor list is `[259 FS, 260 FS]` — **259 is its OWN PARENT.** A summary row's dates are ALWAYS rollup-derived from every one of its children (`rollupParentDates`, `max` of children's ends) — including this very child — so reading the parent's `end` back as a predecessor input closes a cycle no predecessor-graph check (`validatePredEdit`'s `reachesId`) can ever see, because rollup is a completely separate dependency channel from the predecessor graph it walks. `recomputeSchedule`'s 12-pass fixed-point loop grows this child's date every internal pass with no true fixed point (each pass reads the parent's just-inflated rollup, produces a still-later child end, which inflates the parent further next pass) and simply stops at the pass cap wherever it happens to land — then the NEXT PAGE LOAD resumes the same unbounded growth from that already-inflated value. Reproduced exactly (`test/schedulerEngine.test.js`, "cascade fixed point — a task naming its OWN ANCESTOR") using Michael's real task shape.
