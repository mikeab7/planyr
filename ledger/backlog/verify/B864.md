Owner's words fit a stale-tab clobber ("maybe I went over to a tab that didn't update"): the app cloud-saves the WHOLE document last-write-wins, so a second tab lacking the just-created body saved over the tab that had it.
- **Why it bites:** on a fresh load, `cascadeDates` sees `meetingBound:true` but no body in `bodyMap` → `bound=false` → the task falls back to a plain FS date (loses the election date), and **B836's drift guard would then "heal" #88 away from 2027-05-01** to that wrong FS date (a loud rewrite of an intended date).

- **(a) CODE HARDENING — IMPLEMENTED + sandbox-verified 2026-07-16 (own PR, per the meeting-binding/`cascadeDates` own-PR rule):** `cascadeDates` now computes `bodyMissing` (a `meetingBound` leaf whose `meetingBodyId` isn't in the body index) and, when the task HAS a stored date, **soft-pins it** (`t.pinnedStart || (bodyMissing && t.start)`) so preds can't overwrite the intended meeting date + sets `t.meetingBodyMissing`; a bound task with NO stored date still falls through to normal FS scheduling (unchanged). `detectCascadeDrift` now **exempts** `meetingBound` + `deadlineForTaskId` rows (their dates are calendar-/anchor-derived, not simple-cascade drift — like pins), so a legitimate re-snap (or a preserved orphan) never fires the drift banner. - **(b) ROOT CAUSE — IMPLEMENTED + sandbox-verified 2026-07-16 (own PR):** the whole-document cloud-save was last-write-wins with a rev-gate that only BLOCKED a stale tab (snapshotting the loser to history + forcing a reload that dropped its edits) — so a sibling's just-created calendar was lost when the other tab won. **AUDIT-FIRST correction to B850's "Scheduler is two-tab-safe" claim:** the guard blocks the *loser*, but the loser's changes never reach the cloud, and the write itself (`sb.upsert`) is an unconditional whole-doc overwrite — no field-level merge. **Fix:** on a would-be-blocked auto-save the storage layer now **3-way MERGES** our edits onto the newer cloud (`mergeCloudDoc(base, ours, theirs)`, module scope + mirrored/unit-tested in `scheduler-engine.mjs`) instead of blocking: base = the doc this tab last loaded/saved (`baseByKey`), ours = current, theirs = the newer cloud. A side unchanged vs base yields to the changed side; id-keyed arrays (tasks / meetingBodies / contacts) merge per element by id (adds survive, a delete is honored only if the other side left the key alone); a genuine same-leaf conflict prefers ours, the loser kept as a `premerge-ours` Version-History snapshot. The App adopts the merge via a `planar:merged` event, **reconciling against its CURRENT state** (`mergeCloudDoc(ancestor, current, merged)`) so an edit made during the save round-trip is never lost, + a "Merged in changes from another tab" toast. Falls back to the old block-and-snapshot only when no base ancestor exists (seed/offline). **14 merge unit tests** (the exact election-calendar repro: a stale tab's save preserves the sibling's calendar + binding + its own edit; keyed-array add/delete/conflict; nested project add; missing-base fail-safe) + a full node simulation of the two-tab flow incl. an in-flight edit. Full suite (4188) + lint 0 + build green; `index.html` babel blocks esbuild-parse-clean; `MAP.md` regenerated. **→ V347** (the live two-tab race is a mandatory concurrency LIVE-VERIFY class — can't drive two signed-in boards headless). Residual (smaller, noted): a true simultaneous read-check-write TOCTOU (both tabs at the same rev racing the unconditional upsert) is not closed by this — an optimistic conditional write is the follow-up; the merge handles every non-simultaneous ordering.
