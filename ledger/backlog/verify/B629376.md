- **INDEXING — trigram (GIN), not prefix. Said which and why, as instructed.** A restaurant name is usually multiple words ("Bandito's Taco Grill"), and he's far more likely to type one distinctive word ("taco") than the exact start of the string — a prefix (b-tree) index only ever matches from position 0, so it would miss every one of those. `pg_trgm`'s `word_similarity()`/`<%` finds the best-matching SUBSTRING of a longer name against a short query, which is what a search-as-you-type box actually needs. GIN over GiST: slower to build/update, faster to query — right trade for a table that's bulk-loaded once or twice a year (see the module's CLAUDE.md) and read constantly. Index: `gin (lower(name) gin_trgm_ops)`. Threshold 0.3 (pg_trgm's own default, 0.6, is tuned for long-document search and misses short/close variants — measured: "mcdon" scores 0.83 against "McDonald's," comfortably above 0.3 and nowhere near 0.6's neighborhood for a query this short).
- **MEASURED DIRECTLY AGAINST PRODUCTION, not assumed.** `EXPLAIN ANALYZE` confirms the GIN index is actually used (`Bitmap Index Scan on food_places_name_trgm_idx`, never a sequential scan over the 34,000+ rows). Real queries: "taco" → 15 genuinely taco-named places in ~30-50ms (`1 Taco Mas`, `Azteca Taco House`, `Bandito's Taco Grill`, …), "sushi" → 8 genuinely sushi-named places, "mcdon" → `McDonald's` at 0.83 similarity (fuzzy/partial match working), a nonsense query (`zzznonexistentxyz`) → zero rows, not noise padded out to fill the cap. 30-50ms is comfortably inside a 220ms debounce window — the box never feels like it's waiting on the network.
- **DEBOUNCE + CAP, tuned for "feels instant on a phone."** 220ms debounce, a 2-character minimum before firing (typing "t" alone never hits the network), and the RPC itself caps to 15 candidates so client-side "his places first" reordering has headroom to work with before the visible list is sliced to 10. A stale in-flight request is discarded if a newer keystroke has already superseded it (a request-counter guard, not just a debounce timer) — no chance of an old response overwriting a newer one that lands first.
- **HIS OWN PLACES RANK FIRST, and are visibly marked.** Two sources feed "his own": every snapshot place he's already logged (cross-referenced against the same `loggedIds` set the map already uses) AND manual pins (which live entirely outside the snapshot — a client-side substring match against the small, already-in-memory `manualPins` array, since there's nothing to index there). Both are bucketed ahead of unlogged snapshot matches, each bucket keeping its own relevance order; a logged/manual result carries a small "Been here" mark in the dropdown, not just a silent sort position.
