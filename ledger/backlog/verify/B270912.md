- **THE MEASUREMENT.** `public.client_errors` took 679 rows in 24 hours; of 98 `event:perf` rows **87 were automated and 11 were the owner's — 89% noise**. Non-perf was the same story (`assembly-orphan-pad-repaired` 154 · `map-registration-out-of-range` 119 · `assembly-tear-persisted` 91 · `assembly-tear-detected` 65 · `county-healed` 47, all carrying e2e fixture ids), and #954's new logged-out CI lane had just multiplied the rate. Re-measured from the database this session: **5,162 rows · 410 in the last 24 h · 2,174 in the last 7 days · 3.2 MB · oldest 2026-06-20.**
- **WHY IT IS NOT TIDINESS.** #951's recorder exists so the owner pressing *"that felt slow just now"* reaches somebody. That capture was arriving as one row among several hundred synthetic ones a day, separable only by a READ-SIDE filter on his display signature — a workaround, not a design. **An instrument that buries the signal it was built to catch** is the class this repo has now caught six times: the swallowing sink (B265536), the frame-count sustain window, the packed track that emptied on real stalls (B265541), the drift gate's invented fixture (B266086), the growth harness whose plan B was plan A halved. A genuine production incident would have arrived buried the same way.
- **⛔ THE PREMISE OF THE BRIEF WAS FALSE IN THE FIELD, AND THE FIX TURNS ON IT (AUDIT-FIRST).** The dispatch said to gate on `window.__PLANYR_E2E`, citing `docs/perf/PERF-PLAN-SWITCH.md` §1 — *"every performance harness in this repo sets"* it. For the **ui-audit perf harnesses that is true**; for the **e2e suite it is not**, and the e2e suite is where the measured noise comes from: **62 of the 81 specs in `e2e/` never set it**, `assembly-tear-detector.spec.js` — the top producer of three of the five loudest sources — among them. **A flag-only gate would have silenced 19 specs, left every top row untouched, and reported success.** So the primary detector is **`navigator.webdriver`**, which the browser sets itself under any automation protocol, is never true for a real user, and needs no per-spec discipline — it therefore holds for harnesses nobody has written yet. `__PLANYR_E2E` stays as a second door.
- **THE FIX.** `clientErrors.networkReportSuppression(win)` — a pure, exported, unit-tested decision (`automated && !optIn`), checked at SEND time in `sink()`. It **FAILS OPEN**: every unreadable branch returns "not suppressed", because silencing a real user over a throwing property read is strictly worse than one extra test row. Only a strict `true` counts, in either direction.
- **⛔ THE TRAP, WHICH IS THE WHOLE DIFFICULTY.** `verify-capture-pipe` proves the row reaches the wire, and its `rejected`/`offline` arms are the anti-rot half that proves a BROKEN delivery is LOUD — and **both run under automation**. Suppress unconditionally and that verification is disabled by its own fix, passing forever while observing nothing: the sixth instance of the class this closes. So the harness opts in DELIBERATELY (`window.__PLANYR_TELEMETRY_NETWORK`), and **both directions are asserted**.
- **THE LOCAL CAPTURE IS UNTOUCHED** — only the network write is suppressed. `pfTelemetry.recent()`, the IndexedDB capture store and the Storage panel all still work under test, which is what `verify-telemetry` and `assembly-tear-detector.spec.js` read (both re-run green).
- **SUPPRESSED IS NOT UNDELIVERED, and they never share a counter.** `_delivery.suppressed` / `pfRec.state().suppressed` are their own; `undelivered` keeps meaning *the server never acknowledged*. Folding them together would make every harness run look like a delivery failure, which is how a real one stops being noticed. The owner's button gains a third state, **`local`** — an automated run must not tell him the server is unreachable about a pipe that is working.
- **PROVED BOTH DIRECTIONS, AND PROVED THE GUARD CAN FAIL** (DANGEROUS-MEANS-UNOBSERVABLE (b)):
  - clean run — **all 5 arms green**, 12 perfcap rows on the wire from the opted-in arms, **0 writes to `client_errors`** from the suppressed one;
  - **MUTANT A**, suppression made unconditional (the opt-in ignored) → **7 assertions red** across `manual`, `manual-cold`, `rejected`, `offline` and `row` — the pipe guard cannot be blinded silently;
  - **MUTANT B**, suppression removed → **4 assertions red**, including **5 telemetry rows reaching `client_errors`** (a `window.onerror` among them — so error rows are covered, not just perf).
- **A REAL IMPRECISION THE ARM CAUGHT IN ITS OWN FIRST RUN, recorded rather than quietly loosened:** it asserted *"no request of any kind"* and failed on `/auth/v1/health`. Supabase is also this app's DATA backend — an automated run legitimately signs in and reads plans — so the claim is about **`public.client_errors`**, and every other request the page made is now PRINTED rather than ignored, so a future write to some other sink cannot hide behind the narrower claim.
- **⛔ NOTHING WAS DELETED, AND NO READ-SIDE FILTER WAS ADDED** — both were explicitly out of bounds. The table was READ only. Retention is a separate item and a separate decision: **B270913**.
- **A finding for whoever reads the table next:** 0 of the 410 rows in the last 24 h are identifiable as automated by `user_agent` or `url` (CI drives a real Chromium under xvfb against the deployed origin). **There is no server-side way to tell a test row from a real one**, which is why the read-side workaround had to key on his display, and why a client-side gate is the only correct fix — no cleanup query could ever have separated them.
