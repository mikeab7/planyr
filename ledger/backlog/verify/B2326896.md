- **What ships:** `annotationExtract` lifts each building (`isBuilding`: type building, not a bump-out) together with its label node(s) and returns a `family: "building"` descriptor carrying the model's footprint ring (`hints.verts`, `f2p` → PDF through the same M0 a cloud uses). `pdfAnnotations.buildAnnotations` writes a Polygon, Subject "Building", Contents = the label text, with the existing `flattenTree` appearance (fill, outline, dock doors, dimension, label — one renderer, no second path) and regeneration inputs (/C outline, /IC fill, /CA, /BS) read from the footprint's own fill and outline rather than the first ink item (a dock door). Flatten ON is untouched (extraction is never called).
- **Parity decisions (stated):** (1) a building is held to the stricter bar of the flattened picture — any LATER page content that overlaps it (another element drawn over it, a reference drawing or lifted GIS layer, an easement line) keeps it in the page, because a lifted building would paint over that content; an empty GIS band, a court that merely touches it, and thin parcel/label linework do not. The pin pass is top-down, so a markup sent behind the plan under a building is pinned in the page and the lifted building paints over it, as on screen (no need to pin the building). (2) **Found by the parity render, not by reading the code:** a lifted building's opaque fill covered the parcel's acreage chip ("Parcel 1 24.79 AC") that paints ABOVE buildings on screen — the chip now travels inside the topmost overlapped lifted building's appearance and leaves the page, so the default export is identical. Cost: move the building and the chip moves with it.
