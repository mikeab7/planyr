- **⛔ THE DIAGNOSIS IS STRUCTURAL, NOT COSMETIC, and the owner had it right.** B1449 (#952) put the switch in the flyout that opens off the PLAN NAME in the breadcrumb (`Bain / Concept - Original`). The commit called that the "Plan menu" and **the UI carries no such label anywhere** — which is itself why it could not be found. That menu is otherwise entirely plan-scoped: plan name · plans in this site · New plan · Duplicate · Save now · Version history. Smooth zoom is not plan-scoped at ALL — it is a per-DEVICE rendering preference persisted in `localStorage` under `smoothZoom`, so it follows neither the plan, the project nor the account. The on-canvas **View ▾** menu already owns exactly that class of state (B653: dock doors, column grid, dimensions, areas, grid size, snap).
- **WHAT MOVED.** One row, out of `SitePlanner.jsx`'s plan `AnchoredMenu` and into `components/ViewMenu.jsx`, below the grid/snap group behind its own divider. The card's hover text gained "and how zooming redraws".
- **WHAT DID NOT CHANGE — pinned by assertion, because a relocation that quietly flips a default is a behaviour change wearing a refactor's clothes.** The key `planarfit:smoothZoom` · the default (ON) · the `disarmViewAnchor()` call on turn-off, still in the same commit as the persist · the title text, carried over verbatim · `data-testid="smooth-zoom-toggle"`, which still addresses the clickable row.
- **ONE DELIBERATE DIFFERENCE, stated rather than buried.** The old control was a `<button>` carrying a ☑/☐ glyph and a `role="menuitemcheckbox"` + `aria-checked` pair. In the View card it is a real `<input type="checkbox">` in a `<label>`, exactly like the four rows above it — so the checked state is NATIVE, there is no `aria-checked` to keep in sync, and the fake role is gone (`menuitemcheckbox` is invalid outside a `menu` container anyway, so keeping it would have been strictly worse).
- **⛔ DISCOVERABILITY WAS THE POINT, SO IT WAS CHECKED RATHER THAN ASSUMED.** The View card is NOT crowded: it now holds four visibility checkboxes, Grid (ft), Snap, and Smooth zoom — seven rows in a card that already scrolls with the Layers panel beside it. It is a labelled, always-visible affordance on the canvas the setting affects, which is the opposite of the unlabelled flyout it came from. No third home was needed and none is proposed.
- **⛔ THE SECOND HALF THE OWNER ASKED ME TO JUDGE — "Storage on this device…" — AND I DECIDED **NOT** TO MOVE IT. Stating it, per his instruction not to move it silently.** He is right that it has the same shape (device-scoped row inside a plan-scoped menu) and right that it is the weaker case. Two things decide it:
  - **(a) The View menu is the WRONG destination for it.** Storage is not a view or rendering preference; putting it there would trade one mis-filed row for another and make the View card mean two things.
  - **(b) The RIGHT destination is measured shut.** The natural home is the row-1 Settings gear (⚙), which already holds Light/Dark/System and is reachable signed-out. But `src/shared/CLAUDE.md` records why `StoragePanel` is mounted from the plan menu in the first place: **the header gear and `AuthPanel` land in the entry chunk EVERY route downloads, and even a lazy stub there cost +0.8 KB on all four routes and breached the Notes route's bundle ceiling in CI.** That is a measurement, not a preference, and it has not changed.
  - **SO THE DEFECT WAS FIXED WHERE IT ACTUALLY LIVES: the row didn't say what it was scoped to.** The plan menu now carries a `This device` caption above it — the same small-caps section header the menu already uses for `Plan name` and `Plans in this site`. One muted line instead of a bundle breach. If the gear ever stops being on the entry chunk, move it; the reasoning is written at the call site so the next session does not have to re-derive it.
