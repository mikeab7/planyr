### B2061600 — Select-parcels outlines hitched on every zoom/pan settle at site-scale zoom (Georgia): per-tile cached canvases replace the map-sized canvas that reprojected every held lot `[map-finder]` (bug) #site-planner #gis #parcel #perf  *(Owner report 2026-10-03 (NEW-1), Bartow GA site A010-0202-001, build 2feca52. **Amends B1976336** — that item fixed correctness/queries (verified live); this is its smoothness half. DEDUPE-FIRST: recurrence of B1976336's perf concern, minted separately because the cause and fix are a different layer.)*

- Verify: live — **V1486288** (Michael's Chrome, Bartow z14–16). Sandbox proof below.
- **Measured by Michael (his Chrome, renderer `_update()+_redraw()`):** z16 6–8 ms (767 in view) · z15 37–51 ms (8,230 held) · z14 75–94 ms (16,702 held, 7,124 in view). Cost scaled with what was HELD. **AUDIT-FIRST confirmed in code:** every held esri-leaflet child was a Leaflet `Path`, and a Path registers `zoom:_project` + `moveend:_update` on the map, so each settle re-projected/re-clipped/re-simplified ALL held lots before the canvas redrew them.
- **Fix (`lib/parcelTileLayer.js` new, `lib/parcelDisplay.js`):** (1) a held lot is now a `ParcelGhost` — a bare Leaflet Layer keeping `.feature` + `getBounds()` (the ONLY two things the hit-test `optimisticHitAt`, hover attach and export read — **B137 holds: what you see is what you can select**) and registering no map events; ghosts never go through `map.addLayer/removeLayer` (`createLayers/addLayers/removeLayers` overridden one-for-one). (2) The picture is a `GridLayer` of 512-px per-tile cached canvases drawn from a bucketed `ParcelIndex` (a settle draws only tiles it has not; a pan reuses tiles; later-arriving lots repaint only the tiles they touch, once per frame; canvases pooled). (3) Two O(n) costs found by profiling the same settle: esri-leaflet's `_addFeatures` deduped ids with `Array.indexOf` over everything held (now a Set per call), and `candidateCountiesForPoint` ran `Object.entries` on the 175-key normalising Proxy `COUNTIES_MAP` ×81 sample points per settle (~19 of ~24 ms; now read once, plus a per-view memo of `displaySourcesForView`). Hover/selected styling is untouched (the highlight is a separate layer); the z13 "zoom in a little" hint is untouched (`minZoom` unchanged).
- **BEFORE → AFTER (headless Chromium, Bartow-density mock, 9,842 lots held at z14, both builds served on their own ports with the chunk hash read in the same run — a stale preview server cost three earlier comparisons, see below):** z14 `moveend` settle (data held, nothing moving) **103.7 → 0.8 ms** · z15 **15.0 → 0.7 ms** · z14 zoom settle **87 → 14 ms** · z14 pan settle **54 → 3 ms** · z15 zoom 28 → 12 ms · z15 pan 17 → 3 ms. - **Harness traps recorded (carry-forward):** (a) `vite preview --outDir X` **silently moves to the next port when its port is taken** and `kill $!` of an `npx` wrapper leaves the real server running — so an "old vs new" run can hit one build twice. Three comparisons here were invalid for exactly that; start `node node_modules/vite/bin/vite.js preview … --strictPort` and read the served chunk name in the SAME run. (b) A mock that answers a /query instantly lands feature ingestion INSIDE the timing window; delay the mock (350 ms) and wait for data between windows. (c) Waiting for the next `requestAnimationFrame` measures vsync (0–16 ms of nothing); count CPU in the callbacks instead.
