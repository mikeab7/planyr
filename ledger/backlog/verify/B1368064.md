**WHERE THE THUMBNAIL LIVES, stated plainly (the brief asked this be decided and said so).** `public.sites.thumbnail_svg` (text) + `thumbnail_updated_at` (timestamptz) — `src/workspaces/site-planner/db/site_thumbnail.sql`, applied to production (`lyeqzkuiwngunutlkkmi`). The thumbnail is an **SVG string** (a few hundred bytes to a couple KB — a handful of `<path>` elements, no raster), not a rasterized image in Storage: it rides in the same `sites` row the Dashboard already selects for every other card (`dashboardSitesFetch.js`), so showing four thumbnails costs the Dashboard's existing single query two more lightweight columns and zero extra round trips or signed-URL plumbing. It is deliberately a PLAIN column, not part of the CAS/version-guarded `data` jsonb: TIER-BY-REBUILDABILITY (it's always regenerable from the plan's own geometry) plus "exactly one writer per plan, nothing to conflict over" argue against routing it through cloudSync.js's already-heavily-guarded content-merge engine. Full reasoning in that migration's own header.

**HOW IT'S RENDERED.** `site-planner/lib/planThumbnail.js` — a pure, DOM-free function that turns a plan model into an SVG string, reusing the exact geometry/style primitives the live canvas is built on (`elToRingFeet` + the `TYPE` palette from `planStyle.js`, paint-ordered by `byZ`) rather than a second implementation. Given only plan JSON (no React tree, no Leaflet map, no mounted `<svg>`) — unlike `exportSheet.js`, which clones the LIVE canvas and needs one mounted. Boundary = active parcels only (stroke-only by default, matching the canvas's own unfilled-unless-set convention); every drawn element (building/paving/parking/trailer/pond/sidewalk/landscape/road) painted in the app's own TYPE colors. Output is a fixed 4:3 viewBox, content contain-fit (padded, centered, aspect preserved), background-transparent — dropped straight into `<img src="data:image/svg+xml,...">`, so it stays crisp at any size with zero rasterization cost. Returns `null` when nothing is drawable (the empty-panel-with-name case).

**WHEN IT'S GENERATED — both halves the brief asked for:**
1. **Refresh on save.** `site-planner/lib/storage.js`'s `pushSiteToCloud` calls `siteThumbnail.js`'s `refreshSiteThumbnailFromModel` fire-and-forget after every REAL (non-skipped) cloud push, using the model already in memory. Dynamic-imported so this never rides `storage.js`'s own critical-path weight.
2. **Lazy, once, for a plan with no thumbnail yet.** Every existing plan (saved before this shipped) has `thumbnail_svg: null`. `RecentPlansCard.jsx` calls `dashboard/lib/recentPlansThumbnailFallback.js` (a dynamic-import bridge, so the Dashboard's own bundle never carries the weight) for exactly the up-to-4 shown plans that are missing one, which reconstructs a renderable model from the row-synced element engine (`elementApi.fetchElements` + `elementRows.rowsToModel` — the SAME reconstruction the planner itself uses to open a plan, not a hand-rolled second one) and writes the result back — `""` (empty string) is a deliberate sentinel meaning "tried, nothing drawable," so a genuinely blank plan is never re-fetched and re-rendered on every dashboard visit; only `null` (never attempted) triggers a(nother) generation.

**DELETION.** `dashboardSitesFetch.js`'s existing query already filters `deleted_at is null` and sorts `updated_at desc`; a project delete soft-deletes every plan sharing its `group_id` (`cloudSync.cloudDeleteGroup`), so that one filter already excludes a deleted plan AND every plan of a deleted project — there is no separate flag to check and no gap to "fall through": taking the top 4 of an already-filtered, already-sorted list IS the fallthrough behavior. `dashboard/lib/recentPlans.js`'s `pickRecentPlans` is the pure selection (unit-tested).

**LAYOUT.** Joins the arrangeable grid exactly like every other card (`CARD_DEFS.recentPlans` in `dashboardLayout.js` — default 6x8, min 4x5 — draggable/resizable/removable/in the Add-a-card picker, verified headless in Customize mode: drag handle, resize corner, and remove × all present). `dashboard/lib/recentPlansLayout.js`'s `recentPlansLayoutMode` (pure, unit-tested) measures the card's own content box via `ResizeObserver` (the same pattern `NeedsAttentionCard.jsx` already uses) and drops from a 2x2 grid of four to two side-by-side thumbnails before any thumbnail would render below `MIN_THUMB_PX` (84px) — "recognizable" is enforced as a real floor, not a vibe. Empty state (0 plans): one short italic line, no padding with blanks.
