- **THE SHIP — a paired event (`source='event:chunk-recovery'`), because the recovery row cannot be the failure row.** A rescue's mechanism is that the page NAVIGATES: the tab that would report success is destroyed by the fix. So an EPISODE record rides `sessionStorage` across the reload (`RECOVERY_KEY`), and the page that comes back says so itself. Six outcomes: `reload` · `stuck` · `cooldown` · **`landed`** (a `?_r=` page booted — the reload delivered a document that runs) · **`recovered`** (landed, and nothing failed in the 15 s that followed) · **`left`** (an episode was open and the tab escaped some other way — the user rescued themselves, which is not the guard working). Each carries `n` reload ATTEMPTS, `f` failures, the chunk, and the build it came from and landed on.
- **⛔ THE LADDER, and it is a correctness property rather than tidiness.** A paired event carrying a rising counter has a fresh signature every time, so it slips `decideReport`'s 10 s dedupe **entirely** — a naive version would have written a row per cursor move and manufactured the noise it was built to explain. Rows go out on a 1-2-5 ladder (1, 2, 3, 5, 10, 25, 50, 100, 250…) with the true count riding each one: the 2 h 20 m episode costs **about ten rows instead of eight hundred**, and its last row still states its real size.
- **⛔ THE EPISODE EXPIRES (30 min).** Without that, one long-lived tab ratchets the attempt counter forever and every number after the first is a lie.
- **`RECOVERY_SETTLE_MS` IS 15 s, NOT 2.** The chunk that fails is fetched by a route mount or a first interaction, not by the entry script — a page that has merely booted has not yet re-attempted the import it died on, and a short window would call every episode recovered before the failing import was tried. Silence for the settle window is the weakest claim the data supports and it is the one made.
