`[x]` **MEASURED FIRST, per the brief's own instruction not to assume the stated hypothesis.** The hypothesis (re-rasterising the overlay image on every tick) is REFUTED by reading `rotatedImageLayer.js`'s `setOpacity` — it is `img.style.opacity = String(op)`, a plain CSS write, no canvas, no re-decode, confirmed unchanged by this fix. **The real cost was the PERSISTENCE path**: `SitePlansSection.jsx`'s old `setOpacity(o, opacity) => patchAndReload(o, { opacity })` ran on every `onChange` event a range input fires while dragging (not just on release) — each call did one Supabase `UPDATE` (`updateOverlay`, itself a CAS/version round trip) **plus** one full `fetchAllOverlays()` re-fetch and re-render, serialized (queued, not concurrent, but never skipped or coalesced) per overlay id. A rapid drag firing dozens of `input` events therefore queued dozens of full network round trips — an actual, measurable machine-slowing cost, just not the one hypothesized.

- **Fix**: opacity is now applied LOCALLY on every tick (`setOpacityLive` — updates `overlays` React state directly, no network call; the map already reads `o.opacity` off that same state via the existing CSS-only path, so the drag stays compositor-only exactly as expected) and the actual Supabase write is DEBOUNCED to one call per 300ms pause, flushed immediately on `onMouseUp`/`onTouchEnd`/`onKeyUp` (`flushOpacityWrite`) so the final value never sits waiting out the debounce window for no reason after the user lets go. A typical ≤1.5s drag that could previously queue dozens of writes now queues roughly one (mid-drag pauses aside) plus the guaranteed one on release.
