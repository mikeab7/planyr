- **MEASURED on his machine, ONE double-click on the easement:** `pointerdown#1 → polygon[easement hatch]` · `click#1 → polygon` · `pointerdown#2 → polygon` · `click#2 (detail:2) → svg` · `dblclick → svg`.
- **CAUSE:** a click's target is the **common ancestor of its down and up targets**. The first press selects the feature, React re-renders it, the node the browser was holding is gone, so the event collapses to the root `<svg>`. The `onDoubleClick` handlers on the easement/line/polyline `<g>` and on the three element groups were **UNREACHABLE in exactly the case they exist to cover**.
- **The source comments calling the native path "a fallback for when pointer capture doesn't suppress the native dblclick" were WRONG IN PRACTICE — corrected, at all four sites** (`onElDouble`, `onMarkupDouble`, the callout box, and the shared note). They are kept only for a harness dispatching a raw `dblclick` AT a node, where no point hit-test exists, and they now delegate to the same one action so they cannot drift.
- **CHOICE, and the other option was considered:** the gesture is resolved **AT THE `<svg>` ROOT by hit-testing the point**, not by keeping the hit node's identity stable across a selection re-render. Stabilising identity means promising that nothing in a feature's subtree remounts when it becomes selected — but selection is exactly when this canvas grows chrome (grips move to the handle layer, the dimension grab band appears, halos mount), so every future render change would silently re-break the gesture with nothing able to see it. The root is always there, and WHAT was double-clicked is answered by asking the browser what is under the point — **the same hit-test that decided the press targets**, so a second geometric hit-test can never disagree with it. `lib/featureTarget.js` is the pure half; every feature's outermost group now stamps `data-feature="<kind>:<id>"`.
- **ONE DECISION, NOT TWO.** The contract had two implementations and they had already drifted: `onElDouble` opened Properties for a LOCKED element while `startMoveEl` refused to, and nothing could notice because the native route was unreachable. Both routes now call `featureDoubleAction`, and the source guard checks **delegation** rather than an `openInspector()` at each call site — checking each site is what permitted the drift.
- **GUARD — the dblclick's own TARGET is asserted, not just that Properties opened**, so B50008's fix cannot mask this one: `e2e/dblclick-properties.spec.js` records every `pointerdown`/`click`/`dblclick` from a capture-phase listener and asserts a press that landed squarely on a feature was delivered as a click on the bare root. **WHICH event loses its target moves with machine speed** (his busy plan lost `click#2` and `dblclick`; an idle machine loses `click#1`), so the invariant is asserted rather than one trace — pinning a specific event would pin the machine, not the defect. A second case dispatches a `dblclick` whose own target IS the bare `<svg>`, with the reconstructed tap deliberately out of the picture, and asserts Properties opens: **proven RED with the root resolver removed.**
