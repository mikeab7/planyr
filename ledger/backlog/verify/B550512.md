- **AUDIT-FIRST — what the brief assumed vs. what the code actually does.** The brief's working theory was that export "clones the live SVG, so whatever is on screen is what lands on paper," and that a coarse loading-placeholder tile seen on screen could get baked into a PDF. Read against the real code (`exportSheet.js`), that is only true for the DRAWING (buildings, parcels, text) — the aerial is a separate Leaflet `<div>` tagged `data-export="skip"` and is never part of the clone. **B839 (already shipped) independently re-stitches the aerial from freshly-fetched tiles at a zoom it computes for the print frame** — it never reads the screen's tile `<img>` elements at all, so a coarse mid-load screen tile cannot reach an export today. Two of the four requested steps were therefore already true and needed no code change, confirmed rather than assumed:
  1. **"Never bake a coarse fallback tile" — already the case.** `stitchAerialDataUrl`'s base fetch is STRICT (any missing tile → the whole stitch is discarded, never a partial/gappy or mixed-zoom composite) and always requests the exact `{z}/{y}/{x}` the print frame needs, never whatever the live map happened to be showing.
  2. **"Scope the fetch to the sheet, not the viewport" — already the case.** The bbox comes from `exportFeetExtent` (the print frame, or the drawn content's bounds +60ft) — never the panned/overscanned map viewport.
- **WHAT WAS ACTUALLY SOFT, measured with the real pure functions (`pickAerialTileZoom`/`aerialTileGrid`) against representative site sizes before touching any DOM code:**

      site width   picked zoom   vs. Esri's native ceiling (z19)
      2,000 ft     z19 (native)   already sharpest possible
      3,000 ft     z18            one level short
      5,000 ft     z18            one level short
      8,000 ft     z17            two levels short

  `stitchAerialDataUrl`'s zoom picker keeps the stitched canvas under a fixed **3,072 px** cap so the tile count stays bounded — the right call for fetch cost, but a cap with no relationship to what a page actually needs, so it silently gives up sharpness for any site whose printed frame is wide enough to cross it. Below ~2,500 ft (roughly 100+ acres square) the export was **already at the source's ceiling** — nothing to fix there; **above it, every extra acre cost real sharpness for no reason tied to the budget.**
- **THE FIX — budget-driven, not a bigger fixed cap.** `deepenZoomFor(z, maxNative)` (pure, `arcgis.js`) names exactly ONE zoom level deeper than the base pick (≈2× linear resolution — the same ratio the live map's `detectRetina` retina uplift already uses, B170), capped at the source's native ceiling, returning `null` (zero extra requests) once already there. `stitchAerialDataUrl` (`exportSheet.js`) fires this "sharpen" tile set ALONGSIDE the existing base fetch, each tile racing an `AERIAL_DEEPEN_BUDGET_MS = 1000` deadline (one named, easy-to-tune constant — his "+1s fine, +5s not" stated as a ceiling, not approached); whichever sharper tiles land in time are drawn over the (upscaled) base image, and any that don't are simply left as the base — never a hole, never a wait past the budget.
- **⛔ THREE THINGS MEASURED AND FIXED ALONG THE WAY THAT A NAIVE VERSION OF THIS WOULD HAVE MISSED — each one found by testing the real DOM code in a real browser, not by reasoning about it:**
  1. **Dispatch order matters even with a priority hint.** Firing the (larger) sharpen tile set at the same time as the base fetch let it grab the browser's connection pool first, delaying the STRICT base fetch itself — measured 3s+ for a call that should stay sub-second. Fixed by dispatching the base fetch first and marking the sharpen tiles `fetchPriority: "low"`.
  2. **Giving up locally doesn't free the connection.** A first version raced each sharpen tile's promise and just stopped awaiting it at the deadline — the underlying request kept running in the background regardless, and the pile of abandoned-but-still-active requests grew enough to starve the base fetch a second way (6s+ observed). Fixed by genuinely aborting (`img.src = ""`) the instant a tile's own deadline passes, the same technique the existing per-tile timeout already used.
  3. **A worker pool, not a `Promise.all` burst.** The sharpen set is fetched through a bounded 24-wide concurrency pool (`DEEPEN_CONCURRENCY`), not fired all at once — a burst of 150–240 simultaneous requests (what a real "one zoom level deeper" frame needs) is enough to contend with the base fetch regardless of `fetchPriority`, under both an HTTP/1.1 mock (Chromium's ~6-connections-per-origin cap) and an HTTP/2 mock (Node's own default 100-stream cap). Bounding OUR OWN concurrency removes the dependency on guessing the transport's ceiling.
- **RETINA / @2x, established rather than assumed.** Queried Esri World Imagery's own `tileInfo` live: one fixed 256px/96dpi tile set, no `@2x` variant at the same zoom (a literal `@2x` URL suffix round-trips as an ordinary 200, ignored). This matches why B170's live-map retina fix works by requesting `z+1` rather than a distinct high-DPI asset — there is no free lever here; a deeper zoom is the only one, which is exactly what this item spends its budget on.

  Resolution figure, plainly: Esri's imagery tops out near **1 pixel per foot** even at its sharpest zoom — this fix roughly **doubles that to ~2 px/ft** for any site large enough to have been capped, which is a real, visible reduction in how upscaled the aerial looks on paper. **Stated honestly, not oversold: it does not fully close the gap to photographic 300 DPI sharpness at a tight print scale** (which can want several pixels per foot) — that is a ceiling on the SOURCE imagery's own resolution, the same ceiling B169 already documented for the live map, and the reason B171 (a higher-resolution licensed source) exists as its own gated item rather than something a fetch strategy can solve. This fix gets everything achievable out of the free source within budget; it does not pretend to be that separate, larger, currently-gated fix.
