- **The interaction, decided deliberately (key design point a).** "Stops silently accepting edits until reload" — never reload-and-reapply. `cloudUpsertCore`'s existing one-shot self-heal (refetch the fresh version, retry ONCE, whole-header last-write-wins — B672) is the safe, already-shipped case and is untouched: it resolves the ordinary stale-version race silently because it genuinely does resolve it, and it is exactly the rarely-contended meta/settings/overlays content that makes last-write-wins an acceptable merge. What changes is what happens when that ONE retry ALSO comes back empty — which is indistinguishable, over PostgREST, from the trigger outright refusing the write (both read as "200, zero rows"; see key design point b). Reload-and-reapply was rejected as the fix shape because correctly replaying a local edit onto a row this tab hasn't seen risks reintroducing exactly the false-conflict class B672 spent several items (B455/B460/B558/B596) retiring; a reload is the one action guaranteed correct.
- **Detection (key design point b) — audited, not rebuilt, for the primary path; a real gap fixed for a second one.** `casUpsert`/`interpretCas` (`shared/cloud/optimisticUpsert.js`) already asks PostgREST for the affected row back (`.select("version")`) and already treats an empty return as a conflict — that half was correct before this item. What was missing was the OUTCOME of a conflict that survives the self-heal: `cloudUpsertCore` (`cloudSync.js`) used to return the identical `{ok:false, conflict:true}` whether this was the first, silently-healable loss or the final, unresolvable one, so every caller treated it as a routine transient failure ("will retry on your next edit" — false, since retrying from the same stale local state fails the identical way). It now returns `{ok:false, conflict:true, unresolved:true}` for the case that survived the retry, so callers can tell the two apart.
  - **A second, concrete instance of the same class, found while auditing every direct write to `public.sites` (not the primary repro, but the same defect, live in shipped code):** `cloudRole.js`'s `cloudSetSiteRoleFallback` (the degrade path used when `set_site_group_role` isn't migrated in) wrote `{ data: {...} }` with **no `version` in the payload and no `.select()` on the update** — so `sites_enforce_version_monotonic` refuses it EVERY time once live (an update that never sets `version` can never satisfy `new.version > old.version`), and the fallback's `if (error) failed += 1; else {...}` read the resulting `error:null` as success. Fixed the same way as the primary path: the read now also fetches `version`, the write bumps it past what was just read, and `.select("id")` + an empty-array check catches a refusal exactly like an `error` would. `cloudRenameGroupFallback` in `cloudRename.js` has the IDENTICAL shape and is NOT touched — it writes `site`/`siteRenamedAt`, which is explicitly NEW-2's territory per this dispatch.
- **Key design point (c) — the trigger's own metadata-only exemption is not fought.** `sites_enforce_version_monotonic` already exempts a write that changes nothing but `data`/`site`/`name` (returns `new` unconditionally); nothing added here second-guesses that from the client, and the `unresolved` signal can only ever arise from a write that DID change content, which is the only case where the ticket's failure mode is possible.
- **Key design point (d) — the user-facing signal is built on the write's own return value, never on `client_errors`.** `client_errors` is INSERT-only RLS (B279) and stays exactly that; the telemetry row the trigger writes (`event:version-guard-refused`) is untouched and still fires. The new `siteConflict` UI state in `SitePlanner.jsx` is driven purely by what `cloudUpsertCore` returns to the tab that made the write — the one thing that tab already knows without reading anything back.
- **The UI (`SitePlanner.jsx`).** A new `siteConflict` state (mirrors the existing `readOnly` pattern: a ref for closures, gates the autosave debounce effect's cloud push exactly where `readOnlyRef` already did — the local on-device save is unconditional and unaffected, so nothing typed is ever lost) is set whenever `cloudPushWithWatchdog`/the device-storage-full push path resolves `unresolved:true`, covering both places the autosave effect can reach the cloud. It drives: the header save badge (`headerSaveState` → `"error"`, same severity as the per-element engine's own pre-existing `elemSync.state === "stale"`, which is this exact same "give up until reload" shape already established for elements — B673/B1115); the header's small `saveDetail` text ("This plan changed elsewhere — reload to keep saving," ahead of the element-engine's own near-identical existing message); and a new, dedicated top banner (`data-testid="site-conflict-banner"`, no dismiss ✕ — deliberately, so nothing tempts continuing to "work" unaware the cloud push is suspended) with a single Reload action, replacing the generic `cloudSaveFailed` banner ("will retry — your work is not lost") for exactly this state, since that wording is false here. `cloudSaveFailed`'s own render is now additionally gated `!siteConflict` (defense in depth; the two states are already set mutually exclusively).
