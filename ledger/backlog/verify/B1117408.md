DEDUPE-FIRST — searched Open/⏳Verify/Done for "activeSheetId", "tab-switch", "sheet tab", "wrong sheet": no prior item — B1109840 (Done) shipped the multi-sheet tab strip this bug lives inside, and is not a duplicate (it's the feature this is a regression IN, not a report of the same symptom).)*
`[x]` **ROOT-CAUSED AND FIXED THIS SESSION.** The reporter's own suspicion was exactly right: a stale copy of "which sheet is active." `ModelApp.jsx` keeps TWO separate notions of the active sheet — a local `activeSheetId` React state (what the render/`SheetView` actually shows, updated instantly by a plain tab click) and `workbook.activeSheetId` (a field on the undo-tracked workbook value itself). By design (see that state's own header comment), a bare tab click deliberately updates ONLY the local state — never `workbook`, and never through `commit` — because a plain tab switch is navigation, not a content edit, and must never mint (or be reverted by) an undo frame. But every write handler (`onCommitCell`, paste, fill-down, delete, rename-column, every ribbon formatting/freeze/sort/named-range action, and the four structural row/column insert-delete wrappers) resolved its TARGET sheet from `applyToActiveSheet(wb, …)` / `workbookInsertRowAt(wb, …)`, which both read `workbook.activeSheetId` internally — the STALE field, not the one the screen is actually showing. So typing into the tab you just switched TO silently committed into the tab you were just ON, exactly as reported, and a same-sheet formula typed there (`=A1*2`) evaluated against the WRONG sheet's A1 too, since the write landed in that sheet's own cell grid.
- **Fix — compose the correction into the SAME commit as the edit, never as a separate sync.** A new pair of helpers, `applyActive`/`applyStructuralActive` (`ModelApp.jsx`), thread the LIVE `activeSheetId` view state through `setActiveSheet(wb, activeSheetId)` before calling the real mutator, inside one `commit((wb) => …)` call. This was considered against the alternative of silently re-syncing `workbook.activeSheetId` on every tab click (outside the undo stack) and REJECTED: traced through by hand, that shape still breaks the moment undo/redo crosses a tab-switch boundary — `workbook.activeSheetId` in an OLDER undo frame can point at a different sheet than whatever the (undo-independent) view is currently showing, reproducing the identical class of bug on the very next keystroke after an undo. Composing the correction into every commit closes that gap structurally: "which sheet is on screen" and "which sheet this edit lands on" are the same value by construction, on every single commit, however far undo/redo has wandered — there is no second stored copy left to drift. Every call site that used to call `applyToActiveSheet(wb, …)` / `workbookInsertRowAt(wb, …)` etc. directly now goes through one of these two helpers; none of the underlying pure library functions in `lib/sheetModel.js` (and their existing 44 unit tests) needed to change at all — the defect was entirely in which sheet id the integration layer handed them.
- **All the "STILL UNKNOWN" questions the report asked to establish, answered:**
  - *Which side held the stale id?* The commit path (`applyToActiveSheet`/the four `workbook*` structural wrappers reading `workbook.activeSheetId`), not the tab-click handler — the tab-click handler was always correct, it just never had a reason to touch `workbook` at all.
  - *Paste, fill-down, delete, undo/redo?* All affected the identical way — every one of them routed through the same `applyToActiveSheet(wb, …)` call and is fixed by the same change. Live-tested individually (see below); undo/redo specifically no longer matters at all post-fix, since a commit's target is derived fresh from the live view every time rather than from any stored `workbook.activeSheetId`.
  - *Sheet1→Sheet2 as well as Sheet2→Sheet1?* Both directions reproduce identically pre-fix and are both fixed — proven with a dedicated test for each direction.
  - *Three or more sheets?* Reproduces and is fixed identically — proven with a 3-sheet fixture.
  - *Does the misrouted value persist to storage?* Yes it did pre-fix (confirmed: a pre-fix write survives a page reload on the wrong sheet) — post-fix, the correctly-targeted write is what persists, proven by a reload test.
- **The regression test asserts the TARGET SHEET ID, not merely that a write happened — per the report's own explicit requirement**, closing exactly the trap it named (a source-regex/"some cell changed" test passes on the broken behavior too). `test/modelWorkbook.test.js`'s new `describe` block asserts BOTH `wb.activeSheetId` after the commit AND the literal cell contents of both the target sheet (has the value) and the other sheet (does not) — five tests: Sheet2→Sheet1, Sheet1→Sheet2, three sheets, the reported `=A1*2` formula-context case (proves the formula evaluates against the newly-viewed sheet's own A1, not the sheet it left, matching the report's "evaluated to 40 instead of 20" detail exactly), and a structural edit (insert row) after switching. **Mutation-proven**: manually reverted `ModelApp.jsx`'s fix and re-ran the pure-library-level reproduction inline — the old `applyToActiveSheet(wb, …)` shape reproduces the exact reported numbers (`999` lands on Sheet2, not Sheet1) while the fixed `applyToActiveSheet(setActiveSheet(wb, activeSheetId), …)` shape lands it correctly.
