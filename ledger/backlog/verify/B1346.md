`[x]` **Closed 2026-07-31 as REFUTED, with the instrument that refuted it. Parked in ⏳ Verify — `V665`.** The diagnosis was reasoned from the code and explicitly not observed; measured, the second render is not there.
- **The claim:** `setView` runs synchronously in the pointermove handler (React 18 batches it → render 1); `setCursor` is scheduled onto the NEXT animation frame by `scheduleFrameJob("cursor")`, a separate task React cannot batch with the pan → render 2. A straight 2× on the hottest path.
- **Measured: 1.02–1.10 DOM-commit batches per pointermove event** (60 events: 1.10 · 120: 1.05 · 240: 1.02). The apparent "2×" in a first pass was **the measuring driver's own artefact** — Playwright's `mouse.move(..., {steps: 2})` dispatches two pointermove events per call.
- **The mechanism is wrong, specifically.** Of 62 batches that touched the coordinate readout, **61 were batched WITH the pan commit** and exactly **1** was a commit of its own. Chrome dispatches `pointermove` before that frame's rAF callbacks, and React 18's scheduler flushes both pending updates in one render pass, so the rAF-scheduled `setCursor` lands in the same commit as the `setView`. The registration effect accounted for **1** batch across the whole gesture.
- **No fix shipped, deliberately** — there is no phantom to fix, and folding the cursor into a ref would have been a real change made for a measured non-reason.
- **What DID come out of it:** `ui-audit/diagnose-pan-commits.mjs`, the repo's first commit-counting instrument, which needs no instrumented build (a MutationObserver's callback fires once per delivery batch; batches are then classified by what they touched). It records the number that IS real: **193,303 DOM mutation records across 60 pointermoves** even after B1345 — i.e. full reconciliation of every element per frame, which is **B1352**'s territory, not this one's.
