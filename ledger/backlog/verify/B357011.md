- **⛔ THE CAUSE IS STRUCTURAL, NOT A SLIP. The tree merge is a UNION: an ADDITION wins, and a DELETION is the ABSENCE of an entry. Absence loses to any copy that still has one.** So a purge could never survive a merge with a client that had not yet seen it. This is what TOMBSTONE-DELETES exists for, and Notes did not implement it.
- **THE FIX IS A DEFINITION: a purge is a FACT.** `purgeTrashEntry` records the entry id and every page id it named in a tombstone ledger carried in the tree itself, so it merges like everything else. **Rule 0** of `mergeTrees` honours it before any other rule — deliberately first, because rule 1 lifts a live node out when a bin entry names it, and a resurrected entry would do exactly that to a page somebody had since restored.
- **⛔ THE FUZZ FOUND A SECOND HOLE THAT NO HAND-WRITTEN CASE WOULD HAVE.** Two devices that delete the SAME note mint two DIFFERENT entry ids, so purging one tombstones its id and the other sails through the union untouched — **still naming pages whose bytes are destroyed**. That is precisely his zombie state: 15 of 24 rows with `purged_at` set and `doc` NULL, back in the bin offering a restore that could only produce an empty note. An entry is now filtered by the ids it NAMES, not only by its own.
- **AND A PURGE STILL TAKES ONLY WHAT IT NAMED** — a child another device added under a purged parent afterwards is RESCUED, not dropped. Rule 0 shares rule 5's body deliberately, so B342992's defect cannot arrive through the new door.
- **THE ZOMBIES ARE CLEANED UP ON SIGHT:** a bin entry every one of whose pages the SERVER reports purged is purged locally and tombstoned. ⛔ **The server's `purged_at` is the ONLY evidence accepted** — "no body on this device" is a different claim (a signed-in device legitimately has not downloaded every binned body), and conflating them would destroy recoverable entries.
- **THE BIN NOW TELLS THE TWO APART.** *"Empty — nothing was ever written in it"* and *"Its writing was permanently deleted and cannot be brought back"* are opposite facts and it was showing the first for both.
- **ON THE REBASE HALF OF HIS ASK:** the push is ALREADY rev-guarded (`.eq("rev", base)`), so a client behind the server cannot write blind — its update fails and it merges first. That is what happened here: the rebase ran correctly and the MERGE was wrong. Stated rather than adding a second mechanism that would do nothing.
