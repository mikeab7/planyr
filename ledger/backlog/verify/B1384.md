### B1384 — The landing page rendered with NO VISIBLE TEXT: every word was gated on a vendor animation library `[Landing / marketing]` (bug) #ui  *(owner report 2026-08-03, provisional NEW-1, MEASURED on his own Chrome at planyr.io/landing/ — 34 `.reveal` elements, zero above 0.398 opacity, `<h1>` at 0, two screenshots showing a dark grid, the nav, the CTA and a scale bar and NOT ONE WORD. Minted **B1384 / V676** via `git fetch origin main && npm run next-id -- --against-main`, LATE, as the last step before push. DEDUPE-FIRST — searched Open / ⏳ Verify / Done across `landing`, `reveal`, `opacity`, `B658`, `V180`, `V212`: **B658** shipped the current landing build and is the regression's origin, but is Done and archived; this is the defect it introduced, filed on its own number per the owner's framing. Net-new.)*
- **AUDIT-FIRST — THE OWNER'S HYPOTHESIS IS REFUTED, and this is the more important finding.** It is **not** viewport-height dependent. Measured at 1600×521 against the exact live bytes (`curl`'d from planyr.io and diffed byte-identical to the repo file): once the scripts load and the page is scrolled, **0 of 39 elements sit below full opacity**. The short window is fine. Nor was the `h1` "frozen mid-transition": 0.0297 opacity with `translateY(21.3px)` is precisely 1% into the hero's `power3.out` stagger, i.e. the animation had barely *started*, and the page's own `transition: all` reading matches no rule in the file (there is no `transition: all` anywhere in it).
- **THE ACTUAL MECHANISM — a chain of three, and the first link is not the one anyone would have guessed.**
  1. **`.reveal { opacity: 0 }` was the page's RESTING state**, and the only thing that ever set it to 1 was GSAP. So every word on the page was gated on a third-party animation library — permanently, if that library never ran. Measured with the vendor requests blocked: **46 of 53 copy elements at exactly 0.000, `h1` 0.000**, at every viewport size. Same with JS off.
  2. **`build()` ran on `DOMContentLoaded`, which also waits for the DEFERRED 603 KB `three.min.js`** to download *and execute* — deferred scripts run before DCL. The reveals therefore waited on ~718 KB of JavaScript rather than the ~115 KB they actually need. The inline script is the last thing in `<body>`, so there was never a reason to wait at all; it now calls `build()` directly.
  3. **THE TRIGGER, and the real answer: the render-blocking Google Fonts stylesheet.** `<link rel="stylesheet" href="fonts.googleapis.com/…">` is render-blocking, and — the part that actually bit — **a synchronous `<script>` cannot EXECUTE until every preceding stylesheet has resolved.** So a slow, blocked, filtered or ad-blocked fonts CDN froze GSAP at the bottom of `<body>` *even though its bytes had already arrived*. **Measured, unambiguous:** all three vendor scripts fully downloaded at **84 ms**; `DOMContentLoaded` at **12,964 ms**. Thirteen seconds of a wordless page with `window.gsap === null` the whole way. The owner's `max 0.398 / h1 0` reading is that state one instant after the stall released, mid-hero-stagger — which is also why his `h1` read `0.0297` with `translateY(21.3px)` a moment earlier, and why `__landingReady` was already true. **Fixed:** the font stylesheet now loads non-blocking (`media="print"` + an `onload` promotion, with a `<noscript>` fallback), which is safe because the stylesheet has always carried a system-font fallback stack. **After: `DOMContentLoaded` 12,964 ms → 149 ms**, and the reveal animation now actually runs instead of timing out.
- **THE VERIFICATION GAP IS THE OTHER HALF OF THE BUG, and the owner is right that it matters as much.** `__landingReady === true` says the init function *ran*; `ui-audit/verify-landing.mjs` screenshots after a fixed wait at Playwright's default 720 px height. **Neither ever asked the browser what opacity the headline was.** A readiness flag is not a rendering assertion — so both reported success over a blank page.
`[x]` **Shipped 2026-08-03. Parked in ⏳ Verify — `V676`.**
- **THE FIX — the resting state is now legible, and the animation is an enhancement it cannot take away.** `.reveal` and every other start state that hid copy (`.crumb`, `.crumb-sep`, `.spine-vert li`, the calibrate/filed badges, the Gantt bars) rest **fully opaque** in CSS. The hidden pre-animation state is scoped to `html.anim`, a class only the new `<head>` gate adds — and which it **releases** on the first of: `build()` arming it (GSAP is here, the animation starts now), a **1200 ms watchdog**, or the `load` event. Reduced motion never arms it at all, so the copy is simply there. Requirement (b) is now structural: **with the vendor scripts blocked, or JS off entirely, the page reads normally.**
- **The converse hole is closed too:** if the gate already released and GSAP then turns up late, `__landingArmAnim()` returns **false** and `build()` takes the static no-motion path — animating then would snatch words back out from under someone already reading them. Legibility outranks the fade.
- Two `<link rel="preload" as="script">` hints were added for the two vendor files so they start downloading with the document instead of after ~700 lines of markup and CSS, which is what keeps the gate from timing out on an ordinary connection and losing the animation.
- **SHORT WINDOWS ARE NOW FIRST-CLASS, which the rendered check exposed and no static reading would have.** With the words finally on screen at 1600×521 they were *present but obstructed*: a headline sized purely off viewport WIDTH grew to four lines, ran under the 3D mark, and pushed the lede beneath the fixed scale bar. A `max-height: 700px` block caps the headline against viewport height as well, narrows the copy column to clear the mark, and stands down the two decorative furniture pieces (the self-measuring scale bar and the scroll chevron) that are pinned to exactly where the body copy lands on a short window.
- **THE GUARD, PROVEN RED THEN GREEN.** `ui-audit/verify-landing-legibility.mjs` reads **computed opacity** off the real elements at **three viewport heights — 521 (the owner's window), 900, and a 390×844 phone — in three modes: normal (scrolled end-to-end and back to top), starved (the GSAP/ScrollTrigger requests aborted), and JS-disabled.** Against the bytes **currently live on planyr.io**: **✗ 6 of 9 combinations fail, `h1` 0.000.** Against this build: **✓ 9 of 9, every line of copy fully opaque**, with the gate ARMED rather than timed out on desktop and phone — i.e. the animation runs and the legibility floor holds underneath it. It also earned its keep during the fix: it caught the `html.anim` gate stranding the phone-only vertical spine, one edit after the gate was written. The static half runs on every CI build (`test/landingLegibility.test.js`): no un-gated rule may set `opacity: 0` on copy, the gate must be in `<head>`, and `build()` must consult it.
