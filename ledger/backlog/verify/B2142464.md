Or it didn't copy it at all." DEDUPE-FIRST: nearest priors are B36051 (paste modes + layout-table unwrapping — extended here, not duplicated) and B1382548 (font inheritance on paste — unrelated).)*
`[ ]` **🔲 REOPENED (×2) 2026-10-06 — V1559744 FAILED on the owner's own machine after #2077.**
- **Plain-English cause (for the owner):** the HTML parser was never the problem — OneNote tables parsed fine once they reached it. Five separate things stopped them reaching it or ruined them on the way: (1) Excel/OneNote put a *picture* of the table on the clipboard next to the table, and Notes grabbed the picture; (2) a blank cell crashed the paste silently; (3) pasting while a box was only *selected*, with nothing focused, or on blank paper either did nothing or flattened the table into one run-on line; (4) a one-column OneNote table was flattened like an email-signature layout; (5) plain tab-separated text never became a table.
- **Fix:** `lib/notesTablePaste.js` (new, pure) + `notesPastePlain.js` + `notesImageNode.js`/`notesAttachNode.js` (stand down for a table) + `notesExtensions.js` (`keep` table attr) + `NoteEditor.jsx` (armed-paste and nothing-focused/box-selected paste now go through the editor's own paste pipeline; a box made for a table is widened; caret is kept inside the box after a table lands). Tidy no longer leaves a cell childless (the real Excel crash). "Keep text only" on a table = TAB-SEPARATED rows (stated choice); Ctrl+Shift+V of spreadsheet text stays text; plain TSV on Ctrl+V becomes a table.
- **Sandbox-verified:** `ui-audit/verify-notes-table-paste.mjs` — 7 committed clipboard fixtures (`test/fixtures/clipboard-tables`: OneNote desktop + web, Word, Outlook, Excel, Google Sheets, a bordered one-column OneNote table) × html / html+picture / plain × 6 landing spots, chip + merge + keep-text, undo, caret-stays-in-box, real Ctrl+V: **266 checks green on this branch, 111 RED on untouched origin/main** (red-proof). `test/notesTablePaste.test.js` (26) fails on main for the empty-cell and tab-text causes. Existing table/paste harnesses show identical (pre-existing) failure sets on main and branch.
- **Stated limits:** fixtures are modelled on each product's documented clipboard markup, not captured from the owner's machine; whether his OneNote build also put a picture on the clipboard is inferred, not observed (the fix is correct either way). Column widths/colours are best-effort. Merged cells are kept where the schema allows (Word/Sheets fixtures prove colspan).

- **Recurrence ×2 — FAILED LIVE on the owner's machine (2026-10-06, Windows, Chrome, OneNote desktop), after #2077.** He pasted a 6-column OneNote table NESTED inside a bulleted list item ("Cross Dock" bullet, table indented under it): row 1 a merged header (Cross Dock | Front Load | Rear Load, each spanning 2 columns), row 2 SF:/Depth: ×3, five data rows with several empty cells (row 3 Rear Load empty; row 6 only "800K | 620'"), a final fully empty row, grey shading. **What arrived:** every non-empty cell its own paragraph, stacked in one narrow box in reading order; empty cells dropped; no table.

- **Owner priority, verbatim:** "it's fine if we can't paste from OneNote but we need to 100% be able to paste from Excel." EXCEL IS THE MUST-SHIP; OneNote is best-effort but must at minimum arrive as a table or tab-separated rows, never one-cell-per-line. Rule being built: tab-separated `text/plain` becomes a table whenever the HTML route yields no table.
- **Round-2 work (this session, SYNTHETIC fixtures — awaiting the owner's real captures):** (1) `repairTableFragment` — rows/cells with no `<table>` element are re-wrapped before the parse (reproduces the owner's one-paragraph-per-cell symptom; fixture `onenote-fragment-no-table-tag`); `htmlHasTable` now counts rows/cells so a picture beside a fragment still loses. - **Recurrence ×3 — 2026-10-11 (owner, Windows/Chrome, own machine): pasting now WORKS from Excel and OneNote, but the box a pasted OneNote table lands in is about a THIRD of the width it needs** (6 columns, the merged header "Cross Dock / Front Load / Rear Load" each spanning 2 columns, nested in a bulleted item). Same chat block as B2248944 (NEW-1 of 2).
  - **Plain-English cause:** the rule from #2077 ("a box made for a pasted table is wide enough for its columns") counted the columns by the cells in the FIRST ROW. A merged header has 3 cells over 6 columns, so the box was sized for 3. Reproduced on the committed OneNote fixture (`onenote-nested-in-li`, already the owner's exact shape): box 480, table 601 wide, 6 columns squeezed to the floor. And it only ever ran for a box the paste itself had just created, so a table pasted into an existing narrow box was never widened at all.
  - **Fix:** `lib/notesTablePaste.js` `tableShape`/`tableShapeOfNode`/`tableBoxWidth` count columns WITH merged spans, use the natural width (160 per column, or the stored width) plus the box's own padding, cap at the page width or 900 (whichever is wider; never below 100 per column) and never narrow a box; `NoteEditor.jsx` runs it from one paste-transaction hook, so blank paper, a selected box, an existing narrow box and the caret in a box all widen. The widening is an attribute step kept out of undo history (`growNoteAnchorWidth`), so one Ctrl+Z still removes the whole paste (a first version needed two — caught by `verify-notes-table-copy-paste`).
  - **Sandbox-verified:** `ui-audit/verify-notes-box-width.mjs` §1 — 8 clipboard fixtures × 3 landings (blank paper · selected box · existing narrow box): every box ≥ 100 per real column, no column below the floor, no table spilling out of its box, OneNote merged-header read as 6 columns. **Red-proof on main:** the OneNote shape gives box 480 / 3 columns (old rule); the unit test `test/notesTablePaste.test.js` "RED-PROOF: the first row has 3 cells but the table has 6 columns" pins the exact miscount.
  - **Disposition (STANDING RULE #2):** reproduced and fixed. Stopping rule unchanged: closes when a real OneNote + a real Excel capture paste intact AND the owner confirms on his own machine.
