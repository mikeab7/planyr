- **⛔ ROOT CAUSE — THE VERDICT WAS TAKEN AT REQUEST TIME AND SPENT AT EXECUTION TIME.** A framing does not happen when it is requested. `requestFit()` bumped a nonce; a React effect then ran `fit()` on a LATER tick. That indirection is load-bearing and correct (a fit called straight from a handler frames the view without the content the handler just added, so it must run post-render) — but it separates the request from the execution by a gap the main thread can stretch arbitrarily. NEW-1's guard reads `if (!userMovedViewRef.current) requestFit()` **at the timer**, i.e. before that gap. So permission is granted while the user has not moved, and **spent after he has.** The check is real; it is one hop too early. That is precisely why the cold start got BETTER rather than fixed — the guard wins whenever the gesture lands before the timer, and loses only when the machine is slow enough for the gesture to land inside the request→execution gap. **Intermittently. Exactly as reported.**
- **⛔ CAPTURED LIVE, ON THE REAL APP, WITH REAL VALUES — this is not a reading of the source.** Driving the real build at 40x CPU throttling with the verdict in the request-time position, one recorded row: a wheel gesture took the view to **0.4594 px/ft** and a `fit()` then yanked it out to **0.1064 px/ft**, offsets jumping to the canvas-centred framing values. That is "it zooms in very close, then zooms out" in one row, on a build that believed it was guarded.
- **⛔ WHAT THE "SECOND TRIGGER" ACTUALLY IS, stated plainly because the brief reasonably assumed a second mechanism.** It is the same trigger under a slower machine, not a different one. The full idle matrix (below) found **ZERO** unrequested view changes while the app sat idle, at every wait from 30 s to 5 min, on both input paths — the app does not move the view on its own while nobody is touching it. What idle changes is the state of the DEVICE, not the state of the app: coming back to a phone that has been sitting, on a heavy plan, is when the main thread is least available and the request→execution gap is widest. The trigger is load, and idle is a reliable way to get load.
- **Fix.** Two new modules and one rewiring, all in `src/workspaces/site-planner/`:
  - **`lib/viewFramingGate.js`** (new, pure) — the view belongs to whoever touched it last. Every framing takes a **TICKET** when it is REQUESTED and is allowed to execute only if the user has not moved the view since. One rule covers all three cases: the boot reframe takes its ticket at mount (any gesture cancels it); a `Fit view` click takes its ticket at the click (nothing can intervene, so it always runs); a deferred framing takes its ticket when its work starts. It counts MOVES rather than holding a boolean, deliberately — a boolean cannot let `Fit view` work on a plan the user has already panned.
  - **`SitePlanner.jsx`** — `requestFit(ticket)` is now the ONE DOOR every framing goes through, and **the verdict is taken immediately before `fit()` touches the view**, with the ticket riding through the nonce (`fitReq = { n, ticket }`). A suppression is RECORDED, never silent (LOUD-FAILURE), so it is observable from the harness and from the owner's own armed tab. `userMovedViewRef` is gone: two sources of truth for one fact is how the next session reintroduces this.
  - **⛔ A SCOPE MISTAKE THAT WAS WRITTEN AND THEN CAUGHT, recorded so it is not "fixed" later.** The tempting improvement is to hold ownership in module state keyed by plan so it survives a remount. That reads as strictly safer and it is WRONG: `view` is component state with no persisted copy, so a remount RESETS THE VIEW, and the automatic reframe is the only thing that makes a re-opened plan look like anything. Suppressing it because the user panned that plan before the remount lands him on a default view of nothing. Ownership is scoped to the lifetime of the view it is about — one gate per mounted planner. - **⛔ ROOT CAUSE — THE (×2) GATE OWNS "WAS THE VIEW TAKEN?" AND HAS NO OPINION ON "CAN IT BE MEASURED?".** `viewFramingGate.mayFrame`'s move-count check correctly said "nothing intervened" — on a hidden cold boot, nobody was at the wheel, so ownership genuinely was uncontested. But `fit()` (the boot auto-frame) divides by `size.w`/`size.h` (React state fed by a `ResizeObserver` on the canvas wrapper), and a tab that loads BACKGROUNDED (a link opened in a new background tab, a phone-locked reload) can reach the 120 ms boot-fit timer before that container has ever been genuinely laid out. The observer's own MANDATORY first callback still fires — ResizeObserver always delivers one — but for a page nobody has ever painted it can report a degenerate box, and the app's own `Math.max(320, r.width)` floor silently turns that into a plausible-looking 320×360 that reads as "measured" when it is not. `fit()` then computes a ppf from that number against the SITE's real footprint and commits it. Automated rigs keep the page visible throughout and so never enter this state — exactly why every rig passed while his phone kept failing.
- **Fix — a SECOND, independent readiness gate beside ownership, both checked at the same "one door".** `lib/viewFramingGate.js`'s `mayFrame(ticket, readiness)` now takes a second argument, `{ visible, measured }` (both default `true`, so every existing caller and test is unaffected): refuses with `"document-hidden"` if `document.visibilityState !== "visible"`, refuses with `"container-unmeasured"` if the container has not been measured while genuinely visible, and only THEN falls through to the existing move-count ownership check. `SitePlanner.jsx` adds `sizeMeasuredRef` — set `true` only by a `ResizeObserver` callback (or a forced `getBoundingClientRect()` re-measurement on `visibilitychange`→visible) that fires while `document.visibilityState === "visible"`, never on a callback delivered while hidden. The `fitReq` "one door" effect passes `{ visible: document.visibilityState === "visible", measured: sizeMeasuredRef.current }` into `mayFrame`; a suppression for either new reason is **DEFERRED, not dropped** — it retries against the SAME ticket (so a real user move meanwhile still cancels it, exactly as the (×2) gate already guarantees) via a `requestAnimationFrame` poll that costs nothing while the tab is genuinely hidden (rAF is suspended, per FOREGROUND-OR-VOID) and resumes on its own the instant the tab is foregrounded.
