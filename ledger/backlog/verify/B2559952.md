**MEASURED, not guessed (live planyr.io build 8a46501, signed in as the test account, throwaway located plan at 34.95 N −89.83 W, same scripted 75-step real-mouse drag per arm, `ui-audit/measure-layer-pan-frames.mjs`).**
- Layers off: 84 compositor layers, drag stall 33–65 ms. Water & Sewer on: **598 layers**, stall **92–137 ms**, p95 frame 83–100 ms vs 50–66 ms, long tasks in most drags.
- CDP attribution of those layers: **511 of 598 = `div.leaflet-tooltip.pf-line-label`** — one per printed pipe size — plus 72 imagery tiles. Hiding ONLY the label panes (CSS) took the stall back to baseline (37 ms) and the layer count to 88; hiding only the strokes did not. Script / layout / style time was the same in every arm (≈ 850–1000 ms over the drag), so this was never JavaScript or a refetch: it is Chrome compositing hundreds of layers.
- MECHANISM: Leaflet positions a permanent tooltip with `translate3d(x, y, 0)`, and a 3D transform gets its own compositor layer. Swapping the labels' transform to a 2D `translate` live in the page dropped 598 → 192 layers and the p95 to the baseline's.
- Gas lines alone (fewer labels) barely moved the stall (~60 vs ~40 ms); the cost scales with LABEL COUNT, which is why the Water & Sewer row (mains, gravity + force sewer, DCRUA, service lines) is the worst.
- RULED OUT with numbers: per-move refetch (0 GIS requests while the pointer is down in every steady drag; the refresh arrives after release), label re-layout per frame (the declutter runs on `moveend`/`zoomend` only), draw-budget recount (it runs per delivered batch, not per move), script cost (equal across arms). ONE real secondary effect: a drag whose frames take > 160 ms lets the planner's 160 ms commit debounce fire mid-drag, which re-bases the basemap and refetches (80 requests in one slow-paced drag) — fixing the layer count removes the long frames that trigger it.

**FIX.** `lib/flatLabel.js` `flattenTooltip` wraps each label tooltip's `_setPosition` and rewrites the same position as a 2D `translate` (same pixel, no layer); `layers.js` binds every line label through ONE `bindLabel` helper. No visual change (same CSS, same position), applies to every `lineLabel` row on both the planner and the Map view (zoning codes, municipal names, pipe sizes). PDF export untouched (it prints from `lineLabelText`, not the DOM tooltips).
**Guards.** repo-root `test/` **flatLabel** (the 2D transform survives every re-position; every label binds through the helper); live ui-audit **measure-layer-pan-frames** (fails on > 60 extra compositor layers over layers-off, or any GIS request while the pointer is down; its `off` arm is the known-good control and the harness goes VOID if rAF is dead).
**Not touched (parallel session):** the zoning legend. The label mechanism it shares is unchanged in look.
