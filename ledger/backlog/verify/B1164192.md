- Origin: filed 2026-09-07, owner-dispatched urgent bug report.
- **ROOT CAUSE.** Shell.jsx's route-level deletion gate (`checkProjectDeletionStatus` → `cloudSync.cloudCheckDeleted`) asked a SINGLE-ROW question — `select … from sites where id = :projectId` — and `projectId`, per Shell.jsx's own comment, is always "the active Site-group id," never one specific plan. For the overwhelming common case (an untouched project) the anchor row IS the only row that matters and the single-row check is correct by coincidence. It breaks the instant the anchor itself gets individually soft-deleted (exactly what "duplicate a plan, then delete the original" does) while siblings sharing its `group_id` stay live: the query found only the dead anchor, reported `deleted:true`, and Shell.jsx swapped the entire project out for a "This project doesn't exist" / restore notice — even though three-quarters of the project's content was sitting right there, live, one query away.
- **IS THIS A REGRESSION? Stated with the honest limit on what could be checked, not guessed.** This container's local git history is shallow (174 commits, effectively starting ~2026-09-05) and cannot audit further back — so "was this ever different" cannot be settled by `git blame` alone. What IS checkable: nothing in the visible history of the last two days touched `cloudCheckDeleted`'s single-row query shape. The nearest neighboring change, **B1235168/B1235169** (yesterday, PR #1481), touched `ensureProjectRow`'s fast path and added the Drive-folder purge (see B1164193) but left this exact query untouched. The deletion gate itself is documented in this codebase's own history as having shipped as **B848832/B848833** (owner report 2026-09-04) — five days before Richfield's anchor was even soft-deleted was NOT the case here: the anchor was deleted 2026-08-29, six days **before** the gate existed at all, so the gate started misreading Richfield as deleted from the moment it first shipped. The most likely explanation for the nine-day gap before the owner noticed is simply that he hadn't reopened Richfield by any route since 2026-09-04 until tonight — every normal entry point (switcher, Dashboard card, direct URL) sets the identical route `projectId` and would have hit the same gate. **Conclusion: a pre-existing design defect in the gate's original single-row shape, not a new regression from a recent change.**
- **THE FIX — ask about the whole GROUP, not the one row.** `cloudSync.cloudCheckDeleted(uid, id)` now runs two indexed lookups — `id = :id` (catches the anchor itself, or a legacy pre-groupId row with no `group_id` column set) and `group_id = :id` (catches every sibling, including when the anchor has been HARD-deleted and no row named `id` exists at all any more) — and answers `deleted:true` only when **every** row found is soft-deleted. A single live row anywhere in the group is enough to answer `deleted:false`. `checkProjectDeletionStatus`/`projectGateStatus`/Shell.jsx's gate effect are all unchanged — the fix is entirely inside the one function that was answering the wrong question, so every downstream consumer (Shell.jsx's route gate, `CompsPanel.jsx`'s owning-site bin check, `ensureProjectRow`'s refuse-on-deleted guard) is corrected for free.
- **BLAST RADIUS — measured account-wide, not assumed.** Ran the same query shape (an anchor row soft-deleted while its group still has a live sibling) against the ENTIRE `sites` table via a read-only Supabase MCP query against `planyr_production` — not scoped to the owner's account. Result: **exactly two projects on the whole platform carry this shape, both his** — Richfield (`smsdrvzr9gzx`, 3 live siblings) and **Woods Road** (`smsrpaiqu5sv`, anchor deleted 2026-08-13T21:21:18Z, **6** live siblings as measured just now — his own estimate was "four," which reads as an approximate recollection rather than a fresh count; the extra two are plans added to the group since he last looked, and the live measurement is what's cited here). Woods Road is also a **shared TEAM project** (`team_id` set, two distinct `user_id`s among its rows) — confirmed this fix's group query has no notion of ownership and is unaffected by that. Zero other accounts anywhere in the database carry this shape.
