- **⛔ A REAL BUG FOUND AND FIXED WHILE BUILDING THE MATH, worth recording because it would have shipped silently wrong.** A naive fit of raw image-pixel points (y-DOWN, top-left origin) against the project grid (y-UP, north-positive) is a REFLECTION, and a similarity transform (rotation+scale+translate only) cannot represent a reflection — fitting it anyway silently mirrors the placement for any non-degenerate control-point pick. Caught by the unit test itself (an assertion about which direction "south in the image" should land failed on the first draft), fixed by mirroring every image point into a y-up space before fitting/applying and back on the way out (`overlayGeoref.js`'s `toMathSpace`/`fromMathSpace`), with a dedicated regression test (`overlayGeoref.test.js`, the "image y-down vs. grid y-up handedness" case) using control points that vary in BOTH axes so a reflection can't hide behind a degenerate single-axis pick.
- **THE DECISIONS THE BRIEF PRE-AUTHORIZED, all taken:** site plan is its own entity (new `public.site_plan_overlays` table, optional `project_id`/`team_id`, owner-write/team-read RLS mirroring `comps.sql`'s shape) · PDF page picker (rasterizes the chosen page via the existing lazy `pdfRaster.js` primitives, never on the boot bundle) · 2-point control-point georeferencing (the align-mode solver above; drag/scale/rotate fallback wasn't needed since the preferred tool was already there) · post-anchor independent scale check (click two map points, report the real distance in feet via straight state-plane-feet distance — deliberately NOT derived from the overlay's own transform, so a badly-fit georeference can't confirm itself) · `comps.anchor_kind` extended with `'site_plan'` (nullable `site_plan_overlay_id` + `site_plan_point` snapshot; `lat`/`lon` stay NOT NULL and are DERIVED from the georeference at pin time, so every existing map view/list/filter keeps working untouched) · opacity + visible toggle + a simple min-zoom gate (15) so the plan never draws at a meaningless whole-metro zoom, rendered in its own Leaflet pane (z-index 399: above tiles, below Leaflet's default overlayPane so drawn parcel/identify vectors stay visible over it, well below the marker pane so comp pins always show).
- **RENDERING: Leaflet has no built-in rotated-image layer, so one small one was written (`lib/rotatedImageLayer.js`) — the standard 3-corner CSS-matrix technique**, computed each pan/zoom from the georeference's own corner lat/lons; a thin React hook (`useSitePlanOverlayLayers.js`) keeps one instance per visible overlay in sync with the list, mount/update/teardown. This is genuinely new infrastructure (nothing in MapFinder's real Leaflet map rendered an arbitrary raster before), but it holds no georeferencing math of its own — it only turns three already-resolved lat/lons into an on-screen transform.
