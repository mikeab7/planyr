`[x]` **SHIPPED THIS SESSION — root cause fixed, not just guarded against.** Confirmed live against production before touching anything: `comps_site_plan_overlay_id_fkey` was `FOREIGN KEY (site_plan_overlay_id) REFERENCES site_plan_overlays(id) ON DELETE SET NULL`, and `comps_parcel_anchor_has_identity` requires `site_plan_overlay_id`/`site_plan_point` NOT NULL whenever `anchor_kind = 'site_plan'` — so the FK's own cleanup action on a real `DELETE FROM site_plan_overlays` writes exactly the value the CHECK forbids, aborting the whole transaction. This was ALREADY diagnosed correctly by B972512-HARDENING item 5, which shipped a proactive app-level block (`SitePlansSection.jsx`'s `blockedByPinnedComps`) that refuses the delete before it ever reaches the database — but that block **directly contradicted its own confirm-dialog's copy**, which has read "Comps pinned to it keep their location but lose the link back" (choice (a)) the whole time, while the actual behavior was choice (c) (refuse outright). It also only protects the two client code paths that call it — never a future/direct hard-delete (an admin script, a new code path) — and the FK/CHECK conflict itself was untouched at the schema level.
- **DECISION: candidate (a) — a comp survives and reverts to its lat/lon pin anchor.** Chosen and justified over the other two: **(b) soft-delete the comp too** was rejected — a comp is an independent entity (it has its own lat/lon, its own price/date/notes) that happens to be anchored to a plan; destroying it as a side effect of deleting an unrelated row it merely references would be a bigger, more surprising loss than losing one link. **(c) refuse the delete** was rejected as the standing behavior — it's exactly what B972512-HARDENING item 5 already shipped, it already contradicted the UI's own promised copy, and it leaves a plan permanently un-deletable for its owner unless every comp pinned to it (including a teammate's) is first found and re-pinned or removed — real friction for a real, common action (deleting an old flyer). **(a)** costs nothing extra: `comps.lat`/`comps.lon` are NOT NULL on every comp already, and are kept current for a `site_plan` anchor by every placement move (`commit_site_plan_overlay_placement`, `site_plan_overlays_comp_sync.sql`) — so they are always a valid, up-to-date fallback location, never a stale one, and the comp genuinely keeps its place on the map with nothing more than a lost cross-reference.
- **Mechanism (`src/shared/comps/db/comps_site_plan_overlay_delete_reverts_to_pin.sql`, applied to production):** a `SECURITY DEFINER` `BEFORE DELETE` trigger on `site_plan_overlays` (`comps_detach_from_deleted_site_plan_overlay`) does the multi-column flip — `anchor_kind` 'site_plan'→'pin', `site_plan_overlay_id`→null, `site_plan_point`→null — in ONE UPDATE, atomically, for every comp referencing the row about to be deleted, so the CHECK never sees an intermediate violating state. `SECURITY DEFINER` is required, not cosmetic: `comps` UPDATE is owner-only RLS, and a comp pinned to a shared overlay is routinely owned by a teammate, not the person deleting the plan — the identical cross-owner problem `site_plan_overlays_comp_sync.sql` already names for the placement-move recompute. The FK's action changed from `SET NULL` to `NO ACTION` (Postgres's default) as a safety net: if the trigger ever missed a row, `NO ACTION` surfaces a plain "still referenced" FK error instead of `SET NULL` silently re-triggering the exact CHECK abort this fix exists to close.
- **The trigger only fires for a real DELETE — the app's ordinary "Delete site plan…" is a SOFT delete (an UPDATE stamping `deleted_at`)**, which never fires a DELETE trigger at all. Since that action's own confirm-dialog copy already promises the comp "loses the link back," a matching `soft_delete_site_plan_overlay(p_overlay_id)` RPC does the identical detach UPDATE inline, in the same function as the `deleted_at` stamp (one atomic operation). This is a deliberate, PERMANENT detach: restoring a soft-deleted overlay via `restoreOverlay` brings the plan back, never the comp's link to it — the link is stated as lost the moment the delete is confirmed, not hidden pending a restore.
- **App changes:** `sitePlanOverlayStore.js`'s `deleteOverlay` now calls the new RPC instead of a plain `.update()`. `SitePlansSection.jsx`'s `blockedByPinnedComps` function is deleted, and its two call sites (`remove()` — the ordinary delete, `purgeForever()` — "Delete forever" from the trash view) no longer block — both deletes are now unconditional, matching the row's own confirm-dialog text, which needed no wording change since it already promised (a). `overlayErrors.js`'s `comps_parcel_anchor_has_identity` friendly-message branch is kept as defense-in-depth (LOUD-FAILURE: never surface the raw "violates check constraint" text) but its comment now states this constraint should no longer be reachable through any known path.
