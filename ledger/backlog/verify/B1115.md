- **Repro (measured).** A tab running an older bundle with a stale copy issued an 8-op `commit_elements` **every ~1 s for at least 7 s**; **every op was rejected** and `site_elements` revs never moved. The DATA outcome was correct — the CAS did its job — but nothing stopped the client, so one stale tab can hammer the RPC indefinitely.
- **Fix.** `processResults` now reports whether **any** op was accepted. A batch with none increments a reject streak: the retry moves off the 750 ms debounce onto the existing exponential backoff ladder, and after `maxRejectStreak` (default 4) consecutive all-rejected batches the engine **STOPS re-committing**, sets state `stale`, and emits a typed `client-stale` event. One accepted op resets the streak, so a healthy client can never trip it; `retryNow()` clears the hold.
- **LOUD-FAILURE, in plain English.** `conflictToasts` turns `client-stale` into the one message the user must act on — *"This tab is out of date — your recent changes here can't be saved. Reload the page to catch up."* — with no `authoredRecently` gate and no zoom action, because it is not about a single element.
- **Tests.** The retry interval GROWS (each recorded delay strictly greater than the last, the first already past the old debounce) rather than sitting at 750 ms; after N all-rejected batches the state is `stale`, the event fires, and **no further commits are issued**; one accepted op breaks the streak; and the toast reads as a reload prompt.
- **What is still owed (V515).** A genuinely out-of-date tab against a moved-on plan: that the RPC rate visibly decays instead of sitting at ~1/s, that the reload prompt appears, and that reloading clears it.
