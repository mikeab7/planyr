### B366385 — The sharing pointer never SURVIVED a pull, so every "is this shared?" indicator was blank at once `[Site Planner / teams]` (bug) #site-planner #auth #sync #persistence  *(arrived 2026-08-11 as provisional NEW-2 in the same owner chat block. See B366384's provenance for the DEDUPE-FIRST sweep.)*
`[x]` **⏳ SHIPPED. This is the root cause of the whole complaint — the other two are only visible once this one is fixed, which is why the owner sequenced it first.**
- Verify: live — V161952 (`Blocker: auth`)
- Origin: owner chat block, 2026-08-11 — filed and shipped the same session.
- **THE REPORT, verbatim.** *"It's not very clear when a site is shared. I don't really know how to know if a site is shared… And when I do click, it isn't clear that it has been shared, and options still pop up to share it. So it makes it seem like it hasn't been."*
- **⚠ THE CHAT BLOCK'S DIAGNOSIS WAS CLOSE BUT NOT THE MECHANISM, and the fix location differs.** It said *"grep teamId storage.js returns NOTHING, so it never persists into the local site model."* The grep is accurate; the inference is not. `teamId` **is** a Site Model field (`siteModel.js`, schema v8) and it **does** round-trip a local save. The real defect is one function further on.
- **THE MECHANISM.** `mergeSiteContent(a, b)` resolves scalars by taking the copy with the newer `updatedAt` — correct for CONTENT, wrong for a server-owned column. B458's immediate mirror write advances the **LOCAL** `updatedAt` on every edit while the cloud push lags (stated verbatim in `storage.js`'s own B460 note), so on `pullCloud` the local copy is routinely newer and `...newer` took its **stale `teamId: null`**, discarding `sites.team_id`. Every pull, every project. Three surfaces read `s.teamId` and so went blank together: the list row's icon, the share menu's checked state, and TeamPanel's shared-projects count.
- **SAME DEFECT SHAPE AS THE RENAME SPLIT (B1415–B1418), and it takes the same rule: ⛔ never re-derive the winner from `updatedAt`.** There `siteRenamedAt` is the deciding fact; here the deciding fact is simpler — the COLUMN is the authority, so the mirror is COPIED, never voted on.
- **THE FIX, at both seams.** `cloudList` stamps an explicit `shareMirror` (so *"the cloud says private"* is distinguishable from *"the cloud did not say"* — a pre-migration DB has no such column and must be left alone, or every project silently unshares). `mergePulledSites` re-stamps it AFTER the merge; `saveSite` refuses to let a content save move it for a record that already exists (a stale in-memory model carries `teamId: null` EXPLICITLY, and an explicit key wins a spread — that autosave was re-blanking the mirror seconds after the pull set it). A brand-new record keeps its birth team, which is B326416's INSERT path and the one legitimate local writer.
- **⛔ READ-ONLY BY CONSTRUCTION, so B714 is intact.** Nothing here writes a share value outward: `siteRowFor` still strips all three fields from every content UPDATE, `team_id` still moves only through the explicit share path, and the Postgres guard still refuses any other write. B714's rule is WHY this bug existed (the pointer was deliberately kept off the content path), so the fix had to make the READ direction authoritative and nothing else.
- **THEN THE LEGIBILITY HALF** (the owner's actual bar: 35 projects, 2 shared, he could not tell which). The list row now NAMES it — `Shared with HIP Houston` on the existing metadata line, in the accent, rather than an accent glyph whose meaning lived in a hover title. The share menu STATES its state before offering an action (`Shared with HIP Houston` / `Private — only you can see this`), and an already-shared team row reads `✓ Unshare` instead of looking like a fresh invitation, which is exactly what *"options still pop up to share it"* was.
- Guards: repo-root `test/` suite **shareMirror** (18 — incl. a mutation check that replays the pre-fix `mergeSiteContent` behaviour and asserts it loses the team, the pre-migration no-mirror case, the cross-device unshare, and the stale-autosave case).
