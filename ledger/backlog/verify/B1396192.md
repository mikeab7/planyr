`[x]` **FIXED THIS SESSION.**

- **Root cause.** `Scheduler.jsx` rendered `<ScheduleOwnerList>` (the grouped here/Organization/elsewhere list) inside one single JSX block gated on `showEmptyState` — true only when the routed project has NO linked schedule at all. The instant a project has even one schedule, `showEmptyState` is false, the whole block is unmounted, and there was no OTHER place the list rendered. Every one of a multi-schedule project's other schedules — Goose Creek's four besides the one that happened to load — became unreachable from that project's own Schedule tab, which is B1380336's original complaint recurring one level up: the grouping and ownership data were already correct, they just had nowhere to be seen from a loaded grid.
- **The fix.** A "Schedules" button (a stacked-layers icon, ▾) now sits in the header's Row-2 center zone (`ScheduleCenter`, `ScheduleToolbar.jsx`), beside the Grid/Split/Gantt toggle — visible whenever the Schedule tab is open at all, gated only on the same `toolbar.ready && section==="projects"` the view toggle already uses, never on whether a schedule happens to be loaded. Clicking it opens the SAME `ScheduleOwnerList` component, same `partitionSchedules` data, in a dropdown — same sections, same content, same grouping (here / Organization / Other projects), nothing rebuilt. The empty state's own inline rendering of the list is UNCHANGED — it was already the one working case and stays exactly as it was.
- **⛔ Placement was NOT arbitrary, and the first attempt was wrong — recorded because it cost a real regression risk before ui-audit/verify-schedule-header-widths.mjs caught it.** The header's Row 2 is 3 zones (tabs | center | toolbar); the tabs and toolbar zones are both `flex:"none"` and the center zone alone grows to absorb leftover width (B1012560) — which only reads as "the Grid/Split/Gantt group is centered" when the tabs zone and toolbar zone happen to be roughly equal widths. The first cut put the new button in the RIGHT (toolbar) zone, which measurably reproduced — at every width from 1440 to 2560 — the EXACT symptom B1012560 already shipped a fix for once ("the center group sat a CONSTANT ~135px off-center"). The center zone has no such constraint (it centers its own content within itself regardless of width), so the button now lives there instead — `verify-schedule-header-widths.mjs` reads 0.0px off-center at every wide width with the button in place, same as before it existed.
- **⛔ AUDIT-FIRST — one claim in the report does not hold up.** The report suspected "the same gate also blocks creating a second schedule from inside a project that already has one." Read and driven: `onNewProject` (the breadcrumb's "＋ New project", which opens `NewScheduleModal`) is wired unconditionally to `AppHeader` in `Scheduler.jsx`, never inside the `showEmptyState`-gated block — confirmed by a red-proof harness run BOTH before and after this fix: the New-schedule dialog opens from a loaded Goose-Creek-shaped project on unpatched `main` exactly as it does after the fix, with the routed project pre-selected as owner. That half was never broken; recorded here so it is not "fixed" a second time.
