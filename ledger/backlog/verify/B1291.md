**THE SCHEMA WAS ALREADY APPLIED, AND THE CLIENT WAS CODED AGAINST THE LIVE ONE, NOT A GUESS.** `public.notes_trees` / `notes_pages` / `notes_images` + a private `notes-images` Storage bucket went into production (`lyeqzkuiwngunutlkkmi`) as migration `notes_cloud_sync_b1291`; the client was written after reading the live columns back through the Supabase MCP, and the applied DDL is committed verbatim at `src/workspaces/notes/db/notes_cloud_sync.sql` so the repo is not the one place it does not exist. Own-row RLS only, private by default, anon key only — **no team predicate and no cross-user path**, per KEY DECISIONS; a guard test fails the build if one appears. **Nothing on the owner's plate: he ran no SQL.**

**THE SEAM HELD, AND THE WIDENING IS NAMED (the item asked for exactly this).** The store's public surface — `readTreeRaw` / `writeTree` / `readPage` / `writePage` / `putNoteImage` / `purgePages` — did **not change**, so no component, model function or exporter learned that storage moved. What grew is what lives *behind* it: `lib/notesCloud.js`, a private tier with exactly ONE importer (`notesStore.js`) and reached only by a cached dynamic `import()` — the same shape, for the same bundle reason, as `notesImageDb.js`. A sync engine inlined into `notesStore.js` would have doubled that file and buried the local path, which is the path that must keep working unchanged for a signed-out user. Both properties are guard-tested.

**ROWS-CANONICAL-ON-SEED, WRITTEN INTO THE STORE HEADER the way the site-element rule is written into `/CLAUDE.md`.** For a page the server has already seen, the **row wins** on seed unless a *pending local edit* explains the difference; for a page the server has **never** seen, **local wins** and is uploaded. The tree follows the same rule one level up, and when both moved it is **merged, never clobbered**. This closes the same trap B1113 closed: after a seed the device holds the FRESH rev, so a stale cached body would commit *cleanly* — the revision guard cannot help, because the client legitimately holds the current revision. Adopting the row at seed time is what makes it impossible.

**CONCURRENCY IS A REVISION COUNTER AND A NAMED STATE, NEVER A QUIET OVERWRITE.** A server trigger owns `rev`, so every push sends the **guard** `and rev = <the rev it read>` and no rev of its own; zero rows back means another device wrote first. That is a **CONFLICT**: the page enters a named state, a bar says *"also changed on another device"*, and the user picks. **"Keep the other computer's" parks this device's text as a sibling page FIRST**, so *never a lost edit* is a property rather than a slogan. There is no last-writer-wins path anywhere in the module.

**TOMBSTONE-DELETES, ON THREE SEPARATE PATHS — and the third one was a real bug found while building.** (1) The client **never hard-deletes a row**: `deleted_at` = binned (body intact, which is what a restore on the other machine needs to find), `purged_at` = gone for real, with the page's picture rows purged in the same cascade. A vanished row would read as "not uploaded yet" and be pushed straight back up. (2) A **binned or purged row can never raise a false conflict** — binning bumps the rev through the trigger, so a delete would otherwise report itself as a competing edit; `planPageSeed` rebases instead. (3) **ADOPTION IS ALSO A DELETE PATH.** Adopt a signed-out notebook, delete it from the account, sign in again, and "missing from the account tree" would have resurrected it. A notebook is now skipped when the account has it live, has it **in the bin**, or this device has **adopted it before** (recorded in the sync ledger). Three unit tests pin it.

**PICTURES TOO — eager UP, lazy DOWN, and that asymmetry is the decision.** Bytes go to the private bucket with IndexedDB kept as the local cache. Uploads happen on the seed and on every paste, because an un-uploaded picture is a note that opens **broken** on the second machine. Downloads are lazy: `readNoteImage` falls through to the cloud on a cache miss and writes the bytes back on the way past, so pictures arrive with the page that needs them instead of in a sign-in-time avalanche of photos the user may never open. Adoption re-keys a signed-out note's pictures into the account scope in the same pass — without that half, an adopted note would open with every figure missing.

**LOUD-FAILURE on the footer, and PANEL-BREVITY applied to it.** One line, and it is whatever is TRUE: *Saved on this device* · *syncing* · *Synced to your account 5m ago* · *offline, it will sync when you are back* · *sync failed: <reason>* · *one note also changed on another device*. It is derived in ONE place (`notesStorageLine`), so no surface can claim a sync the store did not make, and a failure always names a cause a person can act on. **The sentence it REPLACED, named as the rule requires: `· not synced to the cloud yet`.** Measured: signed out **1 line / 49 → 20 chars**; signed in **1 line / 65 → 31 chars** — a net reduction in both states, no accumulation. `test/notesModule.test.js`'s honesty guard was **inverted in this same commit** (it used to assert the store never said "Synced"), which is the point: the rule did not change, the truth did.

**SIGNING OUT COSTS NOTHING, PROVEN AT RUNTIME NOT JUST AT BUILD.** Every cloud path sits behind an explicit gate. The headless harness asserts a signed-out visit writes **no sync ledger**, never **downloads** `notesCloud` at all, and issues **zero** requests to a notes table or the picture bucket.
