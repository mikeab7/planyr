- **THE CAUSE IS ONE LINE, and the block found it.** `dockZones.js` opened `dockSidesFor` with `const longSides = el.w >= el.h ? ["top","bottom"] : ["left","right"]` — which walls are loaded was a LIVE function of whichever dimension was larger AT READ TIME. Shrink a cross-dock building past square and the entire dock assembly (truck courts, trailer parking, buffers, sidewalks, dog-ears) rotated 90° MID-DRAG; and because the comparison is `>=`, one foot either side of square flipped it and flipped it back, so dragging THROUGH square did it twice.
- **THE FIX — derive by default, preserve once established, the pattern already used for dog-ears, side parking, trailer length and zone spans.** `el.dockAxis` (`"x"` = the top/bottom pair, `"y"` = left/right) is stamped when the orientation is first established and a resize can never re-derive it. Three stamping points, chosen so no plan changes appearance: **creation** (from the box he just drew) · a **load-time heal** (`healDockAxes`, run before the stranded-zone prune, stamping the axis a plan CURRENTLY RENDERS — so a record saved before this field existed keeps its walls exactly where they are and merely stops re-deriving them) · and **`refitChildren`**, the one funnel every building resize goes through (grip drag, edge drag, typed Length/Depth, the on-canvas dimension editor), stamped from the PRE-resize footprint so a row seeded mid-session by the sync engine is covered too. Pure aspect-ratio derivation survives only for a building with no established orientation.
- **A STORED `dockSide` NOW WINS, ALWAYS.** It was honoured only `if (longSides.includes(el.dockSide))`, i.e. an explicit user choice was discarded by an implicit one the instant the aspect ratio flipped. A named wall names an axis, so on an established building it is the more specific statement and it decides. **The `established` gate is not ceremony:** a legacy record can carry a `dockSide` that disagrees with what it RENDERS (that is what the old validation did for a living), and honouring it unconditionally on load would strand — and therefore prune — the zones bonded to the walls the plan actually shows. The heal normalises such a `dockSide` to the wall the plan is really docked on rather than enshrining the stale one.
- **A DELIBERATE WAY TO TURN THE DOCK FACE, since it can no longer happen by accident** — a `Dock face` row in the building's Loading group stating the current walls plus a `turn ⟳` action (`rotateBuildingDockFace`): stamp, prune the apron the old walls owned, relay the stack onto the walls that are loaded now, one undo frame. One row, no explanatory prose (PANEL-BREVITY; the panel-copy budget is unchanged — this is the Properties panel, not a budgeted yield/pond region, and it replaced nothing because nothing said this before).
- **B548 HOLDS AGAINST THE STORED VALUE.** `footprintAxes`, `footprintDepth`, `footprintLength`, the massing panel, the column grid and the dock-door count all read `dockSidesFor`, so they follow the stored orientation for free: past square, depth stays perpendicular to the loaded wall and length parallel to it, which is exactly the "it recomputed where the docks went versus where the parking went" he saw.
- **THE OWNER PRINCIPLE, ENCODED — and the audit he asked for, with an honest result.** *"Let me just play around instead of correcting it for me."* I swept the other resize-time re-derivations in `refitChildren` / `relayoutAllSides` / `relayoutWallKids` / `siteModel`'s heals for the same overreach. **Finding: this was the last one of its kind, and that is because the previous three were already fixed** — `alongLen` (B1123: a pin now requires a gesture aimed at that field), a bonded child's position and span (B1340 ×2: derived unless stamped, and the stamp is written only by a gesture aimed at it), and the along-wall anchor (B1356). Every remaining resize-time derivation is of a value that is DERIVED BY DEFINITION (a bonded child's offset from its host, a zone's depth from its box, the column grid) and none of them can overwrite a stored intent. **What made this one survive the previous three passes is worth recording:** those all guarded a value that has a stored field to protect, and each fix asked "may this gesture write it?". Dock orientation had **no stored field at all**, so there was nothing for those audits to find — the failure was an absent field, not a bad write rule.
