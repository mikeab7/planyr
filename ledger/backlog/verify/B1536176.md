**SCOPE, established by driving the real grid, not by reading the code cold (Ctrl+Z is a keyboard-driven mechanism, not a pure function — it needed a real browser).** A plain text edit, a duration edit, and a date edit on an ordinary row all undo correctly with today's build — the generic undo/redo stack (`history`/`future` refs in `public/sequence/index.html`) is not broken. What's broken is narrower and worse: **Ctrl+Z gets permanently stuck** (not merely one step behind) the instant an edit's side effect flips ANY task's computed red/not-red "Needs Attn." status — which a date edit does routinely, since the default overdue/due-soon health rules are date-driven. This matches the owner's report exactly: task 168 sat at 2026-09-10, one day in the past relative to "today," so it was already flagged red at load; editing it to 2026-09-30 cleared that flag as a side effect of the very edit he made.

**THE MECHANISM, found by instrumenting the real `history`/`future`/`isUndoing` refs, not by reading the code cold.** `reconcileNeedsAttention` stamps/clears a task's `needsAttentionSince` field from a `useEffect` that reacts to `data` itself (B1161792) — it is a REACTION to an edit, not the edit. Its own `setData` call was never gated by the same `isUndoing` flag the Ctrl+Z handler already uses, so:
1. The user's edit commits; the history-capture effect correctly pushes the pre-edit snapshot.
2. The reconcile effect reacts to the new data, clears/stamps `needsAttentionSince`, and issues its OWN `setData`. That commit ALSO trips the history-capture effect (`isUndoing` reads false for it), pushing the post-edit-pre-reconcile snapshot on top — visually IDENTICAL to the current state, since the only field that moved is the invisible flag.
3. Ctrl+Z pops that invisible snapshot. Its date, still mismatched against its own freshly-computed status, immediately re-triggers the SAME reconcile effect, which pushes an equivalent snapshot right back. The real prior edit sits one level further back and can **never be reached — at any number of Ctrl+Z presses.** Measured live: `history.current.length` read **3** after one edit (not 1), and stayed at **3** through two consecutive Ctrl+Z presses with the date never moving.

**THE FIX.** A new `isDerivedUpdate` ref sits beside `isUndoing`; every reactive derived-field recompute (`reconcileNeedsAttention`'s two call sites — the per-edit reconciliation and the midnight day-rollover `refresh()` — plus the holiday-recascade recompute, same shape) sets it immediately before its own `setData`, and the history-capture effect folds that write into the CURRENT snapshot instead of pushing a new one, exactly like an undo/redo restore already does. Reset to `false` on a no-op return (same ref back) so it can never leak forward and wrongly swallow an unrelated LATER edit's own history entry — proven necessary and tested. The focused-cell-editor guard (Ctrl+Z inside an open text input falls through to the browser's own text undo) was already correct and is untouched.

**SECOND DEFECT, CONFIRMED against the app's own resolver (`meetingDatesInRange`), not the report's JSON reading.** `node`-run against the exact recurrence rule from the report (`{freq:"monthly", setpos:[3], weekday:2}`, extraDate 2026-08-04, blackout 2026-07-28): the real September 2026 P&Z meeting is **2026-09-15** (the 3rd Tuesday) — **2026-09-30 is not a meeting date at all**, and neither, for what it's worth, was the original 2026-09-10. `applyMeetingBinding`'s pinned branch (`pinnedDate = t.pinnedMeetingDate || (t.pinnedStart ? t.start : "")`) only ever fires off `pinnedStart` in practice — `pinnedMeetingDate` is a distinct, deliberate "pin this hearing" field that **nothing in this app ever sets** — and `pinnedStart` is set by `updateTask` on ANY direct date-cell edit, for ANY task, meeting-bound or not. So a plain typed date on a meeting-bound row was silently treated as an intentional pin and its `meetingInfeasible` check only ever asked "can the predecessor packet make the agenda deadline," never "is this actually one of the body's meeting days." A row could drift permanently off its own calendar with no visible sign.

**THE FIX.** `applyMeetingBinding`'s pinned branch now also checks `meetingDatesInRange(body, pinnedDate, pinnedDate)` and sets a new derived field `meetingDateOffCalendar`; `meetingInfeasible` is true if EITHER that check fails OR the pre-existing deadline check fails. The pin still holds the typed date (unchanged behavior — a real ad hoc hearing date is a legitimate use), it now correctly reads infeasible/red instead of silently "fine." The row's hover tooltip (`public/sequence/index.html` ~L12864) now distinguishes the two danger causes in plain English rather than always blaming the agenda deadline. Mirrored verbatim in `ui-audit/stress/scheduler-engine.mjs` per the file's own anti-drift contract.
