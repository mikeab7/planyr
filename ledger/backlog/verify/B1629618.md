- **THE GUARD (`src/workspaces/scheduler/db/planar_data_version_monotonic_guard.sql`), applied to production and mutation-proven.** A `BEFORE UPDATE` trigger on `public.planar_data`, `planar_data_enforce_version_monotonic`, mirrors `sites_enforce_version_monotonic` (B1626528) exactly: an UPDATE that changes `value` must carry a `value->>'__rev'` STRICTLY GREATER than the row's stored one, or it is refused (zero rows affected, row left unchanged). **Chose STRICT `>`, not "advance-or-equal"** — the dispatch's own steelman (c) floated advance-or-equal as a mitigation for old-cached-tab risk, but it is the WRONG rule for the exact race this item closes: two tabs racing off the same stale read both compute the identical `cloudRev + 1`, so the colliding write's proposed rev EQUALS the row's already-stored rev — an advance-or-equal rule would ACCEPT that collision, which is precisely the bug, not a benign tie. Strict `>` correctly refuses it. Missing/non-numeric `__rev` (either side) is treated as 0 (`planar_data_rev_of`, exception-safe via `jsonb_typeof`), matching the client's own `revOf`. A write that changes no content (`value` byte-identical) is exempt, the same shape as the sites guard's soft-delete/team-flip exemptions.
- **Point (e), enumerated before building, not assumed.** Every write to `planar_data` funnels through the ONE call site, `_rawSet`'s `sb.from(TABLE).upsert(...)` — grepped every `.from(TABLE)` reference in `public/sequence/index.html`: `get`/`_rawSet`/`getHistory`/`getHistoryValue`/`delete`/`list`/`checkRemote` are the only seven, and only `_rawSet` writes. All six `window.storage.set("hs-v1", ...)` call sites (auto, pre-restore, pre-delete-project, pre-import, pre-recascade) pass the WHOLE document through `_rawSet`, which stamps a fresh `__rev` unconditionally right before every write, `skipSanity` included — so in ordinary (non-racing) operation every real write already produces a strictly-increasing rev and the guard is a no-op; it only ever bites the exact race or a write built from a stale premise.
- **Point (b), decided and justified: reload-and-reapply, not a visible stale-tab lockout.** The client already carries the merge machinery (`mergeCloudDoc`, from B851/B1735728's own fix), so a refusal re-reads the row that won the race and either re-merges (auto saves) or re-sequences (explicit `skipSanity` checkpoints) and retries ONCE — converging silently in the common case (the two writers touched different schedules/fields) and falling back to the EXISTING "stale-block" snapshot + banner only when a genuine, unmergeable conflict remains. No modal on every autosave, per the dispatch's own instruction.
