- **THE FIX ACTUALLY SHIPPED HERE — a genuinely separate, non-overlapping defect in `ensureProjectRow` itself (`src/workspaces/site-planner/lib/storage.js`), untouched by #1475 and unable to collide with however that PR resolves:** `ensureProjectRow` never retried a failed cloud push once the connection returned. A transient offline moment (the mid-test notice in the owner's own repro) leaves a local-only record behind when the cloud push fails — correct and necessary, LOUD-FAILURE, nothing typed is lost — but the very next call's `readSites()[id]` fast path then trusted that local-only record as proof the cloud already had it, and never re-attempted the push, so a project that hit one transient failure could stay unsynced forever even once the connection came back. Fixed with `unconfirmedProjectPush` (in-memory, per-tab) — tracks ids this function has locally materialized but not yet cloud-confirmed, and bypasses the `readSites()[id]` fast path for exactly those ids until the push actually succeeds. Also hardened: `ensureProjectRow` now checks `saveSite`'s own return value and reports a distinct, honest error rather than silently proceeding to a cloud push that was always going to fail (defense-in-depth against the SAME class of bug Shape B is — a blocked local write must never be mistaken for cloud confirmation, whatever blocks it).
