`[x]` **AUDIT-FIRST — the dispatch's own "strong lead" does not hold, and the discrepancy is flagged rather than built around.** Notes has **no realtime subscription at all** — confirmed by reading `notesCloud.js`'s own header ("no per-keystroke wire at all… a page is one WHOLE DOCUMENT, synced by a `rev`-guarded push/pull") and its transport functions (poll + guarded push, no `channel()`/`on()` anywhere in the module). So there is no "realtime echo" for safeguard #2 to suppress — the dispatch was reasoning from the Site Planner's `elementSync.js` shape, which Notes does not share. **Safeguard #2 itself (semantic-equality suppression) is intact and unmodified** — `judgeConflict`'s `identical`/`litter-only` verdicts in `settleQuietly` run unchanged, on every settle, before this item's own new code ever runs (confirmed by reading the call order and by `test/notesTwoClientConflict.test.js` passing unmodified). **Safeguard #3 (per-session journal namespacing) does not apply either** — B1675104's own header already confirmed this "NOT A BUG HERE, not merely assumed": Notes' cross-tab coordination goes through `notesCloud.js`'s server-owned `rev` + `mergeSyncState`'s dirty-flag reconciliation, not a separate per-document journal file keyed by anything that could be shared across tabs.
`[x]` **THE REAL MECHANISM, confirmed by reading `notesStore.js` and then reproduced under a deterministic, gated fake network (never guessed):** `pushPending` is reached from two triggers that shared no lock — `schedulePush`'s own debounce timer, called directly from a real `setTimeout`, and `seed`'s own tail call, reached the instant `busy` is cleared (**before** that call resolves, not after — `busy = false; const pushed = await pushPending();`). `busy` only ever serialises `seed()` against itself; the debounce timer never goes through `refreshNotesSync` and was never gated by anything. So a page created and typed into while this module's own sync pass for that same page is still a real network round trip in flight can have both triggers land while the other is mid-push — for a page's first-ever push (`baseRev == null`) that is a **duplicate-key race on the INSERT**, not merely a refused UPDATE, and the loser's conflict-resolution can, depending on exactly when its own merge base finishes recording, fall through to the whole-document banner over content this SAME window wrote to itself.
`[x]` **THE FIX IS A LOCK, NOT A RETRY.** `pushPending` (`notesStore.js`) is now a reentrancy-safe wrapper around the actual work (renamed `pushOnce`): a call arriving while one is already running sets `pushQueued` and returns immediately, without touching `sync.pages` or the network; the in-flight call, once done, drains any queued follow-up by calling itself once more — so content dirtied while the lock was held still reaches the cloud, it is never silently dropped alongside the suppressed race.
`[x]` **A SECOND, related gap found and fixed in the same pass, while building the reproduction:** a push's SUCCESS handler used to clear `dirty` unconditionally, off the `doc` snapshot it had captured **before** its own awaited network call — so a local edit landing on the SAME page while that push was in flight (typing continuing during the network round trip) got silently marked "fully synced" even though local storage already held more than the server had just received, and would never reach the cloud until some LATER, unrelated edit happened to touch the page again. Fixed: the success handler now compares the just-pushed `doc` against a **fresh** `readPage(id)` (`notesCloud.js`'s own `sameDoc`) — only when they still match is the page marked clean; otherwise it stays dirty against the new rev and a follow-up push is scheduled immediately. `recordMergeBase` is unaffected either way (it always records what the server now genuinely holds).
`[x]` **RED-PROVEN, both fixes, against unmodified code — this is not asserted, it is demonstrated.** `test/notesPushReentrancy.test.js` (new, 2 tests) drives the real store (not a reimplementation) through a manually-gated fake Supabase client so the interleaving is deterministic: (1) a brand-new page's `schedulePush` debounce firing while a concurrent sync pass is mid-push for the SAME page — asserts the network is reached exactly once, ending with exactly one server row and no conflict; (2) the same race with a real edit landing WHILE the first push is in flight — asserts the fuller content still lands, with no conflict, once the lock drains. **Both tests fail on unmodified `notesStore.js`** (`git stash` round-trip, confirmed this session): the gate is hit twice instead of once — the exact duplicate-attempt shape the report described.
