- Verify: live · **V1084032**
- **THE MEASUREMENT, taken on `planyr_production` (`lyeqzkuiwngunutlkkmi`) before any code was read.** `select case when not (data ? 'siteRenamedAt') then 'key-absent' else jsonb_typeof(data->'siteRenamedAt') end, count(*) from public.sites group by 1` → **`null` 64 · `number` 34 · `key-absent` 18**. This is the discriminator the handoff could not make and it decides the whole diagnosis: a key that is PRESENT and null is a **WRITE**, not an absence. Nothing absent-by-default produces it — the 18 legacy rows are what "never written" actually looks like.
- **ROOT CAUSE.** `siteModel.createSiteModel` normalises an unknown marker to an explicit `siteRenamedAt: null` (correct for a model in memory), `cloudSync.slimForCloud` passed it through untouched, and `siteRowFor` sends the whole model as `data` — which **REPLACES** the row's jsonb. So any device whose cached copy predated a rename overwrote that rename's own stamp with an empty one. The handoff's own lead was right: the second writer is a client-side document write. (Its supporting inference — 8 `siteRenamedAt` references and 0 `rename_site_group` in the entry chunk — is separately explained: `rename_site_group` is only ever named inside `cloudRename.js`, which is a deliberately lazy chunk, so its absence from the entry bundle is by design, not evidence.)
- **PROVEN ON THE OWNER'S OWN DATA, not reasoned about.** Group `smrp1wrgg6u5` — Silvestri, the group this entire invariant was built for — was renamed **2026-07-31T19:23:15.307Z**. Four of its five live plans still carry that exact stamp. Plan **`sms9c5oc7jnt`** carries JSON null with `updated_at` **2026-08-05T19:18:05Z**, five days AFTER the rename. A document write erased a real timestamp; `nameAuthority` lost a stamped voter and the group dropped to the legacy majority tier — the coin flip `siteRenamedAt` exists to replace. It is the only group on the account in that state today, which is why a plain split-name query kept coming back clean.
- **THE FIX IS TWO HALVES AND NEITHER ALONE IS ENOUGH.** (a) **Client** — `projectName.renameStamp` is now the ONE parse (four modules had independently re-implemented `typeof … === "number" && isFinite(…)`), and `normalizeRenameStampForWrite`, applied inside `slimForCloud`, **OMITS** a marker this device does not know instead of asserting null. Omitting is the honest move, not a cosmetic one: it is the difference between saying nothing and claiming the project has never been renamed. (b) **Server** — omitting still erases, because the write replaces the whole jsonb, so `db/sites_rename_stamp_guard.sql` (a `BEFORE UPDATE` trigger, the same shape as the existing `sites_normalize_county`) holds the line at the row: **an UPDATE carrying no real stamp may neither clear a stamped row's marker nor change its project name.** Applied to production 2026-09-10; it rewrote no existing row.
- **The name half of that rule is not scope creep — it is what stops the fix backfiring.** Preserving the stamp alone would let an unstamped write land a STALE name on a row that now claims the rename's own timestamp; in a two-plan group that ties the stamped tier and hands the tie to `updatedAt`, which the stale row wins. Refusing both together is the correct reading: the marker and the name it stamps are one fact, and a write carrying neither is not a rename. Every real rename path DOES carry a stamp, and the new test fails the build if that stops being true.
- **A CHOICE DELIBERATELY NOT MADE, recorded so it is not "hardened" in later:** the guard does **not** refuse an OLDER stamp. `renameSiteGroup` computes `max(now, newest-local-stamp + 1)` from the plans THIS device has cached, so a genuinely later rename can legitimately carry a smaller number; refusing it would silently freeze a project's name for any device whose clock runs behind — a worse failure, and a silent one, than the case it would prevent. That residual (a stale-but-REAL stamp beating a newer one) is the B1440976 family and is answered at the pull, not here.
- **Also hardened, same write path:** `rename_site_group()` and `reconcile_site_group_name()` now refuse a null/non-positive `p_renamed_at` **by name**. `jsonb_set` is STRICT, so a null stamp made the whole expression NULL; measured, `public.sites.data` is NOT NULL today so the attempt aborted the group update with an opaque `23502` naming a column the caller never touched — safe, but only by a constraint neither function owns, and unreadable to whoever has to act on it. Both are now `language plpgsql` with an explicit raise the client surfaces on the rename banner.
- **MUTATION-PROVEN, both halves, in the order the house rule prefers — the check was pointed at UNTOUCHED code and required to go RED first.** `test/renameStampIntegrity.test.js` was written before the fix and run against the pre-fix source: **10 of 14 failed**, including `slimForCloud` emitting the key (`expected true to be false`), `siteRowFor`'s `data` carrying it, and 2 offenders in the one-parse sweep — while 4 known-good arms stayed green, which is what localises the failure to the code rather than to the probe. `db/test/sites_rename_stamp_guard.test.sql` was run against **production** before the trigger existed: **cases 1, 2 and 3 failed and every other case passed**; after applying it, **all 8 pass**, fixtures rolled back, 116 rows and the 34/64/18 split unchanged. The teeth are permanent, not just historical: the test feeds `carriesEmptyRenameStamp` the verbatim shape of production row `sms9c5oc7jnt` and requires it to be REJECTED, so a future edit that softens the predicate into a rubber stamp fails there.
- **A defect the teeth caught in the fix itself, on its first run:** `normalizeRenameStampForWrite`'s identity fast path (`at === doc.siteRenamedAt`) matched `null === null` and handed back the very document it exists to refuse. Asserting against the real pre-fix payload rather than a tidy fixture is what surfaced it.
