**AUDIT-FIRST — no event log exists.** Searched the whole schema (SQL migrations, `docs/REFERENCE.md`) and every client store for `activity_log`/`audit_log`/`event_log`/an activity-feed table: **none exists anywhere in this app.** Confirmed directly against production (project `lyeqzkuiwngunutlkkmi`) via the Supabase MCP, not assumed. So this feed is derived entirely from timestamps and state already on the records — see `lib/sinceLastHereFeed.js`'s own header for the full reasoning, and the two real gaps this required plumbing to close:
1. **`public.sites` had no creation timestamp at all** — only `updated_at`. Added one (`src/workspaces/site-planner/db/sites_created_at_20260908.sql`, applied to production): existing rows backfilled to a `1970-01-01` sentinel (so no plan that predates this feature can ever falsely read as "just created"), then the column got `default now()` — a brand-new plan gets a true creation time for free, zero app-code change needed. Verified: all 104 existing rows read the sentinel; new inserts pick up `now()`.
2. **Nothing records a schedule date moving or a task being marked done.** The embedded Scheduler's `planar_data` blob is a live document with no per-field history. Answered honestly by keeping a small per-account SNAPSHOT (plan building-count/sqft for the touched-pursuit set; per-task end-date/health) alongside the last-visit mark, diffed against the current state on each visit — it only ever compares two dashboard visits, never claims to reconstruct history from before this shipped. Stored the same way `dashboardLayout` already is (`profiles.prefs.sinceLastHere` jsonb, own-row RLS, read-modify-write + localStorage mirror).

**What the feed covers, and the honest limits of each:**
- **Plan created / renamed / meaningfully edited** — created/renamed read off real stamps (`created_at`, `siteRenamedAt`) with no scope limit; "meaningfully edited" (a building-count/sqft change) is scoped to whichever plans the existing Pursuits card already fetched element geometry for this visit (reusing that fetch rather than adding a new account-wide element scan) — a tracked/complete/dead plan, or a pursuit nobody opened this session, can still report being created or renamed, just not edited.
- **Schedule dates moved / tasks completed in bulk** — diffed against the snapshot; a task with no prior snapshot entry (the very first time it's seen) reports nothing, by design (no baseline to diff against yet).
- **Comps added** — real `created_at`, with rate (via a local re-implementation of `comps.js`'s `compHeadline` — see below for why it isn't imported) and size.
- **Notes written** — a page's real `createdAt` off the synced tree, quoting its opening words; a page with no words yet is dropped rather than shown with an empty quote.
- Two failure modes named in the brief, both handled: a long absence caps the list at 12 rows and states "+N more since your last visit"; the account's own actions from the last 30 seconds are excluded from every kind, so a reload seconds after doing something never shows it as new.

**Click-through.** Every row opens the thing it describes: a plan/comp row opens its plan (a comp's `project_id` is a bare site id, resolved to the plan's group id off the already-fetched sites list); a schedule-slip row opens the exact task (reusing the existing `openTaskInScheduler` intent); a tasks-completed row opens that project's schedule; a note row opens the exact page — this needed NEW plumbing (`Shell.jsx`'s `noteIntent`, mirroring the existing `docIntent`/`scheduleTaskIntent` shape exactly, plus a small effect in `Notes.jsx` that honors it).

**Design note, stated because it deliberately reads against the grain of an existing rule.** `docs/DESIGN.md`'s `typography.js` reserves monospace for "genuinely code-like content," never numeric product data. This card's sub-line is explicitly monospace per the dispatch's own repeated, deliberate instruction ("a quiet monospace sub-line… the sub-line is what makes this card worth reading") — a compact ledger line mixing text and numbers, not a pure numeric column, so it doesn't contradict what that rule actually governs. Uses the same `ui-monospace, monospace` stack `ParcelDataPanel.jsx` already carries locally for its own non-numeric record content, rather than inventing a new value.

**A real, measured bundle hazard found and fixed while building this.** The first cut imported `shared/comps/lib/comps.js`'s `compHeadline`/`rowToComp` from the Dashboard. `npm run perf:bundle` caught it immediately: `bundle.siteRouteAllowlist` failed with a brand-new "comps" chunk unexpectedly riding the Site Planner's own route, because that module is also reached (dynamically) from `CompsPanel.jsx` and a second, unrelated static importer changes how Rollup chunks it. Fixed by duplicating the small amount of logic needed locally (`dashboardCompsRecentFetch.js`'s own row mapping, `sinceLastHereFeed.js`'s own `compRateLine`) — the same "duplicated rather than shared, for a measured bundle reason" pattern this codebase already uses elsewhere (`releaseCanvas.js`, `ParcelDataPanel.jsx`'s own `MONO_FONT`). Re-ran `perf:bundle` after the fix: the allowlist violation is gone, all budgets pass (a few pre-existing, already-tracked chunks sit inside their headroom bands, unrelated to this item).
