### B2431296 — NEW-1: hovering an element in the editable PDF pops a huge yellow note box ("Planyr / Building 1") in Chrome's viewer `[Site Planner / print-export]` (bug) #site-planner #export #markup  *(owner report 2026-10-21 with screenshot; amends B2384528 / B2127664; owner constraint #33.)*
`[ ]` **⏳ merged — V1864240 PENDING (Verify: live — PDF export; the test-account pdf.js arm is the session's, Chrome + Bluebeam rechecks are Michael's).** Hovering any exported annotation in Chrome's / Edge's built-in viewer shows no note box.
- **Root cause (measured, not read):** the viewer is PDFium. It builds its OWN popup — a fixed 200 × 200 pt yellow note titled by `/T` — for any Text / Line / Square / Circle / Polygon / PolyLine / Stamp annotation whose `/Contents` is non-empty, and opens it on hover. The export wrote `/T (Planyr)` and `/Contents` = the element's name on every annotation. PDFium ignores a file's own `/Popup` annotations, so adding one (or `/Open false`) cannot help; **the only lever is not writing `/Contents`.** FreeText raises none (measured), so a callout's text stays.
- **What ships (`lib/pdfAnnotations.js`, `lib/annotationExtract.js`):** buildings, every other site element, parcel labels and measurements write NO `/Contents`; `/T` is the author only when the model knows one (no more "Planyr"); `/Subj` stays on every annotation (Bluebeam's Markups list: "Building", "Detention pond", "Road" …). The label is the text drawn in `/AP`. A markup's `/Contents` is now ONLY the comment the person typed in its Comment field; a measurement's is only its typed note. **Measurements:** with a `/Measure` the value is the drawn label + `/Measure` (so no `/Cap` caption and no `/Contents`); with no scale known the number is still the caption (the one case where `/Contents` is the only way to carry it).
- **Measured in a real Chrome (`ui-audit/verify-pdf-hover-popup.mjs`, headed Chrome-for-Testing 156 under xvfb, hover every annotation, count popup-yellow pixels):** known-good arm (`/Contents` + `/T (Planyr)` back on) raises ~24,000 px of yellow on 10 of 11 / 28 of 49 annotations — the run is VOID if it cannot; shipped output: 0 on every annotation without a typed comment (11/11, 47/47, and 43/43 on a PDF the real compose flow wrote). Printing: a PDFium render with annotations drawn shows 0 popup pixels with or without `/Contents` (a popup is hover state, never persisted); the file has no `/Popup`, no `/Open`, every annotation `/F 4` (Print only).
- **⚠ DECISIONS Michael can flip (stated, not hidden):** (1) a comment he TYPES into a markup still pops the box on hover in Chrome — it is his own note and Bluebeam's Comments column reads it; PDFium's box is fixed-size, so it cannot be made small. Dropping typed comments from `/Contents` would remove them from Bluebeam too. (2) Measurements no longer carry the caption `/Contents`: if Bluebeam's length/area label disappears after a move, that is why — restore the caption for measurements only and accept Chrome's note on them.
- **NOT checked:** Acrobat (different engine; spec + its documented behaviour only show a note for an annotation with comment text, so none is expected) and Bluebeam itself (none in the sandbox).
