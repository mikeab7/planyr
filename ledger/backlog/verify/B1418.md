- **THE WIRING DEFECT THIS TURNED UP IS THE OWNER'S LITERAL REPRO, AND IT WAS A SEPARATE BUG FROM B1415/B1416.** In MAP mode `SitePlannerApp` passed the breadcrumb `onSelectProject` and `onNewProject` but **no `onRenameProject`** — so the rename fell through to the uncontrolled `projects.renameProject` → the OLD `renameSiteGroup`, which wrote **only to this device** and never pushed at all. A rename made from the map viewer therefore never reached the cloud and came straight back on the next load: *"it didn't remember it."* It is now wired to `renameSite`, the one write path.
- **THE AFFORDANCE.** On the MAP the dropdown lists projects, so the rename is the row's own menu (B439, unchanged). In the PLANNER the crumb names ONE project — the control that names the thing you are looking at — so it now carries a plainly-labelled **`✎ Rename “…”`** row. Both reuse the same inline editor and the same `commitRename`, so there is one rename implementation and not a second to drift. `projects.renameProject` now RETURNS the store's promise, so an uncontrolled rename can surface an honest failure toast instead of the old silent no-op.
- **⛔ `editingWhere` IS NOT REDUNDANT WITH `editingId` — one identity, two editors is a trap, and it cost a debugging session.** The same project id addresses two inline editors: its row in the list, and the new crumb-level row. Keyed on `editingId` alone, clicking either mounted **BOTH**, each with `autoFocus`; the second to mount stole focus from the first, whose `onBlur` committed and closed the editor in the same frame. It read as the rename simply refusing to open, and **only in the planner** (the only surface where both editors can exist) — invisible to any source reading, and invisible to the map-mode tests, which passed throughout. The surface is now part of the key, so exactly one editor is ever live.
