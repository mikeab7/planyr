- **A REAL CORRECTNESS BUG, confirmed empirically before any fix — exactly the class of bug the brief predicted:** `assessRoutedDetention` (`lib/pondRouting.js`) compared the routed peak to the pre-development allowable, but a routing model that OVERTOPS (the basin fills past top of bank — the routing math has no data above that point, so the reported discharge is CLAMPED there) could still read PASS whenever that clamped, artificially-low discharge number happened to compare ≤ the allowable. Reproduced directly against the real engine: a 300×300 ft, 8-ft pond draining a realistic 45-ac watershed with a single 10-in floor orifice showed the 10-yr storm passing cleanly and the 100-yr storm ALSO reading PASS — while the basin was actively overtopping under the 100-yr inflow. **Fixed:** `pass = routed.routedPeakCfs <= preCfs + PASS_TOL && !routed.overtopped` — an overtopped storm is now ALWAYS a FAIL, with `shortByCfs: null` (never a fabricated cfs number once the comparison itself stops meaning what it looks like it means — LOUD-FAILURE). This is the exact "passes the small storm but fails a larger one, and it doesn't show" defect named in the brief's test (d); pinned by 3 new `assessRoutedDetention` tests using that exact reproduced fixture.
- **1) COMPOUND OUTLET MODEL.** `outletStructure.js`'s stage→discharge summing (`outletDischarge`) already supported an arbitrary-length stage array — the gap was the UI, hard-limited to "one primary orifice/restrictor + one optional weir." Rebuilt as a genuine editable STAGE LIST (`SitePlanner.jsx`): any mix of orifice/weir/restrictor stages, each individually editable (size + invert/crest), with "+ Add orifice"/"+ Add weir" and a per-stage "× Remove." New `sizeWeirForRelease` (`outletStructure.js`, the weir-length inverse of the existing `sizeOrificeForRelease`) plus 4 new tests (`outletStructure.test.js`) confirming a genuine 3-stage compound curve sums correctly and transitions cleanly at each invert/crest (the brief's test (a) — much of this was already covered by an existing 2-stage test; extended to 3 stages + a monotonicity check).
- **2) MULTI-STORM ROUTING + CHECK — already substantially built (worth noting, not re-invented):** `assessRoutedDetention` already looped over EVERY `criteria.requiredStorms` (whatever the active jurisdiction defines — Waller/generic 10/100, BKDD 2/10/100, Harris/FBCDD single 100-yr — nothing hardcoded) and already returned a full `perStorm` array with the allowable, routed peak, peak WSE, and required storage per storm, plus a correctly-OR'd `allPass`. What was missing: the overtopping bug above (a silent false-PASS), and the UI simply never rendered the Peak WSE / Storage columns or a prominent overall verdict — both added now (the table is `STORM | ALLOWABLE | ROUTED | PEAK WSE | STORAGE | PASS/SHORT/OVERTOPS`, with a dedicated "Overall — Post ≤ Pre: PASS — every storm / FAIL" banner that cannot read PASS while any row doesn't).
- **3) AUTO-SIZE SOLVES THE WHOLE STRUCTURE.** New pure `autoSizeCompoundOutlet` (`lib/pondRouting.js`, reuses `rationalPeakCfs`/`assessRoutedDetention`/`sizeOrificeForRelease`/`sizeWeirForRelease` — no new hydrology math): seeds a low-flow orifice at the smallest required storm's pre-development peak (the SAME screening midpoint-head heuristic B902's single-stage sizer used), then iterates — reusing `assessRoutedDetention` itself as the judge, never a parallel routing path — enlarging or SHRINKING whichever stage is responsible for the worst-failing storm (direction matters: overtopping means too little capacity, a rate exceedance without overtopping means too much — getting this backwards was a real bug caught and fixed mid-session, see below) and introducing a control weir the first time a larger storm needs help a bigger orifice alone can't sensibly provide. An emergency spillway (a broad weir at the design water surface / freeboard line) is always present as a safety overflow, sized off the largest storm's unrouted peak — never iterated, since it isn't itself part of the Post ≤ Pre proof. On success: writes the compound outlet, all required storms passing. On infeasibility (bounded at 12 attempts): still writes the best attempt, and reports the WORST still-failing storm honestly — by how much, or that it overtops — pointing at "⚡ Auto-size" (re-solve) or "Expand this pond" (below) as the fix. The "Auto-size detention" / "Propose outlet" button (unchanged label logic from B902 — manual override vs. suggested) now always calls this compound solver; a manual "Allowable release" still meaningfully seeds the solve (an `overrideCfs` param) without overriding what the actual Post ≤ Pre check verifies against.
- **Two solver bugs caught and fixed BEFORE shipping, both found by empirically running the real engine, not assumed correct:** (a) an early growth heuristic grew the RESPONSIBLE stage regardless of failure direction, which for an oversized seed diverged (grew an already-too-permissive orifice even further) instead of converging — fixed by seeding from the full design-column head (matching B902's proven approach) and by making growth direction depend on WHY a storm failed. (b) the solver's own bidirectional growth pushed a orifice's diameter to a physically nonsensical 8 FEET while chasing an extreme drainage-area input — which exposed a real modeling gap in `outletStructure.js`'s simple submerged-orifice equation (head is measured to the CENTROID: invert + half the diameter, so an 8-ft "orifice" reports ZERO flow until the water clears 4 ft of head), producing a nonsensical near-zero routed peak that read as a fabricated PASS. Fixed by capping the orifice's role at a physically sane 48 in (4 ft) — past that the compound structure leans on the control weir instead, which is what a real engineer would do anyway. Pinned by a new regression test (`pondRouting.test.js`) reproducing the exact scenario.
