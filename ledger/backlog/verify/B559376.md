- **MEASURED FIRST, per the brief's explicit instruction not to take the report as the spec.** Before changing anything: `StatusPills` offered exactly three values (Not Started / In Progress / Needs Attn.) — no Complete. The ONLY accept path was Enter (or the "Update Successors" button, which does the same thing) via `apply()`, which applies whatever's in `pending` — defaulting every Ready-to-Start successor to `yellow` (In Progress) and every Already-Active one to `null` (no change) unless the user picks a pill. Escape and the ✕ both call `onClose()` with no side effect. Dismissing (any route) applies nothing.
- **THE HAZARD, addressed structurally, not just by care.** B463920 fixed a real bug in this exact modal: the Enter that dismissed it was read TWICE — once by `apply()`, once by the grid's document-level key handler (which opens a picker on Enter by design), reopening the status menu the modal had just closed. The fix was a capture-phase latch (`overlayAtKeyStartRef`) thirteen overlays share. A second accept control on this same modal is exactly the shape that could re-arm it, so:
  1. **Enter's own line is byte-for-byte unchanged** (`if (e.key==='Enter' && changeCount>0) apply();`) — it still just applies `pending`, still defaults Ready-to-Start rows to In Progress with zero interaction. That is the muscle memory kept intact.
  2. **Complete is a genuinely separate accept path**, not a fourth value routed through Enter: a per-row `Complete` pill (reuses the existing hardened `pending`/`apply()`/Enter machinery verbatim — same code, wider value range) for picking Complete on one specific successor, PLUS a dedicated footer button ("Mark Complete") and a dedicated key — **Ctrl/Cmd+Enter**, matching the FormulaBar's existing save accelerator at `handleKey` — that bulk-marks every Ready-to-Start successor Complete in one action (`applyComplete()`, forces `green` for the Ready-to-Start set, leaves Already-Active rows exactly as pending). Never plain Enter for the new action.
  3. **Both accept paths, and dismiss, are asserted clean AND mutation-proven** (`ui-audit/verify-successor-complete.mjs`, real headless Chromium, 29/29): no colour menu left open, no stray grid selection, for Enter (with a hand-picked Complete pill), the Mark Complete button, and Ctrl+Enter alike. Reverting the latch (`if (overlayOpenRef.current) return;`) turns the Enter-path check red exactly as B463920 first proved — **and** the run explicitly checks the two new paths under the SAME mutation: **both stay clean, and this is reported rather than assumed** — Ctrl+Enter is excluded by construction from the vulnerable code (the grid's Enter-opens-picker branch is itself gated `!e.ctrlKey && !e.metaKey`), and a button click never dispatches a keydown at all, so neither can reach the mechanism the latch guards regardless of the latch. That is a stronger guarantee than "the latch protects it," and it's verified, not claimed.
- **CHAIN BEHAVIOUR — decided explicitly: ONE HOP AT A TIME, prompting again, never a silent cascade.** Completing a successor that itself has its own Ready-to-Start successor opens a NEW prompt for that successor — it does not walk the chain automatically. This is not new code: the app already re-opens a fresh prompt whenever `updateTask` flips a task's health to `green` and finds a Ready-to-Start successor of ITS OWN (the existing "fire when task transitions to complete" block), regardless of caller — reusing it uniformly for the modal's own completions (instead of writing a second, modal-specific chain mechanism) is what keeps grid-driven and modal-driven completions behaving identically. Proven live: completing successor #8 via the modal opened a fresh prompt for #8's own successor #9, and skipping that follow-up left #9 untouched — no silent multi-level change at any point.
- **⛔ A RACE THIS ITEM'S OWN BULK ACTION CREATES, FOUND AND FIXED, NOT JUST REPORTED AS A CAVEAT.** The bulk "Mark Complete" button can complete MORE THAN ONE Ready-to-Start successor in a single action. Each independently schedules its own 80ms-delayed "does this one have its own Ready successor?" check, and both used to write directly into the single `successorPrompt` state slot — a genuine race where the second write silently clobbers the first, losing a follow-up prompt the "one hop, prompting again" rule requires. **Measured live, not reasoned about:** a fixture with two parallel branches (Branch A / Branch B, each with its own child) bulk-completed in one action reproduced the loss — only Branch B's follow-up prompt appeared, Branch A's was silently gone. Fixed with a small FIFO queue (`successorPromptQueue`): every triggered prompt queues, and a drain effect shows them one at a time as each closes. **Mutation-proven the fix is load-bearing**, not decorative: reverting the queue back to a direct `setSuccessorPrompt(...)` write reproduces the exact loss on the same fixture (`["Branch B"]` — Branch A gone); with the queue, both `["Branch A","Branch B"]` are offered in sequence.
- **Adjacent case, checked rather than assumed: a successor that is ALREADY complete never appears in the prompt at all** — `successors` is filtered at the source (`t.health !== 'green'`), unchanged by this item, and verified live against a fixture with an already-green sibling: it never shows in either the Ready-to-Start or Already-Active section.
- **Adjacent case: Escape.** Behaves identically to the ✕ and Skip — applies nothing, even with a Complete pill pre-picked on a row (verified for all three dismiss routes).
