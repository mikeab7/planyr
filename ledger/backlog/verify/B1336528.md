- **ROOT CAUSE, confirmed structural rather than a bad number (AUDIT-FIRST).** `shared/ui/cornerClearance.js`'s `cornerClearanceFromBottom` — the exact mechanism B1167120 built to replace the old fixed-292px constant — only ever queried the PARENT document for occupants (Leaflet's own corner box, anything marked `data-canvas-corner`). The Schedule route's entire grid lives inside `<iframe src="/sequence/">` (`Scheduler.jsx`), a separate document this function never had a way to see into — so on that route it always fell back to the bare corner, correctly for a genuinely chrome-free route, incorrectly here because the route only *looked* chrome-free from the parent side. B1321888's own per-route audit table (above) made exactly this mistake for the same reason: it read `public/sequence/index.html`'s static markup (true: no fixed bottom-right element there) but never hit-tested the iframe's live, scrollable grid content, which is what the owner's production repro actually hit (`iframe.contentDocument.elementsFromPoint` at the control's rendered position returned `DIV.drow`, a real grid row).
- **TWO ROUTES CONSIDERED, the general one taken.** (a) [CHOSEN] Make `cornerClearanceFromBottom` descend into same-origin iframes and content-aware hit-test their own DOM (`elementsFromPoint`, the same technique the live diagnosis used) — fixes this route AND any future embedded workspace, with zero changes needed inside `/sequence/` (a large, separately-maintained ~17,000-line legacy page this shell should not have to edit just to be measured correctly). (b) [NOT CHOSEN] Give the Schedule route its own docked anchor (`chromeDock.js`'s pattern), reserving a fixed band whenever that route is open — smaller, but it is exactly the "reserve a worst case that usually isn't there" shape B1167120 already fixed once: a fixed reservation would still be wrong the moment the iframe shows a view with nothing at that corner (the embedded app's own Dashboard/Reports section, or a grid with too few rows to reach the bottom). Chose (a) because it is the general fix and is *why* this bug existed in the first place — the function's whole job is "measure the real DOM," and an iframe's DOM is still real DOM, just behind one more boundary.
- **MECHANISM.** For each same-origin `<iframe>` whose own box overlaps the control's column, hit-test a point near the bottom-right corner of the control's own base-position footprint, translated into the iframe's local coordinate space (`elementsFromPoint` inside a frame is relative to that frame's own viewport). The point is deliberately NOT the footprint's geometric centre — this function is never told the control's height, and a centre computed from width alone can miss genuine overlap near the edges (measured live in the browser-real check below: a 30px control over a 24px row missed it at centre, hit it correctly near the corner). The first (topmost/most specific) hit is a genuine occupant unless it's the iframe's own `<html>`/`<body>` root or fails the same visibility check every other candidate already gets. A cross-origin iframe (none exist in this app today) is silently skipped. A safety cap (`MAX_IFRAME_NEEDED_PX = 160`) stops a degenerate hit (a large structural container with nothing more specific painted at that exact pixel) from reproducing the old reserve-everything failure from a different cause.
