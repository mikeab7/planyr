- **⛔ THE BRIEF'S OWN SUGGESTED COLUMN TYPE WAS A BUG, CAUGHT BEFORE IT SHIPPED, NOT FOLLOWED BLINDLY.** The brief said migrate to `numeric(3,2)`. Tested live against production before writing the migration: `select '10.00'::numeric(3,2)` raises `22003 numeric field overflow` — `numeric(precision, scale)` counts TOTAL significant digits in `precision`, so `numeric(3,2)` has room for only ONE digit before the decimal point, a max of 9.99. A rating of exactly 10 — a perfect score, an entirely ordinary value — would have hard-failed to insert, not silently truncated. This isn't hypothetical: production already held a real `rating = 10.0` (row `9830a4b5-d9b6-4305-a238-c8b93cbb1b00`), which I confirmed would fail under `numeric(3,2)` before touching anything. Used **`numeric(4,2)`** instead (2 digits before the decimal, up to 99.99 — comfortably covers 1-10 at quarter-point resolution). Both the reasoning and the live-tested overflow proof are recorded in `db/food.sql`'s own migration comment so a future session doesn't have to rediscover it.
