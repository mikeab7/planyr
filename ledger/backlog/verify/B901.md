- **Bug (1) root cause — `NumInput` (the shared numeric-field component `SitePlanner.jsx` uses everywhere):** `commit()` treated an EMPTY draft (an intentional clear) identically to unparseable garbage (a typo) — both fell into `clampNum(parseFloat(draft)) == null` → **silently revert to the last committed value, never call `onCommit` at all.** So a field could be typed into but never actually committed to `null` via the keyboard, no matter how it was cleared (Backspace, Delete, Ctrl+A+Delete, triple-click+Delete, End+Backspace — all hit the same silent-revert branch). The reported "1515 → 15115" mangling is this same silent-revert fighting the user's next keystrokes, not a separate bug.
- **Fix (`NumInput`, root cause not a band-aid):** new opt-in `allowClear` prop (default `false` — **every existing call site keeps its EXACT old behavior unless it explicitly opts in**, so a REQUIRED geometry field like building width/depth or a road setback can never silently go `null`). When `allowClear` is set and the draft is emptied, `commit()` now calls `onCommit(null)` instead of reverting. Applied to **all 22** `NumInput` call sites whose `onCommit` already null-coalesces (`Number.isFinite(n) ? n : null` or equivalent) — every one of these was equally broken, not just the reported field: `releaseRateCfs` (the reported field), `daAcres`, `daImpPct`, `pumpRateCfs`, the outlet fields (`diameterIn`, `invertElevFt` ×2, `maxCfs`, weir `lengthFt`), `depth`/`freeboard`/`slope`/`tobElev` ×2/`poolElev`/`receivingFlowlineElev`/`depthToWaterFt`/`padElevFt`/`slopePct`/`shrinkPct`, and the two floodplain-mitigation manual-override fields (`fm.onChange`). Required/geometric fields (width, height, setback, aisle, bay dimensions, …) were deliberately left untouched — their `onCommit` handlers don't null-guard and must never receive `null`.
- **Bug (2) — proposed-outlet removal not surviving a real reload for a signed-in (cloud-synced) session.** Static analysis + a local (logged-out) reproduction attempt **disproved** the owner's own leading hypothesis ("the loader auto-derives an outlet from the persisted release on load") — `defaultOutletForPond`/`propose()` is called from exactly ONE place in the whole codebase (the "Propose outlet" button's own click handler; verified via a repo-wide grep), and a logged-out local reload correctly showed the outlet gone after removal. The real gap, found by reading the element-level cloud-sync engine (`lib/elementSync.js`, B671/B672): the engine's **last-ditch keepalive commit** of still-debounced per-element edits (exists specifically so an edit sitting in the ~750ms debounce window isn't lost on unload) was wired **only** through the app's internal forced-reload registry (`app/flushRegistry.js`'s `flushAll()`), which fires **solely** on chunk-recovery or the ErrorBoundary's own "Reload" button — **never** on a genuine user-initiated browser reload/close, which only fires the native `beforeunload`/`visibilitychange` events. So a real F5/reload-button/tab-close never triggered the keepalive commit; only the (now largely superseded, B672) whole-doc blob save did.
- **Fix (`SitePlanner.jsx`):** the element-sync keepalive-flush effect now ALSO listens to the real `beforeunload` and `visibilitychange`(hidden) events directly — the exact same pattern already used for the whole-doc save a few lines above — in addition to (not instead of) `registerFlush`, which still covers the forced-reload path. Also calls `reconcileElems(false)` first so the very latest edit is diffed into the dirty queue before reading `pendingOps()` (belt-and-suspenders — the debounced autosave effect that normally does this may not have ticked yet).
