- **ROOT CAUSE, found by an Explore agent tracing all three surfaces.** All three (the switcher, `LibraryHome`'s own Projects grid, the Notes sidebar) ultimately call the SAME `listProjects()` = `groupProjects(loadSitesList())` — there is no parallel project store, by design (`projects.js`'s own header: "a project IS a Site Planner site group"). `loadSitesList()` reads a per-device LOCAL CACHE, populated only by `pullCloud()`. The existing self-heal, `warmProjectsIfEmpty()`, is gated on the cache being **genuinely EMPTY** (`if (loadSitesList().length) return {warmed:false, reason:"already-warm"}`) — so a cache that already holds SOME projects but has quietly DIVERGED from the cloud (a device that missed a sync; the codebase already has a `cloud-group-count-diverged` telemetry event for exactly this, with nothing wired to self-heal it) never gets a second chance, no matter how many times the switcher is opened. That is precisely the reported failure: Richfield/Silvestri/Woods Road are real, active site groups: their absence isn't a filtering rule, it's a stale local mirror. (The Library grid's 29 vs. the switcher's 6 is a SEPARATE, non-bug asymmetry — Library's larger number includes file-filing-only entries like "Untitled site" with no real site group at all, which is why Pursuits/Operations, real site groups with no filed drawings, are absent FROM Library instead.)
- **THE FIX, two parts — a union/reconcile, never a narrowing, per the owner's explicit ask.** **(1) `reconcileProjects()`** (new, `shared/projects/projects.js`) is `warmProjects()`'s always-pull sibling — the identical safe/idempotent cloud pull ("the exact pull the Site Planner runs on login"), just no longer gated on the cache being empty. Wired into `ProjectBreadcrumb.jsx` on the dropdown OPEN specifically (never on mount, and throttled to once per 30s) so opening the switcher is never a network hazard, but a stale cache gets a real chance to catch up on the moment a user is actually looking. **(2) `withCurrentProject()`** (new pure helper, `shared/projects/projectModel.js`) backfills the routed/currently-open project into the list SYNCHRONOUSLY, before any network round-trip resolves — the project the owner called out as "the clincher" (standing in it, right now) can never read as though it doesn't exist, even mid-reconcile. A pure union: every other cached entry passes through untouched (`toBe` identity-checked in the unit test when nothing needs backfilling).
- **Pursuits/Operations still survive** (unchanged — they were never victims of this bug; they're real site groups the switcher already lists correctly, just with no Library folder yet, which this fix doesn't touch).
- **Deliberately NOT built this session:** a full three-way union that also pulls in Library-folder-only and Notes-only project references with no real site group behind them at all (e.g. Library's "Untitled site" file-filing artifacts). The owner's own language ("Where a referenced project genuinely no longer exists, say so explicitly... rather than rendering it as a normal group header") asks for that reference to be handled carefully, not silently added as a normal switcher row — and every concrete case in this report (Richfield, Silvestri, Woods Road) turned out to be a real, active site group hidden by cache staleness, not a genuinely orphaned reference. Building a speculative three-store merge without a confirmed case of a real orphan risked polluting the switcher with junk (Library's file-filing-only "Untitled site" entries) rather than fixing anything. If a genuine site-group-less orphan turns up on a future live pass, it's a follow-up, not a gap in this fix.
