**THE ENTRY-POINT AUDIT, done BEFORE choosing where to fix (the #948 lesson).** Create-on-type lives in exactly **one** component — `ContactPicker.commitTyped()` — serving **two** call sites, the grid Owner cell and the master-table Owner cell. That component IS the shared ancestor, so the guard sits there and both routes are covered by construction. The other two ways a contact can come into being are deliberately untouched: **`ContactsPanel.addContact()`** is the explicit "Add contact" form (already a decision — asking again would be the nag), and **`ensureContacts`** is a load-time repair pass, not typing. **The main app (`src/`) has no contact registry at all** — zero matches for `ContactPicker` / `responsibleParty` / `settings.contacts` — so there is no cross-module ancestor and no other cell to fix. Reported rather than assumed.

**⛔ THE FACT THAT DECIDED WHAT "DECLINE" MEANS, and it is not a preference.** `ensureContacts` runs on **every load** and re-derives a contact for **any task owner name missing from the registry**. So "commit the owner but don't create the contact" does not avoid the creation — it defers it to the next reload, where nobody is asked. The owner field and the registry are already **one decision**; this makes that visible instead of changing it. Hence: **confirm = assign AND create · decline = neither, and you are returned to the text.** `test/contactCreateConfirm.test.js` pins `ensureContacts`'s behaviour so a future reader knows the coupling was deliberate and can relax the decline path if it ever stops being true.

**THE ROUTES, and which ones stay silent — because a guard that nags on a normal selection gets turned off within a day and then it has made things worse.** ASKS: unrecognised text committed by Enter/Tab, and unrecognised text on click-away. DOES NOT ASK: an exact registry match · picking a person from the filtered list · the ghost-prefix completion · clearing the field · and the dropdown's own **`+ Add "X" as new contact`** row, which is already an explicit, self-describing choice — double-confirming it would be pure nag. Every one of those is a separate assertion in the harness.

**BLUR WAS DECIDED, NOT INHERITED.** The old handler committed on click-away, which is exactly what would have made the prompt theatre. Committing silently defeats the item; discarding silently throws away typing. So click-away with unrecognised text **raises the question and keeps the editor open** — the one option that neither writes nor loses. Recognised text and an empty field commit on blur exactly as before.

**DECLINING RETURNS THE TEXT UNHARMED, and that is guarded twice** — because getting it wrong would re-introduce the very class B443536 just fixed. `declineNew()` never touches `query`, restores focus, and places the **caret** (never a selection — a selection would let the next keystroke eat the text again). Proven in the browser: decline, then Backspace, and the field reads `Jason Berca` rather than an empty box. Typing while the question is up dismisses it, so it can never sit there quoting a name the field no longer says.

**PANEL-BREVITY.** One plain sentence in the space the dropdown already occupies — `No match — add "Jason Bercaw" as a new contact?` — plus two short buttons. No heading, no paragraph, no dialog wall; saying no is a button AND Escape AND where a stray click leaves you. The unit test measures the VISIBLE copy against a character budget (the first version of that assertion counted `?` in a source slice and caught a ternary — it was measuring the wrong thing and was fixed).
