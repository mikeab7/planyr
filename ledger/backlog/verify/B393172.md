- **WHY IT MATTERS MORE THAN IT LOOKS:** Undo-enabled is the only signal a user or an operator has that a plan has been modified. Once selection alone arms it, a plan you merely LOOKED at is indistinguishable from one you edited — which cost real time, six clicks and six entries, and an unwind to be sure.
- **THE FIX IS AT THE PREDICATE, NOT AT THE 210 `pushHistory()` CALL SITES.** A press handler pushes the pre-mutation snapshot BEFORE it knows whether a mutation follows — that is the transaction model, and unpicking it per call site would be 210 chances to get the drag threshold wrong, which the item expressly rules out. `canUndo` now asks the question the button claims to answer: **does any frame DIFFER from the live state?** `undo()` has always asked exactly that (its `keyOf` dedup); the button never did.
- **IT IS A REFERENCE SCAN, NOT A STRINGIFY.** `keyOf` is a JSON.stringify of the whole plan and this is read on every toolbar render. React replaces the collection arrays on every real mutation, so an identical set of references is proof nothing was committed. The component pays the exact check once per real change (`canUndoNow`, memoised on the drawn collections + the history tick), never per frame.
- **THE SIBLING, CHECKED AND ANSWERED: Redo's state was always right; the CONTROL was mislabelled.** A disabled `<button>` carries no `aria-disabled` attribute at all, so a checker reading that attribute got null and reported the empty Redo control as enabled. Both buttons now carry `aria-disabled` beside `disabled`. Not a state bug — `canRedo()` is `future.length > 0` and the future is empty on a fresh load.
