**WHAT CHANGED, in the order the user meets it.**
1. **AT REST** — the address field, then **Select parcels** (primary, accent-filled), **Draw**, **Drop a pin**. `Draw` is B831780's "Start blank" (`startBlankHere`) promoted out of the caret menu into a first-class button; it commits immediately, because drawing a boundary is already an answer. Nothing is preselected and there is no mode.
2. **THE DECIDE BAR** — B831776's count + ✕ are kept exactly as they were (deliberately NOT rebuilt); only the tail changed, from one verb chosen by `mode` to three live at once: **Plan a site** (`planSelected`) · **Log a comp** (`placeCompOnSelectedParcel`) · **Place a site plan** (the same upload-first `startOverlayUploadRef` path the Comps list's own "＋ Site plan" button uses). The status dot took its colour from `mode`; it is neutral now — it must not imply an answer before one is given.
3. **AN ACREAGE CHIP ON THE SHAPE** — the selection's total acreage renders as a small chip on the selected parcels, as a Leaflet `divIcon` so it travels with the map. The decide bar is pinned centre-top and the parcels can be far from it; this is what keeps the question tied to the ground. `interactive: false`, so it can never eat a press aimed at the parcel under it (CHROME-NEVER-EATS-A-PRESS).
4. **ADDRESS SEARCH STOPS CREATING** — a search now simply FINDS: it moves the map, selects the parcel under the point, and hands you the decide bar (`selectParcelAt` already pushed the found parcel into `selected`, so this fell out of deleting the branch). A search that finds NO parcel offers "Drop a pin here", which marks the point and asks the same question. The toggle's whole job — and its literal `aria-label`, "What an address search creates" — is gone.
5. **THE SPLIT BUTTON IS GONE, AND ALL THREE OF ITS ANCHORS ARE STILL REACHABLE** — *on the map* = Drop a pin → Log a comp · *on a parcel* = Select parcels → Log a comp · *on a site plan* = that plan card's own "Pin comp here" (its three-dot menu, shipped #1559). `startPinOnOverlay` is untouched; it just has one door now instead of two.
6. **THE STICKY ANSWER, which is the one thing this makes slower and the debt it pays back** — under the toggle, flipping to Comp once meant every following search made a comp; ground-first asks each time, so entering comps one at a time costs one extra click each. The last verb chosen leads the next decide bar, reusing B848304's own `planarfit:compAnchorKind:v1` pattern — **sessionStorage, never localStorage**: a sticky answer is a shortcut for the task you are in the middle of, not a mode you can leave armed for tomorrow. A fresh tab starts on "Plan a site", the safest of the three (a plan is private scratch work; a comp is a standing market record). Bulk entry (Paste comps, Import KML) never comes through this toolbar and is untouched.
7. **THE RAIL IS NOT RECOUPLED.** B850016's rule outlives the state it was written about: `mode` is gone, `panelTab` is unchanged, and no centre-toolbar control moves the rail. `panelTab` still READS the retired `planarfit:mapMode:v1` key to seed itself, on purpose — that value is already sitting in every existing user's browser as "which list was I looking at", and dropping the read would silently reset the rail for all of them. Nothing writes that key any more. Guarded by `test/mapModeDecoupling.test.js`, which now asserts the STRONGER property (no toolbar mode exists to couple to) plus that the seed read survives.

**WHAT IS DELIBERATELY NOT IN SCOPE — the fourth verb.** The owner also wants **"add a note"** on this bar. There is no map-anchored note anywhere in this app today — no handler, no record, no marker — so it is a NEW CONCEPT, not a fourth button, and it is filed as its own item, **B1368145**. `verbLabel("note")` returns `""` and a unit test pins that, so nobody can half-invent the feature by adding a label here.
