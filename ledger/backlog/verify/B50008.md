- **CAUSE, measured on his page:** `isDoubleTap` compared **`Date.now()` read INSIDE the handler** against the previous press. The second `pointerdown`'s handler began **307 ms after its own event fired** (`e.timeStamp` 330662 → handler at 330969). `DBLTAP_MS` is 350. The queueing delay alone nearly spends the whole budget, so an ordinary **150 ms double-click measures ~450 ms and is discarded**. The busier the plan, the more often a double-click silently does nothing.
- **FIX:** `e.timeStamp` for both the stored value and the comparison — it is stamped when the browser CREATES the event, so it measures the gesture rather than our response time. Applied to **every** call site by fixing the helper, which they all inherit (elements, markups, both measure paths, the callout box and leader, the pond label, the parcel, the dimension number). The gesture moved into a pure `lib/doubleTap.js`.
- **⛔ DBLTAP_MS WAS NOT RAISED, AND THAT IS THE POINT.** Raising it hides the defect (the budget is being spent by the wrong thing) and makes genuinely slow pairs — a deliberate click, pause, click — start firing as an edit. Pinned by a unit test that shows an 800 ms budget misfiring a 500 ms pause.
- **NEGATIVE CONTROL, as required — proven RED first, in the same run set.** `e2e/dblclick-properties.spec.js` holds the main thread with a real synchronous long task BETWEEN the two presses (dispatched from a capture-phase `pointerdown` listener, so it is the app's own handler queue that backs up, exactly as on his plan) and asserts Properties still opens. **With the wall clock restored the case fails — "a double-click on a busy plan did not open Properties" — and passes on the fix.** The spec also runs the idle case first and notes it, because the idle case passed on the broken build too: a double-click test on an idle page tests nothing here.
- **Related but separate — the amplifier.** Yesterday's measurement (`docs/perf/PERF-TAIL.md` strand) found the main thread 24–80% busy on JS whenever the pointer is over the drawing; that is what supplies the 307 ms. **The clock is wrong even on a fast machine**, so this was fixed regardless and is not filed as a perf item.
