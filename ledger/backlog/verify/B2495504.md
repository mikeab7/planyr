### B2495504 — A FRESH Schedule tab always landed on a project's OLDEST schedule even though the account's remembered "last active" schedule for that project was saved correctly: the shell's carry-in treats ANY linked schedule being active as "already showing the site", so it never asked the embed to consult `lastActiveBySite` `[Scheduler]` (bug, medium) #scheduler #persistence  *(recurrence of B1080547, V934064 FAIL 2026-10-29 — AUTH-SWEEP 2; a fresh tab and a fresh browser context both opened the oldest of three schedules while `schedule_account_index.last_active_by_site` held the third's id)*
**Stopping rule:** a signed-in live run on a throwaway project with three schedules — a fresh tab AND a fresh browser context both open the schedule last used, switching afterwards is never fought, and V934064 records a dated pass.
- Root cause (read from code, then proven by the failing live run): `navState.needsScheduleCarryIn` returns false when the active schedule is any member of the site's linked set; a fresh tab boots on `pickActivePid` (the oldest), so `planar:nav-select-by-site` — the only message whose handler reads `lastActiveBySite` — was never posted.
- Fix: new pure `navState.needsArrivalSelect` + a separate once-per-arrival effect in `Scheduler.jsx` (`arrivalSelectRef`) that posts the select once for a routed site with several linked schedules; the embed resolves the remembered schedule (and no-ops if already active). Guards: `test/schedulerNavState.test.js` (needsArrivalSelect block), existing `schedulerMultiScheduleReturn` unchanged.
- Verify: live
