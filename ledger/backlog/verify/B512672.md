- **HIS DECISION, VERBATIM:** *"Tab on the first item of a list INDENTS IT, and does NOT invent an empty parent bullet… build the indent as a level change on the item, not as 'nest under a fabricated parent'."* Rationale he gave: he has twice asked for this to work more like OneNote, where the list renders one level deeper and the user never sees a bullet they did not type.
- **THE RULE, NOW THE MODULE HEADER'S FIRST SENTENCE, as he asked:** **Tab changes the level of the current item; it never creates a node the user did not type.**
- **WHY IT COULD NOT BE DONE BEFORE, and why the model turned out to be able to represent it after all.** A `listItem`'s content is `paragraph block*`, so ProseMirror nests a bullet by making it a CHILD of the bullet above it — and the first bullet has none, so `sinkListItem` declines. He asked to be told LOUDLY if the list model genuinely could not represent a first-item indent without a parent node. **It can, and the answer is not to change the shape at all:** `indent` is a small integer attribute on `listItem` / `taskItem`. Same nodes, same order, same parents, one number different.
- **THAT MAKES HIS CONSTRAINTS TRUE BY CONSTRUCTION RATHER THAN BY CARE.** Nothing is created, so there is no empty parent to assert the absence of. Shift+Tab is `n − 1`, so returning to the original level is exact rather than a repair. At `n === 0` the attribute renders **nothing**, so an indent/outdent pair leaves the stored document byte-identical.
- **THE OPTION THAT WAS REFUSED, recorded so it is not re-proposed:** mint an empty parent bullet and sink into it. It gets the picture right and puts a bullet with no words in it into the document — which then has to be exported, printed, counted, outlined, searched and eventually deleted by hand. This module has spent six rounds removing exactly that litter.
- **REAL NESTING IS NOT REPLACED, it is completed.** Where `sinkListItem` CAN act it still does, and the result is a real nested list exactly as before. The extension asks `can().sinkListItem(...)` and declines — that question IS the boundary between the two mechanisms, answered by the editor rather than by a rule someone wrote down.
- **IT SITS ABOVE THE LIST KEYMAP (priority 200), and that is load-bearing.** `notesTabKey` is a FALLBACK at 50, which is right for Tab and wrong for Shift+Tab: an item at level 2 by attribute is, to ProseMirror, an ordinary first item, so `liftListItem` would lift it clean out of its list while it still owed two outdents.
- **PDF-PARITY, MEASURED NOT ARGUED.** The level is written into the markup (`margin-left` on the ITEM, so the bullet moves with its words), so the print sheet and the HTML export carry it through the one serializer they already share. The harness opens the printed sheet and reads its first bullet — `indented-on-paper`. Markdown carries the level as indentation, which is how Markdown spells nesting, so the export is **not lossy** (asserted: the lossy list is unchanged).
