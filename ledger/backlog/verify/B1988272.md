### B1988272 — Clicking a lot at Grand Port takes 1.5–2 s before the app shows it heard the click `[site-planner / parcels]` (bug) #site-planner #parcel #perf #gis *(Owner report 2026-09-29, Grand Port / Chambers County: "it's slow to seem like it knows that I clicked on the parcels.")*

`[x]` **Measured before any change (owner's Chrome, build 2aaa1c4, throwaway "Concept A (copy)"):** lot row at 1.47–2.0 s after pointerdown; 0–189 ms nothing on screen (a 152 ms long task), a `Querying county GIS…` span at 189 ms, ~1.2–1.4 s waiting on the county server (`gisdata.pandai.com` Chambers `MapServer/0/query`), row + record panel at ~1.47 s. **The county server is the floor** (any query returning a row is ~0.9–1.3 s regardless of geometry or field list; only `returnCountOnly` is fast, 71 ms). Ruled out: national fan-out (one Chambers query per click) and the outline layer.
`[x]` **1 — instant acknowledgement at the cursor.** New `src/shared/ui/clickAck.js` (+ `.click-ack` in `index.css`): a pulsing ring anchored at the pointer plus a busy cursor, appended as PLAIN DOM synchronously in the pointerdown handler (`beginIdentifyPress`) — deliberately not React state, since the planner's own render is the ~150 ms long task being complained about. Lifecycle can never hang: lot lands → cleared · no lot / source unreachable / error → the ring becomes a short tag ("No lot here" / "Couldn't get that lot") at the same spot, then leaves · a drag (pan) → cancelled on release · a newer click supersedes it · a 12 s watchdog turns a wedged host into the same tag. Reduced-motion: static ring.
`[x]` **2 — kill the pre-query delay.** `quickAddAt` used to set `busy` state BEFORE the county request, so React rendered the whole planner (the long task) ahead of the fetch. Now the request leaves first and the busy text paints in the following task, and only if no answer already landed (`settled` guard, so a fast answer can't be overwritten by a late "busy"). The `quickAddAt` result state now flows through one exit (`setRes`) that also settles the ring.
`[x]` **3 — cut the county wait: NOT shipped, deliberately.** No trustworthy fast source exists to draw the outline first: the Chambers service has no unjoined layer; `returnCountOnly`/`returnIdsOnly` cannot return a shape; Planyr's `/api/parcel-cache/svc/chambers` is a 24 MB whole-county file (3.5 s); the StratMap statewide layer replied in 44 ms but 172 bytes and was never confirmed to carry this lot, and Chambers's outline layer is an image (no vector geometry to hit-test, unlike vector counties where the Map view's B441 optimistic highlight already applies). Painting an outline from an unconfirmed source would break B137 (what he sees = what he can select), so the stored parcel still comes only from the Chambers record. Follow-up if wanted: verify StratMap's correct layer index against several Chambers lots before using it as an outline-first source.
- **Adjacent cases:** *Map view Select-parcels* — a different code path (Leaflet click → `handleClick`), now wired to the same ring (`MapFinder.jsx`), which appears on release there (Leaflet only delivers `click`, not pointerdown); its optimistic highlight for vector counties is untouched. *No-lot click* — ring becomes "No lot here" (e2e). *Slow/failed county* — 8 s fetch timeout ends it with the unreachable tag; 12 s watchdog as backstop (unit-tested). *Rapid clicks on two lots* — the first click is superseded (existing B53 behaviour) and its ring is cancelled; only the second remains, then lands (e2e). *Harris (bare-OBJECTID)* — same code path; sandbox timing below uses a mocked Harris service because the real hosts are egress-blocked.
