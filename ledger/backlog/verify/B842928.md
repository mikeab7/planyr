- **THE MECHANISM — found, not guessed at.** `MapFinder.jsx`'s aerial layer sets `detectRetina: true`, which on a HiDPI display makes Leaflet fetch tiles at the map's rounded zoom **+1** (drawn at half CSS size to preserve geographic coverage — the file's own B220 comment documents this). The labels/Reference layer had **no `detectRetina`**, so its native tile zoom was always exactly the map's rounded zoom — i.e. **structurally one level behind the aerial on every retina display**, which is the owner's dpr ~2.13. That deterministic 1-level/half-density gap is finding #3 in the report ("Half the pixel density of the aerial") and was reproduced byte-for-byte in this sandbox. The reported 6-level gap ("pinned at z9, stayed pinned across two more zoom-ins") is this same structural gap **compounding under real latency**: the Reference layer's tiles are the heavier of the two (ArcGIS composites road/label cartography server-side — measured 35–71 KB PNGs vs the aerial's lighter, pre-cached imagery), so a layer that is already one native step coarser than its sibling falls further behind on every fast zoom transition, and nothing in this codebase's tile-cache eviction (`capTileCache`) or Leaflet's own pruning ever helps a layer *catch up* — they only ever discard what is no longer wanted. Reproduced live in this sandbox (against `arcgisonline.com`, not a mock): a fast 9-double-click zoom-in burst plus two more double-clicks left the labels layer **permanently pinned at native z14 while the aerial reached z15 and stayed there**, unchanged 3+ seconds later — the same shape the owner reported, just a smaller absolute gap than his because this sandbox's request path to `arcgisonline.com` is faster/less contended than a real residential connection loaded with a dozen other GIS overlay layers.
- **⚠ WHAT WAS RULED OUT, per the report's own instruction not to let confidence on the symptom leak into an unproven cause.** Not a `maxNativeZoom` ceiling (`19`, matches the aerial's own native ceiling for the default Esri source; capping there would clip at 19, not 9). Not a server-side placeholder (`server.arcgisonline.com/.../Reference/World_Transportation` genuinely serves distinct, real 256×256 PNG content through z19+ for the reported location — fetched and decoded directly, confirmed via the service's own `?f=json` tileInfo, 24 published LODs to z23). Not the `PLACE_NAMES_MIN_ZOOM` opacity gate (only sets CSS opacity, never touches tile fetching — confirmed by reading `layerZoomGate.js` and the effect that calls `layer.setOpacity`). Not a cross-module import mixup: `FoodMap.jsx`'s `LABELS_TILES` is its own, unrelated module-scoped **object** (`{url, maxZoom, maxNativeZoom, opacity}`) — a naming coincidence, not a shared symbol; `MapFinder.jsx`'s is a plain URL **string**. Not `capTileCache`/`boundTileCache` eviction (identical mechanism runs on both layers; the aerial is unaffected).
- **THE FIX.** `MapFinder.jsx`'s labels-overlay effect now derives `maxNativeZoom` the exact same way the aerial effect two blocks above it already does — `L.Browser.retina ? bm.maxNative - 1 : bm.maxNative` off the ACTIVE basemap (`BASEMAPS[basemap] || BASEMAPS.esri`) — adds `detectRetina: true`, wraps the layer in the existing `withTileRetry` helper (closing the third difference the report's own code-smell reading flagged), and the effect now depends on `[labels, basemap]` instead of `[labels]` so switching to the USGS basemap (`maxNative: 16`, a latent divergence the hardcoded `19` never accounted for) rebuilds the labels layer with the matching ceiling too. Both layers now request the identical native tile zoom, at every step of a zoom gesture, on every basemap choice.
- **ADJACENT CASES — all three checked, as asked, not assumed.** `SitePlanner.jsx` (the in-plan canvas, `:2870`/`:2932`) does **NOT** draw a road-name/Reference labels layer at all — it draws two AERIAL tile layers only (a coarse+detail pair for progressive loading); the report's premise that it might share this defect was wrong, corrected here rather than silently fixed around. `FoodMap.jsx`'s labels layer is its own object, and its **imagery** layer also has no `detectRetina` (B811520, a prior deliberate decision, unrelated to this bug) — so FoodMap's two layers stay in lockstep with each other and do **not** exhibit this divergence; left untouched, and no cross-workspace shared module was introduced to "fix" it, per that workspace's own `CLAUDE.md` **BUNDLE ISOLATION** rule (nothing under `src/workspaces/food/` may import from `src/workspaces/site-planner/`, or vice versa) — the fix is duplicated logic at two independent call sites by design, not an oversight.
