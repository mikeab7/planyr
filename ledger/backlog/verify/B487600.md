- **THE MECHANISM.** `⧉ Duplicate plan` does `saveSite({ ...src, id })`, copying each overlay record WHOLESALE — `storageKey` (cloud object) and `idbKey` (device raster) included. Two plans then point at ONE set of bytes. Every delete path ref-counted that share against `sheetOverlays`, **the current plan's overlay list**, which by construction cannot see the sibling. So removing the picture from the duplicate hard-deleted the original's image out of **both tiers at once**.
- **EVERY OPERATION THAT PRODUCES A SHARED REFERENCE, enumerated — the fix covers all of them, not just duplicate:** `duplicatePlan` (sheetOverlays, both tiers) · `newPlanSameParcel` (`underlay: src.underlay` — the aerial backdrop, whose delete path had **no ref-count at all**) · `copyOverlay`/`placeOverlayCopy` (B461, within and ACROSS plans). **RENAME does not** — `renameSiteGroup` patches `{ id, site, siteRenamedAt }` on the same plan and creates nothing; it was checked because the owner thought he may have renamed rather than duplicated. Sharing can only arise from the three copy paths.
- **⛔ THE BIGGER BLAST RADIUS, same bug one tier down.** `deleteSite` evicted `raster:<siteId>:*` by PREFIX, and a duplicate carries the SOURCE plan's `idbKey` — so deleting the SOURCE plan wiped the device copy for every plan copied from it. The sweep is kept (it is what evicts genuine orphans) but now SPARES every key a surviving plan names (`idbDeleteByPrefix(prefix, { keep })`).
- **THE FIX, three rules** (`lib/sharedAssetRefs.js`): the ref-count spans EVERY plan, never the current one · an UNKNOWN answer releases nothing (an orphaned object costs storage, a destroyed one costs the owner's work) · both tiers are released together or neither.
- **⛔ AND THE DATABASE IS THE AUTHORITY, because the client's list is only ever best-effort.** It knows what THIS DEVICE has hydrated; a stale tab, a second device or a direct Storage API call all reason from an incomplete list and would orphan the bytes exactly as before. `db/overlay_object_release_guard.sql` is a `BEFORE DELETE` row trigger on `storage.objects` that REFUSES while any plan still references the key (soft-deleted plans COUNT — a binned plan is restorable). **Applied to production 2026-08-13 and proven on the real path:** Supabase's own `protect_delete` blocks direct SQL, so the probe set `storage.allow_delete_query` exactly as the Storage API does — the guard refused and named all four Goose Creek plans; the CONTROL (an unreferenced object) passed through. Neither probe committed anything.
