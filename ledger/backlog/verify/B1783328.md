(3) **`rowToOverlay` (`sitePlanOverlays.js`) validated a crop by checking `r.crop.w`/`r.crop.h` directly** — a poly crop has no top-level `w`/`h`, so every polygon crop would have silently vanished on read, the exact bug class B1134754's own crop feature exists to avoid. - **Discriminated union, additive to the existing rect shape (`overlayCrop.js`): `{kind:'rect', x,y,w,h}` | `{kind:'poly', pts:[[x,y],…]}`.** A crop object with NO `kind` key (every row written before this shipped, incl. - **New pure functions in `overlayCrop.js`** (reused verbatim, same module as the rect crop): `cropKind`, `polygonAreaPx` (unsigned shoelace, a degenerate-shape guard only), `clampPolyPoints`, `isUsablePoly` (>= 3 vertices + the SAME `MIN_CROP_PX`-derived bounding-box/area floor the rect crop uses — an overlay can never be clipped to nothing and lost), `normalizePolyCrop`, `rectToPolyPoints`/`polyPointsToRect` (the reversible one-step shape conversion), `isValidCropShape` (the one DB-row validator for either shape), `normalizeCropShape` (dispatches by kind), and **`clipPathValueForCrop`** — the ONE function that turns either shape into a CSS `clip-path` value in image-local pixels (a rect → `inset(...)`, byte-identical to B1134754's original; a polygon → `polygon(evenodd, ...)`). `rotatedImageLayer.js`'s `applyCrop` now delegates to it entirely — one clip mechanism, not two.
- **SELF-INTERSECTING POLYGON — decided, not silently picked: `evenodd`, not refuse-to-close.** Refusing to close would strand a user mid-draw over one careless click near an existing vertex, with only Backspace/Escape to recover — worse than rendering a well-defined (if unexpected) region. `evenodd` is what CSS computes natively with zero extra self-intersection-detection code, and it is the SAME rule the crop tool's own live preview mask uses, so what you draw during editing is exactly what renders once committed.
- **`ImageCropTool.jsx`** (shared by both call sites — the upload flow's page-picker step and an already-placed overlay's "Crop…" button — same as the rect tool) gained a Rectangle/Polygon mode toggle. Poly mode: click to place a vertex; clicking within a small screen-px tolerance of the first vertex, or pressing Enter, closes the shape (>= 3 vertices required); a double-click closes too — detected via the native click event's own `detail === 2` on the SAME click handler (never a separate `onDoubleClick`), which is what stops a double-click from planting a duplicate vertex on top of the one its own first click already placed. Escape mid-draw cancels the in-progress polygon only (not the whole tool); Backspace drops the last placed vertex. Once closed, every vertex is its own draggable handle and the shape is re-editable on a later visit — re-opening the tool against a saved rect crop pre-seeds an editable 4-vertex quad (`rectToPolyPoints`) if you switch to Polygon, and switching back to Rectangle never overwrites your rect draft with a re-derived bounding box — **each mode keeps its own independent draft for the life of one tool session**, which is what "switching must not destroy the other shape's last value" means in practice (a literal round-trip conversion on every toggle would be lossy the moment a poly is edited past its rect-derived seed). The scrim (dim everything outside the crop, never hidden outright) is an SVG `evenodd` mask matching the same fill rule the persisted clip uses.
