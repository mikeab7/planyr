Net-new.)*

`[x]` **AUDIT-FIRST — the root cause is a missing `setSelectMode(false)`, not anything about the "Record info" collapse itself.** `MapFinder.jsx`'s toolbar renders a "Selecting… Drop a pin Cancel" row whenever `selectMode && selected.length === 0`, and its normal AT-REST row only when NEITHER `selectMode` nor a live decide-target is true. "Add a note" (and, read while diagnosing this, "Log a comp" too — see below) finish by calling `clearSel()` alone, which empties `selected` but leaves `selectMode` still `true` — so the toolbar falls through to "Selecting…" instead of AT-REST. **"Plan this site" never showed this defect only because it doesn't need this fix at all**: planning a site flips the app from map mode to plan mode, and the existing return-to-map effect (`MapFinder.jsx`, keyed on `visible`) already resets `selectMode` on the way out — a verb that stays on the map (comp, note) has no such effect to ride and must exit select mode itself.
`[x]` **FIXED — a new `finishGroundAction()` helper (`clearSel()` + `setSelectMode(false)`), used wherever a decide-bar verb finishes without leaving the map.** Wired into the "note" verb's parcel-target branch (the reported case) and into `placeCompOnSelectedParcel` ("Log a comp" from a parcel selection — the same code shape, the same latent defect, found by reading the source rather than left for a second report). Deliberately NOT folded into `clearSel()` itself: the decide bar's own ✕ "Clear selection" button still calls bare `clearSel()`, and staying in select mode there is correct (the user is clearing their pick to choose different parcels, not finishing). The pin-anchored path (drop a pin → any verb) was never affected — `markDecidePin` already turns off select mode the moment a pin drops — and is unchanged.
`[x]` **"Place a site plan" was read, not assumed, and left alone.** Its `run()` ignores `target` entirely and calls neither `clearSel()` nor `clearDecidePin()` on either anchor kind — a materially different, pre-existing shape this item's own report never named and this fix does not touch, to avoid an unreviewed behavior change on a flow (site-plan upload) whose interaction with a still-visible selection wasn't traced.
`[x]` **New unit test, `test/decideBarDismiss.test.js`, mutation-proven** (reverting the fix in a scratch copy reproduces the failure, confirmed then reverted back) — asserts `finishGroundAction` clears both selection and select mode, that the "note" verb's parcel branch and `placeCompOnSelectedParcel` both call it, and that the ✕ "Clear selection" button still calls bare `clearSel()` (so a future edit can't silently fold the two together).
