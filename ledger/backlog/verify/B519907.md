### B519907 — An undo rebuilt the entire basemap, because `origin` came back as a new object `[Site Planner / Map]` (bug) #site-planner #perf #gis #view  *(the FIX for B1121 ×4, found and shipped 2026-08-14. Minted **B519907 / V295136**. DEDUPE-FIRST — searched Open / ⏳ Verify / Done across `B1121`, `B1189`, `B1439`, `B1440`, `origin`, `pushHistory`, `applySnapshot`, `map.remove`, `preserveTilesAcrossSetView`, `boundTileCache`: **B1189** is the same CLASS on a different effect (it fixed the registration layout effect by listing `origin.lat/lon` in its deps) and **B385040** is the same class again on `overlays` identity through `applySnapshot` — neither owns the map-creation effect, and neither stabilises the VALUE. **B1121** is the SYMPTOM this is the mechanism for and stays open on its residual. Net-new.)*
`[ ]` **`pushHistory` snapshots the WHOLE app state, so an undo restored `origin` as a fresh object holding identical numbers — and the Leaflet map-CREATION effect keys on it with `map.remove()` as its cleanup. React runs a cleanup before re-running, so every Ctrl+Z destroyed and rebuilt the whole basemap.**
- **Measured per action on the owner's Richfield plan:** click 0/0 · drag 0/0 · **undo 272 tile `<img>` added + 272 removed** · pan 14/0 · Escape 0/0, with the retained count never leaving 274. Each undo paid 272 element destructions, 272 image decodes and 544 Leaflet subscriptions **for a basemap that had not moved**. ⛔ The tile COUNT is identical either side of the defect — which is exactly why every existing instrument here was blind to it, and why the guard counts CHURN.
- **The fix:** the state is held as `originRaw` and `origin` is derived through a `useMemo` keyed on the two SCALARS, so an equal-valued restore is the SAME object and none of the ten effects keyed on it re-runs.
  - **⚠ NOT a per-effect fix, and B1189 is why.** That item hit this exact class and fixed ONE effect by listing `origin.lat/lon` in its deps — leaving nine others and every future one to remember. Stabilising the VALUE closes all of them at once.
  - **⚠ NOT a tolerant compare.** `sameOrigin`'s 1e-12 is right for *"is this the same site?"* and wrong here: it would pin a genuinely MOVED origin to its old object and strand the basemap at the previous location.
- **PROOF — controlled A/B, same build config, same plan, same 12-round × 6-edit sequence, fix stashed and restored:** listeners **1544 → 1616, +6 EVERY round, 12/12, no plateau** → **1544 → 1656 (one step) then 1656 flat for 11 rounds**; retained heap **+1.66 MB/round → +0.65 MB/round**; renderer RSS delta **457.2 → 241.2 MB**; undo churn **272/272 → 0/0**, redo likewise, map alive with all 274 tiles.
- **⚠ WHAT IS NOT FIXED, stated rather than rounded off.** The listener leak is GONE. The retained-heap slope is CUT BY ~60%, NOT ELIMINATED, and the after-curve is still decaying at round 12 rather than provably flat. The after run also STARTS higher (45.6 vs 25.9 MB) — with the map no longer torn down, more is legitimately retained at load; **the SLOPE is what was fixed, and the slope is what makes a long session degrade.** That residual keeps **B1121** open.
- **Guards, both mutation-proven:** the repo-root `test/` suite **originIdentityStable** (source guards incl. the no-tolerance rule) and the ui-audit harness **verify-undo-tile-churn** (`npm run perf:undochurn` — **exit 0 on the fixed build, exit 1 with the fix stashed**). It carries two CONTROLS — the map must be alive and still holding tiles — because a build that simply never rebuilt the map would otherwise score a perfect zero while being badly broken.
- **⚠ Also fixed: a real defect in the NEW harnesses, caught by this repo's own guard.** They stranded an `ElementHandle` from `waitForSelector` — **B1439**, a strong GC root that inflates every later memory reading. In an instrument whose whole purpose is measuring retention that is contamination, not style. Now `waitForSelectorReleased`.
