**SO THE GUARD WAS NEVER WRONG. THE GAP IS THAT THE CLIENT HAD NO DEFENSE AGAINST EVER SENDING THAT SECOND WRITE.** `storage.saveSite`'s own "write choke point" comment already declares the intended invariant — "a plan may never be written carrying a name that contradicts its own project" — but its enforcement (`resolveNameFor`, fed only the record's SIBLINGS in the same group) is a no-op for a solo-plan project: with no sibling to out-vote it, whatever `site`/`siteRenamedAt` an incoming write claims was accepted outright. A planner canvas left open across a rename made from the project switcher is the ordinary way this fires — the switcher's rename writes straight to `localStorage` via `saveSite`, which the open canvas's own React state never observes, so its next autosave (an "ordinary document save," never the RPC) still holds the pre-rename name and no stamp. That write lands locally with nothing to stop it, then reaches the cloud through the same path every content edit uses (`cloudUpsertCore`) — where the trigger correctly reverts the DATABASE but has no way to tell the client its write was altered, so the LOCAL cache is now the one that's wrong, and that is what the user sees on the next read.

**THE FIX, at the one seam that already existed for this.** `saveSite`'s authority check now also weighs the record's own value *before* this save (`existing`), not just its siblings — but not by simply folding it into the existing vote (a first attempt at exactly that was caught RED by this item's own test suite: when a write doesn't touch `siteRenamedAt` at all, the merge *inherits* the existing stamp untouched, so the two sides tie on stamp, and `nameAuthority`'s own tie-break favors whichever side has the fresher `updatedAt` — always the write in progress, handing the win right back to the stale name). So a write that does not itself carry a stamp STRICTLY NEWER than what the group already has on record is decided directly against the prior stamped candidate, never through a tie-break; a genuinely newer rename still wins outright, unconditionally, so this fixes nothing for a real rename. Only when nothing in the group has a real stamp yet (pure legacy) does the ordinary vote-based logic govern, with `existing` folded in as one more voice — proven algebraically in the code comment, not just tested, that this can never skew a legacy majority repair (`repairSplitProjectNames`), because `existing` only ever re-asserts the vote that plan already contributed to the tally that produced the correction being applied.
