- **THE REPORT.** At high magnification on the live map the setback chip reads **white plate · green border · green numerals**. It must be a **black border and black numerals**, which is what B1184–B1187 / PR #874 shipped and what the owner asked for in the first place: *"the setback is orange, and then the chip showing that setback, the outline of the chip is orange, and then the text is orange. I'd like that to all be … black."* Evidence that it is the chip and not the theme: the parcel acreage badge is still correctly dark on the same canvas.
- **AUDIT-FIRST — the code says exactly what the report says.** The one chip render site resolved `const sbCol = selParcel.sbStroke || PAL.chipInk`. That reads black only while nothing has set a setback colour. The owner's plan carries an explicit `sbStroke` (he picked the green in the colour picker before it became the default), so his chip has been inheriting the line's colour the whole time — and any user picking any custom colour would have got the same. B1187's ink token was never wrong; it was simply unreachable on that parcel.
- **THE FIX IS THE COUPLING, NOT THE VALUE — and it is structural.** `planStyle.setbackChipStyle(ink)` takes **no parcel**, so there is no per-parcel value in scope at the render site to couple to. Border and numerals are the `--canvas-chip-ink` token, the plate is white, full stop. Swapping the theme's ink still works; swapping the line's colour cannot reach it. Setting the chip's ink back to a fallback chain now requires deleting a test rather than forgetting a convention.
- **What is deliberately NOT changed.** The setback LINE keeps its own colour exactly as B1100 shipped it — per-parcel `sbStroke`, Standards defaults, Reset setback line. Only the CHIP is pinned. `setbackLineStyle` is untouched, and the harness asserts a recoloured line still draws in its own colour in the same pass that asserts its chip does not.
- **Pinned so it cannot rot.** `test/setbackChipInk.test.js` (9 tests) asserts the PROPERTY, never the value of the day: every case feeds an arbitrary, deliberately non-black line colour (`#34E802`, `#EF9F27`, `#4F46E5`, magenta, an `hsl()`, a named colour) and asserts the chip is unmoved — a test that only checked "black when the line is green" would pass today and rot on the next default change. It also source-guards the render site: no `sbStroke` / `sbs.stroke` / `PAL.setback` inside the chip block, and no `||` / `??` on the ink line. Both halves were **mutation-checked** — restoring the old `sbStroke || PAL.chipInk` turns them red.
- **Verified here (ATTEMPT-BEFORE-YOU-PARK).** `ui-audit/verify-setback-chip-ink.mjs` seeds two parcels — one untouched, one whose setback line is an arbitrary magenta — and reads the **computed** colours off the live canvas in Chromium: **12/12**. Both chips are `rgb(21, 23, 28)` border and numerals on a white plate, identical to each other, while the two setback rings are genuinely different colours (`rgb(52, 232, 2)` and `rgb(255, 0, 255)`) on the same screen.
