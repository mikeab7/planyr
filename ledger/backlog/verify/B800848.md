- **WHERE THE TIME ACTUALLY GOES, measured, answering the questions asked directly:**
  - **Is the terrain worker actually used, or is the work on the main thread?** The worker IS used correctly — LERC decode, masked smoothing and marching-squares tracing all run in `terrainWorker.js`, off the main thread, exactly as documented. That part was never the problem.
  - **Do contours regenerate on every pan/zoom frame, or are they cached and reused?** The FETCH is correctly cached (`gisCache.swr`, keyed by the fixed ground lattice, 7-day TTL) and the geometry TRACE only reruns for a tile whose bytes were freshly fetched — that part is sound. But the PAINT — turning traced contour data into on-screen Leaflet objects — was NOT incremental: every `moveend` whose visible lattice-tile SET changed at all called `group.clearLayers()` and rebuilt EVERY polyline and label currently in view from scratch (`renderContours`/`terrainLayer`'s `paint()`), including tiles that were already painted and hadn't changed. At working (1-ft) zoom a typical view holds 4–6 tiles and thousands of vertices plus dozens of DOM-backed label markers, so nearly every ordinary pan step tore down and recreated all of it — not just the fringe that actually moved.
  - **How much geometry/how many SVG paths exist at working zoom, and is there any decimation?** Profiled against the real fixture over a realistic 8-tile cover: **2642 composed lines, 60 labels** (labels are already capped at 60 for DOM sanity — `LABEL_CAP`). No decimation of the LINE geometry exists or was added — see the constraint below.
- **THE FIX — cache, don't redraw what hasn't changed (no resolution/interval change, per the owner's explicit constraint).** `contours.js` gained `contourLineKey`/`contourLabelKey` (a stable identity per composed chain/label — level + vertex count + three sampled ground points, all already rounded to 1e-6° by the worker, so two composes of the SAME ground always produce the SAME key) and `diffKeyedPaint` (a pure reconciliation: given the newly-composed keyed items and what's already painted, return only what to ADD and what to REMOVE). `terrainLayers.js`'s `paint()` now diffs against a per-layer-instance `key → Leaflet layer` Map instead of `clearLayers()` + full rebuild: unchanged chains and labels are left as the SAME Leaflet object, never re-projected or torn down; only genuinely new/vanished geometry is touched. This applies to BOTH the contour lines layer and the drainage-arrows layer (`renderArrows`), which share the same `paint()` — arrows are keyed on ground position + direction, stable across a pan at constant zoom (any zoom change replaces the whole tile set anyway, so nothing stale can be reused across a zoom).
- **⛔ CONSTRAINT HONORED, stated loudly per the brief: the 1-ft interval, resolution and every rendered pixel are BYTE-IDENTICAL to before.** `composeContourPaint` (the pure geometry composition — the seam-join, the label thinning, the ONE unit formatter) is completely UNTOUCHED; the fix only changes HOW its output becomes Leaflet objects (reuse vs. rebuild), never WHAT it computes. `test/terrainLattice.test.js`'s existing fixture-driven assertions over the real captured tile (byte-identical composition regardless of tile order, one label per contour, seam-joined halves) all still pass unmodified. This is NOT a resolution or interval change and is not being shipped quietly as one.
- **VERIFIED — real captured DEM data, in Node, not eyeballed:** new tests in `test/terrainLattice.test.js` prove the mechanism directly against `test/fixtures/dep-katy-463x400.lerc`: repainting the IDENTICAL view is a total no-op for the diff (zero adds, zero removes); dropping one tile out of the cover (as if it panned out of view) only retires the keys that actually touched it, while the untouched tile's own interior contours KEEP their identity (proven `> 0` survivors) — the property the whole fix depends on.
- **BROWSER-LEVEL BEFORE/AFTER — measured honestly, including where it fell short of hoped-for.** Built the pre-fix tree to a separate `dist-before` (`git stash && vite build --outDir dist-before && git stash pop`) and compared it against the fixed `dist` with the same harness: a real, continuous, never-revisited 14-step pan at zoom 18, step size calibrated from the lattice's own tile span (`TILE_CELLS × bandCellMeters(zoom) × groundScale(lat)`, converted to feet — not guessed in screen pixels) to genuinely overlap 78% with the previous view each step, CDP `Performance.getMetrics` deltas (script+layout+recalc-style ms) per pan step, median of 14 steps. **Result: before 106.3 ms/step → after 102.6 ms/step, −3.5%** — real and in the right direction, but smaller than hoped. Profiling why (see **B800849**, filed the same session): the composed-geometry recombination itself (`composeContourPaint`'s per-level seam-join + label-thinning), which this fix does NOT touch, costs ~24 ms per repaint on its own and dominates the total — this fix removes the SECONDARY cost (re-creating Leaflet/DOM objects for geometry that didn't change), which is real and verified in isolation, but the LARGER cost is a separate, riskier fix filed as its own item rather than rushed here. Also separately observed (and filed, honestly flagged as unconfirmed) a possible redundant tile re-fetch pattern — **B800850**.
