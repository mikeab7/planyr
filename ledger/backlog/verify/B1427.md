- **THE MECHANISM, measured rather than reasoned.** `navigator.storage.estimate()` + a key census on the owner's Personal (CyberPower) Chrome on planyr.io: **IndexedDB 35.9 MB against a 10,275.9 MB quota (0.3%, persisted: true)** · **localStorage 3.88 MB across 156 keys against the hard ~5 MB per-origin cap (~78%)**. Largest localStorage keys: `planarfit:sites:cloud:<uid>` 523 KB · `planarfit:sites:history:v1` 416 KB · then **three `planyr:giscache:v1:terrain:dem:L16` tiles at 400 / 283 / 280 KB**. The site save writes to localStorage (`storage.js` — `SITES_KEY`, `cloudKey(uid)`, `AUTOSAVE_KEY`); `gisCache.js` lived there too with `maxTotalBytes = 3 MB`, and its own comment already said the budget existed "to keep our namespace from starving site data". 3 MB of cache out of a ~5 MB ceiling leaves under 2 MB for every saved plan plus the cloud index plus the history mirror plus the autosave — so on a Bain-sized plan `setItem` throws `QuotaExceededError`, the device save fails, and the B473 banner fires **while disposable, re-fetchable terrain tiles keep their space**. A priority inversion, with the two stores the wrong way round: the disposable data in the 5 MB box at 78%, the 10 GB box at 0.3%.
- **CAVEAT, stated because it matters:** the census is from the PERSONAL machine. The banner appeared on whichever machine the owner was on, possibly the Work Office PC. The design flaw is machine-independent and this machine is at 78% of the same ceiling.
- **THE FIX IS STRUCTURAL, NOT TUNING — gisCache's persistent tier moved to IndexedDB.** `localDb.js`'s store is already the app's durable KV home, already persisted, and had ten gigabytes unused. The cache keeps its own budget and eviction there, and **the budget did NOT change: 512 KB per entry and 3 MB total are exactly B1162's numbers.** Bounding this cache was always right — it was bounded against the wrong ceiling. Nothing got bigger; it stopped competing.
- **Migration: the legacy namespace is PURGED, not migrated** (the entries are one fetch away, so copying them would only delay the space we are trying to free). The purge runs **at module scope**, not on first cache use — on a device already at the cap the very next SAVE must find the room, and nothing guarantees a GIS layer gets touched first.
- **WHAT IT COSTS, said plainly: IndexedDB is asynchronous.** A cold lookup (nothing in the in-memory L1 yet — i.e. just after a reload) can no longer answer synchronously, so `swr()` returns `cached: null` on a cold L1 miss and delivers the stored copy through the `fresh` promise instead: a few milliseconds later, and still **with no network request**. Every consumer already handled that path — it is the same path an empty cache takes, and `fetchCached`, `terrainLayers` and `vectorOverlay` all await `fresh`. Hydration additionally warms the newest few entries back into L1 (bounded by count AND bytes) so a reload still paints from cache almost at once. The **one** caller that read the store synchronously was the PDF/PNG export, whose terrain branch is sync by contract; `exportSheet.js` now warms the frame's tiles first (**PDF-PARITY** — a wide view whose tiles had cycled out of the 48-entry L1 would otherwise have exported without contours).
- **WITH NO IndexedDB** (private mode, old browser, the node test env) there is now **no persistent tier at all** — L1 still serves the session and a miss is a live fetch. Deliberate, and it is the new rule again: with one store left, that store belongs to the user's work.
- **The L1 in-memory tier is exactly as B1162 left it** (48 entries, LRU by read-touch).
- **⛔ THE SITE PAYLOAD WAS DELIBERATELY NOT MOVED**, per the owner. That is the tempting follow-on and it is a much larger migration touching the exact path B473 exists because of — a device save that fails loses work. It is **B474**'s existing open sub-item, now carrying the risk statement; it did not get a new number (DEDUPE-FIRST).
- **MEASURED RESULT (headless, real browser, `e2e/storage-tiers.spec.js`):** seeded with the owner's own three tiles at their measured sizes, localStorage cache bytes go **986,247 → 0** on load, total localStorage drops to 194 bytes, and the saved plan + the version ring are untouched.
