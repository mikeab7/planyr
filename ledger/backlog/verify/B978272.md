`[x]` **FIXED for item 1: a comp's lat/lon is now atomically recomputed, server-side, every time its overlay's placement changes — including for a TEAMMATE's comp, which the mover's own RLS would otherwise never let them touch.** `site_plan_point` (the {x,y} pixel the user actually clicked) is the source of truth; `lat`/`lon` is a derived cache. Two SECURITY DEFINER RPCs (`site_plan_overlay_comp_points` read, `commit_site_plan_overlay_placement` write) let the overlay's owner read a teammate's `site_plan_point` and write their recomputed position in the SAME transaction as the overlay's own placement update — `comps` UPDATE/SELECT is owner-only RLS, so without this a moved team-shared plan would only ever fix up the mover's own pins. The recompute math (`imagePointToLatLon`, the true inverse of the existing `latLonToImagePoint`) stays in already-tested JS rather than being duplicated in PL/pgSQL.
- **Item 2 — decided and written down, not just implied:** `comps.js`'s `validAnchor` and `comps_site_plan_anchor.sql`'s header now both state explicitly: `site_plan_point` is authoritative; `lat`/`lon` is a derived cache with exactly one legitimate writer (the placement-commit RPC above).
- **Item 3 — MEASURED, not the owner's own guessed mechanism.** The placement math never touches Web Mercator (verified by reading `overlayGeoref.js` directly) — it's pure State Plane feet throughout.
