`[x]` **The mechanism.** `exportSheet.js`'s `buildExportSvgRaw` sets the cloned plan `<svg>`'s `viewBox`/`width`/`height` to the dragged print frame's exact box and relies on that alone to keep every layer — the site plan's own cloned elements/parcels/dimensions, every GIS raster/vector overlay, sheet furniture — inside it. The AERIAL never depended on that clip: it's a fresh raster fetched/stitched pixel-exact to the frame's bbox (`exportAerialForFrame`), so it always reads as cropped correctly regardless of whether the SVG-level clip is actually engaging, while every other layer's correctness rests entirely on it.
`[x]` **The fix — an explicit `<clipPath>`, not an assumption.** `buildExportSvgRaw` now builds a `<defs><clipPath><rect x y w h/></clipPath></defs>` sized to the exact frame box and a `<g clip-path="url(#...)">` (`root`) that every cloned node and every appended layer (aerial, GIS raster/vector under/front/over bands, site-plan overlay images, sheet furniture) is reparented/appended into — every `clone.insertBefore`/`clone.appendChild`/`clone.querySelectorAll` call in the function now targets `root` instead of `clone` directly. `clone` itself is unchanged externally (still the returned `{clone, w, h}`, still gets viewBox/width/height), so `buildComposedSheet`/`exportPNG`/`inlineImages`/`restyleExportClone` need no changes. Handles a non-rectangular frame's edge case by construction: the frame is always a plain rectangle in this app (no freeform-frame tool exists), so a rect clip covers every layer named in the report (parcel/property lines, pond outlines, easement dashes, dimension/TAS/HW-SPEC labels, buildings, trailer-parking hatching, north arrow/scale bar).
`[x]` **Why this wasn't found by trusting the default alone.** Nested-SVG viewBox clipping (`overflow:hidden` by default on a non-root `svg`) measurably DOES work in a minimal reproduction and in a reproduction built from the real `printSheetLayout`/`buildPrintSheetSvg` composition shape (both proven with a headless Chromium canvas-rasterization test during this session — content placed far outside a nested viewBox never bled onto a surrounding page canvas). The explicit clip-path is therefore a defensive hardening — matching this codebase's own established idiom (`overlayCrop.js` already uses an explicit CSS `clip-path` for a placed overlay's crop, rather than relying on implicit clipping) — that makes the guarantee structural instead of implicit, so it cannot regress silently if some future change (a stray `overflow:visible`, a different nesting/rasterization path) ever defeats the implicit default. It directly satisfies the report's own ask: "whatever clip/mask is applied to the base aerial raster … needs to apply identically to every overlay layer."
`[x]` **New live-verify harness.** `e2e/print-frame-crop-clip.spec.js` drives the real app (logged out, no GIS): draws a building spanning most of the canvas, calls the real `window.__plannerExportSvg(frame)` E2E hook (same one `measure-export-lod.spec.js` uses) with a frame a quarter the size of the drawn building, and asserts (a) a `<clipPath>` + clipped `<g>` exist and the clip rect equals the sheet's own viewBox, (b) the drawn building node is a structural descendant of the clip group, and (c) rendering the returned markup nested inside a page-sized canvas exactly the way `buildComposedSheet` nests the plan (offset inside a larger page, matching the owner's actual PDF composition) paints zero non-white pixels in the surrounding margin.
