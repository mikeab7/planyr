- **(a) `gisFetch.js` `_recent` — the request-coalescing map.** Entries were only ever overwritten by the same key or wiped by `clearCoalesced()`, which is called by the tests and by **nothing in app code**. The key embeds the bbox, so a panning session minted unique keys indefinitely, each pinning a whole parsed ArcGIS response whose usefulness expired after five seconds. Now swept on write (the entries were already timestamped) plus a hard entry cap as a backstop. Behaviourally invisible: an entry past its TTL was already never returned, and the coalescing window itself is unchanged and unit-tested both sides of the boundary.
- **(b) `gisCache.js` L1 — the in-memory tier.** The localStorage tier is bounded twice over (512 KB per entry, 3 MB total, `evictOldest` enforcing both). L1 had no bound at all — and the two interact badly: a payload over `maxEntryBytes` **returns early without ever entering the store**, so it never appears in `ourKeys()`, so `evictOldest` can never reach it. The >512 KB GeoJSON responses — the biggest objects in the app — were precisely the ones that lived forever. L1 now has an entry cap with the same recency-touch idiom `pondGeom`'s `_detMemo` uses (a read re-inserts, so insertion order IS the LRU order). A miss is only ever a re-fetch through the existing stale-while-revalidate path, or a rehydrate from the durable tier — it can never change an answer.
- **(c) `parcelSnapshot.js` `loaded` — MEASURED, NOT CAPPED, and that is the finding.** It holds county → the full GeoJSON feature array and is cleared only by the test helper. It could plausibly be tens of megabytes per county, but **the size could not be established from source**, and capping a fallback the map depends on, blind, trades a memory number for a blank map over a county whose live server is down. So `snapshotFootprint()` reports what is actually retained, per county and in total, on demand and never on a render path; it is reachable from a real session's console as `__planyrSnapshotFootprint()`, because a signed-in browser with real county data is the only place the number exists. It is deliberately read-only — a guard asserts it evicts nothing. **If the number justifies a cap, the eviction is nearly free:** the durable copy is already in IndexedDB, so an evicted county rehydrates locally. That work is not done here.
