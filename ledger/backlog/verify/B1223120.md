`[x]` **FIXED THIS SESSION.** On a real phone (narrow width **AND** a coarse/touch pointer — width alone is deliberately not enough, so a narrowed desktop browser window with a mouse is untouched), selecting something and tapping the existing "✎ Properties" pill now raises the Properties panel as a Google-Maps-style bottom sheet instead of the old left-side slide-in drawer: it opens at roughly half the screen height (never full-screen — the map stays visible), a drag handle lets you pull it to a taller detent or drag it down to dismiss, every control inside it is at least 44×44 CSS px, the map pans so the selected object stays visible above the sheet's edge, and the sheet rises above the on-screen keyboard when a field is focused (with the focused field scrolled into view). **Scope boundary, deliberate:** if another rail panel (Yield, Land, …) is ALSO open at the same time as the Properties companion — a rarer combo — the sheet is not built for that case and it keeps the existing left-drawer behavior; the common "select something, open its Properties" path is what became a bottom sheet. The Spreadsheet and Gantt were not touched. Desktop is untouched — same docked left panel, same pixels, confirmed live (below).

- **The token fix, not a hack.** `CONTROL_H` (`src/shared/ui/designTokens.js`) gains a fourth step, `touch: 44` (CSS mirror `--control-h-touch` in `index.css`) — sm/md/lg are unchanged and still govern every existing desktop/mouse control. Inside the sheet, every `button`/`input`/`select`/`textarea` is bumped to that floor via one scoped CSS rule keyed to the token (`[data-bottom-sheet="properties"] button, … { min-height: var(--control-h-touch) }`, plus `min-width` for buttons) rather than hand-editing the hundreds of individual inline styles across every element type's Properties fields — a full per-field retrofit of that surface was judged too large a diff for the value versus one scoped rule reading the same token; the rounded top corners use the existing `RADIUS.lg` (12px, "a surface that contains other things," per docs/DESIGN.md's shape rule).
- **The two hard failure modes the brief named, both closed:**
  1. *Selection buried under the sheet* — every drawn feature already stamps `data-feature="<kind>:<id>"` (the COUNT-EVERY-KIND convention), so the selection's real on-screen box is read off the DOM and the canvas is panned (`view.offY`) just enough to clear the sheet's top edge, restored when the sheet closes or the selection changes. Verified live (below): a selected building's bottom edge sits ~16px clear of the sheet's top edge the instant it opens.
  2. *Keyboard buries the field* — the sheet tracks `visualViewport` (resize/scroll) and rises above the larger of the keyboard inset or the safe-area inset (the JS-number approach from `shared/ui/safeAreaInsets.js`, reused rather than reinvented per the brief — see that file's own header, written for B1176480's help/report button), clamping its own height so it can never run off the top of the screen once the keyboard opens; the focused field additionally scrolls into view. **This half is wiring-and-math verified only** — this sandbox has no real on-screen keyboard to drive (see V888832).
- **Approaches the brief ruled out were not attempted:** no global sizing migration, no repo-wide "flag every control under 44×44" gate, no root font-size/transform scaling, no width-only breakpoint. A new pure lib, `src/workspaces/site-planner/lib/propertiesSheet.js` (phone-sheet-mode test, snap-height math, drag-resolve, keyboard-inset math, keyboard-safe clamp, selection-cover-shift math — 22 unit tests, `test/propertiesSheet.test.js`), keeps the new mechanism scoped and testable without touching any other panel.
- **Verified this session, headless Chromium with real device emulation (iPhone 13: narrow width + a genuinely coarse/touch pointer) against a real built preview server, using a real production plan fixture (FM 359 RD, Fulshear) so the selection/geometry math ran against real building geometry, not a synthetic box:**
  - Sheet renders at `position:fixed`, height exactly 50% of the 664px-tall viewport on open, 12px rounded top corners, a visible drag handle.
  - **Every one of the 32 buttons inside the sheet measured ≥44×44px** (0 under the floor) — the sample included the ✕ close, the ▲/▼ collapse and stepper controls, and the "✎ Edit footprint…" row.
  - **The selected building's own bottom edge measured 15.7px clear of the sheet's top edge** the instant the sheet opened (confirms the map-shift acceptance criterion, not just that the code runs).
  - Dragging the handle up resolved to the "tall" detent (564px = 85% of viewport, matching the coded snap); dragging it down past the dismiss threshold closed the sheet.
  - **Desktop (1440×900, mouse) and a narrow-width-but-mouse browser window (700×900) both measured ZERO bottom-sheet elements** — the old docked panel (desktop) and the old left-drawer companion (narrow+mouse) render exactly as before, confirming the coarse-pointer scoping and desktop non-regression.
- **What is emulated vs. still unverified on a real device, stated plainly (per the brief's own honesty requirement):** the narrow-width + coarse-pointer condition, the drag gesture, the sizing, and the map-shift are driven by Chromium's device-emulation mode (a real touch-capable browser engine, a simulated device descriptor) — not Apple's WebKit and not a physical phone (this session tried to install Playwright's WebKit build for a closer iOS-engine check; both of its download mirrors failed in this sandbox, so that attempt is unfinished, not silently skipped). **Genuinely unverified on-device:** real iOS/Android keyboard raise/lower behavior (`visualViewport` events fired by an actual software keyboard), real finger-drag physics/momentum, and the real notch/home-indicator safe-area value (this sandbox reports 0 — no physical notch to inset around).
