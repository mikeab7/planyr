**WHAT WAS MEASURED (not inferred).**
1. **The brief's inference ("Outlook writes `mso-list` paragraphs and Planyr does not convert them") was WRONG for the code, right for the species.** `convertOfficeLists` already converts `mso-list` paragraphs: a Word-engine clipboard (decimal, 1./a./i. and 1./1.1./1.1.1. variants, red runs, empty `<o:p>` paragraphs) pasted into a box and onto blank paper came in as the right nested list.
2. **What reproduces his symptoms EXACTLY is a Word list that has been through a BROWSER** (Outlook on the web / the new Outlook / anything Chromium): Chromium rebuilds every `style` attribute from its own property table, which has no `mso-list`, so the list information is gone. Copying the committed Word fixture out of a Chromium page with a real Ctrl+C gives hanging-indent paragraphs that begin with the number as TEXT + eight non-breaking spaces. Separately, in the Word-engine path: `classifyMarker("1.1.")` returned **bullet** (only a single number matched), and the list conversion dropped each paragraph's `class`, so Word's document font (`p.MsoListParagraph { font-family: Calibri }` in the clipboard `<style>`) never reached list items ("font is none, wanted Calibri" on every list line).

**THE FIX** (`lib/notesOfficeLists.js`): `takeTextMarker` — a negative text-indent AND a numbered/lettered marker AND a wide gap ⇒ a list item; cuts the marker and the gap and not one more character; level from the legal number's depth, else the rank of the left margin among the run's distinct margins (`marginLeftIn` reads Chromium's `margin: a b c d` shorthand); marker-only paragraphs are dropped; `classifyMarker` reads `1.1.` as a number with a depth; the paragraph `class` is carried onto the rebuilt `<p>`. Spacing: list paragraphs lose their pasted margins as before, so the "much larger gaps" (Chromium inlines a computed margin on every `<p>`) no longer ride in.
