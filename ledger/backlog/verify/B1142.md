- **What was wrong.** The commit path's re-centre trigger watched the CANVAS (`size.w/h`). The map container is a different box — the canvas PLUS twice the overscan (`inset: -geoOverscan`) — and the overscan is derived from the DRAWABLE ELEMENT COUNT, which changes as culling reveals and hides elements while you zoom. So the container can resize with the canvas unchanged: its top-left moves relative to the clip while `invalidateSize({pan:false})` deliberately doesn't move the map pane, and nothing re-centred it. Separately, the re-sync was skipped entirely on the FIRST commit ("nothing on screen yet" — true of the flash, not of the size), so a container that resized between the map's creation and that first commit baked a stale cached size in permanently, with nothing left to compare against.
- **How big.** Measured in the sandbox on a 60-element plan: Leaflet's cached size read 1592×1194 against a real 1438×1366 container, and `diagnose-map-lock` reported the drawing sitting **121.6 px** off the imagery — on current `main`, and on the pre-merge base too, so this is **pre-existing, not a B1122 regression** (verified by building both in throwaway worktrees). The first-commit variant alone measured 86 px at rest, before any gesture. Two orders of magnitude past the one-pixel quantisation B1141 started on, and invisible to any harness whose test plan has no elements to cull — which is exactly why it survived this long.
- **Fix.** Measure the container's own `clientWidth/clientHeight` and fold it into `sizeChanged`, alongside a cached-size-vs-DOM check (**both** are needed: the first catches a resize between commits, the second catches one before the first commit ever ran). Then let the existing branch do its job — re-sync Leaflet's cached size and re-centre through `commit`, which PANS rather than wiping, so this costs no flash and no tile churn, and the B933 no-flash property is preserved. Deliberately the DOM's own number rather than `geoOverscan` arithmetic: the box that matters is the one the browser laid out.
- **Why it matters for the report.** With the container un-watched, B1141's compensation would have had to swallow tens of pixels — and `sanitizeShift` correctly REFUSES that, reporting `map-registration-out-of-range` and applying nothing. Fixing the source is what keeps the registration shift a genuinely sub-pixel correction instead of a mask over a real defect. This is the LOUD-FAILURE rule paying for itself inside one session.
