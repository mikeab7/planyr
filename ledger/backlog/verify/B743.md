- **🔎 Why B742/B743 didn't stick (AUDIT-FIRST, 2026-07-30).** Both prior passes fixed the ROUTE INTO `deleteSel` (the armed-vertex trap, the stale menu ref, the commit timeout) and left `deleteSel`'s own opening line — `if (!sel) return;` — untouched. That bare return is a silent no-op with no message and no telemetry, reachable from FOUR ordinary states, from any of sixteen call sites. So each pass closed one road to the hole instead of filling it, and the next state that reached it read as a brand-new "delete is broken." **Reproduced in headless Chromium on the pre-fix build, not inferred.**
  1. **A MULTI-SELECTION OF EXACTLY ONE.** `deleteSel` branched on `multi.length > 1`, else fell through to `sel` — so a one-item `multi` with no matching `sel` deleted nothing. A marquee that catches one object, or a shift-click that lands on one, reaches this ordinarily.
  2. **A STALE `multi` LEFT BY A SUCCESSFUL DELETE (measured).** The single-selection branch cleared `sel` but not `multi`. Marquee one building → Delete (works) → **every later Delete keypress did nothing at all** (`sel` null + `multi` length 1 → the silent return), until an unrelated click happened to reset `multi`. This is the owner's "a LOT of issues with delete", exactly.
  3. **A STALE `multi` LEFT BY UNDO/REDO (measured).** `applySnapshot` cleared `sel` but not `multi` — same dead key, reached from Ctrl+Z.
  4. **A SELECTION POINTING AT SOMETHING GONE.** Each branch filtered by id, so a dead id removed nothing and `tombstone([])` short-circuited — no rows changed, nothing said. Consistent with the Colorado site's zero-deletes-ever signature.
  5. **THE TYPING GUARD (measured).** The keyboard handler ignores shortcuts while a field has focus. Edit a building's width in Properties, press Delete → nothing happens while the building sits visibly selected, with no explanation.
- **The rework (2026-07-30) — one path, and silence is impossible.** New pure `src/workspaces/site-planner/lib/deletePlan.js` is the ONE decision behind every entry point; `deleteSel` is now a thin shell that applies its result. Three invariants, each tested: **(a) DELETE IS UNCONDITIONAL** — anything visibly selected is deletable, including a PINNED item (pinning guards a drag, never a deliberate Delete); **(b) THE SELECTION IS THE UNION of `multi` and `sel` at ANY count** — the count-dependent branch is gone, so a one-item marquee behaves exactly like a five-item one; **(c) NOTHING IS REMOVED → THE USER IS TOLD WHY** ("Nothing is selected — click the item on the plan first, then press Delete." / "That's already gone…"), and the keyboard Delete is now UNCONDITIONAL so a press with nothing selected reaches the code that can say so. Also: both selection stores are cleared on every delete AND in `applySnapshot`; `deleteMarkupById` / `deleteParcelById` (the two paths that don't route through `deleteSel`) got the same no-silent-return contract; and an unknown ref kind now resolves to NOTHING (the old trailing `else` treated every unrecognised kind as a **parcel**).
- **Also fixed, found in the audit:** the multi branch resolved each element ref to its assembly ROOT first, so shift-clicking a truck court silently deleted the whole building; the single branch went downward. Both now use one downward-only subtree rule — a building takes its whole bonded assembly, a child takes only its own.

- **Data-model question resolved (the owner's part 5): ONE source of truth, not two.** `deleted_at` on a `site_elements` row IS the delete; `kind='tombstone'` rows are a **migration artifact only** — `explodeModel` / `db/site_elements_backfill.sql` turn the legacy blob's `deletedIds` array into one row per dead id with `data=null` (the element's data is gone, only the id survived), which is why `site_elements.sql` says outright that tombstone rows "exist only for migrated legacy `deletedIds`". They cannot disagree: `rowsToModel` reads the single predicate `deleted_at is not null` across rows of EVERY kind into one `deletedIds` set, then subtracts any id that still has a LIVE row of any kind — so a live element always wins over a stray tombstone sharing its id (the legacy `e6327` class).
