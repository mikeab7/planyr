`[x]` **SHIPPED — street basemap moved from CARTO Voyager to Esri's `World_Topo_Map` on the same `server.arcgisonline.com` host the satellite layer already uses. `Verify: live` → V455792.**
- Verify: live — LIVE-VERIFY class (zoom-/data-density-dependent rendering; GIS endpoint behavior)
- **THE PROBLEM, confirmed not an outage.** CARTO's keyless Voyager raster tiles (`{s}.basemaps.cartocdn.com/rastertiles/voyager`) started returning a real image — HTTP 200, `image/png` — with "API KEY REQUIRED — carto.com/basemaps/apikey" stamped diagonally across it a dozen times per tile. This is CARTO enforcing account sign-up on previously-keyless usage, not a transient failure; it does not self-resolve.
- **THE NON-NEGOTIABLE CONSTRAINT.** Zero cost, no account of any kind, free tier or otherwise (the owner's standing instruction for this whole module: "I'm not trying to pay a dime"). A CARTO API key was never on the table.
- **THE FIX.** Replaced `STREET_TILES` in `FoodMap.jsx` with Esri's `World_Topo_Map` tile service (`server.arcgisonline.com/ArcGIS/rest/services/World_Topo_Map/MapServer/tile/{z}/{y}/{x}`) — the same host `SATELLITE_TILES` (`World_Imagery`) has used since day one, so this adds no new dependency and no new attribution relationship. **Axis order fixed correctly**: Esri's tile path is `{z}/{y}/{x}` (y before x), the opposite of Leaflet's own `{z}/{x}/{y}` default — this is exactly what broke the satellite toggle the first time it was built, and the URL template here is deliberately explicit about it rather than repeating that mistake. `maxZoom: 21` / `maxNativeZoom: 19` mirrors `SATELLITE_TILES`'s existing upscale-past-native pattern. The now-dead retina/`url1x` gate (CARTO-only, `@2x` tiles) was removed entirely rather than left as dead code — both Esri layers already serve one tile shape, so the effect's dependency array dropped `narrowViewport` (no longer read).
- **WORLD_TOPO_MAP OVER WORLD_STREET_MAP — a deliberate deviation from the task's own suggested pick, done under the task's own explicit permission ("World_Topo_Map is the fallback if World_Street_Map reads too busy under the pins... say which you picked and why").** Downloaded real tiles for both services at a dense downtown-Houston view (z16, tile 27088/15406) and overlaid synthetic pins across the app's actual rating-colour ramp (reds/oranges/greens) for a fair side-by-side. `World_Street_Map` draws orange/red highway shields and saturated arterial-road fills that visually compete with the pin colour ramp's own reds/oranges — a red-rated pin can read as part of the road network at a glance. `World_Topo_Map` keeps roads in muted grey/white, so pins stay legible at every rating colour. Picked `World_Topo_Map` for pin legibility, not for its (smaller) byte size — `Light_Gray_Base` is smaller still and was correctly ruled out by the task itself, since the owner has separately and explicitly rejected a grey map ("i want some color on the map, its too grey"); `World_Topo_Map` is in colour (green parks, tan terrain, blue water) and keeps that requirement.
- **BYTES, re-measured after the swap on the same downtown-Houston tile, `cache: 'reload'`.** CARTO Voyager @2x (the watermarked baseline, owner-measured): 80.6 KB. Esri `World_Topo_Map` (shipped): 25.8 KB — **~68% fewer bytes per tile**, before the retina question is even in play (there is no retina variant needed now — one tile shape serves every device). This lands directly on top of the B707841 zoom-animation perf work already budgeted against the old CARTO byte counts, making that budget cheaper to hold, not harder.
- **ATTRIBUTION, corrected rather than left "both, to be safe."** `STREET_TILES.attribution` now reads `"&copy; Esri, HERE, Garmin, and the GIS User Community"` (matching `SATELLITE_TILES`'s existing Esri credit style). The OpenStreetMap attribution requirement applies only where OSM tiles are actually served — since this swap means nothing on the page uses OSM tiles anymore, no OSM credit remains anywhere in the food module's attribution control.
- **OSM DOCUMENTED AS THE FALLBACK, not wired in.** A commented-out `OSM_FALLBACK_TILES` block (`tile.openstreetmap.org`, confirmed keyless, 38.9 KB) sits directly above `STREET_TILES` with a note that OSM's own tile usage policy discourages heavy automated use — so it is the fallback if Esri ever does what CARTO just did, not a first choice, and the next session doesn't have to re-research keyless options from scratch.
- **HONEST NOTE, not buried.** Esri's arcgisonline tiles are free to use with attribution — and are what this app has already run satellite on since day one — but Esri's own terms do contemplate an ArcGIS account for production-scale use. Moving street traffic onto the same host adds no NEW exposure beyond what satellite already carries; it just removes the watermark. This is stated here plainly, not discovered later.
