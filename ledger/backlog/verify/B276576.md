- **THE DEFECT.** `index.html:176` carried `<link href="https://fonts.googleapis.com/css2?family=Inter:…" rel="stylesheet" />`. A stylesheet is render-blocking, and — the part that actually bit — **a script cannot EXECUTE until every preceding stylesheet has resolved**, including `<script type="module" src="/src/main.jsx">`. So the whole app boot queued behind `fonts.googleapis.com`, and that host's latency passed through one-for-one. Anyone with an ad-blocker, a filtering resolver or a slow link paid it on **every single load**. `public/landing/index.html:93` had been fixed for this in B1384 (DOMContentLoaded 12,964 ms → 149 ms); the app entry was never carried across.
- **⛔ THE PART THAT MATTERS MORE THAN THE BUG: TWO INSTRUMENTS SAW IT AND MUTED THEMSELVES.** `ui-audit/perf-harness.mjs` downgraded every load-sensitive metric to *MEASURED BUT NOT JUDGED*, and `docs/perf/PERF-BUDGETS.md` wrote the behaviour up as expected. Both were **correct at the time** — the sandbox blocks the font host, FCP went ~330 ms → ~13 s, and crying wolf is worse than silence. But the mute outlived its cause and nothing was watching for that. A budget muted for a bug we have since fixed is a budget nobody is enforcing.
- **THE FIX — SELF-HOSTED, not merely deferred.** The landing page's `media="print"` + `onload` promotion makes the request non-blocking; self-hosting removes the second origin outright, so there is nothing left to be slow, blocked or filtered. Google's own subsetted variable WOFF2 files now ship from our origin (`public/fonts/`), declared with `@font-face` at the top of `src/index.css`, with a `crossorigin` preload of the latin subset in `index.html`.
- **THE COST, AND A CORRECTION TO THE ITEM'S PREMISE.** The chat block asked me to cost this against the bundle ceilings and warned headroom was tight (largest chunk 17.3 KB of 32 KB, total JS 85.2 of 93.9 KB). **Those ceilings do not apply: all four committed bundle metrics — `siteRouteJsBytes`, `notesRouteJsBytes`, `totalJsBytes`, `largestChunkBytes` — measure JS bytes only.** A WOFF2 in `public/` is neither JS nor CSS-inlined (Vite's 4 KB inline limit is far below these files), so **self-hosting spends zero of that headroom.** Transfer size is unchanged at **47.1 KB** (identical bytes, from our origin instead of Google's); `latin-ext` (83.1 KB) is declared but `unicode-range` means it is fetched only if such a character appears, which for this UI is never. Five static weights collapse into one **variable** file (`font-weight: 400 800`). Cyrillic/Greek/Vietnamese deliberately not shipped — the `system-ui` fallback in `--font` covers them.
- **NEGATIVE CONTROL, RED FIRST — `ui-audit/verify-font-blocking.mjs` (`npm run perf:fontblock`).** One build, one server, two documents, same injected latency: **arm A** is the pre-fix build with the removed `<link>` re-injected, **arm B** is what we ship. Arm A **must stall or the harness fails**, because an instrument that cannot see the bug it was built for is not evidence of anything. Measured at a 2,000 ms delay: **first paint 2,372 → 384 ms · app mounted 2,058 → 81 ms** — a **1,988 ms pass-through eliminated** on a 2,000 ms delay, reproducing the owner's one-for-one finding almost exactly. At `--delay 0` (a *perfectly fast* font host — the best possible case for the pre-fix build) it is still **596 → 448 ms first paint, 152 → 98 ms mount**, so the win is not only about slow hosts.
- **THE INSTRUMENT IS UN-MUTED, and the mute now asks the right question.** The old gate was `failedExternal.size === 0 && !NO_TILES` — "did any external host fail" — which is a *different question* from the one that governs paint. A failing aerial **tile** host does not delay first paint by a millisecond. Split into two: **paint-sensitive** (`firstContentfulPaintMs`, `timeToFirstDragMs`) gated on the document carrying zero cross-origin **render-blocking** resources, measured live from the DOM so the mute **returns automatically and names the culprit** if one is reintroduced; **tile-sensitive** (`firstAerialCoverageMs`) keeps the original gate and is **not** un-muted. Immediate payoff: **`timeToFirstDragMs` is judged for the first time and PASSES at 1,435 ms against its 4,200 ceiling.**
- **⚠ WHAT UN-MUTING EXPOSED, AND THE CEILING I REFUSED TO MOVE.** The first judged run reports **FCP 688 ms against the 500 ms ceiling**. It is **not** a regression from this change and the ceiling was **left untouched**: the same harness on the **unmodified pre-fix tree** reports **668 ms** on the same container (run-to-run noise — it was always there, hidden by the mute), and the 500 ms figure was seeded on **production planyr.io on the owner's machine** (measured 328 ms, dpr 2.15, signed in) while this is a shared sandbox container. Re-seeding from a sandbox number, or nudging the ceiling to 700 so the run goes green, would be choosing a threshold to fit a result. **Answering "is 500 right?" needs a production run, which is already logged as V477.** Recorded in `docs/perf/PERF-BUDGETS.md` rather than quietly absorbed.
- **GUARDS, two kinds on purpose.** `test/bootRenderBlocking.test.js` (11 cases, in `npm test`) forbids the static property — no cross-origin render-blocking tag, no third-party font host, preload present with `crossorigin`, both WOFF2 files valid and un-truncated, `font-display: swap` on every face. **Mutation-proven:** re-injecting the removed `<link>` turns it red (2 failures), restoring it turns it green. The browser harness measures; the unit test forbids.
- **ALSO CARRIED ACROSS: `public/sequence/index.html`** had the identical defect and now uses the same self-hosted files (no new bytes). **Stated honestly and asserted in the test rather than hidden:** that page still pulls two *other* render-blocking third-party resources (the jsdelivr icon webfont stylesheet and a synchronous supabase-js script), so removing the font host does **not** make it third-party-free the way it does the app entry.
