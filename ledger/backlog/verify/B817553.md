- **THE PROBLEM, and why it's the mirror image of a prior fix.** B668194 fixed the visit form clearing after save so it doesn't sit there full of stale data — but a form that silently clears with nothing else changing reads as "did that even do anything," not "that saved." The fix that made it tidy is exactly what made it ambiguous.
- **THE FIX has three parts, matching the owner's own list of what should change in the same beat as the click:**
  1. **A real optimistic update, not just a spinner.** `FoodApp.jsx`'s `submitVisit` now inserts a locally-built visit object into `visits` state immediately (before the network round-trip resolves), tagged with a monotonic `optimistic-<n>` id via a new `optimisticIdRef`. The Past-visits list, the score-strip aggregates (visit count, averages, last-visit date — all derived from `visits`), and the map pin (colour driven by whether a place has ≥1 visit) all update in the same render tick as the click, before the server confirms anything.
  2. **Rollback on failure, not a phantom entry.** If `insertVisit` returns an error, the optimistic row is filtered back out by its temp id, `pending` clears, and the existing error-banner path shows the real failure — nothing is ever left on screen that didn't actually save. On success, `reloadVisits()` replaces `visits` wholesale with the server's own rows, so the temp optimistic row is naturally superseded (never duplicated) once the real one lands.
  3. **An explicit, brief confirmation.** `VisitPanel.jsx` gates a "✓ Visit saved" banner (`data-testid="food-save-confirmation"`, themed via the new `--success-bg`/`--success-text`/`--success-border` tokens, matching the existing `--danger-*` pattern) on the exact same B668194 confirmed-save signal `VisitForm` already uses to clear its own fields — so it is structurally impossible for the banner to fire on a failed save. Auto-dismisses after `SAVE_CONFIRMATION_MS` (2.5s); no dismiss button, no modal, no dialog to click through — the owner is logging a meal, not filing a form.
- **THE STATE-CHANGE HALF, the strongest confirmation available per the task's own framing.** A never-visited place's panel changes shape the instant the optimistic visit lands: the score strip and Past-visits section appear (both gated on `everVisited`, itself derived from `pastVisits.length > 0`), and — new this item — the place-level "want to try" toggle (`ActionsRow`'s `wishBtn`) is now fully REMOVED from the DOM once `everVisited`, rather than merely demoted to a secondary visual style as before. A toggle offering to flag a place you've now visited is a stale control, and leaving it visible (even de-emphasized) was itself part of the "did this do anything" ambiguity — this also ships the "hide the toggle once visited" half of B707842's design that item had listed as still-outstanding UI work (see that item's update below).
