### B1447441 — Notes' global help/report button sits on top of the Bin control on phone `[Notes]` (bug) #notes #mobile #ui  *(found by the B1447440 phone-orientation harness, 2026-09-09, running WebKit against real `planyr.io`: on iPhone SE portrait/landscape, iPhone 15 portrait/landscape and iPhone 15 Pro Max portrait — 5 of 6 device/orientation combinations — the app-wide "?" help/report FAB (`app/HelpReportControl.jsx`) renders on top of the Notes workspace's `notes-view-bin` control, 82% of the smaller control's on-screen area overlapped. Both are always-on-screen chrome (neither is inside a scrollable panel), so this is a real, reachable-every-time collision, not a scroll artifact. DEDUPE-FIRST — searched Open/⏳Verify/Done for "help-report-fab", "notes-view-bin", "HelpReportControl" + "overlap"/"mobile": **B1176480** (Done) fixed this SAME control's own safe-area/tap-target/popover-fit defects on iPhone-class screens but never checked it against Notes' own bottom row of controls; not a duplicate. Net-new.)*

`[x]` **FIXED THIS SESSION.** This is the control's THIRD corner collision (map's Imagery & layers panel, #1426 — fixed by measuring real DOM instead of a hardcoded offset; the phone Properties bottom sheet, #1526 — fixed by hiding the control while the sheet is open), so the pattern itself was the real item, not just this one instance.

**Decision: (b) — give the control a way to know what else occupies the corner, not a Notes-only patch — because that mechanism already exists and this is the fourth surface not yet wired to it, not a case for inventing something new.** `HelpReportControl.jsx`'s `cornerClearanceFromBottom()` (`shared/ui/cornerClearance.js`, B966700) already reads a generic contract: any element in the DOM carrying `data-canvas-corner="<name>"` is treated as a real occupant of the bottom-right corner and the FAB rises to clear it, measured, never assumed. Three surfaces already use this exact contract for this exact corner — the Site Planner's zoom stack (`data-canvas-corner="zoom-stack"`), the Model workspace's "+ Add sheet" tab-strip button (`data-canvas-corner="model-add-sheet"`), and — inside Notes itself — the page-outline "☰" toggle (`NoteOutline.jsx`, `data-canvas-corner="notes-outline"`, which fixed this SAME FAB colliding with a DIFFERENT Notes control before this item existed). Notes' Bin/Unfiled footer rail (`SidebarFooter` in `NotesTree.jsx`) was simply never wired to it. So option (a) — patching Notes alone with a one-off offset — would have been the disproportionate choice here, since it would ignore infrastructure this repo already paid for and built to prevent exactly this; option (b) is one attribute, not a new mechanism.

**The fix:** `data-canvas-corner="notes-footer-rail"` on the rail `<div>` that holds Bin (and Unfiled, when present) — not just the Bin button itself, because Unfiled renders above Bin in that column when present, and a marker on Bin alone would under-clear (the FAB would rise just far enough to clear Bin and still sit on top of Unfiled). Marking the whole rail is correct regardless of which rows are present. This is inert everywhere else: on desktop the rail lives inside the narrower left pane and never reaches the FAB's column, so `cornerClearanceFromBottom`'s own overlap check (real DOM rects, not an assumption) never counts it there — geometry self-gates it, the same way every other marked occupant already does.
