- **The fix.** `ensureProjectRow(id, { name, confirmLive })` (`src/workspaces/site-planner/lib/storage.js`) gains a `confirmLive` option: when set, the local fast path (`readSites()[id] && !retryingPush`) is bypassed entirely, and a failed deletion check (offline/blip) REFUSES rather than falling through to the ordinary create-or-trust behaviour — a `confirmLive` caller must never proceed on "we couldn't tell." `library/lib/folders.js`'s `ensureSeeded` — the caller the brief named "above all" (it mirrors a fresh 12+ folder tree into the user's own Google Drive) — now passes `confirmLive: true`. Extending past what the brief literally named: `doc-review/lib/reviewStore.js`'s `fileNewReview` and `refileReview` write actual file BYTES into a project's Drive folder and are exactly the same failure class (a stale local row waving through an upload into a soft-deleted project's tree), so both were given `confirmLive: true` too — same mechanism, same guard, no new code path. Ordinary in-app content saves (Model/Notes/Scheduler/plain Doc Review edits) are UNCHANGED — they still take the cheap fast path, since they have no external side effect to protect a deleted project from.
- **Tests, mutation-shaped (each new case proven to exercise the actual guard, not just call it):** `test/ensureProjectRow.test.js` (+5 tests) — without `confirmLive` a stale local row still short-circuits with zero cloud calls (the pre-fix behaviour, deliberately unchanged for ordinary saves); with `confirmLive`, a project binned from another device is refused even though this device's own row is stale (`cloudCheckDeleted` proven CALLED, unlike the fast path); a genuinely live project still proceeds normally; a failed deletion check (offline) refuses rather than trusting the stale row; a brand-new, never-persisted project still creates + pushes normally. `test/fileNewReviewProjectRow.test.js` (updated) — both `ensureProjectRow` call-site assertions now require `confirmLive: true` in the exact call.
