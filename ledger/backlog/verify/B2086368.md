DEDUPE-FIRST: searched Open/Verify/Done for Library delete / Unfiled / Recently deleted — B2084480 (Unfiled refresh) and NEW-F3 (the folder-tree soft delete) are the neighbours; neither covers Home. `[x]` **Cause (AUDIT-FIRST, matches his measurement):** the soft-delete path (`deleteReview` → Recently deleted → `restoreReview` / `purgeReview`) was written INLINE in `FileBrowser.jsx` (the per-project list). `LibraryHome.jsx` (no project selected: Recent + Unfiled) never had any of it — each row was Open (+ Move to project…) and nothing else — so a file saved from Review with no project could never be removed.
`[x]` **Fix — one implementation, not a second:** the delete / undo / restore / delete-forever logic, its failure notice, the undo toast, the Recently-deleted list and the ✕ + two-step confirm moved out of FileBrowser into `library/components/ReviewTrash.jsx` (`useReviewTrash`, `TrashNotice`, `UndoToast`, `RecentlyDeletedList`, `DeleteButton`). FileBrowser and LibraryHome both consume it. Home's Recent and Unfiled rows get the ✕ (`title="Delete (moves to Recently deleted)"`, an accessible name, a real `<button>` so Tab/Enter work, `.trash-del` = 44×44 on `(pointer: coarse)`), and a `↺ Recently deleted · N` pill opens the same bin (Restore / two-step Delete forever). Nothing is written by a migration or script; no existing row is touched. Removed here: FileBrowser's inline copies of those handlers/markup (net change in visible copy: none; the ✕ glyph replaces the old ×, as named in the report).
`[x]` **Adjacent-case table (all run in a real browser, signed-in against a stub Supabase — `ui-audit/verify-library-home-delete.mjs`, 33/33):**

| Case | Result |
|---|---|
| Row in Recent AND Unfiled | one delete removes it from both (they derive from the same list) — no ghost; Restore returns it to both |
| Project file, from the no-project view (Recent) | soft-deleted; PATCH body is only `deleted_at`; `project_id` untouched; Restore returns it to ITS project, never Unfiled |
| PDF · .docx · .png | each sends exactly one `deleted_at` PATCH for its own id and leaves Unfiled |
| File with markups | the row's `data` (markups) is byte-intact after delete and after restore — soft delete never rewrites it |
| Restore from Recently deleted → Unfiled | back in Unfiled and Recent |
| Delete forever from the no-project view | asks first (two-step); the row is gone from the table and from the bin |
| Failed delete (cloud rejects the write) | a visible notice; the row stays listed and un-deleted |
| File open as a tab in Review | **Decision: the tab is left alone.** Deleting never closes a tab or discards unsaved edits (same as the folder-tree delete today). Review does not listen for Library changes, so the open tab stays; its next save writes into the binned row, and Restore brings back the latest. Closing the tab on delete would risk unsaved Word/text edits, so it was deliberately not done. |
| Keyboard · coarse pointer | ✕ is a focusable `<button>`; Enter arms the confirm and focus lands on it; every ✕ measures 44×44 under touch emulation |
| Project folder tree (regression) | row ✕ still sends the PATCH, undo toast + pill + Restore unchanged |
