### B2163344 — NEW-1: "Your last change didn't reach the cloud" banner fired on writes that DID reach the cloud — a lost REPLY is an unknown outcome, not a failure `[Site Planner / shared-cloud]` (bug) #site-planner #sync #persistence #ui
`[ ]` **⏳ Verify — V1578592.** Owner report 2026-10-06 (build dbe5f15): overlay removed / first crop committed on a fresh plan → banner, yet `public.sites` already held the change at the new version; Retry now then "succeeded".
**Root cause (REPRODUCED, not just reasoned — the writeSerializer-retry hypothesis was REFUTED):** `writeSerializer.js` does not retry anything; the site write already serializes per key (`cloudSync.cloudUpsert`) and heals a stale-CAS conflict internally. The real hole is a write whose **reply is lost** ("TypeError: Failed to fetch" — the PATCH was applied, the response never arrived; these rows are in `client_errors`). `cloudUpsertCore` returned that as `{ok:false,error}` → `cloudSaveFailed` banner, although the row held the change. Reproduced on the live build 80683f6 with Playwright `route.fetch()` + `route.abort()` on the 2nd PATCH (server applied it, browser saw a reset): banner appeared at ~6 s with the row at the new version carrying the crop, and cleared only when the *next* edit's push ran. Also read: steady-state edits, a remove and a remove+crop burst did NOT reproduce (CAS PATCHes v1→v5 clean, no banner).
**Fix (the banner follows the FINAL outcome):** (1) `cloudSync.cloudUpsertCore` — an error that is a transient network error (`optimisticUpsert.isTransientNetworkError`) is an UNKNOWN outcome: re-read the row (refreshes the CAS token — if our write landed this is the bumped version) and re-push once; only a second failure is reported (telemetry `cloud-write-retried`). A genuine failure still returns `{ok:false}` → banner + Retry now unchanged. (2) `SitePlanner.cloudPushWithWatchdog` — a generation counter: a superseded push's failure/watchdog can never paint (or keep) the banner after a newer push ran; any success still clears it.
**Tests:** `test/cloudWriteLostReply.test.js` (lost reply on an applied write → ok:true; two lost replies → still ok:false) — RED on main, green now.
**Stopping rule:** closes on a dated PASS of V1578592 (lost-reply injection on the live build shows no banner and the row holds the crop); a banner on a write that landed re-opens this.
