- **⛔ "CONFIRM THIS DOES NOT SLOW THE MAP" — addressed as a real fix, not just a check that passed.** Auditing the viewport RPC before adding more data (per the explicit instruction) found `food_places_in_bounds_sampled`'s predicate — `where lat >= ... and lat <= ... and lon >= ... and lon <= ...` — never touched the `geom` column at all, so the table's own GIST spatial index (`food_places_geom_idx`, present since the very first migration) sat completely unused; every neighbourhood-zoom pan was a sequential scan. **Measured directly against production, Houston-only (34k rows): 727ms.** Rewritten to `geom && ST_MakeEnvelope(...)::geography` — the bounding-box overlap operator PostGIS's GIST opclass actually indexes — **measured at 86ms for the identical result set**, confirmed via `EXPLAIN ANALYZE` as a `Bitmap Index Scan on food_places_geom_idx`, not a table scan. **Re-measured after the full three-metro load (80,997 rows)** at a downtown-Dallas neighbourhood viewport: still a `Bitmap Index Scan on food_places_geom_idx`, **21.7ms execution time** — confirming the fix's own reasoning (an index scan's cost tracks the matched RESULT size, not the table size) rather than just asserting it. The map does not slow down; if anything this viewport ran faster than the original 34k-row measurement.
- **DISTANCE-AWARE SEARCH RANKING, so a chain's fifteen branches don't read as identical rows.** `food_places_search_by_name` gained optional `p_center_lat`/`p_center_lon` params (the current map view's midpoint, threaded from `SearchBox.jsx`'s `bounds` prop) and a `distance_km` column; every location of a searched chain scores an identical trigram similarity (the name text is the same), so the order-by is `sim desc, distance_km asc nulls last, name asc` — **name relevance still wins first, distance only breaks ties**, never lets a worse match outrank a better one for being closer. Measured directly: searching "chick-fil-a" centred on downtown Houston returns 15 Houston locations sorted 0.2 km → 7.3 km; the identical search centred on downtown Dallas instead returns Dallas locations sorted 0.2 km → 8.7 km — confirming the reorder actually happens, not just that the column exists.
