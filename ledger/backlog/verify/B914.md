### B914 — Review resume leaks one project's last loose PDF (its "upload didn't finish" banner) onto every OTHER project's Review tab `[Doc Review]` (bug) #doc-review #persistence #ui  *(owner-reported 2026-07-21 during V331/V332/V333 live testing: a "Goose Creek PI APPROVED PLANS…" large-file banner appeared on Mesa AND ZZ-VERIFY-TEST Review tabs — two unrelated projects, not on Goose Creek itself — and blocked opening a new drawing there. Minted **B914 / V386** via `npm run next-id`. Provisional.)*
`[x]` **FIXED + sandbox-verified this session (green build · 17-test unit lib incl. the exact leak matrix · logged-out headless smoke of the clean empty state). Parks in ⏳ Verify (Verify: live — cross-project resume needs the real signed-in projects) → V386.** A large drawing opened loose (via **Open**, never filed to a project) whose cloud upload didn't finish was resuming onto the Review tab of ANY project that had no "last drawing" of its own — showing that file's stuck upload banner and its name in the Reviews field, and (because a stuck review was "active") swallowing the next **Open**. It correctly did NOT show on projects that already remember their own last drawing (Bain, Goose Creek), which is why it only reproduced on Mesa and ZZ-VERIFY-TEST.
- Verify: live
- Origin: filed 2026-07-21 from chat (owner, during V331/V332/V333 verification).
- **Root cause (`DocReview.jsx` boot-resume, the B667 per-project resume machinery):** on mount the resume loop walks candidates from `resolveResume` — the URL's project's own last-doc first, then the LEGACY-GLOBAL "last, anywhere" pointer. Its wrong-project guard was `projectId && rec && rec.projectId && rec.projectId !== projectId`. The leading `rec.projectId &&` short-circuits to *allowed* whenever the loaded review has **no** projectId — i.e. an **unfiled** loose PDF. So on a named-project route with no per-project entry, the loop fell through to the legacy global and resumed that unfiled orphan, leaking it (and its banner) onto that project. A project with its own entry never reached the legacy candidate → no leak there.
- **Fix:** a new pure, unit-tested helper `resumeAllowedForRoute(routeProjectId, recProjectId)` in `lib/lastDoc.js` — **no route → resume anything; a NAMED route → resume ONLY that project's own review (exact match), so a projectId-less orphan (null !== routeProjectId) is rejected.** The boot-resume guard now uses it. A project's own map entry always carries that project's id (`writeLastDoc` keys by the doc's `meta.projectId`), so a legitimate per-project resume is never blocked; an unfiled loose PDF still resumes freely when Review is opened with **no** project in the route (its "" bucket).
- **Secondary stuck-UI (same report, same fix commit):** the "Pick exactly two PDFs to compare…" empty-state hint (`err`) persisted across project switches and after a CANCELLED compare picker. Now: `onPickCompare` only complains when files were actually chosen (a cancel leaves the hint clear); `resetSingle` clears `err` on every switch-to-empty / New; the "⇄ Compare revisions…" button clears any stale hint on open.
- **DEDUPE-FIRST:** searched Open / ⏳ Verify / Done for resume / cross-project / lastDoc / leak / orphan. Net-new defect — a hole in **B667** (⏳ Verify — "Review remembers the last document PER PROJECT + the resume self-clobber fix", the feature this patches; a relative, not a dupe: B667 built the per-project memory + fixed self-clobber but didn't guard the legacy-global fallback against a projectId-less record). Unrelated to B686 (non-PDF resume bar) / B448 (dropped-bytes cache).
- **Verified (sandbox):** `test/lastDoc.test.js` — 3 new `resumeAllowedForRoute` cases (no-route allows anything; named route exact-match only; named route BLOCKS a null/undefined-projectId orphan — the exact leak) on top of the existing 14 (17 total, all green). Logged-out headless smoke of `#/markup`: the Review empty state renders "No drawing open" with the three buttons, NO phantom compare hint, NO stuck banner, 0 page errors. Full suite (4686+3) + lint 0 errors + build green; `MAP.md` regenerated (new `lastDoc.js` export).
- **⏳ V386 (live, planyr.io — SIGNED IN, real projects):** with a loose large PDF last-opened globally, visit the Review tab of a project that has never had a drawing (Mesa / a scratch project) → it shows the clean "No drawing open" empty state (NOT the other project's banner), and **Open** works normally. A project that DOES remember its own last drawing still reopens it.
- **Recurrence — round 2 (2026-07-21, Cowork live re-test found round-1 incomplete; fixed same session):** the leak STILL reproduced on Mesa's Review tab (the "Goose Creek…" banner + Reviews-field name) even though the `doc_reviews` fetch correctly resolved to Mesa's OWN doc (`id=eq.rvmqoihur10mmbv`, clean server title "Mesa - Civil"). Root cause: `resumeAllowedForRoute` is correct, but the boot-resume effect (`DocReview.jsx`, `[]` deps) called it with its **mount-time `projectId` closure**. On a deep link the `projectId` prop arrives a beat after mount, so the effect's captured route is still `null` while a slow legacy-global orphan's `loadReview()` is in flight → `resumeAllowedForRoute(null, …)` waved the projectId-less orphan through, and because its await settled LAST it superseded the correct per-project doc the project-switch effect had already opened, re-painting the orphan's stuck banner/name onto Mesa's route. Round-1 (mount-time-Mesa) worked; the late-route deep-link case did not. **Fix:** the resume loop now (a) guards on a live `routeIdRef.current` — a ref mirroring the `projectId` prop every render — instead of the stale closure, so once the route resolves to Mesa the orphan is rejected (`Mesa !== null`); and (b) `return`s early if `openInFlightRef.current` shows a route-driven open already owns the outcome. Verified: full suite (4748) + lint 0 errors + build green; DocReview stays its own lazy chunk. This is a React effect-timing race (can't boot headless — doc-review needs signed-in real data), so V386 stays ⏳ for the signed-in cross-project click-through.
