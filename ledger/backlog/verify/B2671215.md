- **His inference ("the UI likely waits on the Supabase write") was NOT the cause — measured first, as asked.** Two defects, both in the LOCAL path, found with a real browser on the owner's Quiddity plan shape (`bain-quiddity`, two plans, one project):
  1. **The signal never fired.** `storage.saveSite` announced a change on the shared sites-list event only for a project-name / status / role / group change — not the plan's own `name`. The crumb and the plan menu's current row read the names store (`usePlanName`), whose 2 s id→name index is cleared only by that event, so after Enter the old name stayed until the cache expired AND something unrelated re-rendered the planner. Measured: the new name was in storage at once and still absent from the DOM 9 s later; 5 of 5 runs showed nothing within 3 s. The project rename and a rename of another plan were already instant (≈ 3 ms / ≈ 21 ms).
  2. **A rename could be silently UNDONE (found while proving 1).** The planner's autosave sends `...metaRef.current`, and `metaRef.current.name` is a render-time COPY of the plan name; a save built before the rename and written after it (the 50 ms mirror write, the 400 ms settle tick, a flush) wrote the old name back over the new one — 3 of 8 runs after fix 1, 2 of 8 before it. Same species as the project-name split (a copy written back over the source), one level down.
- **What changed:** `saveSite` now (a) announces a changed plan `name` (the one funnel, so every door benefits) and (b) refuses to move the `name` of a record the store already holds unless the caller passes `{ planRename: true }` — only `SitePlannerApp.renamePlan` (the plan menu's one rename) does; a brand-new record still takes the name it is born with, and a refused attempt is reported (`plan-name-write-corrected`). Library file titles (`FileBrowser.commitRename`) now patch the list BEFORE the load + save round trips and restore the old title with a plain message on failure — the only rename found that really did wait on the network. Four existing tests that used `saveSite({ id, name })` as a stand-in for a rename now pass the flag.
- **Adjacent cases, measured (not assumed):** plan current / another / project: all on the new name at the first frame after Enter (harness below, dev and production bundle); Esc cancels and blur commits (e2e); reload shows it (e2e); a device that REFUSES the write leaves the old name and says "Couldn't save the plan rename… nothing was changed" (e2e); Notes rename already instant (`verify-notes-rename-live` 15/15); Spreadsheet sheet-tab rename on screen at the first frame (≈ 6 ms, production bundle); Spreadsheet organization-workbook rename and Schedule rename read from code only (the workbook index is written locally first; the Schedule posts to its embedded app, which replies from a state effect, no network) — **the Schedule rename is on the live V#, not claimed here.** The old `names-matrix` e2e could not see this class (its `expect` retries for 10 s) and has three failures on `main` unrelated to this change (the "File" button / never-drawn-project cases and the plan-name case, flaky before this fix).
- **DECISION FOR THE OWNER, stated not buried:** he asked that a FAILED save "put the old name back". The app is local-first (the device copy is the authority; the cloud catches up on the next edit, with a visible banner and Retry — constraint #6 / B1048400). So when only the CLOUD write fails the new name STAYS on screen and a plain banner says it is saved on this device but did not sync; when the DEVICE refuses the write nothing is saved and the old name stays. Reverting the screen on a cloud-only failure would also erase a rename that is safely on his device. Not changed without his say-so.
- **Guards (red on the old source, green on the fix):** repo-root `test/` **planRenameInstant** (real `saveSite` + real names store, 9 cases; 5 red on the old funnel, the stale-autosave pair red with only that guard off); e2e **plan-rename-instant** (a first-paint probe, NOT an auto-retrying wait — 4 of 6 red on the old source across 3 repeats); ui-audit **measure-rename-delay** — BEFORE: current plan crumb + current row never within 3 s, 5/5 runs; AFTER: 18 ms median / 23 ms worst, 0 undone; live **verify-rename-instant-live** (cloud write held 6 s, then aborted) and the Library step in **verify-library-file-move-live**.
