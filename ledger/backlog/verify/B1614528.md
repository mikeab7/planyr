- Repro (as arrived, reproduced by reading — not re-driving — the shipped chunk that compiles from the two files below): open the Task Report (breadcrumb "Reports / Select a project", no project routed). Click the small external-link icon on any row. Nothing visible happens.
- **Root cause, confirmed against the actual (unminified) source — `src/workspaces/scheduler/Scheduler.jsx` + `src/workspaces/scheduler/lib/navState.js`, which is what the arriving report's minified `Scheduler-DRUp868I.js`/`At()` trace compiles from.** The Task Report's row icon calls the embedded app's own `goToTask(pid, taskId)` (`public/sequence/index.html`), which flips the iframe's internal `section` from `"reports"` to `"projects"` and reports the clicked task's project as `activeId` — a genuine, successful, user-initiated navigation, exactly the shape `selectSchedule()` already knows how to carry into the outer route. But the Task Report is only ever reachable with **no** project routed (`projectId == null`), and `shouldNeutralizeToReports` (`navState.js`) exists specifically to correct the OTHER, ambient case — a stale/leftover project quietly still showing while the route honestly says "no project" (B1644368). It cannot distinguish the two: both look like "section is now `projects`, route is `null`." So it fired the same corrective `planar:nav-dashboard` post it uses for real drift, on an interval, and dragged the iframe straight back — the row's own click landed inside the iframe every time and was silently undone by the shell within one frame, matching the arriving report's captured message log exactly (nav-state "projects" → shell posts nav-dashboard → nav-state "reports", activeId left pointing at the clicked project as a residue).
- **The fix distinguishes a genuine row click from ambient drift by WHEN the transition happens, not by inventing a new message field.** Ambient drift is what an iframe LOAD's first confirmed nav-state can report (the embed's own persisted, account-wide `aPid`, left over from anything); a Task Report row click is a `"reports"` → `"projects"` section change that happens **after** this same load already confirmed `"reports"` at least once. `Scheduler.jsx` now tracks that with `prevConfirmedSectionRef` (reset to `null` on every iframe load, the same shape `navConfirmedRef`/B851×4 already uses), and a new pure function, `resolveReportRowNavigation` (`navState.js`), turns a genuine transition into an action:
  - the clicked task's project **is** linked to a Site Planner project → adopt that site into the route (same mechanism `selectSchedule()` already uses for a linked pick), so Site/Review follow and the task's own project schedule opens with its ancestors expanded (unchanged — `goToTask` already did that part correctly the whole time).
  - the clicked task's project has **no** linked site (Pursuits/Operations) → **KNOWN COMPLICATION, decided:** there is no project-only schedule route to send it to, and disabling the icon would silently do nothing for a real, working row — the same failure in a smaller box. Instead it's recorded as a cross-cutting **pick**, the exact mechanism B748064 already built for picking Operations/Pursuits from the ScheduleCrumb switcher: the grid shows the org-owned schedule with the task in view, the schedule crumb reads its name, and the project crumb honestly keeps reading "Select a project" (no project IS routed — that's accurate, not a contradiction; an org-owned schedule was always viewable with no site selected, e.g. the New-schedule dialog's own "Organization" default).
  - `shouldNeutralizeToReports` gained a required `pickShowing` gate (mirroring `isGridMismatched`'s own use of it) so a recorded pick is never immediately dragged back — without it, the fix for the unlinked case would have been undone by the very mechanism it's routing around.
- **Adjacent case, addressed as asked, not silently left:** the task NAME cell is not a link and does nothing useful on click today (`onClick` runs cell selection, `onDoubleClick` opens inline rename — neither calls `goToTask`). Making it activate the same jump is **not** a one-line change: both gestures are already spoken for by existing behavior on that cell, so wiring navigation through either would need a new trigger (a modifier-click, or reassigning double-click and moving rename elsewhere) — a real design decision, not a mechanical one. Left alone this item, as instructed; flagged here for a future call.
