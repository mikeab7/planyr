`[x]` **⏳ merged — V484 PENDING (Verify: live — `Blocker: real-data` + the embedded Schedule app can't boot in the sandbox).** Owner repro: Tsakiris, `planyr.io/#/project/smrjdgmlinea/schedule`, a project with no linked schedule. The "No schedule linked to Tsakiris yet" panel came up over the Schedule tab; pressing **Dashboard** in the breadcrumb flipped the crumb to "Dashboard / Select a project" but left the panel up, dimming and blocking the dashboard the user had just navigated to — with no X, no Escape and no click-outside, a dead end.
- Verify: live
- Origin: filed 2026-07-28 from chat (provisional NEW-1)
- **Root cause (AUDIT-FIRST, confirmed against the code).** `Scheduler.jsx` had `onDashboard={() => post({ type: "planar:nav-dashboard" })}` — it messaged the embedded iframe and nothing else, so the OUTER route kept its `projectId`. The panel's gate (`showLinkPanel`) is derived purely from the outer route, so it could never unmount. `selectSchedule` already did the right thing (post **and** `onProjectChange?.(linked)`); Dashboard was the one nav action that never carried up. The half-transition was visible in the crumb: the iframe's nav-state flipped `section` to `"reports"` and `currentProject` to null, but `showLinkPanel` did not consider `section` at all.
- **Fix — all three parts, none skipped.**
  - **(a) Dashboard carries up.** New `goDashboard()` mirrors `selectSchedule`: it posts `planar:nav-dashboard` **and** calls `onProjectChange?.(null)`, so the outer route follows what the iframe just did.
  - **(b) Belt-and-braces gate.** `shouldShowLinkPanel` now requires `section === "projects"`. This is a project-scoped resolution panel, so ANY future route↔iframe desync degrades to a missing panel rather than a trapped user.
  - **(c) A real escape hatch.** `LinkSchedulePanel` takes `onDismiss` and renders an X in the card corner plus a window-level Escape handler. Dismissal links and creates **nothing** — it just reveals the empty Schedule tab, and is remembered per routed project (`dismissedFor`), so routing to a DIFFERENT unlinked project still offers to resolve it.
- **The two ping-pong hazards the surrounding comments warn about are both handled.** Clearing the route leaves a window where `projectId` is null but the iframe hasn't yet reported `section: "reports"` — in that window the carry-OUT effect would have re-adopted the active schedule's linked site and put the panel straight back up. `dashboardIntentRef` suppresses the carry-out for exactly that window and is cleared by **the very next nav-state** (and by any deliberate `selectSchedule`), so a non-honouring iframe degrades to the prior behaviour instead of a route that can never adopt again. The `isActive` keep-alive gate is untouched — a HIDDEN scheduler still never writes the route — and the carry-IN effect is untouched (it still never calls `onProjectChange`, so B560's A↔B flash cannot revive).
- **Decision layer extracted so it is testable without a DOM** (the vitest runner is Node-only, no jsdom): `lib/navState.js` gains `dashboardNavActions` / `shouldShowLinkPanel` / `shouldAdoptLinkedSiteIntoRoute`; `Scheduler.jsx` keeps no gate logic of its own.
- **Guards.** `test/schedulerLinkPanel.test.js` (13 cases) locks the whole sequence — panel up on an unlinked project route → the Dashboard action clears the route → the panel is gone; the panel never renders when `section !== "projects"`; every pre-existing gate (`ready`, resolved site name/B560, already-linked, keep-alive, loop-free) still holds; and the carry-out is suppressed only inside the intent window. `e2e/schedule-link-panel.spec.js` drives the real app **logged out** (a seeded local site group + the `#/project/<gid>/schedule` route): Escape closes, the X closes, and Dashboard clears the route AND dismisses the panel. **The e2e guard was proven non-vacuous** — with the old post-only handler restored it fails on exactly the reported symptom (URL still `#/project/<gid>/schedule` after pressing Dashboard).
- **What is verified HERE vs what V484 still needs.** Sandbox-verified 2026-07-28, headless Chromium: all three e2e escape paths pass, plus lint + the full unit suite + build. **Not verifiable here:** the embedded Schedule app (`public/sequence/index.html`) loads its in-browser Babel from a CDN the sandbox egress blocks, so the iframe never boots and never emits `planar:nav-state` — the panel appears via the `ready` fallback timer. That means the *iframe-side* half — the embed actually reporting `section: "reports"`, the anti-ping-pong window against a real nav-state, and a real linked/unlinked schedule list — is confirmed only on a signed-in production session. See **V484**.
- **⚠ AMENDED 2026-07-29 by B1065 / B1066 — parts (b) and (c) above are REMOVED, and V484 is superseded by V491.** Both belt-and-braces suppressors turned out to be strands of their own: the `dismissed` state in (c) permanently removed the only create/link entry point for a project (the owner's Tsakiris report), and the `section === "projects"` requirement in (b) suppressed it for every project whenever the embed sat on its dashboard. Part **(a) — Dashboard carries the route up — stands unchanged and is still the way out**; it is now the ONLY way out, by design. Re-verify this item under **V491**, not V484.
