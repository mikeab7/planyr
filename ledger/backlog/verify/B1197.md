- **Report, verbatim.** *"one of the edge points that I was gonna use to expand the overlay … it's hidden behind the parcel. So let's layer the overlay above the parcel, but I guess a bigger issue is that I don't even have the option to bring it to the front."* On his screenshot the reference's top-right grip sits directly under the green parcel line at the E County Rd 14 corner.
- **The defect is generic, and fixing only the overlay's z-order would have left the trap in place.** A manipulation handle is **chrome, not content**: it must render above every map layer and win the hit test whenever the pointer is over it, whatever is drawn underneath. A handle you cannot grab is a broken handle regardless of layer order — and the next thing that happens to sit on top would have re-created it.
- **AUDIT-FIRST — the sweep the item asked for, with the answer.** The parcel vertex handles, the element resize/rotate grips, the road vertex grips, the add-nodes and the markup handles were **already correct**: they are built as consts and rendered from one `data-export="skip"` chrome group at the very end of the feet-space transform. **Three sets were NOT**, because they were authored inline inside the content pass that draws their object — the **reference overlay's** scale + rotate grips and its B73 calibration marks (below parcels, setbacks, elements and markups: the reported case), the **callout's** B913 width grips and per-leader grips (below measurements and labels), and the **measurement's** B230 control points (below labels). All three are hoisted.
- **The fix.** One `data-handle-layer="1"` group, the LAST child of the feet-space transform, renders every handle set in the planner. In SVG a later sibling both paints over and hit-tests ahead of everything before it, so that single position buys visibility and grabbability **together** — there is no second hit-test rule that could drift out of step with the paint order. The overlay grips ride the overlay's own rotation transform so they stay on its corners; locked/calibrating states, the export skip, and every drag-starter are unchanged (all five already `stopPropagation`, so hoisting them changes no event path).
- **B1184/B1185 are untouched, as the item required** — the screen-space thinning and the smaller mark with the unchanged grab area are decisions about handle SIZE and COUNT, not about which layer they live in. Asserted in the guard.
- **Verified here, on the real render path, logged out.** New e2e spec `e2e/references-handle-layer.spec.js` seeds a plan whose reference's top edge lies exactly ON the parcel boundary, selects it, and for each of the four corner grips reads `document.elementsFromPoint` at the grip's centre: **all four answer as themselves, and the spec first proves the parcel geometry really is stacked underneath them** (otherwise a plan with no parcel would pass vacuously). A real mouse drag of the boundary-covered top-left grip resizes the reference, so the grip genuinely takes the press. The rotate knob is checked the same way. Plus `test/handleLayerOrder.test.js` (21 source guards: every handle set renders from the layer, none of the five ex-inline drag-starters is wired from a content pass again, nothing paints after the layer in feet space, the export skip and the locked/calibrating states survive the move). lint 0 errors · 6,820 tests · build green.
- **What the sandbox could NOT prove (→ V554):** the owner's own bar — his actual signed-in Weld County plan, his actual PNG exhibit, over the real aerial. The seeded repro reproduces the geometry, not his data.
- **Bundle — a budget BREACH, paid back with a matching optimization rather than a raised ceiling.** The feature costs +2.5 KB on the site route. Three peer PRs merged the same afternoon had already spent 30.6 KB of the metric's 32 KB headroom band, leaving `main` at 1409.6 KB against a derived 1410.9 KB ceiling — so +2.5 KB put `largestChunkBytes` **1.1 KB over**, and CI went red. **`npm run perf:ratchet --allow-raise` was deliberately not used:** the repo's rule is that a feature breaching a budget ships with an optimization or does not ship, and there was a real one to find. **`lib/sheetFurniture.js` was split by TIER.** It held both the drawing PRIMITIVES the live canvas needs (scale bar, north arrow, metrics, `screenFurniturePlates`) and the corner-placement + SVG-string tier only the exported SHEET uses. Because `SitePlanner.jsx` (boot path) and `exportSheet.js` (a lazy chunk) each imported from it, Rollup hoisted the WHOLE module into their common ancestor — the site chunk — and tree-shaking cannot help there, since it drops unused exports, not exports used by a sibling chunk. The export-only half moved to `lib/sheetFurnitureLayout.js` and now rides the lazy export chunk: **5.2 KB off the boot path, 1.6 KB off the minified site chunk.** Behaviour is byte-identical (the same functions, moved; every existing assertion in `test/sheetFurniture.test.js` unchanged and green), and the rule is now written into the folder pointer so the next mixed-tier module gets split instead of hoped over.
