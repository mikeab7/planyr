**FIRST, THE THING THE REPORT ASKED TO BE SETTLED BEFORE TOUCHING ANYTHING: what `ppf` means.** `perfRing.js` names it outright — `"ppf", // pixels per foot — the zoom the user is working at` — and `perfRecorderHandle.js`'s `noteViewScale(ppf)` / `SitePlanner.jsx`'s `view.ppf` confirm it: **ppf is the Site Planner canvas's zoom level (pixels rendered per drawn foot), not a timing or latency measurement of any kind, and it has no "bad direction."** The five reports' ppf values (0.185, 0.02, 0.35, 0.033, 0.041) just say how zoomed-in the canvas happened to be when each "Something was slow" button was pressed — 0.02 is nearly the whole site on screen, 0.35 is fairly zoomed in. It is genuine, honest data (`buildReportContext` in `reportsStore.js`), but it is not a performance signal and none of it was used as one below — the network measurements are what this item and its fix are built on, per the report's own instruction.

**ROOT CAUSE, TWO FAMILIES, BOTH THE SAME SHAPE THE REPORT PREDICTED ("independent components each calling the same loader on mount"):**
1. **`auth/v1/user` — `currentIdentity()` (`teams.js`) called `supabase.auth.getUser()`, which round-trips to the auth SERVER to re-verify the JWT on every call**, and it is called independently, on mount, by `MapFinder.jsx`, `SitePlanner.jsx`, `CompsPanel.jsx`, `SitePlansSection.jsx` and `sharing.js` — all of which are mounted at once on an ordinary project open (this app deliberately keeps MapFinder and SitePlanner mounted simultaneously so the map's Leaflet instance survives switching between them). Every one of those reads is answering nothing more than "who is signed in right now," which the already-verified LOCAL session already knows — `auth.js`'s own `getUser()` helper already reads it via `supabase.auth.getSession()` with no network call at all, a pattern `teams.js` had simply never adopted.
2. **`profiles?select=prefs` — FOUR independent modules (`userPrefs.js`, `compsRatePeriodPrefs.js`, and the Dashboard's own `dashboardPrefs.js` / `dashboardSinceLastHerePrefs.js`) each fetch the SAME account row directly, with no shared cache**, each just reading a different key out of the same jsonb blob. `userPrefs.js`'s `loadUserPrefs` alone is called independently by `SitePlanner.jsx`, `MapFinder.jsx` AND `SitePlannerApp.jsx`'s own `sharing.js` share-loader — three of the five observed `profiles` reads from ONE function.
3. **Two things the report flagged that turned out NOT to be bugs, checked rather than assumed fixed:** the "sites?select=id,group_id,site,name,deleted_at TWICE at 887/870ms" pair is `cloudCheckDeleted`'s existing, deliberate `Promise.all([byId, byGroup])` — it already runs in PARALLEL (887/870ms are two concurrent requests, not 1.7s serialized), and merging it into one `.or()` query would trade a documented, deliberately-conservative design (avoiding a hand-built filter expression on opaque ids) for a request-count win with no real latency win — left alone. `site_elements?select=site_id,updated_at` firing 5-7x is `fetchAllElementRecency`/`cloudElementRecency` legitimately PAGING past PostgREST's 1,000-row response cap — each of those calls returns a DIFFERENT page of DIFFERENT rows (this account's total element count, not the 94 on Goose Creek alone), not the same answer refetched. Both are said here plainly rather than silently "fixed."

**THE FIX.**
1. **`teams.js`'s `currentIdentity()` now reads `supabase.auth.getSession()` instead of `supabase.auth.getUser()`** — this doesn't just dedupe the six calls, it removes the network round trip for all of them: every downstream read/write this identity feeds is still authorized server-side by RLS regardless of what uid this returns, so re-verifying the JWT on every call bought nothing but latency.
2. **New shared module `src/shared/profile/profileRowCache.js`** (`getProfileRow(uid)` / `invalidateProfileRow(uid)`) — concurrent callers for the same uid share ONE in-flight request; a settled read is kept for 30s so components mounting a few seconds apart still share one fetch; a real fetch error still REJECTS (never silently collapsed to a cached `null`) so `userPrefs.js`/`compsRatePeriodPrefs.js` keep their existing "fall back to the local mirror on a real failure" behavior exactly as before, and a failed read is evicted immediately rather than cached, so the next caller retries instead of failing for the whole window.
3. **Wired into `profile.js`, `userPrefs.js`, `compsRatePeriodPrefs.js`, `dashboardPrefs.js`, `dashboardSinceLastHerePrefs.js`** — every LOAD now reads through the shared cache; every SAVE path is untouched (each still does its own fresh read-modify-write immediately before its upsert — correctness there matters more than sharing a cache would help) and now calls `invalidateProfileRow(uid)` after a successful write, so the next load is never served a pre-write value.
4. **Nothing here introduces a stale cache that survives a real change** — a restore/delete/rename/plan-switch's own queries are untouched (`cloudList`/`cloudCheckDeleted`/`listDeletedPlansInGroup` don't go through this cache at all — only the `profiles.prefs` row does), so the recently-shipped B1469872/B1482000 "Recently deleted" plan list is unaffected; confirmed by re-running its own test suites (`deletedPlansInGroup.test.js`, `deletedProjectGate.test.js`) — still green, unmodified.
