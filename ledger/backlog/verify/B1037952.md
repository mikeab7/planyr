- Verify: **live** — this is exactly a timing/race bug (a chunk-load failure's own auto-recovery racing the app's own failure banner), a mandatory LIVE-VERIFY class.
- Fix, four parts:
  1. **New durable failure log** (`src/shared/cloud/writeFailureLog.js`) — every background push failure is recorded to `localStorage` SYNCHRONOUSLY, inside the same catch handler that used to only call `setPushError`, so the record survives the exact navigation that can eat the in-memory banner. Drained and re-shown as the SAME banner on the next boot if still unresolved (`SitePlannerApp.jsx`'s new boot-drain effect).
  2. **Cloud-sync badge wired to background failures** — `SitePlanner.jsx`'s `headerSaveState` now returns `"error"` when a `backgroundPushFailed` prop is set (threaded from `SitePlannerApp`'s `pushError`), so the badge can no longer read "Synced" while an unretried background push failure is showing, even though the failure isn't about the currently-open plan's own save.
  3. **A real Retry**, not just "it'll catch up eventually" — the pushError banner and the badge's popover ("Retry now", already-existing plumbing in `CloudSyncBadge.jsx`'s `onRetry`) both re-attempt the exact write that failed: a rename retries with the CURRENT local name (already correct — the local write always lands before the cloud attempt), a push/status retries against the same id.
  4. **Enumeration of every silent `.catch(() => {})` around a cloud write**, per the block's explicit ask — grepped `storage.js`, `elementSync.js`, `cloudSync.js`, `cloudRename.js`, `sharing.js`, `SitePlannerApp.jsx`, doc-review's `usePersistence.js`:
