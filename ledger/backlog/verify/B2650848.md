`[x]` **Diagnosis (measured from the workflow's real run history and the stored rows, 2026-11-04 — GitHub's scheduler dropping runs was the likely reading; it is now shown):** (a) **Not the workflow failing, not the report refused.** All 5 scheduled `Sign-in health` runs finished green; the 7 non-drill rows in `signin_health_checks` are exactly those 5 + the 2 manual runs; a run that died before reporting would be a red run and there is none. `[x]` **The fix.** (1) **Fast check** — `POST /api/ops/signin-heartbeat` (`functions/api/lib/signinHeartbeatRoute.js`): the three network checks (live bundle's bot-check key · Supabase's gate · the sign-in email route) run on Planyr's own server, called **every 15 minutes** (`7,22,37,52`) by a **Supabase `pg_cron` job through `pg_net`** (`src/shared/auth/db/signin_health_edge_cron.sql`). **No secret and no new account/service**: the route ignores the request body and runs the checks itself (a caller can only make it LOOK at the live site, never record a result), and refuses a second run inside 8 minutes. A failure is re-checked ~20 s later in the same request. Measured against production from the sandbox: 3 checks pass, 4 fetches, ~1.1 s. Ruled out: dispatching the workflow from a route (needs a stored GitHub token — a human step and a secret this repo avoids), a Cloudflare cron Worker (new deploy credential), anything paid. (2) **Browser check** stays on GitHub as best-effort; same workflow, same route, now `source: "runner"`. (3) **Two sources, two streaks** — `effectiveHistory`: a pass from one source never ends the other's failure (the fast check does not look at the sign-in form), recovery needs a fresh pass from the source that failed, the 24-unknown "blind" rule follows whichever source is stuck (found while listing silent-stop modes: a fast check stuck on `unknown` would otherwise never alarm). (4) **Dead-man's switch, per source, emailed once** — `evaluateStops` runs on EVERY report from either source: fast check silent **> 45 min** (three missed beats) or browser check silent **> 12 h** (longer than any gap measured, 8.5 h; the old 150-minute limit would have fired on every one) → ONE "a sign-in check stopped running" email (`signin_stop_alerts` holds the episode; retried on later reports if Gmail was down; no all-clear note). A never-reported source is "not armed", not "stopped". The Ops card and `ops-snapshot.mjs --signin` read each source's clock. (5) **Drill** gains steps 6–8 (a check goes silent → one email → no second → cleared) so the stopped-check email is provable live. (6) **Every way the check can silently stop → which signal catches it:** `docs/SIGNIN-HEALTH.md` (13 rows; the honest weak spots are stated — with the fast check dead the watcher is the slow GitHub path, bounded by the daily sweep; nothing can email "the sweep stopped").
