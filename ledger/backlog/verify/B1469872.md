- Verify: live `Blocker: auth` — the reported picture is a real signed-in account's soft-deleted row sitting inside a still-live project group on `planyr.io`; this sandbox's proxy CORS-blocks the Supabase auth handshake, so there is no signed-in way to drive the actual purge-on-dropdown-open path here. Everything reachable without a live account is proven below. See **V1065280**.

**ROOT CAUSE.** `storage.js`'s `listDeletedProjects()` (the account-wide "Recently deleted" bin `ProjectBreadcrumb.jsx` renders) filters every group through `groupStillHasLivePlans()` — correctly refusing to show a project as deleted while it still has a live plan (B1336576, after "Richfield"/"Woods Road" read as deleted with live siblings). But `purgeExpiredDeletedProjects()` — the lazy 30-day sweep that runs every time the project-switcher dropdown opens (`ProjectBreadcrumb.jsx`'s `refreshBin()`) — ran `cloudHardDelete` on every row older than `DELETED_RETENTION_DAYS` with **no such filter**. So a plan deleted from the plan menu while its project still has other live plans was invisible in the only bin that existed, and was then permanently destroyed on schedule — `site_elements` cascade included (`ON DELETE CASCADE` on `site_elements_site_id_fkey`) — with no restore ever having been offered anywhere. `ProjectBreadcrumb.jsx`/`Shell.jsx` are the only callers of `restoreDeletedProject`, and both source entries from `listDeletedProjects()`, which had already hidden the row; `Shell.jsx`'s deep-link fallback (`entry ? entry.ids : [projectId]`) can't reach it either, since its group resolves live at the route gate. `SitePlansSection.jsx`'s "Recently deleted" is a different table (`site_plan_overlays`) and never overlapped this case.

**⛔ RETRACTION (2026-09-10, B1482000's own dispatch) — the sentence above about `Shell.jsx`'s deep-link fallback is WRONG and is being corrected here, not deleted, so the record stays honest.** *"`Shell.jsx`'s deep-link fallback (`entry ? entry.ids : [projectId]`) can't reach it either, since its group resolves live at the route gate"* was inference relayed as measurement, never run. Measured directly this session: navigating straight to a soft-deleted plan's own URL (`#/project/<id>`) DOES reach the route gate's `DeletedProjectNotice`, and it DOES offer a working Restore (`restoreBlockedProject` falls back to `restoreDeletedProject([projectId])` — the single-plan id — exactly when `listDeletedProjects()`'s bin has no matching entry, which is precisely this case). It does not change this item's fix (nobody navigates to a deleted plan's URL by hand in the ordinary flow, and the 30-day auto-purge destroyed the row regardless of whether the deep link could reach it) — it only corrects a claim that should not be repeated. What the deep link actually got wrong instead — announcing "This project was deleted" and naming the whole PROJECT for a row that is really one PLAN inside a still-live project — is B1482000, below.

**Already ruled out before starting (per the dispatch's own "already measured" list, re-confirmed rather than re-derived):** `groupStillHasLivePlans` on the "Delete forever" path (`purgeDeletedProject`), `purgeProjectFoldersFor`, `unfileReviewsForDeletedProject` — all three already carry the guard and fail safe; none of them is where the destructive gap lived. `sites.group_id` carries no foreign-key constraint (confirmed against `information_schema` in the prior B1164193 investigation), so a hard delete of one plan row can't cascade-destroy anything keyed on `group_id` beyond that one row's own `site_elements` — the danger here is destroying the RIGHT row too early, not a wider blast radius.

**THE FIX, two parts — closing the gap rather than just widening the guard.**
1. **`purgeExpiredDeletedProjects` now applies the SAME `groupStillHasLivePlans` check per row, before `cloudHardDelete`, not just before the folder cascade.** A row whose group still has a live plan is left soft-deleted indefinitely instead of aged out blind; the function now returns a `skipped` count alongside `purged`/`failed`, and reports `plan-purge-skipped-live-group` (LOUD-FAILURE) for each row it declines to destroy. `listDeletedProjects`, `purgeProjectFoldersFor`, and `purgeExpiredDeletedProjects` now all agree on what "still live" means — the exact discipline B1164193's own header already asked of every caller.
2. **A real, reachable surface for the plans this exempts — `listDeletedPlansInGroup(groupId)` (`storage.js`, new) + a "Recently deleted" section in the Site Planner's plan menu (`SitePlanner.jsx`).** The plan menu is only reachable while a live plan in this exact group is open, so it's the natural home for exactly the plans the account-wide bin hides. Each row offers **Restore** (`restoreDeletedProject`, already existing) and **Delete forever** (`purgeDeletedProject([id], groupId)`, already existing — its own `purgeProjectFoldersFor` guard correctly no-ops the shared-folder cascade while the group stays live, so this never touches Drive/`project_folders` for an active project). This is the design point the brief raised explicitly: exempting from auto-purge without a surface would just trade "destroyed on schedule" for "retained in a window nobody can reach" — the fix needed both halves, not one.
   - The plan-delete confirm chip in `SitePlanner.jsx` (previously silent on recoverability) now says where the plan goes and points at the new list; the storage.js comment block that used to assert the old (wrong) behavior — *"the individual dead sibling plan keeps aging toward its normal 30-day auto-purge either way (purgeExpiredDeletedProjects, unaffected by this filter)"* — is rewritten to describe the actual, now-fixed behavior.
