### B2270096 — Amends B2308848: browser suggestions stay on address / contact fields, off everywhere else `[site-planner, schedule, app-wide]` (bug) #site-planner #scheduler #ui
`[~]` **⏳ Verify — merged-pending, V1695232 pending (his Chrome).** Owner clarification 2026-10-17: B2308848 (#2357) turned suggestions off on every non-contact field; he still wants them where they obviously help — typing an address, an email, a person's name or company — and does NOT want them on a building depth, a length box, small text or a street label name. Rule: suggest where it obviously makes sense and other top apps do; everything else off.
**Fix:** one decision point, `shared/ui/noAutofill.js`. Default stays OFF (`NO_AUTOFILL` / the app-wide stamp); a field becomes a contact field only by opting in explicitly with `contactField(kind)` (`CONTACT_TOKENS`: name, email, phone→`tel`, company→`organization`, street→`street-address`, city→`address-level2`, state, zip→`postal-code`), which sets the standard token + `data-contact-field` so the stamp (`phoneTyping.js`) leaves it alone. The Schedule iframe carries a byte-checked inline copy. **Audited and opted in:** Schedule › Contacts (name + email, add and edit), Site › "Set this plan's location" address box (`street-address`), Team invite email (`email`); sign-in/profile already carried real tokens (AuthPanel untouched). **Stays off:** every dimension/length/depth/count, labels, street label names, parcel/plan/site names, notes, the Map "Filter by name…" box and the Parcels filter (both now carry the explicit stamp; the Map one had none after #2357).
**Decision — Planyr's own address search (`PlaceSearchField`, "Type an address, city or place…") stays `off`:** it has its own live suggestions, and a Chrome saved-address list on the same spot would pop over/against them; it is also for looking up someone else's place, not the user's own address, so Chrome's list would only be noise. Same for the comps party-name box (own suggestions). The Set-location box has no suggestion list of its own, so it gets Chrome's address suggestions.
**Verified here:** `ui-audit/verify-no-browser-autofill.mjs` now asserts the OFF set is strictly `off` (a real token on a non-contact field fails) AND the contact set carries its exact token (Set-location `street-address`, Contacts `name`/`email`), with known-answer arms that go red for both mistakes; also fixed an instrument defect (stale `data-nba` tags could make the sweep read a different field). 48/48 on the fix, **43/48 on current main** (5 contact assertions red). `test/noAutofill.test.js` pins the token table, the iframe copy and the call sites.
