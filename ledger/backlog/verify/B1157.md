`[ ]` **⏳ IMPLEMENTED — V537 PENDING.** A 40-move burst delivered faster than the display refreshes went from **40 render commits / 1,642 DOM writes** to **1 / 25**, measured before and after.
- Verify: live
- Origin: filed 2026-07-30 from chat
- **Repro.** Select a polygon (a parcel, an element footprint, or a measurement) and drag one of its points. Expected: it tracks the cursor. Actual: it trails behind.
- **Cause, two layers, both in `SitePlanner.jsx`:** (1) `onMove` called `setCursor(fp)` **unconditionally on every pointermove**, with no frame coalescing anywhere on that path — and the two lines directly above it write refs with comments that say *ref-only, no setState in this hot path*. At 60–240 Hz that re-ran the entire render body and rebuilt the whole JSX tree for a coordinate readout. (2) The vertex branches then setState per move on top of that, each invalidating geometry the render body derives — the O(n²) parcel overlap + dissolve (ear-clip triangulation and Sutherland–Hodgman per pair, no memo in `lib/polyClip.js`) and the `els.forEach` metrics loop whose `curbAreaOf` scans the whole array per element.
- **The fix — one keyed frame job per surface.** A later job with the same key REPLACES the earlier one, so a frame commits at most one cursor update and one geometry update. This is safe because every one of these writes is **absolute and idempotent** (put vertex *i* at this point / the cursor is here), never an increment: a dropped intermediate is a frame that was never going to be painted, not a lost update. The readout additionally carries no correctness risk at all — it is a display value and nothing derives geometry from it.
- **Gesture end is where a coalescer usually goes wrong, so it is handled explicitly.** `onUp` and `abortGesture` **flush synchronously via `flushSync`** before any release logic runs. That matters twice: the one release path that judges the FINAL ring (the reshaped-building self-crossing / zero-area check, which rebuilds the dock frame off it) now reads `stateRef.current.els` rather than its own render closure — a closure captured at the previous render cannot see a commit made microseconds ago — and `flushElems()`, which hands the settled canvas to the element-sync engine, sees the real final geometry rather than one move short of where the finger let go. On an abort the flush happens BEFORE `cancelActiveMove`, so the ordering is exactly the old one and a pending job can never land back on the canvas after the revert. The frame is cancelled on unmount.
- **Third fix, unrelated to coalescing:** while idle in select mode with no selection, every pointermove spread, sorted and reversed the whole element array to find the hovered building. Now one linear scan, no allocation — and provably the same answer, because `byZ` is a total order (it ends in an id comparison), so "the max under `byZ`" is the same single element the sort-reverse-find returned.
- **MEASURED, before and after, with the tab visible — `ui-audit/verify-new2-vertex-drag.mjs` (new).** It reuses the standing harness's reference scenario, its frame sampler, and critically its **refusal to report a median it cannot stand behind** (`lib/frameSampling.mjs` — the B1086 trap: rAF is suspended in a backgrounded tab and says nothing about it, and a PARTLY throttled run still yields a plausible-looking number).
  - **Frame time is UNCHANGED and that is reported honestly, not spun:** 16.7 ms median / 16.7 p90 on both builds, at 60–63 fps with the tab visible. The reference scenario is deliberately LIGHTER than the owner's real plan (its own header says so) so both sit on the vsync floor. Frame time cannot separate these builds here, and claiming otherwise would be dishonest.
  - **What CAN be measured is the mechanism, and it is decisive.** A React commit applies its DOM writes in one synchronous batch, so one MutationObserver callback ≈ one commit — which needs no app instrumentation, and is therefore the only kind of probe that can produce a BEFORE number from the base build. Delivering 40 pointermoves **one per macrotask** (a MessageChannel, so no 4 ms clamp — the 120–240 Hz case real hardware produces): **base 40 commits / 1,642 DOM writes → after 1 commit / 25 DOM writes.**
  - **A note for whoever runs this next:** a Playwright scripted drag awaits between events, so it delivers at most one move per painted frame — precisely the case where coalescing has nothing to do. Both builds read 121 commits over 120 moves on that phase. The burst phase exists because of that.
- **Not touched, deliberately:** the pan path (B1122's layout-effect transform), the B65 anti-flash ghost, and every non-vertex drag mode.
