  1. **MISSING CACHE BACKFILL.** The other two places that produce a fresh raster — creating an overlay (`openOverlayFile`) and changing its page — both write the result back to IndexedDB (`idbPut(o.idbKey, r.src)`) so the next load is instant and offline-safe. The rehydrate-from-Storage path downloaded from cloud Storage and re-ran PDF.js/DXF, but never wrote the result back — so **every load on a device whose local cache doesn't already hold this overlay (a fresh browser, "clear site data", private mode, or a first `idbPut` that silently failed) re-pays the full download + re-rasterize forever**, never healing itself. Fixed: all three rehydrate branches (PDF/DXF/image) now backfill IndexedDB the same way the other two call sites already do.
  2. **A RASTERIZE FAILURE WAS SILENTLY MISCLASSIFIED AS "NETWORK."** `rasterizeStoredPdf`/`rasterizeStoredDxf` return `null` on ANY failure — a bad download, OR PDF.js/canvas throwing while decoding a page that DID download successfully (a real possibility on a 5.7 MB, 30×42 ARCH-E1 sheet). The caller could not tell these apart: a genuine rasterize failure was always recorded as `"network"` (implying a retry might help), with **zero telemetry** — the real bug is invisible even in production diagnostics, which is exactly the failure mode that would explain "healthy bytes, healthy permissions, still doesn't render, no error the owner can report beyond 'it doesn't render.'" Fixed: a raster-step failure now gets its own terminal reason (`"render"`, distinct from `"missing"`/`"network"`) and a `reportClientEvent("overlay-rasterize-failed", …)` row naming the site/overlay/key/byte-length — LOUD-FAILURE, so a recurrence of this exact production symptom is diagnosable from `client_errors` instead of a dead end. The on-canvas placeholder gained a matching "Couldn't render … — click to re-add the file" label (offering re-add, not an endless pointless retry on bytes that will decode the same way every time).
