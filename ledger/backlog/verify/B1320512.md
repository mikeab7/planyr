- **THE HYPOTHESIS, AND WHY IT WAS REFUTED, NOT ASSUMED.** The dispatch asked whether pdf.js's real Web Worker was failing to start (falling back to its "fake worker," which runs the ENTIRE parse/decode on the main thread) — LoAF only observes the main thread, so a long task naming the worker bundle's filename is *consistent* with that fallback. Tested directly: monkey-patched `window.Worker` in a real headless Chromium against the built production bundle and dropped a real PDF overlay through the app's own Overlays panel. **A genuine `Worker` is constructed, at the correct same-origin URL, and it exchanges pdf.js's real `test`/`ready`/message handshake successfully — no `"Setting up fake worker."` warning ever fires.** The worker architecture works. The dispatch's own "fallback explanation" — ordinary main-thread `page.render()`/canvas paint, with the chunk name merely shared — is what's actually true, but it undersold WHY: production's `pdf.worker.min-cxA_QnXv.js` (the exact filename the owner's `ltNames` cites) is **not the worker at all** — Rollup names the chunk holding PDF.js's whole MAIN-THREAD API (`CanvasGraphics`, `GlobalWorkerOptions`, `getDocument`, `_setupFakeWorkerGlobal`) after the `?url` specifier that resolves the *real* worker's URL (a separate, untouched raw copy, `pdf.worker.min-CrMmvqMo.mjs`, confirmed as the literal string `new Worker(...)` receives). So every long task the owner's telemetry attributed to "pdf.worker.min" is genuine MAIN-THREAD pdf.js work (page paint + this app's own post-processing), not a parse running somewhere it shouldn't.
- **THE OWNED, FIXABLE PART OF THAT MAIN-THREAD WORK.** `overlayPdf.js`'s `knockoutCanvas` — the white-paper transparency pass every PDF overlay runs through — read/wrote its raster in 512px-tall bands (already banded, B749, to bound the `getImageData` allocation) but ran **every band in one unbroken synchronous loop with no `await` anywhere in it**. Measured on a real PDF built at the owner's own Bain/Richfield overlay's page size (2592×1728pt, ~4,580 vector primitives): one overlay's `rasterizePage` cost 583.9ms with knockout vs. 233.3ms without — the ~350ms difference is (to the millisecond) time inside `getImageData`, entirely uninterruptible. Two overlays pay this twice, back to back, with nothing yielded to the browser in between — matching "the canvas stays frozen … touch nothing."
- **THE FIX.** `knockoutCanvas` now drives its bands through `paintSchedule.js`'s `runBudgeted` — the exact mechanism `terrainLayers.js` already proved out for this identical bug class (long `FrameRequestCallback` tasks from a burst of synchronous canvas work) — yielding a genuine `MessageChannel` macrotask between budgeted batches (the same idiom `terrainLayers.js`'s `scheduleMacrotask` uses, and for the documented reason: a `requestAnimationFrame` continuation lands in the *same* animation frame as other rAF work and doesn't actually free the main thread; a MessageChannel-posted macrotask does). Not a new mechanism — reuse of a proven one. Zero pixels changed: same bands, same `knockoutNearWhite`, same `getImageData`/`putImageData` calls, just yielded between.
