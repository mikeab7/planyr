- Verify: live

- **AUDIT-FIRST, the cause, and it is one defect wearing two faces (this item and B208961).** `addSheet` and `addGroup` both opened with `if (loadingRef.current) return;` — a bare early return. `loadStitch` holds that gate for its whole run, and its whole run was: fetch every source PDF, then rasterise every placed sheet one at a time, committing NOTHING until the last one landed. On a real set that is minutes, over an empty canvas. So every click on every row in that window did nothing and said nothing. The gate itself is CORRECT — B51 added it because a load's blind `setPlaced` would clobber an added sheet — the defect was answering a user action with silence.
- **THE FIX — a press is never dropped on the floor.** A click during a load is QUEUED (`lib/stitchLoadState.js` `mergeAddQueue`, pure + unit-locked, dedupes a double-click to one) and REPLAYED against the fresh `pdfs[]` the moment the load lets go, and the user is told in the same beat (`deferredAddNotice`). A queued add whose file is no longer open is reported by name — never dropped quietly. Two more silent paths in the same handlers closed while here: a source with no `doc` now names itself instead of throwing an unhandled rejection past the handler, and a raster failure inside `addSheet` / `addGroup` is caught and SURFACED (LOUD-FAILURE — surfaced, not swallowed; the owner's "do not paper over it with a try/catch" is honoured by the fact that every catch here ends in a visible message, never a return). A drop of a non-PDF, previously an utter no-op, says so too.
- **AND the load got faster and visible while in there.** `dedupePlaced` moved BEFORE the raster loop — the owner's own JACINTOPORT draft is 14 entries / 8 unique (B633), so six full D-size sheets were being rastered purely to be discarded. Sheets now commit INCREMENTALLY, so the set builds up in front of you instead of appearing at the end. A source that won't download and a page that won't raster are each named rather than folded into one vague line.
- **Guards.** Unit: `test/stitchLoadState.test.js` (15). e2e: **stitch-row-adds-a-sheet** — the assertion is the owner's, verbatim: *click the sheet row → a sheet is actually visible on the canvas*, checked as a rendered `<image>` with a real blob raster behind it and a non-zero box, plus the app's own "Placed sheets · N" tally agreeing. A second row adds a second sheet. A press that cannot run right now produces a sheet OR a word, never neither. Located structurally (not by a testid this branch added) so it is mutation-checkable against the old build.
- **⚠ WHAT THE SANDBOX CANNOT SHOW, stated plainly.** The owner's trigger is a SAVED stitch being re-fetched from Drive, which needs a signed-in account — logged out, a fresh drop takes the fast path and the gate is never held, which is exactly why the headless suite passes on the OLD build for this one assertion. The queue/replay behaviour is proven by unit test and by reading the code; the LIVE confirmation is V10608.
