- **Repro (owner, measured on planyr.io, signed in).** `window.fetch` hooked, `Object.keys(requestBody)` recorded for every `commit_elements` call across two full drag + Ctrl+Z runs. **Eight commits, every one with body keys exactly `p_site` + `p_ops`, all HTTP 200.** No 404, no error, no fallback — the `atomicUnavailable` latch was never involved (`NOTIFY pgrst, 'reload schema'` before the second run changed nothing, consistent with that). Consequence: the round-4 failure verbatim — run 1 split the undo's 12-op batch across THREE transactions (22:05:34.922 host restored · :40.557 six children restored · :41.547 five children at the MOVED coordinates, 7 correct / 5 stranded); run 2 produced six commits sized 12, 3, 12, 4, 5, 5, and its FIRST batch already carried non-uniform coordinates.
- **ROOT CAUSE — one line, and it is mine.** `SitePlanner.jsx`: `commit: (ops) => commitElements(supabase, siteId, ops)`. **A fixed-arity adapter.** The engine calls `commit(ops, { atomic })`; this closure accepts ONE parameter, so the second argument was **silently discarded** and `commitElements` never saw `opts.atomic`. Every batch therefore went out as the plain 2-arg RPC — 200, no error, nothing to notice. Not the gate (`batchSpansAssembly` returns true for a 12-member batch, as its test says), not the transport (it sends `p_atomic` when told), not the deployed bytes (`p_atomic` is present in the served chunk, confirmed both by the owner and by `verify-deploy.mjs`). **The wire between two correct halves.**
- **WHY IT SHIPPED GREEN, stated plainly because this is the transferable lesson.** Every B1117 test drove the engine through a harness whose own `commit` was `async (ops, opts) => …` — it accepted the option the real adapter dropped. **A mock more capable than the shipped adapter proves nothing about the shipped adapter.** The suite asserted the gate's return value and the transport's request body separately, and never once asserted the request body produced by the two of them wired together.
- **Fix.** `commit: (ops, opts) => commitElements(supabase, siteId, ops, opts)`.
- **LOUD guard, so this class cannot recur silently.** `commitElements` now reports `sentAtomic` — what actually went ON THE WIRE, not what was asked — and `fellBack` for the one legitimate un-atomic send (a project with no 3-arg overload). The engine compares intent against reality and emits `element-atomic-request-lost` + an `atomic-request-lost` event when a batch asked for atomic and did not get it. The condition is **`sentAtomic !== true`**, deliberately not `=== false`: a fixed-arity adapter never forwards the option, so the transport never learns we asked and reports `undefined` — exactly the shape of this bug, so silence must not read as success. A plain (non-atomic) call's return shape is byte-identical to the pre-B1120 contract, so no existing caller or test sees a new field.
- **Tests at the REAL boundary (the gap that mattered).** `test/assemblyTear.test.js` now drives the engine through the **real `commitElements`** with only the network faked, and asserts the **REQUEST BODY**: a 12-member assembly batch puts `p_atomic` on the wire (keys exactly `p_atomic`+`p_ops`+`p_site`); a single-element batch carries the production 2-key shape; **the fixed-arity adapter reproduces the exact production body AND is caught loudly** (this case fails against the pre-fix guard); the correct adapter warns about nothing; a project without the migration falls back quietly and is NOT flagged as a wiring bug; plus a source guard requiring the two-parameter adapter and forbidding the fixed-arity form.
- **Sandbox evidence.** `npm test` 6258 green (371 files) · lint 0 errors · build green · `element-atomic-request-lost` present in the built bundle · e2e green.
