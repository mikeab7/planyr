- **CHECKED FIRST, exactly as the pattern in this file requires before any scale change.** `food_visits` is **no longer empty** (it was when B623776 shipped) — 16 real rows, all rated, ratings 7/8/9 only (6/9/2). Verified after the migration too — all 16 rows read back unchanged (same counts, same values, now typed numeric(3,1)).
- **SCHEMA — `numeric(3,1)`, not an integer half-point count.** Chose the representation that keeps the column self-explanatory: the stored value IS the rating (7.5), never "15 half-points" a reader has to remember to halve. This matches the table's own pre-existing `cost numeric(8,2)` — same type family, same reasoning. New constraint: `rating is null or (rating between 1 and 10 and rating * 2 = round(rating * 2))`, rejecting anything that isn't a whole or half point (e.g. 7.3). Applied directly to production and re-verified (`information_schema.columns` + `pg_get_constraintdef`).
- **⛔ THE STRING-COERCION BUG, found auditing this change rather than reported separately.** PostgREST returns a Postgres `numeric` column as a JSON STRING ("7.5"), not a number — the exact reason this codebase already wraps every `cost` read in `Number(...)`. `rating` had never needed that treatment before (`smallint` round-trips as a native number), so switching its type silently introduced two live bugs that would have shipped invisibly: (1) `colorForRating`/`textColorForRating`'s `Number.isFinite(rating)` check returns **false** for a string, so every rated pin would have silently fallen back to the flat "logged" colour instead of the ramp — for EVERY rating, not just halves; (2) `VisitList`'s Rating/Cost column sorts compared the raw values as **strings**, which breaks the moment a two-digit value like "10.0" exists ("10.0" < "9.5" lexically) — a real, if narrower, latent bug in the pre-existing `cost` sort too, fixed in the same pass since it's the identical class of defect on the adjacent line. Fixed by coercing with `Number()` at each read site (`ratingColor.js`'s two functions, `foodStore.js`'s `avgRatingByPlaceId`/`manualPinsFromVisits`, `VisitList.jsx`'s `SORTS.rating`/`SORTS.cost`) — the SAME pattern this codebase already used for `cost`, applied consistently rather than invented fresh.
- **INPUT — ONE range slider, not a button row.** `RatingPicker`'s ten buttons are gone; `RatingSlider` is a native `<input type="range" min={1} max={10} step={0.5}>` — the "obvious... works on a phone" answer the owner named, and inherently one-thumbed-usable (that's what a native range input is). `accent-color` tints the native thumb/track with `colorForRating` of the current position, previewing the ramp colour with no hand-rolled widget. The chosen value is always shown as a number next to the slider (`7.5 / 10`), never only implied by thumb position. **Stays optional**, matching the no-silent-default principle applied to the date field: the slider's initial thumb rests at a neutral midpoint purely for display, but nothing is committed to form state until the user actually moves it (`rating` stays `null` until `onChange` fires) — submitting untouched logs an unrated visit, exactly as before. A "Clear" link reverts to unrated.
- **DATE — starts empty, no default, stays optional.** `visitedOn` state changed from `useState(() => new Date().toISOString().slice(0,10))` to `useState("")`. The DB column (`visited_on date`) was already nullable with no default — nothing to migrate there. Saving with no date already worked (`visited_on: visitedOn || null`) and rendering/sorting a dateless visit already handled it correctly (`v.visited_on || ""`/`"—"`, string comparison only, `new Date()` never parses `visited_on` anywhere in this module) — those were correct by pre-existing convention, not something this item had to add; verified rather than assumed.
- **PIN COLOUR RAMP — handles halves and an undated-but-rated place, both checked directly.** Halves: `colorForRating`/`textColorForRating` already rounded to the nearest of the ramp's 10 steps before this change (`Math.round`); a half rating (7.5→8) was never a crash risk, only the string-coercion bug above could have silently broken it, and that's now fixed with an explicit test. Undated: the colour functions never read `visited_on` at all — a rated-but-undated place was never at risk, confirmed rather than assumed by a dedicated test.
