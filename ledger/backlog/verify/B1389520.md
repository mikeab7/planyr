  What's different about `MapNoteEditor.jsx`'s delete control, next to every OTHER confirm-delete affordance already in this codebase (`CompDetail`'s menu, `SitePlansSection`'s kebab menu — both of which "swap the menu's own content for a confirm step rather than closing"): this one instead **relabeled the SAME button in place** — "Delete" → "Delete — sure?" — inside a fixed-width row shared with Cancel and Save. Growing that label shrinks the flex spacer beside it, pulling Cancel/Save left underneath wherever a second click aimed at the now-wider button actually lands. A miss there hits Cancel: zero network traffic, no error shown, the editor closes — which is bit-for-bit the reported symptom, and consistent with the untouched `updated_at`.
- **The fix.** `confirmDel` now swaps the WHOLE action row for a dedicated "Delete this note?" / **Keep it** / **Delete** row (`MapNoteEditor.jsx`), matching the established `SitePlansSection` idiom rather than reinventing a same-button relabel. The second click can now only ever land on a control that belongs to the confirm step itself — there is no adjacent Cancel/Save for it to be shifted into.
- **Defense in depth, same session.** `mapNotesStore.js`'s `deleteMapNote`/`restoreMapNote` verified success only by checking the response array was non-empty (`!data.length`); hardened to also check the returned row's own `id` matches the one requested, closing the theoretical gap where a truthy-but-wrong response could read as success (B209's class). `compsStore.js`'s `deleteComp` carries the identical un-hardened check — not touched here (out of this item's scope) and worth a follow-up.
