`[x]` **FIXED THIS SESSION, root cause not band-aid, plus a live production data repair.** Project creation is deliberately lazy (`SitePlannerApp.jsx`'s `newBlankSite`): a blank project with no located origin never calls `saveSite` at all — not even locally — until the first drawing edit. So a Library upload into such a project (`fileNewReview`/`refileReview`, `doc-review/lib/reviewStore.js`) was writing `doc_reviews`/`file_facts` rows, and bytes to Drive, keyed to a project id that named no row anywhere, on this device OR the cloud. Those writes survive a reload; the project's own existence does not — the route gate's `checkProjectDeletionStatus` (B848833) reads `{exists:false}` on the next load, exactly like a bad/expired deep link, and blocks it. **Fix: any Library write into a project id now materializes that project's `public.sites` row first, the same way the first drawing would** — the "whichever surface writes first should create it" option, implemented as `ensureProjectRow(id, {name})` (new, `site-planner/lib/storage.js`), the one-answer function every such write calls before proceeding. It is idempotent and non-destructive: a project already real (local record OR a live cloud row not yet pulled to this device) is left completely untouched; a genuinely soft-deleted project is refused with a clear reason rather than resurrected; a cloud push failure is reported honestly (the local copy survives for the next retry) and the calling write is refused rather than compounding the orphan. `fileNewReview` and `refileReview` (the two functions in `reviewStore.js` that assign a NEW project id to a review) both call it, before anything is sent to Drive. The alternative (refuse the ingest outright, never materialize) was considered and rejected: it would have blocked the exact "New project → upload a file" flow the owner's own repro walks through, for no benefit — a confirmed-real project id is exactly what should let the file through.
