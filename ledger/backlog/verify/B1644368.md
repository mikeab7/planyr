`[x]` **ANSWERED FIRST, AS INSTRUCTED, BEFORE ANYTHING ELSE: which project does a write in that grid land on?** Whichever one the embedded scheduler's own `aPid` field names — Goose Creek, in the reported repro. The outer shell's route has **no say at all** over what the embedded app (`public/sequence/index.html`, a wholly separate app loaded in an `<iframe>`) reads or writes: it manages its own active-project pointer, its own save state (`planar:save`, the cloud sync badge Scheduler.jsx mirrors), and its own Supabase writes, entirely independent of the outer URL. Before this fix, nothing hid the iframe or disabled its pointer events while project-less — `showEmptyState` and `gridMismatched` (the two conditions that gate `visibility`/`pointerEvents`) were BOTH `false` by construction whenever `projectId == null` (`isGridMismatched`'s old `if (siteId == null || pickShowing) return false;`). - **THE FIX, two parts working together.** (1) `isGridMismatched` (`src/workspaces/scheduler/lib/navState.js`) no longer treats a project-less route as an automatic "not mismatched." A project-less route now has exactly one honest "matched" answer — the iframe CONFIRMED it switched to its own neutral, cross-project "reports" section (the same view `shouldNeutralizeToReports` already asks it to show) — same as a routed project has exactly one ("the routed site's own linked schedule is active"). An unconfirmed load also now fails closed the same way whether or not the route names a project (the `navConfirmed` check moved above the `siteId == null` branch, not merely alongside it); `pickShowing` still wins outright first, so a deliberate cross-cutting pick (Pursuits/Operations) is unaffected. Wired into the render gate: `isGridMismatched(projects, projectId, activeId, pickShowing, navConfirmed, section)` — the iframe is now HIDDEN (`visibility:hidden`) and UNCLICKABLE (`pointerEvents:none`) for the entire window between a project-less arrival and a confirmed neutral grid, closing the data-integrity gap named above, not just the display one. (2) The `shouldNeutralizeToReports` effect's `planar:nav-dashboard` post now RETRIES (up to 6 tries over ~2.3s, the same envelope `onIframeLoad`'s own `ask()` retry already uses for `nav-request`), because a single post at mount reliably races the iframe's own document load — before its message listener is attached, exactly the race that retry loop already guards against elsewhere in this file — and, unlike the carry-in effect, this one had no natural re-drive: `setSection(nav.section)` is a no-op once the embed's first real report already reads `"projects"` (React bails an unchanged `useState` update), so a lost first post was never retried and the stale grid stayed on screen indefinitely.
