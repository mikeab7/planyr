### B2279568 — Opening a plan re-erased a restored overlay link: the device's stale heal (storageKey null + storageMissing) outvoted the cloud's storageKey in the merge `[Site Planner / persistence]` (bug) #site-planner #persistence #sync
`[~]` Fixed in code (NEW-1 of the 2026-10-15 block); parked ⏳ Verify until V1704704 passes live. Follow-on to **B2244016** (not a recurrence of its mechanism — that was a teammate's RLS refusal; this is the owner's own plan, own folder, object present).
- **Measured (owner's account, 2026-10-15):** the B2244016 restore put `storageKey` back on 12 overlays in 11 plans (cloud stamped newer). Opening Goose Creek's plan `smuwvgr36ouh` re-saved it within seconds (version 251→252) with overlay `e1454628danlgq` back at `storageKey: null, storageMissing: true`; a second SQL restore + reload erased it again (253→254). Deterministic. The drawing still painted from the device raster, so nothing looked wrong. The plans that were not open kept their keys.
- **Root cause (code, AUDIT-FIRST):** `siteModel.mergeSiteContent` unions `sheetOverlays` by id with the NEWER copy winning per record (`unionById`), and the device copy is routinely the newer one (B458's mirror write; a save re-stamps `updatedAt`). So a device copy still carrying the old heal outvoted the cloud's restored key in every merge that runs on open/pull/save (`mergePulledSites`, `saveSite`, take-over, cross-tab), and the next push wrote the null. It is NOT the rehydrate loop re-healing: that loop only runs for an overlay with no `src`, and this one had its device raster; and the object is in the reader's own folder, so `mayHealMissingOverlay` would only fire after a fresh confirmed-missing fetch.
- **Fix:** `siteModel.healPointer` — in `mergeSiteContent`, when the chosen copy of an overlay is healed (`storageKey` empty + `storageMissing`) and the other copy holds a key for the same id, the key is carried back and the flag cleared, whichever copy is newer, in both directions. A non-null key beats a heal flag in every merge direction. A truly-gone object is simply healed again by a fresh confirmed-missing fetch (the B2244016 own-folder rule is untouched).
- **Not touched:** Goose Creek data. The one-plan restore for `smuwvgr36ouh` (PART 2 of `db/overlay_pointer_restore_proposal.sql`, with `version = version + 1`) is run by the owner's chat after deploy, not by this session.
