- **DIAGNOSIS — both suspects in the brief are real strands, and the asymmetry identifies which one fired.** Reproduced headless against the SHIPPED build before touching anything (`ui-audit/diagnose-schedule-strand.mjs`, committed):
  - **SUSPECT 1 — `dismissedFor` — is what fired on Tsakiris.** It is per-project component state (`Scheduler.jsx`) feeding `shouldShowLinkPanel({ dismissed })`, and the scheduler is **kept alive** behind the other tabs (`Shell.jsx` renders every visited workspace with `display:none`, never unmounts it), so a single press of the new X or Escape suppressed the surface for that project for the **entire session**. The repro drives it exactly: panel shown on Tsakiris → Escape → leave to the Site tab and return → **MISSING**; Sylvestri in the same session → **SHOWN**. That per-project asymmetry is the owner's report verbatim, and only this mechanism produces it.
  - **SUSPECT 2 — the `section !== "projects"` gate — is a second, independent strand, but it did NOT fire here.** It is session-WIDE, so it would have broken Sylvestri too. It is real all the same, and worse: the embed persists its `section` in its own saved data, and a routed site with **no** link is never switched off the dashboard section, because the embed's `planar:nav-select-by-site` handler returns its state **unchanged** when it cannot resolve the link (`public/sequence/index.html`). So one press of Dashboard inside the scheduler could hide the create/link surface for **every** project, permanently. The repro confirms it: posting a `section: "reports"` nav-state removes the surface and it never comes back.
- **Why this is a dead end and not an annoyance:** this surface is the ONLY entry point that creates a schedule *linked to a site*. The breadcrumb's **New project** posts `planar:nav-new`, which creates an **unlinked** schedule — so a suppressed project has no path back.
- **Fix — B1066's restructure removes the cause, then this item deletes the dead machinery.** Landed in that order, exactly as the brief specifies. `dismissed` and `section` are both gone from `shouldShowLinkPanel`; `dismissedFor` / `onDismiss` / the X / the window-level Escape handler are all deleted. The gate is now a pure function of the OUTER route — `ready` + a routed `projectId` + no linked schedule + a resolved site name (B560) — so nothing can carry a memory of a previous visit, and the iframe's internal section has no say (an unlinked project gives the embed nothing to show anyway). Clearing the routed project, which is what **Dashboard** does (B1050 part (a), untouched), is the single always-available way out.
- **Guards.** `test/schedulerLinkPanel.test.js` (14 cases) states the fix as invariants: a stale `dismissed` flag cannot hide it, no `section` value can hide it, routing away and back always brings it back, and one project is never affected by another — plus every pre-existing gate and the whole B1050 carry-out suppression sequence. `e2e/schedule-link-panel.spec.js` drives the REAL app logged out: Escape no longer removes it, no Close control exists, and — the regression itself — **Dashboard clears the route, then routing back to the same project brings the empty state straight back.** `ui-audit/diagnose-schedule-strand.mjs` is kept as the reproduction of record for both strands.
