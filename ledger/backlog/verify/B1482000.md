**ROOT CAUSE, TWO PLACES, ONE FIELD MIX-UP.** `sites.site` holds the displayed PROJECT name; `sites.name` holds the PLAN name — both selected by `cloudDeletedRows`/`cloudCheckDeleted`, but two different readers coalesced them the wrong way round for what they were naming:
1. **The plan-menu list.** `storage.js`'s `listDeletedPlansInGroup` (B1469872, new this cycle) mapped `name: row.site || row.name || "Untitled plan"` — `site` (the project) FIRST — so every deleted plan in one project rendered the identical label (the project's own name), and Woods Road's two same-named plans ("Concept A PRINT" ×2) were additionally indistinguishable even from each other.
2. **The deep-link dialog.** `cloudSync.js`'s `cloudCheckDeleted` — reached when a route names a soft-deleted PLAN's own id rather than its project's anchor/group id — correctly gathers only the ONE row it was asked about (its two-query shape, `id = :id` OR `group_id = :id`, can't see that plan's real siblings, which carry a DIFFERENT `group_id`), reports it "deleted", and names it `newest.site || newest.name` — the project's name, because this function's design assumes "every row found = the whole project," which held for a genuine whole-project deletion but not for a lone non-anchor plan.

**THE FIX, both places, plus the disambiguation the report asked for.**
1. **`listDeletedPlansInGroup` now reads `row.name || "Untitled plan"`** — the plan's own name, matching the same field the live "Plans in this site" rows above it already read (`s.name || "Untitled plan"`). Two plans sharing a project can still share a NAME (Woods Road's "Concept A PRINT" ×2), so the plan-menu row (`SitePlanner.jsx`) now also renders `relTime(p.deletedAt)` beside the name — the same relative-time phrasing (`"4w ago"`) the deep-link dialog and the account-wide bin already use — and the list was already sorted newest-deleted-first (unchanged).
2. **`checkProjectDeletionStatus` (`storage.js`) now asks a supplementary question when `cloudCheckDeleted` names a row whose real `group_id` disagrees with the id that was queried** — exactly the non-anchor-plan case: it calls the existing `groupStillHasLivePlans` helper (the same one `listDeletedProjects` and the 30-day purge already trust) against the row's TRUE group. If that group still has a live plan, this is a PLAN deletion, not a project one — the result carries `scope: "plan"` and the PLAN's own name (`cloudCheckDeleted` now also returns `planName` alongside the existing coalesced `name`, so this doesn't need a second query). A genuine whole-project deletion (the id IS the anchor, or the true group has nothing live either) is untouched — `scope` stays unset, defaulting to `"project"`.
3. **`projectGateStatus`/`Shell.jsx` thread `scope` through to `DeletedProjectNotice`**, which now says "This plan was deleted" / "Restore plan" for `scope: "plan"` and keeps "This project was deleted" / "Restore project" (byte-identical to before) as the default — every existing caller that predates this field is unaffected. `data-scope` is stamped on the notice's root for a live check to assert against.
4. **A missing/empty plan name still renders "Untitled plan"** (the same fallback the live plan list and the account-wide project bin already use) rather than a blank row, even when the row still carries a project `site` — covered by its own test.
