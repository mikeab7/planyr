- **THE DEFECT, found by driving the REAL APP in a REAL BROWSER as a fake signed-in non-owner teammate** (`e2e/new1-team-plan-count.spec.js`, `page.route()` intercepts every request to the configured Supabase origin and a `localStorage`-seeded session stands in for real sign-in — the sandbox's proxy CORS-blocks real Supabase auth, so this is how a signed-in path gets driven here at all): `cloudList()` (`cloudSync.js`) never selected a `sites` row's real PostgREST primary key (`id`) — only `data, version, team_id, user_id, share_locked` — and trusted the `id` embedded in the row's own jsonb `data` unconditionally. `mergePulledSites()` (`storage.js`) keys its **entire** merge map by that same jsonb id (`map[n.id] = ...`). Two *different* physical rows (real, distinct primary keys — Postgres enforces that) whose jsonb payloads happened to carry the *same* `data.id` would silently collapse to ONE surviving plan, with zero error anywhere — exactly the reported shape: not zero plans, not a random count, **one specific plan missing**. Reproduced live: the switcher showed 4 of 5 ("Concept B" gone, no trace) on the pre-fix build; git-stashing the fix and re-running confirmed it independently.
- **THE FIX, at the read boundary, same pattern B714 already uses.** `cloudList()` now selects `id` alongside `data` at every migration-fallback tier and corrects a drifted jsonb id to the row's real primary key *before* anything downstream sees it, reporting the correction loudly (`reportClientEvent("cloud-id-mismatch", …)`).
