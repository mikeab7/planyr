- **ROOT CAUSES, confirmed by reading the actual code (AUDIT-FIRST) rather than assuming the report's own inferences:**
  1. **Task `id` is not a stable identity.** `renumberTasks` (`public/sequence/index.html`) reassigns every task's `id` by ARRAY POSITION on every structural edit (insert/delete/indent/outdent/reorder/paste) — its own pre-existing comment says so ("ids are reassigned to visual order every structural edit"). `mergeCloudDoc`, `countChangedTaskRows`, and `changedProjectIds` all keyed strictly on that positional `id`, so a single insert shifted the `id` of every task after it, and every one of those reads as "changed" (or, worse, gets diffed against the WRONG row). This directly matches the report's own INFERENCE ("tasks whose `id` stayed the same while name/dates/parentId/predecessors all changed… OR the diff/merge is matching by array position") — **confirmed, not refuted.**
  2. **`task.focused` (a per-task "show me just what's still open under this row" UI toggle) lived inside the versioned `task` object**, so toggling it on an idle tab bumped `__rev` and read as a genuine edit to every other tab — exactly the class B1107680 fixed for the 13 TOP-LEVEL keys, one layer deeper. Matches the report's own measurement (history 2025→2026 differing ONLY by task 39's `focused: true → false`) — **confirmed.**
  3. **The stale-reload banner (`staleNotice`) was set in two places and cleared in NONE.** A `checkRemote` poll (every 20s + focus/online/visibilitychange) could set it true from a moment that a subsequent successful merge had already resolved, and nothing ever set it back to false — so the banner could sit on screen making the exact claim a "merged" toast had just contradicted.
  4. **The Reload button's own copy promised safety the code didn't provide.** "Your copy is kept in Version History either way" was shown when `saveStatus !== "saved"`, but the button was a bare `window.location.reload()` — no snapshot, no flush, nothing backing that claim for edits that never reached the cloud at all.
  5. **No no-op guard.** An autosave whose content was byte-identical to what's already on the cloud (once view-state is stripped) still wrote, bumped `__rev`, and could trigger a full merge dance on every OTHER open tab — amplifying every one of the above into repeated conflict/merge cycles ("6 premerge-ours snapshots in 13 seconds") whenever several tabs (including the several `?cb=` verification tabs the report itself flags) were open on the account at once.
- **FIX, five parts, all in `public/sequence/index.html` (mirrored in `ui-audit/stress/scheduler-engine.mjs`):**
  1. **`_sid`** — a permanent per-task identity, independent of the renumbered `id`. Minted once at task creation (`mkt`), preserved untouched through every `renumberTasks` call, backfilled DETERMINISTICALLY for pre-existing (legacy) tasks in `normalizeIds` (keyed on `pid` + the task's own id AS STORED before this pass's renumbering — so two tabs independently migrating the SAME still-unmigrated doc derive the IDENTICAL sid instead of each minting a random one and reading the other's copy as a duplicate). `duplicateTask`/`pasteTaskAfter` explicitly mint a fresh sid on a genuine duplicate/copy and preserve the original on a cut+paste (a move, not a new task). `mergeCloudDoc`'s array-matching and `countChangedTaskRows`/`changedProjectIds` (which also rewrite `parentId`/`predecessors[].id`/`deadlineForTaskId`/`minMeetingsAfter.taskId` into sid-space before comparing) all key on `_sid` when present, falling back to plain `id` for every other id-keyed array (contacts/meetingBodies/…, unaffected).
  2. **`TASK_VIEW_FIELDS`/`stripTaskViewFields`** — `focused` is stripped from every task before `stripViewState`'s output is ever compared or saved, the same treatment the 13 top-level keys already got.
  3. **A content-equality no-op guard in `_rawSet`** — a save whose (view-stripped) content already matches the cloud never writes, never bumps `__rev`, never enters the merge path; this tab still converges (knownRev/baseByKey update from the read already done).
  4. **`staleNotice` is now self-healing** — cleared on a successful merge (`onMerged`) and on any `checkRemote` poll that finds it's no longer newer, so the banner can never outlive the staleness it warned about.
  5. **The Reload button now flushes first** — if `saveStatus !== "saved"`, it awaits the SAME real auto-save/merge path a live edit already takes (through the existing guard) before reloading, so a false-conflict reload can no longer discard in-flight local edits with nothing saved anywhere.
