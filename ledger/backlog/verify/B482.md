- **ROOT CAUSE, instrumented rather than guessed — and the two-machine split is what proves it.** `setActiveUser(uid)` is what switches the shared project store from the logged-OUT legacy cache (`planarfit:sites:v1`) to the signed-in user's own (`planarfit:sites:cloud:<uid>`). It was called from **exactly one place in the app**: `SitePlannerApp`'s auth effect. `SitePlannerApp` is a lazily-mounted workspace, and the Shell only mounts a workspace you have actually visited. **"Open where I left off" (`seedBootRoute`) now routinely boots straight into `#/notes`** — so on those boots the Site Planner never mounts, `setActiveUser` never runs, and the store stays bound to nobody for the entire session. Everything downstream then behaves *correctly* on the wrong data: `isCloudActive()` is false → `warmProjectsIfEmpty()` returns instantly having done nothing (B475/B482's fix, correctly declining to pull for a signed-out user) → `loadSitesList()` reads the **legacy logged-out store**. That is the whole two-machine mystery: the office machine has a few pre-cloud legacy sites on disk (so a couple of names resolve, including the street-address one), the home machine has none (so nothing resolves). Same account, same code, different leftover on disk.
- **THE FIX — the binding moved UP to the one component that always mounts.** `Shell.jsx` owns auth already; it now calls `setActiveUser` in its `onAuthChange` subscription, so the store is bound to the account on **every** route, whether or not the Site Planner is ever opened. `SitePlannerApp` still makes the same call and still runs its own pull — the call is idempotent (it early-outs when the value is unchanged) and the planner's same-user re-emit guard is keyed on its own ref, so nothing there changes behaviour.
- **AND THE WARM STOPPED LYING ABOUT WHAT IT DID (LOUD-FAILURE).** `warmProjectsIfEmpty` returned a bare boolean, and `false` meant four different things — logged out · already warm · no uid · **the pull actually failed**. A caller could not tell "nothing to do" from "the cloud refused", so every caller treated a real failure as a no-op. The new `warmProjects()` returns `{ ok, warmed, reason, error }`; `warmProjectsIfEmpty()` is kept as a thin wrapper so the two existing callers' contract is unchanged.
- **A warm that lands now REACHES the other surfaces.** A same-tab `localStorage` write fires no native `storage` event, so a pull that completed inside the header switcher was invisible to every other reader. `notifyProjectsChanged()` / `onProjectsChanged()` broadcast it — deliberately reusing the SAME synthetic `storage` event the breadcrumb already dispatches after a rename, so the existing listeners pick it up with no second mechanism beside them.
