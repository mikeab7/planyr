### B1012 — The road cleanup ran on only ONE of the two read paths, so it did nothing on a signed-in element-synced plan `[Site Planner / sync]` (bug) #site-planner #road #sync  *(owner live-verify 2026-07-25 immediately after B1010 deployed: "i just tried it, doesnt seem like its working" — and he was right. Minted **B1012 / V457**.)*
`[ ]` **⏳ merged — V457 PENDING (Verify: live — `Blocker: real-data`).** B1010 was correct and still invisible.
- **Root cause, measured on the live app + the production rows.** A site reaches the canvas by TWO paths: the site-record blob, normalised by `siteModel.migrate` (where B1008/B1010's `dedupeRoadVertices` cleanup lives), and — for a signed-in, ELEMENT-SYNCED site — the `site_elements` ROWS, folded to a model by `elementRows.rowsToModel`, which imported nothing and applied no migration at all. The owner is element-synced. So: his localStorage site cache showed the cleaned road (18 pts) because that path migrates, while the SERVER ROW still held **24 points with the debris vertex intact** and the canvas rendered from it — the flag still sat on `e38duuwgj:6` at world (231.66, 298.10), the debris vertex, even though the cache's vertex 6 was (301, 450). Proven by reading the flag's rendered position back through the view transform and diffing it against both stores plus the Supabase row.
- **Fix:** `rowsToModel` now runs the SAME exported `migrateRoads` as the blob path, inside the fold rather than at a call site — so a future read path cannot skip it by construction. This is the general lesson from the bug itself: two code paths for the same data will drift unless they share the function.
- **Sandbox-verified:** `test/roadNetwork.test.js` +3 cases — the rows fold collapses debris, a clean road is untouched (no churn), and **both paths produce byte-identical geometry** from the same input, which is the invariant that was broken. Full suite 5347 + lint + build + doc gates green.
