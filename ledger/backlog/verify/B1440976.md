**REPRODUCTION, without signing in to planyr.io.** This session has direct Supabase MCP access to the `planyr_production` project (`lyeqzkuiwngunutlkkmi`) — used READ-ONLY except where stated. Confirmed:
- `db/rename_site_group.sql`'s deployed function (read via `pg_get_functiondef`, byte-for-byte identical to the committed source) stamps `data.site` and `data.siteRenamedAt` and bumps the OUTER SQL `updated_at` column — but never touches the jsonb's OWN `data.updatedAt` field.
- `cloudSync.cloudList()` selects `id, data, version, team_id, user_id, share_locked` — never the outer `updated_at` column — and builds every client-side model as `m = row.data` verbatim. So a model's `.updatedAt` is `data.updatedAt`, ALWAYS, for a cloud-pulled row.
- A live query across every group in production (`… group by coalesce(data->>'groupId',id) having count(distinct site) > 1`) returned **zero split-name groups** — ruling out a half-landed atomic write (B1415–B1418 already proved that path correct) and pointing at a seam where a rename is lost UNANIMOUSLY, with nothing left to disagree.

**ROOT CAUSE.** `siteModel.mergeSiteContent(local, cloudRow)` — the function `mergePulledSites` runs on every cloud pull to reconcile a locally-cached plan against a freshly-fetched row — treated `site`/`siteRenamedAt` as ordinary scalars, taken from whichever side had the newer-or-tied generic `.updatedAt` (`...newer` spread). Since the RPC above never bumps `data.updatedAt`, a device holding ANY locally-cached copy of a plan from before a rename made elsewhere — a second browser, another computer, or the reporter's own device on a later session — has a local `.updatedAt` that is equal to or greater than the freshly-renamed cloud row's (unchanged) `.updatedAt`, so the merge kept the OLD `site`/`siteRenamedAt` pair and threw away the cloud row's fresh stamp entirely. Because EVERY plan in the group goes through this same merge independently, the whole group reverts in unison — `reconcileGroupNames`/`repairSplitProjectNames` (the mechanism B1415–B1418 built to catch a SPLIT) never sees a disagreement to correct, because the losing side's stamp was discarded before either of them ever runs. This is the exact shape `B1181104` found and fixed for `role` — except role's fix (bump `data.updatedAt` in the RPC) does not apply here: a rename's whole design point is that it carries its OWN dedicated stamp instead of `updatedAt` (`projectName.js`'s own header states this explicitly) — the merge just never actually read it.

**FIX.** `siteModel.mergeSiteContent` now resolves `site`/`siteRenamedAt` through `projectName.nameAuthority([A, B])` — the SAME authority function the list-read and save-choke-point paths already trust — instead of the generic `updatedAt` pick, for both operand orders and regardless of which side wins for the rest of the content. An ambiguous or unstamped pair (no rename ever made, or a genuine legacy conflict) falls through unchanged, so ordinary merges are byte-identical to before. Both entry points (`MapFinder.jsx`'s map-view rename and `SitePlanner.jsx`'s in-plan rename via the breadcrumb) funnel into the same `storage.renameSiteGroup` → `cloudRenameGroup` write and are covered by the one fix, per the brief's own diagram. The pre-migration fallback path (`cloudRename.js`'s `cloudRenameGroupFallback`, for a DB where the RPC hasn't been applied) writes the identical shape and is covered by the same merge-level fix without needing its own change.

**ADJACENT CASES CHECKED (per the brief):** single-plan vs multi-plan project — the bug is WORSE on a single-plan project, where there are no siblings left for `reconcileGroupNames` to reconcile against at all, so the merge's own pick is the only vote; a fresh browser that has never cached the plan is UNAFFECTED (no local copy exists, so `mergePulledSites` takes the cloud row directly, no merge call); the renaming device's OWN immediate session is unaffected (its local synchronous write bumps `updatedAt` via `saveSite`'s `nextUpdatedAt()`, which beats the stale cloud row on its own next pull) — the exposure is specifically a browser/device that already had ANY plan of the group cached from before the rename.

**Sandbox proof, proven the same way B1181104 was — a real-shaped fixture, not a synthetic claim.** `test/siteModel.test.js`'s new case reproduces the exact production mechanism (a stale local copy tied or ahead of the renamed cloud row's `updatedAt`, the renamed cloud row carrying a fresh `siteRenamedAt`) and asserts the stamped name wins, order-independent.
