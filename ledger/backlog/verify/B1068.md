- **Root of the confusion.** B935's control was a CHECKBOX between two positions — "On the line" (a ~1-font perpendicular clearance, i.e. just BESIDE the stroke) and "Inside the {road/easement}" (a quarter-width inset). **Neither rides the alignment itself**, and the first one is *labelled* "On the line" — so the owner reasonably read the pair as offering exactly what it doesn't.
- **Fix:** placement is now a THREE-way `<select>` — **On the centre line** (offset ZERO; the halo carries the text over the stroke — the classic street-name look) · **Just beside the line** (the old default, unchanged) · **Inside the {road/easement}** (the old inset, unchanged). Stored as `labelPlace`; `labelPlaceOf(feat)` resolves it and **maps the legacy `labelInside` boolean exactly as it rendered**, so no saved plan changes appearance.
- **The control now shows for EVERY label-bearing feature** (line, polyline, road, easement) — the owner asked for "a road or anything that where it does that line labeling thing". Only the *Inside* option stays road/easement, since a plain line has no body to tuck into.
- **Verified by MEASUREMENT, not assertion** (`ui-audit/verify-label-centerline.mjs`): each placement is rendered in its OWN freshly-seeded page — a reload would silently revert the setting through the harness's init script and make all three measure identically, which is exactly the false pass this harness hit first — and each label's `<text>` anchor is compared instance-by-instance (exact; a rotated bounding box is perturbed by the halo stroke and baseline rounding). Centring moves every label off the old just-beside spot, and all three positions are distinct. **Deliberately NOT asserted:** an order between "beside" and "inside" — "beside" is a font-height clearance in SCREEN space and "inside" a quarter road-width in FEET, so which sits further out is zoom-dependent and always was; asserting an order there would be asserting a zoom.
- **Two source-scan guards in `test/bugHuntGuards.test.js` pinned the exact old call shapes** and were updated *with the reason*: the inline-label opts guard now pins that `size`/`halo` still reach `inlineLabelEls` without pinning the whole opt list (which would fail on every future addition rather than on the regression it exists to catch), and the `onElContext` guard accepts the new `w` payload.
