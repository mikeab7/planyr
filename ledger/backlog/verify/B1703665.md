`[x]` **TWO INDEPENDENT ROOT CAUSES, BOTH FOUND BY RUNNING THE REAL PIPELINE (AUDIT-FIRST), NEITHER GUESSED.**
- **CAUSE 1 — the all-or-nothing radius clamp (NEW-2's "one side gets a bevel").** `teeGeometry`'s `fillet()` (`roadGeometry.js`) measures a corner's available reach as `tMax = (avail − along) × 0.9`, where `along` is roughly the drive's own half-width + curb (≈19 ft for a 37 ft road). Whenever the room to the actual pad corner is LESS than that (a connect point close to a corner), `tMax` computes ≤0 and the code returned a fully degenerate `{R:0}` — and `wedge()` then returned `null` for that corner outright, adding NO pavement at all. Since the road's own pavement STRIP is drawn at full width regardless (`roadStripRing` knows nothing about `avail`), the visible result is exactly the reported shape: the strip's own raw, angled flat end cap left exposed as a "bevel," with the triangular gore between it and the pad's real edge unpaved and open to the grass — MEASURED directly against this exact pipeline (not assumed): at a realistic near-corner distance (10 ft, inside the zone `along` exceeds), one side of a junction returns `wedges.length === 1` instead of `2`.
  - **THE FIX** (`roadGeometry.js`, `teeGeometry`'s `wedge()`): when a corner has no room for ANY curve, it now builds a SHARP triangular chamfer (`T → capCorner → corner`, reusing the exact anchor points the curved branch already computes and stitches its arc into) instead of returning nothing — filling the real, bounded gore between the strip's own drawn edge and the pad's edge with pavement, never a raw exposed bevel. Strictly additive (only ever adds pavement where today there is none) and scoped to `teeGeometry`'s one live caller (`deepT === 0`, the drive-into-pad case) — the road-to-road hull path is untouched. "A bevel is never acceptable output," per the dispatch — this makes the floor a sharp corner where genuinely no room exists, curving automatically the moment real room does.
- **CAUSE 2 — most contacts got no return at all because junction detection required a STORED flag (NEW-2's "seven of eleven contacts are plain butt joints").** Road-to-ROAD tees (`teeJunctionsOf`) have never needed a stored flag to recognise a junction — `teeTargetOf` detects one GEOMETRICALLY, by coincidence of a road endpoint with another road's interior vertex. Road-to-PAD junctions (`driveJunctionsOf`) required `el.driveTee` to be stamped at connect time; ANY road whose `driveTee` was never stamped (an older connect, a road nudged after connecting, one imported/migrated, or simply overlapping a pad without the exact snap gesture) got NO junction processing at all, regardless of how precisely its endpoint sat on the pad's edge — this asymmetry between the two detection mechanisms is the mechanism, not a guess: read directly from both functions' own source before writing the fix.
  - **THE FIX** (`driveJunctionsOf`, now in `src/workspaces/site-planner/lib/roadJunctions.js` — see B1703666's extraction): when a road's stored `driveTee` is absent or doesn't resolve, it now falls back to a GEOMETRIC search over every Paving/Parking-typed element on the plan, using the identical proximity test (within 6 ft of an edge, or literal containment) the connect gesture and the old code already used — mirroring `teeTargetOf` exactly. An explicit stored `driveTee` still wins when present (its kind/return-radius override is preserved); this only widens WHICH targets are considered when nothing was stored, and can only ever ADD a junction, never remove the explicit-connect path.
