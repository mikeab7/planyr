**OWNER DECISION 2026-10-29 (verbatim):** "each plan should remember each layer's opacity. Or like each project, or each project more so. It should be default within the site." → **A layer's opacity belongs to the PROJECT (the site group).** Every plan of a project draws each layer at the project's opacity; changing it in any plan changes it for every plan of the project; a new plan inherits it. On/off stays per plan (`layerOverrides`, unchanged). The map finder (no project open) keeps today's behaviour — it never writes a project. (This replaces the per-site `layerOpacity` header field proposed above: NOT built; no `siteModel`/`headerMerge`/`saveDedupe`/history change, no plan record changed.)
**SHIPPED (NEW-1, 2026-10-29) — which home, and why:** AUDIT-FIRST found no existing project-level home (a project has no row; `profiles.prefs` is account-level, `project_shares` is grants only), and every project-level fact stored ON the plans (name, role, team) is the N-copies shape behind B1415–B1418/B1440976. So the smallest single-authority home was built: **`public.project_layer_opacity`**, one row per `(owner_id, group_id)` where `group_id = coalesce(data->>'groupId', id)` of the plan the caller names (never the drifting `group_id` column; both derived server-side from a plan the caller can reach, so a stranger cannot write into a project by naming a group id), `opacity jsonb` sparse `{layer: 0..1}`. RLS on with NO policies — the only doors are `get_project_layer_opacity(p_site_id)` / `set_project_layer_opacity(p_site_id, p_patch)` (SECURITY DEFINER, `auth.uid()` guard, access = the plan's own sharing: owner or team member to read; owner, or a teammate while the plan is not `share_locked`, to write; `P0002` = plan not in the cloud yet → client keeps its patch and retries, `42501` = view-only → refused loudly). **Merge rule (a stale device cannot overwrite a newer value):** the client never sends the whole map — only a PATCH of the layers that changed (`{fema:0.6}` sets, `{fema:null}` back to default), merged into the CURRENT row in one atomic statement (`jsonb_strip_nulls(old || patch)`), the merged row returned and adopted; there is no client read-modify-write to race, and a device holding an old copy that moves one layer cannot revert another. Sparse: only layers differing from the registry default are stored; absent = default, so every existing plan opens exactly as today (no backfill); a removed registry layer's key is ignored on read and nulled on the next write. Client: `lib/layerOpacity.js` (pure) + `lib/layerOpacityStore.js` (device mirror for a synchronous first paint + debounced patch writer + refresh on open / focus / tab visible) wired in `SitePlanner.jsx`'s existing layer-memory effects (opacity tracked only while that planner is the active one). **Signed out = this device only** (mirror key `local`; signing in switches to the account's project values). **Undo:** an opacity change is NOT an undo step today (opacity-only changes never snapshot — `layerPrefs.js`/the tracking effect said so) and stays that way; the brief's "one undo step per gesture, as today" has no existing behaviour to preserve — stated here rather than invented.
