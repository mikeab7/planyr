`[x]` **FIXED THIS SESSION.** Root cause, found by reading the code (not guessed): dragging-and-dropping a brochure PDF/image onto the map — a normal, expected way to place a site plan — builds a placement with only `{centerLat, centerLon}` and no scale at all. `MapFinder.jsx`'s file-drop handler built `dropPlacement = { centerLat: ll.lat, centerLon: ll.lng }` from the drop point, and `SitePlansSection.jsx`'s `confirmPage` used `f.dropPlacement || suggestPlacement(...)` — i.e. it used the drop point **standalone**, as if it were a complete placement, instead of merging it into `suggestPlacement`'s scale computation. `overlayToRow`'s `ft_per_px: o.ftPerPx ?? null` then wrote a literal `NULL`. `validPlacement`/`overlayPlaced` (`overlayGeoref.js`) require center **and** a positive `ftPerPx` together — a center with no scale has no width or height, so nothing renders (`useSitePlanOverlayLayers` skips any overlay that isn't `overlayPlaced`), and the SAME `overlayPlaced` gate stops the placement-handles controller (`overlayPlacementHandles.js`) from ever arming — so "Editing on map" showed as the active state with **nothing on the map to grab, drag, or resize.** A SEPARATE bug compounded this: `confirmPage` called `onActivateOverlay(overlay.id)` directly after a fresh upload, bypassing the self-heal `onActivate` already has (which seeds a placement via `suggestPlacement` before arming) — so a dropped upload could arm "Editing on map" on a half-placed row with no recovery path from that entry point.

- **CHOSE APPROACH (a), the owner's own recommendation — seed a full, valid placement on every write, never allow a centre-only patch to reach the database — over (b) (a placement-affordance for a null-scale state), because (a) closes the actual reported cause (a drop point standing in for a whole placement) rather than papering over its symptom, and never produces a state that needs a special-case affordance in the first place.**
  1. `MapFinder.jsx` — `suggestPlacement(imgW, imgH, centerOverride)` now takes an optional center override and ALWAYS computes `ftPerPx` (still via `suggestFtPerPx`'s existing view-width clamp, `OVERLAY_SUGGEST_MIN_WIDTH_FT`–`OVERLAY_SUGGEST_MAX_WIDTH_FT` — the same guard that already rules out the OPPOSITE historical failure, a scale implying a plan miles wide, B850432/NEW-2). The drop handler now only ever produces a bare `{lat, lng}` drop point, never a fake placement of its own.
  2. `SitePlansSection.jsx`'s `confirmPage` now ALWAYS calls `suggestPlacement(f.rasterW, f.rasterH, f.dropPlacement)` — the drop point (when present) is a center override merged into a full placement, never used standalone. Every future upload — dropped or picked — is therefore either fully placed (all three fields, always drawable) or fully unplaced (all three null, the honest "not placed yet" state) — never the half-written state that produced this bug.
  3. `confirmPage` only arms `onActivateOverlay` when `overlayPlaced(overlay)` is actually true — the rare case where `suggestPlacement` itself can't run (the map genuinely isn't ready) now leaves the row honestly "Not placed yet" rather than "Editing on map" over nothing; its own "Place on map" button already self-heals via the existing `onActivate` handler.
  4. **Belt-and-suspenders, closing the general class rather than just this one path:** the row list itself now computes `isActive={activeOverlayId === o.id && overlayPlaced(o)}` — "Editing on map" can never render for a row with nothing real on the map to edit, whatever path set `activeOverlayId`. This is also the fix for the reported copy contradiction ("Not placed yet" + "Editing on map" + 100% opacity all showing at once) — the three can no longer disagree, because the middle one can no longer be true while the first is.
