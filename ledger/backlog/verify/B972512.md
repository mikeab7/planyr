`[x]` **DECIDED: DROP the column, not default it — and the decision is forced by what the code actually does today, not a guess.** Read every call site before deciding: an overlay is created in exactly ONE place (`SitePlansSection.jsx`'s upload flow), which always calls `fileNewReview` to create a BRAND NEW `doc_reviews` row in the SAME act as the overlay insert — so the review's owner is, by construction, always identical to the overlay's own `user_id`. The "pick a page from an already-filed document" flow that WOULD make the two differ is B948496's own flagged gap #2, still not built. `review_user_id` was also never part of any FK (`site_plan_overlays.sql`'s own AUDIT-FIRST note: `review_id` alone is sufficient, since `doc_reviews.id` is globally unique in production) and never READ anywhere in the app — grepped the whole tree, zero reads. A column that can only ever duplicate `user_id`, is never queried through, and is never displayed is not information worth a NOT NULL constraint; it is redundancy that broke the first real write. If "pick an existing document" ever ships, the right question then is "who may SEE this review" — a join through `doc_reviews.user_id`/team, the same shape every other cross-table visibility check in this repo already takes — never a second denormalized owner id carried on this table.

- **THE STANDING RULE, closed for this save path AND every future one, not just this one column — `shared/sitePlans/lib/overlayErrors.js` (new), `friendlySaveError(error)`.** He should never see `"violates not-null constraint"` again, from any cause, not only the one that happened to break this week. The function maps the common Postgres/PostgREST error shapes (23502 not-null, 23503 foreign key, 23505 unique/duplicate, 23514 check constraint, 42501 row-level-security/permission, a PGRST204/schema-cache miss, a bare network failure) to a plain sentence in his language, and — the part that keeps it from being a lossy translator — passes an already-hand-written `Error` (e.g. `"Couldn't upload the brochure."`) through UNCHANGED rather than flattening it to something generic: the distinguisher is that a genuine Postgres/PostgREST error always carries a `.code` (a 5-char SQLSTATE or a `PGRST…` code) or reads as SQL-technical text, and a hand-written one has neither. Wired into every save/delete path in the panel that was silently swallowing its own error return before this — not just the one `confirmPage` catch that produced the reported message: `patchAndReload` (rename/opacity/visible toggle) and `remove` (delete) both used to discard `updateOverlay`/`deleteOverlay`'s `{error}` entirely and reload anyway, a "saved ✓ that didn't save" by omission (LOUD-FAILURE's own named class); the live drag-commit handler (`commitPlacementRef`) had the same gap — a failed placement save would leave the map showing a moved plan that was never actually written, silently reverting on the next reload with no explanation. All four now surface a translated message in a small dismissible panel banner (or the flow's own inline error, for the upload/change-page steps) and log the raw error to the console for us, never to him.
