- **⛔ NEW-2(c), 2026-09-05 — a THIRD, separate report on top of NEW-2(b): "I click Map, and it takes me out to the map for a split second before returning me straight to the Goose Creek site." The report's own hypothesis — "very likely the same lastRoute mechanism" — was checked and is WRONG; this is a DIFFERENT mechanism, found by tracing the real code rather than assuming the hypothesis.** `lastRoute` is only ever READ once, at true cold boot, via `seedBootRoute` (module scope, before first render) — it cannot cause a same-session, no-reload bounce-back with no page load in between at all. Both `currentSite` (NEW-2a) and `lastRoute` (NEW-2b) are correctly cleared by `leaveProject`/`goMap` before this bounce is even possible.
  - **Root cause: a STALE CLOSURE in `SitePlannerApp.jsx`'s `onAuthChange` subscription.** That subscription is created exactly ONCE (`useEffect(() => {...}, [])` — correct on its own; re-subscribing every render would be its own bug), so the `applyUser` function it captured at subscribe time is FROZEN for the entire life of the mount — not briefly stale, permanently stale. `applyUser`'s own resume logic (`resumeTargetAfterSignIn`, `lib/bootResume.js`) reads `resumeAllowed`, a prop Shell recomputes as `false` the instant the routed project actually clears — but the frozen closure never sees that recomputation; it keeps reasoning as though the tab is still sitting on its original boot route. So clicking Map correctly navigates away, and then ANY later auth event on the subscription's original frozen logic — a still-in-flight `pullCloud` resolving, a token refresh, literally hours later — reads the stale `resumeAllowed === true` a boot-time deep link produced and re-opens the very project the user just left. This explains the "split second" shape precisely: the map renders correctly, then the stale-closure auth event fires shortly after and silently pulls the user back.
  - **Fix: `applyUserRef`, the standard pattern for a subscription that must stay subscribed once but must always run the LATEST render's logic** — kept in sync every render (`const applyUserRef = useRef(applyUser); applyUserRef.current = applyUser;`, the same idiom the pre-existing `projectIdRef` above it already uses), called at CALL time (`applyUserRef.current(u, event)`) rather than closed over at SUBSCRIBE time. The subscription itself is untouched — still exactly one `useEffect(..., [])`, still one `onAuthChange` call.
  - **Proven with a SOURCE-guard test, not a runtime one** (`test/authSubscriptionFreshClosure.test.js`, new, 4 tests) — this repo's vitest config has no jsdom/component-render environment (Node-only, pure-logic tests), so a stale-closure defect, being fundamentally about React's runtime hook behavior, cannot be reproduced by a pure-function test the way NEW-2(a)/(b) could. Tests assert: `applyUserRef` is kept in sync every render; the subscription callback invokes `applyUserRef.current(u, event)`, never the bare `applyUser` identifier; the subscription still has empty deps (never turned into a re-subscribe-every-render bug); a mutation check (reverting to the bare `applyUser(u, event)` call fails the guard). **Red-proofed**: stashed the fix and reran — the "never the bare applyUser" assertion failed exactly as expected (found the pre-fix direct call); restored, reran — 4/4 green.
