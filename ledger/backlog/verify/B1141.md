- **Report.** *"Sometimes when I place points — for a measurement or drawing something — it seems like my pointer is off … five, ten, fifteen feet off from where I'm actually clicking."* Measured live the same night against the Esri tile grid (each tile's z/x/y is in its URL and its screen rect is readable, so the true lat/lng of any screen pixel is computable without trusting Leaflet or us): **+3.67 ft N / −0.57 ft E at z18 (sd 0.09), +1.54 ft N / −4.36 ft E at z17** — about one CSS pixel, extremely repeatable, direction changing between zooms. A clean OFFSET, not noise and not a scale error. The reporting machine runs `devicePixelRatio` 2.15.
- **AUDIT-FIRST, all four lines the owner asked for, answered against the code:**
  - **(a) fractional devicePixelRatio — RULED OUT as the cause.** Nothing in the screen↔feet↔lat/lng chain rounds: `shared/viewport/viewportTransform.js` (`worldToScreen`/`screenToWorld`) has no `Math.round`/`floor`/`|0` at all, and `mapLock`'s projection has none either. `retinaForZoom` / `detectRetina` only choose tile size and zoom offset — they never touch the pointer chain, so this is **not** a B170-class defect. A fractional ratio still MATTERS, but indirectly: it makes fractional layout widths the norm, which is what (b) trips over.
  - **(b) container origin — one real contributor, and it is OURS.** `p2f` re-reads `getBoundingClientRect()` on every call, so there is no stale origin and no border/padding error. But the planner asks Leaflet to centre on the feet point under the DRAWING's centre (`size.w / 2`, a float off `getBoundingClientRect`) while `commit` lands that centre at the MAP's own half-size, which comes from the integer `clientWidth`. On a fractional CSS width those halves differ by up to a quarter pixel per axis. Leaflet's own whole-pixel snap (`_getNewPixelOrigin` ends in `._round()`, `panBy` rounds its offset) adds up to half a pixel more, twice over. Together: about one pixel per axis — exactly what was measured.
  - **(c) hover vs click — they ALREADY share one path, now proven rather than assumed.** Both funnel through `p2f`: the readout via `cursor` → `cursorLL`, every placement via `p2f(e.clientX, e.clientY)`. There was no second conversion to delete. The harness now measures BOTH ends independently anyway, because "the readout is right" was never proof that a placed point is.
  - **(d) snap/grid quantisation — a real, separate finding, filed as B1143.** Grid snap is OFF by default (`gridSize: 10, snap: false`) and is a deliberate opt-in. The boundary magnet is not: it fired unbounded in feet. See B1143.
- **THE FIX — weld the DRAWING to wherever the basemap actually landed, in the render only.** `mapLock.js` gains `tileNwFeet` / `basemapWrapPoint` / `registrationShift` / `sanitizeShift`; `SitePlanner` measures the residual after each of the three paths that can move the basemap (a resize/container commit, a gesture transform, a settle commit) and applies it as a CSS translate on the SVG canvas. Because `p2f` derives the cursor from that element's own bounding box, **the one transform corrects the render, the readout and every placed point together** — no second conversion to keep in step. `view.offX/offY` are NOT touched: the exactly-reversible pan V478 proved is preserved (`diagnose-map-lock` still returns **0.0000 px** on a pure-pan round trip), nothing accumulates, and the aerial is never resampled.
- **The reference point is the TILE LATTICE, not `map.project`** — and that distinction is worth a paragraph, because it is the difference between 0.29 px and 0.000. Leaflet places the raster lattice from a per-level origin it rounds SEPARATELY from the map's pixel origin, so at a fractional zoom (every wheel gesture leaves one) the tiles and the projection disagree by a sub-pixel amount multiplied by the level's scale factor. The user's reference is what they are LOOKING AT, so registration is measured against a real tile's rendered rect versus its own z/x/y — no Leaflet internals, and the rect already includes the live gesture transform, so one formula serves the gesture and settled branches alike. When no tile is on screen (aerial off, or none arrived yet) it falls back to the map's projection, which is the frame every Leaflet VECTOR overlay is placed in.
- **What B1062 got right, and the one thing it missed.** B1062 measured this residual correctly and adjudicated it as Leaflet's floor, deliberately uncompensated, on the grounds that the only two remedies were (i) a fractional transform on the tile wrap — which resamples, i.e. softens, the aerial (forbidden by B1049/V483) — or (ii) nudging the drawing's view offsets, which would destroy the reversible pan. **Both objections stand; there is a third option it did not consider:** a render-only translate on the SVG, which softens nothing (vector, re-rendered not resampled), leaves `view` pristine, and self-corrects the pointer path for free. It also did not identify contributor (b) as ours. B1062's committed bound stays exactly as it is — it is now a ceiling nothing reaches.
- **LOUD-FAILURE.** A shift past the quantisation range is a MODEL disagreement (a scale mismatch, a stale container size, a half-applied gesture transform), not something to paper over by shoving the drawing sideways: `sanitizeShift` refuses it, applies nothing, and reports `map-registration-out-of-range` with the measured delta. That guard earned its keep during this very session — it is what surfaced B1142.
- **PDF-PARITY, stated rather than skipped.** The shift is deliberately NOT mirrored into the export. It compensates a LIVE-DOM artefact of Leaflet's integer map pane; the sheet composes its own tile mosaic from `view` with no such quantisation, so copying it there would ADD the error it removes on screen. Confirmed by code: `exportSheet.js` / `printSheet.js` never serialise the live SVG, and the shift lives only in that element's inline style.
- **THE COMMITTED HARNESS — `ui-audit/diagnose-pointer-accuracy.mjs`** (the owner asked for it re-runnable, so it is). Ground truth from the tile grid; measures the READOUT path (pointer moved to a pixel, raw lat/lng read back through the `__PLANYR_E2E` probe) **and** the PLACEMENT path (a real two-click Length measurement, checking where its first vertex LANDED) at zoom 16/17/18 × device pixel ratio 1 / 2 / **2.15** plus a deliberately fractional canvas width, on a 60-element plan so culling actually varies the container. Residual reported in CSS px **and in feet at each zoom**, so the overview-zoom case is explicit. **Result: ✓ 120 of 120 readings within 0.25 px — every readout exactly 0.000 ft.** Two design details that keep it honest: the placement round is RETRIED when the frame re-registers mid-gesture (that reading measures nothing), and its click point is chosen in FEET on bare canvas clear of the boundary magnet, because the magnet is a feature and would otherwise be misreported as a transform error.
- **TEETH, measured both ways.** Every case prints the compensation actually applied — 0.07 to 0.77 px, i.e. up to **5.3 ft** at an overview zoom. With the compensation disabled and rebuilt, the harness reports a CONSTANT offset identical at all four spread probes (0.49 px / −2.11 ft E / +3.34 ft N at zoom 16), reproducing the owner's live finding — including its repeatability and its change of direction between zooms — and failing 20 of 60 readings.
