- **Plain-English cause (for the owner):** a "header row" is only a style — grey shade + bold-looking text — not real bold, so the B button, the font controls and everything else read "normal" on a row that LOOKS bold. And the only control, "Header", is wired by the table library to ROW 1 ONLY (`toggleHeader("row")` has `top: 0, bottom: 1` hard-coded), so a header row anywhere else could never be switched off from the toolbar. The brief's guess that Row ↑/↓ "copies header-ness into the new row" was **measured and is NOT what happens** (matrix in `test/notesTableFill.test.js`: Row ↑ and Row ↓ beside a first / middle / last header row all insert a PLAIN row). What actually happens is the header row gets **pushed down**: header on row 1, then Row ↑ (a plain row appears above it) — the same header row is now row 2. That is Michael's table. The one case where a new row IS header is between two header rows (it joins the header block — correct, kept).
- **Fix:** `lib/notesTableFill.js` — `toggleHeaderRows` acts on the caret's row(s) (or the selected cells' rows); the toolbar button is now **"Header row"** and shows pressed when the caret row is a header row (`headerRowsState`); un-headering keeps a header COLUMN's heading cell; merged / row-spanning cells convert whole. `boldTruth` + `selectionInHeaderCells` make **Bold read lit inside a header cell** (header text is bold by style); its tooltip reads "Bold (header row: use Header row to change)" and a click there adds no pointless bold mark. The right-click menu on a table cell carries **Header row** (checked when on) too. Same for the right-click mini-toolbar's B.
- **Sandbox-verified:** `test/notesTableFill.test.js` (31, mutation-proven: toggling only row 0 turns 4 red); `ui-audit/verify-notes-table-fill.mjs` (60 checks, real clicks/keys, judged on the stored doc + computed style, with a known-good arm) — **11 ✗ on the pre-fix build, 0 ✗ on this branch** (red-proof, same harness, base build served on a second port).
