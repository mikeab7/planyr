**ROOT CAUSE.** esri-leaflet's `RasterLayer` (`_renderImage`, esri-leaflet 3.0.19 — the library backing the statewide TxGIO composite's `/export` image overlay) fades a fresh image in from opacity 0 to visible **only if the map's bounds at the moment the image finishes loading exactly equal the bounds it was requested for**. If the LAYER ITSELF is removed (`map.removeLayer(fl)`) while that request is still in flight, the freshly-created `<img>` is orphaned: esri-leaflet adds it straight to the map, bypassing the layer's own tracked `_currentImage`, so the layer's `onRemove` cleanup never sees it — it sits fully loaded, correctly positioned, and stuck at opacity 0 **forever**. The layer's own `"load"` event still fires afterward (Leaflet's `Evented` listeners survive removal from the map), which is why the county-slow notice logic kept working correctly while the picture itself stayed invisible — two independent mechanisms, only one of them broken.

**THE SPECIFIC TRIGGER, confirmed live via `ui-audit/verify-parcel-outline-opacity.mjs` (an unguarded diagnostic run first proved the mechanism, then a teeth-proven guard replaced it):** Waller County's `layerUrl` (`counties.js`) is the exact same URL as the statewide TxGIO composite (it has no CAD of its own), so whichever of the two keys' `addDisplay` calls reaches that URL first — an accident of async `resolveLayerUrl` settle order — becomes its "owner" in `MapFinder.jsx`'s dedupe-by-URL bookkeeping (`NEW-2(a)`, B?). Entering Select-parcels mode unconditionally warms Waller's Drive parcel-snapshot cache (`ensureSnapshot`, independent of anything Brazoria/Rosharon-related); when that snapshot loads, `showSnapshotDisplay('waller')` swaps Waller onto its own vector layer via `removeDisplay('waller')` — and the OLD `removeDisplay` unconditionally tore down the SHARED Leaflet layer object whenever Waller happened to be its owner, **even though `txgio_statewide` (covering the rest of the state, including Rosharon) still needed it**. If the shared layer's `/export` was still in flight at that moment — exactly the "slow county" scenario the owner hit — its image is orphaned per the mechanism above.

**THE FIX, two parts, closing the specific trigger AND the general orphan class:**
1. **`MapFinder.jsx`'s `removeDisplay`** no longer destroys a shared/aliased layer just because the key being removed happens to be its "owner": it now checks whether any OTHER key still references the same layer object and, if so, hands ownership to one of them instead of tearing the layer down — the layer keeps running for whoever still needs it. Only the true last reference actually calls `map.removeLayer`.
2. **`src/workspaces/site-planner/lib/parcelOpacityGuard.js`** (new, pure — no Leaflet/DOM import, split out for the same reason `terrainGate.js`/`adminBoundaryData.js`/`floodTileDecode.js` were, so it's Node-unit-testable), wired into `parcelDisplay.js`'s `makeParcelImageLayer` — the ONE place every parcel image layer is built, so both display surfaces (the map's Select-parcels tool and the in-planner "Add parcel → Identify" tool) get it for free. It tracks every image the layer starts and, on teardown, removes any still-pending one still sitting on the map (closing the orphan class generally — not just Waller's specific trigger, since ANY full teardown mid-flight reproduces it: leaving select mode, closing the in-planner identify tool). As defense-in-depth, it also force-shows a `"load"`'d image whenever it's still genuinely correct for the CURRENT view but wasn't raised by esri-leaflet's own (bit-for-bit) equality check — never for an image esri-leaflet had already decided to discard.

**GUARD ADDED, per the dispatch's own ask ("once loaded, its rendered opacity is non-zero"):** `ui-audit/verify-parcel-outline-opacity.mjs`'s branch 2 polls the real DOM every 150ms across the mocked delay and asserts exactly that — a check that only looked at "the image was requested" would have passed throughout the whole outage, which is precisely what let this ship invisible in the first place.
