- Origin: filed 2026-07-30 from the B1188 audit. Fixed 2026-07-30.
- **The audit AGREED with the filing: Review had the same defect, not a different one.** `DocReview.jsx` kept `propsForId` (an id that had to keep matching `sel`) plus `useEffect(() => setPropsForId((cur) => (cur && cur === sel ? cur : null)), [sel])`. So the section's open/closed state was DERIVED from selection and a deselect — a click on empty sheet, a marquee, a page change — closed Properties the user had deliberately opened. Same shape as B1188, different file.
- **The fix mirrors B1188 rather than paralleling it.** `propsOpen` is a plain boolean only an explicit affordance writes: `openMarkupProps` / `closeMarkupProps`, reached from the double-click, a freshly-drawn markup, a new ✕, and Escape. The selection-clearing effect is **DELETED, not rewritten** — there is deliberately no replacement, because any effect keyed on `sel` that writes the open state is the bug. Selection now chooses the BODY only, and with nothing selected the section HOLDS ITS GROUND on a "Nothing selected" state instead of vanishing.
- **Two things the planner's version did not have to answer, decided explicitly here.** (a) The armed-tool **"Tool style"** block shares the same surface; it keeps its own unchanged trigger, because it is about the tool in your hand, not about the inspector — so arming a tool after a deselect still shows its style rather than an empty state. (b) An owner-owned open flag needs an owner-owned CLOSE or it is a one-way door, so Review gains an explicit ✕ (`aria-label="Close properties"`, matching the planner) and Escape closes the section **before** it touches the selection — the same order `SitePlanner` uses, with the markup left selected so a double-click reopens on it.
- **The declaration check was extended to this surface, as the item asked.** The check's shape did allow it: `e2e/clickContract.table.js` gains `REVIEW_CLICK_CONTRACT` (18 markup tools, each declaring that a double-click opens the inspector and which ones split to in-place text editing) plus `REVIEW_NON_MARKUP_TOOLS` (the five modes that draw nothing selectable, declared so "deliberately no contract" is distinguishable from "somebody forgot a row"). `test/clickContract.test.js` reads Review's own shipped `TOOLS` registry and **fails the build** if a tool is in neither list — so a new markup type cannot ship with an undeclared click behaviour, exactly as for the planner's registries.
- **One guard-quality fix made in passing:** the new source assertions strip comments before matching. These files document the shapes they removed — quoting `setPropsForId(...)` in a comment is how a reader learns what not to reintroduce — and a naive string check trips on its own documentation. Verified the guard still goes RED by reintroducing a selection-derived close and watching it fail, then restoring.
- **Verified here — a real browser, logged out, no blocker left.** New `e2e/review-click-contract.spec.js` drives the actual Review workspace with a locally dropped PDF (client-side pdf.js, no auth, no network) and asserts the whole contract: a freshly drawn markup opens its properties · a deselect leaves the section open on "Nothing selected" · selecting a markup swaps the CONTENTS of the still-open section · a drag on empty sheet (which pans) does not close it · ✕ closes · a double-click reopens · Escape closes · it reopens after that too. **Proven RED on the pre-fix `DocReview.jsx` (both cases fail) and green on the fix.** Because `property-panel` is shared with the tool-style block, the spec asserts against a new `data-props-mode` seam that names the three states apart (markup / tool / empty) rather than inferring state from header text.
