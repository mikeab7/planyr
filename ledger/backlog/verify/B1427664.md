**ROOT CAUSE, traced through the actual code — three defects, each hiding the next.**
1. **The reported gap is real and is exactly what it looks like.** `handleClick` resolves a parcel via `identifyParcelEager` — a single fast POINT query per candidate source. The DISPLAY (the purple outlines) is a separate layer that queries or rasters the WHOLE VIEWPORT, which is inherently slower, and for the statewide TxGIO composite specifically the hang-guard (`markDown`) deliberately NEVER pulls it (removing the one universal fallback would leave nothing to see or click) — so it has no timeout at all and can sit silently slow forever with zero feedback. Bowie/Texarkana has no county CAD, so its ONLY source is that statewide composite: worst case of the gap, and the one the owner hit.
2. **The statewide display's own existing "it's slow" banner was ALREADY DEAD CODE, silently, before this item.** `makeParcelDisplayLayer` draws a query-disabled composite (TxGIO today) as an esri-leaflet RASTER layer (`EL.dynamicMapLayer` with `f:"image"`), not the vector `FeatureLayer` every queryable CAD uses — verified against esri-leaflet's own source (`RasterLayer.js`/`DynamicMapLayer.js`): the raster layer's `f:"image"` branch calls `_renderImage` directly, bypassing the `Service`-based request entirely, so it fires `"loading"` → `"load"`/`"error"`, and NEVER `"requeststart"`/`"requestsuccess"`/`"requesterror"`. `addDisplay`'s pre-existing `fl.on("requesterror", …)` handler for the statewide branch was listening for an event that literal could never fire on this layer type — so the "Statewide parcel outlines are slow right now" banner has never once shown, for any county parked on the composite, since it was written.
3. **A THIRD bug, found only once (1) and (2) were both fixed and a headless proof still came back blank:** `fl.addTo(map)` ran BEFORE any `fl.on(...)` listener was attached, for every branch. `onAdd` (fired synchronously inside `addTo`) is what actually kicks off a layer's first request — a vector `FeatureLayer`'s metadata fetch fires its first `"requeststart"` synchronously inside `onAdd`, and a raster layer's `onAdd` fires its first `"loading"` the same way — so a listener attached AFTER `addTo` missed that very first event and only caught a SECOND cycle, which never comes unless the map is panned again. Reproduced live in this item's own harness: with `addTo` first, the "still loading" notice never armed at all for a view that was never touched again after turning on Select — exactly the reported case (fly to a site, turn on Select parcels, do nothing else).

**THE FIX.** Does NOT make clicks wait for the slower half — the brief was explicit that selection working early is the good half and must not slow down to match the slow half; keeps `identifyParcelEager` exactly as-is. Instead it tells the truth about what's happening, reusing a mechanism the map already has:
- `slowDisplayKeys` (`MapFinder.jsx`, new state) names any display layer whose request has been outstanding past `SLOW_DISPLAY_NOTICE_MS` (2.5s — long enough that a normal ~2s load never flickers it, per the hang-guard's own comment on how fast a live host answers) with nothing drawn yet. Wired for BOTH lifecycles now that (2) is fixed: `"loading"`/`"load"`/`"error"` for a raster (image-mode) statewide composite, `"requeststart"`/`"load"`/`"requesterror"` for every vector `FeatureLayer` (every real CAD, and any future statewide composite whose `/query` isn't disabled) — decided per-layer via `parcelDisplayIsImageOnly(src)`, never assumed from the `statewide` flag alone.
- The existing "+ Select parcels" guidance tip (the ONE explanation anywhere in the app for how this mode works — already had a line for "below the outline zoom, click still works") gets a THIRD line, in between: past the outline zoom but `slowDisplayKeys.size > 0` → *"Parcel outlines are still loading here — clicking a lot already adds it (＋). Hover an added lot and click to remove it (−)."* No new UI surface, no new banner component — the same slot, the same mechanism, a truer sentence for a case it didn't cover yet.
- **Relevance to the current view is judged by the SAME rule B1164656/B1426592 already established for the outage banner** (`sourceNoticeStillPlausible`), reused via a new `displayNoticeShape(key)` — decided from the KEY'S OWN URL (`isStatewideLayerUrl`), never from `STATEWIDE_KEYS.includes(key)`: `addDisplay`'s existing URL-dedupe means the county key that actually OWNS a shared composite's Leaflet layer (and therefore the one that gets marked slow) is very often a REAL county key parked on it (Waller, on the TxGIO composite), not the pseudo-county `txgio_statewide` key itself — the naive `STATEWIDE_KEYS` check judged plausibility against Waller's own bbox (nowhere near the view the layer is actually covering) and the notice could never arm at all. Reconciled on every `moveend`, same as the outage banner, and reset when leaving Select mode.
- **A statewide-scoped "still loading" notice is deliberately WHOLE-STATE, not bbox**, matching the existing outage banner's own state-wide scope for the identical composite — flying from Texarkana to Houston (still Texas) correctly LEAVES the notice showing, since the same slow TxGIO layer genuinely still covers wherever else in Texas the view lands; only a real state change (or leaving Select mode) clears it.
