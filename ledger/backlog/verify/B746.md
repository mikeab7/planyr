### B746 — Ctrl+Z doesn't always work; make it Bluebeam-style when drawing an element `[Site Planner / Doc Review]` (bug) #site-planner #doc-review #selection #markup #ui #persistence  *(owner-dropped 2026-07-10 from chat; provisional **B745**, renumbered **B746** — concurrent `main` (PR #566) took B745 for the GIS vector/thin-line export split + V257. `[x]` **IMPLEMENTED + unit + headless-e2e verified this session; parks in ⏳ Verify only for the live-only edges below → V258.** Two complaints, one investigation (5-lens adversarial workflow, 15 confirmed root causes RC-1..RC-9): (a) **"Ctrl+Z should work like Bluebeam when drawing"** and (b) **"Ctrl+Z doesn't always work."** The Site Planner's Ctrl+Z always ran a *global* undo — it never stepped back the vertex you were placing — so mid-draw it either did nothing or silently reverted a previously-finished shape while the half-drawn one stayed on screen. Now, in all three canvases (Site Planner, Review, Stitcher), Ctrl+Z **peels the last placed vertex while a multi-point draft is in progress and only falls through to a global undo when no draft is active** (matches Bluebeam + the Review/Stitcher modules, which already did this). Plus a batch of "undo did nothing / undid the wrong thing" reliability fixes.

- **AUDIT-FIRST — 9 code-confirmed root causes (each adversarially verified):**
  - **RC-1 (Bluebeam, primary):** `SitePlanner.jsx` Ctrl+Z called `undo()` directly, never `removeLastVertex()`. Fixed to `else if (!removeLastVertex()) undo();` (mirrors `DocReview.jsx` / `Stitcher.jsx`).
  - **RC-2:** `applySnapshot` didn't clear in-progress drafts → a redo/undo could leave phantom draft points floating over reverted geometry. Now nulls every draft (mirrors the siblings).
  - **RC-3:** `removeLastVertex` had no branch for the parcel-edge easement run (`easeEdges`) or the ditch cross-section point (`xsecPts`), and `xsecMode/xsecPts` were missing from the keydown deps → stale closure. Added both branches + deps.
  - **RC-4:** Split tool double-destruction (Ctrl+Z discarded the whole cut path AND reverted a prior action) — falls out for free once RC-1 lands (mid-split Ctrl+Z now peels one cut point). Verified gone.
  - **RC-5:** Edits that recorded NO undo frame — element fill-opacity slider, underlay opacity slider, sheet-overlay opacity slider + %-box, and **Remove aerial underlay**. Now each records exactly one frame.
  - **RC-6:** Standards / type-style edits called `pushHistory()` but `settings` isn't in the snapshot → a **dead frame** that misdirected the next Ctrl+Z into deleting a prior shape. Removed those pushes (Standards are prefs, non-undoable like the 20+ sibling settings fields) — no more misdirection.
  - **RC-7:** Markup fill-opacity slider *flooded* history (one frame per `onChange`) → ~20 Ctrl+Z to undo one drag. All opacity sliders now share one `sliderHistory` coalescing helper (one frame per drag).
  - **RC-8:** Sheet-overlay position was `Math.round`ed in `histKey`, so a sub-foot (zoomed-in) nudge was dedup'd away as a no-op and skipped by undo. Removed the rounding (underlay position never was).
  - **RC-9:** The keydown input-guard diverged — Review/Stitcher skipped only INPUT/TEXTAREA, so a focused `<select>`'s Ctrl+Z hit the canvas. Added SELECT/contentEditable so all three modules gate identically.
  - **RC-10 (found LIVE 2026-07-18 via V258 step 3, ×1 recurrence on this item):** the keydown input-guard (`t.tagName === "INPUT" || …`) treated ANY focused `<input>` — including a `type="range"` slider — as "typing" and unconditionally swallowed Ctrl+Z/Ctrl+Y. A range input has no native browser undo to protect, so select a Building → drag its Fill-opacity slider → press Ctrl+Z WITHOUT deselecting first → silently no-op (confirmed live 3× on project "ZZ-THROWAWAY-TEST", `SitePlanner.jsx` Properties panel). The toolbar Undo button and a click-away-then-Ctrl+Z both worked fine, and the reverted value persisted correctly across reload once undone — isolating the bug to the keyboard-dispatch guard, not persistence. Fixed by narrowing the guard: it now lets ONLY the Ctrl/Cmd+Z / +Y chord through when focus is on a `type="range"` input; every other shortcut (arrows, Delete, letter tools) still respects the guard while a slider has focus, since those DO have real native slider behavior or would nudge/delete the still-selected element out from under the user.
