`[x]` **SHIPPED — pins hold their true constant on-screen size THROUGH a zoom animation instead of visibly ballooning then snapping at the end, with a measured, budgeted, two-tier graceful degrade.**
- Verify: live — LIVE-VERIFY class (zoom-/data-density-dependent rendering)
- **THE MECHANISM, traced into Leaflet's own source (`leaflet-src.js`'s `Map._animateZoom`/`Renderer._updateTransform`), not guessed.** An animated zoom (wheel, +/-, double-click, pinch) jumps the map's internal model to the FINAL zoom immediately — every pin's screen POSITION is already correct from frame zero. The visible transition is a pure CSS trick: Leaflet sets `transform: translate(...) scale(s)` on the canvas RENDERER'S OWN `<canvas>` element (not the shared map pane) and lets the browser's native `.leaflet-zoom-animated{transition: transform 0.25s ...}` interpolate `s` from the start/end ratio down to 1 over ~250ms. Pins are drawn at a CONSTANT pixel radius (never meant to scale with zoom), so for that whole window the ambient `scale(s)` stretches the already-correctly-drawn bitmap — every pin visibly balloons or shrinks in lockstep with the tiles — then SNAPS back to true size the instant the transition ends and Leaflet's own `_reset()` repaints at scale 1. That snap is the reported "pop."
- **THE FIX.** While `s(t) ≠ 1` — read directly from the canvas's own live `getComputedStyle().transform`, the REAL browser-interpolated value, so this never has to reimplement Leaflet's cubic-bezier easing curve — every marker's drawn radius is set to `trueRadius / s(t)` each animation frame (`CircleMarker.setRadius`, which Leaflet itself batches into ONE actual canvas repaint per frame via its own `_requestRedraw`/rAF coalescing), so the NET on-screen size after the ambient scale is applied stays the TRUE constant radius throughout. Positions are untouched — already correct, and the ambient transform is exactly what smoothly carries them, which was already working as intended; only the SIZE needed correcting. Restored to the true radius the instant the animation ends (`zoomend`, plus the loop's own natural exit on every path), so nothing is ever left scaled.
- **PERF BUDGET, measured against the REAL worst case — 2000 markers (PLACES_QUERY_CAP, `foodStore.js`; the owner's own "roughly 1,000" is in the neighbourhood, the real cap is larger), zoomed PAST `MIN_PIN_ZOOM` (a first pass measured from the map's DEFAULT zoom and got a false-good number — the reference snapshot draws NOTHING below that threshold, so that run was silently timing an empty loop; caught via a `setRadius` call-count proof before it was reported, see the code comment for the full trace).** `.scratch-repro/verify-zoom-scaling-perf.mjs`, real Playwright, real Chromium, the REAL `FoodMap` component with synthetic data (network to Supabase/CARTO is blocked from this sandbox): **median 1.1ms, p95 4.2ms, max 15.8ms, 2/98 sampled frames over the 8ms budget** — comfortably inside budget; before this item, ZERO per-frame JS ran during a Leaflet zoom animation at all (the pop was a pure CSS-transform artifact, not a perf cost), so this is the full added cost, not a regression delta.
- **TWO-TIER GRACEFUL DEGRADE, per gesture only (a fresh gesture always starts at full fidelity — conditions genuinely change, e.g. fewer markers once zoomed in past `MIN_PIN_ZOOM`).** `ZOOM_ANIM_DEGRADE_STREAK` (3) consecutive over-budget frames at full fidelity drops to redrawing every OTHER frame; the same streak still over budget at that tier BAILS entirely (restores true radii immediately, falls back to the old transform-then-settle look) rather than ever dropping frames. Stress-tested at 6x CPU throttle (`.scratch-repro/verify-zoom-scaling-degrade.mjs`, same 2000-marker worst case): individual frames reached 17-25ms, confirming real pressure — but only ~1.75 frames land per gesture at that throttle (Leaflet's own zoom-animation window is a fixed ~250ms regardless of device speed), too few for a 3-frame streak to complete within ONE gesture. Documented honestly rather than papered over: on a genuinely slow device a single heavy gesture may not fully degrade before it ends, but nothing runs away — the next gesture starts fresh, and `restoreTrueRadii()` always leaves every marker at its correct true radius regardless of which tier a gesture ended at.
- **THE DEGRADE DECISION IS A PURE, UNIT-TESTED FUNCTION** (`nextZoomAnimTier`, extracted to its own `lib/zoomAnimTier.js` — a live CPU-throttled proof alone can't fully exercise it, per the ~250ms gesture-window limit above), driven directly with scripted frame-time sequences in `test/foodModule.test.js`: stays at "full" while in budget (and a single in-budget frame resets the streak, so noise never creeps it toward "bailed"); "full"→"everyOther" only after exactly the full streak, never before; "everyOther"→"bailed" the same way; "bailed" is a hard floor for the rest of the gesture.
- **CROSS-FADING THE ZOOM-GATED DATA SWAP, checked and deliberately NOT done this session — said plainly, per the item's own instruction, rather than silently skipped.** The reference-snapshot pins popping in/out at `MIN_PIN_ZOOM` does NOT need a second query (the data is already fetched regardless of the `tooSmall` gate — it's a pure rendering-timing question, not a network one). What it DOES need is the same shape of custom rAF-driven redraw loop as the radius fix above, applied to a boolean state flip instead of Leaflet's own `'zoomanim'` hook — there is no equivalent Leaflet-native event to piggyback on for that trigger, so it would need its own tween state machine and its own separate perf-budget/measurement pass, genuinely feature-sized on its own. Left undone and flagged rather than half-built; a reasonable fast follow-up, not folded into this item to keep this session's already-large scope honest.
