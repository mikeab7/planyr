- **The rule (Excel's, exactly).** From the active cell look at the NEXT cell in the arrow's direction: current AND next both filled → the LAST filled cell of that run; otherwise (current blank, or next blank) → the NEXT filled cell in that direction; none → the edge — first / last TASK row (never the "+ New task" row) for Up / Down, first / last VISIBLE column for Left / Right. All four directions. Ctrl **or Cmd (Meta)**. Pure core `src/workspaces/scheduler/lib/gridCtrlNav.js` (`ctrlJumpIndex` · `gridCtrlArrowTarget` · `gridCellBlank`), mirrored byte-identically into `public/sequence/index.html` beside `stepGridRow` (the page is standalone, it cannot import) with a drift guard in `test/gridCtrlNav.test.js`.
- **Visible order, not data order.** Rows are the flattened visible list (`flatTasksRef`), so a collapsed group's children and a Focus-hidden row are skipped exactly as Excel skips hidden rows; columns are `visibleColIdxs()`, so a hidden column is never a destination or a stepping stone; a cursor parked on a hidden column snaps onto the table toward the key (as the plain arrows do). A selection whose row is hidden or gone is not anchorable: the key is left alone (no preventDefault).
- **"Blank" = the cell draws nothing that carries data** (decided and stated in `gridCtrlNav.js`'s header). A computed / rolled-up value on a SUMMARY row (rolled start / finish / duration / cost, a rolled percent) is a visible value → NON-blank; the ID always is. Placeholders are blank: the Notes "+", the "New task" prompt on an unnamed row, the Meeting column's "—" / "— none —" / "set up…", an empty Owner, and the Status / Health cell of an EXPANDED summary (the grid draws nothing there). Formula columns are blank when they evaluate to nothing. Owners stay optional: a column of blank owners is normal data and nothing flags it (owner constraint #1).
- **Edit mode is untouched.** The branch declines while an input / textarea / select has focus, a contentEditable has focus, or a cell editor is open (`editLiveRef`), so Ctrl+Arrow still moves by word in the text; `preventDefault` runs only once the grid has an anchor to move from (verified live: the editor case reports `defaultPrevented === false`). Alt-combos are left alone.
- **"+ New task"** is a blank row to scan THROUGH and never a destination: Ctrl+Down from the last task row stays; Ctrl+Up from "+ New task" lands on the nearest filled cell above (or row 1).
- **Range selection exists in this grid** (Shift+Arrow → `selRange`), so **Ctrl+Shift+Arrow IS built**: it extends from the range's moving end by the same rule, and plain Ctrl+Arrow afterwards collapses the range and jumps the ANCHOR cell (Excel). The range's far end is not the selection, so the grid's selection-chase doesn't follow it — a new `planar-reveal-cell` event reuses the chase effect's own scroll maths (`revealRowIdx` / `revealColKey`, moved out of the effect VERBATIM and shared) to scroll the far end into view. A plain jump needs no new scroll code: it is a selection change, which the existing chase already follows.
- **Neighbours checked, nothing changed.** Plain arrows, Shift+Arrow, Tab, Enter, F2, type-to-edit all untouched. **Home / End / Ctrl+Home / Ctrl+End are NOT implemented in this grid** (only the browser's native scroll runs, selection unchanged) — stated, **not built here**, per the brief. Split view uses the same `GridView`; checked.
