**THE RULE, restated because it's the whole point.** A row on a dashboard or in a file list is a NAVIGATION control — clicking it means "show me this," never "put this on my computer." A download writes to the user's machine and must sit behind its own explicit action; an honest banner describing an unrequested download is not a substitute for not doing it.

**THE CHOICE, stated plainly.** Three options were on the table for where a non-PDF open lands and how the download is offered:
- (a) route the non-PDF to the Library, focused on that file, with Download one click away;
- (b) stay wherever the click originated and show the file's Library entry inline with an explicit Download control;
- (c) keep the Review destination (today's behavior) but replace the automatic download with an offer.

**Chose (c) for the Review-reachable paths (Dashboard, Library Home, MapFinder's brochure link, the boot-resume deep link) and the FileBrowser-local equivalent of (b) for the Library's own file list.** Every other "can't show this right now" condition `fetchSourceBytes` already handles — signed-out, fetch-failed, a corrupt PDF — lands the user in the same place (Review) with a banner naming why and a button to act (`sourceUnavailableMessage`'s existing states; "Open it from the Library to download the original"). Adding a Download button to that SAME banner, instead of building a new cross-workspace "focus this file in the Library" feature, keeps the fix consistent with the existing pattern and small enough to ship and verify in one session — building a deep-link-and-highlight target in the Library's folder tree/file list is real, separate work with no existing plumbing to reuse. The Library's OWN file list (`FileBrowser.jsx`) is a different case: it never routed through Review at all (see the adjacent-surfaces table), a row click there is squarely "browsing my files" rather than "open this drawing," and most files a project holds may well be non-PDFs — routing every one of those clicks across workspaces into Review would be far more disruptive than option (b)'s local, in-place confirmation. So it keeps its existing destination (nowhere) and gains the explicit consent step in place.

**HOW IT WORKS.** `DocReview.jsx`'s `fetchSourceBytes`, on reaching its non-PDF branch, now holds the already-fetched bytes in a new `nonPdfOffer` state (`{ name, blob }`) instead of clicking a download anchor, and shows the redrop banner with a **Download** button in place of the usual "Re-open file…" button; the button's own `onClick` (`downloadNonPdfOffer`) is the ONE place that creates the object URL and clicks the anchor. `nonPdfOffer` is cleared everywhere `redrop` already resets to `""` (a fresh `loadSingleReview`, `resetSingle`), so a stale offer can never survive onto an unrelated banner message or a newly opened document. `library/components/FileBrowser.jsx`'s `open()` no longer calls `downloadFile(f)` directly for a non-PDF row — it arms a `pendingDl` confirmation (file name + "isn't a PDF, can't be previewed here" + Download/Cancel) rendered in the same slot as the existing in-flight/error `dlNotice` banner; `downloadFile` itself is untouched and is now reachable only from that button.
