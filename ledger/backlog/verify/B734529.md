- ⛔ **CORRECTION, same day as the original ship (owner measurement) — READ THIS BEFORE the numbered list below, which describes the AS-CORRECTED design.** The first cut of this item's own text (and the code comments) claimed the `navigator.permissions.query` precheck was the defence against the owner's case. The owner then measured it directly on his real, policy-blocked Chrome, on the real deployed app: **`navigator.permissions.query({name:'geolocation'})` reports `'prompt'`, not `'denied'`.** An enterprise policy of this shape (Chrome's `DefaultGeolocationSetting`) blocks the geolocation REQUEST itself, silently — it does not pre-announce through the Permissions API. So the precheck reads his environment as available and a click proceeds exactly like anyone else's, which means the precheck was NEVER what would have fixed his report, and shipping it framed that way would have been a wrong claim standing in the backlog. **Demoted, not removed:** it stays for what it CAN see honestly (an explicit HTTPS/API absence, or a genuine 'denied' from a real per-site browser block — a different case from his) and is documented as such in both `lib/locateMe.js` and `MapFinder.jsx` now. **The actual defence — which was ALREADY built and shipped, just under-credited in the writeup — is items 2 and 4 below**, and a NEW harness arm (`ui-audit/verify-locate-me.mjs`, "THE CORRECTED SCENARIO") proves both together with `permissions.query` genuinely left un-mocked (reporting the real 'prompt', matching his measurement) and `getCurrentPosition` mocked to call back NEITHER way — 30/30 passing, including this arm. The explicit `map.locate()` timeout was also tightened from 12s to **10s** (the watchdog from 14s to 12s) to sit inside the "8-10s" the owner asked for, rather than leaving the original, already-explicit-but-untouched 12s.
- **AUDIT-FIRST — read the shipped control (`MapFinder.jsx`'s "create the map once" effect) before changing anything.** It already had a good, honest timeout message (`locateErrorMessage(3)`, kept verbatim), an already-EXPLICIT (never Infinity) `timeout` on `map.locate()`, and a same-tick in-flight guard (`locatingRef`) — but `map.locate({ setView: true, … })` unconditionally flew the camera and drew a marker for ANY reported accuracy (including a bare desktop IP guess), there was no independent backstop if neither `locationfound` nor `locationerror` ever fired (the browser's own timeout doing nothing for a provider a policy prevents from ever being asked), and there was no `navigator.permissions.query` pre-check for the states it CAN see.
- **Steel-manned, one by one, all in `lib/locateMe.js` (pure, unit-tested) + `MapFinder.jsx` (wiring):**
  1. **PERMISSION_DENIED / enterprise policy, no prompt ever shown.** `locateAvailability()` calls `navigator.permissions.query({name:'geolocation'})` at mount, BEFORE any click — but per the correction above, this catches only a GENUINE 'denied' (a real per-site browser block), not the owner's policy shape, which reports 'prompt'. Where it DOES apply: renders the control muted (opacity only — `btn.style.opacity`, never a hardcoded color, so it survives dark mode) with an anchored tooltip naming the reason, and a click neither spins nor ever calls `getCurrentPosition`; subscribed to the permission's own `change` event so a later-lifted block re-enables the control live, no reload.
  2. **⛔ THE ACTUAL DEFENCE — the prompt is ignored / the environment silently never resolves.** Two parts, both required: (a) `map.locate()` is now called with an EXPLICIT `timeout: 10000` (never the PositionOptions default of Infinity — an infinite timeout on a request that never resolves IS the permanent-spinner bug); (b) an INDEPENDENT wall-clock `setTimeout` watchdog (12s, a 2s margin past (a)) that fires on its own regardless of whether `navigator.geolocation` invokes EITHER callback — because a policy-blocked provider is free to invoke neither, which is exactly what makes (a) alone insufficient. Both force-stop the spinner and show the honest timeout message. Proven together, with `permissions.query` genuinely reporting 'prompt' (nothing mocked), by the new "THE CORRECTED SCENARIO" harness arm.
  3. **POSITION_UNAVAILABLE (code 2).** Already covered by the existing `locateErrorMessage` fallback sentence; unchanged, still reachable, still non-empty.
  4. **TIMEOUT (code 3).** Kept, tightened to 10s, and now PROVABLY cannot leave the spinner running even when the browser's OWN timeout mechanism does nothing (item 2's watchdog is the backstop for exactly that).
  5. **Insecure context / (6) a Permissions-Policy header or an iframe without `allow="geolocation"`.** `locateAvailability` checks `window.isSecureContext` first (wins over every other signal); a Permissions-Policy violation is handled at the reactive layer — the whole `map.locate()` call is wrapped in try/catch (a synchronous throw is treated exactly like a failed attempt) and a `permissions.query()` rejection is caught and silently falls back to the reactive path rather than being treated as a hard dependency.
  7. **A successful result that is garbage (20-50 km IP accuracy).** New `isAccuracyUsable()` / `ACCURACY_USABLE_THRESHOLD_M` (15 km — above ordinary Wi-Fi/cellular positioning, below a bare IP-lookup's range): `setView:true` was REMOVED from the `map.locate()` call entirely; the `locationfound` handler now decides for itself, so a fix beyond the threshold moves NOTHING and draws NOTHING — treated as a failure with an honest `garbageAccuracyMessage()` naming the accuracy and calling it what it is ("a rough network guess, not a real location"), never a multi-mile circle over half a county.
  8. **`maximumAge` returning an hours-old cached fix.** `maximumAge: 0` is now passed explicitly (Leaflet's own default, made a stated fact rather than an implicit one).
  9. **Far from every saved site.** Flying there is still correct (STEEL-MAN's own framing) — but a "◂ Back to your sites" action now appears in the app's standard bottom-left banner slot whenever the fix lands more than the SAME 50-mile market radius `landingView.js` already uses (`CLUSTER_RADIUS_MI`) from the user's own sites, re-running the exact derived landing view a fresh page open would use.
  10. **Repeated/concurrent clicks** and **(xi) no way to cancel.** Solved together: a 2nd click while a fix is in flight now CANCELS it (`map.stopLocate()` + immediate reset to idle) rather than being a no-op or racing a 2nd request; both async handlers check `locatingRef.current` first, so a late result from a cancelled or watchdog-timed-out request is silently ignored instead of reviving the UI.
  12. **Control state after an error.** Every exit from "locating" — found, error, cancel, watchdog — funnels through one `stopLocating()`, so retry always works; proven for all four paths headless, INCLUDING a fresh click actually re-spinning right after a corrected-scenario timeout (the "retry works" arm).
  13. **`watchPosition`.** Confirmed by source sweep: not used anywhere in this codebase (only the one-shot `getCurrentPosition` via Leaflet's `map.locate()`) — nothing to clear.
  - Aria-label and tooltip: confirmed always present (idle: "Find my location"; blocked: the reason appended), including on the muted state.
