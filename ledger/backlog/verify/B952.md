- **Decision:** option (b) — KEEP them independent (a Library holds many NON-spatial docs — title commitments, MEP sets — that must never auto-splat onto the map; auto-creating a map overlay from every Library upload would be wrong), and make the separation CLEAR so a user isn't surprised. NOT option (a) (a bidirectional link + cascade), which contradicts the product model (Library = documents; Overlays = deliberately-dropped map backdrops).
- **What shipped:** (1) a plain-English note in the Site Planner Overlays panel, shown whenever there are overlays: *"Map overlays are managed here, separate from your Library documents — deleting a Library file won't remove an overlay from the map, and adding a Library file won't add one."* (2) a regression GUARD (`test/libraryOverlayIndependence.test.js`) that reads the real filing sources off disk and fails if the Library filing pipeline (`FileBrowser` + `reviewStore`/`autofiling`/`fileIndex`) ever references the overlay creator (`addOverlayFile`) / the overlay model field (`setSheetOverlays`) / imports SitePlanner or the overlay-storage helper — locking in the independence so a future refactor can't silently re-introduce the surprise.
