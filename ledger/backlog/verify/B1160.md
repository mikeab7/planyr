`[ ]` **⏳ IMPLEMENTED — V539 PENDING.** Nine offscreen-canvas sites now hand their pixels back at the point of last read.
- Verify: live
- Origin: filed 2026-07-30 from chat
- **Finding.** `canvas.width = canvas.height = 0` appeared **zero times** in the entire tree. Every offscreen canvas was left to the garbage collector — and a canvas's pixel buffer is not ordinary JS memory: it lives in the renderer/GPU allocator, outside the JS heap, and the GC tracks it poorly. A few hundred bytes of JS object can hold tens of megabytes of external pixels alive with no pressure to collect them. That is exactly the owner's signature: **~555 MB of tab memory against a JS heap that peaked at ~134 MB.** A heap snapshot cannot see this half, which is why "not a leak, steady-state high" was an honest reading of an instrument that was looking in the wrong place.
- **Behaviourally inert by construction.** The release goes AFTER the last read — after the `toDataURL` / `toBlob` / `getImageData` / copying `drawImage` that has already taken the pixels. Nothing downstream reads the canvas again.
- **Sites, worst first:** `doc-review/lib/pdf.js` `renderInto` (called from `renderDetail` on a 140 ms leading-edge throttle **during a continuous pan**, so a minute of panning was allocating hundreds of full-density buffers — released on the blit AND on the superseded-frame bail) · `site-planner/lib/overlayPdf.js` `renderPageCanvas`, both callers (up to `MAX_RERASTER_DIM` square — an 8192×5500 RGBA buffer is roughly 180 MB, and it re-renders on every zoom-band change per PDF overlay) · `exportSheet.js` ×3 (the stitched aerial, the PNG sheet, the print-DPI PDF sheet) · `dxf/dxfOverlay.js` · `doc-review/lib/pdf.js` page-to-image and page-to-ImageData · `mitigationHeatmap.js` · `image.js`.
- **The one that is released somewhere else, on purpose:** `renderPageToOcrCanvas` HANDS its canvas to the caller, so it must not release it. The OCR runner does, in a `finally`, so a recogniser failure cannot leak it either. Releasing a canvas you have handed out is the way to get this wrong.
- **Deliberately DUPLICATED rather than shared.** `releaseCanvas` exists once per workspace (`site-planner/lib/` and `doc-review/lib/`, byte-identical, each pointing at the other). A single module under `src/shared/` is reachable from both routes, which makes Rollup hoist it into a chunk of its own — measured: `siteRouteChunks` 7 → 8, a real budget breach for four lines of code. The budget was right and the module moved; the ceiling was not raised.
- **The number this is aimed at needs Chrome's own instruments on a real session** — per-tab memory in the Task Manager across a 60 s continuous pan in Review, and `performance.measureUserAgentSpecificMemory()`, which breaks Canvas out as its own type. That is V539, and it is the point of the item.
