- **AUDIT-FIRST — NOT a `refitChildren` bug; it's `refetchReplace` re-seeding from a STALE fetch.** An Explore pass confirmed bonded RECTANGULAR children (sidewalk/paving/parking/dock stack) already track a resize via `refitChildren`→`fitKid`/`relayoutSide`. The real cause is the same stale-seed root as B759: `refetchReplace` (SitePlanner.jsx, fires on every socket (re)join / tab-wake / 4s fallback) `await`s `fetchElements` then `eng.seed(rows)` + `replace(setEls, merged)`. When that fetch's snapshot PREDATES a batch this tab just committed (resize → the building AND its bonded children commit as one batch), the seed rolls the shadow's revs BACKWARD and the rebuild puts the PRE-resize child positions back on the canvas — the building keeps its new size (already on canvas) but a bonded piece snaps back = "separating". `foldNeverSyncedLocal` only covers ZERO-row elements and `foldJournal` is cleared once a commit succeeds, so a committed-then-refetched element was protected by neither. (B759's toast fix suppresses the matching false toast and heals via the echo IF it arrives after the stale replace — but the revert itself needed closing.)
- **The fix (new pure `reconcileSeedRows` in `lib/elementRows.js` + 3-line wiring in `refetchReplace`):** before seeding, replace any fetched row THIS tab's shadow holds a STRICTLY NEWER rev for with our committed data+rev+z (read `eng.shadowSnapshot()` BEFORE `seed` clears it; feed the SAME reconciled rows to `seed` AND `rowsToModel` so shadow and canvas stay in lockstep). Everything else passes through: a foreign-advanced or caught-up row stays canonical (a genuinely stale reconnecting tab has LOWER shadow revs than the server → adopts the server rows → V229 #5 stale-tab clobber guard holds), and a tombstone row is never overridden (TOMBSTONE-DELETES — no resurrection; edit-vs-delete still resolves via the conflict matrix).
