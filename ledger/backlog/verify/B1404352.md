**PART TWO — the breadcrumb never drops the project name.** Second defect from the same click-test: switching Goose Creek to its "TAS Land Sale" schedule made the header read "planyr / Dashboard / TAS Land Sale" — Goose Creek gone entirely. The Scheduler module's breadcrumb shows SCHEDULE names by design (B203/B440 — "the Schedule picker shows SCHEDULE projects... instead of listing the Site Planner's sites"), which was safe only while a project had exactly one schedule; B1080547 broke that assumption on purpose and nothing was updated to match. Fix: `navState.js`'s new `labelMultiScheduleRows` relabels only the rows belonging to a project with **2+** linked schedules — using the `linkedSiteName` each such row already carries — into "Goose Creek / TAS Land Sale"; a schedule still named after its own project (the common single-schedule case, the vast majority of projects) collapses back to the bare name, never "Grand Port / Grand Port". Applied to the list `Scheduler.jsx` hands `AppHeader`'s breadcrumb (not to `ScheduleOwnerList`'s own grouped panel, which already gives context via its heading). This has to relabel the LIST rather than reassign `currentProject.name`: `resolveCurrentName` (projectModel.js) prefers whatever name the list carries for a matching id over `currentProject`'s own `.name`, so a same-string-only fix would have been silently overridden the moment that lookup succeeds — proven by a dedicated unit test reproducing exactly that mechanism.
