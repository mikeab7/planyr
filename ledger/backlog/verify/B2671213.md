### B2671213 — Right-click menu opened a whole menu-height away from the pointer (Add control point out of reach): the shared placement flipped the menu UP on any bottom overflow `[Site Planner / menu]` (bug) #site-planner #ui  *(owner chat block 2026-11-10, NEW-1: "When I right click on a road or any polyline, I'm trying to add a control point, but the right-click menu doesn't start from where I click. My click goes to like the middle of the menu … Add control point should be the slightest mouse movement from where my cursor is." **DEDUPE-FIRST — searched Open / ⏳ Verify / Done across `context menu`, `right-click`, `placeContextMenu`, `contextMenuPlacement`, `Add control point`, `flip`:** no prior item on pointer-distance; B924 is the shared component (it introduced the flip-up to stop bottom rows clipping), B649504/NEW-1 2026-10-22 put Add control point at the top of the road menu — neither covers where the menu opens.)*
`[x]` **SHIPPED.** **Cause, MEASURED (not guessed):** every Site Planner right-click menu (road/element, markup/measure/callout/empty-map, overlay, control-point, parcel) hands the raw `clientX/clientY` to the ONE shared `ContextMenu` (`src/shared/ui/ContextMenu.jsx`), whose pure `placeContextMenu` FLIPPED the whole menu above the pointer the moment it overflowed the bottom by ANY amount. On a 1280×720 window a straight road right-clicked mid-canvas (y≈400) yields a 335-tall menu that overflows by ~25: it opened at y=63 — bottom edge at the pointer, **Add control point 332 px above it** (measured, Chromium). A menu too tall to flip either way clamped to the top margin with the pointer mid-menu. No transform/zoom/centre-on-segment-midpoint cause: positions are the event's clientX/clientY everywhere, the portal is `position: fixed` at body, no `zoom`/scale on any ancestor.
- **Fix, once, in `placeContextMenu`:** on a bottom overflow the menu now SLIDES UP by just the overflow (so the first row stays as near the pointer as the screen allows) and only FLIPS up when sliding would leave the pointer in the menu's lower half (a click hard against the edge — the menu then clears the pointer). A menu that fits in neither direction slides to the bottom margin instead of parking at the top; a menu taller than the viewport still pins to the margin and scrolls. Right edge unchanged (flips to the pointer's left, 2 px gap). Menu contents/order untouched (road: Add control point, then the T).
- **Checked (all share the one primitive, listed in the PR):** road/element `typeMenu`, markup / measurement / callout / easement-label / empty-canvas `mapMenu`, overlay `ovMenu`, control-point `vtxMenu`, parcel `ParcelContextMenu`; also Library folder tree/file browser, Model sheet menus, project breadcrumb row menus (same primitive, so they get the same rule).

Existing `context-menu-viewport`, `road-context-menu`, `pond-context-menu` specs and the whole vitest suite (1479 files) green.
