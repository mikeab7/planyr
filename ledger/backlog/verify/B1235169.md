- **The fix, three layers.** (1) `server/storage/folderMirror.js` gains `purgeProjectDrive({projectId, userId, client, store})` — resolves the project's Drive root (`<uid>/project-<slug>`, the same path every other Drive op in this file uses) ONLY when at least one `project_folders` row was actually mirrored (`driveFolderId` present), trashes it (Drive cascades to every subfolder + filed document), and skips entirely — never calling `folderId()` at all — when the tree was never mirrored, so a never-Drive-touched project can't get an empty folder created just to immediately trash it. A failed index read is LOUD (`ok:false`), matching every other null-store guard in this file. Wired into `functions/api/folders.js` as a new `action:"purge-project"`. (2) `library/lib/folders.js` gains the client half, `purgeProjectFolders(projectId)` — calls the server purge FIRST (while the project's `project_folders` rows still exist for the server to read), then deletes every `project_folders` row for the project **regardless of whether the Drive half succeeded**, reporting a Drive failure honestly (`ok:false`, `error`) rather than silently — the DB rows are never left behind on a network blip. (3) `storage.js`'s `purgeDeletedProject`/`purgeExpiredDeletedProjects` now call this, ONCE PER GROUP (a project is a site GROUP — `project_folders.project_id` is the group id, never a single plan id — so several plans of one group expiring together purge their shared folder tree exactly once, not N times); a folder-purge failure is reported via `reportClientEvent("project-folder-purge-failed", …)` (LOUD-FAILURE) but never fails the `sites` purge that already genuinely happened. `purgeDeletedProject` now takes an explicit `groupId` second argument (`ProjectBreadcrumb.jsx`'s "Delete forever" passes `p.id`, the group id it already has); it defaults to the first purged plan id when omitted, which is correct for a fresh single-plan project (its group anchors on its own first plan's id).
- **The "adjacent case" the brief asked to confirm rather than assume:** `restoreDeletedProject` needs no change — binning never touches `project_folders` (only `sites.deleted_at`), so a restored project's folder tree was never at risk.
