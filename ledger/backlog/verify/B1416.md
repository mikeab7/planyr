- **THE RENAME NO LONGER ENUMERATES PLANS ON THE CLIENT AT ALL.** It used to iterate `loadPlansOfGroup(groupId)` — the LOCAL store — and push each hydrated plan; a plan on a second device, in a fresh browser, or evicted from this one was never written. It now names the GROUP and lets the server touch every row in it: **`rename_site_group`** (`db/rename_site_group.sql`), ONE `update … where coalesce(data->>'groupId', id) = $group` statement, which Postgres applies atomically — so it reaches plans this browser has never loaded and **cannot half-land**.
- **THE GROUP KEY IS `coalesce(data->>'groupId', id)`, NOT the `group_id` COLUMN — and that is load-bearing, not fussiness.** The column is a denormalized mirror that is *known* to drift: the `e2e-fixture-testfit` row's column says `e2e-fixture` while its jsonb says `e2e-fixture-testfit`. Keyed on the column, a fleet-wide split scan reports that fixture pair as a split project and a rename would touch the wrong set; keyed on the jsonb — which is what the client's `groupOf()` reads — it correctly resolves to two different groups. Do not "optimise" this onto the column.
- **SECURITY INVOKER**, so the existing RLS on `public.sites` decides what a caller may rename — no new surface. It touches only `site`, `data`, `version`, `updated_at`: never `team_id` (which would trip the `guard_team_rehome` BEFORE UPDATE trigger and could silently unshare a project), never `user_id`, never `deleted_at`. It returns each row's fresh `version` so the calling tab's CAS tokens stay valid and its next ordinary content push isn't a false stale-version conflict.
- **A DB WITHOUT THE MIGRATION DEGRADES, IT DOES NOT BREAK.** PostgREST answers an unknown function with `PGRST202`; `cloudRenameGroup` then falls back to reading the group's rows **from the server** (never from local storage — that is the whole defect) and rewriting each. Not atomic, but it still reaches every plan, so renaming is never blocked on the migration. **Applied to production 2026-08-04 and used to perform B1417's repair, so the atomic path is the live one.**
- **THE CONFIRMATION IS NOW HONEST.** The old code fired the per-plan pushes with `Promise.all` and did NOT await them, then called `refreshSites()` synchronously — a pull landing in that window rebuilt the list from cloud rows that hadn't been updated yet. `renameSite` now refreshes twice: optimistically (the local half is already written, so the new name paints in the same tick) and again **after the cloud write settles**. A rename that didn't reach the cloud raises a named banner instead of failing silently — which is why the owner only found out by noticing the name had reverted.
- **THE CLOUD WRITE IS LAZILY LOADED** — `lib/cloudRename.js` is reached ONLY by a dynamic `import()` from `renameSiteGroup`, the same pattern as `exportSheet.js` / `rasterIdentifyLazy.js`: a rename is rare and user-initiated, so an RPC call plus a whole un-migrated-DB degrade has no business on the chunk every page load pays for. **⛔ Never static-import it from the boot path.**
- **PERF BUDGET — paid back, and in the end NOT ratcheted.** CI first breached `bundle.totalJsBytes` by 1.6 KB. Measured against `origin/main` 4c76ab5: main alone **4592.9 KB**, this branch **4594.2 KB** → the feature costs **+1.3 KB total**. Three real optimizations shipped WITH the feature rather than a bare baseline raise: the rename's cloud write moved to the lazily-imported `lib/cloudRename.js` (**−1.7 KB off the Site route** — reached only by a dynamic `import()` from `renameSiteGroup`, the `exportSheet.js` pattern), the fallback's three-tier column-degrade ladder collapsed to one `select("id, data")` (the only columns every schema version has), and the inline rename editor de-duplicated into ONE shared module-scope `RenameInput` used by both the row menu and the crumb (**−1.8 KB off the Notes route**, which also renders the breadcrumb). **A ratchet was then made unnecessary by the merge:** B1414 landed on main having hit the SAME ceiling for the same reason and re-recorded the baseline, so this branch's merged build (4606.5 KB) sits inside the band with no raise of its own — this branch's ratchet entry was dropped on the merge rather than stacked on top of it. **⚠ Worth stating because two branches independently tripped it within the hour: the overage is ACCUMULATED DRIFT, owned by B1064, not this feature** — main had already eaten essentially the whole headroom band, so any honest change was going to breach it.
