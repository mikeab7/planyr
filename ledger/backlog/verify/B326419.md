- **THE HOLE THIS CLOSES.** `guard_team_rehome` (B486) let the row OWNER change `team_id` on ANY update. That is right for a deliberate share, but it means a client bug, a stale in-memory model, a replayed cache write or a future refactor could flip an existing private project to shared through an ordinary content save — silently, with the owner's own credentials, and RLS would allow it. Client-side care (B714's INSERT-only rule) is a convenience, never the guarantee.
- **THE FIX.** `guard_team_share` REFUSES any UPDATE that changes `sites.team_id` unless it arrives inside `set_project_team()`, the only thing that sets the transaction-local `planyr.share_intent` flag. Ordinary writes cannot set it (PostgREST sends no `set_config`, and `is_local` stops it leaking on a pooled connection). INSERT is untouched — a brand-new row may be born shared, which is why **"new projects only" is a consequence of the schema rather than a rule the client is trusted to follow.**
