- **THE CAUSE, exactly as the block diagnosed it.** `applySnapshot` ran the layer restore UNCONDITIONALLY on every undo and every redo, and `applyOnOverrides` (`lib/layerPrefs.js`) built `const out = {}` and returned it every call — it carefully preserved each INNER layer state's identity and then threw that away by allocating the map around them. Three effects key off the `overlays` identity: the layer staging/sync effect (whose cleanup clears its intervals and idle callbacks and then re-stages and RE-ADDS the entire Leaflet overlay stack), the coverage recompute, and the persist. So an undo of a plain geometry edit rebuilt every GIS layer on the map.
- **FIXED AT BOTH ENDS, deliberately, because either alone leaves a way back in.** (a) `applyOnOverrides` **and** its `applyAboveOverrides` twin now return the INPUT object when nothing moved — the guard lives with the value, so no caller present or future can trip this by being written carelessly, and React bails out of the setState on its own. (b) `applySnapshot` compares `overridesSig`/`aboveSig` against `prevLayerSig`/`prevAboveSig` (the signatures the persist effect already keeps at "currently accounted for") and skips `setOverlays` / `setLayerOverrides` / `setLayerAbove` entirely on a match, so React is not even asked.
- **⛔ THE INSTRUMENT IS HALF THE ITEM, and without it this defect is unobservable** (DANGEROUS-MEANS-UNOBSERVABLE). The layer SET is byte-identical either side of the bug — the existing `window.__plannerLayers` hook reported `ids` and `on`, both unchanged — so **every check in this repo passes on a build that rebuilds the stack on every Ctrl+Z**. The hook now also reports `identityEpoch`, incremented by the very effect whose deps are `[overlays]`, so "an undo that touched no layer rebuilt no layer" is a NUMBER rather than something a human has to catch out of the corner of their eye. Read-only, same `__PLANYR_E2E` gate, and free (the effect already ran exactly when the identity changed). **MUTATION-PROVEN:** restoring the pre-fix rule takes the epoch from 2 to 4 across two undos and turns that spec red.
- **THE SECOND HALF THE BLOCK ASKED ME TO JUDGE — a still-valid selection now SURVIVES an undo, and it is a deliberate call, not a silent one.** `applySnapshot` did `setSel(null)` unconditionally, so undoing a nudge also closed the Properties panel you were working in — a second thing moving on screen for an edit that only moved geometry. A selection is a POINTER at a feature, and a snapshot that still holds that feature has not invalidated it, so `sel` and `multi` are now FILTERED against the restored collections instead of blanked: a feature the undo deleted drops out, everything else stays put. What is STILL cleared unconditionally, and why: `selVtx` / `splitPath` / `drillId` / `typeMenu` address internal structure (a vertex index, a cut path, a group drill, an open menu) that a restore really can renumber or dissolve. **B743's invariant is stronger, not weaker** — nothing stale can survive a filter that tests membership — and its source guard was REWRITTEN to assert that property rather than the old literal.
