- **THE SETTLE.** Road-to-road tees (`teeJunctionsOf`/`nodeJunction`, `SitePlanner.jsx`/`roadGeometry.js`) are a COMPLETELY SEPARATE code path from road-to-pad tees (`driveJunctionsOf`/`teeGeometry`, the family PR #1743 touched) — confirmed directly, not assumed: `git diff 9164d24 b3be9cf -- src/workspaces/site-planner/lib/roadGeometry.js` touches only `teeGeometry`'s `wedge()` function, and that function's own header states plainly "`teeGeometry` HAS EXACTLY ONE LIVE CALLER (`driveJunctionsOf`)… Road-to-road tees moved to `nodeJunction` after B1011 and never hit this." Byte-for-byte diffed `nodeJunction`, `teeTargetOf` and `roadRunFrom` between the two builds: IDENTICAL. The only other road-geometry change in the 9164d24..b3be9cf range is `e28f97b` (B1690816, `roadNetwork.js`'s `dissolveRings` spike/micro-area cleanup) — read in full; it tightens an already-narrow numerical-noise filter (a turn-angle bound from 100° to 30°, still 5× the real tessellation ceiling, plus a 10 sq ft micro-region floor), and does not touch junction DETECTION at all.
- **THE ACTUAL MECHANISM, found by constructing the two reported configurations directly and running the real pipeline (AUDIT-FIRST) rather than guessing from the correlation.** `teeTargetOf` (`siteGeometry.js`) only ever recognises a road-to-road tee at an EXISTING interior vertex of the through road (`for (let i = 1; i < H.pts.length - 1; i++)`) — deliberately, so a real connect gesture that SPLICES a vertex in (see `roadRunFrom`'s own header) is found reliably. A through road with NO interior vertex there — a plain two-point straight run, or one whose spliced vertex was never created (drawn/dragged into place rather than connected, migrated/imported, or edited after the original connect) — has nothing for that loop to find, however precisely the side road's endpoint lands on it: `teeTargetOf` returns `null`, `teeJunctionsOf` never sees a junction, the two roads are never clustered by `dissolveRings`, and each renders as its own bare, un-unioned rectangle strip — exactly "a plain rectangle simply overlapping the other road, no arcs anywhere." Reproduced directly: a straight 24 ft through road with no interior vertex and a 36 ft side road ending exactly on its line returns `NO HIT` from `teeTargetOf` at any tolerance — on TODAY's code, unrelated to which build measured it.
- **WHY THE TWO LIVE READINGS DIFFER: A CONFIGURATION DIFFERENCE, NOT A REGRESSION**, exactly as the dispatch itself flagged as the other possibility. The 9164d24 oblique-tee measurement worked because that through road carried a real spliced vertex at the tee point; the b3be9cf 36-into-24 measurement failed because that through road did not. Both behaviors are produced by the SAME, unchanged `teeTargetOf` — this is a pre-existing gap that predates both builds, not something PR #1743/#1744 introduced or could have introduced (those PRs never touch this function or its callers).
- **THE FIX** (`teeTargetPointOf`, new export in `siteGeometry.js`) mirrors B1703665 NEW-2's fix for `driveJunctionsOf` exactly (geometric detection replacing a flag/vertex-only requirement): tries the real-vertex rule first (byte-identical to before for every plan that already has one), and only when nothing is found there, projects the side road's endpoint onto the through road's own SEGMENTS, accepting the nearest point within the same `teeCoincideFt` tolerance already used — provided it sits clear of the segment's own endpoints (an endpoint-adjacent hit is either a real vertex, already tried, or a WELD, `weldJunctionsOf`'s job, never this one's, so the two detectors can't double-claim one junction). Returns `{ G, gvi, pts }`, where `pts` is either `G.pts` unchanged (real-vertex case) or a LOCAL, never-stored copy with the projected point spliced in — exactly what a real connect-time splice leaves, so `roadRunFrom`/`nodeJunction`'s existing arm-building code reads it identically either way with no other change needed. `teeJunctionsOf` (`SitePlanner.jsx`) now calls `teeTargetPointOf` and reads `hit.pts` instead of `G.pts` for its `backRun`/`fwdRun` walk — the only two lines that needed to change. `roadJunctionVerticesOf` (the corner-flattening consumer) deliberately still uses the strict, vertex-only `teeTargetOf` — correct, since a virtual (segment-interior) hit has no real bend to flatten.
