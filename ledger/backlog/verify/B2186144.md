DEDUPE-FIRST: not B1121 (map memory growth), B1329 (wheel coalescing), B1046 (per-gesture allocation) or B484/B1344 — those are different costs; B1344's "the harness cannot reproduce the owner's slowness" is explained here: every harness here ran with ONE plan in the device store, the owner's holds ~3.9 MB of them.)*

`[x]` **Step 1 — "U" / "t" / "Lv" de-minified (build 49a80ab rebuilt with sourcemaps, `ui-audit/lib/sourceMapIndex.mjs`):** `U` = `scheduler.production.min.js` `performWorkUntilDeadline` (called with `b` = `flushWork`, then `Em` = React's work loop). So the perfcap's "U" is **React's scheduler running a React render**, which is why the LoAF attribution never named a component. The LoAF script entry is just the MessagePort that wakes the scheduler. The attribution cannot name the cost; a CPU profile resolved through the sourcemap can.
`[x]` **Step 2 — reproduced on the real Silvestri plan** (`ui-audit/fixtures/sylvestri-concept-d-full.json`, the redacted pull of his plan, no synthesized geometry; four GIS layers on, dpr 2.125, 904×416, real wheel steps, 4× CPU throttle to stand in for his machine, FOREGROUND-OR-VOID asserted). New harness `ui-audit/diagnose-silvestri-zoom-step.mjs` prints per-step block time, React commits per step (via the DevTools hook) and WHICH state hook changed in each commit, plus the resolved CPU profile (self + inclusive + per-long-task). With one plan on the device it reads ~300 ms/step, worst task ~170 ms (the 283–307 ms tasks of the capture at his speed). **Supabase pull (sites + site_elements for sms4zs8unbkg) was reachable** and confirmed 134 live rows / 97 elements / 12 markups / 20 callouts / 3 parcels against the committed fixture's 98 / 6 / 16 / 3 — the fixture is a slightly older copy of the same plan; it does not change the finding (cost is not geometry-driven, see below).
`[x]` **THE ROOT CAUSE (named, measured, not guessed):** a zoom step is ~5 React commits in three bursts. In each, **`SitePlannerApp`'s `layerStatus` state changes** (every GIS layer reports loading→ok around each re-request; keys fema/txrrc_pipe/contours/jur_county in the capture), which re-renders the whole app including the **hidden keep-alive map finder**, and that render did, per saved plan on the device: `siteBoundaryInfo` → `siteAcres` → `dissolvedParcelSqft` (O(n²) `polyIntersectArea` overlap scan + clipper union); `usePlanName`/`useProjectName` `getSnapshot` → `loadSiteSummaries()` (JSON.parse of the WHOLE plan store + name reconcile) on every render; and `groupForPlan` → `loadSite()` (another full parse) in the App body. All three scale with the size of the local plan store, which a one-plan sandbox hides. **Per-step block at 4× throttle vs plans on the device (same build d6107bb): 1 plan ~300 ms · 47 plans (1 MB) ~1,060 ms · 93 plans (2 MB) ~1,820–1,960 ms, worst task 714 ms · 4 MB 3,190 ms, worst task 1,263 ms.** Owner's store at last measure was 3.9 MB, so his ~300 ms is the *minimum* of the curve at his CPU speed, and it grows with every plan he saves.
`[x]` **Ruled out, so it is not re-chased:** coalescing identical `layerStatus` reports (`mergeLayerStatus`, built and measured: base 297/303/342 vs fix 297/325/299 ms — no effect, because the reports are real loading→ok transitions, not duplicates; reverted); annotations (callouts+markups+measures ≈ 7% of a step, `--arm no-annotations`); the four GIS layers themselves (≈17%, `--layers none`); the pace-wait `postMessage` self time in a profile is the harness's own MessageChannel yield, not the app.
`[x]` **Step 3 — fixed at the three seams (each pure/cached, never a second source of truth):** (1) `lib/hiddenRenderGate.js` + `MapFinder` default export wrapped in `memo(…, skipWhileHidden)`: a hidden keep-alive map is not re-rendered by its parent (it renders exactly as before the instant it is visible; props changed while hidden apply on show — checked: a rename done while the map was hidden is on the list when it is shown, identical to the unfixed build). (2) `siteBoundary.siteAcres` memoised on a structural signature of exactly what `dissolvedParcelSqft` reads (active flag, ring vertices, save-and-except holes) — an edited parcel is a miss. (3) plan/project names: main independently landed the same fix while this was in flight (`planIndex` riding the one cached pass, B217540 ×2) — merged, nothing of mine kept there. (3) `SitePlannerApp`: `effGroup` memoised on `[activeSiteId, mode, sites]` instead of a `loadSite()` parse in the render body. Net per-step block at 4× throttle, same fixture: **1 plan 306 → 252 ms · 2 MB 1,956 → 292 ms (worst task 714 → 149 ms) · 4 MB 3,190 → 350 ms (worst 1,263 → 165 ms)**; scaling ratio 2 MB/1 plan **5.8× → 1.06×**.
`[x]` **Perf guard (red on unfixed main, green on the fix):** `npm run perf:zoomstore` = `ui-audit/verify-zoom-store-scaling.mjs`, real Silvestri padded with COPIES of the other committed real plans to 0 and 2 MB, best-of-two per arm, fails when a step is >2× slower with the bigger store or the worst task exceeds 300 ms; carries an unpadded control that voids the run if implausible. Verified: d6107bb → ratio 5.78×, worst 669 ms, both FAIL; fix → 1.06×, 152 ms, pass. CI-runnable halves: `test/zoomStoreScaling.test.js` (skip rule; `siteAcres` equals the uncached area and misses on every input it reads; ). The browser guard is not a CI gate (needs a served build); it is an `npm` script like the other `perf:*` harnesses.
