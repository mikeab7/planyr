- **⛔ ROOT CAUSE OF THE RECURRENCE (×2), found by tracing the dispatcher's own discriminator to the end rather than accepting it at face value.** `SitePlannerApp.jsx` has a SECOND resume mechanism, entirely independent of `bootActiveId`: `applyUser`, the handler for a signed-in cloud pull, computed `pickResumeTarget({ routeProjectId: projectIdRef.current, currentId: getCurrentSiteId(), ... })` with **no `resumeAllowed` gate at all**. It fires from a `useEffect(..., [])` — once per **mount**, exactly like `bootActiveId` — and supabase-js delivers `INITIAL_SESSION` the instant it subscribes, i.e. on that SAME first mount, signed in or not. When signed in, it awaits `pullCloud` (the owner's own stopwatch: bounces at 2.1–2.4s — this IS that async gap) and THEN falls back unconditionally to `getCurrentSiteId()`'s last-touched-plan pointer whenever the route names no project. This explains every measured detail at once: it fires once per FIRST mount of `SitePlannerApp` in a tab (so it doesn't matter which of the five other workspaces you came from — the mount is the trigger, not the control); it resumes the MOST RECENTLY TOUCHED plan rather than the one just left (matching Library→Richfield exactly, since `getCurrentSiteId()` is a "last touched" pointer, not a "what was I routed away from" one); and it explains the logo-vs-crumb "discriminator" precisely — the logo click in the dispatcher's own sequence happened AFTER `SitePlannerApp` had already mounted once (from the earlier pin-filter live-verify pass), so its one-shot auth subscription had already fired and settled — a SECOND Dashboard visit via ANY control (logo or crumb) never re-triggers a `useEffect(..., [])` closure. The logo and the crumb call the identical handler; the variable was mount freshness, not which button was pressed.
- **THE FIX (this session).** `lib/bootResume.js`'s new `resumeTargetAfterSignIn({ routeProjectId, currentId, plansOfGroup, hasSite, resumeAllowed })` applies the exact same `resumeAllowed` privilege check `bootActiveId` already honors: `if (!routeProjectId && !resumeAllowed) return null;` before falling through to the existing `pickResumeTarget`. `SitePlannerApp.jsx`'s `applyUser` now calls this instead of the bare `pickResumeTarget`, passing the SAME `resumeAllowed` prop `bootActiveId` uses — closed over at mount by the same `useEffect(..., [])` subscription, so it answers the identical "was THIS mount the boot mount" question for the async path that `bootActiveId`'s lazy initializer already answers for the sync one. A routed project (`routeProjectId` truthy) is untouched — opening a real project is always honest, signed in or not.

- **THE ACTUAL ROOT CAUSE — a THIRD, independent mechanism from the two `resumeAllowed` gates already closed above, found by reading `SitePlannerApp.jsx`'s own URL↔state-sync effects rather than guessing.** Both prior fixes only ever govern the component's FIRST MOUNT (`bootActiveId`'s lazy initializer, and `applyUser`'s once-per-mount auth subscription) — irrelevant once SitePlannerApp is already mounted and merely hidden, which keep-alive makes the common case (opening any project always visits its Site tab first). SitePlannerApp runs TWO effects to keep the route and its own `mode`/`activeSiteId` state in sync: one reacts to the URL (route → state), the other publishes state back to the URL (state → route) — and the second ALSO re-fires whenever `isActive` flips false → true, so reactivating a hidden tab reconciles the URL immediately. Clicking "Dashboard" from a kept-alive tab does BOTH at once, in one `navigate()` call: clears the route's project AND reactivates this mount, in the SAME render. On that render the URL→state effect has only *scheduled* its `setMode("map")`; it hasn't taken effect yet — so the state→URL effect, triggered by `isActive` alone, still reads the OLD, pre-click `mode`/`activeSiteId`, computes a still-truthy `effGroup` for the project just left, and `mayWriteRouteProject` waves it through (a truthy `nextGroup` is always considered an honest write) — writing the very project the click just routed away from straight back into the URL. No cloud pull needed, which is exactly why this lands in under a second instead of 2+.
- **THE FIX.** `bootResume.js` gains `routeProjectJustChanged(prevProjectId, projectId)` — a named, pure predicate (mirroring the URL→state effect's own existing "the first, route-less render is NOT a Dashboard navigation" exception, rather than a second, silently-drifting copy of it). `SitePlannerApp.jsx`'s URL→state effect records, in a ref, whether THIS pass is the one where the routed project actually changed; the state→URL effect checks (and consumes) that ref before writing, and defers entirely when it's true — the URL→state effect owns reconciling that transition, and the re-render it produces supplies a correct, fresh `effGroup` for the state→URL effect to act on next. Every other, legitimate use of the `isActive` reconciliation (switching workspace tabs with no project change, or a plan opened from within the Site Planner itself) is untouched, since the ref only ever reads true on the exact pass a real route-project transition landed.
