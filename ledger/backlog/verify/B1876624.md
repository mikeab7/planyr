### B1876624 — Replace the 1,000-lot vector cap banner with a zoom-based parcel display strategy `[Site Planner / map]` (feature) #site-planner #gis #parcel  *(owner decision, 2026-09-24: retire the "capped this view at N lots" banner and the vector-only display behind it — clicking a lot has never depended on the drawn outlines, so the cap has never affected clickability and the banner communicated a non-problem. Owner's added design point: "there is a zoom level where showing parcels at all is pointless, and at that level we should simply not draw them." Minted **B1876624 / V1340256** via `--against-main`, LATE. DEDUPE-FIRST — searched Open + ⏳ Verify + Done for `parcelTruncation`, `exceededTransferLimit`, `capped this view`, `PARCEL_MINZOOM`: **B1403/V688 is the exact prior item that shipped the notice being retired here** — reopened in spirit (a reversal, not a recurrence of the SAME symptom) and closed as superseded rather than left open; B1401/B1402 (the URL-policy and hang-guard-exemption siblings from the same day) are untouched and unaffected. Net-new feature on top of that reversal.)*

`[x]` **ESTABLISHED FIRST, as instructed, before building.** The "1,000-lot" cap is the ArcGIS server's OWN `maxRecordCount` ceiling, never a client-side slice Planyr imposes — `makeParcelLayer`'s `EL.featureLayer({...})` call sets no `resultRecordCount`/count param, and the retired notice's number came straight from `featureCountOf(e.response)` (the real response's feature count), never a hardcoded literal. Measured examples already on record in `counties.js`: Larimer's own CAD reports `maxRecordCount 1000`; the Colorado statewide composite reports `maxRecordCount 2000` (one view-sized bbox returned exactly 2000 features with `exceededTransferLimit: true`). So the wide regime needs a different DISPLAY, not paging — paging a display query is exactly what `vectorLayers.js`/the nightly snapshot builder already do for the surfaces that need a complete answer, and is not this display's job. The three ways the app already chose among vector/image/snapshot (`parcelDisplayIsImageOnly`, `makeParcelDisplayLayer`, `PARCEL_MINZOOM`) all lived in `parcelDisplay.js`; `PARCEL_MINZOOM` (14) was ALREADY the draw-nothing floor for the one layer a view used to draw — reused verbatim as the "far" floor per the brief's own instruction, not re-derived.
`[x]` **BUILT — three zoom-gated regimes for a real, queryable CAD's own outline display (a query-disabled statewide/TxGIO source is unaffected — its `/query` is disabled at every zoom, not just a wide one, so it keeps rendering as a server image at every zoom exactly as before).** `parcelDisplayZoom.js` (new, plain-Node-testable — `parcelDisplay.js` imports Leaflet + esri-leaflet and cannot be) is the whole decision: `PARCEL_MINZOOM` (far floor, unchanged) and new `PARCEL_VECTOR_MINZOOM` (**16** — the close-in floor; see the driven finding below), plus the pure `parcelDisplayRegimeForZoom`/`parcelUrlSupportsImageExport` functions. `parcelDisplay.js`'s new `makeParcelAdaptiveLayer` is the Leaflet wiring: mounts the vector layer (`makeParcelLayer`, gated `minZoom: PARCEL_VECTOR_MINZOOM`) and the server `/export` image layer (`makeParcelImageLayer`, gated `maxZoom: PARCEL_VECTOR_MINZOOM` — the SAME path the statewide/TxGIO fallback already uses) inside one `L.layerGroup`, and relies on esri-leaflet's own `FeatureManager`/`RasterLayer` zoom-range checks (already re-run on every zoomend, confirmed by reading `node_modules/esri-leaflet`'s source) to switch between them with no rebuild, no listener, and no state machine of Planyr's own. Below `PARCEL_MINZOOM`, neither sublayer draws — the far regime the owner asked for, for free. A source with no `/export` capability (a FeatureServer CAD, e.g. Fort Bend) has no image regime to switch to and is unaffected: one plain vector layer, exactly as before this item.
`[x]` **DRIVEN, NOT ASSUMED — the boundary was calibrated against the real app, not picked cold.** A new hermetic headless harness (`ui-audit/verify-parcel-display-regimes.mjs`, no real network to any GIS host) opens the real `MapFinder` on a throwaway Harris/Houston site, enters select mode, and wheel-zooms the real Leaflet map: it drives the app through all three regimes and asserts the DOM directly (vector `<path>` count, the server-image `<img>` presence, the pre-existing "zoom in a little" far hint, and a real click adding a parcel in every regime). Its FIRST run, at `PARCEL_VECTOR_MINZOOM = 17`, exposed a real calibration problem rather than a harness bug: `MapFinder.jsx`'s own `SITE_PLAN_VIEW_ZOOM` — the fixed zoom several "look at this site" flyTos already use, incl. "Show on map" — is ALSO exactly 17, so the app's own most common "close-in" zoom landed exactly on the wide/close boundary, where both sublayers query at once (redundant, not wrong, but wasteful against a real county server on the single most common view). Moved to **16**, one full zoom level below every existing site-focus flyTo (17 and 18), and the harness re-run clean: vector-only at the site's opening zoom, image-only one wheel-notch further out, nothing at the pre-existing far floor, and a click adds a parcel in all three regimes with zero page errors. `verify-parcel-outline-opacity.mjs` (the pre-existing Harris/Rosharon/Chambers regression harness) re-run unchanged and still green, confirming the statewide-fallback and snapshot-fallback mechanisms are untouched.
`[x]` **THE CAP NOTICE ITSELF IS GONE.** `MapFinder.addDisplay`'s `fl.on("requestsuccess", …)` truncation-banner wiring is deleted; `parcelTruncation.js` (the module built solely to raise it, B1403/NEW-3) is deleted along with its now-orphaned unit tests. The other three notices this same function raises — the statewide-composite "slow right now" notice, the per-county "that county's parcel server is slow, showing statewide outlines" notice, and the Drive-snapshot cache-fallback notice — are UNTOUCHED; only the cap notice is removed, per the brief's explicit instruction.
`[x]` **CLICKING WAS ALREADY, AND STAYS, INDEPENDENT OF THE DISPLAY LAYER IN ALL THREE REGIMES — read, not assumed.** `MapFinder.handleClick` → `resolveCandidates` → `identifyParcelEager` always issues a live point-identify query against each candidate county's own service; nothing in that path reads `displaysRef.current` except `optimisticHitAt`, which is a pre-authoritative-answer OPTIMISTIC highlight only (an early, possibly-wrong guess the authoritative identify always overrides or confirms) — never a gate on whether a click can select. B1427664/PR #1602 already ruled out making clicks wait on a display layer; this item does not revisit that, and the adaptive layer's `eachFeature` (the one thing `optimisticHitAt` needs) delegates to the vector sublayer, which esri-leaflet already empties out whenever it's outside its own zoom range — so the optimistic highlight is naturally offered only in the "close" regime, exactly as it was before this item for a source with no image capability. B137 (what you SEE is a subset of what you can SELECT) holds in every regime, and is now STRONGER in "wide": the image layer draws every lot in view (no record cap), a strict superset of what the old vector-only band could show there.
`[x]` **FALLBACKS PRESERVED, NOT REGRESSED.** The slow-county → statewide-image fallback (`markDown`'s `showSnapshotDisplay`/`setSourceNotice` paths) and the Drive-snapshot geoJSON path (`preferSnapshotForDisplay`'s early return in `addDisplay`) are both unchanged code paths, untouched by this item — the adaptive layer only replaces what a HEALTHY real CAD draws. The hang-guard wiring was extended (not replaced) to cover both sublayers of the adaptive composite, sharing one county-level health state exactly as before (a `wireDisplayHealth(target, kind)` helper wires whichever sublayer(s) exist, since esri-leaflet's vector FeatureLayer and image-mode RasterLayer use different event names for the same lifecycle — see the pre-existing statewide branch this pattern was copied from).
