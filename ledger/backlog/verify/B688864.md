- **AUDIT-FIRST — established which of the report's two candidate causes was real, rather than assuming either (the brief explicitly required this).** Read `SitePlanner.jsx` end to end for how the row's three controls (eye / padlock / ✕) and the picture on screen actually connect, before writing anything:
  1. **The row draws through TWO independent techniques the owner cannot tell apart.** The captured `underlay` object (the padlock/opacity/calibration fields) is rendered as a plain SVG `<image>` — but ONLY `!(origin && basemapOn)`, i.e. only when the LIVE Leaflet basemap tile layer isn't already covering it. `basemapOn` is `basemapSrc !== "off" && !!origin`, and `basemapSrc` **defaults to `"esri"` (on) the instant a plan has a real `origin`** — true for every one of the 48 `fromMap` plans, since they were all captured FROM the map picker, which always sets one. So on every one of those plans, the picture on screen is the LIVE tiles, not the static image the row's opacity slider even claims to control (the row already said as much in a buried sentence: *"Hidden while the live map basemap is on — the basemap IS the aerial there"* — printed, but never acted on).
  2. **The eye (Hide) toggle — `showAerial` — never touched that live layer at all**, and was a bare `useState(true)`, not part of the saved plan. So on a `fromMap` plan (basemap on) it changed **nothing visible in the same session**, and even on the rare plan where it WOULD have mattered (basemap off), it reset to shown on every reload — never persisted, for any plan, ever.
  3. **Remove (✕) DOES clear the archived snapshot** (`underlay: null`, confirmed it writes and persists like every other site-model field) — the brief's option (b), "it writes and the underlay is regenerated," is **REFUTED**: nothing in `MapFinder.jsx`'s `fromMap: true` construction path runs again on an existing plan's reload, so a deleted underlay does not come back. What actually happens is worse for the owner's mental model, not a data bug: **the live basemap tiles were never touched by Remove either**, so the identical-looking aerial stays on screen — read, correctly, as "deleting it does nothing," even though the archived record genuinely is gone.
- **THE FIX — real, persisted hide/delete semantics (the brief's option (a)), implemented rather than the wording-only relabel B525632/B519152 already tried and which the brief explicitly forbade repeating.** New pure module `lib/aerialVisibility.js`: `settings.aerialHidden` (sparse — absent means shown, the same convention `settings.hidden`/content-visibility already uses) is now the ONE persisted fact behind the eye toggle, and `wantBasemapSrc(basemapOn, aerialVisible, basemapSrc)` is the corrected decision for the live tile layer's `want` — gated on that same fact, not just on `basemapSrc`/`origin` as before. `showAerial` in `SitePlanner.jsx` is now derived from `settings` (via `isAerialVisible`) with a `setShowAerial` that persists through `withAerialVisible`, instead of a throwaway `useState`. The background-grey/grid-line cosmetics (`SitePlanner.jsx` lines that painted the dark placeholder / suppressed the drafting grid) are gated the same way, so hiding the aerial also restores the ordinary grid rather than leaving a blank dark rectangle. Two reconciliation edges, so the row-1 Layers-panel "Basemap" dropdown (a separate, pre-existing control over `basemapSrc` itself) can't silently fight the References-panel Hide: picking a source there un-hides (an explicit direct pick wins), and loading a brand-new screenshot un-hides too (so a prior Hide/Remove can't silently suppress content the user just added).
