- **AUDIT-FIRST finding (the reason this shipped narrower than the brief's framing implied):** the brief described land-take and earthwork-$ as features to build from scratch. Reading the actual code showed otherwise — `YieldPanel`'s land donut already computes `pondArea`/`detPct` from real drawn pond rings (never hardcoded to 0), and the Earthwork cost card already has a "Pond excavation" line priced off the user's own $/CY bid with `{code:"plan"}` provenance. The real, unaddressed gaps: (1) that excavation line always prices the FULL basin cut, even for a pond that reuses an existing depression via the "Expand this pond" flow — explicitly admitted in the card's own caption ("the full basin cut, top of bank → achievable floor"); (2) there was no forward-looking estimate of how much MORE land a detention shortfall would take before a pond is drawn or enlarged to cover it.
- **New `lib/pondGeom.js` functions, both pure:** `incrementalExcavationCf(ring, det)` nets a pond's current-geometry cut against `det.baseline` (the pre-expansion ring snapshot the existing "Expand this pond" flow already captures for its own label rendering, repurposed here) — falls back to the full cut when there's no baseline (a from-scratch pond), never fabricates a negative number, ignores a malformed baseline. `detentionLandTakeEstimate({ requiredAcFt, providedUsableCf, avgDepthFt })` turns the site's existing required-vs-provided detention deficit into a screening footprint (footprint ≈ deficit volume / a typical assumed pond depth) — returns `null` (never a fabricated estimate) when there's no real shortfall.
- **Wired in (`SitePlanner.jsx`):** the pond-ledger build loop now computes `incrementalExcavationCf` per pond and carries a new `excavationIncremental` flag; the Earthwork card's "Pond excavation" row relabels to "Pond excavation (incremental)" and its Basis popover explains the netting whenever ANY basin in the plan reuses an existing pond. `YieldPanel` computes a `detentionLandTakeEstimate` off the same `detReq`/`providedUsableCf` figures the existing "raise TOB" berm-apply screen already reads, rendered as a `WatchOutChip` ("Detention shortfall ≈ +N ac more land — screening estimate") directly under the land donut — deliberately OUTSIDE the pie's real percentage math, so it never double-counts or unbalances the pie (guardrail honored: the pie still nets to 100% exactly as before, since this is an advisory about land NOT YET drawn, not a slice of land already accounted for).
- **New criterion, criteria-configurable, not an inline constant:** `screeningPondDepthFt` (default 8 ft, matching the codebase's existing 8-ft screening-depth convention elsewhere) added to every jurisdiction row in `detentionCriteria.js`, threaded through `criteriaFor()`, overridable like every other criterion — this is the ONLY number the land-take estimate uses to turn a volume shortfall into a footprint.
