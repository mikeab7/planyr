### B2429233 — Deleting an account's LAST schedule does nothing and says nothing (breadcrumb inline "Delete" confirm closes, the schedule stays) `[Schedule]` (bug) #scheduler #ui
- Verify: live (test account `e2e@planyr.test`; signed-in, deployed build)
- Found 2026-10-22 while cleaning up B2429232's live check on the test account: Schedule switcher → row kebab → Delete → inline "Delete “Project 60”? This removes 3 tasks." → Delete. The confirm closes, no toast, no error, the schedule is still listed after a reload. Cause (read in code, not yet reproduced in a unit test): the embedded app's `deleteProject` refuses to remove the LAST project (`public/sequence/index.html`, the `planar:nav-delete` handler comment says so) — correct as a guard, but the shell has already shown a confirm and then reports nothing. LOUD-FAILURE: either hide/disable Delete on the only schedule with a one-line reason, or surface "You can't delete your only schedule".
- Not fixed in B2429232's session (one task per session). Stopping rule: closes when deleting the only schedule either works or says why in the UI, proven by a spec.

- **Fixed 2026-10-22 (owner chat block: "fix it, don't file a new one").** Read in code first: there is NO real reason to refuse the last schedule. The guard (`Object.keys(d.projects).length <= 1`) predates B2285440, which made a document with no schedule render the honest "No schedules yet" state; the cloud write already soft-deletes any row missing from the document. **Now:** `removeScheduleFromDoc` (`public/sequence/index.html`, one pure function) deletes the last schedule like any other and leaves `aPid` null (never dangling); the row menu's `canDelete` no longer disables it.
- **Second silent failure found on the same path (LOUD-FAILURE):** the cloud soft-delete (`writeScheduleRowsPrimary`) wrapped `await sb.from("schedules").update(...)` in a try/catch, but supabase-js RETURNS `{error}` rather than throwing — so a refused soft-delete (RLS, network) was swallowed and the schedule base dropped as if it had worked: the row stayed in the database and came back on reload. It now checks the error and zero-rows-touched, keeps the baseline so the next save retries, toasts "A deleted schedule could NOT be removed from the cloud…", and fires `planar:cloud-save-failed`.
- **The shell verifies its own delete:** `Scheduler.jsx` `deleteSchedule` watches the embedded app's next `planar:nav-state`; if the schedule is still listed after `DELETE_VERIFY_MS` it shows a notice naming it (`lib/scheduleDeleteVerify.js`). Any refusal, lost message or cloud failure is now visible, never a closed confirm and silence.
- **Adjacent cases (reported):** deleting a NON-last schedule — worked before and after (unit + e2e). Last schedule of ONE project while other projects still have schedules — never refused (the old guard counted every schedule in the account, not per project); unchanged. Org-level section rows — same single function; the e2e deletes every org row down to zero. The embedded app's own right-click Delete on a schedule had a greyed-out `canDelete` for the last one — now enabled.
- **Proof:** `test/scheduleDeleteLast.test.js` (real function extracted from `index.html`; red on main), `e2e/schedule-delete-verify.spec.js` — the "delete every schedule, last one included" arm FAILS on the old embedded app (Expected 0 rows, Received 1) and passes on the fix; a second arm swallows the delete message so the schedule genuinely stays and asserts the notice. Live signed-in pass + removal of the leftover "Project 60": V1873392.
- Stopping rule (unchanged): closes when deleting the only schedule either works or says why in the UI — now proven by a spec and a live pass.
