`[x]` **FIXED THIS SESSION — AUDIT-FIRST found the real mechanism is a browser-input-path gap, not a wrong decision, and the fix closes that gap without touching the (already-correct) decision table.**
- Verify: live — this is a divergence between a `keydown`-driven input path and a `beforeinput`-driven one that only iOS Safari's on-screen keyboard is documented to produce; nothing in this sandbox (Chromium, or a real WebKit build) can synthesize that specific virtual-keyboard behavior, only a real iPhone can. See **V916800**.
- Origin: filed 2026-09-06 from chat (owner chat block).
- **THE REAL MECHANISM, stated because the brief asked for it rather than a guess.** `blockStartAction` in `src/workspaces/notes/lib/notesBlockKeys.js` already had the right answer for this exact shape — "list-item-to-paragraph" (unwrap the empty item, keep its nested child as a sibling) — and a from-scratch trace plus a real-browser, real-keypress test on the EXACT reported document (`P("Tell Talbert…"), UL(LI("", UL(LI("9/21…")))), P("Figure out…")`, caret in the empty bullet) produced the CORRECT result on Chromium, with no data loss, using the code as it already stood. Disabling the whole fix (`NoteBlockKeys` returning `false`/no plugins) and re-running the SAME real keypress ALSO produced the correct result — Chromium's own fallback keymap happens to get this shape right too. So the defect cannot be reproduced on desktop by any path this repo can drive, which is itself the finding: `addKeyboardShortcuts` is a `keydown`-bound keymap, and iOS Safari's software keyboard is documented (a known, longstanding WebKit/mobile-input class of bug affecting rich-text editors broadly) to delete backward via a `beforeinput` (`inputType: "deleteContentBackward"`) that does not reliably carry a `keydown` a keymap can intercept — the platform's own native list-editing logic runs FIRST, and ProseMirror's DOM-mutation reconciliation (`domObserver`) then has to guess a transaction from whatever that native edit already did to the DOM, which is not obliged to match this file's table for a nested, otherwise-empty item.
- **THE FIX.** `NoteBlockKeys` (`notesBlockKeys.js`) gained `addProseMirrorPlugins()`: a ProseMirror plugin with `handleDOMEvents.beforeinput` that asks the IDENTICAL `blockStartAction`/`runBlockStartAction` question on `inputType === "deleteContentBackward"` and calls `event.preventDefault()` before the platform's own edit can run — so the outcome is the same one-step table regardless of which event the platform actually delivers. On a normal desktop `keydown` this branch never executes at all (the keymap's own `preventDefault` already cancels the browser's default action before `beforeinput` for it is dispatched), so it is purely a backstop for the path that skips `keydown`.
- **PROVEN REACHABLE AND CORRECT, three independent ways, because a backstop nobody has seen exercise is not evidence:**
  1. Disabled the `keydown` handler alone (kept the new `beforeinput` plugin) and re-ran the owner's exact document through a REAL physical Backspace keypress in Chromium — the `beforeinput` plugin took over and produced the identical correct result.
  2. New dedicated harness `ui-audit/verify-notes-backspace-beforeinput.mjs` dispatches a SYNTHETIC `beforeinput` (untrusted, so Chromium performs no native edit for it — only the plugin itself can produce a transaction) directly at `window.__noteEditor.dispatchBeforeInput()` (new `__PLANYR_E2E`-gated hook in `NoteEditor.jsx`). Red-proved: commenting out `addProseMirrorPlugins()` and rebuilding drops it to 2/8 (every real case reverts to "nothing happens" — no native edit, no plugin, no transaction); restoring it returns 8/8, including a negative control (a non-backward `inputType` is left completely alone).
  3. Re-ran the entire existing `verify-notes-backspace.mjs` table (52 rows after this item's additions) against a REAL WebKit engine (Playwright's Linux WebKit build, installable per this file's own `npx playwright install webkit && npx playwright install-deps webkit` note) — every B1260000-related row passed; the only 2 failures are a pre-existing, unrelated WebKit rendering quirk in picture-selection-after-Backspace, confirmed unaffected by this fix and not investigated further (out of scope for this item).
- **WHAT THIS CANNOT REACH, stated plainly rather than glossed over:** real Mobile Safari's on-screen-keyboard-to-DOM bridge, which is what actually produces a `beforeinput` with no matching `keydown`. Playwright's keyboard automation always synthesizes a full physical-key sequence on every engine available in this sandbox, WebKit included — none of it emulates iOS's virtual keyboard specifically. That gap is exactly why this stays `Verify: live` rather than moving to Done.
