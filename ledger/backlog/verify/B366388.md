Confirmed in the source: `active = hoverRow === p.id || menuFor?.id === p.id`, and `hoverRow` is set **only** by `onMouseEnter`; the sole alternative route is `onContextMenu`, a right-click. So on a touch device there was **no rename and no delete at all** — and for a KEYBOARD user the button was not merely invisible, it was **absent from the DOM**, so it could not be tabbed to either.
- **SO THE KEBAB WAS FIXED FIRST, and only then was the duplicate removed.** It is now always rendered; hover only BRIGHTENS it (`--text-tertiary` → `--text-secondary`), because opacity/colour is presentation and must never be the hit-test gate. The row's timestamp / `current` marker now sits BESIDE it rather than being swapped out by it, so hovering a row no longer hides when it was last edited.

- **VERIFIED IN A REAL BROWSER, NOT PARKED.** The e2e spec's old *"the dropdown carries a plain 'Rename' row"* test asserted the removed control, so it was **rewritten rather than deleted** — the concern it encoded is now the thing under test: the duplicate is gone AND the kebab is clicked with **no hover at all**, then rename still writes every plan in the group and survives a reload. 8/8 passed against Chromium.
