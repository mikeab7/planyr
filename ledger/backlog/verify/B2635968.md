- **The hole (read from the LIVE definitions, not the repo files):** with email confirmation off, nobody proves they own the address they sign up with, yet FIVE doors treated "the account's address matches an open `team_invites` row" as proof: `handle_new_user()` (auto-joined a new account), `claim_team_invites()`, the `self join via invite` `team_members` INSERT policy (a raw client insert), the `invitee reads own` `team_invites` SELECT policy (read the row — i.e. the link's secret id), and `list_my_invites()`/`respond_to_invite()`. Reproduced in a real Postgres (PGlite) against the shipped chain before the fix: a sign-up with an invited address joined the team (red test first, 23 of 24 new tests red).
- **The rule:** the emailed LINK is the proof (its id is the invite row's own `gen_random_uuid()` — 122 random bits — and no open invite row is readable by anyone but the team's admins). Nobody joins by address alone. `db/team_invite_proof.sql`: `mailbox_proofs` (RLS on, no policy, no client privilege; a proof belongs to the ADDRESS it was given for), `redeem_invite_link` (signed in as the invited address: proves + joins/declines; another address → `wrong_account`, nothing changes), `list_my_invites` / `respond_to_invite` (a proven mailbox is unchanged; an unproven one is told only that an invitation is waiting — no id, team, inviter or role — and cannot accept OR decline, so a squatter cannot kill the real invitee's invite), `handle_new_user` and `claim_team_invites` no longer join, both address-match policies dropped, `prove_mailbox` (service role only — the hook the "sign-in emails sent by Planyr" session can call to set the same marker).
- **Screens + server:** landing page covers every state (new account → create-account card, no Turnstile · existing account signed out → sign-in with the address filled in · signed in as the invited address → Accept/Decline · signed in as another address → names both addresses + "Switch to …" · just joined → "You're on X." (item 7 — never "already used") · used/declined/replaced/gone → a plain line plus a next step). Account menu: an unproven account sees "A team invitation is waiting"; Accept emails the invitation again (`/api/team/invite-resend`, service-role RPC, the 60 s server throttle, invite ids never reach the browser) and the card says "We sent a confirmation to <address>." with Resend. A once-per-session `WaitingInviteNotice` covers a sign-up without the link and names no team. `/api/auth/invite-signup` (item 8): a person arriving by a valid open link whose address has no account creates it through the admin API with no Turnstile, capped at 8 tries per invite per rolling day, address taken from the invite never the request, session pinned to the user just created.
