**FINDING A — ROOT CAUSE.** There are exactly two places a project (`group_id = id` row) is born, both in `SitePlannerApp.jsx`: `newSiteFromMap` (the parcel-selection path) and `newBlankSite` (the "Start blank" / outage-fallback path, when given a real origin). **Neither one ever looked for an existing project first** — no query, no origin comparison, no check of any kind. The gap between the two production creates (51 seconds) is irrelevant: this mints a duplicate at 51 seconds, at 5 minutes, or at an hour, identically, whether the second call came from a genuine second press or the app re-entering the path on its own — both are covered by the same rule and neither was distinguishable from the row data alone, so the fix is written against the rule, not against a guess about which happened.

- **THE FIX — ADOPT, DON'T MINT.** `findProjectAtOrigin` (new, `src/shared/projects/projectModel.js`, pure/dependency-free) answers "does a project already exist at this ground" by haversine distance (`distanceFeetBetween`) against every locally-known site record, within `SAME_GROUND_FT` (30 ft — tight enough that two genuinely different adjacent parcels can't collide, generous enough to absorb float jitter from re-deriving an origin for what is unmistakably the same click; the real duplicate matched to the last digit). Ties (pre-existing duplicates at one spot) resolve to the most-recently-updated group, never a coin flip. Both `newSiteFromMap` and `newBlankSite` (its located branch) now call it FIRST — reading `loadSitesList()` fresh at the moment of creation, never the possibly-stale `sites` prop — and **open the existing project instead of minting**, unconditionally: pressing "Plan a site" on already-planned ground lands you in that project, it never blocks or errors (owner constraint: "ADOPT IS THE BEHAVIOUR, NOT BLOCK").
- **RED-PROOF (as required).** `test/duplicateProjectOrigin.test.js`'s first suite replays origin/main's `newSiteFromMap`/`newBlankSite` verbatim (mint unconditionally, no ground check) against the owner's exact production origin, twice — **fails the "one row" assertion, reproducing the reported bug mechanically**: 2 distinct `group_id = id` rows, both anchors, byte-identical origin, matching the production shape field-for-field. The second suite proves the fix: the identical two-call sequence through the adopt-gated path yields exactly ONE row, holds for 4+ repeated calls, never rewrites the adopted project (its `updatedAt` is untouched), and a genuinely different origin still mints its own project (adopt is not a blanket dedupe). A third suite is a SOURCE guard pinning that `SitePlannerApp.jsx`'s real `newSiteFromMap`/`newBlankSite` actually call `findProjectAtOrigin` before minting (not a re-derived mock) — 91 tests total in the file, all failing against unfixed `main` before the fix (confirmed by stashing the fix and re-running: 18 of 19 wiring-adjacent assertions fail, plus every adopt-behavior assertion).

**FINDING B — the adjacent, faster hole an owner mid-turn correction found by reading the code (not assumed from the brief).** The ground-adopt check above closes a create that runs AFTER the first has already saved. It does not, by itself, close a FASTER race: the map's decide bar (`MapFinder.jsx`) had **zero in-flight protection** — `runDecideVerb` just called `verb.run(target)` — and `planSelected`/`startBlankHere` each await a county lookup (up to 3s) BEFORE the project is ever written, with `newSiteFromMap`/`newBlankSite` then awaiting a team resolution on top of that. A multi-second window where the "Draw"/decide-bar button is still on screen, live and clickable, with nothing yet indicating a plan is being created — a second press in that window re-enters the same verb before the first press's own `saveSite` has run, i.e. before `findProjectAtOrigin` has anything to find yet.

- **THE FIX.** An in-flight guard at the functions every entry point funnels through, not at each call site (which this item found under-covered: `startBlankHere` alone is reachable from FOUR places — the toolbar's own "Draw" button, the decide bar's "site" verb, `ParcelInfoCard`'s outage fallback, and the map-wide outage offer — and three of the four never went through the decide bar's own guard at all). `runDecideVerb` now refuses to re-enter while a previous `verb.run` is still in flight (`decideBusyRef`, checked via a REF rather than state alone so a stale render closure — the Enter-key listener's own effect does not list this flag as a dependency — still reads the live value; released in a `finally`). `startBlankHere` carries its OWN, independent in-flight guard (`startBlankHereBusyRef`) so all four of its call sites are covered without needing four separate guards kept in sync. Two previously fire-and-forget calls (`planSelected`'s call to `onUseParcels`/`newSiteFromMap`, `startBlankHere`'s calls to `onSkip`/`newBlankSite`) are now **awaited** — without that, the guard's "in flight" window would have closed the instant the write was *initiated*, not when it actually finished, defeating the whole guard.
