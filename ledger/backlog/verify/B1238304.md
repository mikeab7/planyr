- **ROOT CAUSE (Site Planner canvas).** `lib/sheetFurniture.js`'s `scaleBarPlate`/`northArrowPlate` draw a rounded "plate" behind the bar/arrow. Its background was a MODULE-SCOPE CONSTANT (`PLATE_FILL = "rgba(249,248,244,0.84)"`) that never read from the functions' own `pal` parameter at all — while the `ink`/`muted`/`panelLine` args right beside it (the numerals, the "FEET" label, the "N" glyph, the plate border) already resolved correctly through `pal` to the live theme (`SitePlanner.jsx`'s `PAL.ink = themePal.textPrimary`, already theme-aware). So in dark mode the numerals correctly flipped to a LIGHT ink while the plate they sit on stayed the same fixed near-white — light-on-near-white, which is the "washed out / low-contrast grey" the owner described, sitting inside a plate that itself never went dark like its neighbours. Confirmed live (see Verification below): before the fix, dark-theme furniture read `fill="rgba(249,248,244,0.84)"` — pixel-identical to light mode.
- **FIX.** Added a dedicated theme token — `canvasPlateFill` in `src/shared/theme/palette.js` (LIGHT is **byte-identical** to the old `PLATE_FILL` value on purpose, so this fix changes nothing anyone could already see in light mode; DARK is a new translucent dark card matching `--surface-overlay`'s "frosted floating panel over the map" look every other dark-theme overlay panel already uses) + its CSS mirror `--canvas-plate-fill` in `index.css`. `SitePlanner.jsx`'s local `PAL` gained `plateFill: themePal.canvasPlateFill`, already passed into `screenFurniturePlates({..., pal: PAL})`. `sheetFurniture.js` now reads `pal.plateFill || PLATE_FILL` for both plates. Also fixed the alternating "unfilled" scale-bar segment, which was hardcoded `"#fff"` — in dark mode that would sit beside a now-light `ink`, and two near-identical light tones would erase the bar's own black/white alternation; it now reads the PLATE's own colour instead (the classic ink-vs-paper scale-bar convention), which stays maximally distinct from `ink` in either theme by construction.
- **PDF/PNG EXPORT — a real, independent pre-existing defect found and fixed in the same pass, not merely "not made worse."** `exportSheet.js`'s furniture-composition call already passed `pal: PAL` (the SAME live theme object) into the export path — meaning a dark-themed session was ALREADY producing exported furniture with light ink drawn on a plate that (pre-fix) never went dark, and post-fix would have gotten a dark plate too, exactly reproducing the on-screen bug on paper. Fixed by passing `pal: {}` instead, so the export always falls back to the fixed light/print-safe defaults regardless of the app's live theme — a printed sheet must stay paper-colored no matter what theme was active at Download time. Guarded by a new source-guard unit test (`test/sheetFurniture.test.js`) asserting `exportSheet.js` never passes `pal: PAL` to the furniture composer.
- **ROOT CAUSE + FIX (Map Finder, adjacent case, checked per the brief's own instruction).** `MapFinder.jsx`'s scale bar (`L.control.scale`) and its never-disabled attribution control are genuine, unmodified STOCK Leaflet widgets — vendor `leaflet.css` hardcodes them white-background/dark-text with zero app override; the zoom stack (`L.control.zoom`) and the hand-rolled "locate me" button (`leaflet-bar`-classed but custom-built) are ALSO exposed to the same vendor white background (only their corner RADIUS had previously been themed, per B1038016 — color was never touched). Fixed with new `index.css` rules (`.leaflet-bar a`, `.leaflet-control-scale-line`, `.leaflet-control-attribution`, all `:root`-prefixed for guaranteed specificity over vendor Leaflet regardless of stylesheet load order — measured live: a bare specificity match lost to Leaflet's own `.leaflet-container .leaflet-control-attribution` rule) reading the same `--surface-overlay`/`--chrome-text`/`--chrome-muted`/`--border-default` tokens the Layers/View panels already use, so Map Finder's bottom chrome now reads as one consistent look with the rest of the app, in both themes.
- **The distinction this fix draws, and the one that matters for future work here (added to `docs/DESIGN.md`'s Canvas/SVG boundary section in the same commit):** map CHROME (the scale bar, north arrow, attribution, zoom stack, status chips) is a fact about the MAP VIEW and must follow the theme; DRAWING CONTENT (buildings, ponds, paving, parcel lines, labels) is a fact about the SITE and must not — confirmed correct and untouched here (see the retracted-brief note above).
