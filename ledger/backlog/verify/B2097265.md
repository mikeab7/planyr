### B2097265 — Food: dragging the restaurant sheet up and down "doesn't work too great" `[Food]` (bug) #food #ui #mobile #testing  *(Owner block 2026-10-05 NEW-3. Investigated with real touch drags — Chromium CDP touch on the iPhone descriptors — NOT WebKit, which has no touch-drag primitive; the iOS finger itself is on V1519600.)*

`[x]` **What was actually wrong (each reproduced on main, each now a failing-then-passing row in the harness):**
  1. **A flick did nothing.** Release was decided by where the sheet was let go, never how fast, so a quick flick that did not pass the halfway point snapped straight back (3 rows red, both phones).
  2. **Only the thin handle moved the sheet.** A pull on the content or the place-name header just scrolled the list; the sheet never followed (2 rows red). Now a pull up raises the sheet before the list scrolls, a pull down with the list at its top lowers it, and a pull while the list is scrolled scrolls it back — decided once per gesture; a touch that starts on a rating slider is left to the slider.
  3. **A pull down with the keyboard up closed the whole place** and threw away what was typed (also with a form open and the keyboard down). Closing by drag is now refused when a form is open or the keyboard is up; with the keyboard up a pull down puts the keyboard away instead.
  4. **The full height crept.** The sheet sized itself from the scroller's `scrollHeight`, which grows with its own box, so pulling past full left permanent blank space under the content (575 → 595 measured). It now measures the content itself.
  5. Hardening, not separately reproduced: the release read the height from a render's closure (stale on a fast flick) → now a ref; the drag no longer chases a 220 ms height transition.
  **Not broken (measured):** the sheet DOES follow a slow handle drag one-to-one on main, and it did not overshoot the content on a plain over-pull — so neither is claimed.
`[x]` **Fix:** one drag engine (`BottomSheet.jsx`) for handle + content; release rule in `lib/bottomSheetSnap.js` (`resolveRelease`: slow = nearest stop, flick = one stop from where it started, close only when allowed). Tests: `test/foodBottomSheetGesture.test.js` (19) + the touch rows in `ui-audit/verify-food-rating-and-sheet.mjs` section 3 (both phones: follow, settle-on-a-stop, flick up/down per stop, tap = nothing, content pull up/down, list-scrolled, form open, keyboard up, slider-drag leaves the sheet alone).
- **Stopping rule:** closes on a dated pass of V1519600 steps 3-5 on his phone, or him saying drags feel right.
- Verify: live — **V1519600** (Mobile Safari's own touch handling is the part Chromium cannot show).
