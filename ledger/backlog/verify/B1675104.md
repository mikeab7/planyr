- **WHAT THE SITE PLANNER ACTUALLY DOES, established before building anything (the brief's own instruction) — `docs/NOTES-CARRY-FORWARD.md`'s new NEW-1 digest and this item's own `notesBlockMerge.js` header carry the full comparison.** Site Planner's `elementSync.js` is a live, per-tab, in-memory optimistic-concurrency engine over a REALTIME stream of per-ELEMENT rows — shadow/dirty/`recent`-authored-within-15s maps, `isDirectEdit`/`direct` tagging so a cascade-derived write never claims authorship, `semanticallyEqual` (numeric-epsilon) suppressing echo toasts, and a per-TAB-SESSION pending-edit journal (fixed under B846 after a shared per-SITE key let an idle sibling tab's refetch fold-and-clear the active tab's in-flight batch). Notes has **no per-keystroke wire at all** — a page is one WHOLE DOCUMENT, synced by a `rev`-guarded push/pull (`notesCloud.js`), and a conflict is detected only when a push is refused because the server's row moved. So this item ports the CONCEPT (resolve finer than "the whole object," let non-overlapping edits land silently, keep a real disagreement visible and non-destructive), not the mechanism — see the three-way split below.
- **⛔ THE THREE FAILURES THE SITE PLANNER ALREADY PAID FOR — CONFIRMED, NOT ASSUMED, per the brief's explicit instruction.**
  1. **Derived writes must never claim authorship.** Notes already has the equivalent protection, shipped separately and confirmed intact on this branch: `hasUserInputRef` (B1662464, `NoteEditor.jsx`) gates `onUpdate` on a genuine `isTrusted` DOM event, so a load-time schema settle, list renumbering (a pure CSS/browser fact here, nothing stored), or the trailing-paragraph insertion never reach `dirty` at all — they never become a candidate for this merge to see as "authored." Nothing new was needed here.
  2. **Semantic-equality suppression.** Already shipped and untouched (`judgeConflict`'s `identical`/`litter-only` verdicts, `notesCloud.js`) — this item's new code (`resolveDivergence`, `notesStore.js`) is inserted strictly AFTER that check, only for a genuine `"diverged"` verdict.
  3. **Per-session journal namespacing.** **CONFIRMED NOT A BUG HERE, not merely assumed** — Notes' cross-tab coordination goes entirely through `notesCloud.js`'s server-owned `rev` + `mergeSyncState`'s dirty-flag reconciliation (already hardened for exactly the two-window case by B1391/B1055088); there is no separate per-document journal FILE to re-key the way Site Planner's `elementJournal.js` was. The Silvestri "Utility" banner is that system working AS DESIGNED — correctly detecting a real divergence at WHOLE-DOCUMENT granularity — not a namespacing defect. This item narrows WHEN that correct system fires; it does not fix a bug in it.
- **THE ALGORITHM — a real 3-way (diff3-style) merge, because a 2-way diff of just local-vs-server cannot tell "only I touched this" from "we both changed the same original into two different things."** `lib/notesBlockMerge.js` (new, pure): flattens base/local/server into ordered leaf blocks (`notesRedline.js`'s `flattenBlocks` — the SAME flattener the redline view already used, extended so every leaf carries its own untouched `node` and every wrapper its own raw `attrs`, letting a merge rebuild an EXACT document rather than re-deriving one from decomposed runs), diffs base→local and base→server independently, turns each diff into ordered disputed ranges over the shared base-index space, and clusters any ranges that GENUINELY OVERLAP (strict `<`, never touching `<=` — a pure insertion sharing only a boundary point with a neighbouring edit is not a disagreement; an earlier `<=` draft produced false conflicts on exactly that shape, caught by this item's own unit tests before it shipped). A cluster touched by only one side applies silently; one touched by both is a conflict UNLESS both sides produced byte-identical results — and a side's own contribution to an overlapping cluster fills any of ITS OWN untouched sub-range with the ORIGINAL base content rather than dropping it (a second bug caught by this item's own two-client integration test: naively concatenating only "this side's replacement blocks" for a union range wider than one side's own hunk silently dropped a paragraph neither side had touched).
- **THE MERGE BASE — a genuine, provable common ancestor, never guessed.** `notesStore.js`'s `recordMergeBase`/`mergeBaseFor`/`forgetMergeBases`, backed by a new IndexedDB store (`notesImageDb.js` v3, `mergeBase` — ONE row per page, always overwritten) recording the exact document local and server are PROVEN to agree on, at every point that proof exists: a fresh adopt, a successful push, either side of a resolved conflict, and a clean merge's own eventual push. TIER-BY-REBUILDABILITY: it is a cache, not data — a miss (a page that predates this feature, or cleared storage) makes `resolveDivergence` return `false`, and the caller falls straight back to the pre-existing whole-document banner, which is the CORRECT outcome per the brief, not a failure.
- **THE UI NEEDED NO CHANGES.** `Notes.jsx`'s `handleConflict`/`ConflictNotice`/`ConflictReview`/`ConflictSideBySide` already just diff whatever two documents `notesConflictFor` and `readPage` hand them — so for a genuinely disputed region, `resolveDivergence` writes `mineDoc` locally and narrows the conflict entry's `serverDoc` to `theirsDoc`. Both candidates already carry EVERY non-conflicting edit from both sides, so the existing redline naturally shows only the words actually in dispute instead of the whole note, and "Keep mine"/"Keep theirs" resolve exactly that narrowed disagreement — nothing destroyed either way, matching the brief's explicit safety-net requirement.
- **THE SAFETY NET, checked directly:** a delete-vs-edit on the same paragraph is a conflict, never a silent delete (own unit test) — the deleting side's candidate shows the delete, the editing side's candidate keeps the full edited text, and picking either is a deliberate, reviewable choice. A pre-merge snapshot lands in Version History (`reason: "before-merge"`, pinned, forced) before EVERY write this feature makes, clean or narrowed — "a usable pre-merge revision in every case," confirmed in the two-client test, not assumed.
- **A LATENT SIGNATURE GAP FOUND AND FIXED ALONG THE WAY: indent-only edits were invisible to `flattenBlocks`.** A Tab/Shift-Tab that only moves an item's flat `indent` attribute (`lib/notesListIndent.js`) changed nothing the existing redline flattener looked at (the attribute lives on the wrapper, `sigPath` stripped only `uid`) — so an indent-only edit would have silently vanished from both this merge AND the existing redline/conflict-comparison view, on ANY note with a list, not just ones hitting this new feature. Fixed by adding `indent: readIndent(node.attrs)` to the `listItem`/`taskItem` wrapper signature — a strict correctness improvement to the pre-existing redline view as a side effect, covered by both the pure unit tests and a dedicated "list item edited in both windows, including across an indent change" test.
