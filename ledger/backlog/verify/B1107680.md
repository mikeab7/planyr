- **The fix moves all 13 keys out of the versioned document entirely** — they now live client-side only, split by "does a brand-new tab expect to already have this" (the design-latitude test the item itself named): `aPid`/`view`/`section` (per-tab, genuinely different per open tab) go to `sessionStorage` (`planar:tabView:v1`) — survives a reload of the SAME tab, never crosses to a new one; the nine durable preferences (zoom, column widths, sort, grouping, filters, health-column style) go to `localStorage` (`planar:viewPrefs:v1`) — a new tab is expected to already have them, matching the existing `planar:exportPrefs:v1` precedent in the same file. `editProjId` (an in-progress rename) is deliberately never persisted at all — it always resets to `null` on load, same as any other transient in-progress-edit flag, so a stale value can never resurrect a rename box or get counted as a real edit.
- **Mechanism, four pure module-scope functions (new, `public/sequence/index.html`):** `coreChanged(prev, next)` — a shallow, reference-equality check over every top-level key EXCEPT the 13 view keys (safe because every `setData` updater in this file already builds its result via immutable spreads, so an unrelated sub-tree keeps its identity); `stripViewState(d)` — the payload actually written to the cloud, with the 13 keys deleted; `persistViewState(prev, next)` — writes only the storage tier (session/local) whose keys actually changed, never the cloud; `resolveViewState(d)` — resolves the 13 keys on load/import/restore: prefers whatever THIS tab/browser already has, falls back to the value baked into `d` only the first time nothing is saved yet (the one-time migration off legacy `hs-v1` rows), always resets `editProjId` to `null`, and guards `aPid` against pointing at a deleted/nonexistent project (falls back to the document's own `aPid`, then its first project) so `data.projects[data.aPid]` can never read as `undefined`.
- **Wiring:** the main data-change effect now computes `coreIsNew = coreChanged(prevCoreRef.current, data)` and only calls `attemptCloudSave` when `coreIsNew` (never on first load, never on a view-only change) — the HOLIDAY_SET/ROW_H/health-rebuild/holiday-recascade block that follows it is gated the same way (VIEW-INDEPENDENT-ONCE: those derive only from `data.settings`/`data.projects`, so a view-only change correctly does zero recompute). `attemptCloudSave` and all four explicit checkpoint saves (`pre-restore`, `pre-delete-project`, `pre-import`, `pre-recascade`) now write `stripViewState(d)`, never the raw doc. All four `setData(d)` calls in the load effect (cloud-loaded / seed / offline-catch / the shared `applyLoadedDataRef` import-restore pipeline) route through `resolveViewState(d)` first.
