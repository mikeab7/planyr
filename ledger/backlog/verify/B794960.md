- **ROOT CAUSE, measured.** `renderCalloutNode`'s arrowhead size: `const ah = Math.max(7, fontPx * 0.7)`. `fontPx` is properly feet-proportional (scales with the live `rppf`, exactly like the rest of the drawing, so it already exports at the right RELATIVE size on its own). The **`7`** is a bare SCREEN-px legibility floor with no export correction — exactly the class `exportLabelScale.js`'s own header already names ("a 30-px legibility floor" needs the `ppf`/`k` treatment) but this one site was missed. Framing a large exhibit means being zoomed OUT (low `rppf`) at the moment "Continue"/export is captured — routine, not an edge case — and at low `rppf` the floor dominates `fontPx*0.7`, baking a WORLD-FEET size of `7/rppf` into the arrowhead: **measured on a real capture, `rppf=0.023058736`, that floor bakes a 303.6 ft arrowhead** where the design intends **26.0 ft** (`0.7 × 13/0.35`, constant regardless of zoom) — **an 11.7× oversize**, reproduced exactly by an e2e mutation check (see Guards).
- **THE FIX.** `ah = Math.max(7 * labelK, fontPx * 0.7)` — `labelK` (`labelFrame.k`, already computed in the render body for exactly this correction; **1 on screen, so on-screen output is byte-for-byte unchanged**) converts the floor from "7 raw screen-px" into "the canvas-px that will read as 7 sheet-equivalent-px once the export's own viewBox rescales the clone onto the page" — the same physical-legibility guarantee the floor always gave, now measured against the SHEET's scale instead of whatever live zoom happened to be active.
- **A SIBLING DEFECT, found by checking the adjacent cases as instructed ("line weights, dimension ticks, text, hatch spacing, the north arrow") — hatch spacing was ALSO broken, and is fixed in the same commit.** Every hand-authored hatch `<pattern>` (`pat-landscape`/`pat-berm`/`pat-trailer`/`pat-sidewalk`, plus the shared `HatchPatternDef` catalog renderer easements/encumbrances use) is a deliberate constant-canvas-px tile with **no scale ancestor**, by design (`shared/style/hatchPatterns.js`'s own header: "stays the SAME apparent size on screen at every zoom level"). That header ALSO claimed *"PDF/PNG export clones the live `<svg>` verbatim… No export-specific pattern handling is needed or should be added"* — **that claim was WRONG, and is corrected in the same commit (AUDIT-FIRST).** `buildComposedSheet` nests the export clone as its OWN `<svg viewBox=…>` inside a FIXED physical plan box; the browser's native SVG rasterizer (confirmed by reading `exportPDF`'s own `new Image()` + `ctx.drawImage` — genuine browser SVG rendering, not a bespoke renderer) applies that nested viewBox's fit scale to a pattern tile exactly as it does to any other geometry — so the tile's PHYSICAL size on the printed sheet varied with whatever live zoom was active at capture, the identical mechanism as the arrowhead. Fixed the same way: every pattern composes a `scale(labelK)` into its existing `patternTransform` (a new `patHatchTf(rotDeg)` helper for the four hand-authored patterns; a new `labelK` prop, defaulting to `1`, threaded through `HatchPatternDef`'s four call sites). `planyrBarHatch` (the Yield panel's bullet-bar chart) was checked and is correctly OUT OF SCOPE — it's a standalone UI `<svg>`, never part of the cloned plan canvas, never exported.
