- **THE COUNT WAS THREE OF ELEVEN-PLUS.** The flyout offered Draw / Deed / Split. **Remove** (`parcelMode === "remove"`, B598) had no entry point in the rail at all. **Combine** — a whole tool (`startMergePick` / `mergeParcels`, its own banner, its own Enter binding) — had none either. **Setbacks** lived in the LEFT rail, so the same noun was split across two opposite sides of the screen. And **boundary editing** — drag a corner, add one on an edge, Shift-click one off — existed ONLY as prose inside the Select tool's hint string, so a user who never hovered that tooltip never learned the app could reshape a boundary.
- **`lib/parcelActions.js` IS THE INVENTORY, AND THAT IS THE POINT.** The menu is now built from a pure model — every action, the group the work happens in, what gates it, and what it says when it is disabled — so *"does every parcel action have a menu path?"* is a PROPERTY a test asserts rather than something a reviewer notices. `SitePlanner.jsx` maps a row id to the existing handler and renders; it decides nothing. `test/parcelActions.test.js` fails if an inventory entry has no row, or a row has no handler at the render site — which is exactly the drift that produced a three-of-eleven menu in the first place.
- **THE FLYOUT NOW READS create → modify → remove**, matching the `SITE ELEMENTS` caret pattern beside it: **Add land** (Draw · Deed / Title · Click a lot on the map · Add by address) · **Change a parcel** (Split · Combine · Edit boundary corners · Setbacks & parcel settings → · Lock · Count-in/Exclude-from yield · Hide/Show acreage label · Reset label position) · **Remove** (Remove parcels — click to delete · Delete this parcel). Every one of them arms an EXISTING path — nothing here is a second implementation of an action that already lives elsewhere, which is why a complete menu grew no new behaviour to test.
- **A ROW THE PLAN CANNOT USE IS VISIBLE AND DISABLED WITH ITS REASON, NEVER HIDDEN.** Hiding an unusable action makes it undiscoverable, which is the bug. The ONE exception is *Reset label position*, which is meaningless until a label has actually been dragged.
- **EDIT BOUNDARY CORNERS IS A MODE OVER THE EXISTING SELECT GESTURES, NOT A NEW TOOL** — no new hit-testing, no new drafting, no new Esc handling. It arms Select with a parcel in hand and puts the three gestures on screen. **The trap it uncovered: a freshly drawn parcel arrives LOCKED, and `editablePath()` refuses a locked parcel** — so the mode would have taught three gestures and then silently swallowed all of them. The banner says the parcel is locked and carries the Unlock button (LOUD-FAILURE; never unlock behind the user's back).
- **THE NAMING COLLISION IS RESOLVED ON THE OWNER'S OWN SPLIT, and the split is now recorded in code (`PARCEL_SURFACES`) rather than in a convention.** The **right rail owns ACTIONS** — things you DO — and is **"Parcel tools"**. The **left panel owns ATTRIBUTES & SETTINGS** — what a parcel HAS: its acreage, county record, taxes, setbacks, active/locked state — and is **"Land"**. "Land" rather than "Parcels" (still one word apart) and rather than "Property" (which would have collided with the existing **Properties** element-inspector tab — one collision traded for another). Setbacks stay on the left because they are an attribute, and **each side carries a one-click path to the other**: the flyout's `Setbacks & parcel settings → in Land` row opens the panel with the lot selected, and the panel's `Draw, split, combine, reshape… → Parcel tools` row opens the flyout (sliding the rail in first on a phone). The **panel id stays `parcel`** — it keys persisted panel state and every `setLeftPanel("parcel")` call site, and renaming it would orphan them for no user gain.
- **THE INVENTORY WAS BUILT BY GREPPING EVERY `setParcels` / parcel handler, not by trusting the report's list** — which is how the four label/state rows (lock · active · hide chip · reset chip offset), previously right-click-only, and the two county-backed create rows, previously left-panel-only, got menu paths too.
