- Verify: live (the real shell on planyr.io, signed in as the test account) → see the V# filed with this entry.
- Caused by: **B2644624 / #2836** — it registered the window Ctrl+wheel listener only while Ctrl/Cmd is down, armed by keydown/keyup on the FRAME's own window. In the app the Schedule is an iframe (`Scheduler.jsx`); with keyboard focus anywhere else (header, project switcher, a panel) the Ctrl keydown goes to the parent document, the frame arms nothing, and the browser zooms the page. Zoom worked only after a click inside the Schedule. Its harness booted the Schedule standalone, so it could not see this.
- **MEASURED first (2026-11-06, headless Chromium, `main` 49b8f32; the decision between the two candidate approaches):**
  - Approach A (an always-on blocking wheel listener on the scroll panes) was BUILT AS A PROBE and measured as the time from the wheel event to the scroll event it causes, 240 notches per arm, arms interleaved, Grid pane: **p50 22.8 → 38.7 ms at 1× CPU, 28.0 → 44.7 at 2×, 37.9 → 52.2 at 4×; p90 33.4 → 49.5, 69.9 → 100.0, 194.8 → 208.4.** A constant extra ≈15 ms on EVERY notch at every CPU speed (≈ one display frame), i.e. exactly the cost #2836 removed. With a synthetic 25 ms busy frame the median went 39 → 62 ms (the whole slice). Real main-thread load while scrolling 4000 px: 0–2 tasks over 50 ms at 1×, but **74–91 tasks of 53–413 ms in Grid / Split at 4×** (Gantt: none) — each of which a blocking listener makes the next notch wait behind.
  - So A measurably brings the stall back; **B was chosen** (the brief's own rule): keep the gate, arm it from more places.
- **The fix (B):** the frame's Ctrl/Cmd listener is now ALSO armed (1) by any pointer event over the frame carrying the modifier (`pointermove` / `pointerdown`, passive — a pointer event reports Ctrl even when the key went to another document), and (2) by the shell forwarding Ctrl/Cmd down/up and window-blur to the frame (`planar:modifier-keys`, `src/workspaces/scheduler/lib/modifierForward.js`, installed by `Scheduler.jsx`). Still no blocking wheel listener at rest — `verify-schedule-scroll-smooth.mjs` verdict 7 is UNCHANGED and still the contract. The hover-zone split (over the Gantt → timeline, over the Grid → grid) is untouched.
- **What B leaves (said plainly):** (a) keyboard focus OUTSIDE the page document (address bar, another window just switched from) with Ctrl pressed AFTER the pointer last moved — the page never sees the key and the pointer sent no event; moving the mouse a pixel with Ctrl held re-arms it. (b) A trackpad pinch (Chrome delivers it as a ctrl+wheel with NO key at all) — the browser zooms the page, as it has since #2836; only an always-on blocking listener could catch it, and that costs the ≈15 ms above on every notch. Both are asserted/declared in the harness as KNOWN LIMITS.
