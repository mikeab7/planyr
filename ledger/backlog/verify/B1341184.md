**ROOT CAUSE.** `isPickShowing` (`navState.js`, shipped in **B748064**) answers "is the schedule the user just picked the one genuinely active in the embed right now" — true once the embed's `activeId` catches up to a deliberate pick, and it's what lets a cross-cutting Organization pick (Pursuits/Operations) override the route-derived empty state. Its own header claimed this was **"self-clearing: once activeId moves on… this answers false again on its own."** That was never true, and the gap it left was a permanent deadlock, not a rare edge case: `pickShowing` also gates the SELF-HEALING CARRY-IN EFFECT in `Scheduler.jsx` (`if (pickShowing) return;`) — the very effect responsible for moving `activeId` on after a genuine project switch. So the first time ANY schedule was ever explicitly picked from the Level-2 dropdown, `pickShowing` latched **true forever**: nothing could move `activeId` away from that pick again, which kept `pickShowing` reading true on every future render, which kept blocking the one effect that could have cleared it. `pickShowing` also silently disables the empty-state gate (`showEmptyState = !pickShowing && shouldShowLinkPanel(...)`) and the grid-mismatch render gate (`isGridMismatched(..., pickShowing, ...)`) — so with the pick stuck, ALL THREE of the mechanisms that keep the schedule crumb honest about the routed project go dark at once, which is exactly the "no row highlighted, wrong name shown, no error anywhere" shape the owner reported.

**THE FIX.** `isPickShowing` now also requires the pick's OWN project to still match the currently routed one: a pick is recorded as `{ id, projectId }` — `projectId` is the schedule's own `linkedSiteId` when it has one, or the routed project at pick time for a cross-cutting Organization schedule — and `isPickShowing(pick, activeId, section, projectId)` returns false the instant the routed project genuinely changes away from that recorded value, regardless of whether the embed's `activeId` has caught up yet. That re-enables the carry-in effect (which already correctly reads the project's own `lastActiveBySite` pointer via the embedded app's existing `planar:nav-select-by-site` handler — untouched, not re-implemented) the moment Level 1 is switched. Separately, `ScheduleCrumb` (the Level-2 breadcrumb) now receives `activeId={showEmptyState ? null : activeId}` rather than the bare `activeId` — while the routed project owns no schedule of its own and there's no standing deliberate pick, the embed's `activeId` still names whatever OTHER project's schedule happened to be open last (the Mesa case: a project the carry-in has nowhere to send), and the crumb must never repeat that foreign name; it now falls back to its own existing "Select a schedule" label, matching the "no schedule for this project" empty state rendered alongside it.

**NOT changed:** `planar_data`'s `lastActiveBySite`/`aPid` semantics, the embedded app's `planar:nav-select-by-site` handler, or `needsScheduleCarryIn`'s own membership logic — this is wiring, not data, exactly as the brief required.
