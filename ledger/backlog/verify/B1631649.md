`[x]` **FIXED AND RED-PROOFED.** Three real, code-verified gaps in the existing B955 connect system (`SitePlanner.jsx`), each independently confirmed by reading the actual filter/branch logic before touching it:
1. **`driveTargetKind` only recognized `type==="parking"` or a `type==="paving"` rect carrying `el.truckCourt`** (the auto-generated bonded dock zone) — a plain, hand-drawn `paving` pad (the tool's own hint: "Drag for a rectangle, or click points for an irregular paving / drive / truck court") was invisible to the connect magnet entirely. Now any `type:"paving"` rect is a target, defaulting to the truck-scale curb return (the owner's own named primary case; editable per-junction either way, so a car-scale drive is one edit, not a blocker).
2. **`finishRoad` only ever checked `raw[raw.length-1]`** (the final clicked point) for a connect — a road STARTED at a truck court (clicked there first, drawn away) connected nothing, even though the raw click coordinate visibly snapped onto the target's edge while drawing (the same `resolveEndpointConnect` call every point already makes) — the geometry LOOKED touched but no `driveTee` relationship was ever recorded, so no curb-return/outline-cut render ever fired. Fixed by also checking the FIRST point when the last one found nothing.
3. **`findDriveConnect`/`driveJunctionsOf` only matched within a small distance of an EDGE** — an endpoint dropped well inside a large paved rect (not just near its edge) reads a large distance to every edge and never connected. Fixed with `roadGeometry.rectContainsPoint` (point-in-rect via the same `outN` each rect edge already carries): a contained endpoint now also connects, and — because it is unambiguously already inside the paved surface — is **never relocated** (the constraint against silently rewriting the road's own drawn geometry); only a genuinely near-edge match gets the small precision snap every other connect magnet already makes.
Also: the connect magnet now respects hidden-group visibility for drive targets (matching the existing rule for road-to-road magnets — a hidden court is not a magnet), and the live snap-indicator ring, previously only shown from the SECOND clicked point onward, now also shows before the very first point of a fresh road (it was already silently snapping on click; it just never told you beforehand).

**SNAP TOLERANCE — reused, not invented.** The connect magnet uses the SAME tolerance every other endpoint-connect gesture in this app already uses: `min(12 screen px / view.ppf, 10 plan ft)` — 12 screen pixels converted to plan feet at the live zoom, capped at 10 ft in plan units so it can never grow unbounded at a zoomed-out view. Chosen because inventing a second number for drive-targets specifically would make the magnet feel inconsistent depending on what it's about to connect to, with no benefit; if it reads too eager or too shy in practice, it is one shared constant (`ROAD_CONNECT_MAX_FT` / the `12` in `connectTolFt()`) to tune, for every connect type at once.

**NEVER MOVES THE OWNER'S GEOMETRY beyond the small, expected connect-snap.** The target rect (truck court / paving pad) is never retrimmed, resized, or relocated to make a connection fit — only the MOVING road's own just-placed endpoint can snap, and only within the stated tolerance or when it was already unambiguously inside the target (in which case it is not moved at all — see gap 3 above). The two surfaces stay separately selectable and editable afterward (this reuses the existing `driveTee` relationship + `driveJunctionsOf`/`outlineCuts` render, which was already built to keep both elements independent — B955 already proved this, unchanged here). Undoable in one step: the whole placement (geometry + the `driveTee` relationship) commits inside the SAME `pushHistory()`/`setEls` call `finishRoad` already used.

**RED-PROOF, `e2e/road-drive-connect-placement.spec.js` (13 tests, a real browser driving the real canvas):** connects the moment placement completes with no second action · negative case (placed clearly away connects to nothing) · endpoint exactly on the edge · endpoint well inside (containment, asserted NOT relocated by reading both elements' stored geometry back out of `localStorage`) · endpoint just outside tolerance (must not connect — confirmed does not) · a road STARTED at the target (the first-point fix) · both ends near DIFFERENT targets (a REPORTED, not silently mishandled, single-`driveTee`-field limitation — exactly one end connects, the model never carries two or duplicates the road) · road-to-road unaffected (still resolves as a tee, unchanged pre-existing path) · road-to-BUILDING never connects (a building is not paving — stated expected behavior, confirmed) · dragging an EXISTING road's endpoint onto a paving pad after the fact (the shared `resolveEndpointConnect`/`applyDriveConnect` path, unchanged code, now reachable because the target-type gap is closed) · undo immediately after a connecting placement removes the road and the connection as one step · the connection survives a `page.reload()` (localStorage round-trip).
