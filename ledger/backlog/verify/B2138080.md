`[x]` **Cause (owner-measured, confirmed in code):** `html, body` are `position: fixed`, so the guard treated every nonzero `window.scrollY` as the "page dragged off its pin" defect and healed with `scrollTo(0,0)` on every `scroll` / `visualViewport` event. iOS Safari implements keyboard avoidance by scrolling the document even with a fixed body, so the guard undid Safari's own keyboard lift one frame later. The 49 `client_errors` rows `event:page-containment-drift` from his iPhone (scrollY 100–350, scale 1, `#/site #/food #/notes #/admin`) are the keyboard, not the drag.
`[x]` **Fix (`src/shared/ui/pageContainmentGuard.js`):** a scroll is keyboard-driven when an `input`/`textarea`/`select`/`[contenteditable]` is focused OR the visual viewport is markedly shorter than the layout viewport at scale 1 — either is enough. `detectDrift` takes `focusedEditable` / `layoutHeight` / `vvHeight` and returns no scroll drift in that state; the watcher then does NOT `scrollTo`, does NOT report, and only re-announces `planyr:viewport-healed` so Notes / phoneTyping can re-check the caret (they also listen to the visualViewport themselves). A pinch (scale drift) also shrinks the visual viewport and is deliberately NOT treated as a keyboard — scale drift is still reported. Real drag protection (scroll with nothing focused and a full-height visual viewport) is unchanged.
`[x]` **Viewport meta `interactive-widget=resizes-content` — considered, deliberately NOT added.** It would make Chrome Android shrink the layout viewport with the keyboard, which resizes the fixed `html, body` (and so the Site Planner canvas) on every keyboard open — a VIEWPORT-STABLE regression risk that cannot be measured from this sandbox (no Android), for a browser that was never the reported one. Safari ignores it, so it would fix nothing on the owner's device.
`[x]` **Sandbox-verified:** `test/pageContainmentGuard.test.js` (focused editable → null; shrunken visual viewport → null; neither → still reports; scale drift still reported; guard leaves the scroll alone with the keyboard up, heals + reports with it down). `ui-audit/verify-comp-sheet-review-first.mjs` NEW-1 arm (iPhone 13 descriptor): with a comp-sheet input focused and a browser-reported scrollY of 280 the guard makes **zero** `scrollTo` calls; after blur the same report makes `scrollTo(0,0)`. **Mutation-proven:** on the pre-fix guard the focused arm goes red (`scrollTo("0,0")` called). ⚠ **The literal reading in the brief (`scrollTo(0,280)` → read `scrollY` → 280) is VACUOUS in Chromium** — `html, body` are fixed, so the document has no scrollable range and `scrollY` stays 0 whether or not the guard runs (measured: range 0); real iOS scrolls a fixed document anyway, which is the bug. The harness records the literal reading but takes its verdict from the guard's own act.
