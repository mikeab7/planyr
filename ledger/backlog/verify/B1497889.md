**WHAT TRIGGERS THEM, AND WHICH SURFACE CONSUMES THEM (the report's own open question) — the Leasing Comps rail.** `CompsPanel.jsx` — the "Comps" tab inside the map's left rail — renders one `CompRow` per saved comp, and each row calls `useCompLocationText(comp.anchor, …)`, which reverse-geocodes any `pin`/`parcel`-anchored comp that isn't already in its (in-memory-only, pre-fix) cache. The trigger is NOT the project route as such: this file's own header explains `CompsPanel` is "**Mounted whenever the map route is visible … so a comp anchored while browsing Sites still loads and renders as a map pin**" — and this app keeps the map's whole component tree mounted at all times (even while looking at a specific project's Plan view) so the Leaflet map survives switching views. `comps.map(...)` runs unconditionally the instant that mount happens, regardless of whether the Comps tab (or even the Map view) is the thing actually on screen — a map PIN only needs the lat/lon it already has; only a rail ROW or the detail view needs the resolved street address. **Why Bain's reload showed none:** the six geocodes are account-wide (comps are their own entity, not scoped to a project — `CLAUDE.md`), so the same six calls would eventually fire the first time any project's mount catches the map in that transient state; Bain's own cold reload most plausibly caught them already resolved from the Goose Creek check moments earlier in the same investigative sitting (the pre-fix cache was `Map`-in-module-scope, which survives an in-app route change but not a hard reload — consistent with, though not independently provable from, the two checks having been run back to back rather than as two fully isolated sessions). Stated as the most likely explanation, not a certainty — the mechanism above (unconditional mount-time fetch, account-wide) is what's actually fixed, and it holds regardless of which explanation is right.

**THE FIX, both halves the report asked for.**
1. **Deferred off the initial load.** `useCompLocationText` now takes an `enabled` flag; `CompRow`/`TrashRow` thread it from `CompsPanel`'s own `active` prop ("is the Comps tab the one actually showing"). The synchronous fallback (county/coordinates) still renders immediately either way — nothing goes blank — but the network lookup itself is deferred until someone genuinely opens Comps. `CompDetail` (viewing one specific, already-opened comp) is left ungated — that IS the moment someone is looking at it.
2. **Persisted so a coordinate is geocoded once per device, not once per page load.** A successful resolution is now written to `localStorage` (`planyr:compPinAddr:v1`, bounded to 500 entries, oldest trimmed first) and the in-memory cache is seeded from it on module load — a returning visit starts warm. A FAILED lookup is deliberately NOT persisted, so a transient outage retries on the next load rather than being remembered as permanently unresolved.
3. **The GIS-cache flood MapServer call (1.45s, item (c) in the report) was checked and is NOT part of this bug.** It's `layers.js`'s normal fetch for a layer the plan has enabled (a Fort Bend flood contour layer), gated by the layer's own zoom gate and the `layerGateReady` latch (which already defers every layer ADD until the framed view settles) — it runs concurrently with everything else on the page, doesn't block interactivity, and isn't refetching anything already in hand. No change made there; said here so nobody re-investigates it as the same bug.
4. **Related, but explicitly out of scope for this item:** the Dashboard's own Comps card (`CompsCard.jsx`) has a THIRD, separate, unpersisted, uncached reverse-geocode implementation of the exact same pattern. It never appeared in this report (every one of the five "slow" reports is route `project`/`site`, none is the Dashboard), so it isn't touched here — filed separately as **B1497890** rather than silently left unnoticed.
