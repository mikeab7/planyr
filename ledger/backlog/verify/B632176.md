- Verify: live — **V322896** (`Blocker: real-data` — a colleague's real signed-in session is what caught this; the sandbox can prove the DOM location/CSS shape structurally but not a real ancestor's computed layout on his machine)
- **ROOT CAUSE, confirmed by the colleague's own measurements, not guessed at.** `SearchBox.jsx` rendered its results dropdown as a plain `<div style={{position:"absolute", ...}}>` nested directly inside the shared header toolbar row — a flex container that is `overflow: hidden` **on purpose**, to keep the toolbar itself from wrapping/growing. CSS `z-index` only resolves *stacking order among siblings that share a containing/stacking context* — it has no power over an ANCESTOR's `overflow` clip, which is a completely different mechanism (layout, not paint order). No z-index value fixes this; the dropdown was being cut at the toolbar's own bottom edge no matter how "on top" it claimed to be.
- **THE FIX IS REUSE, NOT INVENTION, EXACTLY AS INSTRUCTED.** `shared/ui/AnchoredMenu.jsx` (built for B837's Layers-panel `RowInfo`) already solves this: it portals its content to `document.body` via `createPortal`, positioned with `getBoundingClientRect()` off an `anchorRef`, so it physically leaves the toolbar's DOM subtree and can't be clipped by anything the toolbar does. `SearchBox` now renders `<AnchoredMenu open={showDropdown} anchorRef={inputRef} placement="below-left" hoverSafe>` around the exact same results JSX (loading state, result rows, live-search offer, no-results/drop-a-pin state) — the CONTENT is unchanged, only where it physically renders.
- **`hoverSafe` was a deliberate choice, not the default mode, to avoid a second regression.** `AnchoredMenu`'s default dismiss mode renders a full-viewport interactive backdrop (built for hover-triggered popovers like `RowInfo`, which don't need to be re-clicked). A search box is different — the user needs to click back into the input to reposition the cursor or keep typing while the dropdown is open, and a full backdrop would swallow that click and close the dropdown first. `hoverSafe` mode skips the backdrop and dismisses via a `document.mousedown` listener that exempts both the anchor and the panel — so clicking the input, or a result inside the dropdown, both work as a normal click, and only a click genuinely outside both closes it.
- **Toolbar `overflow: hidden` is untouched, per the explicit instruction not to remove it.** It's still load-bearing for the header's own layout; the fix works entirely by leaving the dropdown's DOM location instead.
- **Guard test, structural — proves the shape, not just that it compiles:** `test/foodModule.test.js` asserts `SearchBox.jsx` imports `AnchoredMenu`, renders `<AnchoredMenu anchorRef={inputRef} ...>`, and contains **no** `position: "absolute"` string anywhere (the exact shape that caused the bug) — so a future edit reverting to a plain absolutely-positioned div fails the build immediately instead of shipping the same clip again. A second test asserts `hoverSafe` is present on the `<AnchoredMenu>`, so the click-away regression this item deliberately avoided can't silently regress either.
