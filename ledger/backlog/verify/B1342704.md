- **THE OWNER'S NARROWING, honored exactly as instructed.** His report named the "+"/"−" glyphs precisely as "on-shape controls," ruled out every panel-level expander himself (Standards, Layers, Yield, the right-rail SITE ELEMENTS carets), and correctly identified the canvas-level double-click handler + the parking field's own on-shape row control as the suspect. That control's real name in the code is `featNode`/`glyphPlus`/`glyphMinus` — the ONE shared trio every on-shape "+"/"−" glyph in the planner renders from (dock-zone extend/pull-in, the dog-ear bump-out toggle, the employee-side sidewalk/parking add/remove, AND the car-parking row add/remove the owner actually pressed).
- **ROOT CAUSE.** These three glyphs render inside the shared `data-handle-layer` group (the ONE always-on-top manipulation-chrome layer, alongside every resize/rotate/vertex DRAG handle). `resolveDoubleClickTarget` (`featureTarget.js`, B233153) treats anything in that group as identification-transparent chrome and falls through to the feature underneath — the CORRECT rule for a drag grip, which performs no action of its own, and the WRONG rule for these three glyphs, whose `onPointerDown` ALREADY performs the control's whole action (grow/shrink a row, add/remove a zone) on every single press. So a double-click on one fired the action twice AND opened Properties for the feature underneath.
- **THE HARDER PART, and the reason a naive fix (a per-glyph `onDoubleClick={stopPropagation}`) was tried FIRST and FAILED.** Measured directly (a capture-phase event trace against the real running app): the glyph's own `onPointerDown` mutates the model on press 1, which re-renders and MOVES the glyph (or spawns a different one — e.g. growing a 1-row field to 2 rows makes a "−" appear near where the "+" used to be) before press 2 lands. The browser's own "a click's target is the common ancestor of its down and up targets" rule (the same B233153/NEW-2 mechanism already documented in `featureTarget.js`) then retargets `click#2`/`dblclick` to a common ancestor OUTSIDE the glyph's own `<g>` — so a `stopPropagation()` on that node never gets a chance to run. This is the SAME species of defect the existing double-click resolver already survives for ordinary features; it does not survive it for a control that relocates itself.
- **THE REAL FIX, at the same level the existing resolver already lives at (the canvas root), not on the glyph.** `gestureActionRef` (`SitePlanner.jsx`, beside the existing `gestureAnchorRef`) anchors a double-click gesture to whether PRESS 1 landed on an `[data-el-action]`-marked glyph — captured in the SAME capture-phase `onPointerDownCapture` that already stamps `lastPressRef`, so it is recorded whatever handler eventually wins the press, survives the glyph moving mid-gesture, and (unlike `gestureAnchorRef`) needs no live selection, since these controls also render on HOVER alone. `onBgDouble` checks it FIRST and swallows the double-click entirely (no Properties, nothing else — the control already did its job on each press) when it is set. `ACTION_ATTR = "data-el-action"` is a new, documented constant in `featureTarget.js` (deliberately the OPPOSITE of the existing `data-chrome`: opaque, not transparent), marking `featNode`/`glyphPlus`/`glyphMinus`. A per-glyph `onDoubleClick={stopPropagation}` is kept too, as a free first line of defence for the ordinary (non-relocating) case — but it is explicitly documented as NOT sufficient alone, so a future reader does not "clean up" the root-level fix believing the glyph-level one already covers it.
- **⛔ A REAL BUG FOUND AND FIXED WHILE BUILDING THIS: reusing `gestureAnchorTarget` (the existing anchor helper) with a dummy non-`"kind:id"` key silently broke the "press 1 keeps the anchor" continuation** — that helper always runs its result through `parseFeatureKey`, which requires a colon and returns `null` for anything else, so the pairing check reported "not still in flight" on every single press regardless of the actual time/distance match. Caught because the FIRST version of this fix passed the parking-field test (press 2 happened to also land on an action glyph, by coincidence of the growth math) but failed the building dock-zone test (press 2 landed on a plain resize-handle rect) — a discrepancy that would have shipped a fix that only worked by accident on the exact case tested. Fixed by importing `pairsWithLastTap` (`doubleTap.js`) directly instead, with no feature-key parsing involved.
