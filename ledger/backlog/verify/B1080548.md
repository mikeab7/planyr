- **THE ACTUAL BUG, and it is exactly the hard part the task named.** A predecessor/successor link pointing OUTSIDE the copied set (to a task left behind in the source) kept its RAW original numeric id on paste. Same-project, that's correct — the id still names a real task there. Cross-project, the destination has its own, unrelated id space of small sequential integers, so the raw id would either get silently pruned by the existing renumbering pass with no notice, or — the real danger — silently resolve onto whatever UNRELATED task happens to share that number in the destination, exactly the "collision silently rewires the destination's existing dependencies" the task warned against.
- **Fix (`public/sequence/index.html`, `pasteTaskAfter`):** a predecessor pointing at another task INSIDE the pasted set is always remapped to its new id (unchanged — this already worked). One pointing OUTSIDE the pasted set: same-project, kept as before (still resolves). Cross-project, now DROPPED rather than kept — and the paste toast reports exactly how many links were dropped ("Pasted 3 tasks — 2 links to tasks left in the source schedule were dropped"), LOUD-FAILURE style, so a paste that lost dependency logic is never silently indistinguishable from one that didn't.
