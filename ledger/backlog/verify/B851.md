- **⛔ THIS ×3 FIX CLOSES A DIFFERENT MECHANISM THAN THE ×2 FIX, AND CORRECTS THAT FIX'S OWN STEP 1b.** The ×2 investigation explicitly examined and REFUTED `carriedRef`'s "already carried" latch as a cause, reasoning that production `client_errors` held **zero** `schedule-route-grid-divergence` events, so "the carry-in always eventually reaches the right state." **That reasoning has a blind spot**, found this session while re-reading the carry-in effect line by line: the LOUD-FAILURE telemetry timer that would record a divergence is armed only *after* the latch's own early-return — `if (carriedRef.current === projectId && section === "projects") return;` sat BEFORE the `post()` call and BEFORE the `setTimeout` that arms the telemetry. So whenever the latch suppressed a re-drive, it suppressed the ALARM for that exact suppression too — a silent latch and a firing alarm cannot coexist in that control flow. Zero telemetry events is exactly what a permanently-stuck latch would also produce; it was never evidence the latch was innocent — the STANDING RULE #2 trap this repo has hit before (an instrument that could not have seen the effect is not evidence of absence), just not previously applied to this item.
- **THE ACTUAL MECHANISM, now traced fully.** `aPid` (which schedule the embedded app shows) is a single GLOBAL, MUTABLE field in the one shared `hs-v1` blob — not scoped to a route, a tab, or a session. The carry-in effect's job is to re-drive it toward the routed project's own linked schedule whenever they disagree. `carriedRef` was meant only to stop that re-drive from fighting a DELIBERATE pick of a cross-cutting unlinked schedule (Pursuits/Operations) — but it actually latched on the ROUTED PROJECT alone: the first time the carry-in successfully landed the correct schedule for a given `projectId`, `carriedRef.current` was set to that `projectId` and STAYED there for as long as the route didn't change — even across a LATER, unrelated write that moved `aPid` away again (a second tab, a stale reconciliation, or simply time passing while the user worked elsewhere in the app). Once that happened, `needsScheduleCarryIn` correctly said "needs carry-in" again, but the very next line's latch check swallowed it before `post()` ever ran — so the grid was stuck on the wrong project **permanently**, with the crumb (which resolves straight from the route, never from `aPid`) reading correctly the whole time. That is precisely the owner's screenshot.
- **Fix, two parts (`src/workspaces/scheduler/lib/navState.js`, `src/workspaces/scheduler/Scheduler.jsx`):** (1) the `carriedRef` latch is REMOVED outright — its one legitimate job (never yank back a deliberate cross-cutting pick) was already correctly covered by the existing `pickShowing`/`explicitPickRef` signal, so the carry-in effect now re-drives on every genuine mismatch, forever, with no "already did this once" memory at all. (2) a NEW hard render gate, `isGridMismatched` (navState.js) — while the grid's active schedule isn't one of the routed project's own linked schedules (and no deliberate pick is showing), the iframe is HIDDEN and a brief "switching" loader shows instead, so a mismatch can never be visibly rendered even for one frame, regardless of what causes `aPid` to drift or how long re-convergence takes. `findBySiteId` also gained a sibling `findAllBySiteId`, since NEW-3 (B1080547, same session) lets a project carry more than one linked schedule — the mismatch/carry-in checks now test membership in the FULL linked set, not just the first match, so switching between two of a project's own schedules can never itself read as a mismatch.

- **RECONCILED, not re-derived: the ×3 fix is genuinely correct AND genuinely insufficient, and both things are true at once.** `isGridMismatched(projects, siteId, activeId, pickShowing)` in `navState.js` is a pure function and its own unit tests (V601824) are sound — they were never wrong. The defect is its INPUT, not its logic: `activeId` is Scheduler.jsx React state, updated ONLY when the embedded app posts `planar:nav-state`. `public/sequence/index.html` (B850) silently self-reloads a backgrounded tab that polls a newer cloud version (every 20s + focus/reconnect/tab-switch) — `if (saveStatusRef.current === "saved" && document.hidden) window.location.reload()`. After such a reload the iframe shows whatever the shared, GLOBAL `aPid` field now says (which can have drifted while this tab was backgrounded/reloading — the same "single shared field, not scoped per tab" root cause the ×3 fix already named), but the shell's `activeId` belief still holds the PRE-RELOAD value until a fresh nav-state lands. So the gate was comparing route-vs-BELIEF, never route-vs-GRID — and a stale belief that happens to already read "matched" sailed straight through it.
- **Fix (`src/workspaces/scheduler/lib/navState.js`, `src/workspaces/scheduler/Scheduler.jsx`): a new `navConfirmed` dimension makes the gate fail CLOSED across a reload, not just self-heal after one.** `isGridMismatched` gained a 5th param, `navConfirmed = true` (default preserves every pre-×4 caller's exact behaviour) — when `false`, the gate ALWAYS reads mismatched, regardless of what the (necessarily stale) `projects`/`activeId` belief says. Scheduler.jsx threads a `navConfirmedRef`/`navConfirmed` pair through the two places that actually observe the shell↔iframe boundary: `onIframeLoad` (which fires on the iframe's `load` event — a plain browser guarantee that holds for the embedded app's own internal `window.location.reload()` exactly as much as for the initial `src` load) resets it to `false` before anything else, and the `planar:nav-state` message handler is the only place that sets it back to `true` (immediately before `markReady()`), meaning it can only ever be re-confirmed by a genuine announcement FROM the current load. A second latent bug in the same mechanism was fixed alongside it: `onIframeLoad`'s retry loop (`ask()`, which politely re-requests nav-state) was gated on `readyRef.current` — a one-way latch that's already `true` after the very first successful boot — so every retry after a reload was a silent no-op; it now gates on `navConfirmedRef.current` instead, so a reload gets its own fresh round of active re-requests rather than depending entirely on the reloaded document's own passive announce. **LOUD-FAILURE:** a new 8s-after-`ready` telemetry event (`schedule-nav-unconfirmed`) fires if a load's nav-state is never confirmed at all, so a stuck "switching…" loader is never silently unexplained in telemetry (mirrors the existing `schedule-route-grid-divergence` timer the carry-in effect already had).
