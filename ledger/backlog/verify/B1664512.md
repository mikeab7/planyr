`[x]` **FIXED AND SANDBOX+LIVE-HEADLESS VERIFIED.** In the shipped chunk the drive-target predicate (`driveJunctionsOf`, SitePlanner.jsx) was `t && !t.points && typeof t.cx === "number" && t.w > 0 && t.h > 0` — any polygon-drawn element (a free-drawn pad or parking field) was excluded outright, so a road could never fillet into one, only into an axis-aligned rect. The SAME exclusion existed one level up, at the TOPOLOGICAL connect gate (`driveTargetKind`/`driveTargetsOf`/`findDriveConnect`) that decides whether a road even records a `driveTee` relationship in the first place — both had to change or the render fix would never fire.
- **THE FIX.** Two new pure primitives in `roadGeometry.js`, in the exact shape `nearestRectEdge` already consumes so it works on either without change: **`polygonEdges(points)`** (the polygon analogue of `rectEdges` — outward normal per edge, oriented away from the polygon's own centroid) and **`polygonContainsPoint(P, points)`** (a real ray-cast, correct for a CONCAVE ring — `rectContainsPoint`'s "inside every edge's half-plane" shortcut only holds for a convex shape, and a hand-drawn field is not always convex). **`polygonDepthBehind(points, at, inwardNormal)`** replaces a rect's trivial `w`/`h` read for the curb-return radius clamp — the max projection of every vertex onto the inward normal from the hit point, which can only ever OVER-estimate depth on a concave ring (never under), so it can only ever under-clamp a return, never let one punch out the far side of the field.
- `driveJunctionsOf` (the render), `driveTargetKind`/`driveTargetsOf` (which targets exist), and `findDriveConnect` (the weld-time magnet) all now branch on `Array.isArray(el.points)` to use the polygon primitives instead of the rect ones — the rect path is completely untouched (same functions, same behaviour) for every existing rect target.
- **VERIFIED:** `test/roadGeometry.test.js` (+7 tests) — `polygonEdges` matches `rectEdges` exactly on the same square footprint, `polygonContainsPoint` matches a half-plane test on a convex ring and is CORRECT (unlike a half-plane test) on a concave L-shaped ring, `polygonDepthBehind` measures the true far-edge distance. `test/roadDriveJunctionFillet.test.js` (+5 tests, "NEW-2" describe block) — a road tee-ing into a polygon-drawn rectangular field across a 0–89° angle sweep dissolves to one connected, simple region exactly like the rect-target suite (including the same 45° no-notch check), AND connects cleanly into a genuinely CONCAVE (L-shaped) field without crashing. `npx vitest run` — 856 files / 17,490 tests, all green. `npx eslint` — 0 new errors.

`[x]` **THE REAL ROOT CAUSE, found live (a static code read alone did not catch it — the shipped code LOOKED correct and read as though B1664512 above had already fixed it).** `driveTargetKind`/`driveTargetsOf`/`findDriveConnect` (the CONNECT decision) and `driveJunctionsOf` (the RENDER decision) both DO branch on `Array.isArray(el.points)` exactly as B1664512 describes — but BOTH carried the SAME extra precondition, `typeof el.cx === "number"`, run UNCONDITIONALLY before that branch. `closeElPoly` (SitePlanner.jsx) commits a freshly free-drawn polygon element as `{ id, type, points, rot }` — no `cx`/`cy` at all; a centroid is synced in only on the element's FIRST reshape (a vertex drag), via `frameBBox`. So a polygon field, from the moment it is drawn, fails `typeof el.cx === "number"` and is silently treated as "not a target" in BOTH places — proven live with a temporary debug dump of the raw elements: `driveTargetKind` rejected the field outright at connect time (no `driveTee` stored at all); after the FIRST half of this fix, `driveTee` WAS being stored correctly, and it was `driveJunctionsOf`'s OWN copy of the identical `typeof T.cx !== "number"` check that then discarded the junction at render time — two independent copies of one wrong precondition, and B1664512's own live-headless verification never exercised either, because its test suite (`polygonJunctionScenario` in `test/roadDriveJunctionFillet.test.js`) replicates `driveJunctionsOf`'s MATH directly, bypassing the connect-decision layer these two functions live in entirely — invisible to any pure geometry test by construction.
- **THE FIX:** reordered both preconditions so `cx` gates only the RECT branch (the one place either function actually reads it, `rectEdges(x.cx, x.cy, …)`), never the polygon one: `driveTargetKind` → `Array.isArray(el.points) ? el.points.length >= 3 : typeof el.cx === "number" && el.w > 0 && el.h > 0`; `driveJunctionsOf` → the same shape, `isPoly` computed first.
