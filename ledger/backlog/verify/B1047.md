`[x]` **⏳ merged — V481 PENDING (Verify: live — `Blocker: real-data`).** Measured: **median frame 20 ms, p90 80 ms, p99 140 ms, max 320 ms over 1,525 frames** of scripted drag — one frame in ten costing five times the 16.7 ms budget. The SVG is NOT a memory driver (4,579 elements, flat across every phase; ~420 MB of the reported 555 MB lives outside the JS heap — see B1049) but it IS the frame-time driver, because cost scaled with the size of the whole model rather than with what is on screen.

`lib/viewCull.js` (new, pure) computes the visible world rectangle from `screenToWorld` on the viewport corners plus a generous margin, bounds each drawable, and filters the element / markup / parcel passes to what the view can reach. Three guards make it safe: the selection and anything mid-drag are force-kept whatever their bounds say; an element whose shape can't be bounded is NEVER culled; and a plan under 40 drawables isn't culled at all (the filter would cost more than it saves).

**The hard constraint is enforced in one place.** `buildExportSvg` clones the LIVE `<svg>`, so `withFullRender` flips culling off, flushes a synchronous full render (`flushSync` — a normal state update would land a frame LATER, i.e. after the clone, and the PDF would quietly print only what was on screen), clones, then restores. `test/viewCull.test.js` asserts the export element count is **independent of the current view** from three very different viewports, that the screen pass at those same views draws strictly fewer, and that every element is visible from SOME view (culling hides nothing permanently). LOD/declutter behaviour is untouched.

Headless, on the real app: `ui-audit/diagnose-map-lock.mjs` reads the drawn set at 125 elements, 64 after panning away, and 125 again on return — culling engages and everything comes back.
