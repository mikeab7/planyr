### B2194744 — The tax table did not render for a Harris lot with no stored account (the 158.20 AC lot) `[Site Planner]` (bug) #site-planner #parcel #gis  *(owner real-data check via Cowork on build a84b189, 2026-10-08 1:58 PM CT: SCHIEL's table showed, the 158.20 AC lot (0421030000129) showed none although `/api/taxunits?county=harris&acct=0421030000129` returns complete:true.)*
`[ ]` **⏳ merged — V1607568 PENDING (Verify: live).**
- **Root cause (measured):** `taxUnitsClient.accountOf` took its account from `attrs[idField]` else the stored `parcel.acct`, and `SitePlanner` passed `COUNTIES_MAP[county].idField` — which is always `undefined` (the registry keeps `idField` on `COUNTIES`). So only a lot with a stored `acct` ever fetched. **36 of the 136 Harris lots in production have no stored `acct`** (the 158.20 AC lot among them); SCHIEL worked only because the B2194740 backfill had stamped its `acct`. Checked every Harris lot: 0 have a mismatched account, 36 have none.
- **Fix:** `accountOf` asks the county record (`countyRecord(attrs)`) first, stored `acct` last; the planner passes the registry's real `idField`. `test/taxUnitsClient.test.js` (the lot with `acct: null` / `HCAD_NUM 0421030000129` resolves; OBJECTID is never answered). `verify-parcels-followup.mjs` gains a live arm (runs against a deployed https BASE_URL): a Harris lot with no stored account shows `parcel-tax-table`.
- **Name question:** the row name TRS 1B-10 -> BAUER HOCKLEY 550 LP is a **derived** display name, not an overwritten stored one: the lot's stored `label` is still null (row rev 2, untouched since 2026-09). Unnamed lots are named situs -> owner -> first legal line (`parcelFallbackName`); the owner column `owner_name_1` was not recognised before B2194737, so the ladder fell to the legal line. Nothing to restore from a snapshot; the owner can type a name on the page to pin one.
