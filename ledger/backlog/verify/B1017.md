DEDUPE-FIRST: a NET-NEW second-order defect inside the outline-cut render **B1009 introduced**, not a recurrence of it — B1009's own symptom (the target's outline ruled straight across the drive mouth) is genuinely fixed; this is a different failure of the same code at rot 90/270, so it takes its own number and cross-references B1009 / V455 step (b). `[ ]` **⏳ merged — V463 PENDING (Verify: live — `Blocker: real-data` + PDF/export parity).** A drive junction can no longer throw geometry outside the footprint of the element it tees into, at any rotation.
- **Root cause (AUDIT-FIRST, confirmed against the code, matching the owner's diagnosis to the foot).** The `if (outlineCut)` block in `SitePlanner.jsx` builds the interrupted-outline corners in **WORLD feet** — `corner(lx,ly)` rotates the local half-extents about the element centre, so `el.rot` is already baked in — and then pushed those polylines straight into `parts`. `renderElPx` returns `parts` inside a `<g transform="rotate(el.rot, c)">`, so **`el.rot` was applied twice**. rot 0 / 180 are unaffected (0° / 360°); rot 90 / 270 land at 540° ≡ 180°, and a rectangle rotated 180° about its own centre is congruent to the unrotated one — so a 42×150 field drew its outline as 150×42 about the same centre, overhanging (150−42)/2 = 54 ft each way (the west half hidden under the building, `Z_LAYER` building 5 > parking 3, which is why only the east overhang was visible). The **second-order symptom** the owner also saw follows from the same line: `outlineCut` sets the plain `<rect>`'s stroke to `none` on the assumption the polylines replace the outline, so at rot 90/270 the field lost its real edge entirely and the only line left on the correct footprint was the derived `curbEdgesOf` band. The adjacent pond baseline ghost and `pondContourEls` already counter-rotate with `rotate(-el.rot)` for exactly this reason — this block skipped it.
- **Fix.** The geometry moved into a pure, documented `rectOutlineCutSegments(el, cutters)` in `lib/roadNetwork.js` (world feet in, world feet out, with the frame contract stated in its header so the next consumer can't repeat the mistake), and the render wraps its polylines in `<g transform="rotate(-(el.rot||0), c)" data-testid="rect-outline-cut" data-el-id={el.id}>` — the same counter-rotate the pond ghost and the stage contours use. With the rotation net-identity the footprint outline is back on the true edge and interrupted only at the drive mouth, so the blanked rect stroke is no longer a hole.
- **Sandbox-verified — and the guard was proven to FAIL on the pre-fix code, not just asserted.** New `test/junctionOutlineCut.test.js` (23 cases): the pure segments' bbox equals the element's true rotated footprint bbox at rot 0/90/180/270 and at oblique rotations; a drive interrupts the outline without pushing anything outside the footprint; the removed length equals exactly the mouth crossings; and the render-frame half asserts the counter-rotate wrapper composes to the identity. Reverting `SitePlanner.jsx` to pre-fix `main` turns that half red. The same file also reproduces the pre-fix composition numerically and proves it was **right at rot 0/180 and transposed at rot 90/270** — the exact reason every earlier rot-0 mock passed while the plan rendered broken.
- **Headless-verified through the REAL render path on the owner's real element set.** New `e2e/junction-outline-cut.spec.js` seeds `ui-audit/fixtures/tsakiris-concept-a.json` and measures the drawn outline against the element's OWN `<rect>` in the live DOM (so the check needs no unit math and is immune to the fit-to-extent zoom): **6/6 green** — the owner's rot-270 field, a rot-90 parking field, rot-0 and rot-180 regressions, a rot-90 paving pad with a truck-court drive, and the export-clone parity case. The rot-90/0/180/paving cases are the SAME real target+drive pair rotated about the target's own centre and moved clear of the plan, so every one goes through the real junction solver. **Confirmed to FAIL on the pre-fix behaviour:** with the counter-rotate removed, rot 270 / rot 90 / the paving pad all report the outline projecting **~35 % of the footprint's diagonal** past its left edge while rot 0/180 still pass — the reported defect, reproduced and then eliminated.
- **PDF-PARITY.** `buildExportSvg` builds the export by cloning the live canvas node, so a transform bug on screen rides straight into the PDF and the PNG. The export case reproduces that clone in-page, re-measures inside it, and asserts the counter-rotate attribute survives verbatim and no outline projects past any footprint edge — it fails on the pre-fix render alongside the on-screen cases.
