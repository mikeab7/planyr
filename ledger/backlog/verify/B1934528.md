`[x]` **ROOT CAUSE, found by tracing every reader of `siteLabel` back to where it's set.** `SitePlanner.jsx`'s `siteLabel` is a plain `useState` captured ONCE at mount from `restored.site`, updated only by `commitSiteLabel` (called from `renameProjectFromHeader`'s `id === groupId` branch). Empirically (see the mutation-tested e2e spec below), the header breadcrumb's own row-rename dropdown — the "..." kebab menu on a project row, reachable from EITHER the Map-mode or the Plan-mode header, and on the CURRENTLY open project or any other — commits through `ProjectBreadcrumb.jsx`'s own uncontrolled project registry (`shared/projects/projects.js`'s `storeRename`), never through the `onRenameProject` prop `SitePlannerApp.jsx` wires to `renameSite`/`renameProjectFromHeader`. So that whole UI surface never touches `commitSiteLabel`, and any SitePlanner instance already mounted for the renamed project (in particular one left open-but-hidden in Map mode — `SitePlannerApp` never unmounts it, `goMap` only flips `mode`, keeping `activeSiteId` for the Leaflet keep-alive) kept the STALE name for the rest of its mount. `ProjectBreadcrumb.jsx` itself never showed this, because it resolves the CURRENT name live off the sites list on its own "planarfit:sites" storage-event listener (`resolveCurrentName`) — exactly the mechanism `siteLabel` was missing.
`[x]` **FIX — `siteLabel` now resyncs off the SAME storage-event channel `ProjectBreadcrumb.jsx` already trusts.** A new effect in `SitePlanner.jsx` listens for the synthetic "planarfit:sites*" `storage` event `storage.js`'s `notifySitesListChanged()` fires on every rename (local, row-menu-driven, or landing from a cloud pull) and re-reads the group's authoritative name via `loadSite(siteId)` (which itself resolves the group's authoritative name per plan, per `projectName.js`'s `resolveNameFor` — the SAME answer the breadcrumb trusts, not a second derivation), updating `siteLabel` only when it actually changed. Safe unconditionally: nothing in this component binds `siteLabel` to a live-typed input, so there is no in-progress edit this could ever clobber. Every consumer of `siteLabel` picks this up for free — the exhibit title block + header line (`PrintCompose.jsx`'s `Field label="Project"` and the composer's own caption), the default PDF/PNG filename (`sheetFileName({project: siteLabel, ...})`, which also feeds the browser tab's title for the downloaded PDF), the KMZ export filename, and the Yield panel header.
`[x]` **Other project-name derivations checked for the same staleness, per the brief's own ask.** The browser TAB title (`Shell.jsx`'s `pageTitle`) is keyed on the active MODULE, never the project name — not affected. Library/Notes/Model/Schedule headers all derive their displayed project name through `ProjectBreadcrumb.jsx`'s own live `resolveCurrentName` (confirmed by grep: no other workspace holds a `useState` mirror of a project name captured once at mount) — the Site Planner's `siteLabel` was the ONE place with this exact anti-pattern. No other fix needed.
