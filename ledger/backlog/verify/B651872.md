- **ROOT CAUSE, the (×2) recurrence — Leaflet's own tile fade-in, not the origin/reset mechanics B651872 already fixed.** Live proof the fade is the WHOLE problem and nothing else is wrong: the owner ran `document.querySelectorAll('.leaflet-tile').forEach(t=>t.style.opacity=1)` in the console on the live, broken page and the map rendered perfectly — correct location, correct zoom, selected pin ringed. `GridLayer._tileReady` (`node_modules/leaflet/dist/leaflet-src.js`) branches on `this._map._fadeAnimated`: when true, a loaded tile is set to `opacity:0` and handed to ONE shared `requestAnimFrame` handle (`this._fadeFrame`) that steps every tile's opacity up each frame — a single shared rAF chain that a burst of tiles loading in quick succession (exactly what a big flyTo jump triggers) can apparently leave orphaned partway, for reasons independent of the origin/reset fix. When `fadeAnimated` is false, `_tileReady` instead marks the tile `active` immediately with **no opacity manipulation at all** — nothing to ever get stuck. FIX: `fadeAnimation: false` at map construction — not a `setTimeout`/`setInterval` forcing opacity, which the owner explicitly asked NOT to do.
- **ROOT CAUSE, the (×3) recurrence — `flyTo`'s own distance-proportional duration, NOT a fractional landing zoom.** The owner's own hypothesis (check `zoomSnap`/`zoomDelta`, whether the target zoom comes from a `fitBounds`) was verified and refuted for this code path: both are Leaflet's untouched defaults (1), and the zoom passed to `flyTo` here is always a literal integer (`Math.max(map.getZoom(), FLY_TO_ZOOM)`), never a `fitBounds`-derived fraction — confirmed by instrumenting a real Leaflet map (not a paraphrase) and logging every `_move`/`_setView` call through a live Houston→Maui flight. **What's actually happening:** `map.flyTo` with no `duration` option computes one from real-world distance via Leaflet's own van-Wijk/Nuutinen curve — measured directly against the real formula: ~1.6s for a same-neighbourhood hop, ~2.4s Houston→Katy, ~4.2s Houston→Austin, **~7.8s Houston→Maui**. For a jump that long, the animation continuously sweeps through EVERY integer zoom between start and destination (12 down to ~5, back up to 16), and GridLayer creates/tears down a tile level at each one it passes through — the "two levels, one fractional-scale, one 0-children" snapshot the owner measured is not a stuck state, it's a NORMAL mid-flight frame of an animation that was still running when it was measured (its own natural landing was still several seconds away). Confirmed by instrumenting the identical flight to run to its true, natural end, repeatedly (4 trials, both with the tile server's baseline latency and realistic 150-350ms jittered latency): it always settles to exactly one level, `scale(1)`, an integer zoom — the existing hard-reset from the (×1) ship is not flaky. The bug is that the flight simply takes too long for the user to perceive as landed before it visibly is.
- **THE FIX, this recurrence: cap `flyTo`'s duration at a fixed 1.5s** (`FLY_DURATION_SEC`, `FoodMap.jsx`) — measured to match what a local jump already takes naturally, so a same-neighbourhood search feels unchanged, while a cross-metro/city/country jump no longer balloons to several seconds. Not a redraw or a timer patched over the symptom (the owner's explicit "do not paper over it" instruction) — it directly shortens the window the animation spends sweeping through unneeded intermediate zoom levels, so the destination's own tiles start loading sooner and the flight settles before the user is watching for it to.

Confirmed by reimplementing `flyTo`'s own van-Wijk/Nuutinen curve and finding the MINIMUM zoom each jump sweeps down to (`.scratch-repro/measure-zoom-depth.html` this session): Katy (~48km, same metro) only dips to z11.7 from z12 — negligible; Austin (~235km) dips to z9.6; Maui (~6128km) dips to z5 — matching the owner's own live capture exactly. - **HOW IT WAS FINALLY REPRODUCED, per the owner's own instruction on how the prior session's attempt fell short.** The prior session's harness used plain `page.setViewportSize()` at a narrow width — Chromium's `isMobile` device-emulation flag (which `page.setViewportSize()` alone does NOT set) changes viewport semantics in ways a plain resize doesn't. This session used Playwright's real device descriptor (`devices['iPhone 14 Pro']` — `isMobile:true, hasTouch:true` together) against the REAL running dev build (not a synthetic stand-in), drove the real "drop a pin" flow (search needs network, blocked in this sandbox; drop-a-pin needs none and exercises the identical `BottomSheet`/`FoodMap` mount path) to get the sheet open, then used `page.setViewportSize()` to grow/shrink the REAL viewport height — a genuine trigger of `index.css`'s real `100dvh` sizing (`html, body, #root { height: 100dvh }`, B168 — "so mobile browser chrome can't crop the bottom of the canvas"), which is exactly what Safari's own chrome collapsing/expanding does. Confirmed live: `#root`'s height genuinely changes; the map host's own `getBoundingClientRect().top` never moves (top-anchored, below the fixed-height `AppHeader`) while its height grows/shrinks — the real trigger, reproduced without needing real Safari.
- **ROOT CAUSE, traced into Leaflet's own source, not guessed.** `.leaflet-map-pane`'s CSS transform went from `matrix(1,0,0,1,0,0)` to `matrix(1,0,0,1,0,60)` after growing the viewport by 120px — Leaflet's own `invalidateSize()` (`leaflet-src.js`) pans the map by HALF the size delta (`oldCenter.subtract(newCenter)`) by DEFAULT, which assumes a resize is symmetric around the container's centre. This app's layout never is: a fixed-height `AppHeader` sits above a `flex:1, minHeight:0` map host, so the host's top-left edge is permanently anchored and only its BOTTOM edge ever moves. The half-delta pan shifts already-rendered tiles inside a container whose own top edge never moved — the pane's new top lands mid-container with nothing painted above it. That is the "clean horizontal line, grey on top" the owner described exactly: not a ragged tile edge (which a stale-size guess would produce), a precise, uniform offset (which a wrong PAN produces).
- **THE FIX, two parts, both needed — confirmed by testing each alone first.** (1) The B651872 (×4) ResizeObserver's own `invalidateSize({animate:false})` call gained `pan:false` — this app's layout is ALWAYS top-anchored, so the default symmetric compensation is never correct here. Tested alone: the grey band persisted. (2) `trackResize:false` at map construction — Leaflet's OWN default (`trackResize:true`) independently binds `window`'s `'resize'` event straight to `this.invalidateSize({debounceMoveend:true})`, with NO way to pass it `pan:false`. The ResizeObserver (which watches the real container, not just `window`, and is already fixed) fully supersedes what `trackResize` was for. Both together: `.leaflet-map-pane`'s transform stays `matrix(1,0,0,1,0,0)` through growth, shrink-back, AND a simulated rotation (width/height swap) — the tile container's real screen position tracks the map host's real position exactly, every time.
