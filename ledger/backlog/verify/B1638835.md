### B1638835 — Route commits are undocumented and unguarded: nothing stops a second writer from being added silently `[App shell]` (task) #infra #ui #testing  *(same dispatch as B1638832, arrived as NEW-4 — an instrumented click showed a `popstate` firing ~1ms ahead of the `hashchange` the app listens to, read as "the router runs twice per navigation," with the request to "make one navigation commit the route once, from one place, and assert it with a test… so a second writer cannot be added silently later." Minted **B1638835** from the same reserved block. DEDUPE-FIRST — searched Open/⏳Verify/Done for "popstate", "single writer", "location.hash write": no prior item audits or pins the set of direct `window.location.hash` writers; `test/dashboardHashSync.test.js` (Done, B1213312) guards a related but different class — a stale READ of the hash, not a second WRITE of it. Net-new.)*
`[x]` **INVESTIGATED AND RE-CHECKED FIRST, per this session's own house rule not to restate a claim as settled fact without re-measuring it — THEN THE REQUESTED GUARD WAS BUILT.** `git grep` for `addEventListener("popstate"` across all of `src/` finds **nothing** — no code in this app ever listens to `popstate`, so the early event the investigation captured has no observable effect on React state; only `hashchange` drives `useHashRoute`'s `route` state, and it fires exactly once per hash write. The popstate/hashchange pair is a well-documented, browser-native side effect of assigning `location.hash` directly (a same-document navigation queues a `popstate` ahead of the `hashchange` task) — not application code dispatching anything, and not itself a bug; the dispatch's own text already flagged this half as "not itself user-visible." `pushState`/`replaceState` are confirmed never called for an ordinary navigation (`route.js`'s `navigate()` assigns `location.hash` directly, which is what a hash route needs to stay refresh-stable with no server-side catch-all — see that file's own header). **The real, adjacent risk the investigation correctly named** — "anything arriving late... meets a navigation already in flight" — is a genuine class this repo has already fought once (`test/dashboardHashSync.test.js`, B1213312: a kept-alive workspace's own URL-sync effect overwriting a just-written Dashboard hash) and this session closed a SECOND instance of (B1638832's Scheduler carry-out effect). Both routed through the ONE canonical writer (`navigate()`) rather than a second hash-assignment site — the actual gap was that nothing enumerated or pinned the COMPLETE set of places allowed to write `window.location.hash` directly, so a third one could be added anywhere with no review and no test to catch it.
- **The fix (the instrument the dispatch asked for).** `test/routeSingleWriter.test.js` — a source-level sweep of every `.js`/`.jsx`/`.mjs` file under `src/` for a direct `window.location.hash =` assignment, pinned against a reviewed, documented allowlist of the exactly THREE that exist today: `route.js`'s `navigate()` (the canonical writer every module tab, breadcrumb pick and cross-module intent goes through), `Shell.jsx`'s `goDashboard()` (writes the Dashboard's literal hash directly because it isn't a `{module,projectId,cross,org}` value `navigate()`'s partial-merge shape can express — B1213312's own documented reason), and `AccountControl.jsx`'s "Admin" menu row (`#/admin` is deliberately not a module slug for the same reason). A fourth site anywhere in `src/` fails the build by name until reviewed and added to the allowlist; an allowlist row with no matching site left in the source fails too, so the list can't rot stale either. A companion assertion pins that no code anywhere adds a `popstate` listener, so if one ever does, this guard is the one that notices and re-opens the "does this actually commit twice" question rather than letting it pass unnoticed. A mutation proof confirms the detector catches a synthetic third writer.
