**THE TWO REPORTED EXPLOITS, both reproduced live in a rolled-back production transaction before any fix was written (11 of 24 new checks failed on the untouched guard — see "MUTATION-PROOF" below for the exact baseline).**
- **(a) OLDER STAMP WINS.** The guard returned early the moment `NEW` carried *any* real `siteRenamedAt` — presence, not recency. A write carrying a stamp of `1` (or any real-but-older stamp) plus a stale name passed outright and overwrote a row whose stored stamp was current. Fixed: the incoming stamp must now be **strictly greater** than the row's own stored stamp to count as a genuine rename — an **equal** stamp loses too, exactly like no stamp at all.
- **(b) COLUMN-ONLY WRITES WERE UNGUARDED.** The revert branch was gated on `(new.data->>'site') is distinct from (old.data->>'site')` and only repaired the `site` **column** inside that same branch. A write that changed only the column (`update sites set site = '…'`, `data` untouched) skipped the branch entirely, leaving the column and the jsonb copy disagreeing about the project's name. Fixed: the guard now reasons about the **effective name** (`coalesce(old.site, old.data->>'site')`) and reconciles both copies back to it whenever either one disagrees, regardless of which copy the caller touched.

**`rename_stamp` TIGHTENED, same session.** It accepted numeric STRINGS in addition to numbers, and any positive value — so the number (or the string) `1` read as a "real" rename time (epoch-ms `1` is 1970-01-01T00:00:00.001Z). Tightened to exactly ONE representation — a JSON **number** only, no numeric-string tolerance (no real writer here has ever produced a string; the client and every SQL writer serialise via `to_jsonb(bigint)`) — and to a plausible epoch-ms **range**, 2024‑01‑01 through 2100‑01‑01, comfortably below every real stamp on record (~2026) and comfortably above zero. This is defense in depth, not the primary fix: (a)'s strict-recency compare already refuses `1` on its own (it's never `>` a row's real prior stamp), but an implausible value should never parse as a stamp at all.

**LOUD-FAILURE, and a false-positive trap caught while building it.** A refused/reverted write now `RAISE WARNING`s (Postgres/Supabase logs) and inserts one row into the existing `public.client_errors` telemetry sink (`source = 'event:rename-guard-refused'`) — the silence was exactly why the original exploit took four rounds and a retraction to find. **The trap:** the overwhelmingly common write that reaches this branch is an ordinary POST-RENAME content save, faithfully carrying the SAME name and SAME (now non-newer) stamp forward — its own comparison is never `>` (it's equal), so a naive implementation would warn and log on **every single autosave after any rename**, not just an attack. Fixed by comparing what the write actually **proposed** against the effective name/stamp before deciding whether anything needs correcting or reporting; an ordinary matching save takes the early "nothing to correct" exit and stays completely silent. Proven both ways (case 6/6b below).

**A THIRD ISSUE, found and fixed while proving the guard change was SAFE, not requested by the dispatch but necessary to ship it without a new regression.** `rename_site_group()` computes the stamp it asks for client-side, from `Math.max(Date.now(), newest-LOCAL-stamp + 1)` — a device whose local cache doesn't include every plan in a group could legitimately name a value lower than a stamp already sitting on a row it hasn't seen. With the guard now STRICT, that row would refuse while its siblings (whose lower stored stamps do clear the caller's value) accept — reopening exactly the split-name defect `rename_site_group` exists to close, this time caused by the security fix itself. **Proven live, staged:** applying ONLY the trigger fix to production and re-running the suite left 22 of 24 green and reproduced the split directly — `p_g2a=Two` (refused) vs `p_g2b=Two Renamed` (accepted) on a two-plan group whose caller-supplied stamp was below one member's real stored stamp. Fixed in `rename_site_group.sql`: it now computes the stamp it actually writes as `greatest(caller's value, the group's own current max real stamp + 1)`, read from the SAME rows the update is about to touch — strictly newer than every row in the group by construction, so the guard can never partially refuse a genuine group rename regardless of what any one caller's local cache knew.
