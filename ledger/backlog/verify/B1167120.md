- **Root cause, exactly as the owner diagnosed it — the MECHANISM that fed 292, not just the symptom.** `HelpReportControl.jsx` fixed `bottom:292` unconditionally. That number is not arbitrary — it is the literal sum of three constants from a DIFFERENT file (`SitePlanner.jsx`, via `sheetFurniture.js`'s `FAB_RESERVE_PX`), computed once by hand at ship time and then frozen into the shell as a plain number with no reference back to where it came from: the narrow-width "✎ Tools" FAB occupies `bottom:16` to `bottom:16+38≈54`; `FAB_RESERVE_PX` (62) raises the furniture row (scale bar/north arrow) above it to `bottom:40+62=102`; the 4-button zoom/report-slow stack sits at `bottom:100+FAB_RESERVE_PX=162` and is `4×30=120` px tall, so its own top edge lands at `bottom:162+120=282`; +10px clearance gives **292**. **The actual defect is that this derivation was copied as a LITERAL NUMBER into a file that has no import, no reference and no runtime relationship to the constants that produced it** — `HelpReportControl.jsx` and `SitePlanner.jsx`'s zoom stack shared no code, so the "292" could never adapt when the thing it was derived from wasn't on screen (every route except the narrow Site Planner canvas), and could never be recomputed if `FAB_RESERVE_PX` or the stack's button count ever changed. A schedule route and a project-model route have no Leaflet map and no Site Planner canvas at all, so the reservation there was pure waste; at the owner's viewport (1191×465) that put the button 63% of the way up the screen, under "Imagery & layers". **The fix below closes this at the mechanism, not just the symptom**: the control now reads the real DOM instead of a hand-copied number, so there is no second place for a future FAB_RESERVE_PX-style constant to drift out of sync with.
- **THE FIX — measure, don't reserve.** New `src/shared/ui/cornerClearance.js`: given a control fixed at `right`+`width`, it scans two kinds of real DOM occupant — Leaflet's own `.leaflet-bottom.leaflet-right` corner container (attribution + the graphic scale), and anything marked `data-canvas-corner="<name>"` — keeps only the ones that actually OVERLAP the control's own horizontal column (which is what makes desktop free of the reservation: the docked tool rail insets the Site Planner canvas's furniture away from the true viewport edge there, so its rect simply stops overlapping, with no breakpoint branch needed), and returns the tallest one's clearance plus a small gap, or a small base offset when nothing is there. `SitePlanner.jsx`'s narrow-width zoom stack and "✎ Tools" FAB now carry `data-canvas-corner` so they're found without HelpReportControl importing anything from the Site Planner workspace (which would break the Shell's "never statically import a lazy workspace" rule). `HelpReportControl.jsx` re-measures on mount (`useLayoutEffect`, before paint), on `resize`/`orientationchange`, and on a cheap 500ms poll (a few `getBoundingClientRect` reads — no MutationObserver, which would fire on every canvas pan/drag frame and is the one cost this control must never add).
