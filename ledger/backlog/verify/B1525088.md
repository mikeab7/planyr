**WHAT WAS ACTUALLY STALE, PER A GENERAL-PURPOSE AGENT'S FULL SWEEP (not guessed at).** The raw cache value itself was never wrong — `saveSite`/`writeSites` (the one write funnel) and `pullCloud` (the one full-cache rewrite) always leave `planarfit:sites:cloud:<uid>` holding the correct bytes the instant a write lands. The gap is entirely in **telling every other already-mounted reader of that cache that it changed.** This codebase already solved exactly this class of problem once — `shared/projects/projects.js`'s `notifyProjectsChanged()`/`onProjectsChanged()`, a synthetic `storage` event re-dispatch (native same-tab `localStorage` writes fire no `storage` event at all; a native CROSS-tab write already does, for free) — but only `ProjectBreadcrumb.jsx`'s own rename/delete/restore handlers called it (`notifyStoreChange()`, its own local copy of the identical mechanism). Every writer reachable from the **map / Sites panel / plan menu** — `SitePlannerApp.jsx`'s `setSiteStatus`/`setSiteDates`/its `deleteSiteGroup` wrapper, `SitePlanner.jsx`'s `handleRestoreDeletedPlan` — only ever called its own component's `refreshSites()` and never announced the change to anyone else. `SitePlannerApp.jsx` DOES already listen for the same `"planarfit:sites"` signal (its "Cross-tab freshness" effect, `SitePlannerApp.jsx:529-533`) — so a status change made from the map already refreshed *that* map's own pins; what never happened is any OTHER surface (another already-open tab whose write came from elsewhere, the project switcher, Notes/Model's project list) hearing about it, and — separately — a tab that's been open a while never re-asks the cloud on its own at all, which is the literal "no refresh short of reloading the page" in the report.

**THE FIX moves to the lowest choke point rather than patching each call site**, so every current AND future writer is covered by construction:
1. **`storage.js`'s `saveSite`** (the ONE funnel every plan-level write already goes through — rename/status/role all call it) now fires `notifySitesListChanged()` — the SAME literal event `notifyProjectsChanged()`/`notifyStoreChange()` already use — whenever the write actually changes an identity-relevant field (`site`/name, `status`, `role`, or which group the plan belongs to) versus the record it's replacing. A pure content edit (geometry, LOI/closing dates, …) leaves those fields untouched and stays silent, so this doesn't turn every autosave into a broadcast.
2. **`deleteSite`'s local removal** fires the same signal (a delete is exactly as identity-relevant as a rename).
3. **`pullCloud`** (the full-cache rewrite every sign-in, `restoreDeletedProject`, and manual re-check already call) fires it unconditionally after a successful merge+write — this is what lets a genuinely different device's edit, once pulled, reach every mounted surface on THIS device too.
4. **`SitePlannerApp.jsx`** gained a second, new listener: when the tab regains visibility/focus after being backgrounded (throttled to once a minute), and the user is signed in, it re-pulls the cloud and refreshes. This is the part that actually closes "no refresh short of reloading the page" for a tab that's been sitting open — a same-browser cross-tab write was already covered for free by the native `storage` event; a change made on a DIFFERENT device needed something that asks the server again, which nothing here did before.

**SCOPE — every writer that can change a site's name or status, and which were already correct.** Six write operations reach the cache: rename (`renameSiteGroup`), role flip (`setSiteGroupRole`), status (`setSiteStatus`), dates (`setSiteDates` — not identity-relevant, correctly excluded), delete (`deleteSite`/`deleteSiteGroup`), restore (`restoreDeletedProject`). **All six already wrote the raw cache correctly — none of them was silently dropping the write.** Three call sites (`ProjectBreadcrumb.jsx`'s own rename/delete/restore) were ALREADY correct — they call their own `notifyStoreChange()`. The gap was specifically the map/Sites-panel/plan-menu call sites for status, dates(n/a), the map's own delete wrapper, and the plan-menu's restore — none of which notified anyone else. Fixing the two shared choke points (`saveSite`, `deleteSite`) plus `pullCloud` covers every one of them at once, including any future writer that goes through `saveSite`.
