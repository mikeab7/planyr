- Verify: sandbox — pure geometry, no LIVE-VERIFY class applies (not GIS, not concurrency, not zoom/timing-dependent rendering, not export parity, and the repro needs no real project data — the bug reproduces on any angled edge with any snap setting). A live click-through would add confidence but not proof beyond what the unit tests already establish byte-exactly; not driven live this session (see note below).
- **ROOT CAUSE.** `insertVtx`'s shared control-point inserter (used by every editable layer — parcel/el/measure/ease/markup, Shift-click AND the right-click "Add control point" menu) computed the click's already-on-the-edge point (`edge.pt` from the pure hit-test, exact), then called `snapPt()` on it — which rounds `x` and `y` INDEPENDENTLY (to the grid, or to 0.01 ft with snap off). Rounding two coordinates separately moves a point off whatever line it was on unless that line happens to be grid-aligned — invisible on an axis-aligned wall, a small kink (and therefore a small polygon-area change) on an angled one, which an end wall on a reshaped building often is.
- **THE FIX.** A new pure `projectOntoSegment(a, b, p)` in the shared `lib/ringMath.js` (a leaf module, imports nothing) — the closest point on the FINITE segment between the two flanking (unmoved) ring vertices, clamped to the segment. `insertVtx` now re-projects the snapped point through it before splicing, using the segment's ACTUAL current neighbors from whichever array is being edited — so the insert always lands exactly on the line regardless of what snapping did to it. Distinct on purpose from `footprintEdit.js`'s existing `projectOntoLine` (an INFINITE-line projection, for a dock corner that is meant to slide arbitrarily far along its wall) — a freshly inserted control point must never land outside its two neighbors, which only a finite-segment projection guarantees.
- **TESTS.** New `test/ringMath.test.js` (8) — `projectOntoSegment`: identity when already on the segment, snapping an off-line point back onto an AXIS-ALIGNED edge, the exact repro shape on an ANGLED edge (proven via collinearity, not just "close enough"), clamping at both endpoints (never extrapolates past them), the degenerate zero-length-segment case, and the reported invariant itself — inserting a control point at a naively-snapped, slightly-off-line position leaves a ring's shoelace area EXACTLY unchanged (`toBeCloseTo(before, 9)`), the same numeric shape as 417,600 → 417,601. `test/footprintEdit.test.js` (23, pre-existing, unchanged/green).
- **Why no live click-through.** The exact numeric repro (angled-edge collinearity + before/after area equality to 9 decimal places) is fully captured by the unit tests above; this session's live time went to B742369's per-frame drag guard, which is the item where a live check adds evidence a unit test cannot (a race/timing shape). If a future session wants belt-and-suspenders, the right-click "＋ Add control point" menu item (`vtxMenu`) is the lower-effort live path — it doesn't need pixel-perfect Shift-click positioning the way the raw gesture does.
