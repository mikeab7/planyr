`[x]` **THE UNCERTAINTY RESOLVED FIRST, THEN FIXED AND VERIFIED THIS SESSION — SCOPED TO THE WIDTH GRIPS ONLY, per the report's own words, after an in-flight extension to the height grips was caught breaking a real invariant and reverted.** Confirmed by reading `dragWidthFromDelta`/`dragHeightFromDelta`: neither has any pane- or window-relative ceiling at all, only the generous corrupted-value guard — so the reported behavior is genuinely "ran out of physical mouse room," never a deliberate clamp. Fixed with a spreadsheet-style auto-scroll: a new `beginEdgeAutoScroll` helper runs a `requestAnimationFrame` loop for the life of a width-grip drag, and while the last known pointer position sits within 32px of the **browser window's own edge** (never the scroller's own, smaller box — see the in-flight correction below) on the side the drag is growing toward, each frame nudges the drag's own tracked pointer position further in that direction — simulating continued mouse movement even though the browser stops delivering real `pointermove` events once the cursor reaches the screen's edge — and scrolls the mat the same amount, so the growing edge stays visible under the pointer. Reuses the SAME `liveWidthFor` closure `onMove` already had (a real move and an auto-scroll tick both just advance the same tracked position and re-run the identical formula), so it cannot become a second source of truth for the width math. The commit-on-release path was corrected to never flatly overwrite the tracked position with the raw final pointer event (which is pinned at the screen edge and would silently discard everything auto-scroll grew) — it takes whichever position represents MORE growth in the drag's own direction instead.
  - **⛔ AN IN-FLIGHT EXTENSION TO THE HEIGHT GRIPS WAS BUILT, FOUND BROKEN, AND DELIBERATELY DROPPED — recorded because the mechanism it broke is worth naming.** The identical auto-scroll trick was first also wired onto `beginHeightDrag`'s bottom/top edges. Caught by `verify-notes-page-height.mjs` §16 going from 77/77 to 72/77 with nothing else changed: a plain, controlled 60px bottom-edge drag reported the OPPOSITE (top) edge moving −171px on a drag that is supposed to hold it fixed. Root cause: unlike the TOP edge (where the `minHeight` grow and the compensating scroll are the SAME amount, so they mathematically cancel for the bottom edge specifically), a bottom-edge auto-scroll has nothing to cancel against — scrolling shifts the WHOLE viewport, so the top edge visibly slid too, breaking the "opposite edge holds" invariant the whole height-drag feature is built on. NEW-7's own report was about the width grips only ("dragging the page WIDER"); the height grips were never part of it, so the fix stays scoped there rather than partially reintroducing this defect — noted in `NoteEditor.jsx`'s own comment so it is not tried again the same way.
  - **⛔ A SECOND DEFECT IN THE FIRST DRAFT, CAUGHT BY THE SAME REGRESSION SWEEP AND FIXED BEFORE EITHER GRIP SHIPPED.** The auto-scroll trigger originally measured distance to the SCROLLER's (`note-mat`'s) own bounding-box edge, not the window's. `note-mat` sits below the toolbar and beside the Pages rail — real, draggable window space the pointer can still move into, not a screen boundary — so keying the margin off the scroller's own (much smaller) box fired auto-scroll during perfectly ordinary, deliberate test drags nowhere near a real edge (a controlled 60px drag reported "moved −82, asked −60"). Fixed to measure against `window.innerWidth`/`window.innerHeight` directly — the one boundary a real mouse genuinely cannot cross, which is the entire reason this mechanism exists.
- Verify: sandbox — headless, a real held-down mouse drag (not a synthetic event) to the literal edge of a 1191px window, held for over a second with no further movement: the page width grew continuously past the visible window (579 → 2356, the `PAGE_WIDTH_MAX` ceiling) purely from auto-scroll, with the mat's own `scrollLeft` advancing to keep the growing edge under the pointer; released and reloaded, the grown width persisted (`localStorage`'s stored `pageWidth` read back `2356`/`2400` across separate runs) — proving the commit path preserves auto-scroll growth rather than snapping back to the screen-pinned release coordinate.
