### B1311 — A note that can hold a picture, without base64 eating the whole browser store `[Notes]` (feature) #notes #persistence #files  *(filed 2026-07-31 from an owner review of B1290; minted with B1310 in one `--against-main` run. DEDUPE-FIRST — searched for `image`, `paste`, `screenshot`, `IndexedDB`, `notes`: the Doc Review / Library file tier (`reviewStore` / Drive) is a different thing entirely — that is a document you OPEN, this is a picture INSIDE a note. Net-new.)*
`[x]` Paste or drag a picture into a page and it stays there — a cropped survey, a site photo, a screenshot of a flood map.
- Verify: sandbox
- Origin: filed 2026-07-31 from chat (NEW-1)
- **THE CONSTRAINT, AND THE HONEST ANSWER TO IT.** Notes persist in localStorage — a few megabytes for the WHOLE origin, shared with every other workspace — and base64 costs a third more than the bytes it carries. Two phone photos would exhaust it and every save after that would fail, in every notebook. So the **document holds an image ID and the bytes live in IndexedDB** (`lib/notesImageDb.js`, hundreds of megabytes), behind the same one storage seam. A data URL rather than a Blob, deliberately: JSON-able (so cloud sync lifts it through the same seam), already the form the Markdown export has to inline, and no object-URL lifetime to leak.
- **Downscaled once, at intake** (`lib/notesImageIntake.js`): capped longest edge, then encoded BOTH as PNG and as JPEG with the smaller winning — which lands on PNG for flat screenshots and JPEG for photographs without either being hard-coded. GIF and SVG pass through untouched; a canvas would flatten an animation to one frame and an SVG to a fixed raster, which is a silent downgrade of what the user pasted.
- **Ceilings are enforced at the STORE, not at the paste site,** so no future intake path can bypass them: `MAX_IMAGE_BYTES` per picture and `MAX_NOTEBOOK_IMAGE_BYTES` per notebook. Over either is a NAMED, VISIBLE refusal on the existing one error channel (LOUD-FAILURE) — never a paste that quietly does nothing.
- **Markdown export inlines each picture as a data URL**, so an exported note is self-contained; a picture whose bytes are gone is written as a named broken reference AND reported in the lossiness notice. The source-scan guard is satisfied in the same commit: `noteImage` is in `NOTE_MD_HANDLED` and has a case in the exporter.
- **A missing image is a VISIBLE broken block, never a blank gap** — the node view says so in words, and the same is true on the printed sheet.
- Delete cascade: `purgePages` reads each purged page's body, collects its image ids and destroys those bytes with it (B1310's purge is the one call site).
- Guards: `test/notesRoundTwo.test.js` (the real store over `fake-indexeddb` — ceilings, scoping, usage, the cascade, the sweep that spares binned pages) + `ui-audit/verify-notes.mjs` §11–§14 (a real clipboard paste, the proof the bytes are in IndexedDB and NOT in localStorage, the export, and the broken state after the record is deleted out from under the note).
