### B1107632 — Replace the one-frame scroll-dismiss race in ContextMenu with an explicit guard `[Model / Global UI]` (task) #ui #model  *(owner chat block 2026-09-03, task titled "NEW-1 — Replace the one-frame scroll-dismiss race in ContextMenu with an explicit guard". `[x]` **SHIPPED — the implicit one-rAF-late arm (B1076480) replaced with an explicit, event-driven guard; the timing coincidence it depended on is gone.** `src/shared/ui/ContextMenu.jsx`'s scroll-dismiss listener used to arm one `requestAnimationFrame` after mount specifically so it would miss the deferred native `scroll` event that follows SheetView's "keep the active cell fully on screen" layout effect (`el.scrollTop`/`el.scrollLeft` writes triggered by the SAME `setSelRange` call that opens the row/column/cell context menu). That ordering held only because Chrome happens to sequence the deferred `scroll` dispatch behind the next `requestAnimationFrame` callback — an implicit coincidence, not a guarantee, and the brief explicitly asked for it to be replaced rather than re-verified.
- **Why NOT a magnitude/delta threshold (the brief's option (b)).** Measured directly: the "keep active cell visible" nudge is NOT bounded to "a few px" in general — it scrolls exactly as far as the cut-off cell needs, which can be nearly a full row/column height. There is no threshold simultaneously bigger than every real nudge and smaller than every real user scroll, so a magnitude gate would either reintroduce the self-dismiss (threshold too low) or swallow small genuine user scrolls (too high).
- **Design shipped (the brief's option (a), generalized): mark the WRITE, not the magnitude.** New shared primitive `src/shared/ui/programmaticScroll.js` — `markProgrammaticScroll(el)` called by the writer immediately before a deliberate, app-initiated `scrollTop`/`scrollLeft` write; `consumeProgrammaticScroll(el)` called by a scroll-dismiss listener, returning `true` (and clearing the mark) exactly once per mark so a genuine LATER scroll on the same element is never masked. A `GRACE_MS` (1000ms) safety net expires an unconsumed mark (the write happened to be a no-op — the cell was already at that exact position, so no `scroll` event ever follows) so a long-lived container can't carry a stale grant into an unrelated future menu; the browser's own deferred dispatch was measured at 11-55ms across 1x-40x CPU throttling in the brief's own prior stress test, so the grace window is a wide margin around real timing, never the primary mechanism. `ContextMenu.jsx`'s scroll listener now arms IMMEDIATELY (the rAF delay is gone entirely) and checks `consumeProgrammaticScroll(e.target)` before dismissing; `SheetView.jsx`'s "keep active cell on screen" layout effect calls `markProgrammaticScroll(el)` right before each of its four conditional `scrollTop`/`scrollLeft` writes.
