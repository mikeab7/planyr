### B1130 — Point features in a vector overlay render as Leaflet's DEFAULT marker, so substations paint as broken-image glyphs labelled "Mark" `[Site Planner / vectorOverlay]` (bug) #site-planner #gis #ui  *(owner-reported 2026-07-29 from chat with a screenshot: the Electric layer on over an aerial, two broken-image icons labelled "Mark" standing where the substations should be. Arrived as provisional "ITEM 1"; minted **B1130** via `git fetch origin main && npm run next-id -- --against-main`. Origin: filed 2026-07-29 from chat. DEDUPE-FIRST: searched Open / ⏳ Verify / Done for `marker`, `pointToLayer`, `broken.image`, `"Mark"` — nothing. The closest prior item is **B695** (hover/click identify + labels for the cached BOUNDARY layers), which is a different mechanism on different layers and explicitly noted that `featureLayerOptions` builds its layers `interactive:false` without changing it. Net-new.)*
`[x]` **Shipped — a GeoJSON POINT with no `pointToLayer` fell through to `L.marker` + an unresolvable `L.Icon.Default`.**
- Verify: sandbox
- **Root cause, confirmed in code.** Leaflet's documented default for a GeoJSON Point with no `pointToLayer` is `L.marker(latlng)` wearing `L.Icon.Default`, and nothing in this repo ever configured `L.Icon.Default`'s image paths for the bundler (`grep`: no `Icon.Default`, no `marker-icon` reference anywhere in `src/`). So the icon's PNG 404s, the browser paints its broken-image glyph, and the marker's alt text — the string `"Marker"` — is clipped by the icon box to read **"Mark"**. Every *other* `L.marker` call site passes an explicit icon (`MapFinder`'s `sitePinIcon`, `terrainLayers`' `labelIcon`, `vectorOverlay`'s label `divIcon`), which is why ONLY GeoJSON point features were affected — and substations are points.
- **⚠ THE REPORT NAMED ONE FILE; THERE WERE THREE PATHS, and the live one was not the file named.** The brief traced it to `vectorOverlay.js:207`'s `L.geoJSON(null, {…})`. That call is genuinely defective, but it is **latent** — every `VECTOR_SOURCES` row today is polygon or line. What actually painted the owner's glyphs is **`layerRequest.js:78` `featureLayerOptions`**, the esri-leaflet path: `hifld_substations` is `kind: "esriFeature"`, and esri-leaflet delegates to `L.GeoJSON.geometryToLayer(geojson, this.options)`, so it inherits the same default. That path also affects `env_cleanups`, `faa_airports` and `txdot_aadt` — all point layers, all broken the same way, none of them mentioned in the report. A third site (`vectorOverlay.js`'s `cachedPipelineLayer`) was found by the guard test after the first two were fixed.
- **Fix.** `mapSymbols.js` (new) owns a `pointToLayerFor(cfg, opacity)` returning a styled `L.circleMarker` in the source's own colour + weight, matching how `evidenceLayers.js` already draws OSM power points; the pure options half is `layerRequest.pointSymbolOptions` (kept leaflet-free so it unit-tests in the node env). Applied at all three construction sites. `EL.featureLayer` is now built in exactly ONE place (`layers.buildFeatureLayer`).
- **Two follow-on defects the fix exposed, both fixed here.** (a) `L.geoJSON` applies its `style` option to circleMarkers too, so the boundary style's `fillOpacity: 0.02` hit-area fill would have flattened a point to near-invisible — `baseStyle` / `styleFeature` are now geometry-aware (`isPointFeature`). (b) the flat `setOpacity` shim sent `{opacity}` only, which dims a stroke but not a disc's FILL, so a dimmed substation stayed solid; it now re-derives a point's whole symbology.
- **Belt and braces.** `installDefaultMarkerIcon()` points `L.Icon.Default` at the real bundled PNGs (imported so Vite resolves them — all three inline as `data:` URIs under the 4 KB limit, verified in `dist/`) and deletes Leaflet's `_getIconUrl` path-guessing hook, so any future accidental default marker degrades to an honest pin instead of a broken image.
- **Guard (the brief's, plus what it caught).** `test/pointSymbology.test.js` — 17 assertions: the pure symbol options, and a STRUCTURAL lock that `EL.featureLayer` has exactly one construction site and every `L.geoJSON` passes a `pointToLayer`. **That structural assertion is what found the third defective call site** (`cachedPipelineLayer`), which neither the report nor the initial fix covered. DOM-level assertions (zero `img` with a default-icon src, zero `alt="Marker"`, zero failed-to-load images, zero marker-pane images, and a Point producing a circleMarker) live in `e2e/layer-point-hover-identify.spec.js` because leaflet cannot be imported in the node test env — 8/8 passing, both themes screenshotted.
- **Bundle budget (`ui-audit/perf-bundle-audit.mjs`) — paid with optimization, and this is the part worth reading.** The naive fix imports leaflet's three marker PNGs; each is under Vite's 4 KB `assetsInlineLimit`, so all three base64-inline into the planner chunk — **~6 KB of JS on the site route's critical path, permanently, for images that should never be fetched at all.** Both Vite-5 ways of emitting them as files were tried and neither works here (`?no-inline` is a **Vite 6** feature — on Vite 5 it silently resolves to nothing, which leaves the fallback BROKEN rather than merely heavy; and `new URL(…, import.meta.url)` against a `node_modules` path emits nothing either). So the requirement was re-read instead of brute-forced: what it has to guarantee is that an accidental default marker degrades to a **real pin**, not that it is byte-identical to Leaflet's blue one. A hand-authored teardrop SVG data URI does that in **~400 bytes instead of ~6 KB** — same guarantee, no vendored copies of a dependency's assets to drift out of sync with the leaflet version. `shadowUrl: null` so the fallback never appends a second `<img>` that can itself fail to load.
- Also: `hitFeature` (`vectorLayers.js`) gained Point / MultiPoint support. Without it a substation was **unhittable** on the planner canvas — the click/hover identify could reach lines and bands but never a point asset. Recorded as a tolerance hit so an exact polygon containment still wins the two-pass ordering.
