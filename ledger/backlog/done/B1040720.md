- Verify: sandbox — full local run + a real CI run on the same commit compared gate-by-gate (see the PR description for the side-by-side).
- **THE ARCHITECTURE, and why it's two files, not one.** GitHub Actions can't dynamically expand a step list from an external file at workflow-definition time, so "build.yml calls the script" and "one gate list, unable to drift apart" can only both be true if the list lives somewhere ONLY the script reads. `.github/ci-gates.yml` is that list — shaped exactly like a GitHub Actions job (`jobs: build: steps:`) so the SAME parser (`jobSteps()`, `ui-audit/lib/workflowContract.mjs`, extended this session) reads both it and `build.yml`'s own remaining (CI-only-plumbing) steps. Its 19 gates were extracted MECHANICALLY from the pre-migration `build.yml` — verified byte-for-byte identical (`name`/`run`/`env`/`with`) via a throwaway script comparing the two parses before the migration file was ever hand-edited, not retyped from memory. `build.yml` keeps only what genuinely can't live in the script: `actions/checkout`, `actions/setup-node`, `actions/cache` (the Playwright browser cache, which must restore BEFORE the script's own `Install Playwright chromium` gate runs to be worth anything), one step that calls `npm run ci-parity` (carrying both Supabase secrets, so every gate that needs them shares the identical resolved value — closing B927104 structurally, not by convention), and `actions/upload-artifact` (visual-regression diffs on failure).
- **ENVIRONMENT PARITY, the part the task called the most important requirement.** `ui-audit/lib/ciGates.mjs`'s `resolveSecretEnv`/`resolveStepEnv` compute the secret map ONCE per run and apply it to every gate needing it — so the base-ref bundle snapshot and the head Build always share the same truthy-or-not `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY`, by construction. When a real secret is absent (the normal case on a laptop), the script substitutes the exact dummy values `ui-audit/visual-regression.mjs`'s own header already documented (B1026272) and says so LOUDLY before running anything and again in the final summary — never silently. `scripts/ci-parity.mjs` also fetches `origin/main` (unshallowing first if needed) before the mint gate / base-ref snapshot run, and installs the pinned Playwright Chromium (`npx playwright install --with-deps chromium`) for the visual-regression gate — the exact revision `package-lock.json` pins, not whatever happens to be pre-installed (this session's own sandbox had chromium-1194/1234 on disk; the pin was 1228 — a live instance of the exact class of bug B1026272 named).
- **WHAT IT DOESN'T COVER, AND WHY (all four are `uses:`-only steps in `build.yml`, named + reasoned about in `ui-audit/lib/ciGates.mjs`'s `KNOWN_INFRA_USES`, and reported by `--list`):** `actions/checkout` (a checkout already exists locally; the script fetches `origin/main` instead, which is the part the gates actually need), `actions/setup-node` (the script checks the running Node version against `build.yml`'s own pin and warns rather than silently running on a different one), `actions/cache` (a CI-only speed optimization, no correctness effect), `actions/upload-artifact` (the failure-diff files are already on disk locally).
- **LOUD-FAILURE, both directions.** `jobSteps()` REFUSES (exit 2) rather than run a stale or guessed list if either file's shape stops parsing; `loadPlan()` warns if `build.yml` grows a second `run:` step outside the one delegator (which would mean a gate snuck back in there instead of `.github/ci-gates.yml`, and would risk the script recursing into itself), and refuses if `.github/ci-gates.yml` ever grows a `uses:` step (GitHub never reads that file, so a marketplace action there could never run).
