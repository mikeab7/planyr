- **Grammar implemented, exactly the six forms asked for:** `A1` · `$A$1` · `A$1` · `$A1` · `A1:B10` · `$A$1:$B$10`, case-insensitive, coexisting in the same formula as `[Column]` structured refs. Cross-sheet (`Sheet1!A1`) is explicitly out of scope per the brief and fails loudly (`#ERROR! unexpected character "!"`) rather than silently mis-parsing — agreeing with the brief's own call that a single-sheet module doesn't need it yet.
- **The surface really was as small as the brief predicted, with one further reduction found during implementation:** token types +1 (`:`) plus a new `ref`/`errlit` token class for `$`-bearing addresses and the `#REF!` literal (a bare `A1`/`LOG10` deliberately stays an `id` token — see the collision note below); AST nodes +2 (`ref`, `range`, plus a small `errLiteral` for `#REF!` — see the #REF! note below); the two resolution chokepoints named in the brief — `evalNode`'s `case "col"` (now also `case "ref"`) and `colArray()` (now also resolving `range` nodes via a new `rangeArray()`) — plus the four collector guards, unified behind one `isRangeArg(n)` predicate instead of four separately-edited one-liners. **The further reduction: `RANGE_ARG_POSITIONS`/`isRowInvariant`/`isCallInvariant` (B866784's hoisting table) needed ZERO changes** — `isRowInvariant`'s `switch` already defaults unrecognized node types to `false` (not row-invariant), so a `ref`/`range` argument in a `rng` call falls through to the existing non-hoisted path automatically and correctly, with no new case needed. Verified this is a safe default, not just a convenient one: hoisting a grid-cell read via `rngResultCache` (keyed on `ctx.rows`) would risk a stale answer if a host ever reused the same `ctx.rows` reference across two different `ctx.grid` states, since that cache has no `ctx.grid` term in its key — leaving it unhoisted sidesteps that hazard entirely rather than extending the cache key to cover a case with no current caller. `colArray`/`rangeArray` still avoid the O(rows²)-shaped defect class B866784 fixed: `rangeArray` gained its own `ctx.grid`-keyed cache, the direct analogue of `colArrayCache`, so many cells summing overlapping ranges in one recalc pass don't each re-walk the grid.
- **Collision handling — LOG10 is confirmed, LIVE, as the only collision, and Excel's own rule resolves it:** re-checked programmatically against the actual current registry (95 original + 14 financial = 109 names, not eyeballed) — `LOG10` is the sole name that also parses as a valid address (column `LOG`=8509, row 10; every other name either carries no trailing digits or, where it does, the letters run resolves past column XFD and is rejected by the same bounds check as any other over-large address). Resolved with Excel's own disambiguation, applied at the single point the parser already had the lookahead for it: the existing "identifier immediately followed by `(`" function-call check runs FIRST (unchanged, still returns immediately, `LOG10(...)` never reaches the reference check); only a bare identifier that is NOT a call and NOT `TRUE`/`FALSE` is then tested against `parseRefText` — so `LOG10(100)` is always the function, bare `LOG10` is always the reference to column LOG row 10. The same ordering is reused verbatim by the rewrite transform below (`isRefEligible`), so the parser and the rewrite can never disagree about what counts as a reference.
- **Bounds rejection — all four named cases confirmed rejected as NAMES (`#NAME?`), not accepted as refs and not producing `#REF!`:** `XFE1` (one column past XFD) · `ABCD1` (too many letters — and measured that the numeric column-value check alone is sufficient to reject every 4+-letter run without a separate length check, since even the smallest 4-letter combination `AAAA`=18279 already exceeds `XFD`=16384) · `A0` (row 0) · `A1048577` (one row past the max). `parseRefText` is the one shared bounds check — `test/formula.test.js` asserts both the end-to-end `#NAME?` behavior and `parseRefText`'s own null/non-null verdict directly, and both were mutation-proved red when the bounds check was disabled.
- **`#REF!` semantics — resolved as a literal-error AST node, not a grid-bounds check, because address-space bounds are already fully handled at parse time (rejected as a name, per above) and there is no OTHER notion of "the sheet's bounds" this engine has visibility into yet (no Model-module grid extent contract exists in this codebase to check against).** The tokenizer now accepts the literal text `#REF!` (case-insensitive) as valid input, evaluating straight to `ferr(FORMULA_ERRORS.REF, …)` — this is what makes `rewriteFormulaForCopy` (below) able to satisfy "must produce #REF!, not a crash and not a silent zero" when a copy/fill shifts a relative reference off the sheet: it writes the literal `#REF!` into the rewritten formula text, exactly as Excel itself does, and the engine now parses that back out to the error rather than choking on `#`/`!` as unrecognized characters. A grid cell that's simply beyond what the host populated (e.g. row 500 on a 50-row sheet) reads as blank, matching Excel's own "beyond the used range" behavior — never `#REF!` by itself.
- **Relative-reference rewrite on copy/fill — built as the brief specified, a pure token-level splice, separately unit-tested with no grid involved:** `rewriteFormulaForCopy(formula, sourceAddr, targetAddr)`. Confirmed: `A1+B1` copied from `A1` to `A5` → `A5+B5`; `$A$1` never moves; `A$1`/`$A1` move only on their relative axis; a range shifts both endpoints together (`A1:B10`→`A2:B11` on a one-row-down copy); a reference shifted below column A or row 1 collapses to `#REF!`; a range with only ONE endpoint pushed off the sheet collapses the WHOLE range to `#REF!` (matching Excel, not just the one bad endpoint); `LOG10(` is never rewritten while a real reference beside or inside it still is; a formula with no A1 refs at all (pure `[Column]`) or a string literal that merely looks like a reference round-trips byte-identical. Deliberately token-level rather than AST-reserialized, specifically so untouched formula text (spacing, string literals, `[Column]` refs, function names) survives byte-for-byte rather than risking a reformat.
- **Row/column INSERT and DELETE ref-shifting was NOT built, per the brief's explicit instruction** — confirmed this is the right call: a fixed-layout pro-forma with a fill handle only ever needs copy/fill, and building it would have meant inventing a sheet-structure-edit contract with no consumer yet.
