`[x]` **SHIPPED THIS SESSION.** Fixed the SILENCE, not the accumulation (which stays, deliberately).
- **The fix.** Every paste (and every Split-one-row-per-line / Merge-into-one-comp transform) now says exactly what it did — `"Added N comp(s) — M in the sheet."` — naming both the delta and the new total, so an append can never read as a fresh single comp. A new **Undo** link removes exactly the rows the most recent paste (or transform) added, tracked by row id (`lastPasteRowIds`), never anything the user entered before or since; clicking it confirms with `"Removed N comp(s) — M in the sheet."`. A standing, always-visible caption under the paste box ("Every paste adds rows to the sheet below — clearing this box never clears them.") states the inbox/set relationship once, so it's read before the confusion happens rather than after. Clearing the textarea still does NOT delete any grid row — confirmed unchanged, per the brief's explicit instruction not to make that destructive.
- **The actual trigger, determined rather than assumed (the brief's own open question).** Every text passed to `commitText` is deduped only against the LAST commit within an 800ms window (`lastCommitRef`) — pasting the identical text twice in a row within that window is treated as one duplicate browser paste-event firing (a real, separate Chromium quirk this guard already existed to absorb), which is why the owner's own adjacent-case check found no append there; clearing the box first and pasting DIFFERENT text is a normal new commit and always appends, exactly as designed.
