- Verify: sandbox — a deterministic CSS/layout property (mouse-driven `gridZoom`, no touch/iOS dependency), fully proven and red-proven in a real, driven Chromium browser; no auth/live-GIS/real-project-data dependency.
- Origin: filed 2026-09-06 from chat (owner amendment to the same session's chat block)
- **Root cause: `gridZoom` — GridView's own existing CSS-`zoom` visual-comfort feature (Ctrl+scroll while hovering the grid, unrelated to the Format panel's separate `rowHeight` setting) — was applied ONLY to GridView's own scroll container (`zoom:gridZoom` on the `[data-grid-scroll="1"]` div), never to GanttView's.** CSS `zoom` re-layouts every descendant pixel, ROW_H included, so a grid zoomed to (for example) ~1.97× rendered its OWN rows at ~47px tall while the Gantt pane — reading the identical, unaffected module-scope `ROW_H` — kept rendering at 24px. Both panes still agreed on the NUMBER (`ROW_H`); only one of them was then visually rescaled, which `test/schedulerEngine.test.js`'s own #4 and the B1113712/B1113713 fix could not have caught (neither exercises `gridZoom`). A secondary, previously-unnoticed consequence: `SplitView`'s scroll-sync (`sync(src)`) copies `scrollTop` directly between the two panes' refs — numerically meaningless once only one side is zoomed, since `scrollTop`/`scrollHeight` are reported in the ZOOMED coordinate space.
- **The fix (`public/sequence/index.html`):** `GanttView` gains a `rowZoom` prop (default 1, a no-op `zoom:1`), applied to its own scroll container exactly the way GridView already applies `gridZoom` to its own. `SplitView` — the only caller that ever passes anything but the default — passes `rowZoom={props.gridZoom || 1}`, mirroring the live grid zoom onto the Gantt pane. Both panes now scale by the SAME factor: every row's rendered top/height becomes identical BY CONSTRUCTION (not tuned to match), the dependency-arrow SVG (which lives inside the same zoomed container) scales in lockstep and keeps landing on its bars, and the scroll-sync's direct `scrollTop` copy becomes numerically correct again (both sides now report scrollTop in the same zoomed space). Standalone GanttView (no grid to align against, at line ~9502) keeps `rowZoom=1` — untouched, unaffected. GridView's own frozen column header (the OTHER named tripwire casualty, drift by a column) is untouched by this fix and was checked as a standing regression net, not because this change had reason to move it.
- **Desktop pixel-parity:** at the default `gridZoom:1` (the overwhelming common case), `zoom:1` is the identity transform — nothing renders differently from before this fix.
- **Tests:** new permanent live-browser harness `ui-audit/verify-gantt-row-alignment.mjs` (`node ui-audit/verify-gantt-row-alignment.mjs`) — drives real Split view at `gridZoom:1` AND `gridZoom:1.6` (a realistic post-Ctrl-scroll value), asserting for every row: grid-row top/height equals gantt-row top/height within 0.5px (both **0.00px** at both zoom levels), every dependency-arrow endpoint's bounding box overlaps a bar (0 orphans, both zoom levels), and GridView's own header left edge still matches its body's left edge (the frozen-header regression net). **RED-PROVEN by hand this session:** reverting the `rowZoom` plumbing reproduced the exact reported symptom on the harness's own fixture — row-top drift up to 176.39px and row-height drift up to 14.39px at `gridZoom:1.6`, both zero at `gridZoom:1` (matching the owner's report being about Split view specifically, not a universal misalignment) — restoring the fix returned both to 0.00px.
