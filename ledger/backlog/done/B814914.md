- Verify: sandbox — a build-time/test-time concern (tokens, docs, a mechanical find-and-replace to existing pixel values); no GIS/timing/auth dependency.
- **THE AUDIT, exhaustive, not sampled: every `<button>` element in the app — 738 of them, across 573 files.** `borderRadius`: 22 distinct values before this item (dominated by raw `7`×43 — no token — `6`×34, `8`×33, `999`×27 "pill", plus a **second, narrower "pill" value, `99`×5** — a real correctness inconsistency, not just style: 99px fails to fully round a button taller than 99px, 999px never does). `height`: 17 distinct values (which DO already split cleanly into three real tiers — ~20-22 / ~24-26 / 30). `fontSize`: 15 distinct values (a fine half-point ladder, 10 through 14, genuinely six-plus real steps in active use, not noise). `padding`: **94 distinct raw strings** — no clean convergence at all.
- **THE TOKENS.** Radius already had a source of truth (`shared/ui/radius.js`'s `RADIUS={pill,sm,md,lg}`, B427411) — left exactly as-is, the canonical file. New sibling `src/shared/ui/designTokens.js` covers the three categories B427411 never touched: `SPACE={xxs:2,xs:4,sm:6,md:8,lg:10,xl:12,xxl:16}`, `FONT_SIZE={xs:10,sm:10.5,base:11,md:11.5,lg:12,xl:12.5,xxl:13,display:14}`, `CONTROL_H={sm:22,md:26,lg:30}` — every value is the tree's own measured MODAL value, never invented, matching `radius.js`'s own stated rule. CSS mirror: `--space-*`/`--font-*`/`--control-h-*` added to `index.css` alongside the pre-existing `--radius-*` block. `docs/DESIGN-TOKENS.md` is the actual "design bible" — the audit numbers, what each token category is for, what shipped vs. what's still open, and a usage example.
- **APPLIED MECHANICALLY, buttons only, zero visual change.** Every `<button>` whose literal `borderRadius` exactly equalled an existing token's pixel value was repointed at the token: `999`/`99` → `RADIUS.pill` (also closes the two-pill-values inconsistency above), `8` → `RADIUS.md`, `6` → `RADIUS.sm`, `12` → `RADIUS.lg` — same pixel value either way, the only change is that it can no longer drift independently. Applied across 22 files that had no radius token imported at all (`RADIUS` newly imported from `shared/ui/radius.js` in each); seven Notes workspace components already had their own tokenized mirror (a documented, deliberate B427411 follow-up) and needed no changes — confirmed by direct inspection, not assumed.
- **⛔ A CODEMOD-CORRECTNESS INCIDENT, caught before shipping, worth recording.** The first mechanical pass corrupted six sites — a naive "first `borderRadius:` within N chars of a `<button` tag" window matched the SAME source span from two nearby buttons in a few files, producing malformed double/triple tokens (`RADIUS.smADIUS.sm`, `RADIUS.pillIUS.pillIUS.pill`) that would have thrown at runtime though they parsed as valid JS (a plain `vite build` alone would not have caught them) — and, separately, one new import got inserted mid-way through an unrelated multi-line `import { ... } from` block, a straight syntax error. All six found by an exhaustive regex sweep for stutter patterns across every touched file (not by sampling), fixed by hand, and re-verified: a clean `npm run build` plus a targeted grep confirming zero remaining malformed `RADIUS.` references anywhere in `src/`.
- **⛔ TWO GENUINE JUDGEMENT CALLS, flagged rather than decided — full reasoning in `docs/DESIGN-TOKENS.md`.** (1) The raw `7` radius (43 sites, no token, sitting exactly between `sm`=6 and `md`=8) — nudging it either way is a real 1px visual change across 43 buttons; left untouched. (2) Padding/font-size retrofitting — 94 raw padding strings is real fragmentation, but collapsing them onto the new scale retroactively would touch visual proportions across a large fraction of the app, which is explicitly out of this item's scope ("do NOT redesign anything"); the scales exist now as the target for new work, not a completed retrofit.
