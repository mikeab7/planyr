### B1924322 — Polygon mode opens as a closed full-frame polygon that ignores clicks, and has no reset of its own `[Site Planner / site-plans]` (bug) #site-planner #ui #comps  *(Owner live-test on planyr.io, 2026-09-22, PR #1785/merged 52032a0. On a plan with no crop, open Crop…, then Polygon: the editor shows a closed 4-vertex polygon on the image corners, and six trusted clicks on the image added no vertices — drawing only starts after finding "Clear polygon", and Polygon mode has no way back to the full image (its "Clear polygon" disables Done rather than resetting to full page; the only full-page reset lives in Rectangle mode). Minted **B1924322** from this branch's reserved block. DEDUPE-FIRST — no prior item covers Polygon's own entry state or its own reset; B1783328 shipped the feature this hardens.)*

`[x]` **AUDIT-FIRST — the closed-quad seed on an uncropped overlay is a DELIBERATE feature for the wrong case, not a bug in general.** `ImageCropTool.jsx`'s own header explains the intent: switching to Polygon for the first time on an EXISTING rect crop should hand over an editable quad seeded from that rect, not an empty draw — a real, wanted behaviour, confirmed working and left untouched. The reported bug is the narrower, different case the live test actually hit: an overlay with NO crop at all yet (a genuinely fresh upload) STILL seeded the same closed full-image quad, with nothing real to derive it from — swallowing clicks until "Clear polygon" is found, purely because `polyClosed` unconditionally defaulted to `true`.
`[x]` **FIX, scoped to exactly the reported case.** `ImageCropTool.jsx` now distinguishes "this overlay already has SOME saved crop" (`hadAnySavedShape`, true if either `savedRectOf`/`savedPtsOf` finds something) from "genuinely nothing saved yet": only in the first case does Polygon mode still seed the pre-existing closed-quad-from-rect behaviour; with nothing saved at all, `polyPts` starts empty and `polyClosed` starts `false` — Polygon mode opens ready to draw, the first click places vertex 1, exactly as Rectangle mode already behaves on a fresh overlay.
`[x]` **Polygon mode gets its own "Reset to full page", alongside "Clear polygon" rather than replacing it** (Clear still starts a fresh empty hand-trace — a real, distinct action). The new action sets the polygon to the same closed 4-corner full-image quad Rectangle's own reset produces as a rect, and `isFullImagePoly` (added for B1924321 above) makes committing it collapse to `crop: null` on Done — identical outcome to Rectangle's "Reset to full page", not a different, poly-flavoured "empty" state.
- Verify: sandbox — real headless Chromium via `ui-audit/verify-crop-polygon-editing.mjs` (extended this session): a freshly-uploaded, never-cropped overlay now opens Polygon mode with "Clear polygon" already disabled (nothing to clear) and zero vertices rendered; the first click places a real vertex 1; a real 3-vertex polygon drawn, closed, then Polygon's own "Reset to full page" clicked and Done pressed commits `crop: null`, exactly like Rectangle's reset. The pre-existing behaviour for an overlay that already has a real rect or polygon crop (seeded quad on first Polygon entry; recovers the original shape on later re-entries) is unchanged and still passes every existing check in the same harness. `npx vitest run` full suite green (incl. `isFullImagePoly`'s own unit coverage, filed under B1924321). `npm run lint` 0 new errors. `npm run build` clean.
