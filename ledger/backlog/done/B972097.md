### B972097 — `siblingMismatches()` has a loophole: separation and relabeling both satisfy it `[global/ui-audit]` (bug) #ui  *(owner chat block 2026-08-31, "NEW-2," verbatim: "Two of the three possible responses to a finding are cosmetic and both pass" — the check stops asking whether adjacent controls share a radius family the moment they're no longer adjacent, so a divider (B950320) or a reclassification (B958466) both silence it without ever converging the row, which is exactly how the same defect survived two "fixes" and reached a third report. DEDUPE-FIRST — searched Open/⏳Verify/Done for "siblingMismatches", "divider loophole", "gap threshold": B950320 (Done) built the check itself and is the one whose loophole this closes; no prior item tightens it. `[x]` **SHIPPED 2026-08-31 (Verify: sandbox — a genuine teeth-check that caught a real bug in this item's own first implementation before it shipped; see below).** `siblingMismatches()`'s adjacency test used to exempt any pair whose horizontal gap exceeded the threshold (12px) outright — so both a hairline divider and moving a control to a different token bucket cleared the check by making the pair read as "not adjacent," never by making the row look right. It now asks, for any pair whose gap exceeds the threshold, whether a divider-SHAPED element (a real bar — width or height ≤2px AND its long axis ≥8px, not a stray pixel) sits inside the gap; if one does, the pair is still judged as adjacent and still has to agree, and a finding on such a pair is annotated `(divider-separated)` in the generated report — informational, not an exemption; the finding still fails the build.
`[x]` **⛔ THE FIRST IMPLEMENTATION WAS WRONG, AND THE TEETH-CHECK IS WHAT CAUGHT IT — recorded because it is the argument for teeth-checking rather than trusting a check that merely runs.** The first version tried to SUBTRACT the divider's own `getBoundingClientRect().width` (~1px) from the measured gap and re-test the remainder against the threshold. Reproducing the exact B950320/B958466 loophole scenario (reverted the account chip's radius to `RADIUS.pill`, reinstated the AppHeader divider, rebuilt) still reported **0 findings** — the divider's CSS margin (`0 2px`) plus the flex row's own `gap` (6px) on both sides is real occupied space a partial-subtraction never credits, so the "effective" gap stayed over threshold and the pair was STILL silently exempted, reproducing the very loophole this item exists to close. Fixed by making the test binary instead of arithmetic: is there a divider-shaped element anywhere in the span, yes or no — if yes, the pair must still agree regardless of the raw DOM gap; if no, the gap is genuine clear space and the pair is genuinely separated.
`[x]` **Teeth-proof, run against the corrected logic on the same reproduced scenario.** With the account chip reverted to `RADIUS.pill` and the AppHeader divider reinstated (a real build, real preview server, real headless crawl — not reasoned from source): the OLD (pre-B972097) `siblingMismatches()` reports **0** sibling mismatches on this DOM. The NEW (tightened) version reports **6** — the account-chip/fullscreen pair × 2 themes × the surfaces it's crawled on (Map landing page, App header), all flagged `(divider-separated)`. Restored to the real B972096-fixed app (no divider, converged radii): **0** sibling mismatches, as expected.
`[x]` **What the tightened check can and cannot enforce, stated plainly per the brief's own instruction not to overclaim.** CAN: catch a mismatched pair separated only by a divider-shaped element, where the pre-fix check would have silently exempted it. CANNOT: verify the divider it finds is `docs/DESIGN.md`'s real divider spec (1px, `--chrome-divider` token) versus any other thin element that happens to fit the width budget — it checks shape and position only, never color or token use. CANNOT distinguish a genuine family boundary (two clusters never meant to visually agree) from a divider used as a loophole to silence a mismatch that should have been converged — both read as `(divider-separated)`; a human still judges which one it is. Documented in both `ui-audit/ui-inventory.mjs`'s own header comment and `docs/DESIGN.md`'s "sibling clause" section.
`[x]` **Re-ran over row 1 AND the Site Planner toolbar (both crawled by the same `SURFACES` list — "App header" and "Tool rail"), per the brief's explicit instruction.** On the real, converged app: **0** sibling mismatches on every crawled surface, including both of those. No instance previously "resolved" by divider or reclassification survives — the ONE known instance (the account-chip pair) was fixed at the source by B972096's convergence, not merely hidden from this check; the teeth-check above proves the tightened check WOULD catch it if the old divider-based fix were still in place.
