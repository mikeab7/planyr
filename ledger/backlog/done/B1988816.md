### B1988816 — Site pin sits outside its own parcel on irregular shapes (Katz, Rankin Rd) `[site-planner / map]` (bug) #site-planner #parcel #gis  *(Owner report 2026-09-30, iPhone Safari, Map view: the orange marker for "Katz" is drawn in the notch of a large L-shaped parcel, on the neighbours' lots.)*

`[x]` **Confirmed cause (AUDIT-FIRST):** `MapFinder.jsx` placed the pin (and the zoomed-in name tag) at `site.origin` — the plan's feet-frame origin, set when the plan was created. It is not derived from the parcel's shape at all, so on a wide-rectangle-plus-tail-plus-notch parcel it can fall in the notch. (The Dashboard Locations map and the Sites-list fly-to use the same stored point.)
`[x]` **Fix:** new pure `lib/siteAnchor.js` = the ONE anchor helper. Largest live/active parcel by net area; area centroid kept when it is inside AND at least 60% as far from the edge as the pole (so convex parcels do not move); otherwise the pole of inaccessibility (`polylabel.js`, extended with `polylabelWithHoles` so a save-and-except hole is never landed in). Computed from geometry at read time, memoised per ring array (a pan/zoom re-render is a lookup); the stored origin is NEVER rewritten. Routed through: the Map pin, the zoomed-in name tag, and `flyToSite` (flies to the same point). Polygons/elements still project about the origin (unchanged).
`[x]` **Path that only has the stored point (noted, not changed):** the Dashboard Locations card — its project rows carry only `origin` (cloud rows are slimmed of parcels since B672), so it stays on the stored point until parcel geometry reaches that card. KML export uses the origin only as a no-boundary fallback (correct). No exhibit/PDF path draws a site marker.
