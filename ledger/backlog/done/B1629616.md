**Finding: the dispatch's premise was stale for three of the four.** This codebase already uses two vocabularies for the same optimistic-concurrency guarantee — `version` (client-incremented, the `sites`/`doc_reviews`/`model_sheets` family via `shared/cloud/optimisticUpsert.js`) and `rev` (server-incremented by a trigger). `notes_pages`/`notes_trees`/`notes_images` already carry `rev` + a guarded client write (`.eq("rev", baseRev)` in `notesCloud.js`) — fully protected. `site_elements` carries `rev` **per row** (not per table) and `commit_elements()` requires the client's last-seen rev on every update/delete, raising if omitted — more granular protection than `sites.version`, not less. Neither is a gap; both were corrected in `docs/DATA.md` §8 and each table now carries a `comment on table` recording why, so a future audit doesn't re-derive this.

**Two genuine gaps, filed separately per the dispatch's own instruction (not implemented in this item):**
- **B1629617** — `comps` has no version/rev column at all, and `updateComp()` does an unconditional whole-row `.update()` from a full in-memory snapshot. A stale edit-form tab (the owner's own two-machines/days-open-tabs pattern) silently overwrites every field on save. Needs `casUpsert` — the same primitive three other tables already share.
- **B1629618** — `planar_data` (the Schedule) already embeds a revision inside the jsonb (`value->>'__rev'`) and already guards client-side (read-check-then-write, plus same-tab serialization that closed 2 of 3 known race interleavings — B851's prior fix), but the one write call site issues a plain `upsert` with no database-level `WHERE` clause tying it to the expected rev, so a genuine cross-tab/cross-device race remains. `planar_history` (insert-only) and `planar_suggestions` (single-field status flips only) are safe by construction and needed no fix.

**Why the two gaps were filed rather than fixed here:** the dispatch is explicit — "If the analysis shows one of them genuinely needs the same treatment as sites, file THAT as its own item... rather than widening this one and half-shipping it." `comps`' fix is small and mechanical and could ship quickly in its own session; `planar_data`'s fix touches a single write call site inside a 17,000+-line hand-maintained file this session did not read start to end, and it drives the owner's live, actively-used Schedule — a wrong trigger there is a worse outcome than the race it would close, so it gets its own reviewed session per **DANGEROUS-MEANS-UNOBSERVABLE**'s actual test (the write path IS observable and IS singular; this is a deliberate caution about blast radius, not a vague "dangerous").
