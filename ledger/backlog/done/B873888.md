- **THE EXTRACTION.** `src/workspaces/site-planner/lib/siteMetrics.js` (new) exports `siteMetrics(elements, parcels, parcelOverlapPairs, settings)` — a pure function (no React, no DOM) returning `{siteSqft, bldg, paving, parkArea, trailArea, pondArea, stalls, trailers, bumpCount, bumpArea, bumpsUniform, providedDetCf, pondCount, maxPondDepthFt, impervious, cov, impPct, detPct, ratio, open, far, acresActive}`. `SitePlanner.jsx`'s old `let bldg = 0; …; els.forEach(...)` block (never memoized — it re-ran on every render, including every pan/zoom frame) is now one `const metrics = useMemo(() => siteMetrics(...), [els, parcels, parcelOverlapPairs, settings])` call, destructured into the same local names every downstream consumer (incl. `<YieldPanel>`) already used — ONE definition, and a net perf improvement (the full curb scan + road-strip tessellation no longer re-run on a bare pan/zoom).
- **THE DEPENDENCY CLOSURE WAS BIGGER THAN THE AUDIT'S LINE NUMBERS SUGGESTED, and is reported rather than glossed over.** The metrics loop calls into a cluster of ~25 pure geometry helpers (curb edges/area, road strip area, junction-vertex detection, stall-count math, `ringOf`/`polyArea`/`rot2`) that were ALSO module-scope functions inside `SitePlanner.jsx` — pure (explicit params, no closures) but physically colocated with the render body, and reused at 50+ other call sites throughout the file. `src/workspaces/site-planner/lib/siteGeometry.js` (new) is their real home now; `SitePlanner.jsx` imports them back for its other ~40 call sites — so this is a bigger, cleaner move than "extract one function," and the alternative (re-implementing or duplicating that cluster inside `siteMetrics.js`) would have been the exact "second mirror to drift" the brief warned against. The per-plan roundabout resolution (`SitePlanner.jsx`'s `roundabouts` useMemo body) was likewise lifted out to `siteGeometry.js`'s `roundaboutsForSite(els, settings)` so the drawn roundabout circle and the yield math's paved-area annulus can never describe two different circles. `curbAreaFrom`'s B1352 resolved-neighbour fast path is retired as dead code — proven mathematically identical to calling `curbAreaOf(el, els)` directly (same `curbEdgesOf(el, els)` reduction either way), which is what `siteMetrics.js` now calls, so the neighbour-map machinery (`resolveDockPlan`/`computeBuildingGrid`, needed only for RENDERING) never had to be pulled in.

- **FAR — added, since it did not exist anywhere in `src/` (word-boundary grep returns only English prose).** Defined as `bldg / siteSqft` (a bare ratio, e.g. 0.35 — never re-scaled like `cov`'s percentage) over the GROSS site area, matching `cov`'s own denominator: this codebase has no separate "net developable area" figure (nothing subtracts easements/floodplain/setback-encumbered ground into one buildable-acreage field), so gross `siteSqft` is the only site-area concept FAR could reuse without inventing a second, un-audited one. Bump-outs are IN the numerator — `bldg` already includes them, and excluding them would silently disagree with the coverage percent sitting next to it in the panel. **Not yet wired into `<YieldPanel>`'s UI** (out of scope — "no new features, no UI" per the brief); available to any consumer, present or future, via `metrics.far`.
