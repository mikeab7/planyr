`[x]` **ROOT CAUSE, confirmed live against the real running app with three targeted repro variants before touching any code.** The Properties panel drops a pending `bldgNumConflict` (the parent state backing the Swap/Shift/Cancel prompt) in exactly two places: the Cancel button, and a `useEffect` that clears it when the SELECTION moves to a DIFFERENT building. `BuildingNumberField`'s own Escape handler reverts its local draft text but never touched `bldgNumConflict` — and B1125's window-level "guaranteed escape hatch" (which the Escape keystroke deliberately bubbles to, so it can also close the docked inspector) closes the PANEL without changing the selection, per its own documented contract ("with the element left selected — exactly what the ✕ does"). So `bldgNumConflict` survives untouched whenever the same building is reselected without the selection ever passing through a genuinely DIFFERENT value in between — confirmed to reproduce via a direct double-click on the same still-selected building, and via a single click on the same building followed by reopening the Properties rail tab; confirmed NOT to reproduce when a genuinely different building is selected in between (that path already worked, because the existing selection-change effect correctly clears it).
`[x]` **THE FIX — Escape now drops the pending conflict itself, the same way Cancel does, instead of relying on a selection change that may never happen.** `BuildingNumberField` (`SitePlanner.jsx`) gained an `onCancelConflict` prop, called (in addition to the existing draft revert) on every Escape press; the call site wires it to `() => setBldgNumConflict(null)` — a no-op when nothing is pending. This closes the gap without touching B1125's escape-hatch contract, the selection-change effect, or the Cancel button's own behavior.
`[x]` **E2E regression coverage, real browser, real app, logged out** (`e2e/building-number-panel.spec.js`): a new case triggers the conflict prompt, presses Escape instead of Cancel, then reselects the SAME building via a direct double-click (the exact case proven to reproduce it) and asserts no stale prompt and no committed number.
