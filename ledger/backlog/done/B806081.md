- **AUDIT-FIRST — confirmed the exact mechanism, then found the established fix shape already in the file.** `addLeaderFor` (armed by the callout menu's "Add Leader" row) is checked at the very top of `onBgDown`, the canvas's BUBBLE-phase pointerdown handler bound on the root `<svg>`. `startMoveEl`/`startMoveMarkup` — bound with `pointerEvents="all"` on every element/markup shape — call `e.stopPropagation()` as their second statement (after only a `tool !== "select"` gate, which does not exclude this case, since Add Leader arms while `tool` is still `"select"`), so `onBgDown` never sees the press when it lands on geometry. The exact same shape already exists and is solved for a different armed gesture: `handleStackPick` (B548822, Alt+click) runs in the CAPTURE phase — before any bubble-phase handler — specifically because "it has to win over whichever feature's own bubble-phase pointerdown paint order would otherwise hand the press to."
- **THE FIX.** New `handleAddLeaderCapture(e)`, wired into the SAME `onPointerDownCapture` chain as `notePress`/`handleStackPick`/`onCanvasVtxDownCapture`, checked FIRST (ahead of the stack picker too — Add Leader is a modal placement, not a modifier, so it must win over an Alt+click as well). It consumes the press (`preventDefault`+`stopPropagation`), computes the feet point, calls the existing `addLeaderToCallout`, and clears the armed state — the identical outcome the old bubble-phase branch in `onBgDown` produced, just reached before any element/markup handler can steal the event. The old `if (addLeaderFor)` branch in `onBgDown` is removed (retired, not duplicated) since it is now unreachable while armed.
- **What is unchanged:** `startMoveEl`/`startMoveMarkup` themselves — no per-handler patching, so every other gesture (selection, drag, group-move, attach/align) behaves exactly as before; only the ONE new capture-phase check sits ahead of all of them.
