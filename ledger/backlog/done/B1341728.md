**ROOT CAUSE — one state gap, not four key bugs.** The Owner cell had become this grid's first HYBRID editor: it drew a chosen contact in the **FINISHED** style — a chip with its own remove control, pixel-for-pixel how a saved owner looks — while holding it as unsaved component state, handed over in a single `onCommit` when the edit ended, with an `onCancel` that threw the whole session away. Escape called that cancel path. Every discard path in the component exploited that one gap.

**THE FIX — the chips are now the truth, so no exit can take them back.** `ContactPicker` is a WRITE-THROUGH editor: `onOwnersChange(names, newContacts)` fires the moment a chip is added, removed or reordered, and `onClose()` merely closes. `onCommit`/`onCancel` are gone from the component and from both call sites, so there is no deferred list left to lose — not to Escape, not to Enter, not to an unmount nobody planned for. `commit()` in both grids was split into `applyCommit` (the range-aware WRITE, byte-for-byte the semantics it always had) plus closing the editor, so a write-through editor can save what it shows without closing itself mid-multi-add. A brand-new contact is now handed over in the SAME call that assigns it, which closes the quieter second leak the brief asked about: on Escape the chip AND the contact both used to vanish.

**WHAT ESCAPE MEANS NOW, and why the two exits no longer disagree (the brief asked for this to be stated).** Escape abandons only what is genuinely IN PROGRESS — a typed-but-unconfirmed fragment in the input — and then, on a second press with nothing left to clear, closes the editor. It is not "commit on Escape" and it is not "abandon, visibly": there is nothing left to abandon, because a chip is no longer pending. Ctrl+Z is the recovery for an add or a removal made by mistake, the same as for any other committed cell edit. Consequences stated rather than buried: **(a)** removing a saved owner and then pressing Escape now KEEPS the removal (it used to restore it) — which is what Tab and click-away already did, so this makes the four exits agree instead of three-against-one; **(b)** each add or removal is its own undo step rather than one step per cell visit.

**THE MULTI-ADD FLOW IS UNTOUCHED.** The "Add another…" prompt, the chip reordering, the accountable-first rule, the six-owner cap, the comma and prefix guards, and the "nothing is ever auto-created on blur" protection all behave exactly as before. The defect was the exit, not the invitation.
