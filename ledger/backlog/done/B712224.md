- **WHAT ROUND 1 ACTUALLY FIXED, AND WHAT IT DOES NOT REACH.** `reconcileElems`'s stale-`stateRef.current`-after-`drainRemote()` race is real and stays fixed — but it only closes the case where a tombstone's canvas removal was BUFFERED (`busyRef.current` true: a gesture, even an incidental pan, in flight on the OBSERVING tab). The owner's actual round-2/round-3 repro runs had tab B **completely idle** — no gesture, nothing ever entered `pendingRemoteRef`, so round 1's fold is a no-op with nothing to fold. A `!shad`-shaped stale read reaches `elementSync.reconcile()` from AT LEAST three other doors round 1 cannot touch: **(a)** a plain React state-update lag between the realtime handler's direct (unbuffered) `applyRemoteInstr` call and `stateRef.current` catching up before the next scheduled diff; **(b)** the canvas seam's own heal-pass write (`assemblyGuard`'s `setEls(guarded)` at the "canvas" `useEffect`) — a PLAIN-VALUE `setState` dispatched in the same React batch as a realtime tombstone's FUNCTIONAL `setEls(fn)` removal, which React's `basicStateReducer` treats as a REPLACEMENT of whatever state exists at apply time, silently discarding the removal (confirmed reproducible on a TORN plan specifically — the production fixture plans in this repo's live check carry an un-persisted tear, so this seam fires continuously during the tombstone burst); **(c)** `refetchReplace`'s `sub()` fold, which re-appends any dirty non-delete entry `model.els` lacks even after `seed()` has dropped the row's tombstone from the shadow. All three converge on the SAME missing invariant round 3 (below) closes directly, which is why patching call sites kept failing.
- **THE ROUND-3 ROOT CAUSE, confirmed against PRODUCTION TELEMETRY (a separate `client_errors` capture on `smt6imo0gda0`, not merely reasoned from source) via a dedicated Opus investigation this session, then independently verified against the current source line-by-line before any fix was written.** `elementSync.js`'s `shadow` Map holds LIVE rows only; its absence means two DIFFERENT things the diff engine could not tell apart — "the server has never seen this element" and "the server holds this element as a TOMBSTONE, and the canvas has not caught up yet" — and `reconcile()`'s `!shad` branch (the "brand-new element → create" path) unconditionally assumed the FIRST. `create` is the one op class with no rev guard, and the server (`site_elements.sql`) deliberately AUTO-RESTORES a create over a same-kind tombstone (continues the rev rather than rejecting it) — a documented, correct behavior for a genuine "delete, then undo" (the comment already sitting beside the old code said so). So ANY stale-canvas window — not just the one round 1 fixed — turns a completed delete into a resurrection, minted with no operation envelope open (matching the owner's `op_kind:"unknown"` observation exactly).
- **THE FIX.** A never-pruned "delete floor" (`maxDeleteRev`, which already existed for a DIFFERENT purpose — the B812/round-4 refetch-resurrect guard — and was only ever populated for THIS tab's own deletes) is now recorded on EVERY tombstone this engine learns of: a foreign delete via `applyRemoteRow` (previously `shadow.delete(key)` with nothing recorded), and a tombstoned row read back from `seed()` (previously silently skipped). `reconcile()`'s `!shad` branch now REFUSES to mint a create against a floored key — reporting `element-create-fabricated` (LOUD-FAILURE, the exact mirror of the pre-existing `element-delete-fabricated` guard) and routing the refusal back through the SAME `onRowsCanonical` channel the delete-side refusal already uses (extended to carry `el: null` as a "remove this from the canvas" instruction, wired in `SitePlanner.jsx` to `applyRemoteInstr({action:"remove",...})`) — so a phantom element is actively corrected off the canvas rather than left to linger. **This closes all three doors above at once**, because it does not depend on WHICH stale-canvas window produced the create — it is asked at the one place every one of them funnels through.
- **THE REGRESSION THIS ALMOST SHIPPED, caught by this session's OWN pre-existing test suite (not by a live check) before any code was pushed.** A blanket refusal of every floored create would have silently broken Undo/Redo of a Delete — `applySnapshot` (the undo/redo seam) restores a whole prior canvas snapshot generically, with no notion of "which of these ids used to be deleted," and its post-restore diff would hit the SAME `!shad` branch with no distinguishing signal from a stale-canvas resurrection. Caught by an existing `elementSync.test.js` case (`"the delete floor for reconcileSeedRows survives >15s (never-pruned) and clears on re-create"`) going from green to red the moment the naive refusal was added. Fixed with a SECOND, narrower, one-shot exemption (`allowResurrect(items)`, mirroring the existing `noteLocalAuthority()` stateful-call pattern) that `applySnapshot` stages — immediately before its own SYNCHRONOUS `flushElems` call, so nothing else can interleave — for every id the restored snapshot holds; consumed (or not) and CLEARED at the end of that one diff pass, never left to linger. The pre-existing B673 "Restore" toast action (`restore()`) was already a distinct, correctly-exempted signal and needed no change. The property-based fuzz harness `ui-audit/session-group-cas.mjs` (an hour of simulated real-engine editing, including its own undo/redo actions) caught the SAME gap in ITS simulated client — updated to mirror the real client's new contract identically, rather than weakening the invariant to pass it.
