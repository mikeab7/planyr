`[x]` **SHIPPED THIS SESSION — the premise was RIGHT, and it was a real data-safety bug, not a misreading.** Root cause, established from the code (`lib/notesRedline.js`'s `buildRedline`), not from the screenshot: the redline ALWAYS treated `localDoc` ("this window") as the REVISED side (green/"added") and `serverDoc` ("the other window") as the ORIGINAL side (red/"removed") — a choice bound to WHICH BROWSER TAB you happen to be reading from, never to which copy is actually newer. In the owner's exact case, "this window" held the OLDER edit (4 days ago, table still present) and "the other window" held the NEWER edit (1 day ago, table converted to text) — so the panel's "Table — added" was true only of the arbitrary local/server pairing, and read backwards against real chronology: going old → new, the table was REMOVED, not added. Fix: `buildRedline` itself is now direction-AGNOSTIC (its header comment no longer claims "local = revised"; it just diffs whichever doc its caller passes first as revised) — `ConflictReview.jsx` orders the two copies by recency (B1076176's `orderConflictVersions`) and always passes the NEWER copy as revised, so "added"/"removed" now reads as a true old-→-new story whenever recency is knowable.
