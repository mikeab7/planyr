- **⚠ Note for the record: #858 / #859 / #860 had already merged by the time this was picked up** (B1130/B1131 raised the three ceilings by hand on 2026-07-30 — the fourth instance of exactly the failure mode the budget file forbids). So this item did not "unblock" them; it removes the reason a fifth PR would need the same hand-edit.
- **THE FIX IS A POLICY.** A byte metric no longer stores a ceiling. It stores a `baseline` — the last deliberately recorded measurement — and the ceiling is **derived**: `baseline + max(2% of baseline, 32 KB)`, from one committed `bundle.headroom` band rather than three hand-typed numbers that each drift alone. Four outcomes, one red: `≤ target` passes silently · `target…baseline` prints ABOVE TARGET and names the owner · `baseline…ceiling` prints **ABOVE BASELINE** with how much band is left, and **passes** · past the ceiling **fails hard**, printing the derivation and the exact ratchet command.
- **`totalJsBytes` is banded too**, as the brief asked — it had 4.3 KB (0.11%) of headroom and was next in line to surprise someone. Its `target` is kept EQUAL to its baseline so it keeps asserting "no known gap", and the ratchet moves both together so it cannot silently acquire an unowned one.
- **THE RATCHET IS A NAMED STEP WITH TEETH.** `npm run perf:ratchet -- --metric … --item B### --reason "…"` (`scripts/perf-ratchet.mjs`) **measures the value itself from a fresh build** — you cannot ratchet to a number you typed — refuses without an `--item` and a ≥24-character `--reason`, refuses a RAISE without `--allow-raise`, and appends to `bundle.ratchetLog.entries`. It writes **surgically** (one `"baseline": N` line + one log entry), never a `JSON.stringify` round-trip, because this file is one people read. Enforcement: `test/perfBudgetPolicy.test.js` asserts **every baseline equals the `to` of its own latest log entry**, so a baseline edited by hand — with no reason on the record — goes RED in CI. That is what turns "a ceiling ratchets down only when an optimization lands" from an intention into a fact.
- **Proven on both sides of the line, not just described.** The new suite pins that the 0.9% growth which failed #860 now reports and passes, that one byte past the derived ceiling still fails, that the band is `max(2%, 32 KB)` and not the percentage alone, that a chunk COUNT gets no band, and that the ratchet script exits non-zero on a missing item, a missing reason, a four-character reason, and a missing metric.
- **The mechanism was then USED, not just installed:** all three baselines ratcheted **DOWN** in this same PR off the optimizations in B1145 and B1064(a) — `largestChunkBytes` 1702.7 → 1378.9 KB, `siteRouteJsBytes` 2266.3 → 2242.2 KB, `totalJsBytes` 3887.3 → 3886.1 KB — with the reason on the record. **No ceiling was raised anywhere in this work.**
