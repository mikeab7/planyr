`[x]` **FIXED THIS SESSION** — see B1557008 for the shared verification run (both live-browser harnesses exercise this guard directly: `verify-contact-confirm.mjs` checks 13–19).

**RESOLVED STRUCTURALLY, not just guarded.** The root cause — comma treated as a literal name character — no longer has a way to reach a name at all in the common, typed case: comma is now a chip DELIMITER, intercepted at the KEY level (`onKeyDown`'s `,` branch) before it ever becomes part of `query`, so typing "Matt LeBlanc, Dallas" now commits "Matt LeBlanc" as a chip the instant the comma is typed and leaves "Dallas" as the next fragment — the original bug's shape (one name with a comma and a fragment glued together) cannot form through normal typing any more. The create path is independently guarded anyway, for the one way a comma can still arrive — a PASTE, not a keystroke: `attemptCreate` refuses outright (`name.includes(",")`, an inline message, nothing created) if a pasted block still carries one. A name that is a PREFIX of an existing contact (e.g. typing "Jason Berc" with "Jason Bercaw" already on file) warns instead of silently minting a near-duplicate, and lets the SAME confirming action through a second time once the person has seen the warning (`lastPrefixWarnedFor`) — this is friction for a likely mistake, deliberately kept to exactly one extra step, never a second full confirmation dialog (see B1557012).
