- **THE MODEL — additive, no migration, byte-identical on every plan that has never touched it.** A callout's leader gains an optional per-leader `elbow` (singular) / `elbows` (array, N-leader) field — the exact singular/plural shape `tip`/`tips` already use, `calloutElbows(c)` mirroring `calloutTips(c)`. Absent (every callout ever saved, and any new one until its elbow is dragged) means "no pinned elbow": the render computes the stub's endpoint as the box's own nearest-edge point (`nearestRectPerimeterPoint`, the SAME function that already computed the old single line's origin), so the stub is zero-length and the run IS the old origin→tip line — **provably, not just intended**, byte-identical to every callout ever saved.
- **THE THREE MANIPULABLE PARTS, per the brief.** Box drag (`startMoveCallout(..., "box")`) — unchanged, moves the label; tip drag (`"tip"`) — unchanged, re-aims the target and does NOT move a pinned elbow; **new** elbow drag (`"elbow"`) — pins that leader's elbow to wherever it's dragged (world feet, absolute — matching how `tip` already behaves, so a routing waypoint stays anchored to the ground it was placed at rather than sliding if the tip or box later move). The elbow grip lives in the always-on-top handle layer (`calloutHandles`, CHROME-NEVER-EATS-A-PRESS), a small square distinct from the round tip grip, defaulting to the same box-edge point the render defaults to — grabbable from first selection, not only after a bend already exists.
- **"Never doubles back through its own text box" — handled by construction, not a special case.** The stub's start point is *always* `nearestRectPerimeterPoint(boxRect, tip)`, recomputed fresh every render from the CURRENT box and tip — the same call that already correctly picked the nearest edge for the old single-line leader. So the DEFAULT (unpinned) elbow can never route back into the box regardless of which side the box sits on relative to the target; a user-PINNED elbow is a deliberate routing choice (an obstacle at a fixed ground point) and stays put when the box or tip move independently, exactly as a real Bluebeam elbow behaves.
- **Multi-leader (B919) composes for free.** `calloutElbows(c)[i]` is per-leader-indexed; `removeCalloutLeader` (shared `markupModel.js`) now splices the matching `elbows[i]` out when a leader is deleted (previously untouched, which would have shifted every later leader's pinned elbow onto the wrong leader, or left a stale elbow ready to misapply itself onto the next leader added) — caught and fixed via a new unit test, not observed live.
- **Translate carries a pinned elbow along.** A whole-callout move (multi-select drag, Ctrl-drag duplicate, cross-plan paste) has to move a pinned elbow with the box+tip or it strands at its old ground position. Fixed at the two shared translate functions (`markupModel.js:translate`, `planClipboard.js:translateCalloutBy`) — both already the ONE place every such move already funnels through, so no new call site was needed.
