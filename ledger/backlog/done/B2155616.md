### B2155616 — Food search: a slightly misspelled name must still put the real nearby place on top (×2) `[Food]` (bug) #food #search  *(owner chat block NEW-1, 2026-10-10. `[x]` **SHIPPED.** Owner could not find the Carrabba's at 6501 S Fry Rd, Katy from Cinco Ranch ("Carabas" put it 7th, below the fold). Not a coverage gap — the row exists. Two causes, both fixed:
- **Client (rankByProximity bands):** the RPC's `word_similarity` is literal text, so far rows whose dirty stored name contains the typo scored 1.0 while the correctly named nearby chain scored 0.4–0.8, and distance only breaks ties INSIDE a band. Fix in `searchProximity.js`: `textScore` now also takes a typo-tolerant name score (`fuzzyNameScore`): query and name word-runs are squashed (punctuation, spaces, doubled letters and diacritics dropped — "Carrabba's" → "carabas") and compared by edit distance with transpositions; 0 edits = 1.0, 1 edit = 0.8, 2 edits (queries ≥6 chars) = 0.6 — an edit always lands a full band below a clean hit. It only ever raises a score; plain prefixes are left to the RPC; queries <4 chars get no tolerance. Exact-hit and saved-first rules untouched.
- **Server (pool):** the p_cap pool was top-by-similarity only, so for "Carabas" Fry Rd was 30th of 60 and worse typos fell off. `food_places_search_by_name_fast` (db/food.sql, migration `food_search_pool_includes_nearby`, APPLIED to production 2026-10-11) now returns top-p_cap by similarity PLUS the 40 nearest candidates within 100 km at the same 0.3 threshold (centre given only; no-centre behaviour unchanged). Cost: ~130 ms/call for a very common word ("pizza", warm, with centre) vs ~75 ms without a centre and ~245 ms for the `_raw` reference; "carabas" ~67 ms.
