`[x]` **IMPLEMENTED AND VERIFIED THIS SESSION.** Rides the exact mechanism the width pin already established, per the brief's own instruction ("do not invent a second mechanism"): a new `pageHeight` ProseMirror doc attribute (`null` | a number), set through `setDocAttribute` via a new `setNotePageHeight` command (`lib/notesExtensions.js`), so it is saved, synced, printed and exported for free with no tree schema, no `migratePageNode` entry and no cloud-merge change — mirroring `pageWidth` exactly. Unlike width, there is deliberately **no preset ladder** — the owner did not ask for one, so `lib/notesPageHeight.js` (new, pure, DOM-free, mirroring `notesPageWidth.js`'s shape) is Fit to content (`null`) plus a dragged Custom number, nothing else.

**Grips.** Two new hit-strips on `note-sheet`, horizontal twins of the existing width grips (`note-page-height-grip-top`/`-bottom`, `row-resize` cursor, same hover-only bar, same `!narrow` desktop-only gating as the side grips — a phone's vertical space isn't the same constraint width's `!narrow` gate was written for, but "four edges, one consistent behaviour" was the brief's own instruction and this keeps the touch target budget identical to the shipped precedent). Growth is expressed the SAME way the unpinned default already was — `NoteEditor.jsx`'s pre-existing `dom.style.minHeight = max(46vh, need)` line now reads `dom.style.minHeight = pinnedHeight != null ? max(pinnedHeight, need) : (need ? max(46vh, need) : "")`, so a pin is a FLOOR under real content (an anchored box needing more room than the pin still wins via `Math.max`) exactly like the width pin's `Math.max(effectivePageWidth, needX)`. **BOTTOM edge** grows `dom.style.minHeight` toward the pointer, no scroll trick needed (the top of the body never moves for this — the same free "opposite edge holds" the width feature's own RIGHT edge gets). **TOP edge** grows the identical `minHeight` (there is only ever one growth direction at rest, DOWN, matching width's rightward-only growth) but additionally scrolls `note-mat` by the same amount the height grew — the exact algebra `beginWidthDrag`'s own LEFT-edge comment already works out, transposed: a body `H` taller and a viewport scrolled `H` further down show the BOTTOM edge at its original screen position, and the TOP edge lands `H` above where it started. A drag's own live floor (`heightContentFloorRef`) is `need` ALONE, never the current pin — reading a drag's floor from the value it is about to overwrite is the exact NOTES-PAGE-GROWTH/B1561104 mistake `docs/NOTES-CARRY-FORWARD.md` §5's family -1 already names (narrowing an existing pin would silently do nothing); a plain click with no real movement commits nothing, matching B391073's standing rule and `beginWidthDrag`'s identical guard.

**⛔ THE REAL BUG THIS SURFACED, and it is the reason section 6 of the brief exists: `box.bottom` stopped meaning "where the flow ends" the moment a height pin could set it past real content.** Before this feature, `dom.style.minHeight` was only ever set for an anchored box's own overflow, so `box.bottom` (`NoteEditor.jsx`'s `focusFromMat`) and "the last real line's own bottom edge" were the same fact, and a click below it always landed genuinely outside `.ProseMirror` (in the sheet's own fixed bottom padding), where the existing B1550976 "click below → caret at end" branch (`focusEndOfSheet()`) already fired correctly. A height pin creates, for the first time, a stretch of true blank canvas **inside** `dom`'s own rendered box, below every real line — and a native click there does NOT reliably place a caret (measured: `document.activeElement` stayed `BODY`). The first draft of this fix replaced `box.bottom` with the document's real end (`editor.view.coordsAtPos(doc.content.size).bottom`) for EVERY case, and that broke a real, pre-existing, tested behaviour caught by `verify-notes-anchor-zoom.mjs`: the ordinary UNPINNED "max(46vh, need)" floor already leaves ordinary blank canvas inside `dom`'s box below a short paragraph, and double-clicking there is the established "open page, place a new block" gesture — replacing `box.bottom` wholesale routed every one of those clicks to "caret at the end" instead, and no anchor ever appeared. The fix that held: the document's-real-end boundary governs `e.clientY >= belowContent` **only while `editor.state.doc.attrs.pageHeight != null`** (a height pin is genuinely active) — every unpinned page's existing behaviour, anchor placement included, is untouched.

**PDF-PARITY.** `pageHeightPinExtentPx(doc)` (`lib/notesPrint.js`, pure, mirrors `pageWidthPinExtentPx`) folds a numeric height pin into the SAME `sheetCss` computation `buildPrintDocument` already builds for width — `min-height: <pin>px` on `.sheet`, reserving that much of the printed sheet exactly the way an already-overflowing page does (real content past one physical sheet already paginates onto the next; a shorter-than-its-pin page simply prints the extra blank space). Driven through the real toolbar Print button and the rendered iframe, not only the pure builder.

**Menu.** A `FormatMenu` "Page height" beside "Page width" (`NoteToolbar.jsx`), on both the desktop row and the phone "Page" overflow group — its one option is "Fit to content" (`pageHeightLabel` reads "Custom" for any dragged value), which is the stated "way back" out of a pin: `editor.commands.setNotePageHeight(null)`.
