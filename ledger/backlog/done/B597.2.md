- **Root cause — TWO independent revert bugs, both surfacing as "the name comes back":**
  1. **(primary) The header breadcrumb dropdown (planner view).** The project switcher owns a local list (`internalProjects`) yet the Site Planner ALSO supplies `onRenameProject`. `ProjectBreadcrumb.commitRename` only re-read that local list in its bare `else` branch, so when `onRenameProject` was present it wrote the new name to the store but never refreshed the list — and a same-tab store write doesn't fire the native `storage` event — so the just-edited row (and the crumb) kept the OLD name. An instant revert on essentially EVERY site rename.
  2. **The map's YOUR SITES list, multi-plan sites.** The list passes a *representative plan* id; `renameSiteGroup`/`renameSite` treated it as a group id. For a site whose newest plan isn't the group anchor, `loadPlansOfGroup(planId)` matched nothing → no save → revert (and, signed in, nothing pushed to the cloud).
- **Fix:**
  - `ProjectBreadcrumb.commitRename` now refreshes the local list + nudges the other `planarfit:sites` surfaces for BOTH branches whenever it is uncontrolled (Schedule's controlled mode still relies on its bridge prop).
  - `renameSiteGroup` (storage) and `renameSite` (SitePlannerApp) resolve the incoming id to its group (`groupOf(loadSite(id))`) before renaming + cloud-pushing, so a group id OR any plan id within it renames the whole site.
- **Tests:** +4 `test/storage.test.js` cases (rename by group id · by a NON-anchor plan id · single-plan · unknown-id no-op).
