- Verify: sandbox
- **PART 1 (the defect, confirmed real):** `colArray()` rebuilt the ENTIRE column array from `ctx.rows` on every call, and the host (`computeFormulaValues` in `public/sequence/index.html`) calls `evaluateFormula()` once per row against the SAME shared `rows` array — so every whole-column aggregate was O(rows) work × O(rows) calls = **O(rows²)**. Measured on this machine before any fix, reproducing the brief's numbers closely: `SUM([Cost])` 2000r=133.6ms/5000r=330.8ms · `COUNTIF([Cost],">50")` 770.2ms/4606.4ms · `SUMIF([Cost],">50",[Budget])` 913.3ms/5150.4ms · `XLOOKUP([Duration],[Cost],[Task])` 94.0ms/539.9ms.
- **THE FIX, two tiers, both keyed on the `ctx.rows` array's own object IDENTITY via `WeakMap` (no manual invalidation — a fresh recalc pass builds a fresh rows array, so a stale entry can never be read; it is simply garbage once nothing references the old array):**
  1. `colArrayCache` — memoizes the built `[Column]→values[]` array itself per (rows array, column key). Fixes the O(rows) rebuild for all 13 range-aware functions unconditionally.
  2. `rngResultCache` — memoizes the ENTIRE result of a range-aware call per (AST node, rows array) whenever **every argument is row-invariant** — decided via a declared `RANGE_ARG_POSITIONS` table (which argument slots each of the 13 functions actually reads as a whole-column RANGE, lifted from each function's own existing implementation, not guessed) plus a recursive, memoized structural scan (`isRowInvariant`) of the remaining scalar arguments. This is what gets COUNTIF/SUMIF from "cached array, still O(rows) criteria-scan per row" down to "computed once, O(1) lookup for every other row."
  3. `parseFormula` also gained an LRU-ish cache keyed on source text (the host re-tokenizes/re-parses the SAME formula string once per row) — this is *also* what makes the two caches above actually hit: the SAME parsed AST node objects recur across a pass's per-row calls only because parsing is now cached.
  4. `TODAY`/`NOW`/`WORKDAY`/`NETWORKDAYS` are always treated as row-variant (conservatively) since they read `ctx.today`/`ctx.calendar`, which aren't part of the cache key.
- **⛔ THE TRAP NAMED IN THE BRIEF, hit and fixed exactly as warned:** a first draft that classified invariance by node SHAPE (any bare `[Col]` arg = hoistable) breaks `XLOOKUP([Duration],[Cost],[Task])` — the FIRST argument is a scalar this-row lookup value, not a range, so hoisting it freezes row 0's answer onto every row. Invariance is decided **per argument POSITION, per function** (`RANGE_ARG_POSITIONS`), never by shape alone. Mutation-proven: deliberately mis-declaring `XLOOKUP`'s target position (or `COUNTIF`'s criteria position) as a range immediately breaks a dedicated regression test built for exactly this trap (`test/formula.test.js` → "row-invariant caching — correctness under the SAME shared rows array").
- **ACCEPTANCE, beaten:** byte-identical results old-vs-new across all 13 range-aware functions, 28 formulas × 200 rows (the brief's own bar was 11/11 × 200 rows), including deliberately adversarial cases (row-varying MATCH/XLOOKUP target, row-varying COUNTIF/SUMIF criteria including a BARE-COLUMN criteria arg, row-varying INDEX position, a nested rng-in-rng call, an `IF` alternating between two invariant branches, and a cached `#REF!`/`#N/A` error faithfully re-thrown on every row).
- **MEASURED AFTER (this machine, not the brief's clone — numbers will differ by hardware/JIT, that's expected):** `SUM([Cost])` 2000r=4.0ms/5000r=7.3ms (**45×**) · `COUNTIF([Cost],">50")` 3.2ms/8.2ms (**562×**) · `SUMIF([Cost],">50",[Budget])` 2.5ms/5.3ms (**972×**) · `XLOOKUP([Duration],[Cost],[Task])` 8.0ms/16.9ms (**32×**). Confirmed genuinely linear (not merely "fast at this size"): SUM at 40,000 rows runs in 23ms (ms/row *falls* as rows grow, the opposite of a quadratic signature). A generous, non-flaky regression guard (`test/formula.test.js`, following the interleaved-min-of-REPS pattern already used in `test/pondViewIndependence.test.js`) asserts 8× the rows never costs anywhere near 8²=64× the time.
- **PART 2 — 14 financial functions added as ORDINARY `{ fn: ... }` entries (none range-aware), taking plain scalar arguments exactly like the existing 95:** `NPV`, `XNPV`, `IRR`, `XIRR`, `MIRR`, `PMT`, `IPMT`, `PPMT`, `RATE`, `NPER`, `FV`, `PV`, `CUMIPMT`, `CUMPRINC`. `XNPV`/`XIRR` take interleaved `(value,date)` scalar pairs (no array type exists in this engine). Every PMT/PV/FV/NPER formula is one rearrangement of the single annuity identity `PV*(1+r)^n + PMT*(1+r·type)*((1+r)^n−1)/r + FV = 0` (documented in `formula.js` next to the code, not memorized). Newton-Raphson with a bracket-search bisection fallback (`solveRoot`) serves IRR/XIRR/RATE.
- **⛔ VALIDATION CAUGHT A REAL BUG the brief's own warning predicted the SHAPE of, though not this exact one:** the first `IPMT` derivation returned the interest **charged** (a positive "amount owed grew by") instead of the interest **paid** (a cash outflow, negative — matching `PMT`'s own sign convention). The trivially-true `IPMT(n)+PPMT(n)==PMT` identity did **not** catch it (since `PPMT` is defined as `PMT−IPMT`, a one-sided sign flip in `IPMT` is silently absorbed by `PPMT` and the sum stays correct) — it was caught by the two identities that check against an INDEPENDENT external total: "sum of `PPMT` over the full term == −PV" and "`CUMIPMT`+`CUMPRINC` over the full term == `nper×PMT`". Hand-traced against a 1-period, 10%-rate, $1,000 loan (`PMT`=−1100 must decompose into `IPMT`=−100, `PPMT`=−1000) to confirm the fix rather than trust the invariant alone.
- **Per the brief's explicit instruction — where a remembered Excel constant would disagree with a structural invariant, the invariant wins, stated out loud:** no such disagreement arose here (unlike the prototype's own PMT experience, cited in the brief) — every invariant below passed against the derived formulas with no numeric constant consulted from memory at all.
