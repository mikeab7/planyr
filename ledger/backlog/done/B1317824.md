- **THE REGRESSION, and why it is the mirror image of B846385 rather than a new defect.** B846385 (2026-09-01) fixed a real prior collapse (long-task attribution lost first) by flipping the shedding priority the OTHER way: the frame track now shed via its ladder and then **all the way to zero** before the long-task table ever lost a single row below its own floor of 4. That overcorrected — on the owner's 2026-09-07 row, 114 frames and ~20 long tasks arrived as `framesKept:0`/`framesDropped:114`/`ft:""`, while every long task rode the row untouched. The worse the stall (the more long tasks it produces), the less of the frame evidence survives — the same shape as the trigger defect caught before merge in PR 951 (a fixed budget that gets progressively less likely to succeed the worse the case it exists for gets).
- **THE FIX.** `encodeCapture` (`perfCapture.js`) now gives the frame track a **reserved floor** — the same `8` that was already the last rung of `FRAME_FLOORS`, no new magic number — that survives as long as ANY long task remains in the row. The long-task table sheds **oldest-first** (previously smallest-duration-first) into whatever room the frame reserve leaves, mirroring the direction the frame track itself already trims in ("the most recent N," not "the biggest N"). Only once the long-task table is fully empty does the frame reserve itself give way, down toward zero — the genuine last-resort case B265541's ladder already documents. Counters are unaffected — still shed first of all, as before.
- **HONEST ACCOUNTING, MADE MORE HONEST.** `framesDropped`/`tasksDropped` (the latter already existed, from B846385) are both still reported. The `note` field no longer reports a bare `"trimmed"` for any of these squeezes — `NOTE_VOCAB` now carries `trimmed-frames` / `trimmed-tasks` / `trimmed-both` / `trimmed-counters`, naming exactly which series a shortfall cut, so a reader never again has to cross-reference `framesKept` to learn whether the frame track survived at all. `trimmed-hard` (the genuine last-resort, row-still-doesn't-fit case) is unchanged.
- **PROVEN RED THEN GREEN, on the owner's own real numbers.** `test/perfRecorder.test.js`'s new test builds a capture with 114 frames (most past the 63ms clamp, so nearly every one also costs an `fx` pair — B265541's mechanism) and 23 long tasks each with a distinct, realistic attribution name, and runs it through BOTH the shipped-before-this-fix order (`preNew1EncodeCapture`, a verbatim copy of the exact code this item replaces, kept in the test as the mutation baseline — not trusted from a description of it) and the new `encodeCapture`.
