`[x]` **DONE — headless-verified 2026-07-29 (Verify: sandbox).**
- **The report.** "When I just scrolled my mouse over some colours, it filled up the entire colour swatch. That's not really the intent, it's to actually use stuff that I used."
- **Root cause (confirmed, and the comment in the code was WRONG about it).** `livePick`'s `onChange` called `pushRecent(e.target.value)`. The code claimed `change` "fires once, when the wheel CLOSES" — in the real browser it fires repeatedly as the cursor moves through the spectrum, so one drag pushed every intermediate shade and filled all ten slots with near-identical colours.
- **Fix — ONE entry per picking SESSION, recorded at commit.** `notePick(v)` remembers the value the open session is on (recording nothing); `commitPick()` at the session boundary records exactly one entry — the colour it settled on. The boundary is the wheel's blur, a new focus, and the picker closing or unmounting, so a session can't leak past the picker's life. Live preview still recolours the object on every event — that behaviour is intentional and untouched.
- **The discrete paths are unchanged:** a swatch click and the multi-select path each push one entry per click, as they should.
- **GUARD, as specified.** `test/colorRecents.test.js` drives N live events + one commit and asserts the list grew by **exactly one**, equal to the final value, with no intermediate present — plus a regression WITNESS test showing the old one-push-per-event behaviour consuming six slots from one drag. Both are new API on this branch, so the suite does not run on current `main`. A source guard also fails if `pushRecent(e.target.value)` ever returns to the wheel handlers, and `e2e/…swatches.spec.js` drives six real `input`/`change` events in Chromium and asserts one stored entry.
