- Verify: sandbox — pure client-side routing logic (which parcel sources COULD cover a point), fully deterministic and tested against the real, committed nationwide county-boundary asset (`public/geo/county-polygons.json`) with no live network involved. Whether an individual live ArcGIS server answers correctly is unchanged by this fix and already covered by the endpoints' own provenance notes in `counties.js` — nothing here needs a live/signed-in pass.

**ROOT CAUSE.** `candidateCountiesForPoint` (`src/workspaces/site-planner/lib/counties.js`) narrows candidates two ways: a padded-bbox pre-filter for counties with one configured, and a last-resort STATE-scoped fallback for a point outside every bbox. That fallback used `stateForPoint`, which is `siteState()` from `siteRegion.js` — a relic of the app's first two states, whose `STATE_ENVELOPES` only knows two rectangles: Texas and Colorado. Every OTHER wired state (Nevada, DC, California, Rhode Island, Maine, and ~26 more `_statewide`-only entries) has NO per-county bbox at all — it's a single statewide composite with no `bbox` field, by design (see the `_statewide` entries' own comments: "NO bbox — it must never win a click by extent"). So a click in any of those ~30 states always missed both the bbox pre-filter AND the TX/CO envelope, and fell through to the function's final line: `entries.length ? inState : entries.map(([k]) => k)` — when `inState` came up empty (which it always did for a non-TX/CO state), it returned **every configured source in the entire file**. That is the 67-request fan-out, verbatim: candidate[0] was always `harris`-adjacent Texas counties (config order), which is exactly the order the network panel showed. Michael's own 2026-09-10 instruction — wire every remaining state county-by-county where there's no statewide source — was about to turn "occasionally wasteful" into "unusable": thousands of sources fanned out on every click.

**THE FIX.** A new `resolvedState(lat, lng)` asks the SAME nationwide county-polygon asset `geometryCountyKey` already reads for point-in-county containment (B209502 — every US county, not just TX/CO, already shipped 2026-09-08) for the point's real STATE, independent of whether a specific per-county entry is configured there. A purely-statewide state like Nevada has no per-county row to hoist to candidate[0], but its resolved `state` field is real, so `candidateCountiesForPoint` can now narrow to exactly that state's configured source(s) — normally one (its statewide composite), occasionally two (a real county CAD plus a statewide backup, or two overlapping county bboxes — the existing Sugar Land harris+fortbend case). Falls back to the coarse TX/CO envelope only while the geometry asset hasn't landed yet (`resolveCounty` reports `pending`), so the very first click after a cold boot still narrows whenever it honestly can. **The old "return everyone's sources" last resort is gone outright** — a point whose state genuinely can't be resolved (asset still pending, or truly outside every covered US territory) now returns NO candidates, never all of them; `resolveCandidates`/`candidatesAtPoint` (both MapFinder.jsx and SitePlanner.jsx — both already funnelled through this one function, confirmed by the existing `parcelClickRouting.test.js` source guard) already handle an empty candidate list with an honest "still loading, try again" message. A resolved state with genuinely zero wired coverage (e.g. New Mexico) now correctly returns nothing to try, instead of trying everything.

**THE `outFields=*`/`returnGeometry=true` HALF OF THE REPORT.** Every candidate query does still ask for full attributes + geometry — that's necessary, since any queried candidate might be the one that actually answers, and there's no way to know which without asking. What's fixed is WHO gets asked: with candidates narrowed from 67+ down to 1 (typically) or 2 (occasionally), the "every candidate pays the full cost" concern the report raised is bounded by the same small number, not by the size of the country. Considered and rejected: a two-phase lean-query-then-full-fetch race, which would add a second round trip to the now-common single-candidate case (net MORE requests for the typical click) for a marginal saving on the rare two-candidate case, while touching the same delicate, extensively-tested statewide-backup racing/grace logic (BACKUP_GRACE_MS, B634) this item doesn't otherwise need to change. Flagging this loudly per house rules rather than silently narrowing scope: the fan-out narrowing is the fix for the report's own numbers (67 → 1–2), and a further two-phase protocol was judged not worth the risk it would add to a subsystem with a long, hard-won bug history (B244/B245/B630/B634/B643).
