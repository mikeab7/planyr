- **Root cause, confirmed in source.** `markupHandles`' `MK_BOX_KINDS` branch (rect/ellipse markups) drew its "B619 thin blue bounding outline" as a `<polygon>` built from the SAME corners as the markup's own visible stroke (`at(sx * m.w/2, sy * m.h/2)`) — geometrically identical to the shape's own path, just 1px wide and painted on top from the always-on-top handle layer (B1197: the handle layer is the LAST child of the feet-space transform, so it always paints over the object's own content regardless of z-order). A user's 2px orange line and this 1px blue line were coincident pixels — the reported defect exactly.
- **The fix — grow the outline OUTWARD, never trace the shape's own path.** A translucent "halo underneath" (the pattern `utilRoute`/`traced`/`encumbrance` markups already use for their own `isSel` cue) does NOT work here, because both `elSelOutline` and `markupHandles` render from the always-on-top handle layer — there is no "underneath" to draw into; anything painted there sits on top of the shape regardless of opacity. So the outline is offset OUTWARD by a constant screen-px gap (`SEL_OUTLINE_GAP_PX = 4`, a new module constant beside `SEL_BLUE`/`SEL_HANDLE_FILL`) so it never touches the shape's own stroke pixels at all, forming a clean ring visibly outside the shape — the report's own "offset the outline outward" direction.
  - **`markupHandles`' box-kind branch** (rect/ellipse): the local half-extents are grown by the gap (converted feet via `rppf`) before the same rotation math (`at()`) that already places the resize/rotate handles — `at(sx * (m.w/2 + gapFt), sy * (m.h/2 + gapFt))`. Only the OUTLINE moves; the resize/rotate handles stay at the markup's TRUE corners/edges, where a drag needs to grab. Covers **every** `MK_BOX_KINDS` member (rect AND ellipse), not just rect, per the item's explicit instruction not to fix only the reported shape.
  - **`elSelOutline`** (the ONE outline for a selected site ELEMENT — a pond, a building, any el with a user-set `el.stroke` override via `elStyle`): both its general branch (`el.points` polygon, or `elCorners(el)` for a plain rect element) and its locked-road `elCorners` branch now run the screen-space ring through a new `outsetPolygon` before drawing, falling back to the ungrown ring when there are too few vertices to offset. The locked-road CENTERLINE halo (translucent stroke along the road's own geometry) is untouched — it was never coincident-opaque in the first place, it's already the "good" halo idiom.
- **New shared primitive, `outsetPolygon(pts, d)` in `lib/parcelOffset.js`** — the mirror-image of the existing `offsetPolygon` (the setback ring's inward offset): both now share one `buildOffsetRing(pts, d, sign)` per-edge-normal-with-bevel-fallback construction (refactored out, byte-identical behavior for `offsetPolygon`'s existing callers), and `outsetPolygon` picks whichever sign GROWS the ring's area instead of shrinking it, with no boundary-clamp (growing past the source ring is the entire point). Used by `elSelOutline` for the general polygon case; `markupHandles`' box-kind branch uses a simpler local half-extent expansion instead, since a rotated rectangle's outward offset is exact and cheaper without going through the general polygon-offset machinery.
- **ANSWERING THE ITEM'S OWN QUESTION — "should `elSelOutline` and `markupHandles` be ONE function?" Plainly: no, and the reason is structural, not inertia.** `elSelOutline` draws ONLY the outline (an element's resize/rotate handles are a separate set, `handleNodes`, keyed off a different selection model). `markupHandles` draws the outline **and** the resize/rotate/vertex grips together, because a markup's manipulation UX is bundled with its own component (rotation, individual edge/corner resize) in a way an element's is not. Merging them would mean one function branching on `sel.kind` to decide whether to also emit grips — more coupling, not less, for two call sites that were never duplicating the same DECISION (both now express "grow outward by a constant gap," but through the primitive they share, `outsetPolygon`/the same half-extent-expansion idea, not through one code path). What WAS a real duplication — two different constructions of "draw an outline exactly on the boundary" — is now gone: both sides grow outward through the same idea, and the geometry primitive (`outsetPolygon`) is shared, not reimplemented per call site. Two implementations of "here is the handle chrome for this kind of selection" is legitimate, matching how `parcelHandles`/`elPolyHandles`/`markupHandles`/`calloutHandles`/`measureHandles` are already five separate, deliberate handle sets in this file (per B1197's own header) — not a class of problem this repo's design arc exists to stop; two DIFFERENT GEOMETRIES for "draw the outline outside the shape" would have been.
