### B735 (×2) — AnchoredMenu / ContextMenu portal backdrop can linger over the newly-active workspace when a menu is left open across a module switch — including the project switcher's own Delete `[App Shell / UI]` (bug) #ui #infra #site-planner  *(self-discovered 2026-07-09 during the B734 post-merge adversarial review; **B735** = highest B# across both files (B734) + 1)*
`[x]` Every `AnchoredMenu` consumer with LOCAL open state (the account dropdown, Site Planner rail flyouts + export/print menus, the project breadcrumb, the scheduler toolbar, the team-role menu) can be left `open` and then have its host workspace hidden by the keep-alive render (`display:none`) if the user navigates **without a click** — browser **Back/Forward** or a programmatic hash change. Because the menu renders in a **portal at `document.body`**, and the click-away backdrop (`position:fixed; inset:0`) renders whenever `open===true`, the hidden instance leaves a full-screen (invisible) click-trap — and, since `place()` doesn't re-run on the display flip so `pos` stays stale-truthy, the menu itself can even render at its stale position — hanging over the newly-active workspace until one click / Esc dismisses it. Rare and self-recovering, but a real UX trap.
- Origin: found 2026-07-09 during the B734 post-merge review (the B734 fix — self-contained per-instance `AccountControl` — surfaced it; the account dropdown itself is already handled, see below).
- **Partial fix already shipped (B734 follow-up):** `AccountControl` closes its own dropdown on `hashchange` (fires on every nav incl. Back/Forward), so the ACCOUNT menu — the most-reachable instance, present in every header — no longer lingers. This item covers the REMAINING consumers.
- **DEDUPE-FIRST (original filing):** net-new. Relatives (not dupes): B734 (the corner-anchor fix + `placeMenu`; this is a different symptom — lingering-after-nav, not mis-anchored-on-open) · B127 (built `AnchoredMenu`).
- **Recurrence (×2), 2026-08-31 — owner chat block (NEW-2), filed alongside the B933856 (×3) Dashboard-breadcrumb item with a note it might share the same root cause: "this delete button doesn't seem to do anything." Repro: open the project switcher from the breadcrumb, click the ⋯ on a project row, choose Delete. Nothing happens — no confirmation appears, no error.** The owner's own read of the production schema (no `projects` table; `sites.group_id` a plain jsonb mirror) suggested "delete has nowhere to write" — that hypothesis is **WRONG and was checked before acting on it**: `deleteSiteGroup` (storage.js) is a real, complete, already-working soft-delete (every plan in the group, `deleted_at` stamped, restorable 30 days) fully wired through `ProjectBreadcrumb.jsx`'s `doDelete`, proven working end to end with nothing else going on (CASE A of the new harness below). The owner's OWN instinct that it shares a mechanism with B933856's "five duplicate shells" was directionally right (both live in the keep-alive architecture) but the exact culprit is this item, B735, not a duplicate-shell issue — confirmed by direct reproduction, not guessed.
- **⛔ ROOT CAUSE, found by direct reproduction in a real headless browser (not guessed):** the project switcher's per-row Rename/Delete popup is **NOT** built from `AnchoredMenu` at all — it's `ContextMenu.jsx` (a separate, more widely-reused primitive: map pins, canvas elements, parcels, markups, the Library folder tree, Doc Review markup objects, and the project breadcrumb all share it). `ContextMenu` opens at a fixed cursor x/y with **no anchor element to watch at all**, so B735's original "watch the anchor go zero-size" fix could never have covered it even if built. And even `AnchoredMenu`'s own case (B1125's existing "clear pos on a zero-sized anchor" fix) never fires for a **NESTED** menu like the project switcher's outer dropdown + its per-row kebab: the outer panel hides itself with `visibility:hidden` (never `display:none`), which keeps every descendant's layout box — the kebab's own anchor button included — at its ordinary non-zero size (measured live: stayed 20×18 px, unchanged, long after its host workspace was switched away). So leaving the switcher + kebab open, then switching module tabs, left the kebab's full-viewport click-away backdrop mounted, invisible, over the newly-active workspace (confirmed via `elementFromPoint` at its center) — silently eating every click there — and switching back left the SAME trap over the original workspace too, blocking even the switcher's own trigger button from reopening.
- **THE FIX, three parts, all in the two shared primitives (fixed once, not per-consumer, per this component's own "fix the class once" philosophy):**
  1. `AnchoredMenu.jsx` gained a `ResizeObserver` on the anchor (catches a `display:none` collapse that neither `resize` nor `scroll` can) **and** a `hashchange` listener that fully **closes** the menu (via `onClose`, not a bare `setPos(null)` — merely hiding would let the ResizeObserver's own next callback silently REOPEN the menu the moment its anchor becomes measurable again, e.g. navigating back to the same workspace, which is worse than the original bug). This app's entire route lives in the hash (route.js), so no consumer here ever legitimately needs a menu to survive a navigation.
  2. `ContextMenu.jsx` gained the same `hashchange` close — it has no anchor to watch at all, so `hashchange` is the *only* signal available to it.
  3. **⛔ THE SUBTLE PART, MEASURED not guessed, and it is what made this exact fix (implemented, then re-tested) still fail 100% of the time in this session's own headless harness, on three separate attempts, before being caught:** a bare `[onClose]` (or `[open, onClose]`) effect dependency is racy for this SPECIFIC event, because every consumer passes an inline arrow (`onClose={() => setMenuFor(null)}`) — a fresh function identity every render — and the HOST re-renders as a direct side effect of the very `hashchange` the listener exists to catch (the route change that fires it is what switches workspaces). That tears the listener down and re-adds it on the SAME render, and browsers snapshot a native event's listener list at DISPATCH time, so a listener removed mid-dispatch is skipped for the event already in flight. Measured with a bare dependency: the handler fired **0 times per navigation, every time — deterministic, not a rare race**. Both components now read `onClose` through a **ref** (updated every render, never a dependency), so the listener registers once per mount and can never be torn down by the very re-render it needs to survive.
  4. **LOUD-FAILURE hardening (`ProjectBreadcrumb.jsx`):** `deleteSiteGroup` legitimately resolves `{ok:true, removed:0}` when this device's local cache holds no plan for a group at all (never pulled, or a stale/emptied cache) — a real "nothing to delete here" outcome that used to read as total silence, indistinguishable from the menu being broken. `doDelete` now flashes a toast on that outcome too, exactly like the existing cloud-failure surface. Not proven reachable through the normal switcher path (the switcher's own project id and `loadPlansOfGroup`'s filter derive from the identical `groupOf` function, so they can't disagree for a project the switcher itself is listing) — added because a destructive control must never fail silently, whatever the cause, per the block's own explicit ask.
- **⛔ THE "15 vs 28" RECENTLY-DELETED DISCREPANCY THE OWNER ALSO FLAGGED — CHECKED DIRECTLY AGAINST PRODUCTION, READ-ONLY, NOT GUESSED.** `listDeletedProjects()` groups soft-deleted `sites` rows by project (`group_id`), matching how Delete itself is offered — so the two numbers were never expected to match one-for-one on their own, but the owner was right to ask which discrepancy this actually was. Read live via the Supabase MCP tool (SELECT only, no writes): the production `sites` table holds **28** soft-deleted rows across **17** distinct projects account-wide — but scoped to the owner's own `user_id` (exactly what RLS + `cloudDeletedRows` already restrict the switcher to), it's **26** soft-deleted rows across **15** distinct projects — an EXACT match to the "Recently deleted · 15" the switcher showed him. **This is not a bug**: the gap between the account-wide numbers and the owner's own is two other rows belonging to a different account (a teammate, or another user entirely) that correctly never appear in his bin — a delete/trash UI showing another account's deleted rows would be the actual bug. No code change; the mechanism is now on record so it isn't re-investigated as a live discrepancy.
- **Verify: sandbox — fully reproduced and fixed logged out, local-only, no cloud dependency at all** (unlike most of this app's UI, this specific mechanism has zero signed-in/real-data surface: the bug and the fix both live entirely in client-side popup lifecycle). `node ui-audit/verify-project-delete-menu.mjs` — CASE A (plain delete, nothing else going on) and CASE B (the exact repro: switcher + kebab left open, navigate away via a real `hashchange`, confirm the new workspace is NOT covered by an invisible interceptor, navigate back, delete a DIFFERENT project fresh, confirm the confirmation view the owner reported as never appearing now appears and the delete completes) — both green. **Mutation-proven, twice over:** (a) stashing both fixed files and rebuilding reproduces CASE B failing exactly as reported (the interceptor check fails, then the switcher's own trigger times out — an uncaught uninterceptable click, matching "nothing happens" to the letter); (b) reverting ONLY the ref-stabilization (swapping `onCloseRef` back to a bare `onClose` dependency, keeping the ResizeObserver/hashchange listeners themselves) reproduces the SAME failure on its own, deterministically — proving the dependency-array fix is load-bearing and not redundant with the listener additions.
