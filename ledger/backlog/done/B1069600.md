DEDUPE-FIRST — searched Open/⏳Verify/Done for "compEntryDockHeight", "dockHeight", "DOCK_HEIGHT", "Paste comps" panel height: HARDENING-12 (B986096) built the bottom-docked panel and its resize handle but never made the DEFAULT height respond to the viewport — a flat 340px was hardcoded regardless of window size. Net-new.)*
`[x]` **SHIPPED THIS SESSION.** Root cause: `DOCK_HEIGHT_DEFAULT` (340) was a flat constant with no relationship to `window.innerHeight` — on a 521px-tall window it consumed 65% of the viewport and STILL left only 76px for the grid, because the paste box + status line + summary row + footer chrome ate the rest of the fixed budget.
- **The fix.** `defaultDockHeight()` now computes the panel's OPENING height from `window.innerHeight`, reusing the exact same viewport margin (`h - 80`) the resize handle already clamps a manual drag to — so the automatic default and the drag ceiling can never disagree about how much of the viewport this panel may claim. A saved height (the user's own prior manual resize) always wins over the computed default, as before.
- **⛔ A REAL SECOND DEFECT WAS FOUND AND FIXED WHILE VERIFYING THIS ONE, NOT SHIPPED SEPARATELY.** The naive `h - 80` default grows the panel to `DOCK_HEIGHT_MAX` (760) on any normal-height window — `ui-audit/verify-comp-entry-p0.mjs`'s own pre-existing DOCKING check (HARDENING-12, "the map above the panel must stay clickable") caught this before it shipped: at a 900px-tall window it left only 128px of map visible, below that check's own 300px bar. The automatic default now uses a SEPARATE, smaller ceiling (`DOCK_HEIGHT_DEFAULT_MAX = 500`) than the manual-drag maximum — generous enough to show several rows without the reported 2-row scroll, but never so tall it swallows the map; a user who wants more can still drag the resize handle up to 760px, an informed choice they make for themselves rather than a default forced on every open.
- **⛔ HONEST RESULT AGAINST THE BRIEF'S OWN "≥8 rows" EXPECTATION, NOT SILENTLY UNDER-DELIVERED.** At a realistic 900px-tall window, 8 simultaneously-incomplete rows (every freshly-pasted row starts without a picked Location, so the "needs a date/location" notes panel is essentially always populated for a multi-row paste) show ~4 rows before scrolling — a real, large improvement on the reported 2.4, but short of 8 in that worst case. Reaching 8 unconditionally would mean either re-shrinking the map strip back into the HARDENING-12 regression above, or a content-aware panel height (growing with row count, not just viewport) — a bigger feature, not attempted here. The originally reported case (2 rows, 1191×521) is fully fixed: 0 vertical scroll.
