- **ROOT CAUSE (pinned in `SitePlannerApp.jsx`):** on a **signed-in** deep link/refresh the user's cloud sites aren't in the local store at the first synchronous render (auth + `pullCloud` are async), so `activeSiteId` is momentarily null even though the route names a project. Two boot reactions then destroyed the resume **before** the pull finished: (1) the active-project→URL sync wrote that transient `null` over the route, **stripping `#/project/<id>/site` → `#/`** (→ finder); (2) the "tidy a dangling `currentSite`" cleanup **nulled the pointer** because the cloud site only *looked* absent. (Logged-out / no-Supabase never reproduced it — the local store is synchronous, so there's no gap; which is exactly why the sandbox + every logged-out self-test missed it.)
- **FIX:** a `bootResolved` gate (new pure `src/workspaces/site-planner/lib/bootResume.js`) holds BOTH the URL sync and the dangling-pointer cleanup until the first auth + pull settles (true from the start when there's no Supabase to wait on, so logged-out is byte-identical). The resume target is now one shared, unit-tested `pickResumeTarget` (used by the first-render boot AND the post-pull resume, so they can't drift). The `bootResolved=true` flip is batched with the resume's `setActiveSiteId`, so the URL-sync effect only ever sees the resolved view.
