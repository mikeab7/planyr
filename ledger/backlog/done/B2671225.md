### B2671225 — An organization workbook deleted on one device stays in the list on a second device that already had the list, even after a reload `[Spreadsheet]` (bug) #model #persistence #sync  *(found by AUTH-SWEEP 4, 2026-11-11, driving V1362416 step 5; Recurrence of none — step 5 of B1912208's live check)*
`[ ]` Two browsers, same account, Organization > Spreadsheet. Browser A creates and renames a workbook; browser B opens the list and sees it. A deletes it (the inline two-step); A's list is empty and stays empty on reload, the cloud row is soft-deleted (`deleted_at` set). B then reloads (true page reload, waited 8 s and again 20 s) and also leaves the tab and returns: B still lists the deleted workbook. A brand-new browser (no local copy) lists nothing. So the deletion never reaches a device that already cached the list.
- Root-cause hint: `ModelApp.jsx` list effect (~line 655) merges `cloudRows` with `localOnly = readLocalOrgIndex(userId).filter(w => !cloudIds.has(w.id))` and writes the merge back — a workbook another device deleted is, by that rule, indistinguishable from "created here, not synced yet", so the local cache entry survives forever (TOMBSTONE-DELETES gap on the read side; the cloud list query filters `deleted_at is null`, so it can't tell the difference). Fix shape: have the list also fetch the account's tombstoned org-workbook ids (or keep a per-entry `syncedOnce` flag) and drop local entries whose cloud row is deleted. Also worth checking: opening the zombie row in B may re-insert (resurrect) the workbook — not tested.
