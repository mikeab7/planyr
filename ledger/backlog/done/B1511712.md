**THE MECHANISM, AUDIT-FIRST.** B1012560's Row-2 layout centers the Grid/Split/Gantt chip WITHIN THE LEFTOVER SPACE between the tabs zone and the toolbar zone (`flex:"1 1 auto"`) — correct only when those two zones are equal width, which its own comment already flagged as a deliberate trade-off. They are not equal (tabs run wider than the toolbar cluster by roughly twice the reported offset), so the chip drifted by exactly half that difference — the same species of bug B384064 already fixed once on Row 1's jurisdiction pill.

**THE OWNER'S OWN CORRECTION TO HIS OWN FIRST ASK, and why it rules out the two obvious fixes.** His first message asked to "center the chip"; his follow-up, before any code shipped, added: "it cant always be centered but when it can it should." He's right, for a reason Row 1 never faced — Row 1's centre content (the jurisdiction pill) SHRINKS/abbreviates when squeezed, so an out-of-flow slot with a measured max-width bound is always safe; this chip's content (Grid/Split/Gantt + the review inbox) is FIXED WIDTH, so unconditionally pinning it to the row's midpoint would, below the width where both sides can clear it, run it straight into the tab strip or the toolbar buttons.

**A PLAIN CSS GRID `1fr auto 1fr` WAS TRIED AND MEASURED TO FAIL, per the dispatch's own "prove it, don't assume it" instruction** — two isolated Playwright measurements against a minimal reproduction: unconstrained, the two `1fr` tracks size to their own content's min-content width, reproducing the exact same leftover-space drift (measured 115.6px, same species as the reported bug); adding `min-width:0` to force the tracks to genuinely equal widths DOES land the chip on the true center (0.0px offset) but lets the wider side's real content overflow its now-undersized track by the same 115.6px, landing directly under the chip (`elementFromPoint` at the chip's own left edge resolved to the chip — the tab text renders underneath it, a measured collision, not a theoretical one). Grid alone does not hold up against the collision case.

**THE FIX — the owner's own two-inequality form, reusing Row 1's B384064 math rather than reinventing it.** Centre only when `leftGroupRight + minGap <= rowCentre - chipW/2` AND `rowCentre + chipW/2 <= rightGroupLeft - minGap` both hold — algebraically identical to `centerSlotMaxWidth`'s existing formula (`rowW - 2*(max(leftW,rightW) + minGap)`, proven in the item's own test), because the tighter of the two inequalities is always the one from the WIDER side group. `AppHeader.jsx`'s Row 2 now measures the row, both zones, and the chip's own fixed content width (a `ResizeObserver` on all four) in a layout effect, and:
- **Centres (out of flow, `position:absolute; left:50%; transform:translateX(-50%)`, `maxWidth` bounded)** whenever that measured bound clears the chip's own width.
- **Falls back to the UNTOUCHED, pre-existing B1012560 in-flow layout** (`flex:"1 1 auto"`, centered in the leftover space) whenever it does not — today's already-correct position, never a new invention, and what decides "what gives way" below the threshold: the tabs zone still never shrinks, the toolbar zone still wraps to a second line first, unchanged.
- **HYSTERESIS** (owner's explicit ask, "a condition evaluated continuously during a window drag flips centred/not-centred repeatedly within a few pixels"): entering `centered` needs the bound to clear the chip's width by a real margin (`ROW2_CENTER_HYSTERESIS_PX`, 12px); leaving it needs no margin. Proven live: a 1px-step sweep across the threshold band in both directions flips mode exactly once per direction, with the enter/exit widths measurably different (1228px / 1215px in the harness).
- **SNAP, NOT ANIMATE**: no CSS `transition` rides `left`/`transform`/`flex` on this zone — a source guard asserts it.
- **NEVER OVERLAPS**: the bound structurally cannot let the centred slot reach either side group, in every state.

**A REAL, PRE-EXISTING TEST-HARNESS BUG FOUND AND FIXED ALONG THE WAY**, not scope creep — it made the new tablet-width check unusable until root-caused. `verify-schedule-header-widths.mjs`'s own mutation-check (forces `flexWrap:"nowrap"` on the live DOM to prove the overlap detector has teeth, then "reverts" it) cleared the property with `el.style.flexWrap = ""` — which does not restore it. React only re-applies an inline style property on a render where that property's OWN VALUE changes between renders; `narrow` never flips again for the rest of the script, so React's diff sees `flexWrap:"wrap"` as unchanged from what it already believes is on the DOM and never rewrites it, leaving the row PERMANENTLY UNABLE TO WRAP for the remainder of that page session. This has been in the harness since B1017840 and never mattered before, because every section after the mutation check tested only wide widths where wrapping was never needed — this item's new tablet-width section (820px) was the first to test a width that needs to wrap AFTER the mutation check runs, and it caught the harness lying about a genuine overlap (`split@820` reported "flow, -103.4px" — a two-line-content stuck rendering on one line). Fixed by writing back the actual value (`"wrap"`) instead of clearing it.
