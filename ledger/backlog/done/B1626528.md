`[x]` **REPRODUCED live, before writing any fix, directly against `planyr_production` (Supabase project `lyeqzkuiwngunutlkkmi`) via the Supabase MCP tools, in a rolled-back transaction on a throwaway row — never one of the owner's real plans.** Simulated the two-window scenario the brief asked for at the write-path level (the level that actually matters — two real browser windows against the CURRENT app would only re-exercise the already-working `casUpsert` path; the exploit requires a writer that bypasses it, which is exactly what an old cached bundle or a hand-built request does):
  - Insert a throwaway row, `version=1`, 3 elements.
  - "Window A draws something" — a real, WHERE-guarded CAS save (`WHERE version=1 → SET version=2`): **succeeds**, 4 elements.
  - "Window B is stale and sends the SAME well-behaved CAS shape" (`WHERE version=1`, its own stale belief): **correctly refused, 0 rows matched** — proves the CLIENT-side conditional filter already works when both sides use it.
  - "Window B / an old bundle sends an UNCONDITIONAL update" (no version filter at all, `version=1`): **succeeded, 1 row matched** — version driven backwards 2→1, the 4th element silently erased. **This is the bug**, and it reproduces the exact "44 → 43" shape named in the brief.

**ROOT CAUSE (AUDIT-FIRST).** The client-side half of this is not missing — it was already built and already correct: `db/optimistic_concurrency.sql` (B314) added `version` to `public.sites`/`public.doc_reviews`, and `shared/cloud/optimisticUpsert.js`'s `casUpsert` — used by every current write path to `sites` (`cloudUpsertCore`, `keepaliveCasPush`) — issues a single conditional `UPDATE … WHERE id=… AND version=<expected>`, with reconcile-and-retry-once-then-report on a genuine conflict (B672's own documented "whole-header last-write-wins" design, unchanged and not relitigated here). What was missing is a backstop that does not depend on the WRITER honoring that WHERE clause: PostgREST has no concept of "the client's own conditional filter" — anything that can reach the table with a valid session for its own row can send an update that skips it, and RLS only ever checks ownership, never a version token. That is precisely "a stale tab walked straight past the client guard," the bin-purge precedent the brief names.

**THE FIX — one BEFORE UPDATE trigger, the same shape every other guard in this table's folder already uses.** `db/sites_version_monotonic_guard.sql` adds `sites_enforce_version_monotonic()`: an UPDATE that changes this row's CONTENT (`data`, or the mirrored `site`/`name` columns) must carry a `version` strictly greater than the one already stored, or it is refused outright (the row is left exactly as it was — `RETURN NULL`, which skips the write for that row). Three deliberate design choices, each checked against the real schema before shipping, not assumed:
  - **Scoped to content-changing writes only.** `cloudDelete`/`cloudDeleteGroup`/`cloudRestore` (soft delete/restore, `deleted_at` only), `db/backfill_group_id_column.sql` (`group_id` only) and the team-share/lock flips (`guard_team_share`) all DELIBERATELY do not bump `version` — their own comments say so, specifically so they cannot hand another open tab a false conflict on a field it never touched. A blanket "every UPDATE must advance version" rule would have broken all three; this guard is a no-op for them by construction (checked: a write touching neither `data` nor `site`/`name` is exempt regardless of version).
  - **A no-op for every legitimate content writer, verified rather than assumed.** `rename_site_group()`, `set_site_group_role()` and `reconcile_site_group_name()` — the three RPCs that touch `data`+`site` together — already bump `version = coalesce(s.version,1)+1` in the same statement (read their SQL bodies directly to confirm, not inferred). And for any `casUpsert` call that matches its own `WHERE version=expected` filter, `new.version` is ALWAYS `old.version+1` by construction — the refuse branch is mathematically unreachable for a well-behaved conditional write; it can only fire for a writer that bypasses the filter, which is the entire point.
  - **Rejection composes with the EXISTING client machinery, zero client changes needed.** Returning `NULL` makes PostgREST report zero rows updated — exactly the shape `optimisticUpsert.interpretCas` already treats as a CAS conflict (`rows.length===0 → {ok:false, conflict:true}`), which `cloudUpsertCore` already handles via its B672 refetch-and-retry-once-then-report path. A caller that predates any CAS awareness (a genuinely old cached bundle with no `.select()`) gets no live signal — unavoidable, since that code has already shipped and cannot be retrofitted — but the row itself cannot be clobbered, which is the actual property this item is about. LOUD-FAILURE either way: every refusal `RAISE WARNING`s and logs one `public.client_errors` row (`event:version-guard-refused`), the same pattern `sites_preserve_rename_stamp` already uses.
  - **The trigger's name sorts alphabetically before every other BEFORE UPDATE trigger on `sites`** (`sites_normalize_county`, `sites_preserve_rename_stamp`, `sites_team_share_guard`), so it evaluates `new.data`/`new.site`/`new.version` exactly as the caller proposed them, before any sibling trigger's own narrow self-correction could manufacture a content diff this guard never asked about. Confirmed live: `sites_enforce_version_monotonic` sorts first in `pg_trigger`.
  - Read `db/sites_rename_stamp_guard.sql` first, per the brief's own instruction, to confirm the two guards don't fight: that guard compares a `siteRenamedAt` epoch stamp inside `data`; this one compares the row's `version` column. Disjoint fields, no interaction, confirmed by inspection and by the exempt-path test cases (soft delete/restore still succeed unchanged with this guard live).

**MUTATION-PROVEN, both directions, live against `planyr_production`.** `db/test/sites_version_monotonic_guard.test.sql` (10 cases, self-rolling-back): a known-good arm (case 0), a well-behaved CAS write still succeeding (case 1), the exploit refused (case 2, the exact repro above), the production "44→43" shape refused (case 3), an equal (non-advancing) version refused too — a tie loses (case 4), LOUD-FAILURE telemetry logged exactly once (case 5), a site-column-only stale write refused (case 6), soft delete and restore still succeeding WITHOUT a version bump (cases 7–8, the exempt paths), and a version jump of more than 1 accepted — not just an exact +1 (case 9, matching the file's own stated design).
