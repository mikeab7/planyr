### B800850 — Contour lines: a lattice tile that stays continuously in view appears to be RE-FETCHED from the network on every moveend, not served from `gisCache` `[Site Planner / GIS]` (bug) #site-planner #gis #perf  *(found while diagnosing B800848 — filed with real uncertainty per AUDIT-FIRST, OBSERVED but not yet confirmed. Root-caused and REFUTED this session, while implementing B800849, against `origin/main` d9f09bb.)*
`❌ REFUTED` — not a caching defect. The observed re-fetch pattern was a HARNESS ARTIFACT: `ui-audit/diagnose-contour-pan-perf.mjs` served a fixture sized 463×400 for every `exportImage` request while the app always requests 528×528 for a lattice tile, so `decodeGrid()`'s dimension check correctly rejected EVERY fetch — `gisCache.js`'s internal `refresh()` never reached its `write()` call, nothing was ever cached, and every subsequent moveend genuinely had nothing to serve from cache. That is the CORRECT response to a fetch that keeps failing, not a cache-key or staleness bug.
- Verify: sandbox — root-caused and reproduced/refuted entirely in the sandbox harness, no live network needed (the harness intercepts the request layer itself, so the finding doesn't depend on reaching the real USGS 3DEP service).
- **How this was pinned down, not just argued from reading the source.** Temporary instrumentation in a scratch copy of `gisCache.js`'s `swr()`/`refresh()` (logged to `window.__b800850Log`, never committed) traced exactly what happened on each `moveend` against the ORIGINAL 463×400 fixture: every call was a genuine "COLD L1 miss" → `readAsync` also missed → `fetcher()` called → and the fetcher's promise **REJECTED** every single time with `grid size mismatch: got 463x400, asked 528x528` — never resolved, so `write()` (and therefore caching) never ran, on the cold load AND on three subsequent centerOn() calls including a literal no-op repeat of the exact same position. Once the harness's fixture was corrected to the real 528×528 request size (see B800849), the SAME instrumentation showed the fetcher RESOLVING and `write()` running on the first (cold) load, and **zero** further network fetches (`+0 network fetches this round`) on three subsequent identical `centerOn()` calls at the same position — exactly the behavior `gisCache.swr()`'s own source already promised (a fresh, non-stale L1 hit never calls the fetcher). A separate run of the real multi-step pan harness with the corrected fixture also showed **0 of 15 unique tiles re-fetched** end to end.
- **`isStale`/`swr`/`write` in `gisCache.js` are confirmed correct and are UNCHANGED by this item.** `write()` updates the synchronous in-memory L1 (`touchMem`) before anything async, and a subsequent `read()` for the same key finds it immediately. There was never a cache-key mismatch, a stale-TTL bug, or a torn-down-and-recreated layer instance; the fetch simply never succeeded, on every prior investigation of this symptom including this session's own first pass, before the fixture-size root cause was found.
- **Relationship to B800849:** the SAME fixture-size defect explains both this item's original "re-fetch" observation and part of why B800848's own before/after measurement showed only a small improvement (the layer was never actually painting real geometry in that harness run either). See B800849 for the harness fix (`test/fixtures/dep-katy-528x528.lerc`, `scripts/gen-terrain-pan-fixture.py`) and its own honest before/after numbers, now measured against a harness that actually exercises the code under test.
- **Why it matters, closed rather than left unconfirmed:** a genuine re-fetch bug of this shape would have been a larger contributor to "the contours thing seems to make my computer lag" than either B800848 or B800849 — worth the investigation even though it resolved to "no bug here." Ruling it out cleanly (rather than leaving it filed as `unconfirmed` indefinitely) is itself the deliverable.
