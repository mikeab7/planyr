### B2078593 — A note must open at FULL PAGE WIDTH on every device, every time (reverses "a saved view wins on open") `[Notes]` (bug (×2), amends B2061331 and #1964) #notes #mobile  *(Owner repro on his iPhone, 2026-10-04 — dispatch block "NEW-3")*

`[x]` **Repro (owner):** "Hard Cost Pricing" (Organization scope, last edited ~a day earlier) on his phone opened at 55%, page top about a third of the way down, the right side of the page and its table off the right edge; on his desktop the same page opened framed differently. He wants the same, full-width opening everywhere.
`[x]` **AUDIT-FIRST — which saved view, and from where (answered before fixing).** The per-page view lived ONLY in each device's own `localStorage` (`planyr:notes:view:v1:<scope>:<pageId>`, written by every pan/zoom/pinch 400 ms after the last change, read first on open and winning outright). It never synced (the store's own header says so on purpose). So the phone carried a view from his own earlier pinch/pan on THAT phone — he had just spent the session pinching and panning while testing the touch-pan fix — and the desktop carried a different one, or none: two independent leftovers, each obeyed on its own device, which is exactly "different between devices". Not readable from here (his device's storage): the exact value on his phone — inferred from the symptom (55% zoom, an offset of about a third of the screen), which is what a leftover pinch looks like. The opening re-framing logic was not at fault; it was never reached, because the stored view returned early.
`[x]` **Decision, stated (asked for): a saved view is kept ONLY IN MEMORY, per page, for the life of the tab.** Leaving a page and coming back inside one session returns to where you were; a reload, a new tab, or another device always re-frames to full page width. NOTHING is written to storage any more, and any view an older build stored is deleted the first time one is looked up (`purgeLegacyViews`, once per load — view keys only, nothing else touched), so a stale one can never come back. Adjacent cases checked in the harness: a page with no saved view · a view saved on a phone, opened on desktop · a view saved on a desktop, opened on a phone · the owner's exact shape (55%, offset).
`[x]` **"Full page width" is now true on desktop too:** `openingZoom` was phone-only; a page WIDER than a desktop window (a 1700-wide page on 1280) opened at 100% with its right edge off screen. It is now a pure function of viewport and page on every device — shrinks until both edges are on screen; desktop caps at 100% (a narrow page is not blown up on a big monitor); a phone may magnify a narrow page up to the existing cap.
`[x]` **No late re-framing reintroduced:** the opening framing logic (re-frame until the page size settles, then latch; never while a grip drag is in flight) is untouched; only what it is allowed to read changed.
`[x]` **Tests:** `test/notesViewNotPersisted.test.js` (3: read-back within a session, nothing reaches storage, a legacy view is purged and never returned) · `test/notesViewport.test.js` +1 (desktop, wide pages, both edges on screen; a narrow page is not magnified). Harness `ui-audit/verify-notes-open-framing.mjs` (WebKit + Chromium; 390×844 and 1280×800 among the sizes): the four stored-view cases above each open at full width, right edge on screen, top near the top, the legacy key deleted, not the saved zoom; a wide page on desktop opens with both edges on screen and zoom below 100%. **Red-proofed on untouched main** (the same harness against a clean origin/main build: every stale-view arm and the wide-page arm ⛔). `verify-notes-touch-landing` seeded a view through storage; it now applies a pan/zoom through a new `__PLANYR_E2E`-gated `__noteEditor.setView` hook (all landing arms green).
`[x]` **Regression runs, head vs untouched main (identical failure identities):** **same failures on both** — `-context-menu` 8, `-touch-box-tap` 0, `-touch-pan` 1 (WebKit flick-inertia timing arm, identical on both), `-phone-layout` 0, `-touch-place` 0, `-touch-menus` (new arms are the point), `-width-matrix` 0, `-page-width` 0, `-page-height` 0, `-anchor-zoom` 0, `-mat-scroll-room` 4, `-menu-layout` 11, `-box-selection` 111, `-pan` 6, `-tier1` 3, `-page-growth` 9. **Different identity, each explained:** `-open-page-adopt` — red once in the loaded batch on head, green on re-run alone (and green on main): a timing flake under the batch's CPU load, not a change. `-canvas` — head GREEN, main RED, by design: its two persistence arms ("the zoom level comes back", "keyed per page") asserted exactly the behaviour the owner reversed; they now assert the opposite (a reload re-frames to full width, nothing is stored; known-good arm proves the view really moved first). `-left-margin-reachable` — already red on main (6 ⛔); on head 9 ⛔: that harness opens a page WIDER than the window and measured a ~29 px left gutter at 100%; full-width opening now shrinks it to fit with a ~8 px gutter, so its "usable left margin" arm fails with a different number and its double-click-in-the-margin arms can no longer hit a margin that thin. **Said plainly — a real tension, not a flake:** the earlier left-margin feature (place a box outside the page by double-clicking its left margin) is harder to reach on first open of a page wider than the window; you can still pan to expose the margin. Owner's rule wins (full width, both edges on screen); a roomier desktop gutter is a one-number change if he wants it.
- **Regression runs for the ×2 fix, head vs untouched main (identical failure identities on all 16):** `-width-matrix` · `-page-width` · `-page-height` · `-anchor-zoom` (red-exit both, no ⛔ lines either side) · `-page-growth` 9 · `-left-margin-reachable` 18 · `-box-selection` 111 · `-mat-scroll-room` 3 · `-context-menu` 8 · `-menu-layout` 11 (all pre-existing reds, same on both) · `-canvas` · `-open-framing` · `-touch-landing` · `-touch-box-tap` · `-touch-menus` · `-phone-layout` green on both.
- **Said plainly — a consequence he accepted by asking:** a reload no longer returns you to where you panned/zoomed on a page; it re-frames. A page deliberately left zoomed in is full width again on the next open.
- **Recurrence (×2), 2026-10-04 — the owner's iPhone, build after #1973: the opening was full width, but the CONTENT rendered at 41% of the page and the table was cut off.** Re-opened here, not a new B# (DEDUPE-FIRST). **Why #1973 missed it, said plainly:** its harness measured the page's EDGES and TOP only, never what was INSIDE the page, and it was reported verified from emulation; he found it on his phone.
`[x]` **Root cause (measured by rebuilding his exact document as a fixture — page 1012, one box x 0 / w 873, a list and a two-column table):** `fitAnchorBox({ hostWidth: paneWidth })` in the layout effect clamped the RENDERED box width to the SCREEN pane's own unscaled width (`note-mat`, 390 on a phone) — a number unrelated to the page the view transform then scales to 37%. Stored 873 rendered as 386 (38–41% of the page instead of 86%), the table's 677-wide body was clipped by the box edge ("…$240 annua"), and it is the same defect on a NARROW DESKTOP window (900 wide: 628) — his desktop only looked right because its pane happened to be wider than the box. The clamp dates from B421490 (scroller era: a box off the end of the sheet landed under the Outline panel); on the unbounded, pannable canvas the stored width is the person's intent.
`[x]` **Fix:** the render fit no longer receives a host width (`fitAnchorBox({ x, w })` → the stored width, minimum floor only). Nothing else changed in layout.
`[x]` **Acceptance, with the screenshots looked at by me, not just asserted:** `ui-audit/verify-notes-box-width-parity.mjs` loads his exact fixture plus a two-side-by-side-boxes page, a box with x > 0, a page pinned below the phone's width and an unpinned default page, in FIVE contexts (WebKit phone 390×844 dpr 3 hasTouch+isMobile · WebKit desktop · Chromium desktop 1280×800 · Chromium phone · Chromium narrow desktop 900×700). Per case × context: rendered box width ÷ zoom == stored w (±1%); box share of the page == stored w ÷ pageWidth (±1%, his fixture); every table inside its box and the page, no cell text clipped; per-paragraph LINE COUNTS identical phone vs desktop within each engine. **86 ✓ on this build; on untouched main 23 ⛔** — with his own numbers (386 vs 873, 38% vs 86%, the table outside its box); the Chromium-1280 context passes on main too (the known-good arm: the fixture is real and the instrument can see a correct page).
