### B966627 — Setback ring/chip silently defaults to the project setback — "not set" and "set to 25" render identically; a real offset-geometry defect confirmed on the way `[Site Planner / Parcels · setbacks]` (bug) #site-planner #parcel #ui #geometry  *(same dispatch, NEW-4. Minted **B966627**. DEDUPE-FIRST — searched `parcelSetbacks`, `setbackChipStyle`, `offsetPolygon`: the fallback this item fixes was noted in its own comment as "for any parcel that predates per-edge" but nothing asserted it stayed visually distinct. Net-new.)*
`[x]` **Confirmed the silent default from source, not the symptom.** `parcelSetbacks(pc)` — the ONE function feeding both the on-canvas dashed ring and the numeric chips — silently substitutes the site's `settings.setback` default whenever `pc.setbacks` is null, which is exactly what a split child inherits when its parent had none (`remapEdgeVector` returns `null` on a null input). Bain's `2A1A1B` has `setbacks: null` in `site_elements`, yet the map drew 25′ dashes and five 25′ chips — a real LOUD-FAILURE violation: no setback set and setback set to 25 rendered byte-identically.
`[x]` **Fixed without changing what value is used** (the default is still the right number to SHOW) **— only how it's marked.** Added `parcelSetbacksExplicit(pc)`, the one place that answers "did this parcel ever have its own setbacks written." The dashed ring now draws with a sparser dash + reduced opacity (the same idiom this app already uses for "not yet confirmed," e.g. the uncalibrated-measurement amber) when defaulted, carrying `data-setback-explicit="0"`; the numeric chip gets a leading **"~"** ("~25′") plus a hover title explaining it's the project default — one glyph, no added panel prose (PANEL-BREVITY N/A here — canvas chrome, not panel copy, budget-checked clean regardless).
`[x]` **A SECOND, independent geometry defect was found and fixed while verifying the "dashes read outside the boundary" half of the report, by measurement, not by trusting the screenshot.** Ran `offsetPolygon` (the shared setback-inset function, `lib/parcelOffset.js`) against `2A1A1B`'s real points at 25′: **2 of its 12 result vertices land measurably OUTSIDE the source ring** (the miter/bevel construction can push a corner past the boundary when the offset is large relative to a short edge — here, a 4.7 ft edge, a remnant of a multi-segment cut, against a 25 ft setback). **CONFIRMS, does not refute, the owner's screenshot claim.** Fixed by clamping: any result vertex found outside the source ring is projected to the nearest point on the source boundary — the true inset there sits between the miter point and the boundary, and the boundary itself is never a wrong place to draw at. An inward offset must never step outward; now it structurally can't.
