### B839840 — Bin shows "permanently deleted" for a page that was simply never written `[Notes]` (bug) #notes #ui #persistence  *(owner chat block 2026-08-28, verbatim: "I created an empty page and binned it. Its bin card read 'Its writing was permanently deleted and cannot be brought back'. An older empty page in the same bin reads 'Empty — nothing was ever written in it'. The scary copy should only appear when writing actually existed and was purged." Same session as B831600(×2)/B831602(×2). Minted **B839840** from this branch's reserved block B839840–B839855 against `origin/main` a5636140. DEDUPE-FIRST — searched Open/⏳Verify/Done for `permanently deleted`, `collectBinFacts`, `gone:`, `everTouched`: B350002/B357011/B357012 built `collectBinFacts` and its `gone` flag but never distinguished "never written" from "destroyed" — this is a genuine gap in that flag's own definition, not a duplicate of any of the three.)*
`[x]` **✅ DONE — the discriminator moved from the body (which cannot tell the two states apart) to the tree's own timestamps (which can), proven red on the pre-fix code and green after, both headlessly (the pure function) and in the real UI (a live click-through into the Bin view).**
- Verify: sandbox — reproduces headlessly with real localStorage + a real Bin-view render; no auth/live-GIS/real-project-data dependency.
- **ROOT CAUSE.** `collectBinFacts` (`lib/notesStore.js`) set `gone: text.length === 0 && !anyStored && pageIds.length > 0` — "empty, and no body found on this device for any page in the cascade." `anyStored` is `true` only when `readPage()` finds a stored body, and `readPage` explicitly returns `null` for "a page that has never been written" (its own doc comment) — which is EXACTLY the state of a page created and binned before its first autosave debounce ever ran. So `!anyStored` was true for two unrelated situations that happen to look identical from the body alone: a page whose content was genuinely destroyed (the original B357011-era motivation — a real server-side purge, or `deletePages` clearing a body it once had), and a page that never had anything to lose in the first place. The bin showed the first sentence for both.
- **THE FIX.** `updatedAt` on a tree node moves off `createdAt` ONLY through `touchPage`, and (per `Notes.jsx`'s `handleSaved`, which the real editor calls only after `writePage` actually lands a save — never on a keystroke) that is the tree's own honest record of "a write really happened here at some point." `collectBinFacts` now also tracks `touched` per id during its existing tree walk and requires `everTouched` (at least one page in the cascade shows `updatedAt !== createdAt`) before `gone` can be true. Without that proof, an empty/bodyless page reads as "Empty — nothing was ever written in it", never as destroyed.
- **VERIFIED, both the pure function and the real UI, proven red on the old code first.** `test/notesBinFacts.test.js`: a never-touched page (created via `addPage`, no `writePage` call at all) now reads `empty:true, gone:false` — reverting the fix to `!anyStored` alone flips this to `gone:true`, confirmed by stashing the fix and re-running (1 failure, exact assertion); a page that WAS touched (`writePage` + `touchPage`, matching what a real save does) and then lost its body (`deletePages`) still correctly reads `gone:true`. `ui-audit/verify-notes-bin-never-written.mjs` drives the real Bin view with three seeded rows — a never-written page, an older page with a stored-but-empty body, and a genuinely touched-then-purged page — and confirms the exact on-screen copy: the first two both read "Empty — nothing was ever written in it", the third still reads "Its writing was permanently deleted and cannot be brought back".
- **An existing test's own fixture needed the same correction.** `test/notesAnchorPrune.test.js`'s "a container whose only child is PURGED" case built its "purged" simulation the same way `collectBinFacts` used to judge it — a page with no body and no `touchPage` call — which is indistinguishable from "never written" under the corrected rule. Updated to call `touchPage` on the child first, so the fixture actually simulates a write that landed and was then lost, matching what the test's own name claims.
