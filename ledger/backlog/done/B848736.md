`[x]` **SHIPPED THIS SESSION — the full data-model collapse, not just the chrome.** A map-captured aerial is now a bottom-pinned `sheetOverlays` record (`fromMap:true`) inside the ONE References row list — there is exactly one dropzone and one list, and nothing announces an aerial when a plan has none.
  1. **Bottom-pinning** (`lib/overlayOrder.js`): `isPinnedMapReference` (`fromMap===true`) always sorts to the front of the `below` band regardless of array position, and is identity-stable when already correctly ordered (no undo-history churn). `overlayOrderFlags` reports a pinned row as permanently `atFront`/`atBack`; the panel's existing Bring-to-front/Send-to-back buttons render for it same as any row (never a special-cased row shape) and simply grey out, matching how "already at the end of its band" already reads for any other row.
  2. **Georeferencing preserved exactly.** `fromMap:true` rows keep the old aerial's own affordances: Calibrate renders as a single disabled chip with the exact required explanation ("This aerial came from the map — it's already to scale, so manual calibration is disabled") instead of the ordinary Trace-a-length/Align-to-map pair; Rotate, Width and "Draw above the plan" are hidden (resizing/rotating/promoting would fight true-to-scale placement); whole-plan rotation (`sitePlacementRotate.js`) and Print-overlay (`overlayPrint.js`) both exclude the pinned row the same way. `exportSheet.js` needed **zero internal changes** — `exportCtx()` hands it `underlay: mapRef` (the one deliberate back-compat shim), so `fromMap` placements keep exporting through the existing dedicated aerial compositing path.
  3. **A real gap found and closed along the way: non-uniform image scale.** The map-capture step's Web Mercator projection produces a slightly different `ftPerPx`/`ftPerPxY`; only the OLD dedicated `underlay` render path ever supported that — `overlayAlign.js` (`scaleY`, `centerOf`/`imagePointToWorld`/`tlFromCenter`) and the panel's render/chrome/resize code were all ported to be `ftPerPxY`-aware so a folded aerial doesn't warp.
  4. **Live-basemap stand-down (B688864) ported unchanged.** `lib/aerialVisibility.js`'s `isAerialVisible`/`withAerialVisible`/`wantBasemapSrc` are untouched; the render just asks `if (o.fromMap && (!showAerial || (origin && basemapOn))) return null;` instead of gating a separate `underlay` variable. `showAerial`/`settings.aerialHidden` stays a PLAN-LEVEL toggle (works even with no aerial row, since a georeferenced plan's live tiles alone can stand in for "the aerial") — deliberately NOT folded into the row's own per-object `visible` field.
  5. **Migration is lossless, in-memory-only, write-back on next ordinary save — never a mass rewrite.** `siteModel.js`'s `foldAerialIntoOverlays` runs inside `createSiteModel` (the one canonical funnel every load/save/merge path already goes through) and gives the folded record a FIXED id (`legacy-aerial`, not random) so `mergeSiteContent`'s cross-copy union treats two independent folds of the same legacy `underlay` as one record, not a duplicate. Verified live: a plan saved BEFORE this change (raw `underlay`, empty `sheetOverlays`) renders correctly at first load — then, once one ordinary edit triggers the existing debounced autosave, the re-saved record carries no `underlay` field and `sheetOverlays` holds exactly the one folded row.
