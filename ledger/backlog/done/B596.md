### B596 — Merging parcels raised a false "someone else has this open" conflict (merge dropped ≥2 items with no tombstone) `[Site Planner / Persistence]` (bug)  *(owner-reported 2026-06-30 on planyr.io — "when I tried to merge parcels it gave me a note that someone else had that tab open… no one did; it only happens when I merge, not when I add"; minted **B596** = highest real B# across both files (B595) + 1; SAME data-loss/tombstone family as B459/B556/B594/B595; branch `claude/parcel-merge-notification-bug-c7kgoo`)*
`[x]` **DONE + headless-verified the SAME session per STANDING RULE #1. lint 0 errors · 2105 unit tests green (+3 in `test/cloudThinGuard.test.js`) · build green · lazy split intact · `ui-audit/verify-b596-merge-tombstone.mjs` 6/6 (real Chromium, logged-out) + existing `verify-merge-banner.mjs` 6/6 (merge flow intact).** Merging parcels combined them into one but recorded **no tombstone** for the consumed parcels — so collapsing 3+ parcels (a net drop of ≥2 items) tripped the **thin-clobber guard (B459)**, which misread a legitimate active-tab merge as a stale-tab clobber and blocked the cloud save with a FALSE **"This project was changed in another session — Take over editing"** banner. Adding parcels GROWS the count, so it never tripped — exactly matching the owner's "only when I merge, not when I add."
- Part of: **B648** (Persistence & Sync epic).
- **Root cause (`SitePlanner.jsx` `mergeParcels`):** the merge did `setParcels(arr.filter(out the selected) + [newMergedParcel])` with no `tombstone(...)` call. `contentCount` counts parcels, so N→1 dropped the count by N-1; for N≥3 that's ≥2 unexplained losses, and `wouldThinClobber` blocks a ≥2 drop with no NEW `deletedIds` to explain it. (A 2-parcel merge drops only 1, under the threshold — which is why it sometimes "worked".) This is the **same class** as B556's "phantom conflict": a deliberate active-tab shrink with no tombstone read as a stale clobber.
- **Fix:** the merged-away parcels are genuinely removed (replaced by the new parcel), so **tombstone them** — the same invariant every other delete honors (B276/B556). This (1) explains the drop to the guard so no false conflict fires, AND (2) prevents the old parcels being **resurrected** by a reload / cross-tab / cross-device `mergeSiteContent` union (the latent second bug the missing tombstone left). Chose tombstoning over `noteLocalContent` (the B556 undo/redo remedy) precisely because a merge is a real deletion, not a reversible-by-re-add shrink — so the stronger anti-resurrection guarantee is correct here. `pushHistory()` already snapshots the pre-merge `deletedIds`, so **undo cleanly drops the tombstones and restores the parcels**; the new parcel's fresh `uid()` can never collide with a tombstoned id (B594 salting).
- **Tests:** 3 new `test/cloudThinGuard.test.js` cases prove the data-layer math (3→1 with no tombstone = wrongly BLOCKED; with the 3 ids tombstoned = ALLOWED; a 2-parcel merge fine either way). Headless `ui-audit/verify-b596-merge-tombstone.mjs` drives the real UI: seed 3 adjacent parcels → shift-select → **Merge parcels** → the persisted model holds 1 parcel with all 3 old ids in `deletedIds`.
