- **Fix — a new, manually-triggered workflow that lets CI author its own baselines.** `.github/workflows/authorize-visual-baselines.yml`, `workflow_dispatch`-only (a `reason` input, required, mirrors the existing `--reason=` requirement; optional `surface`/`viewport` inputs mirror the script's own dev-convenience flags). It runs the *identical* setup `build.yml`/`ci-gates.yml` already use to judge the gate — same `ubuntu-latest` runner image, same `npx playwright install --with-deps chromium` resolution (reads the exact revision from `package-lock.json`, never a locally-convenient substitute), same real `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` repo secrets at build time — then runs `node ui-audit/visual-regression.mjs --approve --reason="…"` against ITS OWN render and commits the resulting PNGs + `manifest.json` + regenerated `docs/VISUAL-REGRESSION.md` straight back to the SAME branch that triggered it, using the workflow's own `GITHUB_TOKEN` (`permissions: contents: write`). The commit is ordinary, reviewable branch history — a human still sees exactly which pixels changed in the PR diff, same as any hand-approved baseline; the only thing that changed is WHO rendered the picture the gate compares against.
- **No gate logic touched.** `ui-audit/visual-regression.mjs` (the whole file — `--check` path, the 0.02% tolerance usage, `evaluateDiff` calls, the phone-viewport structural gate, `PHONE_PIXEL_DIFF_ADVISORY_ONLY`) is byte-identical to `origin/main` at the point this shipped — confirmed via `git diff origin/main -- ui-audit/visual-regression.mjs` returning empty before the triage addition below, which itself only adds a new exported `buildTriageMarkdown` function and a `diffMagnitude` field pushed alongside existing `--approve` results — `TOLERANCE`, `evaluateDiff`, and the `--check` pass/fail path are untouched by that addition too. `ui-audit/lib/visualBaseline.mjs` gets a static "Authoring baselines from CI" documentation section inside `buildStatusMarkdown()` (pure text, regenerated into `docs/VISUAL-REGRESSION.md`) — `SURFACES`, `VIEWPORTS`, `THEMES` and every other exported gating value are untouched. This item adds an authoring path and documents it; it does not loosen, skip, or bypass anything the gate already checks.
- **Guardrails against the gate becoming a rubber stamp:** (a) `workflow_dispatch` only — no `push`/`pull_request`/`schedule` trigger exists anywhere in the file, so baselines are never regenerated as a side effect of an ordinary push; (b) a first step hard-fails (`exit 1`) if dispatched against `refs/heads/main`, so a baseline can only ever be authored on a branch that still has to pass review + the gate itself before merging; (c) `--reason` is mandatory, exactly like the existing local `--approve` path, so every CI-authored baseline still carries a stated reason in the manifest and in `docs/VISUAL-REGRESSION.md`; (d) workflow-dispatch inputs are passed through `env:`, never interpolated directly into the `run:` shell block, closing the standard GitHub Actions script-injection vector for untrusted input.
- **⛔ TRIAGE PRESERVED, not replaced (mid-session owner addition, closing a real gap the original brief had — a CI-authored baseline path can quietly become bulk approval, which is exactly what defeated per-baseline review on a real incident the addition cited).** Every run now posts a PR comment (falls back to the run's own job summary if no PR is open yet) listing **every** surface/theme/viewport it touched — changed AND unchanged alike, never a filtered list — each with a real diff magnitude against the prior committed baseline (`buildTriageMarkdown`, `ui-audit/visual-regression.mjs`). A baseline that changed on a surface the PR's own diff never touches is therefore visible to the reviewer before merging, not buried in a job log that expires. **What this does NOT do, stated plainly rather than overclaimed:** it does not gate regeneration behind a separate human-confirms-then-a-second-run step — one dispatch renders, commits, AND posts the triage in a single job, because splitting authorship and commit into two separate workflow runs would need to persist rendered PNGs across runs with no simple built-in mechanism, and would not by itself stop a reviewer from merging before reading the comment either way. The judgment call is preserved by making the full, honest list impossible to miss on the PR — not by adding a second gate a reviewer could also click through unread.
