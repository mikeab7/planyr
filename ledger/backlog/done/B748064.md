- **BOTH HYPOTHESES TESTED AGAINST MEASUREMENT, NOT GUESSED.** Read `planyr_production.planar_data` (key `hs-v1`, Supabase MCP, SELECT only — no write, no auth, nothing touched) and `planyr_production.sites`: Woods Road's group_id is `smsrpaiqu5sv`, confirmed to have no schedule linked to it; of his six schedule projects, Goose Creek/Grand Port/8 South/Pappadoupolos each carry a `linkedSiteId`, Operations and Pursuits carry none — exactly the order and the split his screenshot shows. This **refutes** the "the whole switcher is dead because no iframe is mounted" hypothesis (the iframe stays mounted, just visually hidden — `visibility:hidden`, never unmounted) and **confirms** the "cross-cutting unlinked schedule" hypothesis: only the two unlinked targets are inert; the four linked ones already worked.
- **ROOT CAUSE.** `Scheduler.jsx`'s `currentProject`/`showEmptyState` are derived PURELY from the routed site's own link (`findBySiteId(projects, projectId)`). `selectSchedule()` DOES post `planar:nav-select` to the embedded scheduler and the embed DOES switch its own active project internally — confirmed by reading `public/sequence/index.html`'s message handler (`setData(d => ({...d, section:"projects", aPid:m.id}))`, unconditional on link status) and by instrumenting the real bridge in a headless run (the `nav-select:<id>` command is posted and received every time, linked or not). The pick genuinely lands. But for an UNLINKED target, picking it never calls `onProjectChange()` (there is no site to route to), so the outer route never moves, so the route-derived empty state keeps covering the iframe that just switched underneath it — the switch is real but invisible. A linked target only ever worked because its pick ALSO moves the route, which is what makes the route-derived state resolve to the newly routed project. **No console error, no dropped postMessage, nothing to see on the wire** — confirmed by attaching a console/pageerror listener across the exact click: nothing is logged in either the broken or fixed case, matching the brief's own caution that "a message posted into the void looks identical to a handler that no-ops."
- **THE FIX — `isPickShowing(pickId, activeId, section)`, a new pure helper in `navState.js`.** Scheduler.jsx now tracks the id of the switcher's last explicit pick (`explicitPickRef`); `isPickShowing` answers true once the embed's own reported `activeId` catches up to that pick, on its projects section. When true, it overrides both `currentProject` (shows the picked schedule, e.g. "Operations", instead of the stale routed project's name) and `showEmptyState` (false — there IS something to show now), so the iframe becomes visible with the picked schedule active. Self-clearing by construction: once `activeId` moves on to anything else — a later pick, or the carry-in effect reasserting the routed project's own schedule after a genuine navigation — the comparison stops matching and the override lapses on its own; no separate reset needed beyond clearing it on a Dashboard press (an explicit "I'm leaving the projects section" signal).
- **PRODUCT DECISION, named rather than silently picked (the brief's own "not obvious" flag):** the OUTER route (Site/Review/Library/Notes tabs) is left pointed at whatever project was routed before the cross-cutting pick — picking Operations from Woods Road leaves Site/Review/Library/Notes still showing Woods Road, only the Schedule tab shows Operations. This matches the existing `carriedRef` design already in this file (a deliberate pick of a cross-cutting schedule from an ALREADY-linked project is explicitly never "yanked back" by the carry-in — same intent, extended to the schedule-less case). The alternative — clearing the route entirely so the other tabs go to "no project" too — was considered and rejected: Operations/Pursuits have no site of their own to route to, so clearing would lose the routed project's context for a schedule that was only meant to be glanced at. Flagged here in case Michael wants the other behavior instead.
