- **B844416 (the first recorded defect in this instrument) IS ALREADY SHIPPED — checked directly rather than assumed, per the owner's explicit instruction not to state this either way without checking.** It is in `docs/archive/BACKLOG-DONE.md` already (dated 2026-08-29) and its fix is live in `perfCapture.js`'s `attributionLabel()`: when `sourceFunctionName` is empty (true of every anonymous callback), the label now falls back to `invoker:sourceURL-basename:charPosition` instead of stopping at the bare invoker category. Confirmed present in the current source, not re-fixed here.
- **THE DEFECT THIS ITEM FIXES, distinct from B844416: the SHEDDING ORDER, not the per-task label.** `encodeCapture()` (`perfCapture.js`) used to shed, in order: oldest counters → smallest long tasks (floor 4) → frames down the `FRAME_FLOORS` ladder (floor 8) → and if STILL over budget, wipe `tasks` and `counters` to `[]` ENTIRELY and re-shed frames. A frame TRACK is mostly redundant once the summary stats exist (`frames`/`p50Ms`/`p95Ms`/`p99Ms`/`maxMs`/`jankFrames` already ride the numeric columns); a long-task ROW is the only place a script gets a NAME, not recoverable from anything else in the payload. So the worse an episode, the more likely it needed the deep shed, and the more likely it lost 100% of its attribution to keep 8 frame samples — exactly the real capture's shape.
- **THE FIX — the priority is reversed, and a hidden second cause of the same collapse is fixed alongside it.** Counters still shed first (a scene snapshot is the least time-critical fact in the row). Frames now shed via the SAME ladder, then all the way to ZERO, before the long-task table loses a single entry below its own floor of 4; only past that does the task table give up its smallest entries, one at a time, down to zero as the true last resort before the pre-existing bare-row fallback. **Separately found and fixed while building the reproducing fixture:** `ltNames` shipped the WHOLE session-wide interned string table (up to `STRING_TABLE_MAX`=64 entries, `perfRing.js`) on every capture, not just the names the KEPT tasks reference — so a session that accumulated many distinct long attribution strings over its life could blow the byte budget on the names array alone, independent of how many task rows survived, which no amount of the reordering above could fix by itself. Every encode now re-indexes to a compact per-row table holding only the names the surviving tasks actually use. Two new accounting fields, `tasksDropped`/`countersDropped` (added to `CAPTURE_NUMERIC_KEYS`), name what the OTHER series lost, mirroring the existing `framesKept`/`framesDropped` — before this, `encodeCapture` computed those counts internally but never surfaced them anywhere.
- **PROVEN RED THEN GREEN, on a fixture that reproduces the real collapse.** `test/perfRecorder.test.js`'s new "a severe episode… keeps long-task attribution" test builds a capture shaped like the real one (24 long tasks each with a distinct, near-cap-length attribution name; a jankful 4,096-frame track) and runs it through BOTH the shipped `encodeCapture` and `legacyEncodeCapture` — a verbatim copy of the pre-fix shedding order, kept in the test file as the mutation baseline rather than trusted from a description. The legacy order reproduces the real defect exactly (`lt`/`ltNames` both `undefined`); the shipped order keeps 16 attributed tasks in the same byte budget. A second new test proves the `ltNames` re-indexing directly (3 tasks referencing 2 of 64 possible names → exactly those 2 names ship, not 64). One PRE-EXISTING test (`capturePipe.test.js`, B265541's own "the shed steps DOWN past 60 rather than falling off it") asserted the OLD priority's invariant (frames never below 8) and is updated to assert the new one (frames may reach zero; the long-task table survives the same squeeze) — its title and body say so explicitly rather than silently changing the assertion.
