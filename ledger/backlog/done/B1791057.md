`[x]` **Answered empirically, not by reading the SQL alone — RLS ownership refuses the write independently of the version/CAS token. This is NOT a security finding.** Read the live policies directly off production (`pg_policies`, project `lyeqzkuiwngunutlkkmi`): the `update own or team sites` policy's `USING` clause is `user_id = auth.uid() OR (team_id is not null AND is_team_member(team_id) AND not share_locked)` — it names nothing about `version` at all. Proved it with a real write attempt, not just a read of the policy text: a self-rolling-back live test against production (`src/workspaces/site-planner/db/test/sites_cas_ownership_independent.test.sql`, run via the Supabase MCP, 4/4 PASS, then rolled back) has a non-owner send the EXACT client-shape CAS update — the correct current `version`, the identical `WHERE id=… AND version=…` shape `casUpsert` itself sends — against another account's row: **0 rows updated**, row provably untouched. A second check with NO version predicate at all also gets 0 rows, confirming ownership is what fires, not a coincidental version mismatch. A control (the real owner, same version, same shape) succeeds in the same transaction, proving the harness can see a positive result (WRONG-CASE) rather than failing for an unrelated reason. **Conclusion: the `sites_enforce_version_monotonic` trigger and the client's own `.eq("version", expected)` filter are a genuine, useful CAS guard against a stale write from the SAME account — but they are not what stands between one account and another's row. RLS ownership does that, independently, and it holds.**
