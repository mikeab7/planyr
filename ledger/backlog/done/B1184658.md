`[x]` **IMPLEMENTED AND UNIT-TESTED THIS SESSION.** `resolveOrCreateTrackedSiteForComp` (`storage.js`) used to swallow a failed background `pushSiteToCloud` and hand back `{ groupId: id, created: true }` regardless — a project_id the database can never actually resolve, since `comps_project_id_fkey` is NOT DEFERRABLE. Decided per the report's own "either/or, say why": **treat a failed push as no attachment** (the comp saves unattached, fixable via the now-working Site dropdown — B1167137's fix), rather than blocking the save on the push succeeding first — a worse UX for an intermittent network hiccup, and inconsistent with this whole mechanism's "the owner should never have to wait on a site before recording a deal" design.
- Verify: sandbox — pure logic, fully covered by a mocked cloud-push failure; no live-verify class applies (not timing/race, not concurrency, not GIS, not zoom-density, not PDF/export, and the fix is generic rather than real-project-data-dependent).
- Origin: filed 2026-09-05 from chat (adversarial review)
- **The fix.** On a push failure, `resolveOrCreateTrackedSiteForComp` now returns `{ groupId: null, created: false, matched: false, error: "…" }` instead of a phantom id. The LOCAL tracked-site row is left in place either way (it still mirrors on the next edit/reload/autosave, same as any other site write) — only the comp's LINK to it is withheld until it's provably real. **No FK error can reach the UI**, because `comp.projectId` is simply never set when `groupId` comes back null — both of `CompsPanel.jsx`'s existing save paths (`save()` for the single-comp form, `saveGridRows()` for the paste grid) already tolerated a falsy `groupId` correctly; the bug was entirely that the function LIED about success, not in how the callers used the result.
- **Surfaced in plain words, not left silent.** The single-comp form's existing `assignNotice` slot now also carries the failure message when resolution fails (reusing the same UI the "attached to X" success notice already uses). The paste-grid path counts unattached rows across the whole batch and shows one informational line ("Saved — N row(s) couldn't be linked to a site (offline?)…") — the save itself always succeeds now; nothing is held back by one row's site.
- **VERIFIED BY SIMULATING THE FAILURE, not by reading code, per the report's own instruction.** `test/resolveOrCreateTrackedSiteForComp.signedIn.test.js` (new, mocks `cloudSync.js` directly, both the signed-out `storage.test.js` suite AND this new signed-in one exercised): a scripted `cloudUpsert` failure produces `groupId: null` + a real error string, while the local tracked-site row is confirmed still present (`loadSitesList()`); a scripted success still returns normally. The rolled-back live FK probe (`23503`, `comps_project_id_fkey`, zero rows left behind — `ZZ-FK-PROBE` confirmed absent afterward) grounded the mechanism before writing the fix.
