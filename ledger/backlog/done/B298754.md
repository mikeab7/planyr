- **⛔ RESTORING CREATES A NEW VERSION. IT NEVER DESTROYS HISTORY.** The state being left is snapshotted and PINNED first, so restoring the wrong version is itself undoable by restoring the one taken a second earlier. The rule is a pure function (`planRestore`) whose unit test asserts the plan contains **no delete of any kind** — the property, stated, rather than a comment claiming it.
- **⛔ AND IT GOES THROUGH THE OPEN EDITOR, NOT ROUND THE BACK OF IT.** Writing the restored JSON straight to storage while an editor holds the old document is a silent-loss bug by construction: the editor's own unmount flush writes its stale copy back over the restore a moment later. Handed to the editor it is one ordinary transaction — undoable, saved by the one save path, visible immediately.
- **RETENTION IS DENSER RECENT, COARSER AS IT AGES** — everything inside the last hour, hourly for a day, daily for a month — and **the newest row is pinned unconditionally**, because a history whose current row can be swept is a history that can be empty at the exact moment you need it. Pure, so every tier boundary is a test.
- **⛔ SNAPSHOTS LIVE IN INDEXEDDB, NEVER LOCALSTORAGE (TIER-BY-REBUILDABILITY).** The small tier was measured at ~78% of a hard ~5 MB cap on the owner's own browser with real saved plans in it; a note's typing history is bulky and bursty and would crowd irreplaceable work out of exactly the store that must never fill.
