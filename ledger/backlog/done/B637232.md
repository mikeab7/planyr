`[x]` **✅ DONE — shipped and headless-verified this session (44/44 checks in `ui-audit/verify-schedule-indent-outdent-delete.mjs`, incl. 3 mutation proofs).** `public/sequence/index.html`'s keyboard handler called `indentTaskById(selectedId)`/`outdentTaskById(selectedId)`, and the right-click menu called the same by-id helpers with `taskCtx.task.id` — both read a SINGLE task id and never looked at `selRange`. **Measured live before the fix** (throwaway repro against a fixture mirroring the owner's screenshot — "ALTA & Topo Survey" → "PI" → 6 children): drag-selecting rows 11–16 via the ID column, then pressing Alt+Shift+Right, moved only whichever row `selectedId` happened to be (the drag/shift-click ANCHOR — the LAST row entered during a top-to-bottom ID-column drag, or the FIRST-clicked row if the selection was made with shift-click/shift-arrow, since that branch deliberately never updates `selectedId`). Right-clicking ANY row inside the same 6-row selection and choosing "Indent →" from the context menu moved only THAT row, ignoring the other five.
- **THE FIX, one shared resolution rule for both entry points.** `rowRangeSelIds()` (new) returns every task id in the current row selection regardless of which COLUMNS it spans — unlike the pre-existing `fullRowSelIds()`, which requires a full-column span because IT exists to disambiguate "delete rows" from "clear cell content"; indent/outdent has no such ambiguity, so it never needed that restriction. `structuralTargets(anchorId)` resolves "the row range if the anchor is inside one, else just the anchor" — one function, used identically by the keyboard handler (anchor = `selectedId`) and the context menu (anchor = `taskCtx.task.id`), so the two entry points can never again diverge into "acts on the selection" vs. "acts on one row." Both call into new `indentSelectionByIds`/`outdentSelectionByIds`, which replace `indentTaskById`/`outdentTaskById` entirely (renamed, not wrapped) and dispatch to pure, unit-tested `indentSelection`/`outdentSelection` (mirrored in `ui-audit/stress/schedule-tree-ops.mjs` for `test/scheduleIndentOutdentDelete.test.js`, which also source-pins both call sites so a revert to a bare `selectedId`/`taskCtx.task.id` call fails CI).
- **SEMANTICS DECIDED, not left emergent (Smartsheet-style):**
  - **A contiguous block moves as ONE unit.** Only "root" rows — selected rows whose PARENT is not itself selected — get reparented; a selected row whose parent IS also selected is left untouched, so a parent-plus-its-own-children selection preserves relative depth for free (the child's `parentId` is never touched at all).
  - **INDENT is all-or-nothing, gated on the TOPMOST selected row.** Every root row moves to the SAME new parent (the row immediately above the topmost row, at the topmost row's own level — the pre-existing single-row eligibility rule, unchanged). If the topmost row has no eligible predecessor (e.g. it's the first child of its parent), the WHOLE block is a clean no-op — there is no sane partial result when every root row shares one destination. Verified live: selecting a parent's entire 6-child block (whose topmost is the parent's very first child) and indenting moves nothing.
  - **OUTDENT has no shared destination, so it is per-row: rows already at depth 0 are skipped individually, everything else that can outdent does, independently.** Adjacent root rows sharing the same current parent are promoted as ONE batch, not one row at a time — moving them individually re-derives "the end of the old parent's remaining subtree" against a shrinking array and reverses their relative order (measured while designing this: row A moved first landed AFTER row B, which moved second, exactly backwards). Verified live for a genuinely mixed selection (one depth-0 row + one deeper root row in the same contiguous range): the deeper one promotes, the depth-0 one is left exactly where it is, neither blocks the other.
  - **Non-contiguous selection (rows 11, 14, 16 with gaps) cannot occur and needed no design decision** — the app's entire selection model (`selRange`) is a single rectangle of rows × columns; there is no ctrl-click or other discontiguous multi-select anywhere in this codebase.
- **B463072-shaped landmine, MEASURED live, not assumed — and it does NOT reproduce here.** A leaf with a typed duration (`durValue`/`durUnit`) that becomes a parent for the first time correctly shows its ROLLED span in the duration cell (B463072 already fixed this display path — `fmtTaskDuration` reads `isSummary`). Reversed the same operation (outdented every child back out, making the row childless again) and read the duration cell again: it cleanly restored the ORIGINAL typed value, because `cascadeDates` re-derives a leaf's span from `durValue`/`durUnit` the instant a row drops out of the `parentIds` set on the next recompute pass — and `rollupParentDates` never touches `durValue`/`durUnit` in the first place, so nothing was ever stale to begin with. This self-heal is a property of the existing engine, not new code from this fix, but it applies equally to any operation (indent/outdent/delete-promote) that changes who has children, and it is now asserted in both the live harness (`ui-audit/verify-schedule-indent-outdent-delete.mjs` section E1) and unit tests.
- **Health rollup, MEASURED for both directions.** A row that GAINS a red-health descendant via indent rolls up to red once collapsed; a group that LOSES its only red child via outdent improves to gray — both read straight off the existing `computeRolledHealth`/`rolledHealthMap`, which is a pure function recomputed from the CURRENT tree on every render, so reparenting needs no special-case code to stay correct. Verified live (`ui-audit/verify-schedule-indent-outdent-delete.mjs` section E2).
- **ONE UNDO STEP for the whole batch.** `indentSelectionByIds`/`outdentSelectionByIds` each call `setData` exactly once per invocation (structurally: one function body, one `setData` call, source-pinned), which is what makes the app's existing "one `history` push per `data` change" undo mechanism restore the whole multi-row move in a single Ctrl+Z — verified live for both a 4-row indent and a 3-row outdent.
- **Predecessor/successor links survive trivially** — indent/outdent only ever change `parentId`; no task's `predecessors` array is touched.
- **`canOutdent`, used to disable the context menu's "Outdent ←" item, now reflects the WHOLE resolved target set** (computed at the call site against `structuralTargets`), not just the single right-clicked row — so a multi-row right-click correctly disables Outdent only when every targeted row is already at depth 0, rather than reading just the clicked row's own depth.
