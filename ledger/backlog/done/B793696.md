- **THE CORRECTED EXPLANATION.** The repo-level "Workflow permissions" default is a **CEILING**: a workflow's own `permissions:` key (workflow-level or job-level) can only ever narrow the token below that ceiling, never raise it above. With the ceiling set to read-only, `pr-auto-ready.yml`'s `pull-requests: write` request — at either YAML level — was never going to be honored, and neither `markPullRequestReadyForReview` nor `enablePullRequestAutoMerge` could ever have succeeded, on any PR, no matter how the workflow file was written.
- **⛔ CORRECTING THIS ITEM'S OWN EARLIER READING OF THE EVIDENCE.** The failed run's job log (`get_job_logs`, PR #1188's run #8, job `98311585681`) prints a `GITHUB_TOKEN Permissions` block reading `PullRequests: write`, and this item originally treated that line as proof the token actually held write access at call time — reasoning from there to "this must be a restriction on the specific mutation, not a scope problem," a third case beyond the owner's original (a)/(b) framing. **That inference was wrong.** The printed line reflects what the workflow's OWN `permissions:` key DECLARED/REQUESTED, not what the repo-level ceiling actually let through to the real API call — the two can disagree, and here they did. The GraphQL FORBIDDEN response is the one place the REAL, ceiling-capped permission shows up. Recorded as a caution for the next session reading a `GITHUB_TOKEN Permissions` log block: it is evidence of the request, not proof of the grant.
