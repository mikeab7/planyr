`[x]` **✅ DONE, with an honest limit stated rather than papered over — the DETAIL VIEW now matches the app's own established read-view date convention; the EDIT FORM's native date picker was left alone, because it was never a second, invented format.**
- Verify: sandbox — a pure parsing/formatting function, unit-tested; the display half is a static string, no live browser needed.
- **WHAT I FOUND, before changing anything (AUDIT-FIRST).** `compFieldRows` pushed the raw `comp.compDate` string straight through — `"2026-08-28"`, no formatting at all. Every OTHER read-view date in this app (`FileBrowser.jsx`, `SiteReviewModal.jsx`, `MapFinder.jsx`) formats the same way: `toLocaleDateString(undefined, { year: "numeric", month: "short", day: "numeric" })` → `"Aug 28, 2026"`. The edit form's `<input type="date">` is the SAME native picker every other date-entry field in this app already uses (there is no custom text-based date field anywhere in the codebase) — its `"08/28/2026"` display is the browser's own locale rendering of that native control, not something this app's code chose or can restyle without replacing the picker with a non-native one (a materially bigger change, not what was asked, and a UX regression from the accessible native control).
- **THE FIX.** `compFieldRows` now formats `comp.compDate` through a new `fmtCompDate` helper before rendering: parsed by its Y/M/D parts (`iso.split("-").map(Number)`, the same date-only parsing idiom already used in `detentionRules.js`) into a LOCAL `Date`, never `new Date(iso)` directly — comp_date carries no time, so parsing the bare string as UTC and displaying it in a timezone behind UTC would print the wrong day. Detail view now reads `"Aug 28, 2026"`, matching the rest of the app. The edit form's native date input is unchanged.
- **HONEST RESIDUAL, stated per LOUD-FAILURE rather than claimed as full parity:** the two views still don't print byte-identical text — one is a formatted read-view string, the other is a native OS/browser-rendered picker whose exact text is outside this app's control. What WAS a real inconsistency (an app-wide convention on one side, a raw unformatted ISO string with no convention on the other) is now resolved; what remains is inherent to using an accessible native date control for editing, which every other date field in the app already accepts.
- **VERIFIED** — `test/comps.test.js`: `"2026-08-28"` → `"Aug 28, 2026"`; a January-1st date near a US-timezone UTC boundary (the case that would break a naive `new Date(iso)`) → `"Jan 1, 2026"`, proving the Y/M/D parsing rather than assuming it.
