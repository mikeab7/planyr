`[x]` **SHIPPED THIS SESSION.** Independently re-measured live (headless Chromium against a fixture-seeded local dev build, AUDIT-FIRST) before trusting either the original report or the retraction: the grid's own `<div role="grid">` wrapper carried `tabIndex={0}`, a SECOND tab stop sitting in front of the active cell's own roving tabIndex — Tab from the paste textarea landed on this bare, unlabeled wrapper (not a data cell) before ever reaching the sheet, and once selection sat on the Location column (an "action" cell), its `<td>` carried no `tabIndex` of its own at all (only the inner `<button>` did) — a census that only reads `<td>` values, taken at exactly that moment, would read zero, which is what the original report's now-retracted claim most likely caught. Four fixes, all in `CompEntryGrid.jsx`: **(1)** the wrapper is `tabIndex={-1}` now — still `gridRef.current?.focus()`-able programmatically (every existing focus-recovery call keeps working) and still receives every bubbled keydown, just no longer a natural Tab stop, so Tab now lands directly on the active cell. **(2)** The roving anchor for the Location column moved from its inner `<button>` (which used to conditionally claim `tabIndex={selected?0:-1}`) onto the `<td>` itself, matching every other column — the button is now permanently `tabIndex={-1}`, never an independent tab stop, reachable from the focused cell instead via the pre-existing "focus follows selection" effect (unchanged: `.focus()` still works on a `tabIndex={-1}` button) and via `onGridKeyDown`'s pre-existing Enter/typed-character activation (keyed on `selection`, not on which element holds DOM focus). Verified this keeps the grid's single-tab-stop invariant intact: exactly one element carries `tabIndex="0"` at any moment, at any scale tested (3 rows: `{zero:1, negOne:35, none:0}`), and it correctly moves with arrow-key navigation. **(3)** The delete `✕` button — previously with NO `tabIndex` attribute at all, hence unconditionally in the native tab order for every row — is now `tabIndex={-1}`; reachable from the focused row instead via a new **Shift+Delete** shortcut (`removeSelectedRows`, operating over the current selection/range, routed through the same undo-covered `commitRows` the mouse-click delete already used — Ctrl/Cmd+Z restores it identically). Fixing this surfaced a real regression in the new shortcut itself before it shipped: removing the row holding DOM focus let the browser drop focus to `<body>` (the standard behavior when a focused element is removed), taking every subsequent keystroke — Ctrl/Cmd+Z included — out of the grid's own `onKeyDown` reach; `removeSelectedRows` now reclaims focus on the grid container immediately after committing the removal, the same recovery `finishEdit` already does after a commit. **(4)** Tab/Shift+Tab used to wrap forever at the grid's own edges (`computeDestination`'s row-axis clamp has nowhere further to go) — both in plain cell-navigation (`onGridKeyDown`) and, separately, in the editing commit-and-move path (`finishEdit`'s "land the next cell in edit mode" reopen, HARDENING-10 NEW-3), which is the more commonly hit path since a click or Enter already opens editing. Both now detect the genuine edge case (source cell in the last visible column of the last row going forward, or the first visible column of the first row going backward) and let Tab through unhandled / skip the reopen, so a keyboard user reaches the footer's Close/Save buttons instead of looping inside the last row's fields — a purely additive check alongside the pre-existing `samecell` guard, touching no other `moveDir` shape (Enter's row-move is unaffected). **ARIA contract finished**: `scope="col"` on every column-label header cell, `scope="colgroup"` on the group-band cells (`scope="col"` on the one-column remove-button spacer, since it isn't really a multi-column group), `aria-label="Comp entry sheet"` + `aria-rowcount`/`aria-colcount` on the grid wrapper, and `aria-selected` on every cell (true only for the active one). Every change here is scoped to `onGridKeyDown`/`finishEdit`'s Tab-move branches and cell/header rendering — the module's own long-standing moratorium on `onEditKeyDown`'s commit/blur machinery (the Enter/Tab-discards class, closed in prior HARDENING rounds after five regressions) was read in full and not touched.
