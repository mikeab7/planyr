**The report.** *"If I double click on the parcel, it shows the owner as Forestar USA, and then the next line is just the owner as Forestar USA again. And then the legal description is probably too much information — there should probably just be a dot dot dot and a dropdown so that we can see the rest of the information."*

**(a) The duplicate — cause, and it is NOT the one the brief predicted.** The brief's hypothesis was that the matcher emits one row per matching COLUMN (e.g. `OWNER_NAME` **and** `NAME_CARE`, which the Weld-shaped records really do both carry). **That is not what happens, and the code says so:** `apprRows` walks `APPR_FIELDS` **once per LABEL** with a used-key set, so it is already one row per logical FIELD, first matching column wins — for every field, not just Owner. The actual defect was one layer up: the panel rendered a dedicated **Owner headline** *and then* the curated list, which contains an Owner row. Two renderers, one fact. (Worse, the headline used a **local copy** of the Owner regex rather than the shared field map, so the two could have disagreed about which column the owner comes from.)
**The fix.** The headline reads the shared `ownerName(attrs)`, and the list is built by `parcelPanelRows`, which drops any row that merely repeats the headline. The one-row-per-field property is now **guarded** rather than merely true (`test/parcelPanelRows.test.js`), including on a record offering several candidate columns per field. Only an EXACT repeat of the headline is dropped — three money rows all reading `$0` are three real facts and all three survive.

**(b) The long tail.** The default view is **Situs address · Account / ID · Acreage**. Everything else — Land value, Improvement value, Total value, Land use, Zoning, Year built and the unbounded metes-and-bounds **Legal** description — folds behind one **closed** `More details (n)` disclosure, with the Legal value height-capped so it scrolls in place instead of growing the panel. The separate "All county fields" expander is untouched.

**One derivation, two hosts — the choice, stated.** The planner panel and B1166's map-search card **share `appraisal.splitCuratedRows`** (which rows, in what order, formatted how) on top of the `apprRows` field resolution they already shared; `parcelCardRows` is now a one-line call into it. They do **not** share a component: one is a floating card over the map with its own dismiss/plan actions, the other a docked panel Section. Sharing the derivation is what stops them drifting; sharing the component would have forced a props-shaped compromise on both. `test/parcelPanelRows.test.js` pins the sharing itself, and `ui-audit/verify-parcel-card-height.mjs` re-run 13/13 proves the card is unchanged by the refactor.

**Paid for its own bytes.** The panel's two Sections moved into `components/ParcelDataPanel.jsx` behind `LazyPanel` (the B1064 tranche): they only ever render for a lot that came from a county identify, and they were riding the planner's boot chunk for every session. With `ParcelInfoCard` also made lazy, this change is a **net −2.2 KB on the largest chunk** despite adding six features — measured against a stashed build of the same base.

> **Tests / verification.** `test/parcelPanelRows.test.js` — 11 cases on a Weld-shaped synthetic record (owner exactly once; a second owner-ish column never becomes a second row; one row per logical field, for every field; three `$0` rows all survive; the three-row default; Legal never in the default view and always last in the tail; nothing curated is lost; the empty case; and the shared-derivation pins). Headless: the owner headline appears **once**, the default view is exactly the three rows, and the fold is **closed** with 5 rows behind it — in both themes.
