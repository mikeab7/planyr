Investigated → confirmed correct by construction, and locked it in.** There was no pre-existing *cost* paving figure to fold curb into — the only paving area the app derived was the **impervious/SF** metric, where including the curb band is *correct* (curb is impervious surface), so that stays untouched. The new cost takeoff (B181) derives paving from the road's **face-of-curb-to-face-of-curb travel width** (`roadTravelWidth` = `min(w,h) − 2·curb`), which **excludes** the curb by definition: a 30′ FC-FC road yields 30′ of paving, never 31′. So the defect the brief warned about (folding the 6″ curb each side into paving) cannot occur — the cost math reads travel width, not the full element rectangle.
> **Locked against regression:** `roadQuantities` (in `lib/costTakeoff.js`) takes the FC-FC width explicitly and a unit test asserts a 30′ FC-FC × 1000′ barrier-curb road = exactly **30,000 SF (3,333.33 SY)** of paving with curb **outside** that width — so a future change that folded curb back in would fail the suite. **Live-confirmed in-browser:** a seeded 26′-cross road (FC-FC travel 25′) reads **1,611 SY** in the Yield panel (25 × 580 ÷ 9); had curb been folded in (26′) it would read 1,675 SY — the 1,611 proves the exclusion. 300 tests green, lint 0 errors, build green.
