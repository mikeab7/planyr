It doesn't seem like it's attached to this part, it's bouncing as I'm scrolling, which is odd because it should just be attached." A prior message in the same block supplied the MEASURED mechanism (gap from input to popup 42px before scroll; after a 120px scroll, input moved to a new position, popup top read the SAME 376px it started at — a 0px response, not merely a laggy one) with an explicit instruction not to re-diagnose it. Ships as part of B1557008's PR. Minted **B1557011** from the same reserved block. DEDUPE-FIRST: net-new.)*

`[x]` **FIXED THIS SESSION** — real headless-Chromium verification with genuine mouse-wheel scroll events, `ui-audit/verify-owner-scroll-tracking.mjs`, 14/14 checks: the popup's top moved exactly with the input's top across a real 150px wheel-scroll (both moved 150.0px, gap unchanged at 2.0px before and after); a second editor, scrolled a full viewport's height out of the grid's own visible bounds, closed outright rather than floating over the header or hanging outside the grid; chip drag-reorder (a genuinely separate mechanism, verified in the same pass since it shares the same popup) correctly promotes the dragged-to-first chip to accountable, confirmed both in the closed cell's display and in MasterView's sort order.

**MECHANISM.** The popup is `position: fixed`, portaled straight to the iframe document's body (the whole Schedule grid runs inside an iframe — DOM queries against the top document find nothing; it's same-origin and reachable via `document.querySelector('iframe').contentDocument`). Its position used to be computed once on open and refreshed by `window.addEventListener('scroll', fn, true)` — a capture-phase listener that, against this app's specific nested grid scroll container inside the iframe, was measurably not firing reliably: the freeze-then-snap-on-next-keystroke pattern in the owner's own measurement is exactly what a listener that fires late (or not at all until some OTHER state change forces a re-render) looks like.

**FIX.** Position tracking is now a `requestAnimationFrame` loop, running continuously while the picker is open: it re-reads the input's real `getBoundingClientRect()` every frame, so it has no event to miss and cannot desync from whatever the browser is actually painting — the same treatment covers wheel scroll, scrollbar-drag scroll, keyboard scroll, and window resize uniformly, because none of them are singled out; the loop just reads the DOM. Two behaviors chosen deliberately (the brief said either is defensible): the popup **flips above the cell** when there isn't room below (estimated against a rough popup-height, re-evaluated every frame); the editor **closes outright** (committing whatever chips exist, same as a blur) the instant the cell's own position leaves its scroll container's visible bounds — chosen over "keep tracking off-screen" because a popup still computing a position over the frozen sticky header is worse than no popup. Both grid views now carry a `data-scroll-bounds` marker on their own scroll container (GridView's existing `data-grid-scroll` div; MasterView's `tableWrapRef` div) so the picker can find "my container" generically via `closest()` without prop-drilling a ref through the `Cell` sub-component.
