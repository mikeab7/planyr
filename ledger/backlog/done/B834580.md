`[x]` **SHIPPED — reused `paintSchedule.js`'s `runBudgeted` (the exact primitive B802400 round 5 built), no second scheduler.** The saved-site layer group is now added to the map EMPTY, then every polygon construct+add — the expensive part, since Leaflet's `Path.onAdd` projects a ring synchronously the instant it's added to a layer already on the map — is queued as one op and drained a bounded time-slice at a time, yielding via a genuine `MessageChannel` macrotask between slices (the same idiom `terrainLayers.js` uses, and for the documented reason: a `requestAnimationFrame` continuation gets folded into the SAME frame as Leaflet's own queued redraw, so it can't actually hand control back between slices).
- Verify: sandbox
- **CANCELLATION**, since this rebuild can now legitimately still be running when the effect fires again (deps changing mid-paint): an epoch ref (`sitesPaintEpochRef`) bumped at the start of every `build()`; any in-flight budgeted continuation from a superseded build checks its captured epoch and silently stops rather than racing to populate/replace `sitesLayerRef.current`.
- **REAL BEFORE/AFTER NUMBER, honestly scoped.** At the task's own literal production counts (5 sites, 778 elements — matching Richfield/Schiel/Silvestri), this fast headless sandbox never crosses the browser's ~50ms long-task threshold at all, even pre-fix (max single animation-frame gap 33.4ms) — an honest property of this environment (no concurrent GIS/tile decode, presumably faster hardware than the report was filed from), not evidence the mechanism doesn't matter, since the blocking cost scales with element count by construction (confirmed by reading `LayerGroup.onAdd`: it iterates every child in one synchronous loop). `ui-audit/diagnose-map-plan-zoom-cost.mjs` proves the scaling directly at 10 sites x 300 = 3,000 elements (a deliberate stress multiple, run specifically to produce an observable number in this sandbox): **pre-fix 1 long task at 88.0ms, max frame gap 83.3ms · post-fix 0 long tasks, max frame gap 50.0ms** (right at the scheduler's own 40ms budget plus overhead, as expected).
