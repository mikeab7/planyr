- **Report (owner, verbatim).** "I'm clicking X on element to close, or on the properties menu to close out the building properties, and it's literally not responding. And before that, I was double clicking on the building to open the properties menu and it wasn't responding either."
- **REPRODUCED FIRST, as asked — and the condition matters.** A single clean tab, logged out, on a blank site: draw a building → click the rail's **Properties** tab → double-click the building (panel opens) → click ✕ → **the panel does not close.** `e2e/inspector-close.spec.js` failed on `main` at exactly that assertion (panel count 1, expected 0) and passes on this branch. **The second-tab concurrent-writer condition was NOT required** — the bug is deterministic state logic, so there was no race to chase. (No `client_errors` telemetry for the window, consistent with that: nothing throws.)
- **Root cause — the seam between B733 and the NEW-1 takeover.** The ✕ only dropped the explicit-open marker (`setPropsFor(null)`). That suffices while the inspector holds the dock through its takeover memo, but the panel ALSO renders through `propsTab && companionSel` — and **any deliberate rail click clears the memo** (`setDockMemo(null)`), while the relinquish in the takeover layout effect is guarded by `if (memo)`. So `leftPanel` stayed `"properties"`, the second branch kept rendering, and every click landed, every handler ran, and nothing changed. The "double-click won't open" half is the same stuck panel seen from the other side: with the panel already up (and stuck), a double-click produces no visible change either. The relinquish can't simply be un-guarded — it must NOT fire when the tab was opened deliberately with nothing selected, or the docked Properties tab could never stay open at all. So dismissal is now explicit.
- **Fix.** ONE `closeInspector()` shared by the ✕ and the keyboard: it drops the marker AND releases the dock — back to the panel the inspector replaced when there is a memo, otherwise to nothing — so the panel is gone either way, which is what ✕ promises. **Escape is now a guaranteed escape hatch**: it closes the inspector first (element stays selected, matching ✕) and consumes the key; a second Escape falls through to the existing catch-all deselect. The panel's visibility is mirrored to `inspectorShowingRef` during render because the window keydown listener's dep list does not include `leftPanel` — the ref is the live truth, the render branch and the ref are one fact.
- **Investigated in the order the brief specified, and (1) was real too — hardened.** With a colour picker open, `document.elementFromPoint` over the building returns `AnchoredMenu`'s click-away backdrop: `position:fixed; inset:0` at z-index 4000, covering the whole app including the panel ✕. Correct while a visible menu needs dismissing (it costs one click), indefensible otherwise — and it WAS reachable otherwise: `placeMenu` returns null for a zero-sized anchor (its host rail/panel gone `display:none`), and the old code left a stale `pos` standing, so an invisible layer could swallow clicks with nothing on screen to explain it. The backdrop is now gated on the menu actually being placed, and a stale `pos` is cleared when the anchor stops being measurable. **The Standards sticky footer was NOT a suspect on inspection** — it is a real flow sibling (`flex:none`), not an overlay, so it cannot intercept anything. (2) re-render churn was not the cause: the panel opens and closes fine with the element nodes being re-rendered underneath.
