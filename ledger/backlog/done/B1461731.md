**THE PROBE/DISCOVERY TOOLING'S OWN HOST-LEVEL BREAKER, `ui-audit/lib/hostThrottle.mjs` (new).** Reuses `sourceHealth.js`'s logic directly (imported, not re-implemented — one behaviour, not two competing definitions of "unhealthy") but keyed on HOSTNAME rather than county, because a probe walks many services that can share one host (the neighbour walk from B1461730 above is the clearest case) and a struggling host affects all of them at once; the two never collide in practice since they run in separate processes (browser runtime vs. this Node tooling) with no shared memory. `recordHostOutcome(url, ok, ms)` judges HOST health on the TRANSPORT alone (did it answer, how fast) — an ArcGIS error body or an HTTP error status still means the host responded (a SOURCE problem, handled separately by `probeSource`/`walkForReplacement` reading the body), so those don't count against the host itself; a thrown network/timeout error, or any response ≥ the slow threshold, does. `waitForHostSlot` adds a floor (250ms) on spacing between requests to the same host, so the neighbour walk's own directory-then-services-then-layers sequence doesn't fire back-to-back at a host that may already be struggling. Wired into `probe-statewide-parcels.mjs`'s core `fetchJson` — the ONE fetch wrapper every probe script in this folder routes through (directly, or via the neighbour walk / health sweep's shared use of it) — so this is universal across the folder's tooling, not opted into per-script. A single bad response never opens the host breaker (3 consecutive, same as the app's own threshold), so the neighbour walk can still try a handful of sibling services on a host right after one of them errors; only a genuine pattern (the Nevada case: an 18s error, then total non-response) trips it.
