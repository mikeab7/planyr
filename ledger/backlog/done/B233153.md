**THE CAPTURE (owner's machine, planyr.io signed in, Bain / "Concept A — Quiddity Hydrologic", main @ #959).** A capture-phase listener at the svg root, one double-click on the pond water:

```
pointerdown#1 → path{url(#grad-water)}          ← the pond's own fill; it SELECTS, blue grips go 4 → 16
pointerup#1, click#1 → same path
pointerdown#2 → rect{transparent}               ← rect[data-export="skip"][data-testid="vtx-handle"],
click#2, dblclick → rect{transparent}             18×18, inside g[data-export="skip"][data-handle-layer="1"]
```

**That rect is one of the POND'S OWN VERTEX HANDLES.** Selecting the pond mounts the handle layer (41 nodes) and one 18px transparent hit square lands exactly on the point that was pressed. **The first press summons the thing that blocks the second.** Press 2 therefore never reaches the pond: the double-tap cannot pair (`isDoubleTap` is called from the feature's own `pointerdown`, which never runs) and the native `dblclick` retargets. Zero console output — the failure is completely silent.

**RULED OUT, with the readings.** The pond group is `cursor: move` and `pointer-events: auto`, and `elementFromPoint` resolves to the pond BEFORE press 1 — not locked, not pointer-inert, not covered beforehand. The leading hypothesis on the filed item (an exception while rendering the pond's Properties) is refuted: nothing threw.

**WHY SIX SANDBOX VARIANTS MISSED IT, and this is the part worth more than the fix.** The variable is not the SHAPE — polygon, `det` record and expansion baseline were all already covered. It is **VERTEX COUNT AGAINST HANDLE SIZE AT THE PROBE POINT.** A real pond ring has dozens of vertices so its basin edge is peppered with 18px hit squares; every seeded variant was a FOUR-vertex ring whose grips sit at four distant corners, nowhere near a centre probe. That is exactly how a green 19/19 certified a pond nobody could click.

**THE FIX — AT THE RESOLVER, NOT ON THE POND.** `lib/featureTarget.js`'s `resolveDoubleClickTarget` used to answer `null` the moment a handle-layer node was on top ("a handle owns the press"). It now **skips** it: a vertex handle is chrome belonging to the selected feature, never a feature. One rule, and every element type that renders grips is closed at once — a pond-shaped special case would have closed one report and left the parcel, the polygon element, every markup with vertex grips and every future grip open. It is the same rule `pressIsOverElementBody` beside it has always applied.
- **DRAGGING IS UNTOUCHED, and that is asserted, not asserted-about.** Grips keep their own `pointerEvents` and their own `onPointerDown`. What changed is *which feature was double-clicked* — identification, never delivery.
- **CHROME-NEVER-EATS-A-PRESS gains its third instance** (after B1174's measurement chips and B1327's acreage badge), with the corollary now written into the named rule: **chrome mounted BY the first press is invisible to any check that reads the DOM before the interaction.**

**THE INSTRUMENT, which is the other half of the deliverable.** Nothing in this repo could observe the middle of a gesture. Two things fix that permanently:
- **`window.__plannerHitTarget(x, y)`** — E2E-gated, read-only, nulled on unmount like every other planner probe. It asks the app's OWN resolver what a double-click at a point would address RIGHT NOW. A harness that re-implemented the rule would test its own copy of it (the "a second hit-test is free to disagree" trap `featureTarget.js`'s header names), and a harness that agrees with itself while the app fails is how this shipped green.
- **THE TWO-PRESS INVARIANT** — press once, re-ask, require the same feature. That is the only probe shape that can see chrome which does not exist until the gesture is half-finished, and it would have caught this AND the road dimension number (B50010).

**AND A SECOND HARNESS DEFECT THE CAPTURE EXPOSED, which had blinded the whole audit.** `audit-doubleclick-properties.mjs` drove its double-clicks as two bare `down/up` pairs. **Chromium synthesises a native `dblclick` only when the second press is stamped `clickCount: 2`** — two bare pairs leave the counter at 1 and no `dblclick` is ever delivered. So every row was passing on the reconstructed double-TAP alone and the root resolver — the half that carries a real user double-click — **was never exercised at all**. That is precisely the half a grip kills. The presses are still separate (pointer capture must release between them); only the stamp changed.
