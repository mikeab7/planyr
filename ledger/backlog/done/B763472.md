### B763472 — Schedule row drag: killed the middle "reparent" band, unified before/after depth resolution, and fixed the grip↔ID-number spacing `[Scheduler]` (bug) #scheduler #ui  *(owner report, #1107 live regression 4 days after ship, verbatim: "moving tasks up and down on the schedule is kinda finicky... I tried to move a task above another task, and it somehow put it as a subtask for the task that it was hovering above." Owner refined the fix across the session: first "kill the middle band, two outcomes only"; then the depth rule "match the row above, but never shallower than the row below"; then "drop the drag grip/number spacing" and "there should be a visual so I actually know I'm moving something" — all three folded into one PR per his instruction.)*
`[x]` **Measured, fixed, and re-measured — band geometry, depth resolution, grip spacing, and drag visual feedback.**
- Verify: sandbox — extensive REAL-mouse-driven headless Chromium testing (never synthetic dispatchEvent), at his exact row height (20px) and the slider max (34px), against a fixture shaped like his reported scenario. 46/46 checks pass, including a mutation battery proving every new guard is discriminating (not just green). No auth/GIS dependency for this module (standalone JSON import/export), so this is fully Claude-doable per ATTEMPT-BEFORE-YOU-PARK, not deferred.
- **STEP 1 — BAND TABLE (measured, not assumed).** OLD (#1107, three-band): before/after each 30% of ROW_H, reparent ("into") the middle 40%. At his 20px rows: before/after = 6.0px each, into = 8.0px — the riskier outcome was the BIGGER target. NEW (this fix): before/after 50%/50%, no into band, at every row height 20–34.
- **STEP 2 — PIXEL SWEEP, real drags, every 1px, both row heights, OLD source (pinned at pre-fix commit `0903bc8`) vs NEW.** OLD@20px: into=7px, before=7px, after=6px (into ≥ either individual band, confirming the reported bug quantitatively). NEW@20px and NEW@34px: **zero** "into" outcomes across the full sweep — a drag can no longer reparent by vertical position alone.
- **THE FIX, three parts, all in `public/sequence/index.html` (`GridView`'s `startRowDrag`):**
  1. **Two outcomes only.** `computeAndPaint`'s frac split is now `<0.5`/`>=0.5` (before/after), no middle band. Making a task a subtask is what indent (Shift+Alt+Right / right-click menu) is for; drag no longer overlaps that job.
  2. **Depth rule, unified.** New `resolveDropParent(gapIndex)` resolves depth from the GAP (the pair of rows bounding the drop point), not from whichever half of whichever row the cursor happened to be over — the old code derived depth from "before" and "after" independently and could disagree with itself on the exact same gap, which is the actual mechanism behind "drop above X reparents into X." Rule: match the row above, clamped to never be shallower than the row below (the row below can only be deeper if it's the row above's own first child — a flattened depth-first walk steps at most one level deeper — so landing any shallower would silently ADOPT that child into the dropped row's new subtree). Verified via **child-count-before/after** on every affected parent at all 5 owner-named insertion points (expanded-parent→first-child, last-child→next-section, below a collapsed group, above the first row, below the last row of the whole schedule) — zero silent adoption in every case.
  3. **Real bug the pixel sweep caught mid-implementation:** the dragged row(s) are still physically present in `tasks` at their old array position during the drag (only dimmed, never removed, per the zero-DOM-churn design) — so a gap immediately beside the drag's OWN start could resolve "the row above/below" to the dragged row itself, and `moveSelectionToDestination` silently fell back to "end of the list" when asked to insert after a row it had just excluded. Fixed by skipping the blocked/dragged set when finding the true row above/below.
- **VISUAL FEEDBACK (owner, verbatim: "there should be a visual so that I actually know that I'm moving something... professionally done").** Audited what existed: a plain 2px full-width insertion line + (pre-fix) a same-color outline on the "into" target — no depth cue at all. Now: the insertion line is **depth-aware** — it starts at the exact x-offset the dropped row's own name text would start at (same `4+level*14` formula the name column itself uses), so a sibling-level drop and a nested drop are visibly different lines, not the same line at two heights; a small leading dot for legibility at 20px rows; the dragged row(s) get a dashed "in-flight" outline in addition to the existing dim. Pre-existing and left unchanged: grip visible before press (`.rowgrip` opacity), grabbing cursor during drag, edge auto-scroll. Confirmed (not just assumed) that auto-scroll doesn't fight the #1101/B463922 scroll-anchor effect — that effect is keyed on the `tasks` array reference, which never changes mid-drag (zero re-renders), so there's no concurrent write; measured post-drop scroll state is sane (check I2). Screenshots at his 20px row height (at-rest grip, mid-drag sibling-depth line, mid-drag nested-depth line) sent with the PR.
- **GRIP↔ID-NUMBER SPACING (owner, verbatim: "not a ton more space, but... enough that it makes sense").** Was `paddingLeft:4` on a number sitting directly under an 8px-wide grip strip — touching. Now `paddingLeft:12` (clears the grip + a small gap). Measured: gap 0→4px; ID cell still exactly 30px (the gap came from padding, not a widened cell); a REAL 3-digit id (his actual row numbers — built a 121-task fixture since ids auto-renumber to sequential 1..N on every load) is NOT truncated at either row-height extreme. A 4-digit id is PROJECTED (font-metric calculation, not yet DOM-verifiable — no project has 1000+ tasks) to need ~9px more column width; flagged, not silently clipped, not a regression against anything that worked before. Grip's own hit area untouched (still exactly 8px, pointer-events always on, opacity hover-gated only) — re-verified row-range select still works (badge + selected-cell background color), the exact thing an earlier version of this grip broke.
- **ADJACENT CASES, all measured:** dropping above the first row (top-level) · below the last row of the whole schedule (lands at that row's own depth — accepted consequence, outdent unchanged) · onto a collapsed group header (beside it, never inside, never force-expanded) · a parent-with-children dropped near another parent-with-children (subtrees stay separate) · a multi-row selection (moves as one block) · dropping onto the row directly adjacent to the source (the smallest possible move, and the one he described doing) · a genuine no-op drop (pushes no spurious undo entry — one Ctrl+Z after it lands on the exact same state as one Ctrl+Z with no drag at all).
- **UNDO:** one Ctrl+Z fully reverts a depth-changing drop, confirmed.
