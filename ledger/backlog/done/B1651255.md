`[x]` **IMPLEMENTED AND UNIT-TESTED — two new named traps in `ui-audit/discover-county-parcels.mjs`'s acceptance test (`acceptCandidate`), the harness this repo already uses for parcel-source vetting.**

**NAMED TRAP #2 — the city-hole.** A county layer can carry a correct count AND a correct extent and still have a hole exactly where the county's largest city sits, because the city publishes its own parcels separately (Minnehaha County, SD — B1651249 above — is the worked, real-world example: a plausible 23,044-polygon count, a full-county extent, and a point query at Sioux Falls, its own largest city, returns ZERO). Neither count nor extent can catch this; the catching test is a point query AT the county's largest city, run SEPARATELY from the three generic geometry-spread points (which pick maximally-SPREAD points and can miss the city entirely, or pass by luck). `acceptCandidate` now accepts an optional `largestCity: { name, lat, lng }` — when supplied, `probeLargestCity` runs this extra probe and REJECTS a candidate that passes every spread point but returns zero at the named city, naming the trap in the rejection reason.

**NAMED TRAP #3 — the title is never the measurement.** A service's own title claiming "Countywide" is a claim, not evidence: "Land Trust of Jackson County Missouri Parcels (Countywide)" (`services.arcgis.com/sbDzK061dd6DNPHv/.../ab748f/FeatureServer/0`) says countywide in its own title and holds exactly 516 features — a land-bank holdings subset, not the county's parcel fabric. `COUNTYWIDE_CLAIM_RE` flags a title matching "county-wide"/"countywide"; when it matches, `acceptCandidate` runs one cheap `returnCountOnly` query and rejects if the real count is below `COUNTYWIDE_MIN_FEATURES` (2000 — comfortably above the 516-feature counterexample, well under every real countywide layer this repo has wired). Runs BEFORE the spread-point probing (cheaper), and never runs at all for a title with no countywide claim, so this is additive — the existing acceptance test is unchanged for every candidate that doesn't trigger it.

**Both traps are now part of the SAME acceptance test every future county-source dispatch already goes through** (`acceptCandidate`, called from `discoverCounty`'s route pipeline via `pickWinner`), so they run automatically whenever a caller supplies a `largestCity` or the candidate's own title claims countywide — no separate checklist step to remember.
