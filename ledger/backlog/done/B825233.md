- **THE SCRIPT.** `scripts/verification-queue-audit.mjs` parses every `### V###` heading inside `VERIFICATION.md`'s `## 🔲 Needs verification` section, classifies each block `failed` (carries an explicit ❌) or `open` (everything else — deliberately inclusive, since this file spans years of formats and a real chunk of still-owed items never spell the ⏳ emoji), extracts every `` `Blocker: <kind>` `` tag present, and takes the NEWEST ISO date mentioned anywhere in the block as a "last touched" proxy (an item with no date at all is reported as `noDate`, never guessed into either bucket).
- **THE THRESHOLD — 60 days, chosen and justified, not defaulted.** The measured distribution has a real break there: of the dated pending items in the owner's own audit, 125 clustered in the 31–60 day band (one or two `improve`-cadence cycles) and 60 sat past it — the genuinely neglected tail (capped by a 436-day outlier). A 30-day line would flag the entire routine backlog and say nothing useful; 60 days isolates only the items that survived more than two full monthly cycles untouched.
- **THE GATE IS A RATCHET, deliberately, matching this repo's own `perf-ratchet.mjs`/`panel-copy-budget.mjs` shape — not a blanket fail.** `scripts/verification-queue-ceiling.json` records today's own counts as the ceiling; `--check` fails ONLY if a future run's no-Blocker or stale count exceeds it, naming the new offenders. Today's existing debt does not fail tomorrow's unrelated PR — explicitly instructed not to attempt the 130-item fix in this same item, and a hard gate against the current count would have done exactly that. `--write-ceiling` regenerates the baseline after a genuine improvement; raising it to silence a real regression is against the file's own header comment, same convention as every other ratchet here.
