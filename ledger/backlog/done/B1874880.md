`[x]` **`functions/gis-proxy/[[path]].js` — new Cloudflare Pages Function, ~80 lines, no dependencies.** Deploys automatically with the site build (no `wrangler.toml`, no env var). Route `/gis-proxy/<host>/<rest of the county's own path>?<query>`: the first path segment names the upstream host, checked against a hard-coded `ALLOWED_HOSTS` set (`www.sgrcmaps.com`, `mgrcmaps.org`, `maps.crc.ga.gov` — a `..` path segment or a host not on the list is refused, 400/403, before any fetch); GET and POST only (anything else 405); rebuilds `https://<host>/<path>?<query>` and forwards the method, query string, and for POST the body + its Content-Type; forwards no client cookies/Authorization; sends `User-Agent: planyr-gis-proxy`; a 20s `AbortController` timeout; an upstream failure or timeout is a named JSON 502 (LOUD-FAILURE — never a silent empty 200); the response copies through status + body + Content-Type only (which is what strips `Set-Cookie` and everything else upstream by omission) with `Cache-Control: public, max-age=300` on a genuine 200 and `no-store` on anything else.
`[x]` **Client wiring — one real fix, found by reading every call site rather than guessing.** A county's `layerUrl` can now be root-relative. `arcgis.js`'s `fetchJson` (the ONE choke point every parcel call — `queryFeatures`/`queryAtPoint`/`identifyAtPoint`/`getLayerInfo`/`listLayers`/`resolveLayerUrl` all route through it) did `new URL(url)` with no base, which throws on a relative string; a new `resolveGisUrl(url, base = window?.location?.origin)` fixes it — an absolute URL is returned untouched regardless of base (so every existing county is byte-for-byte unaffected), a relative one resolves against the app's own origin. `gisFetch.js`'s `fetchArcgisJson` (the GET→POST fallback, B1871968) never calls `new URL` at all — pure string/`URLSearchParams` manipulation — so it already works unmodified with a relative URL; checked, not assumed. The `trim` helper (`arcgis.js`) only strips trailing slashes — confirmed it does not mangle a leading one. The on-screen parcel layer (esri-leaflet, pointed at the same `layerUrl`) needs no change at all — a relative URL resolves same-origin natively in a browser fetch/XHR, which is exactly the point of routing it through the app's own path instead of a cross-origin one.
