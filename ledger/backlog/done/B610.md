### B610 — Silent-failure gap: a filed drawing whose Drive key↔id mapping write failed read as "saved ✓" then went missing on next open `[Server / storage]` (bug)  *(surfaced 2026-07-02 when Michael reopened the old storage-adapter/Drive handoff — the NEW-1…NEW-4 vision — and asked "have we drifted"; the review found this live bug; minted **B610** = highest real B# across both files (B609) + 1; branch `claude/storage-adapter-drive-discussion-6m5236`. Extends the **B209** no-silent-failure guarantee to the durability-mapping layer — folds INTO B209, not a parallel mechanism.)*
`[x]` **Fixed + verified this session. *Moves to BACKLOG-DONE on merge.***
- **Root cause:** after Drive bytes uploaded OK, the durable Planyr-key↔Drive-id write (`public.drive_files`) was **best-effort** — `adapter.save` fired `idMap.bind(...)` and discarded the result (`server/storage/adapter.js`); `idStoreSupabase.set` only `console.warn`ed on a failed write and returned `undefined`; the resumable-upload COMMIT (`functions/api/files/resumable.js`) ignored the outcome too. So a failed mapping write still reported `ok:true` → the upload showed "saved ✓", but nothing could resolve the file → `downloadFromDrive` missed it and the drawing was silently gone next open. Exactly the class B209/NEW-4 exists to prevent.
- **Fix (honest failure + best-effort rollback, no orphan):** `idStoreSupabase.set` now returns `{ok}`; `idMap.bind` normalizes any store result to `{ok}` (a legacy `undefined`-returning set = success → back-compat, so only an explicit `{ok:false}` rolls back). `adapter.save` checks the bind result and, on `{ok:false}`, rolls the just-uploaded bytes back (`backend.remove`) and returns a visible `fail(...)` — the client then falls back to Supabase (small files) or flags re-drop (large), truthful and orphan-free. The resumable COMMIT does the analogous Drive-file rollback (`client.del(fileId)`) and returns 502.
- **Also (lower severity):** `reviewStore.deleteReview` swallowed Storage/Drive cleanup failures yet still reported `ok` → orphaned bytes, silently. It now returns `{orphaned, cleanupFailed}` and the Library shows a dismissible "a copy may linger — remove it in Google Drive" notice (data isn't lost; the row delete stays authoritative → a notice, not a red banner).
- **Tests:** `test/storageAdapter.test.js` (rollback on mapping-failure + back-compat), `test/idStoreSupabase.test.js` (`set` returns `{ok:false}`/`{ok:true}`), `test/bugHuntGuards.test.js` anti-drift guard. lint 0 · full suite **2163 green** · build green.
