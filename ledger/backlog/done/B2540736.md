Related, distinct mechanism, so a new id.)*
`[x]` **SHIPPED + LIVE-VERIFIED (2026-10-29). Verify: live → Done.** **ROOT CAUSE (AUDIT-FIRST):** `SheetView` keeps `edit` / `editValue` as component state and is not keyed by sheet; nothing cleared it on a sheet change (only `setEdit(null)` inside `commitEdit`/`cancelEdit`), the cell editor has no blur, and `TabStrip`'s `startDrag` cancels the tab's mousedown so focus never leaves it. So: Sheet1, click B5, type `500` (no Enter), click the Sheet2 tab → the editor stays open on Sheet2, and the next Enter / click commits `500` through `applyActive` (which writes to the SHOWING sheet) into Sheet2!B5, overwriting it; Sheet1!B5 never gets it. The formula bar's pending text was silently reset by its re-seed effect on the same switch.
- **Fix (Excel's contract — leaving a sheet COMMITS the entry to the sheet being left):** `SheetView` and `FormulaBar` expose an imperative `commitPending()` (cell editor reads the synchronous `editValueRef`; formula bar commits only when its draft differs from the cell, rule in `lib/pendingEntry.js`). `ModelApp.commitPendingEntry()` runs it BEFORE every handler that changes the showing sheet — `onSelectSheetTab`, `onAddSheetTab`, `onDuplicateSheetTab`, `onDeleteSheetTab`, `onNavigateTrace`. Add/duplicate/delete now commit with a functional `commit((wb) => …)` (ids come from `nextSheetId`, which a cell edit never moves) so the flushed cell edit is not overwritten by a workbook captured before it.
- **Red-proof:** `e2e/model-tab-switch-commits.spec.js` (3 specs: cell editor, formula bar, add-sheet) failed on the pre-fix code (the Sheet2 cell was left in edit mode, empty) and passes now; `e2e/model-cell-editor-undo.spec.js` still 5/5. CI-runnable half: `test/modelTabSwitchCommit.test.js` (the pending rule + source guards that every sheet-changing handler flushes first).
