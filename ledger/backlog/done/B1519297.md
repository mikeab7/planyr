- Verify: sandbox — proven by unit tests (`test/compSheetColumns.test.js`, `test/compParse.test.js` — a new describe block proves a pasted spreadsheet block's Notes/Comments column, and a headerless positional paste's trailing Notes field, both still land in `draft.notes` and survive into the saved comp via `draftToComp`) plus a real headless Chromium pass driving the actual note-mark control end to end against a fixture-seeded local plan (signed out, no GIS): the mark renders per row, a click opens a floating multi-line editor anchored to it, typing then Escape closes it and keeps the text (reopening shows it), Tab off a row's last cell (both mid-edit and merely-selected) focuses that row's note mark, and Shift+Tab from the note mark returns focus to that same cell. **Two real defects surfaced by that live pass and fixed in the same session, not by reasoning about the code:**
  1. The note popover is a portal (`AnchoredMenu`, rendered via `createPortal` to `document.body`), and a portal's events still bubble through the REACT tree it's rendered from (not the DOM tree it's mounted in) — so pressing Escape to close the note editor ALSO reached the panel's own "Escape closes the whole sheet" handler on the identical keypress, arming the "Discard N unsaved comps?" confirmation over top of the sheet the user was still working in. Fixed by adding `noteEditorRowId` to that handler's existing `editing`/`armedRowId` guard (both the desktop and, for symmetry, the always-inert-there mobile copy).
  2. Tab off a cell that auto-entered edit mode (a single click enters edit immediately, per HARDENING-10 NEW-3 — the common, mouse-driven way to reach "the last cell") landed real focus on the note mark, but the sheet's own pre-existing "focus follows selection" effect then immediately stole it back onto the just-edited cell, because that effect's only guard was "is focus already somewhere inside the grid" — true for the note mark too. Fixed by teaching that effect to decline to move focus when the currently-focused element is already a note mark.

**THE DESIGN.** `src/shared/comps/lib/compSheetColumns.js`: `notes` is removed from `SHEET_COLUMNS` outright (no sheet cell; no part of `visibleColumnIndices`/`fillDownColumn`/`spillPaste`/`computeFlexWidths` — all four were audited, not assumed) but exported standalone as `NOTES_COLUMN` (still a real `simpleColumn`-shaped object) so `compMobileLayout.js` keeps a genuine column definition for its own full-width mobile Notes field. `FLEX_NOTES` and the three-regime `computeFlexWidths` middle case ("Notes shrinks first") are gone; the four remaining growers (Location/Title/Landlord-Seller/Tenant-Buyer) now use a plain two-regime split (surplus by weight above nominal; deficit shared proportionally down to floor) and get the freed width. The underlying `comps.js`/`compParse.js` `notes` field is completely unchanged — still stored, saved, parsed and exported exactly as before.

`src/shared/comps/components/CompEntryGrid.jsx`: a new fixed-width `<td>` (`NoteMarkCell`, `NOTE_COL_W = 26`) sits between the last data column and the existing remove-row column, sticky-positioned to stay visible next to it under horizontal scroll. Its glyph (`NoteMarkGlyph`, a small outlined square with two lines drawn only when a note exists) renders in `--accent` when the row carries a note and `--border-default` when it doesn't — never a text preview. Pressing it (click, or Enter/Space once focused) opens `NoteEditorPopover` — a real multi-line `<textarea>` in an `AnchoredMenu` (the app's existing anchored-menu placement, `placement="above-left"`, no new positioning routine), floating over the map without changing the panel's height or moving any row. Typing is local state; Escape or a click-away (both already handled by `AnchoredMenu` itself) commits the value into that row's draft and closes — "keep what was typed" without a per-keystroke undo frame. The mark takes no part in the grid's own cell-selection model, arrow-key navigation, Ctrl/Cmd+D fill-down, or Excel-style paste-spill (all four still operate purely over `SHEET_COLUMNS`/`visibleIdx`, untouched) — the ONE bridge to the keyboard is Tab off a row's last visible column, which hands off to that row's note mark (`data-note-row`) rather than wrapping to the next row, and Shift+Tab from the note mark returns to that same last cell. This is wired in two places, since a click and a keyboard arrival reach "the last cell" through two different code paths in this file (`onGridKeyDown`'s own Tab branch for a merely-selected cell; `finishEdit`'s Tab-commit branch for a cell that auto-entered edit mode) — both were audited and fixed, not just one.

**COLUMN-INDEX AUDIT (the highest-risk part of this item, per the dispatch's own brief).** Every column-position caller in this file and `compMobileLayout.js` was checked: none hardcode a numeric column index — `columnIndex(key)`/`SHEET_COLUMNS[idx]` are always looked up by key, and the desktop grid's own `selection.col`/`editing.col` are always members of the live `visibleIdx` array (recomputed off `rows`), never a stored literal.
