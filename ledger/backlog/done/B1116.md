- **Repro (measured on production, signed in).** Drag a building, Ctrl+Z within ~2 s. The client emits **exactly two `commit_elements` calls, twelve ops each, and nothing else** — verified on the wire. But `site_elements` lands TORN in two transactions: **17:27:08.552 — `e25duuwgj` ONLY, RESTORED, rev 79**, then **17:27:09.649 — all ELEVEN children at the MOVED coordinates**. One of the undo batch's twelve ops was accepted; eleven were refused, and the move's values stood. The client then **treated the commit as complete, adopted the torn rows, and issued nothing further for 40 s.**
- **Root cause (AUDIT-FIRST) — and it is MINE, from the previous round.** The eleven children are bonded, so every one of their ops is tagged DERIVED. B1099's derived-yield rule — correct and necessary when *another writer* beats us — fired here against **our own tab's earlier move commit**, so all eleven stood down in silence while the host's single accepted op went through. Yielding to yourself is never right: a self-conflict is a torn write, not a foreign edit. Secondarily, nothing anywhere checked whether a batch landed WHOLE.
- **Fix (client half — shipped).** Two changes: **(1)** the derived-yield branch now requires `foreignAuthor(row)`, so an op can never stand down against this tab's own earlier write; **(2)** a new **assembly-split detector** in `processResults` — if any member of an assembly was accepted while another was refused, the batch is TORN and **nothing is settled**: every refused member of that assembly is re-enqueued (the conflict branches have already adopted the fresh revs, so the retry targets the current rows), an `assembly-split` event is emitted, and if it will not converge after `maxRejectStreak` rounds the engine goes to the loud `stale` state rather than looping.
- **✅ SERVER HALF NOW LIVE (was blocked; unblocked the same day).** `commit_elements` is one transaction, but a per-op rev conflict recorded a result and CONTINUED, so accepted ops still committed — right for independent elements, catastrophic for an assembly, and **not closable from the client**. `src/workspaces/site-planner/db/commit_elements_atomic.sql` adds a **defaulted** `p_atomic boolean default false` third parameter for all-or-nothing group commit; the existing 2-arg call is untouched. **The owner applied it to production (`lyeqzkuiwngunutlkkmi`) on 2026-07-29 and rollback-verified it against the real Tsakiris assembly** — a two-op atomic call with one good rev and one stale one returned `{applied:false}` and left BOTH rows unchanged. The client now passes `p_atomic` for assembly-spanning batches (**B1117**, shipped), with a latching fallback so an environment lacking the migration degrades instead of breaking.
