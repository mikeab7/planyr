### B561 — Site→Schedule switch is buggy: flashing, placeholder name, raw id, false "newer version" banner `[Cross-module / Schedule]` (bug — regression in B493)  *(owner-dropped 2026-06-29 — "switching from the Pappadoupolos site plan into the schedule is super buggy… flashing between the name and 'pick a site'… it gave the project a random name that was just letters and numbers… and it says a newer version was saved on another device which isn't true"; minted **B561** = highest real B# across both files (B560) + 1 — renumbered from a provisional B560 a concurrent `main` (header-selector consolidation) took)*
`[x]` **DONE + headless-verified the same session. lint 0 errors · 1793 tests green · build green · `ui-audit/verify-cross-module-link.mjs` 11/11 (4 new anti-regression checks).** Four symptoms, ONE root cause in the B493 cross-module wiring (`src/workspaces/scheduler/Scheduler.jsx`):
- **Flashing (whole screen + top-left name) = a two-effect feedback loop.** The *carry-in* effect (route→iframe: `planar:nav-select-by-site`) and the *sync* effect (iframe→route: `onProjectChange(linkedSiteId)`) fought each other: arriving on site A while the iframe's last-active schedule was linked to a different site B made the sync effect rewrite the route to B, which re-fired the carry-in toward A, which re-fired the sync toward B… every `onProjectChange` → `navigate()` → hashchange re-rendered the whole workspace → flash. **Fix:** the sync effect now only adopts the iframe's active link into an **empty** route (`projectId == null`) — provably loop-free (once set, it's inert; it never overrides a routed project). A user switching schedules in the breadcrumb still carries up, via a one-shot `selectSchedule()` (wired to `onSelectProject`), not a reactive effect.
- **Placeholder "Select a project" for ~2 s = no last-known-good.** The breadcrumb read only the iframe's nav-state (empty until the iframe boots). **Fix:** when the route carries a project, the crumb shows the schedule linked to it OR the routed project's real name as last-known-good — never the iframe's transient active schedule (which may belong to a different project mid-carry-in).
- **Random letters/numbers as the name = the raw `group_id` leaking.** `routedSiteName` fell back to the raw `projectId` when the site list wasn't warm, and that string was shown AND posted as the created schedule's `name`. **Fix:** the name resolves to a real name only (no id fallback); the resolution panel + its Create action are gated on a resolved name, so a schedule can never be shown/created named a group_id (`LinkSchedulePanel` also disables Create defensively).
- **False "a newer version was saved on another device" = a self-conflicting save burst.** The oscillation/redundant carry-in fired a burst of `setData` in the embedded app → overlapping auto-saves → the scheduler's optimistic-save guard (`cloudRev > knownRev`) tripped against the tab's OWN in-flight write. **Fix:** the `planar:nav-select-by-site` handler (`public/sequence/index.html`) no-ops when that schedule is already active — no needless `setData`/save — and killing the oscillation removes the burst.
- **Files:** `src/workspaces/scheduler/Scheduler.jsx`, `src/workspaces/scheduler/components/LinkSchedulePanel.jsx`, `public/sequence/index.html`.
