### B2417216 — Select parcels: show lot outlines from further zoomed out, without hammering county servers `[Site Planner / Map: Select parcels]` (feature) #site-planner #gis #parcel #perf  *(owner-approved design, mockup reviewed 2026-10-22; NEW-1 of the owner chat block)*

`[x]` **Three stages from each source's own cutoff** (Davidson 17, Rutherford 16, Harris 16, Dougherty 14 — "close" is today's behaviour, untouched): **mid** (cutoff−1) = lots ≥ 0.2 ac, parcel-ID labels on the lots ≥ 0.5 ac; **wide** (cutoff−2, never below zoom 12) = lots ≥ 0.5 ac, simplified lines, no labels. The selected lot is its own always-drawn highlight (unchanged). The bottom hint says what is held back ("Showing larger lots. Zoom in for small lots and labels."), and "The parcel server is busy — showing the lots already loaded." while a county is backing off. No auto-zoom; parcels-on-top untouched. Thresholds: 0.5 ac is the owner's house-size cutoff — measured on Nashville (Davidson, 1400×850 view): 0.5 ac keeps 892 of 9,323 lots at z15 and 274 of 2,254 at z16; a typical Katy house lot is 0.14 ac (HCAD sample: 6,000–6,300 ft²) so it is hidden at both stages; 0.2 ac for mid hides those too while keeping the larger suburban / small-commercial lots.
`[x]` **Built to shed county load, not to hide after download** (`parcelWideRequest.js`, `parcelWideEngine.js`, `parcelWideLayer.js`):
  - **Size filter in the request**: a `where` on the source's VERIFIED GEOMETRIC area column (`Shape__Area >= 21780` at wide, `>= 8712` at mid); a tile that still hits the record cap is re-asked with the cutoff ×4 (twice at most), the partial answer staying drawn.
  - **Generalised geometry**: `maxAllowableOffset` = half a pixel at the tile's bucket zoom, `geometryPrecision=5` (measured on Harris: 39,006 → 8,733 vertices for the same tile).
  - **Fixed tiles keyed to a zoom bucket** (512 px, alphabetical params) through the existing relay `/api/gis-cache/svc/<b64>/query` — each tile is fetched from the county once and served to every user from our cache. Relay fixes found while wiring it: an ArcGIS 200 `{"error":…}` body is never stored (it would have been served to everyone for 24 h), and a /query key is 64-bit (`cacheKeyStrong`) because a 32-bit hash collision would put another tile's lots in this tile's place; imagery keys are unchanged. A 404/400 relay falls back to the county directly.
  - **No requests while moving** (250 ms debounce after the last view change), **tiles that left the view are aborted** (the query worker now honours `{type:"abort"}`), **≤ 3 in flight per source**, **429/5xx/network → exponential back-off 2/4/8/16 s** (several in-flight failures count once), retried tiles park after 4 attempts and a refused (non-transient) tile is never retried; LOUD telemetry `parcel-wide-tile-failed` once per source per session.
  - **Snapshots**: Chambers/Waller's in-memory saved copy, when loaded and the source has a verified column, serves the tiles with zero requests. (Neither has a verified column today, so both keep their current cutoff.)
  - **One metadata read per layer** (memoised `layer.metadata`) replaces one per consumer.
`[x]` **Which sources get the wide view — data, not a guess** (`parcelAreaFields.js`, generated by `scripts/probe-parcel-area-fields.mjs`): each source's geometric area column is sampled (~60 lots) and its unit proved against the lot's own geodesic area (ft², m², acres, Web-Mercator m²/ft²) before it is trusted. Run 2026-10-22: **873 distinct layer URLs → 473 verified (521 county/composite keys), 400 not** (kept at today's close-in cutoff, each with its reason in the file): 369 are hosts this build sandbox cannot reach (e.g. Mississippi MARIS, Bartow/Cobb GA, Chambers' Pandai host, Shelby/Hamilton TN) — re-run the script from a network that reaches them; 13 publish no geometric area column (e.g. TN statewide — appraisal acreage is 0 on real big lots, so it is deliberately not used); 10 have an unrecognised unit; the rest failed a sample/filter test. Named counties: Davidson, Rutherford, Dougherty (`Shape__Area` ft²) and Harris (`Shape.STArea()` ft²) all verified.
`[x]` **Measured against the live county servers** (`ui-audit/measure-wide-parcel-requests.mjs`, 1400×850 view, 20 Culvert St Nashville; "today" = the shipped build, which draws nothing and sends 0 requests there; "lowered" = the cutoff simply lowered, i.e. every lot downloaded and hidden on the client): **Davidson z15 (wide): 8 requests / 694 KB on the wire / 16,438 lots (one answer truncated by the county's cap) → 8 requests / 95 KB / 1,966 lots (−86% bytes, −88% lots)**; Davidson z16 (mid): 6 / 133 KB / 3,056 → 6 / 40 KB / 824 (−70%). Rutherford z14: 12 / 250 KB / 5,975 → 12 / 163 KB / 3,449; z15: 53 → 45 KB. Harris (Katy) z14: 12 / 351 KB / 10,026 lots with **10 of 12 answers truncated by the county's 1,000 cap** → 12 / 339 KB / 6,252 lots, none truncated (same bytes, but complete); z15: 277 → 188 KB (7 truncated → 0). Dougherty z12: 429 → 364 KB, 12 → 14 requests (2 tiles re-asked); z13: 713 → 543 KB, 6 → 11 requests (5 re-asked). **Honest reading:** a COLD view sends about the same number of requests as the old cell query (fixed tiles ≈ the same grid); the saving per cold view is bytes and county rows (large in a dense city, small where the lots are already big), and the real county load falls because every tile after the first user's is served from our cache and a pan re-asks only the tiles it has not got (settled-pan arm: 4 of 6).
`[x]` **Real counties, real browser** (`ui-audit/verify-parcel-wide-live.mjs`, run against the built app — no relay in `vite preview`, so tiles fell back to the county directly; the answers are the county's own): every named county passes close/mid/wide/back — the close stage receives house lots (known-good arm: 0.006 / 0.147 / 0.003 / 0.000 ac smallest), the mid and wide answers carry the size where-clause + generalised geometry, **98% of every answer's lots are ≥ 0.55 × the stage cutoff** (lowest 2nd percentile 0.196 / 0.212 / 0.196 / 0.205 ac at mid, 0.505 / 0.498 / 0.503 / 0.458 ac at wide; the 0.55 allowance is because the outlines come back generalised — an ungeneralised sample of Dougherty's own service at the 0.2 ac cutoff measured 0.195–0.2 ac), the hint reads "Showing larger lots…", and zooming back in brings the small lots and removes the hint. Bytes in that run (one view each): Davidson close 272 KB / 894 lots → mid 45 KB / 824 → wide 72 KB / 1,251; Rutherford close 149 KB → mid 52 KB / 1,205 → wide 155 KB / 3,147; Harris (Cypress/Katy) mid 8,023 lots / 1.06 MB over 34 answers (the county's 1,000-record cap forces re-asks) → wide 207 KB; Dougherty mid 645 KB / 17,464 lots → wide 1.0 MB / 25,272 lots (the wide view of a flat 45 km-wide county view is heavy; a 2,000-record tile re-asks at ×4).
`[x]` Look checked on screenshots (Nashville z15.5/16.5/17.4, north Harris z14.5/15.5/16.4): warehouses and tracts outlined with labels at mid, residential subdivisions blank at mid/wide, full detail back at close. Known characteristic, not a bug: a tile that overflows the county's record cap is re-asked with a tighter cutoff (×4, twice at most), so in a very dense tile the lots shown are the larger ones and the hint says "larger lots"; Harris' 1,000 cap triggers it most.
