- **Prerequisite confirmed, not assumed:** `index.html`'s `<meta name="viewport">` already carries `viewport-fit=cover` (present before this session — the mobile-pinch-fix script and the boot watchdog both predate it). Without this, every `env(safe-area-inset-*)` call resolves to 0 and the whole fix would be inert; it was checked first, and no change was needed there.
- **Fix 1 — safe-area insets reach the control's own offset math as NUMBERS, not CSS-only.** New `src/shared/ui/safeAreaInsets.js`: a hidden probe element (`[data-safe-area-probe]`) whose padding is set from `env(safe-area-inset-*)`, read back via `getComputedStyle` (`env()` has no JS-readable form of its own). Every other safe-area consumer in this app (Food's `BottomSheet.jsx`, B1168128's Site Planner FABs) writes `env(...)` straight into a CSS string, which is the right, simpler answer for a FIXED literal offset — this control's offset is DYNAMIC (`cornerClearanceFromBottom` measures real occupants — Leaflet's controls, the Site Planner's narrow-width FAB stack — and clears whichever needs the most room), and that occupant-overlap math runs in JS against `window.innerWidth`. A CSS-only `calc()` would position the button correctly but leave the overlap math blind to the inset — in LANDSCAPE, where `safe-area-inset-right` is genuinely non-zero (the notch/dynamic-island rotates to a side edge), the column the button occupies would be computed as if flush against the true edge when it is actually shifted in. `HelpReportControl.jsx` now folds `safeAreaInsets().right`/`.bottom` into `cornerClearanceFromBottom`'s `right`/`base` params before the overlap check runs, for both axes.
- **Fix 2 — re-measure on `visualViewport` `resize`/`scroll`, not just `window` `resize`/`orientationchange`.** iOS Safari's collapsing bottom toolbar changes the VISUAL viewport without firing a plain `resize` on `window` (the layout viewport is unchanged) — the existing 500ms poll would eventually catch up, but the listeners make it immediate. Both listeners are added/removed alongside the existing ones in the same `useLayoutEffect`, guarded on `window.visualViewport` existing.
- **Item 3 (popover fit) — verified, not rebuilt.** `AnchoredMenu`/`placeMenu`'s existing viewport clamp (an 8px margin on every edge) already prevents horizontal overflow for this menu's 280px width down to 320 CSS px (iPhone SE) — confirmed empirically at 320/375/393/430 rather than assumed from reading the clamp math. No code change was needed for this item.
- **Item 4 (tap target) — unchanged, confirmed not shrunk.** Still 44×44 (`FAB_SIZE`), asserted by the harness at all three named devices.
