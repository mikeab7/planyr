- **Model:** the defaults are **stamped at creation** (not resolved at render) — matching the panel's literal "Defaults for new elements" wording, so changing a default only affects parcels drawn *afterward*. This deliberately differs from the element `typeStyles` render-fallback because a parcel's fill is optional and stores `null` for "explicitly off"; a render-time `??` fallback would collide "off" with "unset". A duplicated / merged / split / imported-that-preserves parcel copies its source style and never stamps.
- **New pure export `parcelDefaultStyle(settings)` in `lib/planStyle.js`** (Node-tested, `test/parcelDefaultStyle.test.js`, 8 cases): returns only the style keys the user actually customized in `settings.parcelStyle`, so an untouched default leaves the parcel to the theme-aware built-in render fallbacks (no stroke → the theme's parcel color; no weight → 2; no dash → solid; no fill → unfilled). Fill is opt-in — `fillOpacity` rides along only with a fill color; `dash:"solid"` and `fill:null` are treated as "not customized".
- **Wiring (`SitePlanner.jsx`):** new `settings.parcelStyle` (default `{}`) + `setParcelStd` (settings-only, RC-6 not-undoable). The Standards → Parcels controls mirror the parcel inspector's Outline/Weight/Style/Fill controls but write to `parcelStyle` (color swatches use `livePick(…, false)` — no dead undo frame). Every fresh-parcel creation site spreads `parcelDefaultStyle(settings)`: `closePoly` (draw), `addRectParcel`, `importFeature` (county lookup), `parcelsFromRings` (identify-a-lot). Merge/split/duplicate untouched (source-style-preserving).
