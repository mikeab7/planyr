- **DESIGN DECISION 1 — per-TYPE default + per-ELEMENT override (both, not either/or), because the brief asked for an explicit recommendation.** Recommended and shipped: styling defaults off `easeType` (so every pipeline easement in a drawing set looks alike out of the box — what a real plan set wants), and any individual easement can override fill/stroke/fillOpacity/hatch independently (so a specific conflicting or sensitive easement can still be called out). This exactly mirrors the precedent `planStyle.elStyle` already set for elements (`el.fill ?? base.fill`) rather than inventing a third styling shape — a consistency argument, not just convenience. Owner can override to type-only or per-element-only by saying so; the "↺ Reset to type default" button in Properties is the undo path either way.
- **DESIGN DECISION 2 — status (existing/proposed) does NOT get a new appearance channel, and its existing effect is UNCHANGED.** It already drives ONE thing today — proposed easements dash their outline, existing ones are solid — and that predates this work. Flagged explicitly for the owner: several drafting offices use the OPPOSITE convention (existing = dashed/hidden-line since it's often buried and unconfirmed by this survey, proposed = solid/definite). Deliberately left as-is rather than flipped, because flipping it would silently re-style all 26 production easements (100% currently `status:"existing"`, i.e. all solid today) with no user action taken — that read as too large a silent visual change for a session that wasn't asked to touch status semantics. It is a one-line change (`SitePlanner.jsx`'s `proposed ? dashZoom(...) : undefined` on the easement polygon) if the owner wants it flipped. Fill/hatch/colour are NOT status-driven — status stays a pure dash cue, appearance stays purely type/override-driven, so the two questions ("what kind of easement" and "is it built yet") don't compete for the same visual channel.
- **DESIGN DECISION 3 (asked for explicitly) — encumbrances (`kind:"encumbrance"`, the metes-and-bounds deed/title objects, e.g. Grand Port's `e1454610zupcbv`/`e1454611zupcbv`) share the identical appearance model.** They already carried `fill`/`stroke`/`fillOpacity` fields (stamped at creation in `buildEncumbranceMarkup`) that the renderer silently never read for `fill`/`fillOpacity` (only `stroke`/`weight`/`dash` were live) — dead data on every encumbrance ever drawn. Wiring those two fields up is a DISCLOSED SIDE EFFECT: Grand Port's two encumbrances already carry non-default `fillOpacity` (0.14 / 0.10 for the except-hole) from creation, so they will now show a faint colour wash matching their own outline colour that they did not show before. Judged as "the feature the stored data always implied and never got wired to" rather than a regression, and flagged here for the owner to weigh — reversible in one line (`ENCUMBRANCE_DEFAULT.fillOpacity` in `easements.js`) if he'd rather it stayed off until touched.
- **IMPLEMENTATION.** New shared, reusable primitive (built generically on purpose, per the brief's "consider whether it should extend to other element types" — only easement/encumbrance are WIRED to it this session, nothing else touched): `src/shared/style/hatchPatterns.js` — a pure hatch catalog (none/diagonal/diagonalReverse/cross/horizontal/vertical/dots) as tile specs, no JSX. `src/workspaces/site-planner/lib/easements.js` gains `easementStyle(e)`/`encumbranceStyle(e)` resolvers (type default, per-element override, `hasOverride` flag) and `easementPatternId`/`encumbrancePatternId` (shared type pattern id when unedited, a per-element id once styled — keeps pattern count bounded to types + actually-edited easements, not one per easement). `SitePlanner.jsx` gets ONE generic `HatchPatternDef` module-scope renderer (MODULE-SCOPE-COMPONENTS) that replaces the old hand-authored per-type `<pattern>` blocks with byte-identical output, plus dynamically-rendered per-element override patterns (only for easements/encumbrances a user has actually styled), plus new Properties-panel fields (Fill color / Fill opacity / Hatch / Outline color / "↺ Reset to type default") for both the easement panel and a new encumbrance-specific block in the generic markup panel.
- **HATCH SCALING WITH ZOOM (asked for explicitly).** Every hatch tile — type-default AND per-element — is defined in constant SCREEN-PIXEL space (`patternUnits="userSpaceOnUse"`, no scale ancestor reaches it, because the planner projects feet→screen px before drawing rather than scaling an SVG group) — the exact same technique every pre-existing pattern in this app already uses (`pat-berm`/`pat-trailer`/`pat-sidewalk`/`pat-landscape`). This means a hatch tile's apparent size never changes with zoom: it cannot coarsen into a solid block zoomed in or thin into aliased mush zoomed out, by construction.
