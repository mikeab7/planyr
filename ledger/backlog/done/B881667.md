### B881667 — Unknown project sub-route shows the false "your tab is out of date" banner and never redirects `[App shell / routing]` (bug) #site-planner #ui #infra  *(owner live repro on planyr.io, 2026-08-30, AFTER PR #1232/#1234 merged, on a hard-reloaded tab explicitly confirmed to be on the new bundle: navigating to `#/project/<id>/review` (the real Review route is `/markup` — `/review` has never existed in any build) showed the "That part of Planyr is newer than the copy this tab has open — reload to get it." banner, the Site tab rendered underneath, and the URL kept reading `/review` forever. `[x]` **ROOT-CAUSED + FIXED at the source + mutation-proven in the sandbox, sweeping the whole class of bad aliases, not one string.**
- Verify: sandbox — deterministic route-parsing logic with no timing/GIS/real-project-data dependency; the genuine-skew counterpart case is proven in the same harness.
- **ROOT CAUSE.** `shouldOfferReload` (`buildSkew.js`) treated a route miss (`unknownModuleSlug`) as sufficient on its own to show the reload banner, with **no check against the actual served build** — conflating two things that look identical from the inside: a slug shipped in a build newer than this tab's (a reload genuinely fixes it) and a slug that never existed in ANY build — a stale bookmark, an old shared link, a renamed route (no reload can ever fix it, because even the newest build still won't recognize it). Separately, the resolved fallback route was never written back to the address bar, so a bad link stayed in the URL bar forever even though the Site tab correctly rendered underneath it.
- **THE FIX, two parts.** (1) `shouldOfferReload` now requires **confirmed** build skew (`isBuildSkewed(loaded, served)`) before a route miss shows the banner at all — the same evidentiary bar every other reason in that function already meets, per its own "silent when it cannot know" contract. (2) Shell.jsx fires an immediate `/version.json` check the moment a route miss is seen (rather than waiting up to 20s for the routine poll), and once that check **proves** this tab is already current, corrects the visible URL to the resolved fallback route via `history.replaceState` — but **only** once skew is ruled out, so a genuine "newer build" deep link is never silently discarded before the user gets a chance to reload into it. On genuine skew the banner still shows and the URL is deliberately left untouched (a reload must still land on the real link).
- **PROVEN RED before the fix, per house rule.** New `ui-audit/verify-unknown-subroute.mjs` sweeps four aliases (`/review`, `/docs`, `/files`, `/plan` — the class, not the reported string) against the REAL, already-served `/version.json` (no faking needed — the build genuinely is current): no false banner, URL self-corrects to the project's Site tab, the Site Planner renders the routed project. A separate case serves a deliberately different build id via route interception: the banner DOES show, names `route-miss`, and the URL is left untouched. `git stash`-ing the fix and rebuilding reproduces the pre-fix defect exactly — all 4 aliases show the false banner and never correct the URL (8 assertions red).
