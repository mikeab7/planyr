`[x]` **FIXED, deployed to production, and independently re-verified three separate ways in this same session.** `src/workspaces/site-planner/db/purge_one_deleted_plan.sql` precondition 1 read `auth.uid()` inline, three times, inside `if not (v_row.user_id = auth.uid() or (v_row.team_id is not null and is_team_admin(...)))`. With no JWT, `auth.uid()` is SQL NULL; `v_row.user_id = NULL` evaluates to NULL rather than false, the whole `or` chain lands on NULL, and plpgsql's `if not (NULL) then` never runs the refusal body — an unauthenticated `/rest/v1/rpc/purge_one_deleted_plan` call sailed straight through every precondition into a genuine, permanent `DELETE` (cascading to `site_elements` via its `ON DELETE CASCADE`).
- **THE FIX, two independent layers, both shipped (defense in depth):**
  - **(a)** Hoisted `auth.uid()` into a local `v_uid` and added an explicit **precondition 0** — `if v_uid is null then raise exception 'purge_one_deleted_plan: not signed in' using errcode = 'PLYR2'; end if;` — running BEFORE precondition 1's ownership disjunction. This is the exact pattern this codebase's other owner-checking `SECURITY DEFINER` functions already use (`set_plan_lock`, `soft_delete_site_plan_overlay`, `share_project`, `revoke_share`, `site_plan_overlay_comp_points`, `commit_site_plan_overlay_placement`).
  - **(b)** `revoke execute on function public.purge_one_deleted_plan(text) from public, anon;` (re-granting only `authenticated`) — independent of (a). Supabase grants EXECUTE to `anon` directly on a newly created function (not merely via `PUBLIC`), which is what had left the deployed grantees as `PUBLIC, anon, authenticated, postgres, service_role` despite the file only ever granting `authenticated`.
- **AUDIT-FIRST — independently swept every `SECURITY DEFINER` function in the repo for the same shape** (28 functions across 24 files, every body read in full — not sampled). Confirmed `purge_one_deleted_plan` was the ONLY instance of an `auth.uid()`-inside-a-disjunction refusal with no prior NULL guard. Ten functions already use the safe hoisted-guard pattern; fourteen more are structurally fail-closed on a NULL uid by construction (an `EXISTS(...)` returns false rather than NULL; a `WHERE col = auth.uid()` matches zero rows rather than erroring), so they were never at risk from this shape. `guard_overlay_object_release()` — a suspect the dispatch itself named — is confirmed NOT vulnerable: its `v_uid` is used only inside a message-REDACTION `CASE`, the actual refusal (`if n > 0`) is wholly independent of it, and it is a trigger function with no direct `/rest/v1/rpc/` path at all. Two non-vulnerable hardening opportunities were found and are deliberately left unactioned here (out of scope — zero-risk hygiene, not a fix for anything broken): four functions (`list_team_members`, `claim_team_invites`, `folder_set_drive_meta`, `can_read_shared_review_file`) rely on structural fail-closed behaviour with no *explicit* `revoke ... from anon` stated; adding one to each is a follow-up, not filed as its own B# since DEDUPE-FIRST found no live risk behind it.
