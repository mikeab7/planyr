### B2584320 — A NEW organization workbook never uploaded its edits to the cloud until the page was reloaded `[Spreadsheet]` (bug) #sync #testing  *(found 2026-10-30 by the live save-path check V2033376 — org arm O1b; reproduced in the REGULAR grid, so not a Univer defect)*
`[x]` **✅ DONE — merged (PR #2751, build `d9a0082`) and PASSED live 2026-10-30 (V2033376 run 2, O1a–O1c).** Repro (planyr.io, test account, both grids): Organization ▸ Spreadsheet ▸ "+ New workbook", type a value, wait. The `org_model_sheets` row stays at version 1 with empty cells forever; reload and it works.
- **Root cause (read off the network log, not guessed).** `onOrgCreate` opened the workbook AND fired the first cloud insert in the same breath. The open-time load (`GET org_model_sheets?id=eq…`) ran before the insert landed, got `[]` (ok, no row) and left `cloudVersionRef = null`. The first edit's push therefore carried `expected == null`, which `orgContentRow` turns into an INSERT — and the row already existed: `409 duplicate key value violates unique constraint "org_model_sheets_pkey"`. Every later push repeated it. A project workbook is unaffected (its row is made on open by a different path); an EXISTING org workbook is unaffected (the load finds its version).
- **Fix.** `onOrgCreate` (async, with a re-entry guard) awaits the create's cloud answer first and opens the workbook on it — success, refusal (said out loud by `applyOrgOutcome`) or a thrown save (opens the local copy anyway). The open-time load then finds version 1 and the push is an ordinary compare-and-set update. Guard `test/modelOrgCreateOpensAfterInsert.test.js` (red against the old order: 3/3 fail).
- **Why it matters to the Univer cutover:** the owner's standing rule is that changes always upload; for a brand-new organization workbook they did not, in either grid, and the only symptom was a 409 in the network log.
- **Owner constraints:** none contradicted.
- Verify: live — a cloud-sync race on the real deploy (mandatory LIVE-VERIFY class). `Blocker:` none. Check = O1b of `ui-audit/verify-univer-save-live.mjs` (V2033376): edit in Univer inside the debounce window, back to the list, the org row holds the edit.
- **Stopping rule:** closes when V2033376's O1a–O1c record a dated PASS on the served build named in the same call.
- **Live result (2026-10-30, planyr.io build `d9a0082`, same run as the assertions):** a new organization workbook, edited in the Univer grid and left inside the save delay, now has the edit in its `org_model_sheets` row (was: version 1, empty cells, 409 on every push); reloaded, it shows the same value. Stopping rule met.
