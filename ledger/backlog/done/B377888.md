- **THE MEASURED INCIDENT.** Two tabs on plan `smsdrvzr9gzx`. Tab A created a building assembly (host + 2 truck courts + 2 trailer rows). Tab B held a delete formed before those ids existed. Tab B's delete lost its CAS and `elementSync.js`'s *"delete WINS — re-issue at the fresh rev"* branch stripped the stale rev and re-issued against the NEW rows: at **13:38:49.543–546 three deletes were re-applied to rows 1.75 s old**, and `e1454940cgzlnc` and `e1454943cgzlnc` died.
- **⛔ THE RULE, and why "delete wins" is right and was still wrong here.** Delete-vs-EDIT is two writers disagreeing about a row that EXISTS, and removal is the less recoverable intent, so it is the one that should not need re-doing. Delete-vs-CREATE is not that: the delete is a decision about a row that no longer exists, and re-issuing it kills something it was never about. **A delete whose base rev predates the row's creation must be DROPPED, not re-issued.**
- **⛔ AND THE SIGNAL IS NOT THE ONE THE REPORT NAMED, which is worth recording because it changes the fix.** There is no `created_at` on `site_elements` and the RPC returns none, so "predates the row's creation" cannot be read off the wire. Two client-side observations replace it, and the SECOND is the one that catches the measured case:
  - **BY REV / BY CLOCK** — the tab saw the element come into existence (a live row for a key its shadow had never held) at a rev above, or a moment after, the one the delete targets. Recorded BEFORE the pending branch in `applyRemoteRow`, because the case that matters is precisely the one where a delete for that key is already queued.
  - **⛔ BY PROVENANCE — the diff INVENTED the delete.** `reconcile` mints a delete for exactly one reason — the shadow holds an element and the collections do not — and it cannot tell "the user deleted this" from "a row arrived from another tab and never reached the canvas". `applyRemoteRow` writes the shadow entry ITSELF, so if the upsert it returns is dropped on the way (a snapshot applied over it, a gesture buffering it, a remount) the next diff issues a delete for an element this tab NEVER HELD. That delete's base is not stale — it has no base at all. Such a key is tracked until a diff proves the canvas has genuinely shown the element; until then a delete for it is refused and the row is handed BACK to the canvas instead.
- **THREE SEAMS, because one was not enough and the reason generalises.** The conflict-result branch is the obvious one. **`opFor` sends a delete at the shadow's CURRENT rev, not the rev it was formed against** — so a delete whose shadow was advanced by `applyRemoteRow` while it sat queued does not lose its guard at all: it goes out expecting exactly the row that was just created and **the server ACCEPTS it, in total silence, with no conflict anywhere.** So the question is asked (a) in the DIFF, (b) before the op is BUILT, and (c) after a refusal. The unload keepalive is filtered too — it has no result handler, so a delete that lands there is unobservable by construction.
