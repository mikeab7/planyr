- **CONFIRMED/REFUTED, per the owner's own ask: related trigger, DIFFERENT mechanism from B850432 — write ONE fix here, a separate one there, per the code path each actually runs.** `suggestPlacement` (`MapFinder.jsx`) sizes a fresh overlay to `0.6 × the CURRENT map viewport's real-world width` with no floor or ceiling (`overlayGeoref.js`'s `suggestFtPerPx`) — so opening the upload flow while the map sits at ANY extreme zoom (the empty-account landing view, or simply wherever the map was last left) scales the plan to match, however absurd. That is genuinely the root of NEW-2's giant number. **It is NOT, on its own, why NEW-1's overlay never painted** — that is a separate, silent zoom GATE (`SITE_PLAN_MIN_ZOOM = 15`) that hides every overlay below a real building-scale zoom regardless of its size; a same-order-of-magnitude wide viewport triggers BOTH defects at once (which is why they were reported together), but a small image placed while merely zoomed a few levels too far out would still hit B850432's gate while never triggering this one. Confirmed by reading both code paths independently — `visibleSitePlanOverlays`'s zoom filter runs in `MapFinder.jsx` and has nothing to do with `suggestFtPerPx`'s math.
- **The fix.** `overlayGeoref.js`'s `suggestFtPerPx` now clamps the suggested overlay WIDTH into `[OVERLAY_SUGGEST_MIN_WIDTH_FT (150), OVERLAY_SUGGEST_MAX_WIDTH_FT (3000)]` regardless of the live viewport — a site plan or broker flyer is realistically a couple hundred to a few thousand feet across, never a sliver of a foot and never tens of miles. A viewport-derived width already inside that range (the ordinary case — the user is looking at roughly the right area) passes through completely unchanged; only a genuinely extreme viewport gets clamped. "Move / resize" still lets the user scale the plan to whatever the real drawing needs — this only fixes the STARTING guess.
- **Verify: sandbox** — pure math, deterministic, no browser/auth needed to prove it.
- **Self-verified:** `test/overlayGeoref.test.js` — 3 new cases (an absurdly wide viewport clamps to the max width; a tiny viewport clamps to the min width; an already-plausible viewport passes through untouched, `toBeCloseTo` the pre-fix formula) alongside the 2 pre-existing `suggestFtPerPx` cases, all passing unchanged (the clamp bounds were chosen wide enough that neither existing assertion's inputs fall outside them). Reproduced the reported number directly: `suggestFtPerPx(1_037_243, 800)` (the owner's implied viewport width, back-solved from his reported 622,346 ft ÷ 0.6) now returns a width of exactly 3000 ft instead of 622,346 — 800×600 renders at 3000×2250 ft, a plausible large-flyer size. `npx vitest run test/overlayGeoref.test.js` — 25/25 green. `npm run lint` on the touched file — 0 errors.
