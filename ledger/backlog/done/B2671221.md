### B2671221 — Review tabs never reach the account: `srcKeyOf` joins name and size with a NUL (`\u0000`) and Postgres rejects it, so the whole `profiles.prefs` write 400s `[doc-review]` (bug, HIGH) #doc-review #persistence #sync

*(Recurrence of B2058144 — found by AUTH-SWEEP 4, V1476304, 2026-11-11. DEDUPE-FIRST: grep of Open/⏳Verify for reviewTabs/tabSync/22P05/u0000 found only B2058144 and B2080752. The hermetic harness `verify-review-tabs-sync.mjs` hides it because its fake Supabase never enforces jsonb's no-NUL rule.)*

- Verify: live (PASSED 2026-11-11, see AUTH-SWEEP 4 re-check note below)
- **Observed (build 47040a4, chunk `DocReview-DWfA5qZb.js`, signed in as `e2e@planyr.test`, desktop Chromium + WebKit emulated iPhone descriptor):** Review › Open… three files → three tabs, page/zoom remembered, reload restores them from the LOCAL copy (all fine). But `profiles.prefs.reviewTabs` on the account stays `{tabs:[], at:<old>}` forever: every push is `POST /rest/v1/profiles` → **HTTP 400** `{"code":"22P05","message":"unsupported Unicode escape sequence","details":"\\u0000 cannot be converted to text."}`. A second device (fresh WebKit emulated iPhone context, same account) therefore opens Review BLANK.
- **Root cause hint:** `src/workspaces/doc-review/lib/reviewTabs.js` line 42 `srcKeyOf = (name,size) => \`${name}\u0000${size}\`` — that string is stored in each tab's `srcKey`, and `syncTab`/`buildSyncDoc`/`serializeTabs` copy it into the pushed doc. jsonb cannot hold `\u0000`. Because the push upserts the WHOLE `prefs` object, the 400 also blocks any other pref written while a disk-opened tab is open (check `userPrefsStore` LOUD-FAILURE: no banner was seen). Fix shape: use a printable separator (e.g. `\u001f` is still a control char but legal in jsonb; safest `|` or `::`), or strip `srcKey` from the synced doc (it is only a local disk-pick de-dupe key) and migrate old local copies (`planyr:review:tabs:v1` already holds NUL keys; `findByRef` compares with the same literal).
- **Control (hand-written account copy with `srcKey:""`, test account's own prefs, reset afterwards):** the PULL side works — a fresh WebKit (emulated iPhone) context and a fresh desktop show the same 3 tabs, same active tab, same page/zoom, × only on the active tab, no page overflow; an unsaved .docx on the desktop survives the phone closing its tab. But a close/page change made on the phone (tabs it had opened from the account still get a NUL `srcKey` via `upsertTab`) never reaches the account, so steps 6–7 of V1476304 fail the same way.
- **Stopping rule:** closes when a tab opened from disk on device A (srcKey present) is written to `profiles.prefs.reviewTabs` (200/201, no 22P05), and a fresh second device shows it; guard: a test that runs `JSON.stringify(buildSyncDoc(...))` for a tab made through `srcKeyOf` and asserts no `\u0000`; extend the fake Supabase in `verify-review-tabs-sync.mjs` to 400 on `\u0000` so the hermetic arm can fail.

- **Re-confirmed 2026-11-11 on build `9a67d51`:** opening a single PDF from disk still POSTs `profiles` → 400 `22P05`; local `srcKey` = `"<name>\u0000<size>"`; the account copy stays `[]`.
