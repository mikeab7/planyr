`[x]` **ROOT-CAUSED AND FIXED THIS SESSION.**
- Verify: sandbox — fully reproducible headless, no auth/live-GIS/real-data dependency.
- **THE MECHANISM, confirmed live, not theorized.** `SheetView.jsx`'s grid container is the ONE `onKeyDown` handler for the whole sheet — the in-cell `<input>` has no listener of its own, so every keystroke, focused on the input or not, bubbles to this same handler. Typing the FIRST character of an entry (nothing being edited yet) is captured unconditionally via `startEdit`'s seed, which also mounts the input with `autoFocus`. Every character typed AFTER that is meant to land in the now-focused input's own `onChange` — but nothing guarantees DOM focus has actually reached the input by the time the next keystroke arrives (a slow-enough render, which naturally gets slower as a session accumulates more rows/undo history — exactly why the failure got worse, not better, over a session), and the container's `if (edit) {...}` branch handled ONLY Enter/Tab/Escape, silently dropping every other key on the assumption the input must already have it. When that assumption was wrong, the dropped keystrokes were gone outright, and `editValue` was left holding just the seed character — exactly what the next Enter committed.
- **PROVEN, both directions, in a real browser.** Built the app, opened a fresh project's Spreadsheet, pressed one real key (seeding `startEdit`), then dispatched the REST of an entry's keystrokes as `bubbles:true` `KeyboardEvent`s directly on the grid container (never touching/focusing the actual `<input>`) — reproducing, byte-for-byte, the exact race a slow render creates. Against unmodified `origin/main`: stored `"1"` for a typed `"123456"`. Against the fix: stored `"123456"` in full. Also confirmed the fix does not double-apply characters when the input IS properly focused (40-entry real-typing round trip, zero mismatches) and that a mid-entry handoff — some characters via the fallback, the rest via the now-focused input's own `onChange`, including a Backspace correction — round-trips correctly with no duplication.
- **THE FIX does not chase the render-speed race itself** (there is no way to prove that closed for every future slower render) — it removes the FAILURE MODE: a keystroke that reaches the container while a cell is mid-edit and the event's real target is not the in-cell input is now applied directly to `editValue` (insert / Backspace), exactly what the input's own `onChange` would have done with it, so it makes no difference to the user whether the input had focus yet. New pure module `lib/editorFallback.js` (`editorHasFocus`/`fallbackEditAction`/`applyFallbackEdit`), wired into `SheetView.jsx`'s `onKeyDown`.
- **Regression guard, in `test/` (not `e2e/` — `.github/workflows/e2e.yml` only runs on schedule/`workflow_dispatch`, so nothing there gates a merge):** `test/modelCellEntryFallback.test.js` unit-tests the fallback's decision table directly, then drives 40 consecutive cell commits through the REAL production path — `lib/editorFallback.js`'s own exports feeding `lib/sheetModel.js`'s real `commitCellText`/`applyToActiveSheet` — with every character of every entry routed through the fallback (the exact scenario measured live), asserting every one of the 40 stored values round-trips in full; a second case repeats it for the exact mixed content types measured (a rent, a vacancy rate, two formulas, a plain label).
