`[x]` **ROUND 2 IMPLEMENTED AND VERIFIED THIS SESSION. Disposition (STANDING RULE #2), by name: REPRODUCED IT AND FIXED IT.** Two real defects, both in `NoteEditor.jsx`'s page-width measurement effect, neither touched by round 1:
(1) **`matPadX` never shrank for "full."** Every NUMERIC pin (Narrow/Normal/Wide, a completed drag) correctly keeps the SAME natural (580-based) gutter regardless of the pane — that is deliberate, load-bearing, and what stops the page's left edge jumping (the "centring splits the width across both edges" defect NOTES-PAGE-GROWTH's round 2a already named and rejected). "Full width" is not like them: its entire point is the pane, and `resolvePresetPx("full", …)` already promises the frame fits with only a small margin — a promise the render broke by leaving the surrounding padding at the big natural size regardless. Fixed by deriving the gutter, for the "full" pin ONLY, from the SAME resolved width the frame itself commits to (`pinnedBase`) rather than a second, independent number: whatever room is left after the frame, split evenly, `Math.floor`'d so it can only ever under-fill (a stray pixel of invisible grey), never over- (a stray pixel of forced scroll). Below `resolvePresetPx`'s own floor (a pane too narrow for even Wide, B1566928) this correctly shrinks toward zero and the pane scrolls — the same already-accepted "the floor wins" behaviour Wide already has there, not a new one.
(2) **`paneWidth` was read on the scroller's border box (`offsetWidth`), not its content box (`clientWidth`).** `note-mat` scrolls vertically and its own bottom reach (`matExtraBottom`, B1344626) keeps a scrollbar present on nearly every note, consuming real horizontal space `offsetWidth` does not know about — measured live, `offsetWidth` 923 vs `clientWidth` 913, a 10px gap baked into every gutter calculation regardless of pin. A new `paneContentWidth` (the scroller's own `clientWidth`) is used ONLY for the two places that needed pixel-exact fit — the gutter above, and `pinnedBase`'s own resolution (`resolvePinnedBaseWidth(pageWidth, { paneWidth: paneContentWidth })`) — never for `naturalSheetWidth`, table/box-fitting, or the reach spacer's own `matReachWidth`, all of which keep reading the original `offsetWidth`-based `paneWidth` exactly as before; that measurement has its own already-documented feedback-loop history (this effect's own header comment) a fix for THIS defect has no business touching. Safe because `note-mat` is `box-sizing: border-box` (the app-wide reset): its `clientWidth` cannot be moved by the padding this same effect writes onto it, only by the flex layout or the scrollbar's own presence, neither of which this effect's output feeds back into — confirmed by re-running the full existing suite (drag/undo/reload/PDF-parity) with zero regressions.
