- **ROOT CAUSE, measured live, not assumed.** `MapFinder.jsx`'s `siteRow` renders a project's name in a flex row alongside up to two standing-fact flag chips ("no boundary", "no location," B845089/B1401952). The two chips were `flex:"none"` (refuse to shrink, ever); the name span had no `min-width` floor. With ONE chip visible this was survivable — the name still had most of a 232px-wide panel to itself — but B1401952 legitimately added the SECOND chip ("no location"), and on a row carrying both (exactly his own duplicated-ALUMAX pair: no origin set, no parcel drawn either), the two fixed-width ~71px/64px chips claimed essentially the whole row and every pixel of negative space fell on the name, which had nothing stopping it from shrinking to nothing. Measured live, real Chromium, this panel's real 232px fixed width: the name span rendered **2.1px wide — under one glyph** — reproducing the reported single-character clipping exactly. The filter row one line up has the identical shape: the sort `<select>`'s longest option ("Recently touched," the account's own default sort) was also `flex:"none"`, so it claimed the row and left the "Filter by name…" input only 71px, too narrow for its own ~91px-wide placeholder text — "Filter by n."
- **THE FIX — give the name (and the input) priority; let the secondary chrome shrink and degrade gracefully, never the other way round.** `src/workspaces/site-planner/MapFinder.jsx`:
  1. The name `<span>` gets an explicit floor (`NAME_MIN_PX = 64`) it is never squeezed below, on `flex: "0 1 auto"` — shrink is now bounded, but **grow stays 0, unchanged from before this item** (see the CI-caught correction below for why that distinction matters).
  2. The two flag chips move into their own shrinkable wrapper (`rowFlagGroupStyle`, `flex: "0 1 auto", minWidth: 0, overflow: "hidden"`) and `rowFlagBadgeStyle` itself changes from `flex:"none"` to `flex: "0 1 auto", minWidth: 0` plus its own `textOverflow: "ellipsis"` — so under real pressure a chip shortens to a legible ellipsis stub ("n…", full text still on hover via its existing `title`) rather than either refusing to yield (the defect) or the name being the one that collapses.
  3. Same shape, one row up: the filter `<input>` gets its own floor (`FILTER_MIN_PX = 112`, sized to its measured placeholder text width + padding) and the sort `<select>` beside it drops `flex:"none"` for `flex: "0 1 auto", minWidth: SORT_SELECT_MIN_PX = 96` + `textOverflow: "ellipsis"` (see the correction below for why the select needed its OWN floor, not just permission to shrink, and why both option labels needed shortening too).
  - **What the panel does at its narrowest, stated rather than assumed.** The panel is NOT user-resizable — it has exactly two states, a fixed 232px open width on desktop (`MapFinder.jsx`'s `map-sites-panel`) and a collapsed chip; on phone/narrow it's `min(320px, calc(100vw − 16px))`, always wider than the 232px desktop case and never narrower. At every width the app actually renders, the name floor now guarantees it never reaches zero characters; measured on the reported 2-chip case the name still gets 80–140px of real width across every width tested (see table below) — the floor is a backstop that isn't even the binding constraint in the reported scene, because natural proportional flex-shrink already leaves the name with more than its floor once the chips have given up their share.
- **⛔ CORRECTED, same session, CAUGHT BY THE REAL CI RUN'S VISUAL-REGRESSION GATE — not by sandbox re-reading. Two distinct mistakes in the first push, both found the same way: a diff the sandbox could not reproduce (no CI-pinned Chromium here — see B1026272's own header in `ui-audit/visual-regression.mjs` for why that specific browser build is load-bearing and not swappable), read from the failed run's own log and pixel-diff report, then fixed by REASONING about the exact flex math rather than by guessing.**
  1. **The name span's `flex-grow` was wrongly set to 1 (`"1 1 auto"`) in the first push.** The intent was "the name should win the space," but flex-GROW and the shrink FLOOR are different properties, and only the floor was the actual fix this item needed. With grow:1, the name grows to fill any unclaimed space in its row on every ORDINARY (unsqueezed) row too — pushing its own flag chips visibly away from it, widening the gap between the name text and its chips on rows that were already correct before this item. The Dashboard's `map-landing` visual-regression baseline (zero Sites rows seeded — this surface can never be about squeezing) still failed, which is what proved the defect wasn't a squeeze case at all. Fixed: `flex: "0 1 auto"` — shrink is bounded by the floor, grow stays 0, exactly as it was before this item; every already-correct row is now byte-identical to `main`.
  2. **The filter-row fix, by itself, still moved pixels on the account's DEFAULT view — and that part was a real, unavoidable content change, not a mistake to revert.** A floor on the input alone forces the sort `<select>` to shrink on every load where the account's sort preference is its default ("recent"), because — measured, not assumed — **Chromium sizes a native `<select>`'s closed box off the WIDEST option in its list, never off the one currently selected.** So the OLD "Largest first" (13 characters) was still governing the box's own width even while "Recently touched" (17 characters, the actual default) was what displayed — shortening only one of the two long labels never helps, because the other one alone still forces a box wider than this fixed 210px-wide row (232px panel − 16px padding − 6px gap) has room for once the input keeps its floor. Both were shortened together ("Largest first" → "Largest", "Recently touched" → "Recent") and the select was given its OWN floor (`SORT_SELECT_MIN_PX = 96`, alongside `FILTER_MIN_PX = 112`) — measured live (real Chromium, cropped screenshots of the control alone) to comfortably fit EVERY option's full text with a few px to spare, for all three options, not just the default. The shrink/ellipsis path stays wired as a defensive backstop; it no longer fires in the account's ordinary default state, which is what the CI baseline actually renders.
  - **What this means for the still-open CI check on the PR:** the corrected build's `map-landing` surface picture is now a clean win (shorter labels shown IN FULL, no ellipsis anywhere) rather than the earlier "Recent…" mid-word cut — but it is still, unavoidably, a real content change from the committed baseline (a floor on the input can never coexist with the select's OLD full-length default text at this row's fixed width; something has to give, and the input winning is the whole point of this item). Approving that new baseline needs the EXACT CI-pinned Chromium revision (`playwright`'s pinned 1228, confirmed unavailable in this session's sandbox, which carries only 1194/1243) — B1026272's own header in `visual-regression.mjs` documents a prior incident where approving with a "nearby" browser build produced a baseline that then mismatched real CI's, so this item does not attempt a local `--approve`.
