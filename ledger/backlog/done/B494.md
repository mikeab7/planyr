### B494 — Schedule module loading overlay sticks for a full 9 s "sometimes" (slow/buggy ready signal) `[Scheduler / loader]` (bug)  *(owner-dropped 2026-06-27 — "fix the loading icon for the scheduling module, seems kind of slow or buggy sometimes"; minted **B494** = highest real B# (B493) + 1 — renumbered from a provisional B493 a concurrent `main` took for the cross-module-link feature)*
`[x]` **DONE + verified (branch `claude/pdf-viewer-quality-x40e5a`). lint 0 · 1641 tests · build green · NEW headless `ui-audit/verify-scheduler-loader.mjs` 3/3 (+ diagnostic `observe-scheduler-loader.mjs`).**
- **Repro (headless, observed):** switch to the Schedule module → the "assembling schedule" loading overlay (`ModuleLoader`, B224) sat visible for the FULL **9 s** before cross-fading out, regardless of how fast the embedded `/sequence/` app was. Root cause: the overlay only dropped on the embedded app's FIRST `planar:nav-state` message, whose ONLY backstop was a lone `setTimeout(…, 9000)`. So whenever that first signal was slow or missed — a network hiccup, the embed's deps loading slowly, the embed not yet interactive — the loader stuck for a flat 9 seconds (the "slow/buggy sometimes").
- **Fix (`Scheduler.jsx` + a tiny responder in `public/sequence/index.html`):** make the ready signal **reliable + bounded**. (1) **Handshake** — on the iframe's `onLoad` the shell posts `planar:nav-request` (retried ~every 380 ms for ~2.3 s, in case the embed's own listener isn't attached yet); the embedded app answers by re-emitting `nav-state` from `latestData` (a no-op until its data has loaded), so a missed/slow first emit can no longer strand the loader — it drops the instant the embed is interactive. (2) **Bounded fallbacks** — reveal the embed ~2.5 s after its document loads even if it never answers (a slow/broken embed shouldn't hold a full-screen spinner), with a 6 s absolute backstop if `onLoad` itself never fires. `markReady()` + a ref make every path idempotent (one cross-fade). The proactive `nav-state` fast path is unchanged, so a clean boot still drops the loader immediately.
- **Verified:** `verify-scheduler-loader.mjs` 3/3 (real built shell, the embed stubbed via request-interception so the handshake/fallback paths actually run — the real embed's CDN is blocked in the sandbox so its iframe never finishes loading here): a **responsive** embed drops the loader at **~520 ms** via the handshake (was 9000 ms); a **silent** embed is bounded to **~3000 ms** (onLoad+2.5 s), not 9 s, and doesn't drop prematurely. Diagnostic `observe-scheduler-loader.mjs` shows the sandbox worst case (embed never signals, `onLoad` never fires) improved 9.5 s → 6.5 s (the backstop).
