- **Measured on production BEFORE the change (2026-10-30, `planyr.io/gis-proxy/gisdnr.state.co.us/…`):** `…/arcgis/rest/services` → `200 text/html` (an ArcGIS directory page served as planyr.io); `…/query?f=json&callback=x` → `200 application/javascript`; `…/0/applyEdits?f=json` and `/arcgis/admin?f=json` → forwarded to the upstream (`200`). `public/_headers`' `nosniff` does not reach Pages Function responses.
- **Fix, four pure exported limits in `functions/gis-proxy/[[path]].js`:** (1) `classifyPath` — only ArcGIS read shapes (service / layer metadata, `layers`, `legend`, `info`, `query`, `identify`, `export`, `exportImage`, `tile/z/y/x`, the services directory); POST only to `query` / `identify` / `export` / `exportImage`; the write verbs (`applyEdits`, `addFeatures`, `updateFeatures`, `deleteFeatures`, `calculate`, attachments, `uploads`, replicas, `append`, `truncate`) and `admin` / `manager` / `sharing` / `generateToken` / `tokens` refused anywhere in the path, 403; `cleanSegments` refuses dot segments (also `%2e%2e`), encoded slashes / backslashes, control characters, `;`, double-encoding, 400. (2) `forceJsonFormat` — an `f` the app does not consume (html, jsapi, kmz, pdf, none) becomes `json`; JSONP `callback` dropped; applied to the query string and to a urlencoded POST body (other POST body types 415); an already-safe request is passed byte-for-byte. (3) `classifyResponseType` — JSON / geojson / protobuf / png / jpeg / gif / webp / tiff only; HTML, SVG, XML, JavaScript, PDF refused with a JSON error that keeps the upstream's status; `text/plain` or no type is re-labelled JSON **only** when JSON was asked for. (4) every response, errors included: `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; sandbox`, and `Content-Disposition: attachment` for non-images. Nothing else of the upstream's headers is copied.
- **Measured to choose the allow-lists, not guessed:** one layer per allow-listed host through the production relay — 135 answered, 132 `application/json`, **3 `text/plain` carrying valid JSON (greenecountyassessor.org, maps.clintoncountypa.gov, opcgis.deq.state.ms.us)**, which is why text/plain is re-labelled rather than refused; the other 5 were upstream outages. The app sends only `/query` GET/POST, `/export`, `/identify` and metadata `?f=json` (esri-leaflet's POST is urlencoded; `serializeEsriParams` likewise).

- **Adversarial review by a fresh agent (before the PR left draft) — four reproduced findings, all fixed in the same PR, none broke a legitimate request (419 registry URLs re-classified, zero refused):** (1) **a redirect target skipped the path / method / format checks** (an allow-listed host answering 302 to its own `/arcgis/admin/…/delete`, or 307 replaying a POST body at `…/applyEdits`, was followed) → `redirectTarget` now runs the next hop through `cleanSegments` + `classifyPath` (with the post-downgrade method) + `forceJsonFormat`; (2) **a path merely ending in a layer id was relayed anywhere on the host** (`/wp-admin/post.php/delete/5`) → a path must contain `rest/services` (or be `rest/info`); (3) **the JSON branch echoed the upstream's raw Content-Type** (`application/json; x, text/html`, which Chromium reads as the last value) → the type is rebuilt as `<media>; charset=utf-8`; (4) **a non-canonical `f` was forwarded verbatim** (`f=json%20`, `f=json%0a`, `where=1;f=html`) → only a byte-exact `f=<consumed format>` passes untouched, everything else is rewritten, and `;` is scanned as a pair separator.
