- **ROOT CAUSE, confirmed by reading the code (not guessed): the PLANNER CANVAS never hits this bug at all.** `SitePlanner.jsx` draws a centerline road through its own `roadStripRing`/`roadDenseCenterline` (buffers the tessellated centerline by `travelW + 2*curb` via `metesAndBounds.bufferPolyline`) — it never calls `elRingFeet`. `elRingFeet` (the generic "points, or a w/h/rot box" outline) is called from exactly three places: `MapFinder.jsx` (the reported bug), `lib/kmzExport.js`, `lib/multiStyle.js`.
- **ADJACENT CASE CHECKED, per the brief's own instruction — the KMZ (Google Earth) export was NOT affected.** `kmzExport.js` already had its own `elToRingFeet(el)` wrapper (referencing B596) that special-cases `el.type==="road" && el.pts` by buffering the centerline exactly like the planner does, falling back to `elRingFeet` for everything else — and the KMZ polygon-export path (`siteToFeatures`) already called `elToRingFeet`, never the bare `elRingFeet`. **`multiStyle.js` is also unaffected**: its `selectionRingFeet` already special-cases a centerline road (`Array.isArray(o.pts) && !o.points`) BEFORE it would ever reach `elRingFeet`, returning the raw centerline as an open polyline for selection chrome — so `elRingFeet`'s road branch is dead code on that path today.
- **THE FIX consolidates rather than re-derives:** `elToRingFeet` (same formula: `bufferPolyline(roadCenterline(el.pts, el.vtx, {}), max(1, travelW + 2*curb))`, curb defaulting to 0 when absent — unchanged from the proven KMZ formula) now lives in `planStyle.js` beside `elRingFeet`; `kmzExport.js` imports and re-exports it instead of defining its own copy (its `roadCenterline`/`bufferPolyline` imports, used nowhere else in that file, were removed); `MapFinder.jsx`'s `showPlans` effect calls `elToRingFeet` instead of `elRingFeet`. The planner canvas (`SitePlanner.jsx`) was **not touched** — its own `roadStripRing` is a separate, junction-aware (`sharpAt`/`trim`) implementation used by 85 call sites across that file, and extracting it was judged too large a blast radius for this session; `elToRingFeet` deliberately mirrors its FORMULA without importing FROM it.
- **PROVEN RED then GREEN**, `test/planStyle.test.js`: a fixture matching the reported production shape (travelW 40, curb 1, ~2,000 ft centerline, stored bbox 4974.38x262.92 ft) — `elRingFeet` alone reproduces the bbox-area defect (pinned as a mutation check); `elToRingFeet` returns a ring whose area is within 0.5x-2x of `centerline_length x (travelW+2*curb)` and more than 5x smaller than the bbox. A 2-point legacy road (no travelW/curb) and every non-road element are asserted BYTE-IDENTICAL to the old `elRingFeet` output. `test/kmzExport.test.js`'s existing 39 tests (incl. its own `elToRingFeet` suite) pass unchanged post-move.
