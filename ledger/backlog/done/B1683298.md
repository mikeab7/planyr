### B1683298 — A stray "click and type" placement caret survives a press on a sketch box's own embedded label field and hijacks the next keystroke `[Notes]` (bug) #notes #ui  *(found 2026-09-16 stress-testing B1683296's own fix under a realistic precondition — a click on blank note-body space before touching the sketch, arming `NoteEditor.jsx`'s `pendingPlace` — which is NOT part of Michael's own reported symptom but reproduces a genuinely separate, real defect the moment it is present. Minted **B1683298** from B1683296's reserved block B1683296–B1683311. DEDUPE-FIRST — searched Open/⏳Verify/Done/Done-archive for "pendingPlace", "focusFromMat", "cancelPendingPlace", "click and type": B1385024/B1385025/B1385026 built and refined this mechanism and are Done — none of them names this ordering gap. Net-new.)*

`[x]` **FOUND AND FIXED, RED-PROOFED AGAINST UNMODIFIED CODE, DETERMINISTIC (no timing dependency — straight to Done).** `focusFromMat`'s own comment already states the intended rule: "ANY press forgets an armed caret… clicking anything else simply drops it." The code did not follow it: `if (el.closest("input, textarea, select, button, a")) return;` ran BEFORE `cancelPendingPlace()`, not after, so a press whose target was an `<input>` skipped cancellation entirely. A sketch box's own label field is a real `<input>`, embedded in the document exactly like any node view's overlay — a press there hit this exclusion and left a stray placement caret (armed by an earlier, unrelated click on blank note-body space) fully intact. The window-capture "a real field outranks an armed caret" keydown handler could not rescue it either: it excludes only fields OUTSIDE the ProseMirror editor's own DOM, and a node view's overlay input is structurally `dom.contains(active)` — "inside the editor" — by construction, so it does not count as the outranking field the check was written for. Net effect, measured directly: the first character typed into the sketch box's label field was silently redirected into a brand-new, unrelated anchored block elsewhere in the note, and the label field stayed empty — `pendingPlace`'s own DOM marker (`data-pending-place`) read `"1"` (armed) through the box's creation AND its relocate, and only cleared once the hijacked keystroke consumed it.
- **THE FIX (`NoteEditor.jsx`, `focusFromMat`):** moved `cancelPendingPlace()` to run unconditionally, before the input/textarea/select/button/a early return. `cancelPendingPlace` is side-effect-free beyond clearing that one piece of state (`setPendingPlace((p) => (p ? null : p))`), so calling it earlier changes nothing about how the pressed control itself handles the press — the exclusion still does exactly what it did before for every OTHER purpose `focusFromMat` serves, just no longer at the cost of a stale caret surviving.
- **VERIFIED, real trusted browser input, before/after comparison against unmodified code:** armed `pendingPlace` via a real click on blank note-body space, created a sketch box via the note toolbar's "Box" command, relocated it via B1683296's own fix, then typed a character — before this fix: `pendingPlace` stayed `"1"` through every step and the typed text never reached the label field; after this fix: `focusFromMat`'s mousedown correctly reads `null` immediately once the relocate press lands, and typed text lands in the label field and commits normally on Escape.
- **Both the discovery precondition and the fix generalise beyond sketch mode** — see `docs/NOTES-CARRY-FORWARD.md` §1 entry 31: any node view with its OWN embedded `<input>`/`<textarea>` (a future callout field, a table cell editor) sat exposed to the same gap.
