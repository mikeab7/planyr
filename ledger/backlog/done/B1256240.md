`[x]` **FIXED THIS SESSION — root cause found by live measurement, not guessed.** AUDIT-FIRST: reasoning about the existing CSS (`flex: 0 0 ${w}px` plus an ellipsis span with `minWidth:0`) suggested numbers should already clip correctly; a real headless-Chromium measurement proved otherwise — the cell's own outer `<div>` (the actual flex item) was rendering at up to 146px inside a 120px column. Root cause: a flex item's AUTOMATIC minimum size defaults to its own content's min-content width, and for `white-space: nowrap` text that min-content width equals the FULL unwrapped string — so a long, un-wrappable General-format number silently grew the cell's own box past its column's flex-basis and shoved every later column in the row rightward, which is what actually produced "paints across the column boundary and over C/D/E" (not an ellipsis-clip failure — the box itself was growing). B1076480's inner-span `minWidth:0` never reached this: it only stopped the SPAN from refusing to shrink, not the outer DIV that owns the box. Two-part fix: **(1)** `SheetView.jsx` — `minWidth: 0` added to the cell's own outer flex-item style, pinning its automatic minimum to zero so the flex-basis (the actual column width) is the box's real, final width regardless of content — the same class of fix as B1076480's span, just on the element that was actually missing it; this alone stops every non-spilling cell kind (numbers, dates, bools, short/occupied-neighbour text) from ever growing past its column, while leaving B1076480's fill-handle/resize-handle overflow-visible fix completely untouched (`overflow` itself is not touched by this change). **(2)** New pure module `lib/generalFit.js` (`fitGeneralNumber(value, availableWidthPx, measure)`) implements Excel's own retreat order for an unformatted ("General") NUMBER cell: full precision first; then fewer DECIMAL PLACES (rounding, never touching the integer part, and never rounding a genuinely nonzero value down to a bare "0" — it falls to scientific instead of doing that); then scientific notation, narrowed the same way, starting from ITS OWN natural loss-free precision; then a column-filling run of "#" once nothing legible fits. Wired into `SheetView.jsx`'s per-cell render, gated on `cell.kind === "number" && formatAt(sheet, r, c) == null` — an explicit format (Currency, Percent, a hand-typed custom token) never enters this path at all, so it keeps its own `formatNumberToken` rules and is never re-rounded. The computation reads the LIVE column width at render time (not memoized against sheet content), so it reacts correctly to a live column-resize drag, exactly like Excel's own General format does. Nothing about the stored cell/formula text changes — `cell.display`'s full-precision string is still what's stored/copied/exported; only a new local `shownText` (the fitted string) is what's painted into the non-editing span.
