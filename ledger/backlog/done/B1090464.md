`[x]` **SHIPPED THIS SESSION.** Two shared validators in `compParse.js` — `hasAmbiguousGrouping` (any comma-group after the first that isn't exactly 3 digits, checked on the number's INTEGER portion only so a genuine decimal tail like "4,150,000.00" isn't a false positive) and `precededByDroppedMinus` (a bare "-" TIGHTLY, with no whitespace, glued to the matched digits — deliberately NOT triggered by this corpus's own spaced-dash clause separator, "3.2 AC land - $850k - Jan 2026") — wired into every rate/price/size numeric match point (`wrapMoneyMatch`, `findRateToken`, `findSizeToken`, `findPriceToken`). Either condition now makes the module treat the number as **BLOCKING**, its own module's existing taxonomy for "the shown value would be silently wrong" (never SOFT, which means "visible, correctable"): the field is left genuinely blank, the exact raw text is preserved verbatim in Notes so nothing vanishes, and a `blocking` cell flag keeps the row out of "ready to save" (`rowHasBlockingFlags`) until a person re-enters the number by hand — no guessing either direction. A new labelled-price detector (`findLabeledPrice`, mirroring the existing TI/NOI/cap-rate label-detector pattern — "price"/"sale price"/"purchase price"/"asking price"/"sold for", both value-then-label and label-then-value) closes the "1,200,000 price" gap: `findPriceToken`'s own bare-number refusal (deliberately still refuses an UNlabelled bare comma-integer, unchanged — that's the genuinely ambiguous case, correctly left blank) is now tried second, after the label check. A $0 rate and a rate above a flat $200/SF ceiling (implausible under either monthly or annual quoting) are both accepted — the shown number IS what was typed, correctable at a glance — but flagged **SOFT** with a plain-language reason, closing "accepted with no confirmation, no ceiling." `generic.rateBasis`'s NNN default (HARDENING-11) moved to fire whenever a row types as `lease`, not only when a rate was successfully read, so a blocked/unreadable rate never regresses `leaseRateExpense` to a raw `null` instead of the blank-string convention every other unset field uses.
