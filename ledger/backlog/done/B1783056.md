`[x]` **AUDIT-FIRST — the real constraint, confirmed by reading the code before touching it (the dispatch's own "CURRENT BEHAVIOUR" section was a MAP.md inference and only half right).** `lib/exportSheet.js`'s `sheetPlanAspect`/`sheetLayoutBoxesIn` were never the constraint — those two feed the sheet's own plan-box math and were never wired into frame dragging at all. The real lock was in `SitePlanner.jsx`: `startPrintResize` captured one fixed opposite CORNER and `onMove`'s `"printResize"` branch always recomputed `hFt = wFt / printAspect()` — so every corner drag was silently re-projected onto the sheet's own plan-window ratio, and there were only ever 4 corner grips, no edge grips at all. **A second, independent lock compounded it**, not mentioned in the dispatch brief: `recomputeCompose` re-ran `fitFrame(pf.cx, pf.cy, pf.wFt, pf.hFt, box.planW / box.planH)` every time paper or orientation changed **while already in the compose screen** — so even if the drag itself had been free, opening Compose (or just switching paper size) would have silently snapped the frame straight back to the sheet's aspect. Both are what "it only lets him drag one specific aspect ratio" actually meant. **What did NOT need fixing, confirmed by reading rather than assumed:** `buildExportSvg`'s nested nested `<svg>` already uses `preserveAspectRatio="xMidYMid meet"`, and `exportStyle.sheetFitScale` / `exportLabelScale.sheetLabelPpf` already reduce a mismatched aspect to ONE uniform `min(sx,sy)` scale for stroke weights and the label tier — the "sheet fits the frame" HALF of this request was already correct and aspect-agnostic; the UI simply never let anyone reach a frame the fit math would have to handle. PNG export was already free-aspect too (it rasterizes the frame's own `w×h` directly, no paper concept at all). **One incidental pre-existing bug found and fixed while here:** `SitePlanner.jsx`'s own `exportPDF` wrapper only ever forwarded its first 6 params to the lazy `exportSheet.js` chunk's `exportPDF` — so `doPrint`'s 7th argument (the "Stats band" toggle) never reached the actual downloaded PDF, even though the live compose preview (a separate direct call) honored it. Fixed in the same commit since both functions' signatures were already being extended for the 8th (page override) parameter.
`[x]` **Free-aspect drag, unconstrained, no minimum aspect, no silent correction on mouse-up.** New pure module `lib/printFrameDrag.js` — `FRAME_GRIPS` (4 corners + 4 mid-edges, replacing the old 4-corner-only set), `frameGripAnchor` (the fixed opposite corner/edge a grip drags around) and `resizeFrame` (free: each axis a grip drives sizes independently off the pointer, the other axis untouched; `snap: true` reproduces the OLD locked-aspect formula bit-for-bit). `SitePlanner.jsx`'s `startPrintResize`/`onMove` now call these instead of the inline aspect-forcing math. **Old behaviour stays one modifier away**, exactly as asked: holding Shift while dragging ANY grip (corner or edge) snaps to the sheet's plan-window aspect.
`[x]` **The sheet's plan window FITS the frame, never the other way — `recomputeCompose`'s aspect-forcing re-fit is REMOVED.** Changing paper size, orientation, or opening Compose no longer touches the picked frame's shape at all (the explicit-engineering-scale path is untouched — that mode legitimately derives the frame FROM the plan box, by deliberate design, and its resize handles stay hidden as before).
`[x]` **New "Fit to frame" sheet-size option, in the compose step's Sheet section.** `printSheet.js`'s new `pageSizeForFit(paper, frameAspect)` sizes a page to the frame's own aspect at the CHOSEN paper's long edge (Letter's 11″, Tabloid's 17″, ARCH D's 36″, …), floored at 3″ on the short edge so an extreme aspect never crushes the title-block margins. `printSheetLayout` (and `sheetPlanAspect`/`sheetLayoutBoxesIn`/every `exportSheet.js` call in the chain: `buildExportSvg`, `sheetLabelPpfFor`, `buildComposedSheet`, `exportPDF`) now accept an optional `page` override that REPLACES the standard paper/orient lookup everywhere — the label tier and the final rasterized page can never disagree about which page is actually printing. Standard sheet sizes stay the default; the checkbox is mutually exclusive with an explicit engineering scale (each setter stands the other down — the two would otherwise fight over what decides the page, since an explicit scale derives the frame FROM the plan box while Fit-to-frame derives the page FROM the frame).
`[x]` **Orientation auto-flip, as a default, not a lock.** `printFrameDrag.orientationForAspect` — entering Compose (`enterCompose`) sets the sheet's Landscape/Portrait to match the picked frame's own shape when they disagree, once; touching the Landscape/Portrait control itself (now wrapped to latch `orientTouchedRef`) means that explicit choice sticks for the rest of that compose session, exactly as asked. The chips grey out (with a tooltip) while Fit-to-frame is on, since orientation is then moot — the page always takes the frame's own shape either way.
`[x]` **Adjacent cases, checked against the actual code, not assumed:** PNG export already free-aspect (unchanged, confirmed above). KMZ export does NOT derive its bbox from the print frame at all (`exportKmz` reprojects the whole drawn model — parcels/elements/measures — regardless of any frame; the dispatch's "KMZ derives its bbox from the frame" inference was wrong, confirmed by reading `exportSheet.js`'s `exportKmz`, so nothing needed to change there). The B839 aerial tile Stitcher (`exportAerialForFrame`/`stitchAerialDataUrl`) already builds its bbox from `exportFeetExtent(frame)`, which is aspect-agnostic by construction (`{minX,minY,maxX,maxY}` from `cx,cy,wFt,hFt` — no assumption anywhere that `wFt`/`hFt` match a sheet ratio); confirmed unaffected. The initial auto-computed frame (`enterPrintMode`, "fit site") and the on-canvas presets are untouched and, since the aspect-forcing re-fit is gone, are now treated by the rest of the pipeline exactly like a hand-dragged frame — there was no separate mechanism to unify. `printFrame` itself is plain session `useState`, never persisted to the site model, so "frames already saved with a plan must load unchanged" does not apply — there is nothing on disk to migrate.
