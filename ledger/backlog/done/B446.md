### B446 — Dropping/opening a file gives no clear signal it registered `[Doc Review / Markup]` (bug)  *(owner-dropped 2026-06-24 as "NEW-1"; fixed same session per STANDING RULE #1)*
`[x]` **DONE + verified (branch `claude/vibrant-pascal-wkg50i`). lint 0 · 1434 tests · build green · headless V131 (`ui-audit/verify-open-feedback.mjs`, 6/6, logged out).** Owner repro: drop a PDF (especially with a doc already open, or open from the Files panel) → no immediate, unmistakable sign anything is happening; it can look like nothing registered ("silence is a crash").
- **Root cause:** `setBusy(true)` existed but the only "Opening…" text rendered in the EMPTY state. The B294 drop-over-open path and the `openReview`/Files-panel/`loadSingleReview` paths render no empty state, so they showed no loading signal at all; a non-PDF reject set `err`, which the canvas never displays, and a null drop / `loadReview→null` could no-op silently.
- **Fix:** a canvas-level **"Opening &lt;name&gt;…" overlay** (`data-testid="opening-overlay"`, spinner + filename, reuses the `spin` keyframe) driven by `busy`, rendered in BOTH the empty-state and the canvas branches (so it covers the prior sheet on a drop-over-open). `busy`/`busyLabel` are now set on EVERY entry path — `openFile`, `openReview`, `loadSingleReview` — and cleared in token-guarded `finally`s so a rapid switch can't let an older load's finally hide the newer overlay. **Silence-is-a-crash:** `openFile` surfaces a null drop + a non-PDF reject + a read failure on the always-visible `openErr` banner (role="alert") AND the inline `err`; `openReview` surfaces a missing-row and a `loadReview→null`. A superseded (older) load stays intentionally silent — the newer load owns the feedback.
- **Deduped:** a GAP in **B294** (which only wired the drop *handler*, not feedback) + the **B405/docIntent** open paths — not a duplicate of any.
