- Verify: sandbox — this item's own deliverable (the wording change + the audit's answer) is proven by the same unit tests and the same live run recorded on B689904; no separate live check applies.
- **The model half was already correct and is untouched:** `identifyJurisdiction`/`formatJurisdictionBadge` (jurisdiction.js) never let a POINT query (no ring — no parcel drawn) return more than one ETJ or county in the first place; the H-GAC and TxDOT layers don't publish overlapping polygons at an exact coordinate, confirmed live at Woods Road's own origin (zero cities, zero ETJ, exactly one county) and structurally impossible to violate since a bare point can only fall inside however many polygons genuinely contain it. The two-ETJ case only ever arises for a RING (whole-tract) identify, which per Local Gov't Code ch. 42 is legitimate — a drawn tract CAN cross the apportionment line between two cities' ETJ, one on each side.
- **The presentation half was wrong, and is the fix:** the badge's `+` separator means "co-equal peers, both apply" everywhere else it's used (two counties genuinely straddled, two cities that both hold the whole site) — applying the same mark to two ETJ names implied both fully govern the tract, which ch. 42's apportionment rule says is never true. `jurisdictionLabel.js`'s `leadFor`/`etjSlotFor` now special-case `etj.length > 1` to say the tract **CROSSES** the two names (`"ETJ crosses City of Fulshear + City of Simonton"`) rather than naming each `"City of X ETJ"` and `+`-joining them; `JurisdictionBadge.jsx`'s tooltip adds one line explaining the apportionment rule whenever this fires.
- **The audit, answered directly (the dispatch's explicit ask — "SAY WHICH IT TURNED OUT TO BE"):** the tooltip's "H-GAC ETJ — current edition" provenance claim is TRUE. Driven live this session: every ETJ answer in this codebase (`etjSourcesForPoint` → `ETJ_SOURCES` in `jurisdiction.js`) is a real ArcGIS REST query against H-GAC's own hosted feature layer at `services.arcgis.com` (`HGAC_City_ETJ`), routed by the point's metro bounding box. It is NOT derived by buffering city limits by a population-based radius — no such derivation exists anywhere in this file or its dependents. The layer's own published coverage gap (it carries 34 named H-GAC cities, not all of them — B280705/`etj_baytown`'s own header) is the one honest caveat already surfaced (`etjUnmappedCities`), unrelated to this item.
