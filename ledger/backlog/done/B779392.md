- **(1) THE ROTATION.** `XSectionPreview`'s band rects now vary in `x` and share one `y` — bands drawn left to right, matching the road as it's actually drawn on the plan-view canvas. `bandLayout`'s existing sign convention (offset 0 = the road's true drawn centerline) is unchanged; only the axis it's projected onto moved. Lane striping is vertical now (was horizontal), and the in-band type/width label is centered in the band's own horizontal span rather than its vertical one.
- **(2) THE HORIZONTAL DIMENSION STRING — replaces the rotated total label at the root, not a patch.** A tick mark at every band boundary, each band's own width figure underneath, the running total (still `f1(rowW)′ total`, never rotated) beneath that. This is what B776560's rotated `<text transform="rotate(90 …)">` needed to become: a rotated label needs the box's HEIGHT to hold its whole rendered length, which is exactly what clipped it to "tot" at any modest height; a horizontal string never has that problem at any section width, by construction, so this removes the bug's root cause rather than reserving more space for the old approach.
- **(3) THE CENTERLINE.** A dash-dot line (`8 3 1.5 3`) runs through the section at `xOf(0)` — the section's true drawn offset, not the geometric middle of the whole preview box (they differ whenever a flank band like a sidewalk sits on only one side). The mark itself is drawn as two stacked plain-ASCII "C"/"L" glyphs rather than the Unicode centerline symbol (U+2104), deliberately — a symbol from an unusual Unicode block risks silently rendering as a tofu box in some font stacks, where two ordinary capital letters cannot.
- **(4) LABEL COLLISION — a leader line out, never a clip/squeeze/overflow, both for the in-band type label and the dimension string's own width figure.** `packRows` (new, pure, module-scope) greedily row-packs a set of `{mid, halfW}` items so nothing sharing a row overlaps; used independently for (i) in-band labels too wide for their own band's column, which move onto a leader line above the swatch showing the FULL "Type · width" text (no longer needing to fit ANY column once outside it), and (ii) dimension-string numbers too wide for their own band's ticks, which drop one row lower on a short leader stub. Fit is decided by a deliberately-conservative text-width estimate (`estTextW`, erring wide) rather than a real DOM measurement, so a borderline label is more likely to get a leader than to risk a squeeze. Verified live against the owner's own named case (a 20′ median beside a 2′ curb-and-gutter band): the curb band's full label and its width figure both render, fully unclipped, with zero overlapping label boxes anywhere in the preview.
- **(5) THE LIST-TO-PREVIEW CORRESPONDENCE, preserved rather than lost in the rotation.** The dialog tracks which band row is hovered or keyboard-focused (`activeIdx`) and passes it to the preview, which outlines the matching band in the accent color. Wired via `onMouseEnter`/`onMouseLeave`/`onFocus`/`onBlur` on each band row (the row itself also gets a subtle background tint) — verified live: hovering the Median row highlights exactly the Median band and nothing else; moving away clears it.
- **(6) SCALE TO FIT — measured, not assumed.** The preview measures its own wrapping `<div>`'s real width via `ResizeObserver` (synchronously in a `useLayoutEffect`, so there is no flash of the wrong size on first paint) and sizes its per-foot scale to exactly fill that measured width, capped at a legibility ceiling for a narrow/single-band section. The SVG's `width`/`height` attributes always exactly match its `viewBox` (the same discipline B776560 established for the vertical layout's height, now applied to the width, which is now the axis that has to fit) — verified live at the dialog's default width, and again after shrinking the browser viewport to 480px: the SVG's own width attribute matches its rendered pixel size exactly at both sizes, it never exceeds its wrapping container, and the dialog itself never gains a horizontal scrollbar.
