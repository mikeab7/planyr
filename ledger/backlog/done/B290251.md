`[x]` **✅ DONE 2026-08-09 — the gate no longer reads main's own items as this branch's mints, and a genuine double-mint is still fatal (now in TWO places rather than one).**
- **THE FIX, and it is NOT the one-liner the costed plan proposed.** The plan's shape was `priorIds = union(onBase, onMain)` for the TAKEN test. **That would have silently deleted the B1140 case** — the whole reason the merge base is used — because in B1140 the id IS on main, so unioning it into `priorIds` exculpates exactly the collision the gate exists for. What shipped instead keeps `added` measured against the merge base and asks a second question of each id it flags: **is the heading here byte-identical to main's heading for that id?** Identical → the content came from main, advisory. Different → two features, one number, fatal, and the message now prints BOTH titles.
- **⛔ AUDIT-FIRST CORRECTED THE ITEM'S OWN DIAGNOSIS BEFORE ANY CODE WAS WRITTEN.** Reproduced in a throwaway-repo lab: **a plain `git merge origin/main` was never affected at all** — the merge commit moves the merge base to main's tip, so main's ids stop being "added" by construction. The failing shape is a resolution that takes main's CONTENT without its ANCESTRY (`git merge --squash`, `git checkout origin/main -- BACKLOG.md`, a rebuilt branch), which is what leaves the base behind while the tree carries main's headings. An e2e arm exercising only a clean merge commit would have passed before the fix and proved nothing — so both arms exist, and the content-only one is the arm that goes red on the old code.
- **Measured, before → after, same lab, same four cases:** content-copy merge **3 fatal offenders → 0** · genuine double-mint, unmerged **fatal → fatal** · genuine double-mint after merging main **PASSED SILENTLY → fatal** · clean merge commit **clean → clean**.
- **THE THIRD CASE IS A BUG THIS ITEM DID NOT KNOW IT HAD.** Once a branch merges main, the base moves past the collision and the old gate had nothing left to see: an independently double-minted id sailed through the pre-push hook. It is now caught at push time by a duplicate-heading check (B308704) reusing the detector `test/idUniqueness.test.js` runs. **That is what makes the relaxation above safe rather than merely argued** — the check that was loosened and the check that was added cover each other.
- **Neither the merge-base reasoning nor the fatal-TAKEN verdict was weakened.** `test/mintFatality.test.js` is green: the fatal verdict is still a function of a present, proven collision and of no aggregate of peer state.

`[ ]` `npm run check-mint` measures "ids added by this branch" against the MERGE BASE, so after you merge `origin/main` into a branch to clear a conflict, every id main added since the base looks like this branch minted it — and the gate then calls each one `ALREADY TAKEN on origin/main` and blocks the push.
- Verify: sandbox
- **Measured, 2026-08-09.** Branch base `cf4f77b`, main tip `ae2ce02`. `git merge origin/main` (the resolution `CLAUDE.md` prescribes for a `dirty` PR — *"merging `origin/main` into the branch fixed it instantly"*) → the gate failed with **11 fatal offenders**: B280402, B280403, B280704–B280707, B286000, B286001, V78961, V79264, V84560. Each was verified to appear **exactly once** on `origin/main`, **exactly once** in the working tree (the same item, arrived via the merge), and **not at all at the merge base**. There was no duplicate heading anywhere in either file pair.
- **Why the input is wrong and the verdict is right.** `scripts/check-mint.mjs` computes `priorIds` from the merge base *(its own comment explains why — the B1140 case, where main merged an item under a number a branch was independently holding)*. That reasoning is sound and should not be undone. The gap is that it does not EXCLUDE ids reachable from `origin/main` itself: an id that is on main **and** whose content came from main is not something this branch minted.
- **Severity: it blocks the documented recovery path, so it is worse than it looks.** A stale PR needs a new push, a `dirty` PR swallows every nudge, and the fix for both is to merge main — which arms a pre-push hook AND a required build step against you. The obvious escape (renumbering) would be actively WRONG here: it would renumber *main's* items on this branch, creating the real duplicate the gate exists to prevent.
- **The route around, used on #972 and worth writing into `CLAUDE.md` either way: REBASE instead of merging.** `git rebase origin/main` makes the merge base main's tip, so only the branch's own ids read as added and the gate goes green with nothing renumbered. Costs a `--force-with-lease` push.
- **Costed plan — DO NOT BUILD blind; this is the mint gate and a wrong change here is expensive.** ~0.5 session. The one-line shape is `priorIds = union(onBase, onMain)` for the TAKEN test while keeping the base-only set for the peer-claim test — but that must be argued against B1140's case explicitly (does an id minted independently on BOTH sides still fail? It must), and `test/mintGateE2E.test.js` already drives all four outcomes against real git refs in throwaway repos, so the new case belongs there as a fifth arm proven red first. **Per `test/mintFatality.test.js`, whatever lands must keep the fatal verdict a function of a present, proven collision — never of an aggregate of peer state.**
