### B1895541 — Toolbar buttons could format the wrong place while a block-placement was armed (numbered list "stops at 2") `[Notes]` (bug) #notes #ui  *(Same dispatch as B1895536 — item 6 of 9, "numbered list stops at 2" from the owner-approved mockup's own bug list. Minted **B1895541**. DEDUPE-FIRST — searched for "pendingPlace" + "toolbar", "commitPendingPlace": no prior item covers a toolbar button interacting with an armed placement.)*

`[x]` **WRONG-CASE discipline applied before writing a fix: the literal reported shape was tested first, and repeatedly refused to reproduce.** Direct typing of a fresh 5-item numbered list (via the "1. " markdown shortcut, via the toolbar's own Insert-numbered-list button, converting an existing bulleted or checklist list mid-way, and round-tripping through a reload) all rendered a correct, structurally sound `<ol>` with five sequential `<li>`s and no CSS mechanism anywhere in this module resets or hides a native list-marker counter (checked: `notesIndentLevel.js`'s marker rules only ever set `list-style-type`, the glyph, never a counter value). Per STANDING RULE #2 (an owner-reported symptom is never closed on a null), the search for the REAL case continued rather than stopping there.
`[x]` **A real, reproducible defect WAS found and IS fixed, in the same area.** `NoteEditor.jsx`'s own `pendingPlace` mechanism (double-clicking blank canvas ARMS a caret but creates nothing — "a press arms a caret, it does not create anything," its own header) deliberately does NOT focus the editor, so the keystroke that would normally commit it is caught by a `window`-level capture listener instead. A toolbar button click is neither a keystroke nor a focus-stealing gesture (every button already cancels `mousedown` so the caret survives a click, by design) — so clicking a toolbar formatting button (Insert numbered list, Checklist, or any other) WHILE a placement is still armed silently applies to whatever the document's LAST REAL selection was (often a stray trailing paragraph), while the next keystroke commits the armed point as a brand-new, entirely unformatted box. Measured live: double-click → press "Insert numbered list" → type five items produces an empty `<ol>` nowhere near the typed text, and the five items land as plain unlisted paragraphs in a fresh box the button never touched — a shape that could plausibly read to a user as "the numbering broke."
`[x]` **FIX.** `NoteToolbar.jsx`'s root now calls a new `onBeforeAction` prop (`NoteEditor.jsx` wires it to `commitPendingPlace()` with no text — the exact same function the real keystroke path already uses, called with no content so it just turns the armed point into a real, empty, FOCUSED box) in `onMouseDownCapture` — CAPTURE phase, so it runs before any individual button's own `stop`/`onClick`. This is a general fix for every toolbar control, not list-specific: any button pressed while a placement is armed now commits the box first and then applies its own command to the real, current selection inside it. A no-op whenever nothing is armed (the underlying function already guards `if (!at) return false`), so ordinary toolbar use elsewhere is unaffected — reconfirmed by re-running direct-typing and select-all-then-Bold checks after the fix.
`[x]` **Red-proof test, matching the brief's own request.** A headless Playwright check reproducing exactly the found defect's steps (double-click, click Insert-numbered-list BEFORE typing, then type five items) FAILS on the pre-fix code (0 list items — five plain paragraphs in a separate box) and PASSES after the `onBeforeAction` fix (one `<ol>` with five `<li>`s, correctly inside the box the button was meant to format).
