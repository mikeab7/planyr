`[x]` **Shipped this session.** Typed durations now resolve the way a developer means them — two measuring sticks keyed to the unit — with both the parsed duration and the computed end visible.
- **Recorded BEFORE editing (the two symbols the owner asked me to inspect, not guess):**
  - **(a) current duration-parse + end-date derivation:** `duration` was stored as a plain **integer = inclusive count of working (business) days** — no unit concept; `0` = milestone. Parsed in the grid via `applyUpdate` → `parseInt(val)||0` (so `3w`→3). End derived by `calcEnd(start,dur) = addBD(start, dur-1)` (skip Sat/Sun + `HOLIDAY_SET`). End is re-derived from duration in `updateTask`, `previewProject`, `cascadeDates`, `normalizeToV6`, and the holiday-recompute effect. Migration used a boolean `_v6` flag (not a numeric version), idempotent via early-return.
  - **(b) the start-date lock:** the `pinnedStart` boolean — `cascadeDates` does NOT re-derive a `pinnedStart` task's start from predecessors (`if (!preds.length || t.pinnedStart) …`); it's set implicitly when a Start is typed/dragged and cleared when predecessors are edited. **UI:** an amber **padlock SVG** on the Start cell shown only when pinned; click → unpin + re-apply predecessors.
- **What shipped (mirroring, not guessing):** a small **pure, dependency-free** helper set in `public/sequence/index.html` (mirrored VERBATIM into `ui-audit/stress/scheduler-engine.mjs`, the tested copy): `parseDurationInput` (3w/3 weeks · 15d/15 days · 2mo/2 months · 1y/1 year · bare number→days · empty→milestone · **junk → {error} so the field shows a visible inline error, never a silent 0**), `addCalendarMonths` (end-of-month clamp: Jan 31 +1mo → Feb 28/29), `rollForwardToWorkday` (plain forward off a weekend/holiday — no month-crossing guard, owner decision), `workdaysBetween` (**closed form** — full-weeks×5 + partial-week remainder − HOLIDAY_SET weekday hits; NO day-by-day loop), and `resolveDuration` (d/w = working days via `calcEnd`; mo/y = calendar add + roll-forward, working-day count **derived** off the span). Week = **5 working days, hard-coded** (6-day weeks are B617, deliberately NOT parameterized here). No months→days factor anywhere. Reuses the existing `HOLIDAY_SET`/`ensureHolidays` path — no new holiday list.
- **Model:** each task keeps its canonical working-day `duration` (every existing consumer unchanged) + the typed intent `durUnit`(`d`|`w`|`mo`|`y`) `durValue`. `cascadeDates`/`rollupParentDates`/`updateTask`/`previewProject`/new-task factory/holiday-recompute all made unit-aware. Duration cell renders the unit (`fmtTaskDuration`) with a derived-working-days tooltip for mo/y; the end date stays visible in the Finish column.
- **Migration `_v6 → _v7` (`normalizeToV7`, idempotent):** stamps `durUnit:'d'`/`durValue:duration` on every legacy task; re-derives via `resolveDuration('d')` which **equals** the old `calcEnd` → zero end-date shift by construction. Wired into all 4 load-pipeline sites. **Ran the real before/after diff on the live production dataset** (scheduler Supabase `hs-v1`, **667 tasks**): **0 real shifts** — the only 5 flagged were **parents** rolled up from an intentional Sunday year-end milestone, whose end comes from rollup (unchanged), not `calcEnd`. Reproduced data-safe in `ui-audit/stress/verify-b615-migration.mjs` (18,000 no-shift pairs + parent-rollup + idempotency + the new units).
- **Accepted-on-purpose divergences (not bugs):** the same "7 months" on a Jan vs Jul start yields slightly different working-day counts; "4 weeks" (20 wd) ≠ "1 month" (calendar).
