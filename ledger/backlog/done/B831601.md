`[x]` **✅ DONE — new right-click command, one undo step, marks preserved; two real bugs found and fixed chasing it; the already-shipped paste half re-verified green.**
- Verify: sandbox — reproduced and fixed headlessly with real right-clicks and menu clicks; judged on the stored document per house rule.
- **THE COMMAND (`lib/notesTableToText.js`, new).** Each `tableRow` becomes one line: a plain paragraph, or — when the table is the ONLY content of a `listItem`/`taskItem` (Michael's exact Silvestri case) — a SIBLING list item at the same level, inserted in place of the item that held the table. When the table shares its list item with other content (e.g. a line above it), only the table is removed and the sibling lines are inserted right after, leaving the other content untouched. A multi-cell row joins its cells with a plain `" · "` separator; every inline node's marks (bold, links) ride straight through unchanged, since only the block containers are restructured. One ProseMirror transaction, so Ctrl+Z undoes the whole conversion in one press. Wired onto the document's right-click menu (`DocMenu` in `NoteEditor.jsx`) as "Convert table to text", offered only when the right-click actually landed inside a `<table>`.
- **BUG #1, found and fixed: a custom Tiptap command that builds its own `state.tr` reports success and does nothing.** `editor.commands.x()` (what a menu row's `onClick` uses) always dispatches the ONE `tr` object it built before calling the command function and threaded through as a prop — the `dispatch` callback it hands you is a no-op. The first version of `convertTableToText` called `state.tr` (a getter that returns a FRESH `Transaction` on every read) instead of destructuring `tr` from its own props, mutated that throwaway object, and `editor.commands.convertTableToText()` returned `true` while the stored document was byte-identical — caught by adding `window.__noteEditor.runCommand(name, ...args)` (gated behind the existing `__PLANYR_E2E` flag) and comparing the command's return value against storage.
- **BUG #2, found and fixed: a right-click's caret placement is asynchronous.** Measured on a plain paragraph, no table involved: the native DOM selection moved correctly on `mousedown`, but ProseMirror's own `state.selection` only catches up through a `selectionchange` listener that fires **~20ms after `contextmenu` has already run** — so the document menu, built synchronously inside `onContextMenu`, was reading wherever the caret used to be, not where the user just right-clicked. Fixed by resolving the click position with `editor.view.posAtCoords` and calling `setTextSelection` by hand in `onContextMenu`, unless the click landed inside the CURRENT selection (so Cut/Copy on an already-selected phrase is untouched). This is a general fix — it corrects every selection-dependent menu row (e.g. the Link/Remove-link label), not only the new one.
- **Focus comes home after the command runs** (`editor.commands.focus()`), matching the existing box-delete precedent (B421489) — a menu click leaves focus on the button it clicked, and Ctrl+Z cannot reach a document that is not focused.
- **The PASTE half of this ask was already shipped** (`notesPastePlain.js`'s `isLayoutTable`, B36051 amendment 2) — re-verified green rather than reimplemented: a pasted single-column table lands as plain paragraphs, not a table, in all three paste modes including the default.
- **VERIFIED.** `ui-audit/verify-notes-table-to-text.mjs`, 17/17: the reported case (table is the whole list item) converts to 4 sibling list items with bold and link marks intact and one Ctrl+Z restoring the table whole; a table sharing its list item with other content leaves that content untouched; a top-level table (no list) converts to plain paragraphs, never inventing list items outside a list context; the paste regression check passes.
