`✅` **Done — shipped this session. 20/20 in `ui-audit/verify-notes-caret-a11y.mjs`, with a known-good arm.**
- Verify: sandbox
- **HIS REPORT:** *"Can you make it so that my cursor shows where it should… those little red marks are where my cursor goes. It's just an accessibility thing that I've added to my PC, but it doesn't seem to match very well on this module."* That is Windows 11's **Text cursor indicator**, which takes its rectangle from the accessibility layer and never from what is painted.
- **⛔ THE HYPOTHESIS IN THE BRIEF IS REFUTED, WITH MEASUREMENTS, AND THAT REFUTATION IS PART OF THE ANSWER.** It proposed that the boxes are CSS-`transform`-positioned, so Chrome would report their untransformed bounds. They are not: `computed transform: none` on every editing host, and painted geometry equals layout-tree geometry **to the pixel** at 80%, 100% and 200% zoom, scrolled and not (`diagnose-notes-caret-bounds`). The geometry this module controls was never wrong.
- **WHAT WAS ACTUALLY WRONG, dumped from the real accessibility tree:**

        note-title  →  role=textbox   editable=plaintext   multiline=false   ✅
        note-body   →  role=GENERIC   editable=richtext    multiline=—       ⛔

  The page title was a proper text control and the writing surface was not — a generic node that merely happens to be editable. **A generic node exposes no text pattern for a platform client to read a caret rectangle out of**, so the OS falls back to the bounds of the editable REGION, whose top-left corner is up and to the left of any box placed on the page. That is the direction he photographed, and it explains why the offset grows the further into the page the caret sits. Fix: `role="textbox"` + `aria-multiline="true"` (a textbox that does not say it is multiline is treated as a single-line field, whose caret rect is one line's geometry). Now `role=textbox editable=richtext multiline=true`.
- **⛔ THE HONEST LIMIT, stated rather than implied:** this repo runs on Linux and cannot read Windows' UI Automation. The harness proves the module now exposes a real multiline text control with a real caret, and that its painted and layout-tree geometry agree everywhere measured. It does NOT prove what Windows then draws. If he still sees the markers misplaced after this, the next step is his machine, not this code — and that is a `V###`-shaped question, not a null.
- **THE KNOWN-GOOD ARM IS THE PAGE TITLE** (DRIVER-SCROLL-IS-NOT-APP-SCROLL clause 6): it was already correct before the fix, so it is a value known independently of the code under test. If it ever stops reporting `textbox`, the harness is reading the tree wrongly and exits **2 as VACUOUS** rather than scoring the unknown arm.
