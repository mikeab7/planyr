`[x]` **FIXED THIS SESSION — root cause found by reading the evaluator, not guessed.** AUDIT-FIRST: all five (`NPV`/`XNPV`/`IRR`/`XIRR`/`MIRR`) were registered as EAGER (`fn`-style) functions, whose arguments the evaluator resolves by calling `evalNode()` on every argument node BEFORE the function body ever runs (`node.args.map(a => evalNode(a, ctx))`). `evalNode()` throws `#VALUE!` by design on a bare `"range"` AST node (`case "range": throw ferr(VALUE, "a range reference cannot be used where a single value is expected")`) — ranges are only ever meaningful inside a RANGE-AWARE (`rng`-style) function, which receives the raw argument NODES (not pre-evaluated values) so it can choose to flatten a range via the existing `colArray`/`isRangeArg` machinery `SUM`/`COUNTIF`/`INDEX`/`MATCH` already use. So the failure was unconditional and argument-position-independent: ANY range anywhere in these five functions' argument lists threw before their (correct) math ever ran, exactly matching the report's own discriminator.
`[x]` **THE FIX.** Converted all five registry entries from `fn` to `rng`. A new shared helper, `flattenArgs(argNodes, ctx, ev)` (beside `collectNums`/`isRangeArg`), expands any range/`[Column]`/named-range argument in place, in order, via `colArray`, and evaluates everything else via `ev()` unchanged — so every previously-working scalar/cell-reference call shape is untouched byte-for-byte, and a range now just contributes its values in natural (row-major) order. `NPV`'s cash-flow tail and `XNPV`'s/`XIRR`'s legacy interleaved-scalar tail both route through it; `IRR`/`XIRR` additionally recognise Excel's own two-argument array shape — `IRR(values,[guess])` and `XIRR(values,dates,[guess])` — whenever the values (or values/dates) slot holds an actual range, zipping values against dates by POSITION rather than flattening-then-chunking (the first cut of this fix got that wrong for `XNPV`'s two-range form specifically — flattening `[I1:I5, H1:H5]` into one list and chunking it into consecutive pairs mispaired every value against the wrong date and produced a nonsense multi-hundred-percent rate; caught immediately by a live headless re-run, not shipped). A supplied `guess` only seeds `solveRoot`'s Newton step (its bisection fallback finds the same root over the fixed bracket regardless of starting point) — it is never treated as an extra cash flow. **`MIRR`'s argument order changed** to Excel's own trailing-rates shape, `MIRR(cf1, cf2, …, financeRate, reinvestRate)` — generalised so the leading cash-flow group may mix scalars and ranges, collapsing to plain `MIRR(values, financeRate, reinvestRate)` when `values` is one range (exactly the report's own `MIRR(I1:I5,0.08,0.08)`). This replaces the engine's previous non-standard rates-first ordering (`MIRR(financeRate, reinvestRate, cf0, cf1, …)`, which the report's own discriminator does not use and no real spreadsheet uses) — the range fix would otherwise have permanently frozen a wrong argument order in place; the two existing MIRR identity tests were updated to the new order, same math, same assertions.
