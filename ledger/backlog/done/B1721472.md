`[x]` **FIXED AND VERIFIED THIS SESSION — the ambient hover tooltip now only ever appears for a genuine hit, on every raster-painted layer, not just FEMA.**
- **Root cause.** Roughly half the GIS layer registry (Drainage channels/BKDD, wetlands, the City of Houston mains, HCFCD, the RRC wells, the CCN/MUD territories, …) is a server-rendered PICTURE (an ArcGIS MapServer `/export` image), not real features in the DOM. The only way to know whether the cursor sits on something in one of those layers is to ask the service's `/identify` operation — so the existing hover pipeline (`lib/rasterIdentify.js`'s debounced controller, wired through `lib/rasterIdentifyMap.js` for the map finder and `SitePlanner.jsx`'s `ensureRasterHover` for the planner canvas) fired that request on every cursor-rest position and RENDERED every outcome, including the non-hit ones: `"pending"` → the literal "Checking…" text, then `"none"` ("Nothing here"), `"unsupported"`, or an honest network-error message — all appearing over bare ground with nothing drawn there. B1490144 (2026-09-10) had already hit exactly this for FEMA and fixed it by excluding that ONE layer from cursor identify entirely (`identify:false`/`canvasIdentify:false` on the registry row) — which is why the owner remembered FEMA as "fixed" — but every other raster layer was deliberately left on the old, ungated path (that item's own comment says so).
- **The fix — generalised WITHOUT losing the feature.** A raster layer still has no client-side way to hit-test a picture, so the debounced `/identify` request itself is unavoidable and unchanged (same state machine, same tests, same debounce/abort/timeout behaviour — `rasterIdentify.js` and its 59-case unit suite are untouched). What changed is what the two RENDER sites do with a non-hit outcome: they now drop/never show the tooltip for `pending`/`none`/`unsupported`/`error`, and render ONLY on a genuine `hit`. Two call sites, one shared root cause:
  - `lib/rasterIdentifyMap.js`'s `attachRasterIdentify` (used by both the map finder and, via `rasterIdentifyLazy.js`, warmed the same way — this is the shared "hover/mousemove listener used across multiple GIS layers" the brief asked to audit): `render(state, at)` now returns `dropTip()` for anything other than `IDENTIFY_STATE.hit`, instead of building a Leaflet tooltip from `stateMessage(state)`. The dead transient-dismiss-timer machinery (`TRANSIENT_MS`, `dismissTimer`, `clearDismiss`) is removed with it — there is nothing left to dismiss once a non-hit state never renders.
  - `SitePlanner.jsx`'s `ensureRasterHover` (the planner canvas's own hover path — the backdrop map is `pointer-events:none`, so this is the ONLY way the planner can ever ask a raster layer anything): its `onState` callback now calls `setGisHover(null)` for anything but `IDENTIFY_STATE.hit`, instead of setting `{ ...anchor, note: stateMessage(state) }`. The now-unreachable `gisHover.note` render branch in the hover-readout JSX is removed too.
  - **A DELIBERATE action stays fully honest, unchanged.** The map finder's click-to-pin popup (`attachRasterIdentify`'s `onClick`) builds its own separate controller with its own `onState` that still renders every outcome via `readoutNode(state)` — LOUD-FAILURE keeps governing an action the user actually asked for (a click); only ambient mouse movement goes silent on a non-hit.
- **Applied globally, not just to Drainage channels, per the brief.** Both fixed functions are the SHARED mechanism every raster-painted layer's hover goes through (confirmed by reading `lib/layers.js`'s `rasterIdentifyLayers`/`identifyCapable` gating, which every raster row shares) — there is no per-layer branch to have missed. FEMA's own `identify:false`/`canvasIdentify:false` opt-out (B1490144) is untouched and still means FEMA never even reaches this path; every other raster layer now behaves the way the owner remembered FEMA behaving, without losing the ability to name a real hit.
