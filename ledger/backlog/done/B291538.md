- **⛔ AUDIT-FIRST — THE REPORT'S SYMPTOM IS REAL AND ITS MECHANISM IS NOT.** There is no double-click→fullscreen handler anywhere in the codebase, and a sweep of sixteen double-click points across the note pane put the caret in the document at every one of them. What exists is a **bare `f`** bound at the window to "toggle fullscreen", excluded only when the press TARGET is itself a typing surface. So the instant any gesture leaves focus on `<body>` — which a press on inert chrome does — the next letter typed is read as a command and is gone. **Measured: with a note open and focus on `<body>`, one bare `f` entered real fullscreen and the keystroke vanished.** That is his bug, and it fires on any gesture that does not land focus, not only a double-click.
- **THE FIX, and it is the rule rather than the case: a bare letter is never a global command while a writeable document is on screen.** The shortcut checks for a live, PAINTED `contenteditable` (the same `getClientRects()` probe the header already uses for its keep-alive gate, because workspaces are kept mounted-but-hidden) and stands down when it finds one. Where there is no document — the Site Planner canvas, the map — the bare `f` is untouched, which is why `verify-new1-fullscreen.mjs` still passes 32/32.
- **AND FULLSCREEN GETS THE HOME HE ASKED FOR — both halves.** A **visible control** in the header's row-1 right zone (it had none at all before: the only ways in were one letter and folklore), and **Ctrl/⌘+Shift+F**, checked ahead of the typing-surface guard so it works with the caret inside a note.
