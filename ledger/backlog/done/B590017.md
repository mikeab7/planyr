`✅` **Done — shipped this session. Measured at four positions down a 620px window.**
- Verify: sandbox
- **⛔ THE OLD RULE WAS A GUESS, AND THAT IS THE WHOLE DEFECT:** `top: Math.min(at.y, innerHeight - 420)` — a hard-coded **420px estimate of the menu's own height**, never checked against what rendered. A menu taller than the guess still ran off the bottom, and the row that fell off was the LAST one, which is `Delete this box`.
- **WHAT LANDED:** `placeMenu` is a PURE rule over the MEASURED assembly, applied in a **layout effect** (before paint, so the menu is never seen in the wrong place and then corrected). Prefer below-right of the pointer · **FLIP above** when it will not fit below · clamp into the viewport with a margin · a menu taller than the viewport starts at the TOP, because clamping the bottom would push the first rows off. `visualViewport` is preferred over `innerHeight` deliberately: on a maximised window it already excludes the taskbar, which is exactly his case.
- **⛔ THE WHOLE ASSEMBLY IS MEASURED, STRIP INCLUDED** — measuring only the list would reproduce the same class of error one layer down.
- **MEASURED:** at screen y=499 and y=579 in a 620px window the menu **flips** and `Delete this box` lands at 493 and 573 — fully on screen. Mutation-proven: restoring the 420 guess fails 7 tests and **2,046 placements** in the property sweep.
