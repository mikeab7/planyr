`[x]` **ROOT-CAUSED (a real, provable axis-misjudgment in `hostClampOf`'s geometric heuristic — the same species of bug B385041 already fixed once for a building's own dock axis) AND FIXED, with a mutation-proven regression test.**
- **THE MECHANISM.** `hostClampOf(el)` decides which host-local axis ("x"/"y") faces away from the building a bonded element (a dock zone, a side-parking row, a wall strip) hugs, so a resize can pin the HOST-facing face and grow the FAR face outward. It picked that axis with a geometric guess — `(|l.x|-host.w/2) >= (|l.y|-host.h/2) ? "x" : "y"` — a proxy for "which side is this element on" that silently assumes the element's ALONG-the-wall offset stays smaller than its PERPENDICULAR one. That assumption breaks for a short employee-parking field sitting off-centre on a long wall (or one a dog-ear bump-out has lengthened): its along-wall offset can genuinely exceed its depth offset, so the heuristic names the wrong axis. `clampToHost` then re-pins the WRONG axis on a depth-only edge drag — the ALONG-wall position snaps toward the wall's centre and (via the downstream `relayoutWallKids`/`sideParkAlongRun` side-park refit) the field's run resets toward the span default, while the depth itself may still track — which reads exactly as the owner's report: "drag the south-edge handle, the field grows from the wrong edge" (and jumps/resizes along the wall in the same gesture).
- **MEASURED, not just reasoned.** A 60 ft employee-parking field on a 200 ft LEFT wall, its own centre 115 ft along that wall (still genuinely ON the wall — its near end sits at 85 ft, inside the wall's 100 ft half-length): `|l.x|-host.w/2 = 9` (half its own depth) vs `|l.y|-host.h/2 = 15` — the heuristic calls this a top/bottom-wall element. Confirmed live in a real browser: dragging the field's depth-axis edge grip away from the wall moved its along-wall position (`cy`) and reset its along-wall length (`w`) even though only the depth grip was dragged.
- **THE FIX.** `hostClampOf` now reads the element's own STORED wall tag first — `el.sideParkSide` / `el.sidewalkSide` / a dock zone's own side (via the existing `zoneSideOf` helper) — and only falls back to the geometric guess when no such tag exists (an arbitrary attached rectangle with no wall role). This is the identical "trust the stored fact, don't re-derive it" pattern `dockZones`' `dockAxis` fix (B385041) already established for the same reason: a heuristic that infers a stable fact from live geometry re-derives a WRONG answer the moment geometry moves off the heuristic's implicit assumption, and the fact was already sitting on the element the whole time.
- **SCOPE, checked directly:** the fix only changes which axis/sign `hostClampOf` reports when a stored wall tag exists; it changes nothing for an element with no such tag (still the old geometric guess, unchanged), and nothing for the `gap`/`outX`/`outY` math itself (unaffected — those still measure the real perpendicular clearance regardless of which axis wins). Existing dock-zone e2e coverage (`side-park-explode-sidewalk.spec.js`, 2/2) re-run clean; `dock-zone-anchor.spec.js`'s 4 failures reproduce identically on a clean, unmodified `origin/main` checkout (a pre-existing incompatibility with the app's current Dashboard-landing route, unrelated to this fix — confirmed via `git stash`).
- **DRIVE-BY FIX, found while instrumenting this bug (not scope creep — the file was already open for this exact investigation): a stray literal NULL BYTE in `siteModel.js`** (`` `${host.id}\0${side}` `` instead of `` `${host.id} ${side}` `` in `normalizeWallKids`'s gap-bucketing map key) was making the whole file register as binary to `grep`/ripgrep-based tooling, silently hiding every future text search over it. Harmless as a Map key (JS strings tolerate embedded nulls) but actively hazardous to tooling; replaced with the evident intended space, one byte, no behavior change.
- **A second, related discovery — NOT fixed here, filed for its own item rather than silently left:** `normalizeWallKids`'s own "was this field torn off its host" self-consistency check (`siteModel.js`, the `acrossErr`/`alongLimit` guards) will legitimately re-centre an unstamped or borderline-off-default side-parking field on mere LOAD, independent of any resize gesture — matching the documented, deliberate "no stamp ⇒ span default" migration policy (dogEar.js NEW-2), but a plain body MOVE of a side-parking field (dragging it along the wall without an edge-drag) never writes the `sideParkFit` stamp that would make the new position survive that heal. This is a real, separate usability gap (a plain move doesn't persist), not the reported resize-direction bug, and is intentionally NOT touched here — see B1749155 below.
