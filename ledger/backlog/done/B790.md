`[x]` **IMPLEMENTED — a toggled-on raster overlay no longer reports "loaded" (blue) the instant it's added; it stays "loading" until the server-rendered image ACTUALLY lands, and flips to amber "source slow or unavailable — the map may be missing data" if the export never arrives.** This is the owner's exact complaint from the 2026-07-11 NFHL slowdown ("FEMA showing blue as if it's working, but nothing paints"). AUDIT-FIRST root cause found in the live code: `syncOverlayLayers` (`lib/layers.js`) called `onStatus(k, "loaded")` **optimistically on `addTo(map)`**, before the export `<img>` resolved — and esri-leaflet fires NO error for a silent hang, so a degraded agency (FEMA held/killed exports 20–30 s) left the row on a false blue forever.
- **Fix:** extracted the status machine into a pure, unit-testable `wireRasterStatus` (`lib/layerRequest.js`, leaflet-free): status starts at "loading"; only a real `'load'` event → "loaded"; a **stall watchdog** (`RASTER_STALL_MS = 15 s`) flips to a NEW amber `"slow"` state when no `'load'` lands in time; a real error event → "failed" (or one proxy→direct fallback first, which no longer claims a premature "loaded"); a later `'load'` clears "slow" back to "loaded" (recovery on a pan). `layers.js` now wires through it and reports "loading" (not "loaded") on add.
- **Amber, not red (KEY DECISIONS palette rule):** RED (`--danger`) is reserved for a genuine error; a stall is "too slow, data may be missing," which is retryable — so `LayerPanel` renders `"slow"` on `--warn-text` amber with an inline reason, and `combineLayerStatus` ranks it just under "failed".
