**B36(e) — Abort in-flight evidence-layer fetches + guard against stale post-unmount renders** `[Site Planner / GIS]` (bug) #site-planner #gis  *(the fetch-AbortController sub-item of the 2026-06-15 bug-audit B36 cluster — recorded as a bold entry, NOT a `### B36` heading, so it doesn't read as a duplicate id; parent B36 stays OPEN for a/d — the county-resolution work tied to B13)*
`[x]` **DONE (Verify: live — V331; the Leaflet layers can't load in the node-only test env, so no unit test).** The two view-driven evidence overlays (`lib/evidenceLayers.js` — OSM Overpass power/hydrants, Mapillary detections) checked `if (!map) return` only BEFORE their `await`, so a fetch that resolved AFTER the layer was toggled off (`onRemove` nulls `map`) still ran `group.clearLayers()`, drew markers into the detached group, and fired `onStatus("loaded")` for a layer the user had turned off — and nothing cancelled the now-useless request.
- **Fix:** (1) a post-`await` `if (!map) return` mount guard in BOTH `overpassLayer` and `mapillaryLayer`, so a stale response never paints/reports into a detached group. (2) An `AbortController` on the Mapillary path (a direct, un-cached `fetch`): `fetchMapillary(bounds, token, signal)` forwards the signal; `onRemove` aborts the in-flight request; the catch swallows the resulting `AbortError`/`sig.aborted` silently (the removal owns the UI — no false "failed", no `lastKey` reset that `onRemove` already did). The Overpass path rides `gisCache.swr` (cached), so it is intentionally NOT aborted — aborting a cached fetch would poison the shared SWR cache; the mount guard alone is correct there (the request still warms the cache but never renders detached). Documented inline.
