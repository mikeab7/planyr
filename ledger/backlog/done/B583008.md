Dragging rightward shrank `room`, so the box reflowed under his hand; on release `moveNoteAnchor` commits only x/y, so the stored width came straight back and it sprang wide again. **B539648 replaced "narrow it" with "grow the page" at PLACEMENT and in the RESIZE drag, and the move drag kept the old rule.**

It was one function call.
- **THE FIX IS A SEPARATE FUNCTION, NOT A FLAG:** `moveAnchorPoint` has no width arithmetic in it at all, so a move cannot resize by any route. A boolean on `placeAnchor` would have left the arithmetic sitting in the move path for somebody to re-enable.
- **⛔ AND THE FIRST VERSION OF THE HARNESS WAS VACUOUS — IT WENT GREEN ON THE DEFECT.** It read the box five times during the drag with a 60 ms pause between reads. `fitAnchorBox` runs from a ResizeObserver and re-derives the rendered width from `data-anchor-w`, so a narrowing written to `style.width` alone is undone on the very NEXT FRAME: the box really does reflow, repeatedly, for one or two frames per pointer move, and a reader arriving 60 ms later always finds it restored. The measurement had to move onto the FRAME CLOCK (a `requestAnimationFrame` sampler inside the page). With teeth it reports `160–300` and the words wrapping 1 → 2 lines, on the right-edge cases, in both drag directions, at both zooms — and stays green on the mid-page cases that never failed. A second instrument bug was caught in the same pass: comparing unzoomed `style.width` against zoomed `getBoundingClientRect` failed every 200% row, including the correct ones.
