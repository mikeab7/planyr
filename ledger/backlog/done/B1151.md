- **AUDIT-FIRST, what the code actually did.** A measurement was the LAST drawn object with no style of its own. Its colour was hardcoded at the single place it was painted — `const mcolor = warn ? "#b45309" : PAL.accent` — and no measure object carried a `stroke` / `weight` / `dash` / `fill` field anywhere in the model, while a markup shape beside it had the full set reachable from the properties panel. So double-clicking an area measurement opened a panel with nothing to style. The report is exactly right.
- **THE FIX — one resolver, the same editing surface, every mode.** `lib/measureStyle.js` (new, pure) is now the ONE place a measurement's paint is decided: stroke, line weight, line style, and for a closed area a fill colour and fill opacity, for **all four modes** (line · polyline · area · count), not just area. The properties panel reuses the markup panel's own controls — the shared `ColorField` (so measurements inherit the recently-used-colours list), the shared `DASH_OPTIONS` list, the shared live-pick/one-undo-frame writers — rather than standing up a parallel surface.
- **Born with the user's Standards defaults**, the `parcelDefaultStyle` mechanic exactly (B929): `measureDefaultStyle(settings)` is stamped at all four creation sites, a new **Standards → Measurements** section sets them, and the panel's one Apply pushes them onto measurements already drawn (`standardsApply.applyMeasureStandard`, the parcel WRITE mechanic — measurements are stamped, not resolved at render). Ladder: built-in < account default ("Save for all projects") < project default < per-measurement override. A value equal to the built-in is deliberately NOT stamped, so an untouched plan gains no keys and renders byte-identically.
- **THE ONE DELIBERATE EXCEPTION IS PRESERVED, and it is now tested rather than incidental.** When the drawing is UNCALIBRATED the measurement is forced amber over the user's colour — for both the line and the fill — because that is a CORRECTNESS signal ("this number is in raw units, not real feet"), not decoration. The colour is not destroyed, only overridden: it returns the moment the sheet is calibrated, and the panel says so in plain English. The owner rule that a selected measurement carries **no × delete badge** also stands, unchanged.
- **Double-click opens Properties** — verified live rather than assumed; it already worked (`isDoubleTap` in `startMoveMeasure`, B750 parity) and now has a guard so it cannot regress.
- **A SECOND, UNRELATED DEFECT FIXED IN PASSING, found while wiring this.** Every colour chip in these panels was blank: the callers passed a style override containing `background: "var(--surface-raised)"`, which is spread ON TOP of the current colour `ColorField` paints as the chip's background. So the control you click to change a colour showed no colour — in the markup panel and the parcel-drawing panel too, not only the new one. One word removed in three places; guarded.
- **Sandbox evidence.** 31 unit assertions in `test/measureStyle.test.js` — every mode round-trips a FULL style through save and reload, a new measurement picks up the Standards defaults, the built-in resolves to the pre-styling render byte for byte (weight 1.5 / +1 selected, fill 0.10 / +0.06 selected), and the uncalibrated amber still wins over a user colour — plus 22 wiring guards in `test/measureWiring.test.js` and the headless harness `ui-audit/verify-measure-presentation.mjs` (a green dashed heavy run and a violet count both painting their own colour, light and dark, the full control set present in the panel). `npm test` 6547 green · lint 0 errors · build green.
