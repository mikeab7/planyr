- Verify: sandbox — this is a pure state-machine defect (which window of already-retained frame history a capture reads), fully reproducible and provable with a scripted frame series; no browser, no GIS, no auth needed. ATTEMPT-BEFORE-YOU-PARK applies and was followed: driven directly rather than filed as `Verify: live`.
- **ROOT CAUSE, read directly from `perfTrigger.js`/`perfRecorder.js`.** `triggerState(s).windowMeanMs` is the LIVE sustain window `feedFrame` maintains — a rolling ~2-second (`sustainMs`) buffer of the MOST RECENT frames. `fire()` (the AUTO-capture trigger) explicitly **RESETS** that window the instant it fires (`s.winHead = s.winTail = s.winN = 0`), so the next few seconds of frames rebuild it from scratch. `perfRecorder.js`'s `capture()` used `ts.windowMeanMs`/`ts.slowFraction` — that same LIVE window — for a MANUAL capture's headline numbers (`windowMeanMs: kind === "auto" ? v.windowMeanMs : ts.windowMeanMs`). A manual press taken shortly after an auto-fire (or after any lag has simply ended on its own) reads a freshly-reset window that has only had time to refill with FAST, recovered frames — reporting the tab as smooth exactly when the owner pressed the button believing it was not.
- **THE FIX — read the FULL retained history, not just the live 2-second window.** `worstWindow(times, deltas, {spanMs, minFrames, slowBar})` (new, `perfTrigger.js`) is a pure two-pointer sliding-window-maximum scan over the recorder's already-retained frame track (`ringOrderSince(_frames, since)`, up to `captureWindowMs` — tens of seconds, far wider than the live 2-second sustain window) — it returns the highest-mean `spanMs`-wide sub-window found ANYWHERE in that history, using the SAME `sustainMs`/`sustainMinFrames` shape the live trigger's own window uses so "a window" means the same thing in both readings. `perfRecorder.js`'s `capture()` now computes this for EVERY capture (auto and manual alike) over the same `order`/`deltas`/`times` it already builds, and reports it alongside the existing live reading as five new fields: `worstWindowMeanMs`, `worstWindowSlowFraction`, `worstWindowRatio`, `worstWindowFrames`, `worstWindowAtMs` (the last one a relative offset into the capture window, the same convention `gaps`/`tasks` already use) — so a reader gets BOTH "how it's running right now" (unchanged) AND "the worst it got in the last stretch," clearly two different numbers rather than one number silently meaning two different things depending on when the button was pressed.
- **THE PRIVACY ALLOWLIST WAS UPDATED, NOT BYPASSED** — the five new fields were added to `CAPTURE_NUMERIC_KEYS` in `perfCapture.js` and populated in `buildCapture()` through the existing `num()` helper (which already omits any non-finite value, so a capture with too little retained history to find a worst window simply carries none of the five keys — never a fabricated zero).
- **VERIFIED — `test/perfWorstWindow.test.js` (6 new tests):** null/degenerate-input handling; picking out an obviously-worse window among fast neighbours; `minFrames` never letting a too-small window win, even beside a single huge spike; `slowFraction` computed correctly against a supplied `slowBar` (and omitted when none is given); and the exact reported scenario reproduced end to end — a ~2-second bad window (mean over the slow bar, matching the real 288.6 ms/0.67 report) followed by ~0.6 s of recovered fast frames, where `worstWindow()` still finds and returns the bad window (anchored at when it actually happened) while a LIVE-window-only reading over the same final state — the pre-fix behavior, computed inline in the test for direct comparison — lands on the recovered tail instead, reproducing the exact defect. `npx eslint` clean on every touched file; `test/perfRecorder.test.js` (47 tests, incl. the structural no-per-frame-allocation guard, which `worstWindow` is correctly excluded from — it runs once per capture, not once per frame) and the broader perf suites (`perfBudgetPolicy`, `perfBudgets`, `perfInstrument`) all pass unmodified.
