- **THE BUG, measured directly (`beginWidthDrag`, `NoteEditor.jsx`).** The page's own left edge is architecturally pinned in content-space — it never moves, by design, since NOTES-PAGE-GROWTH's own history (`/CLAUDE.md`'s "-1" recurring-bug-family entry) already rejected letting it move. Dragging the LEFT grip therefore grew the total width and scrolled the mat by the identical amount so the RIGHT edge held its screen position — correct — but that same scroll ALSO carried everything else painted in the mat left by the identical amount, content included, because nothing distinguished "the sheet's own boundary, which the pointer is dragging" from "the words inside it." Measured on the real built app: a 90px left-drag moved the body text's own on-screen X position left by 90px, matching the report exactly.
- **THE FIX reuses an ALREADY-BUILT, ALREADY-TESTED mechanism rather than inventing a new one — `sheetGrowLeft`, NOTES-FREE-PLACEMENT's own left-padding growth (built for a free-placed box overflowing the page's left edge), together with the existing `useLayoutEffect` a few screens down that measures the body's on-screen position and scrolls to hold it fixed whenever `sheetGrowLeft` changes.** The left grip's live drag now grows `sheetGrowLeft` (the gap between the sheet's own fixed edge and where the body starts) by the same amount the width grows, instead of leaving that gap untouched — the SAME scroll compensation formula as before now corrects for a real shift of the body caused by the wider gap, so it holds the body still, and the sheet's own rendered left edge — whose content-space position never moves — is what is left to visibly track the pointer. New pure `leftWidthGripPad(startPad, delta)` (`notesPageWidth.js`) composes across a shrink-then-regrow round trip and floors at 0, mirroring `topEdgeCompensation`'s own shape for the vertical twin of this problem.
- **⛔ A SECOND, INDEPENDENT BUG FOUND BUILDING THIS FIX'S OWN VERIFICATION, CAUGHT BEFORE IT SHIPPED: the measurement effect DOUBLE-COUNTED the pad on commit.** `pinnedPageWidth` (the content-column target derived from the committed total width) was computed with no knowledge that part of that committed total was already spoken for by the drag's own pad, so on release the page jumped a SECOND time by the pad's own amount (measured: a 90px drag correctly held at 670px total for the whole live gesture, then jumped to 760px — 90px too many — the instant the mouse came up). Fixed by subtracting the currently-active pad from `pinnedPageWidth`'s own baseline before it is used as the content-column floor, so `growLeft + padX + contentW` sums back to exactly the width that was committed, with real content overflow still composing past it via the pre-existing `Math.max`. Caught and fixed within this same session, before verification — never shipped.
- **NOT persisted as a distinct concept — an accepted, precedented trade-off, mirroring `heightTopPadRef`'s own header for the vertical twin of this problem.** The pad lives in a ref, not the document; a RELOAD settles at the app's ordinary right-grown rest position with the same STORED total width (confirmed: the committed `pageWidth` attribute round-trips exactly through a real reload), losing only the "grew from the left" illusion, never the resize itself.
