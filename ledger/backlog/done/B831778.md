### B831778 — Map visibility decoupled from which rail tab/toolbar mode is active `[Site Planner / Map]` (bug/feature) #site-planner #ui #comps  *(same owner chat block — the LOAD-BEARING requirement the whole redesign exists to satisfy: "if selecting the Comps tab hides site pins, the design has failed and Michael's original objection is back." Minted **B831778** from the same reserved block. DEDUPE-FIRST — net-new; no prior item ties map-pin visibility to a UI tab at all, so there was nothing to amend.)*
`[x]` **✅ DONE — Sites and Comps are independent checkboxes in the Imagery & layers panel, BOTH ON by default; switching the tab or the toolbar switch changes what you BROWSE/what an add-action is ABOUT, and provably never changes what's DRAWN.**
- Verify: sandbox — pure UI state + a source-level proof; no GIS/timing/auth dependency (the map-pin geometry itself needs no network — it's drawn from already-loaded `sites`/`comps` props).
- **THE MECHANISM.** Two new persisted booleans, `showSitesLayer`/`showCompsLayer` (`planarfit:mapShowSites:v1`/`...mapShowComps:v1`, default true), rendered as plain checkboxes ("Sites (N)" / "Comps (N)") at the top of the Imagery & layers panel. The two map-layer-build `useEffect`s (`sitesLayerRef`/`compsLayerRef`) now filter on `showSitesLayer ? sites : []` / `showCompsLayer ? comps : []` — added to each effect's own dependency array — and **`mode` never appears in either effect, anywhere, not even in a comment** (see the test below for why that last clause is enforced, not just claimed).
- **⛔ THE PROOF, because "I read the diff" is not evidence for a class of bug this repo has a named rule about (VIEW-INDEPENDENT-ONCE's sibling: a control's DISPLAY state contaminating a DIFFERENT control's DRAW state).** `test/mapModeDecoupling.test.js` extracts both real `useEffect` bodies straight out of `MapFinder.jsx` (brace-balanced, comments stripped) and asserts neither ever contains the bare identifier `mode`. **Proven RED first, for real, not asserted:** the extractor's own teeth-proof runs it against a deliberately mode-gated fixture and confirms it flags the mention; when first run against the ACTUAL file it genuinely failed — both effects' own explanatory comments happened to use the word "mode" while describing what NOT to read, a real false-positive the comment-stripping step then fixed, which is itself evidence the extractor was reading real source and not a rubber stamp. Green after the comment-strip fix, on the true final effect bodies.
- **DOM-level companion proof**, since a source read doesn't need seeded data but a human clicking through would want to see it too: `ui-audit/verify-map-toolbar-rebuild.mjs` drives the real built app, confirms both checkboxes exist and default checked, then flips the toolbar switch to Comp mode and re-reads both checkboxes — unchanged, at all three widths (900/1400/2400).
- **Armed-state safety net, filed as its own item (B831781) but load-bearing here too:** while the checkboxes prove pins stay drawn regardless of tab, B831781's ring is what stops a USER ACTION (a raw map click while Comp mode is armed) from being taken while believing Site mode is active — the two together are what the brief calls "the design works."
