`[x]` **REPRODUCED live, before writing any fix** (a throwaway two-building fixture, the predecessor of this item's `ui-audit/verify-grid-view-scale.mjs`): a 200×150 building and a 1200×600 building on one plan, at the identical zoom — the large building drew its full 31-line column grid, the small one drew none. Screenshot kept in the PR.

**ROOT CAUSE, confirmed by reading the code before writing the fix (AUDIT-FIRST).** `SitePlanner.jsx` gated the interior column grid at BOTH its render sites (the ordinary rect branch and the reshaped-polygon branch) on `Math.min(w, h) >= FEAT_BTN_MIN_PX` (72px) — **that building's own** rendered footprint in screen px. `FEAT_BTN_MIN_PX` (B225) is the right gate for a different question — does THIS building have room on screen to seat the +/− edit-control cluster — and stays correct there; it was never the right gate for "is the drawing zoomed in enough to read a column grid," because a building's footprint size varies building to building. So the reveal zoom was a function of which building you asked about, not of where the map was zoomed — exactly the mixed state reported.

**THE FIX.** `buildingGrid.gridLinesVisible(ppf)` — a pure function of the render scale ALONE (screen `ppf`, or the export sheet's own px/ft via `lfPpf`), with no building size, position or rotation term reaching it. Both `SitePlanner.jsx` call sites now gate on `gridLinesVisible(lfPpf || ppf)` instead of comparing a per-building pixel size. The threshold (`GRID_MIN_PPF = 0.32 px/ft`) is derived from the grid's OWN typical bay size (`GRID_DEFAULTS.bayMin` — the tightest end of the industry flex band, never any one drawn building), picked so the narrowest common bay still renders at least 16px wide before the mesh appears — below that a column grid reads as a smear rather than individual lines.

**CHECKED, per the dispatch brief, all via `ui-audit/verify-grid-view-scale.mjs` (real headless Chromium against the built app; needs no sign-in and no external GIS):**
- **one very-large + one very-small building on one plan** — a 25-sample ppf sweep across the threshold never shows a mixed frame; the sweep is proven capable of showing the OLD bug (`test/gridViewScale.test.js` replays the retired per-building rule byte-for-byte and confirms it genuinely disagrees with itself somewhere in the identical range, so a vacuous fixture isn't quietly passing).
- **all buildings the same size** — sanity check, flips together.
- **rotated buildings** (37°/53°) — identical sweep, identical result; the gate reads only `ppf`, which carries no rotation term by construction.
- **a building sitting partly off-screen** — panned so ~92% of a building's footprint is outside the viewport; the grid decision (drawn/absent) matches the fully-on-screen read at the same `ppf` in every case tried, both above and below the threshold.
- **continuous zoom, no stagger** — the sweep is 25 discrete `ppf` steps and every one is all-or-none; there is no code path left that could show one building's grid without the others', because one render pass now reads one `ppf`/`lfPpf` value for every building on the plan.
- **the exported/printed sheet** — two single-building plans (small-only, large-only) exported from two very different LIVE trigger zooms (0.05 ppf and 1.2 ppf); in every case both plans agree with each other, and the export's own grid-line count doesn't move with whichever live zoom triggered it (the sheet already reasons at its own `exportLabelScale.js` scale — unchanged by this fix, just no longer defeated by a per-building term).

**Threshold trade-off, stated as the brief asked for.** A single global `ppf` floor means: a building smaller than one bay module in both directions never shows interior lines at ANY zoom — it has none to draw (`divideSpan`'s own "a short span is a single bay" rule, untouched by this fix) — and a small multi-bay building's bays necessarily look no more generous than a large building's do at that same zoom. At `GRID_MIN_PPF` (0.32 px/ft) the tightest common module (a 50ft bay, `GRID_DEFAULTS.bayMin`) renders ≈16px wide and the typical 56–58ft bay ≈18–19px — legible individual hairlines rather than a smear, at the sizes that actually appear across this repo's own fixtures and backlog history (roughly 300–900ft building spans). No per-building carve-out was reintroduced to chase a better-looking number for any one size — the brief explicitly forbade that, and this fix doesn't do it.
