### B2061329 — iPhone: tapping a box (even the one you are typing in) dropped the keyboard; no way to delete a box from the keyboard `[Notes]` (bug) #notes #mobile  *(Claude Code dispatch block "NEW-3," adversarial iPhone review 2026-09-29, sent 2026-10-04)*

`[x]` **Still reproduced on current main** (not already fixed): the new box was never marked editing, so a tap back into it took the stage-1 path (`preventDefault` + `setEditingId(null)` + `editor.commands.blur()`).
`[x]` **Fix:** (1) `commitPendingPlace` now names the new box (`addNoteAnchorAt` takes an optional `aid`) and marks it selected + editing in the same tick, so the first tap into it is never a stage-1 tap on ANY device. (2) On a TOUCH press (`lastPointerTypeRef`), `focusFromMat` skips stage 1: the box becomes selected + editing and the press is left to the browser, which puts the caret at the tap point inside it — no blur, keyboard stays up, box A → box B costs one tap. Picture boxes keep stage 1 (no words to enter). (3) Stale-caret Backspace (B1555152 / B434416) is guarded differently on touch: there is no stale caret, because the caret is placed natively inside the tapped box and the box is marked editing, so Backspace is routed to its text. Desktop's stage 1 + blur is untouched (known-good arm below). (4) Backspace on an EMPTY box removes it on touch (`selectionKeyDown`'s editing branch; touch only).
`[x]` **Harness:** `ui-audit/verify-notes-touch-box-tap.mjs` — WebKit hasTouch+isMobile, real `touchscreen.tap`: tap inside the box you just typed in → focus stays, zero `focusout`, box selected+editing, caret moved to the tap; tap A→B same; Backspace on an emptied box removes it; known-good arm = desktop mouse click still takes stage 1. Also re-ran WebKit `verify-notes-touch-place` / `-touch-landing` (green).
