### B2151073 — Phone Properties sheet: the sheet's top rows can end up above the top of the screen when iOS scrolls the view, and a field low in it is not brought into view `[Site Planner / phone Properties sheet]` (bug) #site-planner #ui #mobile  *(Found by the 2026-10-06 live signed-in WebKit pass (B2151072): `ui-audit/verify-phone-typing.mjs --live` — "Building number — FIELD visible above the keyboard — field 85–129 vs visible 109–388", iPhone 15 descriptor, the model where `innerHeight` stays tall (the production iOS 18.7 telemetry shape), 1 run in 2. Minted from this branch's reserved block. DEDUPE-FIRST: B1215682 built the sheet, B2088384 the keyboard work, B2046224 Food's twin — none covers "scrolled view" geometry. Net-new.)*

`[x]` **What was wrong — two faults, both measured, neither visible in any earlier harness because both need iOS to have SCROLLED the view (`visualViewport.offsetTop` > 0), which is what real iOS does to reveal a field.**
  1. **The sheet stood taller than the visible area.** `keyboardInsetPx` subtracts the scroll (correct for the sheet's BOTTOM edge, which must sit on the visible area's bottom), but the height clamp read `layout − inset` as "room above the keyboard" — that is the visible height PLUS the scroll. So with the view scrolled by 130 the sheet's top edge sat 83 above the visible area on the iPhone 15 descriptor (sheet top 47 vs visible top 130; 79 vs 130 in the shrinking-`innerHeight` model) and its first rows — "Building number" — were off-screen.
  2. **The field-reveal never ran when iOS scrolled by the keyboard's FULL height.** `keyboardBand` (`phoneTyping.js`) detected the keyboard as `layout − visible − offsetTop > 120`; at full scroll that is 0, so it concluded "no keyboard" and returned before scrolling anything — a field on a short sheet's bottom edge stayed half under the keyboard (found while testing fault 1: shrinking the sheet exposed it; on main the taller sheet only hid it).
`[x]` **Fix:** `propertiesSheet.js` `keyboardHeightPx` (layout − visible height, scroll-free) + `sheetMaxHeightForKeyboard` (visible height − 24, applied as a CSS `max-height` so it bites at once — NOT through the sheet's own 220 ms height animation, which the page's field-reveal would measure half-done); `phoneTyping.js` `keyboardBand` now treats "visible area shorter than layout" as the keyboard whatever the scroll, and `revealTarget` measures "does the whole edit card fit" against the room the card actually scrolls in (a short sheet's scroller), not the keyboard-free band. Tests (red first): `test/propertiesSheet.test.js` (+5), `test/phoneTyping.test.js` (+3).
`[x]` **Browser proof, red → green on the same rows** (`ui-audit/verify-phone-typing.mjs`, stub backend, WebKit, both phones × both iOS models): a new permanent row "site — Properties, view scrolled late by iOS" focuses the sheet's first fields, scrolls the view the way iOS does, and requires the SHEET'S TOP EDGE inside the visible area AND the field visible. **main 1106/1118 (the 12 new rows red: sheet top 79/47 vs visible top 130) → fix 1118/1118.** Properties surface alone, fix: 276/276 on two consecutive runs (main passed the 106 older rows of that surface — none of them looked at the sheet's top edge).
