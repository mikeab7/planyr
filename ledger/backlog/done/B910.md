### B910 — Clicking a measurement does nothing / gives no feedback on repeated clicks `[Site Planner]` (bug) #site-planner #selection #ui  *(owner-dropped 2026-07-21 as "NEW-1"; minted **B910**)*
`[x]` **FIXED + sandbox-verified this session (build green · 13-test unit lib · 2 headless e2e specs pass logged-out).** On the canvas you draw a Distance/Area/Perimeter/Count measurement, then click it — and nothing happens: no selection, no handles, no × delete badge, no hint. Root cause (both candidate causes in the report confirmed): the Measure tool **stays active after you draw** (deliberate — so you can measure many things in a row), but the measurement's transparent hit target AND `selectMeasure` both gated on `tool === "select"`, so the measurement you'd just drawn silently swallowed every click. Every OTHER drawn item is grabbable the instant its tool hands back to Select (markups/roads call `setTool("select")` on commit, e.g. `SitePlanner.jsx:3711`); measurements never do, so they were uniquely un-clickable.
- Verify: sandbox — CLOSED (green build + `test/measureHit.test.js` (13) + `e2e/measure-select.spec.js` (2, logged-out) all pass; the interaction is fully exercisable on a blank site with no auth / no GIS, so per ATTEMPT-BEFORE-YOU-PARK it was driven headless here, not filed for a live pass).
- Origin: filed 2026-07-21 from chat ("NEW-1").
- **Fix (`SitePlanner.jsx` `selectMeasure` + the three measure hit targets):** (1) the hit target's `pointerEvents` now goes live in the **Measure tool too** (`canGrab = tool === "select" || tool === "measure"`), not only Select; (2) `selectMeasure` no longer early-returns off the tool — a click on a finished measurement **drops back to Select** (`setTool("select")`, so the grips/×/highlight — all gated on Select — appear immediately) and selects it; (3) **mid-draw is preserved** — while a new measurement is in progress (`tool === "measure" && measDraft.length > 0`) the click is NOT stolen (no `stopPropagation`), so it falls through to `onBgDown` to place the next vertex, even when that vertex lands on an existing measurement; (4) **repeat-click cycles the stack** — a second click at the same spot walks the selection DOWN through every overlapping measurement (**smaller-area-wins** so a tiny measurement on top of a big one is reachable first, then wraps), replacing the old "2nd+ click re-sets the same `sel`, visibly inert" behavior. Empty-canvas click still deselects (unchanged `onBgDown` path).
- **New pure lib `lib/measureHit.js`** (Node-tested, zoom-agnostic — tolerance is a feet-space buffer = on-screen px ÷ `view.ppf`): `measuresUnderPoint(measures, p, tol)` → hit indices ordered smaller-area-first (lines/counts = area 0 → ahead of areas), ties by index for a stable cycle; `nextMeasureSelection(order, currentI)` → next selection (top/smallest on a fresh click, next-underneath on a re-click, wraps, null when nothing's under). Plus `ringArea`/`pointInRing`/`distToPolyline`/`measPoints`/`measModeOf`.
- **Dedup note (DEDUPE-FIRST):** distinct symptom, same lineage as the measurement-editing tranche — **B141** (Bluebeam-style editable measurement vertices) and **B230** (Shift-click/right-click vertex insert, no "+" dots), both Done. Those add editing *once a measurement is selected*; this fixes *getting it selected in the first place* from the Measure tool. Reconciled against them — reuses the existing `startMeasureVertex` grips + `isSel && tool === "select"` render path (AUDIT-FIRST), does not fork the hit-test.
- **Verification harness (both pass):** `e2e/measure-select.spec.js` drives the real SVG canvas logged-out — (a) draw a Length measure, stay in the Measure tool, single-click it → the `data-testid="measure-selected"` group (grips + ×, only rendered when a measure is selected AND the tool is Select) appears, proving both the selection and the tool-drop from one click; then an empty-canvas click clears it; (b) two crossing measures → click the crossing selects one, a second click at the same spot cycles to the other (`data-sel-i` changes), never a silent deselect.
