The mechanism already existed and already worked (closing never resolved anything, and the persisted sync ledger already re-detects the SAME conflict on the next load) — what was missing was that closing didn't read as safe, which is exactly what the owner reported.** Traced `ConflictNotice.jsx`/`ConflictReview.jsx`: the close control (previously a bare "✕") only ever flipped a local `open` boolean — it never called `resolveNotesConflict`, so nothing about the conflict is touched by closing. Separately traced the STORAGE side (`notesStore.js`/`notesCloud.js`): a conflict lives in an in-memory `conflicts` Map, repopulated every `startNotesSync()` from `planPageSeed`'s pure classification of the PERSISTED sync ledger (`dirty: true` + a base rev that no longer matches the server's current rev → `conflicts.push(id)`) — so as long as the local edit stays unpushed (which it does, precisely because nothing resolved it), the SAME conflict reappears on the next load with BOTH copies intact. **Proved this end to end, not just read from source**: `test/notesConflictDefer.test.js` (new) drives the REAL `notesStore.js` module through a genuine reload — `vi.resetModules()` (fresh JS state, exactly what a browser reload does) over the SAME persisted localStorage (what a reload does NOT reset) — with the conflict deliberately never resolved in between, and asserts the reopened tab re-detects the identical conflict, with the server's copy unchanged and the device's own unresolved edit still sitting exactly where it was, then confirms a genuine resolve still works normally from there. The hardening: the close control is now a labelled **"✕ Decide later"** button (never a bare icon, which reads as "cancel/discard" to someone deciding whether it's safe to leave), plus one line under the header stating "Both copies are safe either way — pick a version below, or close this and decide later." — so the mechanism that already worked now SAYS so, in the same place the owner was looking when he couldn't tell.
