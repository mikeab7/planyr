### B1754864 (×2) — A parking element split into rows/aisles snaps back to its pre-drag size when you release a resize handle `[Site Planning canvas]` (bug) #site-planner #geometry #ui  *(**Recurrence: 2026-09-18** — owner dispatch, arrived immediately after PR #1762 (this item's own first fix) merged and deployed: "select a drive aisle inside a split parking area… drag a resize handle to lengthen the aisle… on mouse release it snaps back to its exact original position and size." Per DEDUPE-FIRST this reopens the ORIGINAL number rather than minting a new one — same symptom, same surface, a genuinely different gesture than the first fix's own tests drove.)*

`[x]` **ROOT-CAUSED (a second time), FIXED, AND MUTATION-PROVEN — the first fix (PR #1762) was correct as far as it went; it was never exercised against the handle that still broke it.**
- **What the first fix actually covered.** PR #1762 wired `relayoutFreeStack` into `refitChildren`'s freestanding-split-stack branch, and its own test suite (`e2e/split-parking-resize-drag.spec.js`) drove exactly two cases: growing the innermost row's DEPTH edge, and the outermost row's DEPTH edge. Both are pure `edgeResize` drags (`nx=0`), which — by construction — never touch the piece's own `w`.
- **The gap: a CORNER drag (`mode: "resize"`), which moves `w` and `h` independently in the same frame.** Reproduced directly, headless, against the CURRENT (post-#1762) build: split a freestanding 200×60 ft field into row/aisle/row, corner-drag the AISLE outward — its own `h` genuinely grows (68 ft, confirmed via the DOM box and the persisted model) and its `w` grows too (200→244 ft, an ordinary consequence of a corner drag), but its siblings never moved (`row1` stayed exactly at its pre-drag `[769.1, 787.1]` while the grown aisle now spans `[745.1, 813.1]`, fully swallowing it) — the untouched, later-created, opaque `row1` then paints over the grown region, which is what reads as "snapped back" on release. Reproduced identically corner-dragging an END ROW into the aisle.
- **THE ACTUAL ROOT CAUSE.** `freeParkStack`'s sibling-membership test (`lib/parking.js`) requires a candidate's `w` to match the anchor's `w` within `eps` (0.5 ft) — the only signal available to tell this stack's own pieces apart from an unrelated field sitting nearby, since a freestanding stack carries no host/bond tag to group by. `refitChildren`'s branch re-derived that anchor from `next` — the array already carrying THIS FRAME's dragged geometry — so the instant a corner (or along-wall edge) drag grew the resized piece's width past the epsilon, its own still-unmoved siblings stopped matching it, `freeParkStack` returned a chain of length 1, and `relayoutFreeStack` was never called. A pure depth-edge drag (`nw` unchanged by construction) can never trip this, which is exactly why #1762's own tests — and every live click that happened to land on a depth edge — looked fixed.
- **THE FIX: resolve stack membership ONCE per gesture, from the clean pre-drag geometry, not re-derived from the mutating array on every frame.** New `freeStackIdsFor(el)` (`SitePlanner.jsx`) calls the existing `freeParkStack(el, els)` against the UNTOUCHED element — the same "capture once at gesture start" shape `wallKids`/`hostClampOf` already use for the wall-bonded path — and is now called at all four places a freestanding stack member can be resized: `startResize`/`startEdgeResize` (stored on `drag.current.freeStackIds`, read every frame of a live drag) and `resizeSelEl`/`resizeElToValue` (computed once, before the one-shot typed-field commit). `refitChildren`'s branch consumes `opts.freeStackIds` when present, mapping the captured ids onto the current frame's `next` array rather than re-deriving membership from it; a caller that somehow didn't capture it (there should be none left) falls back to the prior, width-sensitive derivation rather than skipping the relayout outright.
- **Adjacent cases checked, per the dispatch's own list — this is the widened coverage the dispatch asked for.** All handle positions on the aisle (both depth edges, both corners) and on both outer rows (depth edge toward the aisle, corner toward the aisle) now grow correctly with the stack staying contiguous; the ORIGINAL fix's own two depth-edge cases re-verified with zero regression; a WALL-BONDED (building-attached) stack is untouched by construction (`freeStackIdsFor` returns `null` whenever `el.attachedTo` is set, exactly mirroring the first fix's own `!attachedTo` guard) — and is structurally immune to this specific defect regardless, since `relayoutWallKids` groups siblings by **bond tag** (`attachedTo` + `sideParkSide`), never by geometric width matching, so a corner drag's width change has nothing to break there.
- **MUTATION-PROVEN.** Two new e2e tests (`e2e/split-parking-resize-drag.spec.js`, driving a real corner-handle drag via `page.mouse` on the actual `rect[data-handle="corner"]` SVG grip — one on the aisle, one on the innermost row) both **fail** against the pre-this-fix build (`piece 1 and piece 2 touch with no gap/overlap: Expected < 0.01, Received 35` / same on the other pair — a real, measured 35 ft overlap) and both pass with the fix, alongside the original two (still-passing) depth-edge tests.
