`[x]` **SHIPPED THIS SESSION.** Reproduced first in a real headless browser against the owner's exact shape (a REAL three-level chain — Contacts: > Jerry Hayley > 713-416-5353, each item the sole child of the one above, built the same way `sinkListItem` builds any real nested list) before writing a line of fix, per AUDIT-FIRST — the numbers matched his write-up exactly (45/90/135 after one Tab, compounding further on each subsequent Tab, symmetric back down on Shift+Tab).
  1. **THE MECHANISM, measured rather than assumed.** `margin-left` is a normal CSS box property: it shifts an item's own border box, and everything genuinely nested inside that item (its child `bulletList` and everything in it) rides along for free, because it lives inside the now-shifted box. `lib/notesListIndent.js`'s `itemsInSelection` walk was already correct about WHICH items a selection touches (one hit per textblock, nearest indentable ancestor only — B519680's own fix, untouched) — but `shiftIndent` then bumped the `indent` ATTRIBUTE on every one of those hits independently. For a Select-All spanning a real ancestor→descendant chain, that means the child gets its own `margin-left` bump ON TOP OF the shift it already inherited from its ancestor's own bump — every level of real nesting the selection spans adds its own step a SECOND time. A single caret with no selection was never affected (only one hit, nothing to double) — measured and confirmed correct before and after — which is exactly why the bug read as selection-shaped even though the underlying rule is about real structural nesting, not selection size.
  2. **THE FIX is one filter, in `itemsInSelection`:** a hit that is a real structural descendant of ANOTHER hit in the same selection (its node's position range falls inside the other hit's) is dropped from the set — it still gets one level deeper, carried by its ancestor's own shift, exactly as a real child already rides its parent's real nesting with no attribute of its own. Only the outermost item in each real-nested chain touched by a selection is ever bumped. Verified this makes a single caret on the middle item and a Select-All across the whole chain converge on the SAME shape of result (exactly one item in the whole document carries a nonzero attribute either way) — which is what "must behave identically for a caret and for a selection" (his requirement 1) actually cashes out to.
  3. **NEVER AN INLINE `margin-left` any more (his requirement 3), even though it was not the root cause.** `lib/notesIndentLevel.js`'s `indentAttrs()` now renders only `data-indent="<n>"`; the actual margin is looked up from ONE stylesheet table (`indentCssRules`, new pure export) — a fixed `n × 1.5em` rule per level, generated once and consumed by BOTH `components/NoteEditor.jsx`'s `EDITOR_CSS` and `lib/notesPrint.js`'s `PRINT_CSS` (PDF-PARITY — a level renders identically on screen and on paper by construction, same as before, just no longer a value computed and stamped onto the element by hand). `parseIndent`/round-trip parsing is untouched (it already read `data-indent`, never the style).
  4. **Toolbar/menu consistency, found adjacent to the fix and closed in the same pass:** `NoteToolbar.jsx`'s Increase/Decrease indent buttons called `sinkListItem`/`liftListItem` directly with no fallback at all — they silently did nothing on a first/solo item (unlike Tab itself, and unlike `NoteEditor.jsx`'s own mobile `MiniBar`, which already had the correct `sinkListItem() || indentListItem()` fallback). Now mirrors that existing, already-tested pattern.
  5. **Requirement 4 (Tab outside a list) — deliberately UNCHANGED, stated rather than silently left.** A plain paragraph still inserts a real tab character on Tab and nothing on Shift+Tab-with-nothing-to-remove (`lib/notesTabKey.js`, B1392); the Escape-then-Tab hatch to the browser is untouched. That design predates this bug, is unrelated to it, and the note editor's own `aria-label` promise ("Tab indents; press Escape then Tab to leave the note") stays true.
  6. **Requirement 5 (stray existing margins) — decision made explicitly, nothing rewritten silently.** Existing stored documents are NOT touched by this fix — every existing `indent` NUMBER on every node is left exactly as it was. Two reasons: retroactively flattening real structural nesting into pure attribute levels would mean rewriting the actual document TREE (not a render formula) on load, for every note that has ever held a nested list, which is a far larger and riskier change than this bug warrants, touching the module's most heavily-guarded data-integrity code; and it isn't necessary — Shift+Tab now walks back exactly one level per press with no overshoot (proven symmetric in both the unit tests and the live measurement below), so any note that still looks over-indented from before this fix is fixed by placing the caret on the affected line and pressing Shift+Tab the right number of times, same as it always was, just reliable now.
  7. **VERIFIED, not eyeballed.** `test/notesListIndent.test.js` — 4 new cases at the pure `shiftIndent` level, reproducing his exact chain shape (only the outermost item bumped on the first Tab, the same item bumped again on a second Tab, a single caret and a full-chain selection converging on the identical one-item-bumped result, and a MUTATION case confirming the OLD unfiltered walk really does find all three) — plus the existing "writes a margin" test updated for the new no-inline-style contract and a new `indentCssRules` coverage case; all 27 tests in the file pass, and the full repo suite (14,780 tests) is otherwise unaffected (one unrelated `MAP.md` drift from the new `indentCssRules` export, regenerated). **Measured live, in a real headless browser, before AND after the fix** (`page.evaluate` reading `getBoundingClientRect` + `getComputedStyle` on the real chain): before — baseline 23/45/68px, one Tab → 45/90/135px (doubled step), two Tabs → 68/135/203px (kept compounding), Shift+Tab × 2 back to exactly 23/45/68px (the original bytes). After the fix — baseline unchanged, one Tab → 45/68/90px (a clean, constant ~22-23px step — exactly what "shift the block down one level" means), two Tabs → 68/90/113px (still a clean constant step, never doubling), Shift+Tab × 2 back to exactly 23/45/68px, and a single caret on the middle item alone converges on the identical 45/68/90px a full-selection Tab produces. Every `style` attribute read `null` throughout — no inline margin anywhere. `ui-audit/audit-notes-tab.mjs`'s 29-row pinned table (his own Richfield "Utilities" fixture — nested lists, an autolinked email, tables, a positioned box, the page title) shows **zero drift**, run against both the dev server and a real production build.
