- **ROOT CAUSE, read directly from `node_modules/leaflet/dist/leaflet-src.js`, not guessed at.** `GridLayer._tileReady` branches on `this._map._fadeAnimated`. The Site Planner's map is constructed with `fadeAnimation:false` (an existing, unrelated, already-shipped setting) — so on the non-fade branch, **every single tile calls `this._pruneTiles()` the instant it finishes loading**, not once per burst: `tile.active = true; this._pruneTiles();`. `_pruneTiles()` is O(retained tiles) — three separate `for (key in this._tiles)` passes, the middle one walking up to 5 parent zoom levels and down 2 child levels (`_retainParent`/`_retainChildren`) for every tile that is "current" but not yet "active", which is the state of every tile still in flight during a burst. A re-anchor that brings up ~150+ new tiles in quick succession (the reported 90 → 257) therefore reruns that whole O(n) pass roughly once per tile that resolves — an O(tiles-loading × tiles-retained) cost — for a decision whose end state does not depend on how many times it ran in between (current tiles are never pruned; only what should no longer be retained is decided, and that decision doesn't change between two tiles resolving a millisecond apart).
- **THE FIX — coalesce, don't skip.** `tileLifecycle.js`'s new `throttleTilePruning(layer)` wraps a tile layer's `_pruneTiles` so repeated synchronous calls within one burst collapse into a single deferred run, via a MessageChannel-posted macrotask — **not** `requestAnimationFrame`, because Leaflet's OWN tile-ready path also schedules a `requestAnimFrame(this._pruneTiles, this)` once the burst's last tile resolves, and the browser runs every rAF callback due for a frame back-to-back with no yield in between, so an rAF-based defer here would just line up alongside Leaflet's own call and buy no separation — the same MEASURED reason `paintSchedule.js` already gives for using a macrotask instead of rAF (see its header, from B802400 round 5's own adversarial reproduction). Wired onto both the coarse backfill and the retina detail tile layers in `SitePlanner.jsx`, alongside the existing `preserveTilesAcrossSetView`. Every call still runs the real `_pruneTiles` exactly once, eventually — nothing is skipped, only coalesced. `fadeAnimation` itself is untouched (fixing the mechanism at its actual source rather than reintroducing the fade-stuck bug that setting exists to avoid).
- **A SECOND, SMALLER INEFFICIENCY IN THE SAME FILE, fixed alongside it because it's the same code path the brief pointed at directly ("`L.TileLayer._update`/`_setView`/`_tileReady` doing O(retained tiles) work").** `capTileCache` (the existing tile-cache-cap maintenance, B1427/NEW-7) called `map.getCenter()` and `map.project(center, z)` **once per retained tile** inside its distance-sort loop, even though the center is the same point for every tile in one call and the projection only differs when the zoom differs (normally one, occasionally two, distinct zooms are ever retained at once). At 257 tiles that was up to 257 redundant `getCenter`/`project` calls on every single "load"/"moveend" firing. Hoisted `getCenter()` out of the loop and memoised `project` per distinct zoom — now O(1) `getCenter` + O(distinct zooms) `project` instead of O(n) of each.
- **MEASURED, real Chromium, before vs after — `ui-audit/diagnose-aerial-reanchor-block.mjs` (new).** This sandbox cannot reach the real Esri/USGS hosts (egress-blocked, the same wall every GIS item here cites) or match the owner's CPU/GPU, so tile requests are fulfilled by `ui-audit/lib/fakeTile.mjs` (a real decodable PNG per tile — Chromium does the real decode/texture-upload work) with staggered latency, and the METRIC is a COUNT rather than a clock (this repo's own established idiom for exactly this class of question — B236592/B221763, "count invocations, not milliseconds" — because wall-clock LoAF timing in this sandbox is noisy in a way the owner's real capture is not). The harness opens a real, already-anchored plan (Goose Creek, `perfScenarioSite()`), lets it fully settle, then switches to the Richfield fixture (a different origin, so its tile grid is genuinely unfetched this session) and counts how many times the REAL underlying `_pruneTiles` algorithm executes during the switch — patched onto the shared Leaflet prototype via the already-existing Goose Creek layer, so the count is honest whether or not `throttleTilePruning` is wrapping it on top. **Three repeated runs each side, git-stash isolated (the same technique B802400 round 5 used for its own before/after):** pre-fix **183 / 183 / 183** real `_pruneTiles` executions per switch; post-fix **88 / 82 / 91** — a consistent ~52% reduction in how many times the O(retained-tiles) algorithm actually runs, for byte-identical final state either side (same tile count, same element count, same DOM node count — this changes only how many times a decision is redundantly repeated, never what ends up on screen).
