`[x]` **TWO CONFIRMED, DISTINCT ROOT CAUSES in `ProjectBreadcrumb.jsx`, both fixed — and the owner's question answered directly: NEITHER predates #1232's list-merge work; both are genuine defects IN `unionProjectLists`/`withCurrentProject`, the functions that PR's own B854xxx work built. #1232 introduced the mechanism these bugs live in, not merely exposed a pre-existing one.**
- Verify: live — the repro explicitly cites the owner's real project (Goose Creek), a mandatory LIVE-VERIFY class. Both mechanisms are proven in the sandbox below via a real postMessage-speaking iframe stub and a real multi-project switch; confirmed live 2026-08-31 (V496865, drained from `verification-inbox/2026-08-31-b881664-b881666-live-pass.md`) — no third mechanism was found.
- **ROOT CAUSE 1 — a namespace mismatch (the Schedule tab).** Scheduler.jsx's controlled `currentProject` is the routed site's LINKED SCHEDULE object once one exists (`{id, name, linkedSiteId, linkedSiteName}`) — its `.id` is the SCHEDULE's own id (a small integer-like string), not the site-GROUP id `listProjects()` keys its registry by. `withCurrentProject`'s dedupe check (`projects.some(p => p.id === currentProject.id)`) always missed against that id, so `ProjectBreadcrumb.jsx`'s `refresh()` unconditionally prepended a synthetic registry entry keyed by the schedule id and marked "current" — sitting beside the REAL, group-id-keyed registry entry for the same project (which the row-render's own `cur` check does NOT mark current, since its id doesn't match either — hence the ordinary timestamp on the second row). Separately, `unionProjectLists` never recognized that a controlled entry's `linkedSiteId` and a registry entry's `id` can name the SAME real project — every linked schedule, not just the current one, fell into `extra` beside its own registry row.
- **ROOT CAUSE 2 — a stale closure (any workspace, kept-alive).** The mount effect that registers the "storage" event listener has deps `[controlled]` — a per-instance constant, since a kept-alive workspace's `ProjectBreadcrumb` never remounts on a later project switch — so that listener's `refresh()` call was permanently bound to whatever `currentProject` was at FIRST mount. A synthetic `notifyProjectsChanged()` storage event fired from anywhere in the app (a rename, a warm, another tab) after the user switched projects could re-derive `internalProjects` from the stale project.
- **THE FIX, three changes.** (1) `ProjectBreadcrumb.jsx`'s `refresh()` now resolves through `linkedSiteId` when present, reconciling against the SAME identity space the registry actually uses. (2) `refresh` always reads `currentProject` through a ref kept current every render, so no caller (a mount-time listener, an in-flight promise) can act on a stale value. (3) `unionProjectLists` (`projectModel.js`) now drops a controlled entry whose `linkedSiteId` names a project already covered by a registry row — the registry copy (richer: real timestamp) is the one shown, and `Scheduler.jsx`'s `selectSchedule` resolves a click on that registry row back to the correct schedule id before posting into the iframe (proven via a real click-through, not just a render check).
- **PROVEN RED before the fix, per house rule.** New `ui-audit/verify-project-switcher-dedupe.mjs`: CASE A (Schedule, a routed project with a linked schedule, the exact namespace-mismatch shape) — one "Goose Creek" row, and clicking it still correctly selects the schedule's own id in the iframe.
