- Verify: sandbox — every case is deterministic and reproduced/proved in a real headless browser against a seeded plan; nothing here depends on timing, a live GIS endpoint, or a signed-in account.
- **ROOT CAUSE.** "Edit boundary corners" (`startBoundaryEdit`) arms the plain Select tool and auto-selects a parcel — it is not a distinct `tool` id, by design (dragging a corner/adding one on an edge/Shift-deleting one have always worked in Select with a parcel selected; the menu row + banner just teach the three gestures). Every cursor ternary in `SitePlanner.jsx` follows the shape `tool === "select" ? <what's-underneath> : "crosshair"`, so this mode read as ordinary Select everywhere and showed what the object underneath would do there (grab a building, drag a parcel, edit a setback) instead of the mode's own corner-editing affordance. A new derived flag, `editingCorners = boundaryEdit && tool === "select"`, is the one condition every such ternary needed to add.
- **THE FIX, one flag threaded through every affected site:**
  1. The base `<svg>` canvas root's own idle cursor (bare map / empty parcel interior — the "grab" the report measured).
  2. `renderElPx`'s three render branches (polygon/pond/paving, centerline road, rect/rotated-rect building) — covers EVERY element type generically, since none of the three branches is per-type. Threaded as a new trailing parameter (`editingCorners = false`) through `renderElPx` → the memoized `ElNode` wrapper → both `<ElNode>` call sites, so existing callers are unaffected by the added parameter's default.
  3. The parcel's own boundary hit-stroke (both the per-parcel loop and the setback-adjacent-ring loop) and the selected parcel's setback grab band.
  4. `renderMarkupNode`'s shared cursor (covers every markup kind generically, easements included).
  5. The callout box, the measurement chip/count-marker/area/line grab bands, and the two overlay-reference cursor sites.
  6. **Found only by driving the adjacent-cases check the dispatch asked for, not by source-reading alone:** a pond's own on-map label (click-to-select/double-click-to-inspect, `isPondLabel`), the parcel acreage badge (`draggable`, hover-armed per B280402/B1327 — kept its documented "cursor and handler read the SAME flag" invariant, so it now also loses interactivity while editing corners rather than decoupling from it), a selected parcel's per-side length dimension numbers (`parcelEdgeLabels`'s `editable`, guaranteed to render every time since `startBoundaryEdit` always selects a parcel), the setback numeric chips (`setbackChipNodes`, same reasoning as the acreage badge — the setback RING itself stays visible, only its clickable chips step aside), and the on-building "+/−" dock/bump-out/parking-row quick-add controls (`sideAddNodes`/`parkingAddNodes`, hover-armed via `featActiveId`).
- **THE TWO LEGITIMATE VARIATIONS, both confirmed working, not just left alone:** the corner handle you can drag still reads a grab affordance (`vtxRect`'s existing "move" cursor, unaffected by this fix since it isn't part of the `tool==="select"` ternary family); the edge where a new corner would be inserted reads a distinct "copy" cursor at the exact point `insHint`'s existing dot marks, scoped to the parcel actually being edited so a stray `insHint` from some other selected editable path can't paint it on the wrong parcel.
