**THE MECHANISM.** `purgeExpiredDeletedProjects` (site-planner `lib/storage.js`) fires from `ProjectBreadcrumb.jsx`'s `refreshBin()` on every project-switcher open, and hard-deletes (`cloudHardDelete` → a plain `supabase.from("sites").delete()`) any soft-deleted plan past `DELETED_RETENTION_DAYS`. B1469872 (shipped the day before) taught that function to skip a plan whose group still has a live sibling — but that guard is a JS check, invisible to any tab that loaded its bundle before the fix deployed. `buildSkew.js`'s "a newer build is available" notice is deliberately non-blocking and dismissible (by design), so nothing forces such a tab to reload — it can sit open for days, as measured. `site_elements_site_id_fkey` is `ON DELETE CASCADE`, so the hard delete also destroys every element row.

**THE FIX — a database-level guard no client bundle, old or new, can skip.** New file `db/sites_block_delete_live_group.sql`: a `BEFORE DELETE` trigger on `public.sites` (`sites_block_delete_live_group()`) refuses to hard-delete a row when (a) it was never soft-deleted at all, or (b) another row sharing its project group still has `deleted_at IS NULL`. Runs inside the same transaction as the DELETE — any error aborts the whole statement, so an inconclusive check can never fall through to a destructive default. Backed by a new expression index (`sites_group_key_idx`) on the same key.

**THE GROUP KEY — deliberate choice, per the dispatch's own ask.** Uses `coalesce(data->>'groupId', id)` — the SAME key `rename_site_group()`/`set_site_group_role()` already trust — never the `group_id` COLUMN, which `rename_site_group.sql` and the site-planner `CLAUDE.md` both document as a denormalized mirror known to drift from the jsonb. A destructive, irreversible action must use the authoritative value, not the mirror. (The pre-existing CLIENT-side liveness check — `cloudCheckDeleted`/`cloudDeleteGroup`/`listDeletedPlansInGroup` — reads the `group_id` column instead; left untouched, since a jsonb-keyed server guard is strictly more protective than the column-keyed client check it backs up, never less.)

**WHY A WHOLE-PROJECT PURGE STILL WORKS.** The rule is "refuse when a LIVE sibling remains," never "refuse when any other row exists." Every hard-delete call site (`purgeDeletedProject` — "Delete forever" — and the 30-day sweep) only ever acts on already-soft-deleted rows, so a genuinely dead project has no live sibling anywhere in its group, before or after any one row is removed — the check passes for every member regardless of delete order, whether issued as the app's current per-row `Promise.all` or a future batched statement.

**⚠ ONE KNOWN, DELIBERATE CONSEQUENCE, surfaced rather than silently absorbed:** the plan menu's own per-plan "Delete forever" (`SitePlanner.jsx`'s `purgeDeletedProject([p.id], groupId)`, offered for a plan discarded from an otherwise-still-live project) now ALSO refuses while that plan's group has any other live plan. Before this fix, that manual action could already permanently destroy real element data with one click and zero server-side check — arguably the MORE dangerous of the two paths, just not the one an unattended timer could trigger. The refusal surfaces through the existing failure toast, loudly, not silently (see `cloudSync.js` below). If purging one dead plan out of a still-live project is wanted as a deliberate feature, that is separate, not-yet-built follow-up work — flagged here for Michael, not decided unilaterally.

**Client-side surfacing:** `cloudSync.js`'s `cloudHardDelete` now detects the trigger's distinguishing error code (`PLYR1`) and returns a clear, honest message ("This plan's project still has another active plan — it can't be permanently deleted while any of them are live.") plus a dedicated `purge-blocked-live-group` telemetry event, instead of a generic "delete failed." Every existing UI caller (`ProjectBreadcrumb.jsx`'s bin, `SitePlanner.jsx`'s plan menu) already surfaces `res.error` on failure, so no UI code needed to change.
