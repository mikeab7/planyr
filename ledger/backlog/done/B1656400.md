`[x]` **FIXED AND VERIFIED THIS SESSION.** Reproduced first, root-caused, then fixed — no diagnosis-only. **Repro (headless Chromium, logged out, local fixture — a numbered list "First/Second/Third"):** placed the caret at the end of "Second" and pressed Tab for real (`page.keyboard.press`, per SYNTHETIC-KEYS-DONT-EDIT). `editor.can().sinkListItem()` succeeds (Second has a sibling above to tuck under), wrapping it in a brand-new `<ol>` inside First's own `<li>` — real ProseMirror nesting, not the attribute path. **Measured:** the ordinary sibling gap between two top-level items was **6px** (`"First"`'s paragraph bottom to `"Second"`'s paragraph top); after the real-sink Tab the SAME pair read **15px**. Cause: `.planyr-note .ProseMirror ul, .planyr-note .ProseMirror ol { padding-left: 1.5em; margin: 1em 0 0 0; }` (mirrored in `lib/notesPrint.js`'s `PRINT_CSS`) is meant to space a list away from a paragraph that PRECEDES it elsewhere in the document — it also matched the newly-created NESTED `<ul>`/`<ol>`, whose top margin then landed between a parent item and its own just-sunk child, which is the next line of the SAME list, not a new block. A second Tab (the flat `indent` attribute, once `sinkListItem` has nowhere further to sink — B512672's mechanism) adds no vertical change of its own; the whole drop is already there after the first press, which is why "press Tab again" is when the owner noticed it rather than when it was introduced. **Fix:** one override rule in `components/NoteEditor.jsx`'s `EDITOR_CSS` — `.planyr-note .ProseMirror li > ul, .planyr-note .ProseMirror li > ol { margin-top: var(--note-list-gap, 2px); }` — gives a list nested INSIDE a list item the item's own gap instead of the generic block margin; the untouched generic rule still spaces a list that genuinely follows a paragraph. PDF-PARITY: `lib/notesPrint.js`'s `PRINT_CSS` gets the identical override, and its `densityCss(id)` (Comfortable/Compact) now also emits the nested-list override at the chosen density's own gap rather than a bare 2px, so paper matches whichever density the note is set to. Re-measured after the fix: the nested-child gap reads 6px, identical to an ordinary sibling — confirmed live with the same headless reproduction. **No contradiction with `## Owner product constraints`.** Checked every entry — none apply (a stylesheet-only fix; nothing about ownership, Colorado data, rate/rule records, project creation, banner semantics, live-check scope, canvas framing, or phone Split is touched). - Verify: sandbox — reproduced live in headless Chromium (logged out, local fixture, no external GIS, no auth) before AND after the fix, with the exact pixel gap recorded above; `npx vitest run` full suite green (855 files / 17,427 tests, no regressions); `node ui-audit/audit-notes-tab.mjs` (the existing pinned Tab-context table) still matches every row; new permanent guard `node ui-audit/verify-notes-list-indent-height.mjs` (6/6, red-proofed by stashing the CSS fix and re-running — the vertical-gap check failed exactly as expected: "ordinary sibling gap 6px, nested-child gap 15px"); new unit test in `test/notesListIndent.test.js` asserts the stylesheet TEXT for both the editor and every print density, likewise red-proofed by stashing the fix (both new checks failed on the pre-fix source). - Files: `src/workspaces/notes/components/NoteEditor.jsx`, `src/workspaces/notes/lib/notesPrint.js`, `test/notesListIndent.test.js`, `ui-audit/verify-notes-list-indent-height.mjs`. - Base: `origin/main` @ `0f17770`.
