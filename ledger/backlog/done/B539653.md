### B539653 — ⛔ MY OWN ARROW-KEY GATE SILENCED THE SECOND ESCAPE, so a box could not be deselected from the keyboard `[Notes]` (bug) #notes #ui  *(found 2026-08-14 by `verify-notes-box-selection` while landing B539651 — six rows across three window sizes. **A REGRESSION IN B519681**, which shipped earlier the same session. Minted **B539653** from this branch's reserved block B547776–B547791 against origin/main 7a9d689.)*
`[ ]` **⛔ SHIPPED. Caused by me, in the fix for his arrow-key report.**
- Verify: sandbox — `ui-audit/verify-notes-box-selection.mjs`, 91/91.
- **THE DEFECT.** B519681 made every global binding in the module decline while there is a live caret in editable text — correct, and correct in **the two states that were measured**. The two-stage box gesture has a THIRD state nobody measured: Escape #1 backs out of editing, Escape #2 deselects — and **after #1 the editor still HOLDS FOCUS**. Measured at every step: `activeElement` is the ProseMirror div, `isContentEditable` true. So the gate declined Escape #2 and the box could never be deselected from the keyboard.
- **⛔ THE FIRST ATTEMPT AT THE FIX WAS WRONG AND THE HARNESS SAID SO.** It assumed the blur had landed and only required focus to be inside the selection's own host. It changed nothing, because focus never left. **Reasoning about the state twice cost two builds; probing it took one.**
- **THE RULE:** the gate exists so a binding cannot steal a key the person typing NEEDS. **Escape is not one of those** — a caret has no use for it — so it is named in `UNGATED_KEYS` and never gated. Every key the caret DOES want is still gated in that same state, asserted both ways.
- **⛔ IT DOES NOT REOPEN B434418's "HANDLED TWICE":** that defect was Escape running in the mat AND the window binding, and the mat's call was deleted then. There is still exactly one handler; this only stops the gate from silencing it.
