- **Measured cause (not the screenshot inference).** The hidden rows were NOT gaps in IDs and NOT a collapsed subtree: they were Baytown Platting's finished children hidden by the group's **Focus filter** (`task.focused`, the "N hidden" chip). Every insert path ran "expand & un-spotlight ancestors" — `focused: false` on the new row's parent — so Insert above TIA (new parent = Baytown Platting, from the deeper-row-above rule) switched that group's Focus OFF: its hidden finished rows reappeared, and the new row, spliced into the raw array just before TIA, sorted after them. Reproduced in a real browser on main 8584b49 (`ui-audit/verify-schedule-insert-above.mjs` against the pre-fix page: rows "Done step 5…9" appear and the new row lands below them). The un-focus existed because a blank new row is itself something Focus hides (not started).
- **Fix.** One pure positioning function, `insertRowAbove(tasks, visibleIds, anchorId, newTask)` (index.html, after `promoteChildrenAndDelete`; mirrored verbatim in `ui-audit/stress/schedule-insert-above.mjs` with a byte-identical drift guard), read off the grid's own VISIBLE order: no row above / row above is the selection's parent → same parent as the selection, directly before it; otherwise → next sibling of the visible row above, placed directly before the first VISIBLE sibling after it, or as its parent's last child (so after its hidden subtree and hidden siblings). It never touches `isExpanded` or `focused`. The Insert key and right-click "Insert Row Above" both go through `insertAboveAnchor`. The new row stays on screen under its parent's Focus filter through a session-only pin (`focusPins`, by `_sid`, view state, never saved) — it is also left out of the chip's hidden count; any Focus toggle re-applies the filter and drops the pins.
- **Multi-row selection:** one row inserted above the TOP row of the selection (documented choice). **Enter unchanged** — it never inserts (source-pinned).
- **Not changed (adjacent, noted):** Insert Row Below / Add Subtask / Duplicate still switch the target parent's Focus off when they add into a focused group; out of this item's scope.
- **Tests.** `test/scheduleInsertAbove.test.js` (14): the red-proof runs main's old algorithm (copied verbatim) through the same assertions and requires it to FAIL, then requires insertRowAbove to pass — (a) no row's hidden/collapsed state changed, (b) parent = the earlier group, (c) after all its children and immediately before the selected summary; plus each edge case (first visible child, very first row, collapsed summary above stays collapsed, task vs summary selection, hidden siblings between, manual nested collapse without Focus, no anchor, pin); wiring pins.
