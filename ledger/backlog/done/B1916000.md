But if it's on a table... a double click should hit the table, not the other canvas tool." `[x]` **ROOT CAUSE, confirmed by reading the code before touching it (AUDIT-FIRST), matching the dispatch brief's own inference.** The Notes page is a pure placement surface (NOTES-CARRY-FORWARD's NEW-1, 2026-09-22): every mousedown that does not land on a `.planyr-anchor` box (or a picture/file, the one existing exemption) is read by `focusFromMat` (`NoteEditor.jsx`) as BLANK CANVAS, where a stationary double-click arms a placement caret. `NoteToolbar.jsx`'s table insert (the drag-to-size grid picker and the "+" insert menu) called `chain().insertTable(...)` at whatever the editor's CURRENT SELECTION happened to be, with no check that the selection was inside a box — and on a page where nothing has been clicked into yet, `state.selection` defaults to the document's own top-level trailing structural paragraph (real to ProseMirror, but unreachable by any click). A table inserted there sat outside the box model entirely, and — before this fix — the content guard did not recognise a bare `table` either, so every later press on it read as blank canvas: exactly the report.
`[x]` **FIX, PART 1 — new tables always land inside a box.** `notesAnchorNode.js` gained two small exports: `selectionInsideAnchor(state)` (walks the selection's ancestor chain for a `noteAnchor`) and `nextAnchorSpot(doc)` (a sensible below-the-lowest-existing-box default point for a control with no click coordinates, e.g. a toolbar button). `NoteToolbar.jsx`'s `insertTableSmart` (used by both the grid picker and the "+" menu) checks `selectionInsideAnchor` first and, when nothing is focused, creates a box (`addNoteAnchorAt`) before inserting the table — dispatched synchronously so ProseMirror's history groups both into one undo step, the same discipline `commitPendingPlace` already uses for a typed placement.
`[x]` **FIX, PART 2 — the content guard itself now recognises a table, per the brief's explicit "either way" instruction.** `focusFromMat`'s content guard (`NoteEditor.jsx`) now also treats `table`/`.tableWrapper` as content, never blank canvas — a safety net for whatever else might put one at the top level (a legacy document not yet reopened; some future insertion path this round did not anticipate). `notesFlowMigration.js`'s existing, unconditional on-read migration already folds any top-level table into a box the next time the page is opened, unchanged by this round — proven still true, not merely assumed.
`[x]` **Both stage-1/stage-2 box conventions (B434416, pre-existing) are left untouched and are exactly what makes the fix complete rather than partial.** A box created by the toolbar (never yet mouse-selected) still takes a first click to SELECT and a second to ENTER, precisely like any other box — that is not this bug; the bug was that NEITHER stage was ever reached, a new box was silently created instead. Once selected/entered, a table cell behaves like any other cell: the caret goes in, typing lands in the stored document, a double-click on a word selects it, Tab moves between cells, and the right-click menu (wired independently, via `onContextMenu`'s own `.closest("table")` read) still offers "Convert table to text".
