### B1611841 — A road ending deep inside a pad grows a degenerate blob instead of returns at the pad face `[Site Planner / road-geometry]` (bug) #site-planner #road #geometry  *(same owner chat block as B1611840. Minted **B1611841** from the same reserved block. DEDUPE-FIRST — searched Open/⏳Verify/Done/Done-archive for "endpoint well inside", "degenerate blob", "past the pad edge": B1612608/B1664512 built "endpoint contained anywhere in the target connects at all" but never addressed how far past the entry face a CONTAINED endpoint can sit before the junction geometry itself breaks — net-new.)*

`[x]` **FIXED AND RED-PROOFED.** `driveJunctionsOf` (`SitePlanner.jsx`) anchored the whole road→pad junction on the road's RAW drawn endpoint, using `nearestRectEdge(P, edges)` to pick which target edge is "the" entry — which answers "which edge is geometrically closest to this POINT," not "which edge did this road actually cross to get here." Those agree only while the endpoint sits near the target's own perimeter. A CONTAINED endpoint (a valid connect since B1612608 — "lands on, overlaps, or falls within tolerance," not just near an edge) that clears the target's own midline silently flips the "nearest edge" to a different side of the target than the one the drawn road actually crossed, and every downstream quantity (`throughDir`, the along-edge run, the court-depth radius clamp, the building-obstacle check) was then measured against a line the road never followed — degenerating into the reported small blob instead of a curb return at the true entry face.

**RED-PROOF, `test/roadDeepEndpointJunction.test.js` (new, 9 tests).** `oldEdgeSelection` replicates `driveJunctionsOf`'s pre-fix edge-selection exactly, using only pure, exported lib functions (the same pattern `roadDriveJunctionFillet.test.js`'s own scenario helpers already use). Confirmed RED against unmodified `origin/main`: a straight approach through a 600-ft-deep pad's bottom edge, walked from 0 to 300 ft past it, has its chosen edge flip from the true entry edge to the pad's RIGHT edge past 150 ft — and the produced curb-return wedge set collapses to empty (`[]`) at 200 ft and 300 ft, the "degenerate blob" the dispatch reported (measured directly, not assumed).

**THE FIX:** `roadEdgeCrossing(outsidePt, insidePt, edges)` (new, pure, exported — `roadGeometry.js`) asks the right question directly: where the SEGMENT from the road's own approach point to the endpoint actually crosses the target's boundary (a real bounded segment-vs-edge intersection, not a nearest-point search), returning the crossing closest to the endpoint or `null` if none is found. `driveJunctionsOf` now anchors the junction (`T`/`throughDir`, the along-edge run, the court-depth radius clamp, the building-obstacle check, and the side reach available to the return — the portion of the drive now inside the pad is subtracted from the reach, since it's absorbed into the pad rather than counted as approach pavement) at this crossing point instead of the raw endpoint, falling back to the pre-existing (unchanged) behaviour only when no real crossing is found. The already-verified near-edge cases (B1645792/B1664512) are provably unaffected: when the endpoint already sits on the target's edge, the crossing point IS the endpoint (to numerical noise), so nothing about those cases changes — confirmed by the full existing `roadDriveJunctionFillet.test.js` suite re-running green, byte-identical, throughout.

**Confirmed GREEN after the fix, and swept every ADJACENT CASE the dispatch asked for:** the chosen edge never flips at any depth from 0–590 ft of a 600-ft pad; the junction wedge geometry (area signature) is IDENTICAL regardless of depth (0.66 sq ft floor per wedge, never empty); real, simple, non-degenerate curb returns exist at every depth tested; an OBLIQUE approach (10–30° off perpendicular, not just straight-through) also resolves at the true entry face; a free-drawn POLYGON pad target (B1664512's own target kind) resolves the same way as a rect pad; "just inside the edge" (2 ft) produces byte-identical geometry to "exactly on the edge"; "past the far side of the pad entirely" either correctly doesn't connect at all (the endpoint is genuinely outside every target, per the existing B1612608 connect rule — nothing to fix) or, within tolerance of the far edge, resolves there honestly with no crash; the flood-fill self-test control (B1645792/B1681521's own acceptance instrument) still sees the real geometry cleanly, with zero enclosed unpaved area near the (now-absorbed) junction.
