### B643104 — Schedule grid: changing the row-height slider throws the on-screen row out of the rendered window `[Schedule]` (bug) #scheduler #ui  *(self-discovered while sweeping B463922 for "any other instances" per the owner's own instruction — NOT itself owner-reported, and NOT the same bug: different trigger (a Format-panel settings change, not a click on the schedule), different mechanism (an ABSENT compensating scroll write, not a wrong one). DEDUPE-FIRST — searched Open / ⏳ Verify / Done for `ROW_H`, `rowHeight`, `FormatPanel`, `heldRowHRef`, `row-height`: no prior item; filed here rather than folded into B463922 so a future search for this specific defect finds it.)*
`✅` **Done — shipped in the same commit as B463922 (×2), same PR (#1101). Split into its own item on request so it has its own record.**
- Verify: sandbox
- **ROOT CAUSE — an ABSENT write, not a wrong one.** `ROW_H` is reassigned per-render at `public/sequence/index.html:5505` (`ROW_H = Math.min(34, Math.max(20, data.settings?.rowHeight || 24));`), and every row's rendered position reads it directly at render time (`style={{top:ri*ROW_H, ...}}`, e.g. line 9251). Pre-fix, nothing recomputed the container's `scrollTop` when `ROW_H` changed — the raw pixel offset stayed exactly what it was, now describing a completely different row than before the resize. This is the opposite failure shape from B463922: that bug was an app write firing with the WRONG delta; this one is no write firing at all where one was needed.
- **MEASURED, pre-fix (formal harness, `ui-audit/verify-grid-row-hold.mjs`, section "B548xxx — a row-height change must not throw the view out of the rendered window," run against commit `bbec97ea`, the parent of the fix):** `✗ row-height — row 156 is no longer rendered (was at 399px)`. Not a large delta — the row left the render window entirely (the virtualiser dropped it, since nothing told it to look at the new area).
- **MEASURED, post-fix, same row, same selection state:** `✓ row-height — selected row 156 held its place across the resize (399px → 399px)` — held exactly, Δ 0px.
- **THE FIX.** A second `useLayoutEffect`, keyed on `ROW_H` (`heldRowHRef` tracks the previous value), using the same anchor priority as B463922's effect — the selected row while it's on screen, else the row at the top of the viewport — and one unified formula, `el.scrollTop = Math.max(0, st + anchor*(ROW_H - prevRH))`, where `anchor` is either the selected row's integer index or the top-of-viewport row's fractional index. The same formula covers both cases; holding a specific row's index fixed across a uniform per-row rescale is algebraically the same operation whether that index is a whole selected row or a fractional viewport edge.
- **RELATED TO, NOT PART OF, B463922.** Both were found in the same sweep and ship in the same commit, but they are different bugs: B463922 is triggered by a click and caused by a wrong anchor choice; this one is triggered by a settings change and caused by a missing compensation entirely. See B463922 for the click-anchor bug and the sweep that found this one.
