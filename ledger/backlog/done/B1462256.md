- Verify: sandbox — logged out, no external GIS or account needed (ATTEMPT-BEFORE-YOU-PARK): the select-parcels toggle and opening an already-seeded local site are both purely client-side. Driven headless and proven both ways (fails on the pre-fix build, passes on the fix) — see below.

**ROOT CAUSE, exactly as measured before touching anything (AUDIT-FIRST).** `MapFinder` is mounted by `SitePlannerApp.jsx` as `<MapFinder visible={mode === "map"} ... />` and STAYS MOUNTED when a project's planner is open — only `visible` goes false and its wrapper gets `display:none`. Its three transient notices (the select-parcels tip, the statewide-backup notice, the cached-snapshot notice) all render through the shared `FloatingNotice` primitive, which `createPortal`s into a fixed host appended to `document.body` OUTSIDE MapFinder's own DOM — so `display:none` on the hidden wrapper does nothing to hide a portaled notice. None of the three render conditions checked `visible`, and the one reset effect that existed (`useEffect(() => { if (visible) {...} }, [visible])`) cleared `selectMode`/`selected`/etc. only on RETURNING to the map, never on LEAVING it — and never touched `backupNotice`/`cachedNotice` at all, on either half of the flip.

**THE FIX, both halves the item asked for, not just one.** (1) All three notice render conditions are now gated on `visible &&` directly — a MapFinder notice can no longer render while `visible` is false, full stop, regardless of what any other state does. (2) The reset effect now clears `selectMode`/`backupNotice`/`cachedNotice` UNCONDITIONALLY on every map<->plan flip, in both directions — not only on return — closing the asymmetry the item called out by name. The pre-existing `isActive`-independent behaviour (peeking at another module tab and coming back preserves an in-progress parcel selection) is untouched — the effect still keys on `visible` alone, never `isActive`.

**⛔ A REAL, UNRELATED CONFOUND SURFACED WHILE BUILDING THE LIVE CHECK, worth recording so it isn't rediscovered blind.** MapFinder's `err` state shares the exact same render slot as the select-parcels tip (`!err && selectMode`, an existing, documented, out-of-scope design also called out in `e2e/notification-position.spec.js`), and this sandbox's egress-blocked GIS hosts eventually flip `err` true on their own client-side timeout — measured directly at **~7-8 seconds** after arming select mode, with no navigation involved at all. A naive `expect(tip).toHaveCount(0)` with this repo's default 10s retry window would happily wait out that unrelated timeout and report a false PASS on the UNFIXED build — confirmed by running the first draft of the e2e spec against a deliberately un-patched build and watching it pass anyway. The shipped spec (`e2e/mapfinder-notice-leak.spec.js`) caps that assertion at an explicit 2-second retry window, well inside the ~7-8s confound, so it can only pass by observing the real, immediate fix; verified mutation-proof both ways (fails in ~4s against the pre-fix build with `tip count: 1`, passes in ~2.5s against the fix).

**Guards, both new and both proven mutation-red on the pre-fix source, not just written and trusted.** `test/mapFinderFloatingNoticeLeak.test.js` (5 tests, source-guard shape — the `handleLayerOrder`/`headerNavPriority` pattern this repo already uses, since MapFinder pulls in Leaflet and isn't unit-render-tested): asserts every `<FloatingNotice` call site in `MapFinder.jsx` is gated on `visible` (so a FUTURE notice added here without the gate fails this test on sight — the "guard so a future FloatingNotice rendered from a mounted-but-hidden component cannot leak the same way" the item asked for), and asserts `setSelectMode(false)`/`setBackupNotice(null)`/`setCachedNotice(null)` run unconditionally (outside the `if (visible)` branch) rather than only on return. 2 of 5 sub-assertions fail against the pre-fix file (confirmed via `git stash`). `e2e/mapfinder-notice-leak.spec.js` (1 test, live render) drives the real app: arms select-parcels mode on a seeded local site, opens that project's planner without ever turning select mode off by hand (the owner's exact sequence), and asserts the tip is gone from the DOM entirely within 2 seconds.
