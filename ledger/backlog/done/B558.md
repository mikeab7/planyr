- **Root cause (ONE bug, not two — explains BOTH the re-prompt AND the "no other tab" phantom):** the banner re-appearing is the **blue cloud-CONFLICT banner** (`cloudConflict`, "changed in another session"), driven by the **B459 thin-clobber guard** (`wouldThinClobber` in `cloudSync.js`) — NOT the amber Web-Locks read-only banner. That guard blocks a push that drops **≥2 items the cloud still has with no delete-tombstone to explain the drop**, treating it as a stale-tab clobber. The bug: **`deleteSel` removed the building AND all its bonded children (dog-ears / sidewalks / parking, `attachedTo`) from `els` but recorded NO tombstone** — only `removeOverlay` (B276) ever tombstoned. So deleting one building dropped ≥2 items unexplained → the guard FALSELY rejected the save as a cross-session conflict, with **no second session anywhere**. A **MOVE** keeps the item count (`lost = 0`), so it never tripped — exactly the owner's move-vs-delete tell. Secondary latent bug from the same gap: "Take over editing" union-merges the cloud copy back, **resurrecting the just-deleted building** (the never-ending loop).
- **The whole CLASS, not just building-delete (owner asked "what else causes this?"):** any DELIBERATE local op that shrinks the plan by ≥2 vs the last-synced baseline with no tombstone. Found + fixed all of them:
  - **Deletes** (building+assembly, multi-select, parcel, callout, markup, parcel-drawing, stranded-zone auto-prune on reshape) → now **tombstone** the removed ids (mirrors `removeOverlay`/B276). New shared `tombstone(ids)` helper in `SitePlanner.jsx`; wired into `deleteSel` (both branches), `deleteDrawing`, and the strand-prune. This both clears the false conflict AND makes deletions stick through `mergeSiteContent` (no resurrection).
  - **Undo of a multi-element add** (drawing a building adds building+parking+sidewalk in ONE undo frame → one Ctrl-Z drops ≥2), **Redo**, **cancelled drag**, and **Restore to a thinner version** → tombstones are wrong here (a redo must re-add the items), so instead the active tab rebases its own thin-clobber baseline via new **`noteLocalContent(id, model)`** (`cloudSync.js`, re-exported through `storage.js`), called from `applySnapshot` (undo/redo/cancel) and the version-restore handler.
- **Why the 8 South stale-clobber protection (the whole point of B459) is untouched:** `noteLocalContent` only ADJUSTS an existing baseline and is called ONLY on an explicit user undo/redo/restore — a passive STALE background tab never does those, so its baseline stays at the cloud's fuller count and its thin push still BLOCKS. The cross-session CAS **version** guard (B314) also still rejects a genuine concurrent change. Proved by a dedicated unit test.
- **NOT triggers (verified):** move / resize / rotate / group / add / split-parcel / vertex-delete / cross-tab+takeover merges (all union-up or count-neutral).
