- **ROOT CAUSE, traced to two real upstream sources rather than assumed — this codebase does not compose either raw string from scratch, it composes the PROJECT NAME from whichever of them wins `siteNameFromParcel`'s ladder, and passes the winner through unmodified.**
  1. **Bowie County's own appraisal-district record** (harvested verbatim by the state's TxGIO/StratMap statewide parcel service, which is what a rural county with no CAD of its own rides) publishes a single composed `SITUS_ADDR` field. Queried live against the real endpoint at the exact coordinates the production duplicate-project item (B1399568) recorded: `SITUS_ADDR: "ALUMAX RD, NASH,"`, `SITUS_CITY: "NASH"`, `SITUS_STAT: " "` (blank), `SITUS_ZIP: " "` (blank) — the trailing comma is baked into the county's own field, not something Planyr assembled. `situsAddress()` (`appraisal.js`) returns that field's value unmodified, by design — it is one column, not something this codebase joins from parts.
  2. **Esri's own forward-geocode `Match_addr`** shows the identical shape one level up. Queried live against `geocode.arcgis.com` for the exact address the second production row is named after: `"address": "16000 Aldine Westfield Rd, Houston, Texas, 77032"` — byte-for-byte the stored `sites.site` value. That string reaches `MapFinder.jsx`'s naming ladder as `searched` (`parcelInfo?.label`) when no parcel/situs was resolvable at the geocoded point, and was stored verbatim. (This row is fully populated — nothing was dropped — which is why it looks unlike the Bowie row on the surface but is the same class of defect: an unsanitized pass-through of an upstream, comma-joined label.)
  - **Why state and zip came back empty for Bowie but not for Houston (item 2 of the brief):** these are two different mechanisms, not one flaky lookup. The Houston row is a live Esri geocoder rooftop match for a well-known, fully-mapped street address — full city/state/zip is the ordinary case there. The Bowie row is a rural county's own appraisal-district data reaching the app through the state parcel harvest; Bowie's own SITUS_ZIP is blank across every neighboring record checked (a countywide gap in that column) and SITUS_STAT is blank on several records too (inconsistent, not a single flag) — this is a genuine data-quality gap in a less-developed county's own records, not a coordinate or network failure on Planyr's side. The composer must treat a partial upstream record as the normal case for a rural lookup, never as an error — which is exactly what the fix below does (it never surfaces an error or blocks project creation on a partial address; it just doesn't keep the empty part's separator).
  - Since Planyr does not control either upstream composer (the county's own harvested field, or Esri's own label format) and can't rely on either one to fix its own join, the fix is defensive at the one choke point this codebase already has for "what should a new project be named": never let a comma-joined label with an empty segment reach a project's name, regardless of which address source produced it.
- **THE FIX.** `appraisal.js` gains `tidyAddressLabel(s)` — pure: split on `,`, trim each part, drop empty parts, rejoin with `, `; returns `null` if every part was empty (so a caller's own fallback ladder still runs), and is byte-identical (idempotent) on any already-clean label. `siteNameFromParcel()` (the one documented function that names "the plan a new plan is seeded with from a picked parcel") now tidies whichever candidate wins its ladder (situs, else searched, else account id) before returning it — the existing mailing-address exclusion check still compares the untidied candidate, so that guard's behavior is unchanged. `MapFinder.jsx`'s `startBlankHere` (the OTHER of the two places a project is born — the located-blank-plan path, which names the project directly from `parcelInfo?.label || addr.trim()` and does not go through `siteNameFromParcel` at all) now runs that same raw label through `tidyAddressLabel` too, so both birthplaces are covered.
