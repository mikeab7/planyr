- **THE DECISION EVERYTHING ELSE FOLLOWS FROM: store the DOCUMENT MODEL (ProseMirror JSON), never Markdown.** Markdown cannot express a merged table cell, a text colour, a font size, a highlight or a checked task — so storing Markdown would have capped the editor at what Markdown can spell, which is the exact inverse of the functionality-first ordering the owner asked for. Markdown is an **export**, and an honest one: what it can say it says (GFM pipe tables, task lists, code fences, quotes, links), what it cannot falls back to the inline-HTML subset every renderer passes through (`<u>`, `<mark>`, `<span style>`, a full `<table>` for merged cells), and `docToMarkdown` **RETURNS the list of constructs that needed a fallback** so the UI names them after an export instead of letting the user discover the gap in another app.
- **THE TREE.** notebook › section › page. A notebook carries an optional `projectId` or `null` for loose; binding at the NOTEBOOK level (not the page) makes "everything on Goose Creek" a one-line filter, and a **loose notebook is visible from inside EVERY project** — a scratch notebook you cannot reach from where you are working is one you stop using. A new notebook is born with a section and a page, so there is nothing to create before typing.
- **THE TREE HOLDS NO PAGE BODIES.** The tree is one storage key; each page body is its own (`planyr:notes:tree:v1:<scope>` / `planyr:notes:page:v1:<scope>:<pageId>`). One blob holding every note would mean every keystroke's autosave rewrites every note ever written — a cost that grows for the rest of the notebook's life. `<scope>` is the signed-in user's id or the literal `local`, so two accounts on one machine never read each other's notes.
- **THE EDITOR: Tiptap, headless, with the entire UI hand-rolled on Planyr theme tokens.** Justified against the repo's dependency rule in the module header: a rich-text engine is not a contenteditable div — selection across nested lists and table cells, undo over compound transactions, Word/Outlook paste normalisation and a serialisable document model are a multi-month build with a permanent bug tail. All packages MIT, all bundled (nothing fetched at runtime), and the whole set rides the lazy editor chunk. **We hand-roll the entire UI and never the engine.**
- **THE TOOLBAR** — headings 1–4 via a block-style select, font family, font size, bold/italic/underline/strike/inline code, text-colour and highlight swatch popovers, clear formatting, four alignments, bulleted/numbered/checkbox lists with indent and outdent, quote, code block, divider, link, insert table, undo/redo, export to Markdown — plus a **TABLE group that renders only when the caret is genuinely inside a table** (row above/below, delete row, column left/right, delete column, merge-or-split, toggle header row, delete table). Every active state is read from `editor.isActive(...)` and **never mirrored into React state** (a mirrored copy drifts the moment the caret moves by any route the toolbar did not originate). Every control cancels `mousedown`, or "select a word, click Bold" would bold nothing.
- **⛔ THE TWO BUGS THE LIVE CHECKS CAUGHT — the component shape IS these fixes, and both are guarded.**
  **(1) Switching pages inside the save debounce LOST the last thing typed.** The obvious flush — ask the outgoing editor for its document on the way out — is a bet on React hook-cleanup ORDER, and it loses: the editor's own cleanup can win, and the flush then queries a destroyed instance. So `onUpdate` snapshots the document as **plain JSON at edit time** (`pendingRef` holds `{id, doc}`) and the flush writes that OBJECT — by then there is nothing left to ask anybody for. The parent additionally **keys the editor by page id**, so a page switch unmounts the instance and its cleanup flushes. `beforeunload` runs the same flush.
  **(2) Reopening a note containing a TABLE crashed the workspace into its error boundary** — `TypeError: Cannot read properties of null (reading 'commands')`, from an effect calling `editor.commands.setContent` against an instance whose command manager was already null. The keyed remount **removes that effect entirely** and the whole class with it: each page gets its own instance, reads its initial content once via a `useState` initialiser, and has its own undo history — which also kills the stale-undo-stack bug where undo walked you into another page's text. There is deliberately **no "sync content on pageId change" effect**, and a source guard fails the build if one appears.
- **A THIRD BUG, found by the harness during this session and fixed the same way.** The tree's flush effect was keyed on `tree`, so every tree change ran the PREVIOUS effect's cleanup — which cleared the freshly-scheduled write timer *and* wrote the tree from its stale closure. Creating the first notebook therefore persisted the EMPTY tree and cancelled the real write, so the notebook vanished on reload. Same discipline applied: capture the value in a ref at edit time, keep the flush referentially stable so it registers once. **A debounce and an effect that both own the same write is a race; only one of them may.**
- **LOUD-FAILURE.** A full quota, a disabled store or a private-mode browser must never look like a clean save. Every failure path broadcasts through `onNotesStorageError` and renders as a named banner; every write returns a boolean that drives the Unsaved/Saved/Not-saved badge. There is no swallowed catch in the store, and a source guard asserts it. The header reads **"Saved on this device"** and does **not** imply sync — sync is **B1291** and is not built.
- **TOMBSTONE-DELETES.** `deleteNode` returns the FULL cascade of orphaned page ids (deleting a notebook orphans every page under every one of its sections), and the caller clears every one. Proven live: deleting a section took the localStorage page-body key count 2 → 0.
- **NO DIALOG BOXES.** Rename is an inline field (Enter commits, Esc cancels); delete asks with an inline "Delete? ✓ ✕" row on the row itself. Guarded across all eight module files.
- **SEARCH covers page titles AND page BODIES**, merged with titles first and an excerpt on body hits — titles pure in `notesModel`, bodies through the store via `docToText`.
- **CHROME.** New `--accent-notes` **#B8418C** (magenta-plum) + `--on-accent-notes` + `--accent-notes-text` (#8C2F69 light / #F0A6D2 dark), mirrored into `shared/theme/palette.js` with a test keeping the two in step. **The hue was picked to clear two hard floors at once, not by eye:** white body text on the fill is **5.03:1** (AA text) AND the fill clears **3.46:1** on the DARK chrome. The first plum tried, #A03270, passed the first (6.59) and FAILED the second (2.64). - **BUNDLE — load-bearing, and the gate fails without it.** The editor is pulled by `lazy(() => import("./components/NoteEditor.jsx"))` **from the workspace root**, inside a Suspense, so the notebook tree paints before the engine downloads. **Measured in this container:** Notes route **554.6 KB**, with the engine a separate on-demand chunk of **463.8 KB** that is not fetched at all until a page is actually opened (asserted live). New `bundle.notesRouteJsBytes` budget wired into `ROUTE_KEYS`, the audit and the ratchet. **`bundle.totalJsBytes` was RAISED** with the measurement on the record: `origin/main` measured **3929.9 KB** in this same container against this branch's **4411.9 KB**, so **the whole +482.0 KB delta is the new workspace** — that metric counts every emitted chunk *by design*, which is what makes it the honest catch-all, so no further splitting reduces it. **A future rise in it WITHOUT a new route is a regression.** `siteRouteJsBytes` moved **+1.0 KB** (the header tab) and `largestChunkBytes` is **byte-identical to main** — the Site route, which is what the owner's slowness complaint was about, is untouched. The owner has explicitly accepted this growth: a new module is supposed to add weight.
