### B831600 (×2) — Selecting across table cells jumped and flashed `[Notes]` (bug) #notes #ui #selection  *(owner chat block 2026-08-28, Silvestri "Utility" note: "when I click and highlight stuff, it just jumps and flashes." Fixture: a 4-row × 1-col Outlook signature table, no class on `<table>`, nested several levels deep inside a list item — per `docs/NOTES-CARRY-FORWARD.md` §2, simplifying this fixture hides the defect. Minted **B831600** from this branch's reserved block B831600–B831615 against `origin/main` 142d614b. DEDUPE-FIRST — searched Open/⏳Verify/Done for `table`, `selectedCell`, `CellSelection`, `jump`, `flash`: no prior item.)*
`[x]` **✅ DONE (×2) — root-caused with a real mouse drag (not a programmatic Range), fixed, and mutation-proven (the guard fails on the pre-fix code with the exact reported symptom). Round 1's fix reached production and immediately reopened; round 2's fix is synchronous by construction, proven red on round 1's own code, and held against three conditions round 1's guard never tested.**
- Verify: sandbox — reproduced and fixed headlessly with a real Chromium drag; no auth/live-GIS/real-project-data dependency (the fixture reproduces the reported shape exactly).
- **ROOT CAUSE, measured, not guessed.** `NoteToolbar`'s Table button group renders only `{inTable && (...)}`, so the instant the caret enters a table the toolbar wraps to an extra row (39px → 75px measured). The toolbar is a SIBLING of the scrollable mat in the same flex column, so the mat's own top edge — and everything painted inside it, the table included — slides down by that exact delta the moment you press the mouse down inside a cell. A drag that starts there has its target crawl out from under a STATIONARY pointer on the very first frame: instrumented before the fix, the native selection never extended across cells at all — `document.getSelection().isCollapsed` stayed `true` through the whole gesture, hopping between wrong text nodes (some OUTSIDE the table) on every mousemove, because each move's screen coordinates resolved against content that had silently moved since mousedown. Leaving the table reverts the bar and the sheet snaps back — the "flash".
- **ROUND 1's FIX, and why the first attempt was wrong.** `NoteEditor.jsx` adds a `ResizeObserver` on the toolbar that folds its measured height delta into the mat's own CSS `transform` (`translateY`), before paint — VIEWPORT-STABLE's prescribed shape. The first attempt compensated `scrollTop` instead (matching this file's existing zoom-compensation code nearby) and it was wrong for this case: zoom changes the CONTENT's height, so there is always scroll slack to absorb into; this shift changes the MAT's own box height, not the content's, so on a short note — exactly Michael's case — `scrollHeight - clientHeight` was already 0 and adding to `scrollTop` was clamped straight back to zero, measured with the table still moving the full 36px. A `transform` has no such floor.
- **VERIFIED (round 1), both directions.** `ui-audit/verify-notes-table-select.mjs`: a known-good control arm (a real drag across four plain paragraphs, no table) stays green throughout; the reported case (real drag across the Silvestri-shaped fixture) now shows zero frame-to-frame jump and the drag correctly builds a `CellSelection` (`.selectedCell` on all 4 cells, `editor.state.selection.empty === false`) where before it stayed collapsed. **Proved the guard goes RED on the unfixed code** (stashed the fix, rebuilt, re-ran): 4/7 checks failed with the exact reported shape (36px jump, collapsed selection, 0/4 selectedCell) — then restored the fix and re-confirmed 7/7 green.
- **Recurrence: 2026-08-28 (×2), same day — owner live-verified the merged round-1 build on planyr.io himself and it still jumped.** Hard numbers from a real drag on Silvestri > Utility, scroll position pinned and unchanged throughout (ruling out scroll re-anchoring): toolbar height flips 38.9px → 74.8px and the table moves the full 35.9px at the same moment, with no correction visible afterward — walking `.ProseMirror` up through `.planyr-note` found every ancestor's `transform` reading `none`. **ROOT CAUSE OF THE RECURRENCE, measured with a `requestAnimationFrame` sampler (the round-1 guard only ever sampled every ~45ms, 2–3 frames apart, and structurally could not catch this):** a `ResizeObserver` callback is a PASSIVE, after-the-fact mechanism, not the synchronous layout effect VIEWPORT-STABLE actually prescribes. On the round-1 build, the frame where the toolbar first measures its taller height still has the mat's `transform` empty and the content already down by the full delta — a real, visible one-frame jump, reproduced on demand — and only the NEXT frame corrects it. That is exactly "jump and flash"; under the owner's real machine (load, a longer-running drag, however Chrome scheduled the notification) the gap can stretch well past one frame, which is what reached production as a shift that never visibly corrected.
- **ROUND 2 FIX.** `inTable` is now computed inline in `NoteEditor.jsx` — the identical boolean `NoteToolbar` renders its extra row on — and the compensation runs in a `useLayoutEffect` keyed on it: a layout effect commits after the DOM mutation but before paint, in the SAME render as the toolbar's row change, so there is no frame in which one is true and the other is not. The `ResizeObserver` stays, now only as a fallback for OTHER causes of the same resize (a window resize changing button wrap, a webfont finishing its load), sharing one height/shift accumulator with the layout effect so the two paths never double-count a delta.
- **VERIFIED (round 2), against three conditions round 1's guard never tested, each proven RED on round 1's own merged code before being proven green on round 2's fix:** (1) the `requestAnimationFrame` race window itself — 1/60 frames raced on round 1's code, 0/60 on round 2's; (2) the scroller PINNED AT MAXIMUM SCROLL (an owner-named condition — his own report had scrollTop pinned with no slack left, the exact case round 1's rejected `scrollTop`-only attempt already failed under) in BOTH directions — entering the table (toolbar grows) and the mirror case, leaving it (toolbar shrinks, moving content the other way): 1/60 race frames each on round 1's code, 0/60 on round 2's, with `scrollTop` itself never moving at all (ruling out a scroll-based mechanism entirely); (3) a PLAIN PARAGRAPH after the table, asserting its own `getBoundingClientRect()` directly rather than inferring correctness from the table's rect: 1/60 race frames on round 1's code, 0/60 on round 2's. `ui-audit/verify-notes-table-select.mjs` grew from 7 to 16 checks across 6 sections. **A self-caught test bug along the way, corrected before it reported a false pass or fail:** the first version of the max-scroll check inferred "compensated" from whether `mat.style.transform` was non-empty, which is right for the GROWING direction but wrong for SHRINKING, whose correct settled state is net-zero (an empty transform) — it reported the shrink case as still racing on the FIXED build. Rewritten to compare the visible position against its own settled value, never against a specific CSS property's shape.
- **NOT COVERED, named rather than silently skipped:** a drag that starts outside the table and has to trigger the browser's own edge-autoscroll to reach a cell below the fold (a separate mechanism, layered on top of this compensation, not exercised here); two rapid successive enter/leave transitions inside one animation frame (the accumulator is additive by construction, but no test exercises more than one transition per sampling window); a table inside a positioned box (`noteAnchor`) triggering the same toolbar growth — only row-level (not frame-sampled) coverage exists for that combination, in `sweep-notes-table.mjs`.
