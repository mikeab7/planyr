### B459 — The cloud save guards the version NUMBER but not CONTENT, so a stale/thin tab silently overwrote a fuller cloud row `[Site Planner / Persistence]` (bug, DATA-LOSS — the actual 8 South 5-building killer)  *(owner pushed back on the 400ms-debounce story 2026-06-25 — "a 400ms gap can't lose 5 buildings I watched save"; he was right; minted **B459** = highest real B# (B458) + 1)*
`[x]` **DONE + unit-verified (branch `claude/youthful-volta-ns1n75`). lint 0 · 1504 tests (cloudThinGuard.test.js +9) · build green.** Owner's skepticism was correct and is the key insight: the 400 ms debounce (B458) can only ever lose the ONE edit in flight — it cannot explain losing 5 buildings placed over minutes and watched save. Losing 5 needs a SECOND failure, which I'd wrongly waved off as "benign" (the Q3 re-push); Cowork independently refused to take it on faith.
- **Root cause (proven by code audit):** the CAS guard (`optimisticUpsert.js` `casUpsert`) is `WHERE id=… AND version=…` — it compares the version SCALAR only, **never the `data` content**. So a tab holding a stale/thin model (e.g. road-only after a bad load / the deploy-crash reload) at a version that still MATCHES the cloud would PATCH right over a fuller cloud row (5 buildings → road-only) and bump the version, badge still "Saved" (it did save — the wrong, thinner copy). There was **no fetch-merge and no content check** anywhere on the write path.
- **Fix (`cloudSync.js`):** alongside `siteVersions` we now remember the **content baseline** we last synced per site — `siteContent` (item count) + `siteTombs` (tombstone count) — populated by `cloudList` (from the cloud row) and advanced on every successful write. New pure `wouldThinClobber(model, baseCount, baseTombs)` blocks a push that would drop **≥2 items the cloud still has with no delete-tombstone to explain it** (`lost = (baseCount − newTombstones) − contentCount(model) ≥ 2`). `cloudUpsert` returns `{ ok:false, conflict:true, thinned:true }` on a hit → the existing **B455 loud + blocking** conflict banner fires; because the write is REFUSED, the cloud stays intact and the next reload union-merges the fuller copy back (no loss). The keepalive forced-reload push (B452) is guarded the same way. Legit incremental **undo** (≤1 unexplained drop/push) and any **tombstoned delete** pass through untouched.
- **Why ≥2, not ≥1:** an undo-of-a-synced-add drops exactly 1 non-tombstoned item — common; the stale-tab clobber drops the whole divergence (5+) in one push. The threshold cleanly separates them; a rare large legit drop trips a recoverable "reload to merge", never silent loss.
- **Closes the loop with B458/B453:** B458 keeps the on-device mirror current; B453 union-merges on boot; **B459 stops the cloud being thinned in the first place.** All three together make the 8 South loss-shape impossible.
