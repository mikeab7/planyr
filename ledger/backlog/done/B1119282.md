### B1119282 (×2) — Choice cells (Type/Unit/Per/Basis) swallowed typing entirely, and Unit carried no dropdown caret `[Site Planner / comps]` (bug) #comps #ui #keyboard  *(owner chat block 2026-09-03, NEW-4, same measurement pass — clicking the Unit cell (value "SF") and typing "A" or "8" did nothing: no editor mounted, the value stayed "SF"; separately, Unit carried no dropdown caret while Type/Per/Basis all did. DEDUPE-FIRST — searched Open/⏳Verify/Done for "showPicker", "type-ahead", "dropdown caret" + comps: B850434/B1066370 (two-click reports on plain `<button onClick>` controls in `CompsPanel.jsx`/`SitePlansSection.jsx`) are a different file and a different control shape — not this. `[x]` **SHIPPED THIS SESSION, both halves, root-caused rather than patched around.** Root cause (found with an instrumented probe — a capturing `window` keydown listener plus a raw CDP keypress, not guessed): HARDENING-10 NEW-3's `.showPicker()` call, fired unconditionally on every select-cell open (including a plain click), opens the browser's native OS popup — and once that popup is open, a subsequent letter keystroke reaches **no page-level JS listener at all**, not React's delegated handler, not this file's own native AT_TARGET listener, not even a capture-phase `window` listener. The keystroke never reaches the app, matching the report exactly. Confirmed the alternative live: a select that's FOCUSED but CLOSED (no `showPicker()`) correctly receives the keydown and the browser's own native type-ahead changes its value.
  1. **The `.showPicker()` call is removed.** A select-kind cell still enters edit mode on the first click/F2/Enter (focused, outlined, immediately typeable) — it just no longer auto-pops its native list open; a second, ordinary click on the now-mounted `<select>` (native browser behavior, no JS needed) or arrow keys still reach the visible list. This is a deliberate, documented narrowing of HARDENING-10 NEW-3's "one click reaches an editable state," argued because a silently swallowed keystroke is worse than one extra click for a mouse user browsing the list visually.
  2. **Deliberate, matchOption-driven type-ahead** closes the gap outright rather than depending on native behavior alone: `matchOption` (compSheetColumns.js's existing prefix-match helper, now exported) is called both when `beginEdit` opens a select cell WITH a typed character (the "select a cell, then type" path via the grid's own keydown handler) and, new, inside `onEditKeyDown` for a cell that's ALREADY open (the literal "click, then type" repro) — jumping straight to the first option whose label/value starts with the pressed character and committing it exactly as a real `onChange` already does (picking an option IS the complete action here). A non-matching character is a no-op, never a guess, same rule `applyCellEdit` already follows elsewhere in this sheet. The printable-character branch in the grid's own keydown handler also gained a missing `e.preventDefault()` (every sibling branch there already had one) — closes the "first-character doubling" class named in the brief, where an un-prevented keydown's default action could double-insert the seeding character once focus lands on the freshly mounted editor.
  3. **Unit's caret (round 1 — INCOMPLETE, see Recurrence below)** — `SheetCell`'s caret condition (`col.kind === "select" && st.state === "editable"`) was extended to `st.state === "fixed"` too, which was Unit's own state on a non-land row (always SF, never a real per-row choice — `compSheetColumns.js`'s `editableFor`). The caret was meant as a purely visual-parity signal there, never a claim of editability — clicking a fixed Unit cell was checked to still mount no editor.
