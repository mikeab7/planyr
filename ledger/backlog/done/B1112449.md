- **Root cause: `unionProjectLists`** (`src/shared/projects/projectModel.js`) drops a bridged (controlled) schedule entry whenever its `linkedSiteId` already has a registry row (`byId.has(p.linkedSiteId)`) — correct and necessary when exactly one schedule links to a site (the registry row is richer: real timestamp/status), but with TWO OR MORE linked schedules **both** bridged copies match that same check and get dropped, leaving the site's ONE registry row as the switcher's only entry for either schedule. Clicking it passes the SITE's id to `Scheduler.jsx`'s `selectSchedule`, whose fallback `projects.find(p => p.linkedSiteId === id)` (`.find()` — first match only) could only ever resolve to the first-created schedule.
- **Fix, two parts:**
  1. **`unionProjectLists`** now counts how many controlled entries link to each registry site. A site with exactly one keeps the prior behavior unchanged (registry row wins, bridged copy dropped). A site with two or more: the registry row is dropped instead (it can no longer stand in for all of them) and EACH linked schedule gets its own row, carrying the site's registry `updatedAt`/`status` for sensible sort order — so every schedule is independently clickable with its own real, unambiguous schedule id.
  2. **`Scheduler.jsx`'s `selectSchedule`** no longer falls back to a bare `.find(p => p.linkedSiteId === id)` (always-first, silently ambiguous). It now uses `findAllBySiteId` and prefers whichever of the site's schedules is ALREADY active over always snapping to the first — so a bare site id (which the fixed switcher no longer produces, but a future/other caller still could) resolves to a stable, non-regressing answer instead of an arbitrary one.
  3. **The breadcrumb naming the WRONG schedule (folded in as NEW-3, see below)** — `currentProject` used to be `linkedSchedule` (first-linked, always), so on a multi-schedule site the crumb named the first-created schedule regardless of which one the grid was actually showing. `Scheduler.jsx` now computes `activeLinkedSchedule` (the linked schedule matching the iframe's own `activeId`, falling back to first-linked only while nothing among the linked set is yet active) and feeds THAT into `currentProject`. A site with exactly one linked schedule is unaffected — `activeLinkedSchedule` is just `linkedSchedule` again.
- **"switching sticks" was already covered, verified rather than assumed:** `needsScheduleCarryIn`/`isGridMismatched` (B1080547) already test membership in the FULL linked set (`findAllBySiteId`), not just the first match, so once a site has two rows the carry-in never fights a deliberate switch between them — confirmed by reading, not re-built.
