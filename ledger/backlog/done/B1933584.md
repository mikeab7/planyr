`[x]` **ROOT CAUSE FOUND AND LIVE-REPRODUCED, not just read from source.** `MapFinder.jsx` keeps its Leaflet map alive while the Map view is hidden (`display:none`, never unmounted — `SitePlannerApp.jsx` mounts BOTH the Map and Plan hosts permanently). A "hand memory back while hidden" effect used to call `tileLifecycle.releaseLayer(map, layer)` DIRECTLY on whatever `overlayRefs.current[key]` held. For a ROLE-SPLIT layer — FEMA (`roleLayers: {area:[28], line:[27]}`) and BKDD's two role-split rows (`bkdd_drainage`, `bkdd_dmp`) — that ref is `rasterComposite(slots)`, a plain `{__pfParts, setOpacity}` object never itself added to the Leaflet map, so `releaseLayer` was a silent no-op on it: `map.removeLayer` returned immediately (the composite was never in `map._layers`), leaving the composite's TWO real esri-leaflet layers fully attached, still bound to `moveend`, with nothing left anywhere that referenced them once `overlayRefs.current.fema` was deleted. They repaint the next time the map is interacted with (a pan/zoom crossing FEMA's own street-level scale gate is exactly what surfaces it), checkbox unchecked or not — matching the report exactly. `syncOverlayLayers`'s OWN internal toggle-off path was already correct (it always unwrapped `__pfParts`); the bug was this SECOND, independent caller re-deriving the release rule and getting it wrong.
- **LIVE REPRO, sandbox-network-stubbed** (`e2e/mapfinder-overlay-teardown-leak.spec.js` — FEMA's `?f=json` + `/export` stubbed the same way `e2e/layer-point-hover-identify.spec.js`'s B1490144 block does; the sandbox cannot reach `hazards.fema.gov` for real, per this repo's own standing note): toggle FEMA on from the Map view (it paints) → open a project's planner (Map view hides) → the shared `overlays` state turns FEMA off (the seeded project has no saved layer override, so SitePlanner's own per-site restore-on-mount effect resets it — functionally identical to the user unchecking it) → return to the Map view and zoom in (a real UI interaction, the `.leaflet-control-zoom-in` button, never a synthetic event). **Proven RED on the pre-fix build:** export requests to the FEMA host go 4 → 8 after the return-to-map interaction — a further, unsolicited paint with the checkbox reading unchecked. **GREEN after the fix:** the count stays flat and the diagnostic hook below reports zero orphans.
- **THE FIX, generic — `releaseOverlayRef` (layers.js), not a FEMA-only patch.** Exported the composite-unwrap rule `syncOverlayLayers`'s own internal `release()` already had (`if (lyr.__pfParts) … else releaseLayer(map, lyr)`), so `MapFinder.jsx`'s hidden-view teardown effect now calls the SAME function instead of the raw `tileLifecycle.releaseLayer`. Covers every role-split row (`fema`, `bkdd_drainage`, `bkdd_dmp`), not just FEMA.
- **A SECOND, independently-confirmed defect fixed in the same pass (LOUD-FAILURE): `wireRasterStatus`'s `'load'` handler (layerRequest.js) had no `isActive()` gate**, unlike every other late-arriving callback in that function (the stall watchdog, `requesterror`). An export request still in flight when a layer is toggled off/released could report the Layers-panel status dot "loaded" (blue) for a layer that no longer exists, the moment its underlying `<img>` finished downloading. Fixed the same way the sibling callbacks already were.
