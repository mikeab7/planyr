`[x]` **ROOT-CAUSED AND FIXED — the actual mechanism, not a visual nudge, and every other render site that shared it.**
- **ROOT CAUSE.** Three separate padded-box `<text>` renders in `SitePlanner.jsx` — the callout/text-box body (`renderCalloutNode`), the parcel acreage chip, and the measurement summary chip — placed each line's baseline with a hand-tuned magic ratio (`fontPx * 0.82` / `fs * 0.82`) off the SVG default (alphabetic) text baseline, instead of centering it on its own line slot. The box's HEIGHT was already built symmetrically (`h = lines*lineH + padY*2`, `boxH = fs + padY*2`, `boxH = lines.length*lh + padY*2`), but the 0.82 ratio was a flat constant tuned to look centred on one sample string — it does not derive from the font's real ascent/descent metrics, so it puts a different amount of white space above the glyphs than below them for every other string. Copy-pasted verbatim across the three sites, so the defect and the fix are both one mechanism, not three.
- **THE FIX.** Each line now renders with `dominantBaseline="middle"` at its own SLOT CENTRE (`padY + lineH/2 + i*lineH` for the callout; `padY + fs/2` for the single-line parcel chip; `padY + lh*k + lh/2` for the per-row measurement chip) — the same `dominantBaseline="middle"` convention every other centred `<text>` in this file already uses (element name labels, dimension numbers). Since the box height is already symmetric, the gap from box-top to the first slot's centre and from the last slot's centre to box-bottom are now BOTH exactly `padY + lineH/2` (or the per-site equivalent) — provably equal, for any line count, independent of which specific glyphs are on the first vs. last line.
- **MEASURED, before and after, in a real headless browser** (`ui-audit/verify-callout-padding-symmetry.mjs`, seeded via a real fixture, not a synthetic DOM): the pre-fix build read **11.37px / 7.68px / 3.61px** top-vs-bottom slot asymmetry on the callout / parcel chip / measurement chip respectively (30–100% more space on one side than the other); the fixed build reads **0.00px** on all three, exactly as the symmetric box-height formula guarantees.
- **Regression guard.** `test/calloutPaddingSymmetry.test.js` — a source guard against the exact old broken expressions reappearing (not just the bare "0.82" substring, which this fix's own explanatory comments also mention by name), a positive check that all three sites now carry `dominantBaseline="middle"` at the new slot-centred `y`, and an algebraic proof (against the real `calloutLayout()` output, several line counts and zoom levels) that the box-height formula keeps the slot-symmetry invariant.
- **PERCEPTUAL-PARITY / visual-regression.** This deliberately changes the picture (that is the whole point — the old picture was wrong), so PERCEPTUAL-PARITY's "imperceptible" bar does not apply; `node ui-audit/visual-regression.mjs --check` (against the CI-pinned Chromium revision 1228) reports every desktop surface/theme pair **identical, 0 differing pixels** both before and after this change — the demo fixture used for those baselines carries no callout and its parcel/measurement text happens to sit outside the diffed pixels, so no baseline needed re-approving. The 8 pre-existing phone-viewport advisory warnings are unrelated (a standing, already-flagged Chromium-revision drift, unaffected by this change).
