### B298753 (×2) — Quick open did not take the keyboard, so typing went into the note behind it `[Notes]` (feature → bug) #notes #ui #persistence  *(originally filed 2026-08-09 from the owner's Tier-1 chat block; RE-OPENED the same day from his live verification of the merged build. DEDUPE-FIRST — this is a defect in the palette B298753 shipped, found on the build B298753 produced, so it takes the RECURRENCE treatment rather than a new number: anyone searching `quick open`, `Ctrl+K` or `QuickOpen.jsx` must land on ONE item carrying the whole story. Searched Open / ⏳ Verify / Done across `focus`, `overlay`, `palette`, `activeElement`, `keydown`, `B1392`, `B1393`, `B36051`: no other item covers keyboard ownership of an overlay.)*
`[x]` **✅ DONE 2026-08-09 (×2) — the palette claims the keyboard at the CHORD, not when it mounts. Nothing typed while it is open can reach the document, and nothing typed is lost either.**
- Verify: sandbox — reproduced HERE first, then fixed, then mutation-proven (ATTEMPT-BEFORE-YOU-PARK).
- Recurrence: 2026-08-09 — *"Ctrl+K opens the panel, but THE PANEL DOES NOT TAKE KEYBOARD FOCUS. I typed `Quadvest` and every character went into the NOTE behind the panel. The list never filtered. The word was written into his real Entitlements note, which had been empty."* **Data written into an owner's note by a feature that looks like a search box.**
- **⛔ THE MECHANISM, REPRODUCED BEFORE ANYTHING WAS CHANGED.** The chord only set React state; the PANEL claimed the keyboard by focusing its own field in a mount effect. Between those two moments nothing was claiming anything and the editor still had focus. The width of that gap is the whole bug: on a warm cache it is one React commit and **one character** leaks (measured: the `Q` of `Quadvest` landed in the document); on the FIRST Ctrl+K of a freshly-deployed build it is the download of the palette's lazy chunk, so **the whole word** leaks and the panel then appears showing an unfiltered list — which is exactly what he saw.
- **⛔ THE FIX DOES NOT DEPEND ON FOCUS, WHICH IS THE POINT.** A correctness property must not be a race with a chunk download, a React commit, and anything else that might take focus back. One window-level capture handler in `Notes.jsx` — the module that is ALREADY loaded — decides both things: it opens the palette on the chord and, from that same event onward, swallows every key not aimed at the palette. The open/closed flag is a **ref, flipped synchronously inside the event**, not state: an earlier version armed the swallow from a `useEffect` on `quickOpen` and still lost the first character to the commit it waited for.
- **⛔ AND SWALLOWED KEYS ARE BUFFERED INTO THE QUERY, NOT EATEN.** Discarding them would fix the data loss and leave the feature feeling broken — you type a name and nothing happens. Buffering puts every character where the person meant it to go, so typing straight through the chord filters the list before the panel has painted.
- **A SECOND, QUIETER BUG FOUND WHILE FIXING THE FIRST:** the panel called `select()` on mount. With an empty query that did nothing — but with a character buffered by the new gate it highlighted it, so the next keystroke replaced it and the field read `uadvest`. The caret goes to the END now; `select()` is gone.
- **Escape returns the caret to where it was.** The palette remembers `document.activeElement` before taking focus and restores it on close, so the next keystroke goes back into the note rather than to the page.
- **THE SAME CLASS ON THE OTHER TWO SURFACES, checked rather than assumed.** The **slash menu** is the deliberate opposite — its keystrokes are *supposed* to reach the document, because the `/h2` you type IS the filter and is removed when a command runs; what must not arrive as text is the navigation, and arrows/Escape are asserted inert. The **history pane** is a side pane that never takes focus, so typing while it is open must keep going to the note — a pane that quietly ate keystrokes would be the mirror image of this bug and just as invisible; asserted.
- **⛔ WHY THE ORIGINAL CHECK PASSED, and what changed so it cannot again.** `verify-notes-tier1.mjs` §3 waits for the panel before it types. That wait is exactly what a person does not do, and it is what made a data-writing bug look like a passing feature. The new rows assert BOTH halves every time — the list filtered to the expected note AND the underlying document byte-for-byte unchanged.
- **AND A MEASURED ADMISSION, recorded because it decides which row has teeth.** On a warm cache the race does not reproduce in this sandbox at all: against the broken build the timing rows stayed green at 55 ms between keystrokes **and** at full speed, because Playwright's key dispatch is slower than a React commit once the chunk is downloaded. So the two rows that actually catch it are the **deterministic** one — focus is put back in the note with the palette open, which is his symptom with the race taken out — and the **cold** one, which delays the palette's chunk in a fresh browser context so the gap is a real network round trip.
- Sandbox: `ui-audit/verify-notes-tier1.mjs` §10–§12 (15 new rows). **Mutation-proven: reverting the gate, the `select()` removal and the focus restore turns 7 rows red**, including the deterministic focus row and all three cold-chunk rows — and the mutated build reproduces the owner's report exactly (`Quadvest` in the document, list unfiltered). Full suite green, lint 0 errors, build green.
