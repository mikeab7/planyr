**Findings, measured not assumed:**
1. **ID collision is NOT the mechanism.** IDs mint from a per-BRANCH reserved block (B6864–B6867), not a shared counter — confirmed live: `npm run next-id -- --against-main` on this branch returned `B1592848–B1592863 · V1130832–V1130847`, "reserved by branch name, so a session minting at the same moment cannot draw the same number." So every one of the measured collisions is pure **textual adjacency in an append-only file**, never two sessions racing for a number.
2. **A safe, precondition-checked resolver already existed (`scripts/resolve-ledgers.mjs`, B296224) and simply was not being run.** It refuses (real conflict markers, nothing written) the instant an id appears on both sides of a hunk, and rolls back a union that would introduce a cross-file duplicate. Documented in `CLAUDE.md` since 2026-08. PR #1673/#1675/#1656 all went conflicted and were hand-rebased instead — the tool was never broken, it was a separate step nobody remembered mid-merge.
3. **While reproducing the brief's "one branch edits while another appends" case for real (a live git merge, not reasoning about one), found and fixed a genuine gap in that resolver's own precondition** — reproduced against the actual shipped code before touching it. An in-place edit to a non-heading line inside an existing item (two branches each rewriting the same item's `- Verify:` line differently) never puts a `### B#` heading inside the conflict hunk, so the id-overlap check saw two empty sets and called it safe: `resolveConflicts()` returned `ok: true` and would have unioned both edits into one item's body — exactly the "two sessions amending the same item" failure the script exists to be incapable of, just invisible to a heading-only check. Same gap covers an edit racing a delete/archive-move (one side empty, the other a bare body fragment). Fixed: a hunk is now also refused whenever either non-empty side is not a clean, complete new-item insertion (`isPureItemInsertion`, `scripts/resolve-ledgers.mjs`).
4. **Dogfooding `safe-merge` against this session's own real (shallow) clone surfaced a second, real gap in the WRAPPER itself, fixed in the same pass.** `git merge` can fail for reasons that are not a content conflict at all (a dirty working tree, a shallow clone unable to compute a merge base, `refusing to merge unrelated histories`) — in every one of those cases `unmergedPaths()` is trivially empty, and the first draft of `merge-ledgers-safe.mjs` read that as "safe to finish" and went on to run `resolve-ledgers.mjs` (a harmless no-op) and then `git commit`, which is meaningless when no merge is underway. Fixed by checking `.git/MERGE_HEAD` — present iff git actually entered a merge — before treating "no unmerged paths" as license to commit; a merge that never started is now refused outright (`outcome: "merge-did-not-start"`), with the real git error surfaced and nothing touched. Pinned by both an injected-spawner unit test and a real dirty-working-tree E2E reproduction (`test/mergeLedgersSafe.test.js`).

**Adjacent cases — measured by actually creating the branches and merging them (`test/mergeLedgersSafe.test.js`), not reasoned about:**

| Case | Measured outcome |
|---|---|
| Two branches append DIFFERENT, well-separated entries | Git's own `ort` merge strategy resolves with **zero conflict**, no tool involved. Proximity alone does not create a conflict — an edited line a few lines from an unrelated insertion still merges clean; only a genuine line-range overlap does. |
| Two branches append at the EXACT SAME anchor (both prepend to the top of a section — the #974 shape) | Real conflict, disjoint ids → `safe-merge` auto-resolves via `resolve-ledgers.mjs`, exactly one merge commit, nothing left for a human. |
| One branch appends using an existing line as its insertion anchor while another branch edits that exact line | **The case union handles worst.** Real conflict, in ONE hunk mixing the edit and the insertion. Before this item's fix: a bare union would write the edited line, the original line, AND the new item all concatenated — the existing item's block corrupted with a duplicated line and a different item's content grafted into the middle of it (reproduced and asserted in the test). After the fix: `safe-merge` REFUSES — conflict markers left in place, nothing committed. |
| A branch appends to BOTH `BACKLOG.md` and `VERIFICATION.md` in one commit, merged against a branch that touched both | Both files' conflicts resolved independently in one pass; exactly one merge commit for both. |
| Rebase vs merge on the identical branches | NOT the same operation. Merge: one command, one merge commit (2 parents). Rebase: pauses per replayed commit; `git commit` mid-rebase **succeeds** but only closes that one step — the rebase is still "in progress" afterward and git says so ("use git rebase --continue once you are satisfied") — a materially different completion story than merge's clean single commit. `resolve-ledgers.mjs` still works mid-rebase (it only reads the working tree's conflict markers), but finishing needs `rebase --continue`, not `commit`. `safe-merge` deliberately targets merge only, matching this repo's standing preference never to rebase shared branch history. |
