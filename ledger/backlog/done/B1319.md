**The defect — five things, all visible in one frame.** (1) **SIZE:** the editor was `W=96 · H=30 · fontSize 13` while the setback chip it edits is a 26 × 15 pill with 9.5 px text — roughly four times the thing it edits, in every dimension. (2) **THE VALUE TWICE:** it rendered at `bp.y - H - 8`, i.e. ABOVE the anchor, so the editor's "25" and the chip's "25′" were on screen simultaneously, one right above the other. (3) **IT COVERED THE WORK:** it landed on the building, the setback line and the setback drag handles — the exact geometry you are looking at while deciding the number. (4) **NATIVE SPINNERS:** a bare `input type="number"`, so the browser painted its own chevrons; they match nothing else in the app, which already has its own steppers (B463/B618). (5) **STYLING THAT MATCHED NOTHING:** a 2 px accent border, a `ui-monospace` face and a heavy drop shadow, none of which appear on any other control in the planner.

- **THE FIX IS AN IN-PLACE EDIT, and that is what removes four of the five faults at once.** Clicking a setback chip turns THAT CHIP into the field: the pill stays where it is, at its size, and its text becomes editable with the value selected so typing replaces it. Nothing grows, nothing moves, nothing is covered — and the value appears exactly once, because the chip IS the editor. The static chip is SUPPRESSED while its editor is open (`pill` returns the field INSTEAD of the plate+text, an early return rather than a sibling), so the two can never both paint.
- **`lib/numEditBox.js` is the new pure home for WHERE the editor paints and AT WHAT SIZE** — the chip's metrics (`SETBACK_CHIP`, `setbackChipPlateW`) moved there from the render site, so the plate and the field cannot drift apart, and the guard test measures the editor against the REAL chip rather than a copy of its numbers. `numEditFitsSpawn` states the invariant this item exists to keep; the old 96 × 30 box fails it, which is what makes the guard non-vacuous.
- **The editor is SHARED, so the fallback had to be designed, not left behind.** Road width, element dimension, overlay trace length and aerial calibration have no chip to become. Those keep a small FLOATING field — same component, same tokens, same absence of spinners — brought from 96 × 30 @ 13 px down to 54 × 18 @ 10.5 px, and OFFSET up-and-to-the-side of the anchor instead of centred over it, so the dimension being measured stays readable.
- **The native spinners are gone app-wide, not per-field** (`index.css`: `appearance: textfield` + both `-webkit-*-spin-button` pseudo-elements), so a number input added tomorrow cannot reintroduce them. At 15 px the right stepper is **no visible buttons at all**: ArrowUp/ArrowDown nudge by one, Shift by ten, clamped at zero (`nudgeNumEditValue`), with the browser's own step suppressed so a nudge can't double.
- **Restyled to the app's own control tokens:** one-pixel border, `NUM_FONT` with `font-variant-numeric: tabular-nums` (the same pair the chips already use, so the digits sit exactly where the chip's digits sat), no drop shadow. The focused-input treatment is the app's shared one from `index.css` (accent border + a soft ring), which is the point — it now matches every other input in Planyr instead of being the only control with a shadow.
- **`display:block` on the field is load-bearing, and the harness is what caught it.** An `<input>` is inline-level, so inside a `<foreignObject>` it sits in a line box and the strut above it put the field **5 px below** the plate it replaces — the first harness run measured `Δ 0.00, 5.00` and failed. A block box has no strut; the check now reads `Δ 0.00, 0.00`. Same trap B1140 hit with the contour hover label.
- **Every behaviour that already worked is kept:** Enter commits · Escape cancels · blur commits · the full-canvas backdrop click commits · and the **Alt-click override of a single segment inside a grouped run** (the run opener's closure is untouched; it only gained the `chipKey` third argument). The chip key is passed FROM the pill and never re-derived in the opener, so the field and the chip it replaces cannot disagree about which one it is.
- **MODULE-SCOPE-COMPONENTS:** `components/NumEditField.jsx` is defined at module scope, not inside the planner's render body, and the focus+select runs in a mount-only `useLayoutEffect` (an inline `ref` callback would re-fire every keystroke and re-select mid-edit).
- **Guards (the three the brief asked for, plus the behaviours).** `test/numEditInPlace.test.js` — 21 tests: the field is never larger than its spawn across every chip text the app can produce (with the OLD box asserted to FAIL the same invariant), it lands exactly on the plate's rect, the chip and the field are never both in the DOM, the floating fallback is at chip scale and offset off its anchor, the app-wide spinner suppression is present for both engines, and the nudge/commit/cancel/Alt-click behaviours hold. `ui-audit/verify-numedit-inplace.mjs` — the live pass, below.
- **PANEL-BREVITY: n/a** — no yield or pond panel copy touched. Net copy change in the product is **negative**: the editor now shows a number and nothing else.
- **Bundle:** inside band, no ratchet raise needed (`perf:bundle` green; the two new modules are ~1 KB of code and land on a route that already imports the render site).
