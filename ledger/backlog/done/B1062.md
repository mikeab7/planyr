**Why neither guard caught it (AUDIT-FIRST, reconciled against the code, not the claim).** `ui-audit/diagnose-map-lock.mjs` asserted *"the basemap sits at exactly the drawing's scale at start, far and back"* — three SCALE assertions plus a map-CENTRE return, and no assertion that a real out-and-back GESTURE returns the DRAWING to its starting lock. `test/mapLock.test.js` asserts the round-trip invariant analytically over the pure model, which by construction cannot see a quantisation that lives in Leaflet's commit path. The residual lived exactly in that seam.

**Adjudicated: it is (i) a genuine bounded quantisation, NOT the reporting harness — and it is ONE SCREEN PIXEL, not 36 feet.** The live probe was zoomed out to ~36.7 ft per screen pixel, which is the only reason a one-pixel offset reads as 36.5 ft; the error is constant in PIXELS, so it shrinks with the zoom (inches at a working site zoom) and can never put a pond over a freeway. Driven both ways in the sandbox against the real page:
- **A pure PAN is exactly lossless and does not move the registration at all.** A mouse drag moves the view by whole pixels, so the pan the basemap needs is a whole number and Leaflet's rounding is the identity. Replaying the live harness — 4 × 300 px drags out, settle, 4 back, **twice** — returns **0.0000 px**, as does an exactly-symmetric programmatic out-and-back and a single long 98,000 ft excursion. So the live residual did **not** come from the panning, and the harness-asymmetry hypothesis is **refuted for the pan path**.
- **A ZOOM commit does move it.** Leaflet can only place the basemap on whole screen pixels — `_getNewPixelOrigin` ends in `._round()`, the map pane's position is integer, and `panBy` rounds its offset — while the drawing's offsets are arbitrary floats. Every `setView` re-snaps the basemap onto a fresh whole-pixel grid and the registration hops to a new sub-pixel remainder: **measured wandering between 0.25 and 0.74 px across repeated zoom commits, never growing.** Bounded by half a pixel at any instant and a whole pixel between two instants — which is exactly the 36.5 ft (= 1.0 px) the live pass measured.

**Deliberately NOT compensated, and the reasoning is recorded so it is a decision rather than an omission.** The only two ways to remove the last sub-pixel are to leave a permanent fractional transform on the tile wrap — which resamples, i.e. **softens**, the aerial, the one thing B1049/V483 forbade buying anything with — or to nudge the drawing's own view offsets, which would destroy the exactly-reversible pan B1043 exists to guarantee. A sub-pixel offset is a better outcome than either. What it is owed is a **committed bound**, which is what this item ships.

**The gate now asserts POSITION, with the epsilon committed rather than implicit** (`ui-audit/diagnose-map-lock.mjs`):
- `LOCK_EPSILON_PX = 1.0` — how far the drawing may sit from the imagery at any instant or between any two instants. Stated in **pixels, not feet**, because the quantisation is a pixel-domain effect and a feet threshold would be meaningless at one zoom and vacuous at another; the feet equivalent is printed alongside every reading so the number stays legible.
- `PAN_EPSILON_PX = 0.001` — a pure pan has no rounding to do, so an out-and-back pan must return **exactly**. This is the tight one, and it is the assertion the original B1043 defect would have failed outright.
- New readings per state: the **instantaneous** drawing-vs-imagery offset (`lockOffsetPx`'s idea, measured against the LIVE Leaflet map rather than the pure model, so it sees what the unit test cannot), and the live session's own **per-element geo probe** — the lat/lng the basemap assigns at each drawn element's screen centre.
- New phases: the live harness replayed (4 × 300 px out, settle, 4 back, **twice**, with an explicit accumulation check between the two trips), and a **zoom** out-and-back repeated three times, since zoom commits are the only path that re-snaps the basemap.

**Two harness traps, both hit here, both now written down in the file so the next person does not re-chase them:**
- **Anchor by geometry signature, never by a held DOM reference** (the live session's own finding — B1047's culling removes and RE-CREATES off-screen elements, so a held reference goes stale mid-excursion). Extended: the signature must also be **unique or discarded** — a `rect` laid out by a transform carries no `x`/`y` attribute, so a naive signature degenerates to one string for many elements and the harness silently compares element A against element B. That mis-anchoring read as a **perfectly constant 1.72 px "residual"** until the uniqueness filter went in.
- **The SVG and the Leaflet container are separate, non-coincident boxes** (a few hundred pixels apart in this layout). Comparing an SVG-local coordinate with a container-local one without that delta reads as a huge constant "error" that is pure frame mismatch — it showed up as 386 px.

**Teeth, verified both directions this session — the position half is not vacuous.** Re-injecting B1043's original mixed model (linear-in-latitude position + zoom re-derived at the panned-to centre) makes the gate FAIL on `far: the drawing sits 2.236 px off the imagery (epsilon 1 px)` **as its own failure line**, independent of the scale assertions; restoring the fix returns it to PASS. This also forced a real change: the excursion was lengthened from one drag (~25,000 ft) to **four (~98,000 ft, the scale of the live repro)** — at the short distance the re-injected defect sat at **exactly 1.00 px**, right on top of the quantisation floor and indistinguishable from it, so the guard would have missed the very bug it exists to catch.

**One code change, with honest scope.** `exactContainerPoint` (new, `lib/mapLock.js`) is `latLngToContainerPoint` without Leaflet's snap; `SitePlanner.jsx` now uses it to aim the pan commit and to build the live gesture transform. Leaflet's public `latLngToContainerPoint` rounds the projection, so aiming a pan with it rounds once there and again inside `panBy`. **It measured as no change, and provably cannot be one on an even-sized container** — `round(round(w) - k) === round(w) - k` for integer `k`, and half-the-size is then an integer. It removes the odd-dimension case (where the two roundings can disagree by a pixel) and removes a rounded input from the gesture transform, which is fractional by nature and never wanted one. **It is explicitly NOT the source of the V478 residual** — that is Leaflet's zoom-commit snap, which no call-site change can reach. Recorded this way rather than as a fix so a later reader does not mistake it for one.
