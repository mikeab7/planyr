**AUDIT-FIRST — THE HYPOTHESIS WAS TESTED, NOT ASSUMED, AND HALF OF IT DID NOT HOLD UP UNDER MEASUREMENT; SAID PLAINLY RATHER THAN PAPERED OVER.** Instrumented `ProjectBreadcrumb.jsx` live (console traces on `commitRename`/`pickProject`, plus a document-level capture listener recording every native click/focusin/focusout/keydown/keyup) and drove the exact reported gesture through a real Chromium browser (Playwright), varying every adjacent case the dispatch named — Enter vs click-away vs Escape, the renamed row at the top of the list vs further down, the project being renamed being the one currently open vs a different one vs none. **The first half of the hypothesis is CONFIRMED, measured directly: the dropdown's row order visibly reorders live, mid-edit, the instant a rename commits, while the dropdown stays open** — `groupProjects`' recency sort really does re-run and really does move the renamed row (and displace whatever was above it) before the user has done anything else. **The second half — that this reorder is what makes Enter's own keystroke land on the wrong row's click handler — could NOT be reproduced through automation despite the range of scenarios above**: in every measured run, once the rename input unmounts, DOM focus settles on `<body>` (not on any button), the subsequent native `keyup` for the same physical Enter press targets `<body>` too, and no `click` event ever fires on a neighboring row. This may be a real browser/OS-specific focus-retention quirk this sandbox's Chromium doesn't reproduce, or it may be that the reported "opens a different project" is the SAME underlying hazard (a shifting list under live interaction) manifesting through a path this session's instrumentation didn't happen to hit. Either way, the confirmed half is a real, user-visible defect in its own right — a dropdown that reorders itself out from under an open rename is wrong regardless of whether it also swallows the next keystroke — and the fix below closes the entire class rather than chasing one unreproduced mechanism.

**THE FIX, exactly the two design points the dispatch named, plus the read-path fix for its third:**
1. **Freeze the row order for as long as the dropdown stays open, once an edit starts.** `applyFrozenOrder` (new, pure, `src/shared/projects/projectModel.js`) re-orders a project list to match a snapshot of ids taken before the edit began, appending anything the snapshot doesn't know about (a project created since) at the end. `ProjectBreadcrumb.jsx` takes that snapshot the moment `startRename` fires (once per dropdown session — a second rename doesn't re-freeze onto whatever the first already shuffled) and clears it only when the dropdown closes. Content (name, "just now") still updates live through the frozen positions — only ORDER is held.
2. **Re-anchor focus to the renamed row's own button, by identity, never by position.** Measured directly: after a commit (or a cancel), `document.activeElement` fell to `<body>` with nothing to correct it. `ProjectBreadcrumb.jsx` now keeps a `rowButtonRefs` map (project id → its own activate button) and, in a `useLayoutEffect` keyed on `editingId`, moves focus to the just-edited row's own button — so a keystroke landing after the rename has a correct, predictable place to go instead of nowhere.
3. **The same-session's own read-path fix, per the dispatch's third symptom** ("the renamed name doesn't show up in the list for a beat — as if re-read from the server"): `commitRename` used to call `refresh()` SYNCHRONOUSLY right after issuing the rename write — but `storeRename` (`projects.js`) is a dynamically-imported async call by design (the heavy storage engine loads on first use, B927105), so that immediate `refresh()` could still read the PRE-rename data, and — worse — would silently clobber an optimistic update with that stale read in the same tick. Fixed by patching the renamed project's name into local state OPTIMISTICALLY (immediately, before the write even starts) and moving the reconciling `refresh()` to run only once the write has actually settled (inside the existing `.then()`), never before. Confirmed the same read path: yes, it's the identical `refresh()` call the reorder symptom traces to.

**ADJACENT CASES, checked live as instructed, not assumed:** Enter vs click-away (blur) vs Escape — all three commit/cancel through the identical `editingId`/order-snapshot machinery, so all three are covered by the one fix; the row being renamed at the top of the list vs further down — both frozen identically, and renaming the already-top row is a no-op for order by construction; the project being renamed being the one currently open vs a different open project vs none open at all — none of the three navigates anywhere in any case, proven below.
