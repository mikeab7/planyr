`[x]` **AUDIT-FIRST correction — the dispatch's own "CAUSE" pointed at the wrong function for this repro, and that discrepancy is recorded rather than silently worked around.** The dispatch said `resolveSearchField`/`detectField` (parcelQuery.js/counties.js) was responsible for the card showing "0"/"-1"/"64810". Reading the actual render path: `counties.js`'s `detectField('id')` **never matched OBJECTID/FID at all** — its old regex had no such alternative — so it was not the mechanism producing this repro. The real cause is a SECOND, wholly separate id-shaped-column regex that lived only in `MapFinder.jsx` (`const ID_RE = /(…|objectid)/i`, used solely via `findAttr(attrs, ID_RE)` to compute the "Account / ID" card value and the plan hand-off's `acct`) — it additionally matched a bare `"objectid"` substring, and on a WinGAP-export layer whose FID/OBJECTID/OBJECTID_1 column sits ahead of the real parcel number in field order, it won every time. An ID **search** on the same county already queried the correct column (via `resolveSearchField`) — the card and the search had simply never been the same code, so they silently disagreed. Hardening `detectField`'s ranking (which the dispatch also explicitly asked for, with its own unit-test spec) is real and correct defense-in-depth, but by itself would have changed nothing about the reported symptom, since `MapFinder.jsx` never called `detectField` to build the card value in the first place.
`[x]` **Fix, three parts, all required.** **(1)** `counties.js`'s `detectField(fields, "id")` is now RANKED, not one flat alternation: `ID_RE_STRONG` (a real parcel/account-shaped column — broadened to also catch `parcel_?no`/`parcel_?num(ber)?`/`parcel_?nbr`/`parcelnumb`/`^parcels$`/`pin` -anywhere/`^apn$`, on top of the existing `hcad_?num`/`acct`/`account`/`parcel_?id`/`prop_?id`/`pid`/`quick_?ref`/`geo_?id`/`gid`) → `ID_RE_WEAK` (a bare `"Parcel"` column — real, but too generic to trust over a real number; Cook County GA carries both) → `ID_RE_OBJECTID` (the layer's own row identity — `objectid*`/`fid`, tried ONLY when nothing else qualifies, so a county with no better column still gets a working ID search rather than "No account/parcel-id field on this layer" — this is what ga_baldwin/ga_tift now fall back to). A `pinIdField: true` row still short-circuits all of this, exactly as before. **(2)** `pinIdField: true` added to all 32 third-pass rows that already carry a measured `idField` (every third-pass county except `ga_baldwin`, which has no measured column, and `ga_richmond`, which was never given one and is untouched by this item) — `ga_effingham` PARCEL_NO, `ga_barrow` Parcel_no, `ga_cook` Parcel_No, `ga_twiggs` PARCELID, `ga_hall` PIN, `ga_whitfield` PARCEL_FUL, `ga_fayette` PARCEL_NO, `ga_spalding` PARCEL_ID, `ga_newton` PARCEL_NO, `ga_oconee` PARCELID, `ga_butts` GSI_PIN, `ga_monroe` PARCELID, `ga_troup` parcelnumb, `ga_peach` PARCELS, `ga_muscogee` TaxPIN, `ga_morgan` Parcel_No, `ga_brantley` Parcel_No, `ga_charlton` PARCEL_NO, `ga_clay` Parcel_No, `ga_crawford` PARCELNO, `ga_crisp` Parcel_No, `ga_dade` PARCEL_NO, `ga_dooly` Parcel_No, `ga_echols` PARCEL_NO, `ga_emanuel` Parcel_No, `ga_evans` PARCEL_NO, `ga_greene` Parcel_No, `ga_lanier` PARCEL_NO, `ga_meriwether` Parcel_No, `ga_sumter` PARCELID, `ga_turner` Parcel_No, `ga_ware` PARCEL_NO. **(3) The actual fix for the repro:** `MapFinder.jsx`'s local `ID_RE` constant and its three `findAttr(attrs, ID_RE)` call sites are DELETED — replaced by a new export, `idAttrFor(county, attrs)` (`lib/parcelQuery.js`), which resolves the id VALUE off the exact same field `resolveSearchField` would choose for a search on that county (pinned or detected), so the card and a search can never name two different columns again. `findAttr` itself is untouched and still used elsewhere in `MapFinder.jsx` (e.g. `backupCountyLabel`).
