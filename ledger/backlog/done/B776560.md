- **(1) THE RULE, applied: A PREFIX OF A VALID NUMBER IS NOT AN ERROR — validate on blur/Enter/commit, never on keystroke.** The band-width field is now `BandWidthInput` (`RoadCrossSectionDialog.jsx`), a local draft/commit input mirroring `SitePlanner.jsx`'s established `NumInput` contract: a local `draft` string the user types into, `onChange` only ever updates that draft, and `bands` (the committed model the preview/totals read) is written ONLY on blur or Enter. No error styling of any kind is shown on this field — an unparseable draft at commit silently reverts to the last committed value, and a below-minimum one is silently clamped up, never blocking or flagging a keystroke. `type="text"` + `inputMode="decimal"` (not native `type="number"`), matching the codebase's established safe-numeric-input idiom.
- **(2) EVERY NAMED ADJACENT CASE, handled and individually named in a test — none paints red or disturbs the preview mid-type.** `parseWidthDraft` (new, pure, `lib/roadCrossSection.js`) is the commit-time-only parser: returns `null` (never an error, never committed) for an empty field, a lone ".", "0" on the way to "0.5", a trailing "12." on the way to "12.5", and a moment of pasted-odd text — and returns the real number for a leading zero like "08" (a legitimate way of having typed "8") and for "12." itself (`Number("12.")` is unambiguously 12, so committing right there takes that plain reading rather than reverting). `MIN_BAND_WIDTH_FT` (0.1, matching the field's pre-existing floor) is applied only at commit via `Math.max(MIN_BAND_WIDTH_FT, n)` — never mid-type.
- **(3) THE PREVIEW HOLDS COMMITTED GEOMETRY, as a byproduct of (1), not a separate mechanism.** `XSectionPreview` reads straight from the `bands` state, which the draft/commit split now only ever updates on a real commit — so mid-edit, the preview and every derived total (Section width, Total ROW width, Pavement area) provably hold the LAST COMMITTED geometry, verified live by typing "2" then "5" and asserting the dialog body text is byte-identical to the pre-edit baseline until blur.
- **(4) THE PREVIEW'S OWN "giant numeral in an empty box" bug, fixed at the actual root — a viewBox/CSS-size mismatch, not narrowness itself.** The old preview derived its SVG `viewBox` height from content (`h = rowW * scale`) while separately clamping the CSS *display* height into `[60, 280]`, so a narrow section's tiny viewBox got stretched by the browser to fill a much taller box — every fixed-unit font size (labels, the total) stretched right along with it. **First fix attempt (an `aspectRatio` CSS trick with `width: 100%`) was tried, MEASURED, and REJECTED**: it reproduced the same class of blow-up, just driven by the dialog's own wide container instead of by `rowW` (glyphs measured 3–4x their authored size). The shipped fix renders the SVG at its own FIXED pixel size — `width={CONTENT_W} height={PREVIEW_H}`, exactly matching its `viewBox`, so 1 authored unit is always exactly 1 real CSS px whenever the dialog has room for it (which it always does, `min(720px, 100%)` wide) — and only ever SHRINKS, never grows, via `maxWidth: 100%` + `height: auto` on a narrower viewport. The per-foot scale is capped at a legibility ceiling and otherwise sized to exactly fill the fixed height, so content height never exceeds the box — a narrow section renders a shorter, vertically-centered band stack instead of an oversized one. Measured live: a 2′ single-band section's own label glyph now renders at 11px (was reading as an "enormous numeral" before the fix); a normal 24′ section's glyph renders at 13px — consistent, not disproportionate.
- **(5) THE ROTATED "TOTAL" LABEL — no longer rotated, no longer clipped or colliding, checked at all three named cases.** The running-total label was `<text transform="rotate(90 …)">`, which needed the box's HEIGHT to hold the whole string's rendered length; at any modest height that clipped it to a fragment ("tot") with its glyphs overlapping the dimension ladder. It is now a plain horizontal label positioned clear of the ladder — the owner's own second acceptable option ("lay it out horizontally"). Verified live, each with the label's own bounding box measured against the SVG's: the single-band default (24′), a genuinely narrow section (2′), and the owner's own 12/12/20-median/12/12 boulevard (68′) all render the label horizontal, fully unclipped, reading the whole word ("68′ total", never "tot").
- **(6) "Pavement area … per 100 ft of road" — judged genuinely ambiguous, not left alone.** The qualifier used to sit BEFORE the number as a parenthetical ("Pavement area (per 100′) 200 SF · 22.2 SY"), easily skimmed past and misreadable as the road's real total area.
