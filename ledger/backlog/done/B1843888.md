`[x]` **ROOT CAUSE, confirmed by reproducing it rather than guessing.** `.github/workflows/build.yml`'s single "Run CI gates" step (`npm run ci-parity`, which executes every gate in `.github/ci-gates.yml` — including `Test (pure-logic smoke tests): npm test` — as one shell step) carries `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` as env for the WHOLE step, because the later `vite build` and bundle-budget gates in that same step need them. `npm test` therefore inherited the real production credentials too, and `src/workspaces/site-planner/lib/supabase.js` (imported by `src/shared/telemetry/clientErrors.js` for every `reportClientEvent`/`reportClientError` call, and by `src/workspaces/library/lib/folders.js`'s `purgeProjectFolders`) read `import.meta.env.VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` unconditionally and built a real, network-reaching client regardless of it running under a test runner. `vitest.config.js` had no `setupFiles` to intervene, so nothing stood between a test exercising `purgeProjectFoldersFor` (`storage.js` ~line 1533/1536, `groupId:"g1"` — a fixture id that exists in neither `project_folders` nor `sites`) and a real POST to `client_errors` plus a real DELETE attempt on `project_folders`, both against `planyr_production`. `[x]` **THE FIX, at the root rather than the two call sites.** Both of the app's two Supabase client constructors (`site-planner/lib/supabase.js`, and `food/lib/supabaseClient.js` — the food workspace's own deliberate duplicate, kept separate for its own BUNDLE ISOLATION rule) now check `import.meta.env.VITEST` — a flag Vitest itself sets, which a test can't spoof away merely by re-stubbing the Supabase URL/key — and refuse to read `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` at all when it's set, forcing `RAW_URL`/`SUPABASE_URL`/`SUPABASE_ANON` to `""` and `supabaseConfigured()` to `false` under vitest regardless of what the process env actually holds. `supabase` therefore stays `null` under every vitest run, which every consumer already treats as "app is unconfigured, run fine anyway" (per this repo's existing design — `clientErrors.js`'s `sink()` returns `{ok:false, reason:"no-cloud"}` with no network call when `!supabase`; `folders.js`'s `purgeProjectFolders` returns `{ok:true, skipped:true}` when `!supabase`) — no new guard logic was needed at either call site, the existing null-safety already does the whole job once the client itself refuses to configure.
`[x]` **This is a complete fix, not a narrower patch at `purgeProjectFoldersFor` alone** — every current and future writer that goes through either Supabase client (there are exactly two `createClient(...)` call sites in `src/`, both now guarded) is covered by construction, not by chasing individual call sites.
