- Verify: sandbox
- **Why the reported number was negative anyway, precisely — not "the owner measured wrong," but a specific, nameable instrument gap.** The report computed a 1D horizontal gap (`toolbar.left − center.right`) without first checking whether the two elements were on the SAME line. Once the row wraps, the toolbar sits far to the LEFT (flush against its own second line's right edge, which is still less than where the centre group's line-one content ends) while the centre group's box has grown wide to absorb the leftover width on line one — so a purely horizontal comparison between an element on line 1 and an element on line 2 produces a large negative number that reads exactly like an overlap, even though the two are vertically separated and never touch. Reproduced this specific mechanism in the harness: a naive 1D gap at 960px (Split/Gantt scope) read a large negative number matching the reported shape in sign and rough magnitude; the correct 2D rectangle-intersection check on the SAME geometry reports no overlap, and a screenshot at that exact width confirms it by eye.
- **The harness and verify script were rewritten to check the RIGHT thing, and to never again produce this false alarm.** `ui-audit/header-schedule-harness.jsx` now renders TWO scopes (`grid` and `split`) covering both real Schedule toolbar widths, since the wrap threshold differs between them. `ui-audit/verify-schedule-header-widths.mjs` now measures the centre group's and the toolbar's TIGHT content bounding boxes (the union of their real children, never the growing flex-zone box) and asks the only question that is actually correct once two things can be on different lines: do these two rectangles intersect as real 2D boxes (`rectsOverlap`, standard AABB intersection) — never a same-line-assuming 1D left/right gap. When they ARE on the same line, the gap is additionally asserted non-negative as a belt-and-suspenders check. Both narrow-clip and wide-off-centre assertions from B1012560 are retained unchanged and re-scoped per view state.
- **Mutation-proven that the new check has real teeth, not just that it passes today.** At runtime (a live DOM style override, no source edit) forced the row's `flexWrap` to `"nowrap"` at 900px — simulating what a genuinely broken build (no escape valve) would render — and confirmed the 2D overlap check correctly flags a **real, detectable overlap** in that state (`overlap=true`), then reverted the mutation before the remaining checks ran. 55/55 checks pass on the real, unmutated build (narrow-clip ×2 scopes ×4 widths, no-overlap ×2 scopes ×6 widths, the one mutation-teeth check, wide-symmetry ×2 scopes ×4 widths); the one deliberately-mutated check goes exactly as red as it should when run against the forced-nowrap state.
- **Re-measured after this session's own change merged to main, not reported off the investigation alone** — see the session reply for the live post-merge confirmation, and the PR for the exact numbers.
- **No degradation order for the centre group (icon-only, overflow menu, etc.) was designed or built.** The suggestion in the follow-up report was a fix for what was believed to be a clickability-breaking overlap; since there is no overlap and no clipping, inventing a new compact UI mode would be unrequested complexity for a problem that does not exist. The header becoming two lines tall in the ~760–1000px range (exact threshold depends on which Schedule view is open) is the SAME already-documented, deliberate fallback this file has described since before this investigation, and is not itself a reported symptom.
