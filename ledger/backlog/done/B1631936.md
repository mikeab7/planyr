### B1631936 — Starting a rename from a site's map-pin menu while the Records (formerly Comps) tab was active silently did nothing `[Site Planner / map]` (bug) #site-planner #ui  *(owner chat block, verbatim repro: "open the Site Planner map view, switch the side panel to the Comps tab, then start a rename on a project from the project switcher menu... nothing appears at all." Minted **B1631936** from this branch's reserved block B1631936–B1631951 against freshly-fetched `origin/main` 90a7cf2c. DEDUPE-FIRST — searched Open/⏳Verify/Done/Done-archive for "renaming.id", "startSiteRename", "openSiteMenu", a rename hidden by the Sites/Comps tab: no prior item describes this editor being hidden by the rail tab; net-new.)*

`[x]` **CONFIRMED, not assumed — AUDIT-FIRST.** The dispatch's own hypothesis was right: the inline rename editor is a plain `<input>` rendered only inside `siteRow(s)`, and the Sites list that calls `siteRow` for every site is itself only rendered when `{sitesPanelOpen && panelTab === "site"}` (`MapFinder.jsx`). The ONLY entry point into a rename is the site's "status/pin/rename/delete" menu (`openSiteMenu`), reachable from BOTH a right-click on a Sites-list ROW (dead while the Comps/Records tab is active — the row isn't in the DOM) and a right-click on the site's own MAP MARKER (unconditionally live, since the marker layer is gated only on the "Sites" imagery checkbox, never on which rail tab is showing — B831778's decoupling). So the reported "nothing appears" repro is: right-click the marker → Rename… → `setRenaming({id,name})` arms an editor with no row anywhere to receive it.

`[x]` **THE FIX.** Every rename now starts through one function, `startSiteRename(s)` (`MapFinder.jsx`), which — in the SAME batched update — switches the rail to the Sites tab, opens the panel if it was collapsed, clears whichever filter (name filter or the "missing location" filter) would hide the target row, expands its status group if a non-pinned row's group is collapsed, and THEN arms the editor. A new `useLayoutEffect` scrolls the row into view the instant it mounts (whichever of the panel's nested scroll regions holds it — the outer panel scroll, a status group's own, or the Pinned section's); the input's existing `autoFocus` puts the caret in on the same mount, so nothing further was needed for focus.

`[x]` **CHECKED, per the dispatch's own table, live in headless Chromium against a real seeded map with two real projects (not a synthetic single-row fixture):**
