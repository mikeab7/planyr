`[x]` **FIXED AND VERIFIED THIS SESSION — root cause confirmed live, not guessed at.** The Site Planner canvas has a non-passive `wheel` listener bound to the canvas WRAPPER (`SitePlanner.jsx`'s wheel-zoom block) that calls `e.preventDefault()` on every wheel event unless it bubbles through a `[data-wheelscroll]` node — the escape hatch every other floating panel (Layers, etc.) already uses. `PrintCompose.jsx`'s full-screen compose screen renders `position:fixed` OVER the canvas but is still a DOM DESCENDANT of that same wrapper, so it never carried the attribute: every wheel notch over the dialog — including over the OPTIONS COLUMN, which has its own `overflowY:auto` and plenty of real content to scroll at a short window height — silently zoomed the hidden canvas underneath instead of scrolling anything. Fixed with one attribute, `data-wheelscroll="1"`, on the compose screen's own root — it opts the WHOLE screen out of the canvas's wheel-zoom handler at once, so the options column's native `overflow:auto` scrolling takes over with no other code path involved.
  - **Per-region findings, as the report asked ("say in the PR which regions own the wheel and why"):** wheel over the **options column** now scrolls it (previously did nothing) — this was the reported bug. Wheel over the **preview image** does nothing visible either way (the preview implements no zoom-on-wheel of its own) — but BEFORE this fix, a wheel notch there silently re-zoomed the hidden canvas behind the dialog (an invisible side effect the owner would only discover after closing the dialog and finding the drawing at a different zoom); this fix closes that too, since the whole screen is now opted out. **Trackpad two-finger scroll** fires the identical native `wheel` event Chromium's mouse path does (only the per-tick delta size differs), so the same one-attribute fix covers it — verified with a run of small deltas, not assumed. **Keyboard PageDown and ArrowDown were never broken** — measured directly (focusing a control near the TOP of the panel, to avoid the browser's own focus-scroll-into-view confounding the reading — DRIVER-SCROLL-IS-NOT-APP-SCROLL) confirms both already scrolled the panel correctly before and after this change; a first, flawed pass at this same measurement (focusing a control already near the BOTTOM of the panel) produced a false "PageDown does nothing" reading, caught and corrected before it was reported as a finding — the confound was the focus jumping the scroll straight to its own maximum before the key was ever pressed. **The dialog is genuinely scrollable at a SHORT window height**, confirmed at 1400×600 (the reported constraint — "his viewport is the constraint, so test short, not tall"): the options column's content (676px) exceeds the visible height (500px) at that size, and Download PDF stays reachable in the footer once scrolled to the bottom.
