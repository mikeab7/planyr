- **WHY THE PUSH ROWS ARE EXACT AND THE PR ROWS ARE UPPER BOUNDS, stated rather than glossed.** For a squash merge GitHub writes the merge commit at the instant it merges, so its **committer** timestamp *is* the push moment. For a `pull_request` event the committer timestamp is when the commit was written locally and precedes the push by however long the session took to get there — so those three figures are at or above the true lag. The worst number in the table is therefore 44 s, and the truth is below it.

- **THE LIVELOCK ARGUMENT IS RESTATED SO IT NO LONGER DEPENDS ON THE PERIOD, which is the stronger claim and the one that survives.** The old §2 argued "the loop's period (~30 min) is far longer than the rate at which the mark advances", which makes the ratchet sound like a race that a big enough head start could win — and that reading is exactly what produced #931's *"chosen ~850 clear of the mark so it survives the lag"*. The period-independent form: the rule passed a branch only if its ids were strictly above the maximum held by any *other* in-flight branch, so for two branches A is green iff `a > b` and B is green iff `b > a` — **both cannot hold at once**. With `n` branches, `n − 1` are red by construction and the only remedy the rule offers turns the green one red. **Set the lag to the 3 s now measured and it still livelocks**; it would just have burned its ninety-eight thousand ids in minutes. There is no lead large enough when the finish line is defined by where the other runners are.
