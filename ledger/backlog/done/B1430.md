- **THE FALSIFIED COMMENT.** `lib/localDb.js`'s header called the store "durable, uncapped" and "a store that can't fill". Both are false, and that framing is what let a ~5 MB tier and a ~10 GB tier be reasoned about as ONE thing for a year. Replaced with the measured numbers (IndexedDB **35.9 MB / 10,275.9 MB quota, 0.3%, persisted: true**; localStorage **3.88 MB / ~5 MB hard cap, ~78%**, 156 keys) and the two facts that follow: the quota is a real, finite, disk-derived number that can be SMALL on a full disk; and **`SitePlannerApp.jsx:25` calls `idbPersist()`, so this origin is PERSISTENT — the browser will NEVER evict it for us.** That is correct for data safety (a user's only copy of a raster is not the browser's to throw away) and it is precisely why a budget is not optional: nothing else is going to clean up after us.
- **THE NAMED RULE — `TIER-BY-REBUILDABILITY`, in `/CLAUDE.md` under Engineering rules**, so it can be invoked by name in a brief like every other rule here. Four binding parts: **(1)** the two tiers differ by three orders of magnitude and are never summed, never reported combined, and never called "uncapped"; **(2)** the small store is for irreplaceable work only — a cache competing with it is a priority inversion; **(3)** a budget is not optional even in the large store, because the origin is persistent; **(4)** no eviction may ever cost data that cannot be rebuilt — every reclaimable class declares a rehydration source, and reference images declare `rebuild: null` (B474's raster hazard). Plus the corollary: **measure, don't reason** — nothing knew its own size before B1429, which is why the first diagnosis of this crisis was wrong by three orders of magnitude.
