`[x]` **FIXED THIS SESSION.**
- Verify: sandbox — a pure layout-computation bug in `lib/notesPageWidth.js` (no auth, no external GIS, no real-project data — ATTEMPT-BEFORE-YOU-PARK), reproduced and fixed with unit tests (`test/notesPageWidth.test.js`, 26/26) and a headless, signed-out Chromium pass driving the real page-width menu at the owner's own window width and a sweep of others (`ui-audit/verify-notes-page-width.mjs`, 41/42 — see the one unrelated pre-existing failure named below).

**ROOT CAUSE, confirmed by reconstructing the owner's own numbers before touching any code.** The three fixed menu presets (Narrow 440 / Normal 580 / Wide 900) always render their literal px, **ignoring the pane's width entirely — that is `resolvePresetPx`'s own existing, deliberately-tested behavior**, not a bug (`resolvePresetPx(900, {paneWidth:500})` already asserted `900` before this fix). "Full width" was the one preset computed the OPPOSITE way: `paneWidth − 48` (`FULL_WIDTH_GUTTER`), with no floor. On a window only a little wider than Wide's own fixed 900 — the owner's exact ~1190px case — `paneWidth − 48` came out **smaller** than 900, so the last row of the menu read as a step down from the one above it. Reconstructed exactly from his report: content-column widths 358/498/818/793 (Narrow/Normal/Wide/Full) back out to raw sheet widths 440/580/900/875 once the sheet's own padding (`SHEET_PAD_X.wide×2` = 80) and 1px border are added back — an exact match confirming Wide rendered its unclamped 900 while Full's pane-relative math landed at 875.

**THE FIX — picked the first of the two options the brief offered:** clamp "Full width" so it can never read narrower than the widest fixed preset, rather than shrinking the fixed presets to fit. `resolvePresetPx("full", …)` now returns `Math.max(paneWidth − FULL_WIDTH_GUTTER×2, FULL_WIDTH_FLOOR)`, where `FULL_WIDTH_FLOOR` is derived from `PAGE_WIDTH_PRESETS` itself (`Math.max` over every fixed preset's own px — never a second literal `900`, so a future wider preset stays the floor automatically). Below that floor, "Full width" now deliberately overflows the pane — `note-mat`'s own `overflow: auto` already scrolls for an oversized pin or table, so this reaches an existing mechanism rather than building a new one. Narrow/Normal/Wide are completely untouched (their own "ignores the pane" test still passes unchanged), and neither the stored `pageWidth` attribute nor `pageWidthLabel`/`pageWidthPresetId` changed at all — a pin still reads its own honest name (Narrow/Normal/Wide/Full/Custom) regardless of how it renders, so the previously-shipped "a page whose content the label correctly named while the sheet had grown past it" behavior is untouched. Also corrected a stale doc-comment on `resolvePinnedBaseWidth` from PR #1662 that claimed every pin "never returns wider than the pane" — that was never true of a numeric pin (confirmed by the pre-existing test asserting the opposite), only of `"full"`.

**TEETH PROOF.** Reverted just the fix, rebuilt, and re-ran the new harness cases against the unfixed code: at the owner's 1190px window, Wide rendered 900 and Full rendered 874 (fails); at a 900px window, Full rendered 584 while Wide held 900 (fails). Restored the fix, rebuilt, re-ran: both pass, and the harness reports the full ladder at three window sizes (below) with everything else in #1662 (edge grips, undo/redo, drag-back, click-with-no-drag, PDF-PARITY) still green.
