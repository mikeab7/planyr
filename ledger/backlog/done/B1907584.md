`[x]` **ROOT CAUSE, confirmed exactly as diagnosed.** `readFromScheduleRows` (the flipped-account load path) necessarily seeds `scheduleBase[id]` from the RAW stored `schedules.data` row — it runs before the App's normalize pipeline exists at all. But the in-app document is never byte-equal to that raw row once `normalizeToV8`/`normalizeIds`/`ensureContacts`/`normalizeOwnerLists`/`recascadeWithDrift` and `stripViewState` have run on it, so `writeScheduleRowsPrimary`'s `_mEq(s.data, base)` no-op short-circuit compared apples to oranges on the FIRST save of every load — every schedule read as "changed" and got rewritten with zero real edits. Multiple live instances of the same account (the Shell keeps the Scheduler iframe alive in every open `planyr.io` tab — `Scheduler.jsx`'s keep-alive `isActive`) each hit this independently, so idle instances raced each other's writes and refused one another over content that was never actually in conflict.
`[x]` **FIX A — the baseline now matches what a save will actually diff against.** New `window.storage.reseedScheduleBaseline(doc)` (`public/sequence/index.html`, storage IIFE) strips view-state and decomposes the doc the SAME way `writeScheduleRowsPrimary` does (`decomposeForDualWrite`), then reseeds `scheduleBase`/`indexBase` from that — called right before every `setData(resolveViewState(d))` in the App's load effect (the returning-load path that actually reproduces this bug, the import/restore path, the first-time seed path, and the offline-fallback catch). `scheduleKnownRev` is deliberately left untouched — revs come from the real rows, not from re-normalizing the document.
`[x]` **FIX B — an identical-content refusal is adopted, not fought over.** `writeOneScheduleRow`: a refused write whose re-read shows the cloud row is byte-identical to what this tab tried to send (or whose 3-way merge resolves to exactly the cloud row's own content) now adopts the cloud rev/data and returns cleanly — no second CAS write, no `stale-block`/`premerge-ours` history snapshot, no console noise. Only a genuine content difference still performs the real merge + second write.
`[x]` **FIX C — a caught-up refusal never raises the banner.** Falls out of Fix B: `writeScheduleRowsPrimary` only sets `anyFailure` (and dispatches `planar:stale`) for a refusal that genuinely could not be reconciled — never for identical content.
`[x]` **FIX D — an empty merge stays silent.** The App's `onMerged` handler now suppresses the "Merged in changes saved elsewhere" toast (and its `event:merge-toast` telemetry row) when the merge changed zero task rows AND the merged `projects` tree is byte-identical to the ancestor's — the exact "0 tasks updated across 0 schedules" shape from the measured logs. A real project-metadata-only change (name/`linkedSiteId`, no task diff) still toasts, since only `countChangedTaskRows` alone is never trusted to mean "nothing changed." `staleNotice` still clears unconditionally on any successful merge, empty or not.
`[x]` **FIX E — a clean, visible tab catches up silently instead of nagging.** The 20s live-refresh poll's `check()`: when `window.storage.checkRemote` reports "newer" and this tab is CLEAN (`saveStatus === "saved"`) and VISIBLE, it now calls a new `window.storage.silentRefresh("hs-v1")` (re-reads the real rows, reseeding every baseline the same way Fix A does) and applies the result via the existing `applyLoadedDataRef` normalize-and-adopt path, clearing the banner with no user-visible nag. A DIRTY tab (unsaved edits) still gets the banner — it has something of its own to protect, so a silent overwrite would be the wrong failure mode. The existing hidden-tab silent RELOAD is unchanged.
`[x]` **Regression tests, extracted from the real shipped source (never a reimplementation) — same "can't drift from what's shipped" pattern as `test/schedulerSaveQueue.test.js`/`test/schedulerViewState.test.js`.** New `test/scheduleRowsBaseline.test.js` (17 tests): the raw-row-vs-normalized-doc baseline mismatch reproduced directly (today's code would write every schedule; after Fix A the same no-op check matches); `writeOneScheduleRow`'s identical-content adoption incl. a MUTATION-DISCRIMINATING case (no baseline yet for a schedule — only Fix B's check-#1 short-circuit can save it, since `mergeCloudDoc` is never even called without a base) and the post-merge-equals-cloud case; a genuine conflict still performs the real second CAS write (no regression); a full two-instance `writeScheduleRowsPrimary` acceptance scenario (editor writes one row, the idle instance's own autosave then writes ZERO rows and raises no stale event — the exact acceptance criterion this item was dispatched to prove); `onMerged`'s empty-merge silencing (incl. a project-metadata-only change still toasting); `check()`'s silent catch-up (incl. a dirty tab still getting the banner, and the hidden-tab reload staying unchanged). **Mutation-proven for every fix**: temporarily disabled each of Fix A/B/C/D/E in turn and confirmed the corresponding test(s) go red, then restored (diffed byte-identical to the shipped file afterward) — a guard nobody has seen fail is not a guard (DRIVER-SCROLL-IS-NOT-APP-SCROLL §6).
