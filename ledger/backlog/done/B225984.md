- **THE MECHANISM, and it is not the one the announcement check guards.** GitHub's auto-merge captures the squash commit **title and body when auto-merge is ARMED**, not when it fires. PR #931 armed auto-merge while its ids were still `B3001–B3004` (the third of six ratchet-era renumbers). Every later renumber updated the branch, the headings, the commit subject and the PR title — and none of them updated GitHub's frozen copy. Proof by elimination: the PR title at merge time was `B221760/B221761 · B221762 · B221763 — V23408/V23409` (set by this session, and the merged **files** match it), yet the merge commit reads `B3001`; the only place that string ever existed was the PR title several hours earlier.
- **THE FIX — one binding step, added to `CLAUDE.md` → *Workflow & deploy* and to `docs/CI-REQUIRED-CHECK.md` §5: after ANY change to a PR title, DISABLE and RE-ENABLE auto-merge.** Re-arming is what makes GitHub re-snapshot the message. Renumbering always changes the title, so this fires on exactly the branches most at risk.
- **⛔ WHY NO MACHINE GUARD WAS BUILT, stated rather than quietly skipped.** The obvious guard — scan `git log` on `main` for ids naming no heading — is **weak by construction here**: `actions/checkout` fetches depth 1, so in CI it would scan one commit, pass trivially and rot into a permanent green. That is the exact failure mode **VIEW-INDEPENDENT-ONCE §6** names ("fails if a registered one was never OBSERVED"). Making it real would mean `fetch-depth: 0` on every build to catch a defect that only a title edit can cause. The honest answer is a procedure step, and this bullet is here so nobody re-litigates it.
- **The scan was still RUN, once, by hand, and its result is the baseline:** across all 59 commits this shallow clone holds, **`fdcb02d` is the only commit on `main` naming an id that has no heading.** Stated with its limit — a deeper clone could hold more, and this session could not see them.
