### B420 — Parcel grabs only by its boundary/setback, not its interior (free the interior for building work) `[Site Planner]` (bug)  *(owner-reported 2026-06-23 as "NEW-1", live; minted **B420** = highest real B# across both files (B419) + 1 — B416–B419 were taken by concurrent PRs #313/#314/#316 while this was in flight; branch/commits/code tags first read B417, renamed on the merge-in of main)*
`[x]` **Filed AND fixed + headless-verified the SAME session per STANDING RULE #1 (branch `claude/vigilant-cerf-6rvxga`). lint 0 · 1320 tests · build green; new regression harness 7/7.**
- **Repro (owner, live):** in Select mode, clicking anywhere inside a lot's interior selected the parcel and popped the parcel menu — even when you were trying to edit a building/element sitting in that lot; a press in the open interior near (but not on) a footprint grabbed the parcel. **Expected:** a parcel is grabbable only by its boundary edge or its setback line; the interior is click-through (presses fall to whatever element is painted on top, else the background pan — exactly as on empty canvas). Appearance unchanged; hit-area change only.
- **Root cause (code-confirmed):** the visible parcel `<polygon>` (`SitePlanner.jsx`, parcels render block) carried `pointerEvents="all"`, so the whole fill was a hit target even when `fill:"none"`; both `startMoveParcel` and `onContextMenu` → `setParcelMenu` fired from any interior point.
- **Fix — boundary-only hit model:** the visible polygon is now `pointerEvents="none"` (its fill never captures, even when a translucent fill is toggled on — boundary-grab stays consistent regardless of fill state; deliberately NOT `"painted"`, which would re-arm the interior whenever a fill is set). A companion transparent **fat hit-stroke** on the same ring (`stroke="rgba(0,0,0,0.001)"`, `strokeWidth={12}`, `pointerEvents="stroke"`) carries `startMoveParcel` + the context menu — reusing the B146 easement-edge fat-stroke technique. ~12 px is **zoom-independent** because `f2p` (`worldToScreen`) already projects feet→screen pixels, so the polygon is drawn in pixel space (the existing easement-edge picker uses the same flat `12`; no division by zoom needed). The **setback outline** gets the same fat hit-stroke for active parcels (owner explicitly wanted "boundary OR setback"); a shared `onParcelContext(e,id)` opens the parcel menu from either grab target.
- **Preserved (re-verified, no regression):** B310 click-vs-drag + B311 "Select parcels" toggle (both keyed on `startMoveParcel`, which now fires from the boundary instead of the fill), Shift-click-to-merge (`toggleMerge`), align-edge picking (`alignToParcelEdge`), unlocked-parcel drag-to-move, and B230 shared vertex editing (it hit-tests at the svg root via `editablePath`/`hitEditPath`, independent of the fill, so vertex handles + insert/delete are untouched). The B311 tooltip was reworded "click a lot" → "click a lot's edge or setback line" (label only, no logic change).
- **Distinct from B155/B156 (the inverse, not a contradiction):** those make small markup-shape *interiors* grabbable (correct for annotations). A parcel is a *container*, so boundary-grab is the right inverse. **Layers on B310/B311**, does not replace them.
- **Verified (V121):** new `ui-audit/verify-b420-parcel-boundary-grab.mjs` **7/7** — interior click does NOT select, boundary click selects, setback-line click selects, right-click parity (interior opens no menu, boundary opens it), no page JS errors. Repointed `verify-b310-b311` / `verify-edge-runs` / `verify-edge-runs-irregular` off the now-dead interior-click / `pointer-events="all"` selectors → all green; `verify-b221-b222` (a pond element on a parcel still selects + its vertices insert/delete 4→5→4→3), `verify-parcel-split-control`, `verify-b383-add-parcel`, `verify-parcel-resilience` all still pass.
- **Deduped:** net-new. NOT B155/B156 (markup interiors — the inverse), NOT B310/B311 (gesture/toggle — preserved), NOT B146 (reuses its technique), NOT B213 (inactive parcels already draw no setback line).
