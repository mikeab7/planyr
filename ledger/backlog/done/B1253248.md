- **ROOT CAUSE, stated once because it explains all six instances below:** `selectTool()` (the tool-rail switcher) never clears `sel`/`selParcel` when you pick a placement tool — by design, so Properties can stay open across a tool pick. Most selection-only chrome in `SitePlanner.jsx` independently re-checks `tool === "select"` before rendering or reacting (parcel handles, element-polygon handles, markup handles, callout handles, measure handles all already did this correctly). Six places did not, and each is exactly the "it will change based on what's behind it" the owner described:
  1. **`handleNodes` (the resize/rotate/road-vertex grip layer for Building/Paving/Parking/Trailer/Detention Pond/Road) had no `tool !== "select"` guard at all** — the one sibling handle-group missing the check every other one has. A building selected before switching to ANY placement tool kept its live corner-resize ("nwse-resize"/"nesw-resize") and rotate ("grab") cursors, and dragging from one actually RESIZED/ROTATED the old building instead of placing anything new. `startResize`/`startRotate` (the two drag-starters) were also missing the `tool !== "select"` early-return every sibling starter (`startEdgeResize`, `startRoadEnd`, `startRoadVtx`, `startCalloutResize`, `startMeasureVertex`, `startMarkupVertex`, `startMarkupResize`, `startMarkupRotate`) already carries — defence in depth, since the render gate alone should already be sufficient.
  2. **`setbackChipNodes` (a selected parcel's per-edge setback chip) had no tool gate at all** — a selected parcel's chip stayed a live "click to edit the setback" hotspot, with a `pointer` cursor, through any placement tool; its sibling `setbackGrabNode` and `parcelEdgeLabels` already had this right.
  3. **The road min-radius warning flag (the "!" corner dot + its "Fix" label pill) is standalone review chrome that renders regardless of tool** (deliberately — it must stay a VISIBLE warning at all times) **but its `onPointerDown` called `e.stopPropagation()` and `setSel(…)` unconditionally** — so a placement click landing on a flagged corner was swallowed into selecting that road instead of placing anything. Fixed by gating `pointerEvents`/cursor on `tool === "select"` (visibility untouched — the dot and pill still always paint).
  4. **The broken/loading overlay-reference placeholder** ("Couldn't load … click to re-add the file") **had no tool gate at all**, same shape as #3 — a placement click over it was swallowed into its re-add/retry action.
  5. **Two purely cosmetic misses** — the callout/text box and the reference-image body both fell back to `cursor: "default"` (a bare arrow) instead of `"crosshair"` outside Select. Functionally harmless (their own drag-starters already checked `tool === "select"` before acting, so nothing was ever grabbed by mistake) but exactly the affordance mismatch reported: hovering either while placing something else showed neither the placement cursor nor a real select affordance, just a stray arrow.
  6. **A mid-draft measurement's grab-band (`canGrab`) didn't exclude the draft itself** — `canGrab = tool === "select" || tool === "measure"` stayed true for the WHOLE time the Measure tool was active, including mid-draft on a brand-new multi-point measurement, so hovering an existing finished measurement mid-draft still promised a `"move"` grab that `startMoveMeasure`'s own guard (`measDraft.length > 0` → let the click through) would never actually honour. Narrowed to `tool === "select" || (tool === "measure" && !measDraft.length)`.

- **Adjacent cases, checked as instructed, not just the one named case:**
  - **Empty canvas vs. over an existing element** — placing over empty canvas was never affected (root SVG cursor already correctly falls back to `crosshair` for every non-select tool); the bug only ever showed up over a LEFTOVER-SELECTED or standalone-chrome object, now fixed above.
  - **Building vs. paving vs. parcel boundary** — all three route through the two fixed mechanisms (`renderElPx`/`handleNodes` for elements, the parcel body/handles for parcels); one fix, verified per-type in the table above (buildings directly, the rest by shared code path).
  - **Snap available vs. not** — untouched on purpose: snap feedback (`insHint`, the small accent dot at a snap point) is a separate, `pointerEvents="none"` visual drawn ON TOP, never a cursor change, so it stays visually distinct from a "select" affordance exactly as asked, and is unaffected by any of these fixes.
  - **Mid-drag vs. hover-before-first-click** — the click-to-place shapes (line/rect/ellipse anchored placement, `mkRect.pending`) read the same tool-driven root cursor throughout; the one genuine mid-gesture case found (mid-draft measurement, case 6 above) is fixed.
  - **Modifier key held** — Alt only affects snap bypass (`altSnapOffRef`), never cursor selection logic; no interaction with any of the six fixes.
  - **Touch** — hover-affordance state (`hoverElId`/`hoverChipId`) was already correctly gated on `tool==="select"` before this item and is read identically regardless of input modality; touch has no separate code path for any of the fixed cursors.
