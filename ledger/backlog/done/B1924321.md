### B1924321 — Saving a Rectangle crop throws away the Polygon crop, so switching shapes isn't reversible across saves `[Site Planner / site-plans]` (bug) #site-planner #ui #comps #persistence  *(Owner live-test on planyr.io, 2026-09-22, PR #1785/merged 52032a0, throwaway overlay `14f7e5e7-f2c7-41f6-a767-87c77510b599`. The row held `crop {kind:'poly', 6 pts}` (version 8). Open the editor, switch to Rectangle, press Done — the row became version 9 with `crop null`. Reopen and switch to Polygon: it shows the default full-frame 4-corner quad, the 6-point polygon gone for good. Minted **B1924321** from this branch's reserved block. DEDUPE-FIRST — searched for "crop coexist", "rect poly switch", "dormant crop": B1783328 itself shipped rect⇄poly switching that is reversible only WITHIN one tool session (its own `ImageCropTool.jsx` header claims independent per-shape drafts "for the life of one tool session" — true, but the live test found the claim false ACROSS a save). Net-new, not a duplicate of B1783328 which is the feature this hardens.)*

`[x]` **AUDIT-FIRST — root cause traced through TWO layers, not one.** `ImageCropTool.jsx`'s own `commit()` wrote only the ACTIVE mode's shape (`onCommit({kind:mode, ...activeFields})`), discarding the other mode's in-session draft entirely — the claimed "independent drafts" protection only ever covered same-session toggling (no Done pressed on the other shape in between), which is exactly the gap `ui-audit/verify-crop-polygon-editing.mjs`'s pre-existing round-trip check never exercised (it never pressed Done on the OTHER shape before switching back).
`[x]` **FIX, layer 1 — the crop object can now carry BOTH shapes' fields.** `overlayCrop.js` gained `savedRectOf(crop)`/`savedPtsOf(crop)` (read whichever shape's fields are present, regardless of `kind`) and `isFullImagePoly(pts, imgW, imgH)` (a closed 4-vertex ring covering the whole image is "no crop", same as a full-page rect — needed for B1924322 below). `ImageCropTool.jsx` now seeds BOTH `draft` (rect) and `polyPts` (poly) directly from whatever was already saved (via refs captured at mount, `initialRectRef`/`initialPtsRef`), rather than deriving the inactive shape's seed from the active one, and `commit()` carries the OTHER shape's last-drawn value forward as an extra field on the committed object — `{kind:'rect', x,y,w,h, pts:[...]}` or `{kind:'poly', pts:[...], x,y,w,h}` — but ONLY when that overlay already had a saved value for it (never invents a dormant shape from nothing, so a rect-only crop never spuriously grows a `pts` field). Neither DB CHECK branch (`site_plan_overlays_crop_poly.sql`) restricts extra keys, so this needed no migration.
`[x]` **FIX, layer 2 — the WRITE PATH'S OWN normalizer was silently stripping the dormant field, and this is the layer the live test's exact steps actually hit.** `overlayCrop.js`'s `normalizeCropShape` (called by `SitePlanner.jsx`'s `setOverlayCrop`, the Site tab's own crop write path, `OverlayCropDialog.jsx`'s parent) rebuilt a "clean" object from only the active kind's own fields — so even with layer 1's fix, a crop object correctly carrying a dormant `pts` field was re-normalized right back down to a bare rect the moment it passed through this function. Found by adding a temporary debug trace to `commit()` and confirming the dormant field WAS present at the point `onCommit` was called, but ABSENT in the persisted row — i.e. lost between the tool and storage, not inside the tool. `normalizeCropShape` now preserves a dormant shape the same way `commit()` does, and — matching a genuine live edge case the fix has to answer, not left implicit — a full-page rect committed alongside a dormant polygon now falls back to the polygon rather than discarding everything, mirroring `commit()`'s own "reset to full page with nothing drawn preserves what's already there" behaviour.
