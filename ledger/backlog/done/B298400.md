- **WHAT THE SCRIPT DOES** (`scripts/build-flood-tiles.mjs`, `npm run build:floodtiles -- harris co_larimer` / `-- --all` / `--dry-run`). Pages NFHL layer 28 by `DFIRM_ID LIKE '<fips>%'`, projects to the four attributes the identify card reads, drops what FEMA paints nothing for, and pipes newline-delimited GeoJSON through **tippecanoe** to `-Z8 -z13`. It emits a sibling `public/flood/manifest.json` recording, per county: the NFHL effective date (newest FIRM panel) AND the oldest panel's, the DFIRM study ids, published/fetched/kept counts, what was dropped and why, the pyramid, the measured bytes, and the tippecanoe version. The manifest is **merged, not overwritten**, so a one-county rebuild cannot silently retire another archive's vintage.
- **⛔ THE DROP RULE RUNS THROUGH THE APP'S OWN CLASSIFIER, so the archive and the app cannot disagree.** `resolveFloodZone` (`floodZone.js`) decides keep/drop, not a substring test in the script. **Unshaded Zone X is dropped** — FEMA's own renderer paints nothing for it, so absence of a polygon means outside the mapped floodplain (Harris: 1,217 of 10,802 polygons, 11%). **Shaded Zone X is KEPT**, including the five subtypes beyond `0.2 PCT` that FEMA paints in the 0.2% class (`1 PCT DEPTH LESS THAN 1 FOOT` and `1 PCT DRAINAGE AREA LESS THAN 1 SQUARE MILE` alone are 54k polygons nationally) — a narrower test would have thrown away exactly the band that drives COH Ch.19, Fort Bend §9 and Waller §A(8). `STATIC_BFE`'s `-9999` sentinel becomes an honest absent value rather than riding into a tile to be printed as an elevation.
- **⛔ NOTHING IS EVER DROPPED FOR SIZE.** `--no-feature-limit --no-tile-size-limit` are deliberate and must stay: tippecanoe's defaults drop features out of dense tiles to stay under 500 KB, which for a regulatory flood map means a floodplain silently disappearing at one zoom in one place — the single worst thing this layer could do. Simplification below the max zoom stays on; that is generalisation of a shape, not removal of a feature, and it is what makes a tile a picture rather than a number. `--detect-shared-borders` keeps adjacent zones simplifying identically so no hairline gaps open between them.
- **⛔ ONE REAL BUG THE SPIKE FOUND, MEASURED RATHER THAN GUESSED: FEMA 500s ON A BIG RESPONSE, NOT ON A BAD REQUEST.** Harris rows 10,000–10,802 are large multi-ring polygons. Asking for all 802 in one page returns `HTTP 500` after ~10 s, **every time**, with a 636-byte error body. The IDENTICAL query at `resultRecordCount=400` returns 200 and **12.6 MB in 9.8 s**; 200 rows → 2.1 MB; 100 rows → 0.64 MB. So the constraint is response SIZE, and a fixed page size cannot work for a county whose polygon complexity varies by two orders of magnitude. **The first version of this script retried the same oversize page four times, which is the one strategy guaranteed to fail.** The fetch now HALVES its window on failure and grows it back on success, always retrying the SAME offset so no row can be skipped. Fort Bend needed it too, at offset 0.
- **⛔ AND ONE PAGING RULE THAT LOOKS LIKE TIDINESS AND IS NOT:** `orderByFields=OBJECTID`. `resultOffset` paging over an unordered result set is undefined — the service may return a row twice and skip another, and the totals still look plausible. The fetch also dedupes by OBJECTID and reports any short count loudly rather than shipping a quietly incomplete archive.
- **⛔ THE COST WORTH FLAGGING, since nobody asked me to weigh it: 11.2 MiB of BINARY now lives in git history, and every NFHL refresh adds another ~11 MiB, permanently.** That is the real price of `public/`-as-delivery, and it is the thing to revisit before this scales past a handful of counties (a build-time fetch, or an out-of-band asset store, would trade it for a build dependency). It is cheap at this size and it does not shrink.
