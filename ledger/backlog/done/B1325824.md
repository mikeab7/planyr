- **WHICH "MAP", established live against production (not assumed from phrasing) — the owner corrected his own brief mid-session after driving it himself:** `#/map` redirects to `#/site`, which is the Site Planner workspace with **no project selected** — `mode === "map"` in `SitePlannerApp.jsx`, rendering `MapFinder.jsx` (the pins-across-the-metro finder: Sites/Comps rail, address search, "+ Select parcels", the Imagery & layers rail). It is a **STATE of the Site route**, not a separate route — exactly the place "New project" and leaving an open project already land on. `firstLanding.js`'s `MAP_ROUTE`/`MAP_HASH` are `{ module: "site-planner", projectId: null }` / `"#/site"`.
- **CURRENT FIRST-RUN BEHAVIOR, established by reading the code (not assumed):** a bare-domain visit with no stored "last route" pointer (`lastRoute.js`) lands on the **Dashboard** (`#/`, B1213312) — a grid of data-backed cards (Pipeline, Jump back in, Going quiet, Comps summary, Schedule health, Pursuits, Needs attention), never the Map. This has been true since the Dashboard shipped; before that, bare "#/" WAS the Site Planner's map (B1213312's own header documents the change). So today's actual gap is exactly what the owner described: a brand-new visitor never sees "the money maker."
- **SCOPE — first-timers only**, per the owner's explicit choice when asked: every returning boot (a resumed route, OR a genuinely project-less returning account's plain Dashboard) is **completely untouched**. Confirmed by test: `test/firstLanding.test.js`'s "returning user's stored resume target is completely unaffected" case shows byte-identical output whether or not the new check exists, and a genuinely-zero-project *returning* account (not a first-timer — see the rule below) still lands on the Dashboard exactly as before.
- **"FIRST-TIMER", the precise rule chosen (candidate (b) from the brief — "no projects at all" — checked at whichever source is DURABLE for this user), and why the other two candidates were rejected:** candidate (a), "no stored last-opened project," is rejected outright — it's the exact local-storage flag a cleared browser wipes, so it would misclassify a returning user on the FIRST bad day their cache clears. Candidate (c), "first sign-in on the account," would need a new server-side flag (a `profiles` column/RPC) for a fact the app can already answer without one. The shipped rule: a route-less boot with nothing worth resuming (`isFreshRoutelessBoot`) redirects to the Map only if **no evidence exists anywhere this account/browser can be asked that it has ever had a project** — the cloud, when signed in (`cloudSync.hasAnyLiveSites`, a head-only existence count RLS-scoped exactly like `cloudList`, which **survives a wipe of local storage** since it asks Supabase directly) plus any not-yet-migrated legacy local work (`pendingLegacyCount`, so a signed-out user who made real local sites and THEN signs in for the first time is not misread as new); the local cache, when signed out (`storage.hasAnyLocalSites`), since that's the only record an anonymous session has at all. **Acknowledged gap, stated rather than papered over:** a signed-OUT visitor has no server identity, so clearing local storage IS genuinely indistinguishable from a first visit for that case only — there is no signal left anywhere that could tell the two apart. The moment they sign in, the durable cloud check takes over. Any failure in the existence check itself (a broken dynamic import, a cloud read error) defaults to `hasAnyProjects = true` — the Dashboard they'd already be looking at, never a wrongly-forced Map.
- **DEEP LINKS ARE SACRED — verified, not assumed:** the redirect predicate (`isFreshRoutelessBoot`) is `INITIAL_HASH_EMPTY && isDashboardRoute(hash)`, and `INITIAL_HASH_EMPTY` (`route.js`) is true **only** for a truly bare `""`/`"#"` — never for a spelled-out `"#/dashboard"`, a project link, or any other explicit hash. Headless case 3 below drives exactly this: `#/dashboard` typed explicitly stays on `#/dashboard` even for a zero-project account. Case 4 drives a deep link to a specific project and confirms it is never touched.
- **ADJACENT CASES, driven or reasoned through explicitly:**
  | Case | Result |
  |---|---|
  | Brand-new account, zero sites, bare domain | **Lands on the Map** (headless case 1, below) |
  | New account invited into a team with existing shared projects | Cloud existence check sees the team's shared rows (RLS-scoped identically to `cloudList`) → **not** a first-timer → Dashboard, unaffected |
  | Returning user, stored resume pointer present | **Untouched** — `isFreshRoutelessBoot` is false the instant `seedBootRoute` finds something worth restoring; headless case 2 resumes a stored cross-project Library view exactly |
  | Returning user whose stored pointer names a deleted project | Untouched — Shell's existing `projectGate`/`DeletedProjectNotice` (B848833) owns this path entirely; a stored pointer is present, so the first-landing check never engages |
  | Sign-out then sign-in | Untouched — signing out doesn't clear `lastRoute`; a stored pointer (if any) still wins on the next boot exactly as before |
  | Deep link to a project / a plan / a specific module | **Never redirected** — headless cases 3 & 4, plus the "any other explicit deep link" sweep in `firstLanding.test.js` |
  | Phone width vs. desktop | Unaffected — this is a routing decision, not a layout change; MapFinder/Dashboard each already handle their own responsive layout |
  | The Map route (`#/site`) reached directly | Unaffected — not the Dashboard hash, so the predicate is false regardless of project count |
- **THE PRODUCT RISK, checked rather than shipped past:** what does the Map render for a zero-site account? A headless screenshot of the real dev build (fresh browser, empty storage) shows exactly what the owner described driving live: header reads "planyr · Map · Select a project", the left rail shows **Sites 0 / Comps 0** with the Site/Comp toggle and "+ Select parcels", an address search, and a working Imagery & layers rail (FEMA flood zones, MHFD drainage, streams) — a genuinely designed empty state (`landingView.js`: zero located sites → the whole continental US, "the honest empty state: the user has no work to show, so show them the country and let them search or click in"), not a blank or broken screen. Compared against the Dashboard's own zero-data state — seven data-backed cards (Pipeline, Jump back in, Going quiet, Comps summary, Schedule health, Pursuits, Needs attention) that would ALL read empty/"no data" for a brand-new account — the Map is the clearly better front door even at zero data: one honest, functional empty state beats seven. **Verdict: ships as-is; this is a net improvement even for the empty case, not just for the owner's own 34-site account.**
