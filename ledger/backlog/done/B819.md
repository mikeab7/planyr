### B819 — False "open in another tab" banner on the Library with only ONE tab open `[App Shell / Library]` (bug) #ui #infra #persistence  *(owner-reported 2026-07-13 from chat — screenshot of the Library showing "⧉ This project is open in another tab. Only one tab can edit at a time; the others are read-only…" with the owner unsure any second tab was even open. Branch `claude/library-popup-issue-4oh86u`. Minted B818 via `npm run next-id`; RENUMBERED → **B819** on merge-in of `origin/main`, which took B816–B818 + V306/V307 for the scheduler cadence work. → V308.)*
`[x]` **FIXED this session — root-caused, fixed at the pure-protocol level, and PROVEN with a standalone repro (bug reproduced true, fix drives it false) + a new regression unit test; full suite green (3755), `eslint` 0 errors, build green, lazy chunks intact.**
- **AUDIT-FIRST root cause — a regression from B669's keep-alive interacting with B313's presence banner.** The Shell keeps every VISITED workspace mounted-but-hidden for instant switching (B669, `Shell.jsx:145`), so a SINGLE tab can have several `AppHeader`s alive at once (e.g. the Library header + a kept-alive Review header on the same project). Each header runs its own `useMultiTab` → `createMultiTabPresence` (B313), and each got a **fresh random `tabId` per instance** (`multiTab.js`). Because `BroadcastChannel` delivers messages between instances in the **same document** (not only across real tabs), those same-tab headers announced the same project id and saw each other as a *different* tab → `summarizePresence` set `conflictRisk:true` → the banner fired with only one real tab open. Compounding it, the banner's "the others are **read-only** until you take over editing there" text describes a lockout the **Library doesn't have** (per-file/per-row ops, no single-active-editor lock), so it was doubly wrong there.
- **The fix (two parts, both minimal):**
  1. *`src/shared/presence/multiTab.js` — ONE presence identity per browsing context.* Added a module-scoped `documentTabId` (lazy `getDocumentTabId()`); `createMultiTabPresence` now uses `opts.tabId || getDocumentTabId()`. A module singleton is per-realm = per-tab: every instance in one tab shares the id (the existing line-71 self-echo guard then makes them ignore each other), while a genuinely separate tab is a fresh realm with its own id — so the real cross-tab warning still fires. Tests pass an explicit `opts.tabId` to simulate distinct tabs inside one realm.
  2. *`src/workspaces/library/Library.jsx` — `multiEditOk` on the Library's `AppHeader`.* The Library supports concurrent multi-tab use (no read-only lockout), so the B313 warning is inapplicable and must not show even across two genuine tabs — same contract the Site Planner uses via `multiwriterEnabled()`.

The banner *logic* is proven in the sandbox (unit test + standalone protocol repro below).
