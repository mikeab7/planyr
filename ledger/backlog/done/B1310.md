- **DELETE IS NOW A MOVE.** `deleteNode` lifts the node into `tree.trash` with `{ kind, node, parentId, index, title, deletedAt, pageIds }`. An **Undo** bar appears at the moment of the delete (not a dialog — house rule), the rail gains a **Bin** view with Restore / Delete forever / Empty, and a 30-day sweep runs lazily on load.
- **TOMBSTONE-DELETES IS INTACT, NOT WEAKENED — this is the part to read before changing anything here.** The FULL cascade of orphaned page ids is still computed by the same walk at the moment of the delete, and is stamped on the entry. What changed is WHEN it executes: `notesStore.purgePages` is the one call site that frees bytes, and it clears the body **and every image** of every id on that entry. Nothing can be resurrected in between, because no read path looks in `trash` (`findPage` / `allPageIds` / `recentPages` / search all skip it), so a future merge or sync sees exactly what it saw before.
- **Two restores that are easy to get wrong, both handled and both tested:** a node whose PARENT is also binned restores the parent first (recursively); a node whose parent is gone for good lands in a named **"Recovered notes"** home rather than being refused. A restore must never fail into nothing — refusing one would make the bin as lossy as the delete it replaced.
- **The bin cannot leak storage.** The load-time orphan sweeps (`sweepOrphans` for bodies, `sweepImagesOfMissingPages` for pictures) are handed the union of LIVE **and** BINNED page ids — a sweep that knew only the live tree would destroy exactly what a restore needs, which is the trap this pairing exists to avoid.
