- Verify: live
- **Root cause (measured, not assumed):** the only drop handlers on the Library were on the FileBrowser *pane* and the folder-rail rows. A drop on any other spot — the app header, the rail gutter, the signed-out / "pick a project" empty states, the Library home — had NO handler, so the browser's own drop action ran (Chrome saves the file). The one window-level `preventDefault` in the app lived inside the Site planner and only while that planner was mounted.
- **Fix:** ONE shared tracker `src/shared/files/fileDrag.js`, armed at boot (`main.jsx`): a bubble-phase window `preventDefault` on `dragover` AND `drop` for any drag whose `dataTransfer.types` includes "Files" (so the browser can never open or download a dropped file ANYWHERE in the app — Map, Site, Review, Notes, Library, Food all covered), plus a Library catch-all: `FileBrowser` takes a drop anywhere on its view through the SAME `dropInto` the Upload button uses; the Library home (no project open) and the empty states refuse out loud ("Couldn't add “x.xlsx” — pick a project first…", `library-drop-notice` / `library-home-drop-notice`); the Site canvas now names a file it cannot take instead of leaving it to the browser. A type the Library cannot accept shows the existing tray rejection row naming the file.
- **Same-day find (the owner's "Library and Map overlays appear together"):** `MapFinder`'s window-level drop handler was gated on `visible` (the map↔plan MODE) and NOT on the active workspace, and the Site workspace stays mounted behind `display:none` — so with the portfolio map as the last Site view, EVERY file dropped on the Library/Review/Notes was routed into the Map's site-plan intake. Now gated on `visible && isActive` (`dropLive`).
- **Guards:** repo-root `test/fileDragGuard.test.js` (29, incl. source guards on every wire and the hidden-view gate); `ui-audit/verify-file-drag-overlays.mjs` (real DragEvents with a File; pre-fix main = 16 red, fixed build = all green; known-good arms; VOID if nothing ever rises).
