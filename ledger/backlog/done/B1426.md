- **The honest answer is more specific than the report, and it matters.** 4,657 ms was the **service METADATA endpoint** (`?f=json`, a 19 KB payload). The screening path never calls it — that number is a cold first connection to TxDOT's ArcGIS Online org, and it does not describe anything a user waits for. Re-measured 2026-08-05: **cold 1,302 ms, warm 40–124 ms**.
- **In the request the app ACTUALLY makes** — the buffered proximity `/query` — aadt is **410 ms** (median of three) against a **113 ms** median for its six peers (lpst 94 · rail 112 · airports 113 · epaCleanups 122 · substations 101 · transmission 219). So it IS the slowest row, by about **3.6x, not 28x**, and the cause is that it is a large statewide point layer on a busy shared org rather than anything we are doing wrong. Reporting 28x would have sent the next session hunting for a bug that is not there.
- **So the fix is volume, not a rewrite.** Every proximity source fired TWO requests per screen: the features (capped at 100) and a separate `returnCountOnly` for the exact total. ArcGIS reports truncation via `exceededTransferLimit` — below the cap and untruncated, **the features ARE the population**, so the second request asks the agency for a number we already hold. Measured on the Goose Creek ring: **seventeen sources, thirty-four requests → seventeen**, and on every one the feature count already equalled the reported total. The wall-clock win is small (the two ran concurrently) and that is not the point: the point is request volume against **metered** agency services — H-GAC's org was returning HTTP 429 "API calls quota exceeded" during this same audit, and halving what we ask for is the only lever we have on that.
- aadt also gets its own **6 s abort cap** so the registry's slowest row cannot spend the shared 9 s budget and stall the panel behind it; it degrades to an honest "unknown" instead. The truncated and at-the-cap cases still fetch the exact count, which is what keeps every reported number identical.
