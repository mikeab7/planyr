`[x]` **AUDIT-FIRST: Escape WAS already wired** — `SitePlanner.jsx`'s big Escape branch (~line 6344) already clears `splitPath`/`mergePick`/`boundaryEdit`/every in-progress draw-tool draft and resets `tool` to `"select"`; nothing there was broken. **The real defect is upstream of it, in the shared key-scope gate that runs before ANY branch fires** (`keyScopeVerdict` in `site-planner/lib/keyContract.js`, fed by `shared/keyboard/keyScope.js`), and it is TWO bugs in the same gate:
- Verify: sandbox
- **BUG 1 — any `<input>` was classified as a genuine text-entry FIELD purely by TAG, `type` never checked.** `TEXT_ENTRY_TAGS.includes("INPUT")` (and the parallel `isTextControl` used by the focus latch) answered FIELD for a **checkbox** exactly like a real text box — and the Parcels panel's per-row "Active" toggle (the owner's screenshot: "inputs and checkboxes" visible) IS a checkbox. `keyScopeVerdict`'s FIELD branch then refused EVERY declared key unconditionally, `escape` included. Fixed the same way this repo already fixed the analogous SLIDER/PICKER cases (B464048/NEW-1 — "a guard may only refuse a key the focused control can really use"): `NON_TEXT_INPUT_TYPES` (checkbox/radio/button/submit/reset/image/file/color/hidden) now falls through to the ordinary CHROME/CANVAS latch, exactly like a focused `<button>` already did — a genuine text-like `<input>` type (text/number/email/search/tel/url/password/date/…) is untouched.
- **BUG 2 — even a genuinely focused text field refusing Escape buys nothing, because Escape types no character.** Per B1125's own words ("the GUARANTEED escape hatch"), FIELD's blanket refusal was never supposed to include it — it just did, because the FIELD branch never checked which key it was refusing. `escape` (and ONLY `escape` — a new declared `guaranteed: true` on its `KEY_CONTRACT` entry, not a blanket `entry.scope === "app"` exemption) now survives FIELD scope; undo/redo/shortcuts stay refused there on purpose, because a text box's own native Ctrl+Z must still win while it is genuinely focused. A PICKER's own Escape-closes-the-dropdown consumption (`CONTROL_CONSUMES`) is untouched too — that case self-resolves and was never "stuck".
- **⛔ MEASURED, NOT ASSUMED — which reproduction order actually triggers it, and it corrects this item's own filing brief.** A trace of the code suggested "touch the checkbox, THEN arm Split, THEN cut, THEN Escape" as the repro and asked for it to be proven RED first; driven for real in headless Chromium, it did **not** reproduce on the pre-fix build — arming Split means clicking the ✂ Split **button**, which is itself focusable and takes `document.activeElement` off the checkbox before Escape is pressed, landing on BUTTON → CHROME scope, which already allowed Escape through. What DOES reproduce (proven RED pre-fix, GREEN post-fix) is the checkbox taking focus **while the cut is already live** — exactly the owner's screenshot, checkboxes and the red cut line on screen together — with Escape pressed right after, so the checkbox is still `document.activeElement` at that instant. The suggested `fieldEdit: true` (persisted-latch) condition was also checked directly and found harmless on its own: that state resolves to CHROME, which already unconditionally allows a `scope:"app"` entry; FIELD, driven only by the CURRENTLY focused node, was the one real gate. Full measurement on the record in the e2e spec's own header comment.
- **Second bug flagged and now moot, not separately patched:** a refused Escape was SILENT (`shouldHintRefusal` never hints a non-mutating key) — exactly the case where silence is wrong, since the user presses Escape *because* they are stuck. Fixing BUG 2 removes the refusal itself for the case that mattered, so there is nothing left to hint; the remaining silent PICKER case is a working dropdown closing, not a stuck user, and hinting it would be a false alarm.
- **Adjacent modes checked, not just the one hit** — the fix is in the ONE shared gate every mode's Escape branch sits behind, so Draw / Measure / Reshape (`boundaryEdit`) / Trace / Cross-section / Easement / Print-frame / Overlay-calibrate all inherit it together; driven live for Split (the reported case) and Merge/Combine (`mergePick`) via `e2e/parcel-escape-during-split.spec.js`, both proven working with a checkbox holding focus.
- **Proven RED before the fix, in both the pure function and the real app**, per house rule: `test/keyContract.test.js`'s two new/changed FIELD-scope assertions fail on the pre-fix source (`expected true to be false` / `expected undefined to be true`); `e2e/parcel-escape-during-split.spec.js`'s discriminating case fails identically against a pre-fix production build served locally, and passes once the fix is restored and rebuilt.
