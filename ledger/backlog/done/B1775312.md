- **MECHANISM, confirmed by instrumenting the real running pre-fix build with console-logged state (not assumed from reading the code alone).** The left width grip's `beginWidthDrag`'s `apply()` (`NoteEditor.jsx`) wrote `scroller.scrollLeft` directly on every `pointermove` — an ABSOLUTE jump to the full compensation needed since the drag started — while, in the same call, setting `sheetGrowLeft` (the sheet's left padding) ALSO retriggers a pre-existing, separately-built layout effect (`NOTES-FREE-PLACEMENT`'s "hold the body's screen position" mechanism, already used for placed-box growth) that measures the real committed layout shift and does its OWN compensating scroll, INCREMENTALLY, off its own last reading. Both writers were individually correct for what each was built to do; running both on every frame doubled the compensation, over-scrolling by that frame's own delta — an error the very next `pointermove`'s absolute write then papered back over, only for the commit right after it to reintroduce a fresh one. That correct → wrong → correct cycle, once per `pointermove` for the whole gesture, is the reported shake.
- **TWO THINGS MASK THIS BUG, and missing either one would have shipped a false-green test over a live defect (caught here, not assumed):**
  1. **A uniform step size cancels the error algebraically.** The doubled amount is a SECOND DIFFERENCE of the padding sequence (this step's delta minus the previous step's) — identically zero when a drag moves the exact same distance every single step. A first draft of the acceptance harness used a constant per-step delta and reported a false, perfectly steady pass on the genuinely broken pre-fix build. Only an UNEVEN step sequence — the shape any real hand's drag actually has — exposes it; the shipped harness drives one.
  2. **A brand-new page's very first left-drag has no scroll room to corrupt yet.** The direct `scroller.scrollLeft = …` write races ahead of React's commit, so at that instant the scroller has not yet grown to accommodate the wider sheet and the browser silently CLAMPS the write back to zero — a total no-op the first time reach room does not already exist, with the (correct, alone) layout effect quietly doing all the real work. The identical drag on a page that already has ANY established width change (a prior preset pick, an earlier completed drag — ordinary continued use) has real reach room already, the clamp does not engage, and the same gesture shakes for real. Measured directly: **11px of real, oscillating drift** driving the exact same uneven-step sequence against the instrumented pre-fix build starting from a Wide (900) pin, versus a perfectly steady 0px starting from a never-touched fresh page. This is why the acceptance harness insists on more than one starting width — the weakest arm alone would have shipped green over a live bug.
- **THE FIX.** `apply()`'s left-edge branch no longer writes `scroller.scrollLeft` at all — it only calls `setSheetGrowLeft(pad)`, letting the one pre-existing layout effect (already correctly designed, already unit-tested for this exact feature) own the entire compensating scroll. That effect's own incremental `+=` accumulation lands on the identical correct absolute target every time with no double-count, and — because it is a `useLayoutEffect` — the padding change and its compensating scroll are now GUARANTEED to land in the same commit, before paint, closing the "different frames" framing in the dispatch's own mechanism lead as well as the double-write framing.
- **ADJACENT CASES CHECKED, per the acceptance bar's own instruction not to fix only the named edge:**

  - **The page-width MENU presets** (Narrow/Normal/Wide) never went through this drag code at all and show zero drift, as expected. **Full width** and **Fit to content** legitimately move the body when picked — reading the measurement effect shows those two use a DIFFERENT, pane-relative gutter formula than the three fixed presets, and switching into or out of "full" re-bases that gutter by design (the effect's own documented "a change in the gutter is a re-base, not a shift to hide" rule) — reported for visibility in the harness output, correctly NOT asserted as a regression.
