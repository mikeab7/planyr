- **The three originally reported, root-caused and fixed:**
  1. **Context menu had no chrome and was mispositioned.** `workspaces/model/components/ContextMenu.jsx` reused the generic `AnchoredMenu` (built for a real ELEMENT anchor) against a synthetic 1px point-anchor div, but never passed `panelStyle` (so the portal rendered with no background/border/shadow — read straight through it to the grid) and used `placement="below-right"` (right-edge-aligned, correct for a button anchor but mathematically wrong for a 1px anchor — it always resolved to a large negative offset, hard-clamped to the viewport margin, so the menu opened pinned to the screen edge regardless of the actual click position). **Fix:** routed through the ALREADY-EXISTING, purpose-built `shared/ui/ContextMenu.jsx` primitive (B915) instead — used everywhere else in the app (map pins, canvas elements, parcels, the Library tree) — which measures the real menu box and flips up/left near a viewport edge rather than merely clamping, and gets proper chrome via `panelStyle={menuPanelStyle}`.
  2. **Right-clicking a column header did nothing after another menu was already open — a regression, not a missing feature.** Root cause was in the SHARED `AnchoredMenu.jsx` primitive (still used by every ribbon dropdown/button menu in the app): its full-viewport click-away backdrop closed only on `onClick`, which per spec fires ONLY for the primary (left) mouse button — a right-click anywhere on that backdrop produced no `click` at all, so the backdrop never closed, and the browser's own `contextmenu` hit-test resolved to the topmost backdrop instead of whatever was actually underneath: a silent, total dead right-click. **Fix:** the backdrop now also closes on `onMouseDown` (fires for every button, and precedes the native `contextmenu` event, so the backdrop clears in time for the real target to receive the click) — a defense-in-depth fix for every OTHER AnchoredMenu consumer app-wide, not just Model.
  3. **Breadcrumb read the literal word "Project" instead of the real name.** `ModelApp.jsx` was the only workspace that never warmed the on-device project-name cache on mount (Notes.jsx/Scheduler.jsx both do) — a fresh tab/deep-link/reload landing straight in Model saw an empty-or-stale cache. `warmProjectsIfEmpty()` (what Notes/Scheduler use) is gated on the WHOLE cache being empty, so it doesn't help the more likely real case — a cache that already holds OTHER projects but has quietly diverged and is simply missing/stale for this one (documented gap, B853266). **Fix:** `reconcileProjects()` (the always-pull sibling, no empty-cache gate) on mount + `onProjectsChanged` subscription so a later cloud pull self-heals the breadcrumb too.
- **Five MORE found while fixing the first three and while building the real pro-forma the brief also asked for — none reported, all real (one confirmed a non-issue):**
  4. **Fixing #2's mechanism (Model's own switch to the shared `ContextMenu.jsx` primitive) surfaced a DIFFERENT, genuine self-dismiss race: right-clicking a row/column at the visible edge of a tall/wide sheet closed the menu it had JUST opened, within ~10-15ms, with no way to tell it apart from "the click did nothing."** Root cause, in `shared/ui/ContextMenu.jsx`: opening this menu often selects the row/header/cell that was right-clicked, and a SEPARATE "keep the active cell fully on screen" layout effect can react to that same selection change by nudging the scroll container a few px — a real, deliberate scroll, not user input. Chrome does not dispatch the resulting native `scroll` event synchronously with the `scrollTop` write; it lands a frame later — after this primitive's dismiss-on-scroll listener had already armed on mount, so it caught its own opening gesture's side effect. **Fix:** the `scroll` listener now arms one animation frame late — a genuine LATER user scroll (wheel, scrollbar) still dismisses correctly; only the opening gesture's own synchronous side effect is exempted.
  5. **Fixing #2 exposed a new bug in the SAME underlying mechanism: a right-click that lands INSIDE an already-selected multi-cell range collapsed the selection to the single clicked cell BEFORE the context menu's own "act on the selection" logic ever saw it** — so "Delete rows"/"Clear contents" from that menu would have silently acted on the wrong range. `SheetView.jsx`'s cell `onMouseDown` ran unconditionally for any mouse button. Fixed: a right mousedown landing inside the current selection now preserves it (matches Excel/Sheets — a right-click OUTSIDE the selection still starts a fresh single-cell one).
  6. **The fill handle didn't work at all when dragged in a straight line — silently filled nothing.** Root cause: the handle is a CHILD of its cell, straddling the cell's own corner by design; the cell's `overflow:hidden` (needed to ellipsis-clip long text against an occupied neighbor) also clipped the handle out of hit-testing at that same boundary, so a press on the handle's own visible right/bottom half landed on the NEXT column's cell instead. Fixed: the cell's own text now has its own dedicated clipping wrapper, freeing the outer cell box to stay `overflow:visible` so the handle (and the column-resize strip) are genuinely hit-testable where they're drawn.
  7. **Freezing both rows AND columns together, then scrolling, silently mislabeled a frozen row's own row number** — data stayed correct and visible, but a frozen row's number in the left gutter got overpainted by whatever row had scrolled underneath (e.g. frozen row 1 showing "37"). Root cause: the row-header gutter cell's z-index was a flat `2` for every row; a frozen row's `position:sticky` + explicit z-index makes it a real stacking context that TRAPS that z-index inside it, while a scrolling row (`position:absolute`, wrapper z-index `"auto"`) has no such context, so its own z-index escapes to compete directly against the frozen row's wrapper z-index — a tie the later-in-DOM scrolling row always won. Fixed: the frozen row wrapper's own z-index raised to `3`, clearing everything a scrolling row's children can reach.
  8. **A "double" bottom border on a total row investigated and found NOT to be a defect** — a 1x-DPR screenshot made a genuine `3px double` CSS border look like a single thick line; confirmed correctly rendering as two visible parallel lines at a realistic 2x device pixel ratio (matching the owner's real display per PERCEPTUAL-PARITY's own stated geometry). No change made; recorded so it isn't re-investigated.
