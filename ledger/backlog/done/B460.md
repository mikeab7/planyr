### B460 — Opening/reloading a plan re-pushed it and bumped `version` with no edit → spurious "changed in another session" conflicts `[Site Planner / Persistence]` (bug, UX)  *(Cowork Phase-B flag #2, 2026-06-25; minted **B460** = highest real B# (B459) + 1)*
`[x]` **DONE + unit-verified (branch `claude/youthful-volta-ns1n75`). lint 0 · 1506 tests (storage.test.js +2 net) · build green.** Data-safe before the fix (B459's CAS + content guard means the re-push can't clobber), but the version churn was firing a benign-but-scary loud "reload to merge" banner in any OTHER open tab/device.
- **Root cause:** `mergePulledSites` `toPush` re-pushed a row when `(local.updatedAt) > cloud.updatedAt` — and B458's immediate per-edit mirror write advances the local `updatedAt` on every edit while the cloud push is debounced/lagging, so EVERY reload re-pushed identical content, bumped `version`, and made other sessions see a (false) conflict.
- **Fix (`storage.js`):** new stable `contentSig(model)` (drawn collections sorted by id + tombstones, as JSON; both sides are `createSiteModel`-normalized so identical content hashes equal). `toPush` now re-pushes ONLY when the row is cloud-absent OR `contentSig(merged) !== contentSig(cloud)` — i.e. the merge actually ADDED/CHANGED/DELETED content. `map[id]` is the union (⊇ cloud) so this never pushes a thinner row; a no-op re-open pushes nothing (no version churn → no spurious conflict). A real add/move/**tombstoned delete** still re-pushes (delete propagation preserved — explicit regression test). Dropped the obsolete `updatedAt >` and `contentCount >` clauses.
