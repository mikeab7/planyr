- **Defect 1 — CONFIRMED, real, and the more serious of the two: `migrateSheet` in `sheetModel.js` echoed a loaded sheet's OWN saved `columns`/`rowCount` straight back with no floor applied.** `rowCount: raw.rowCount || DEFAULT_ROW_COUNT` only floors an ABSENT/zero value — an old sheet's genuinely-saved `rowCount: 200` is truthy, so it passed straight through untouched; the old `columns` array was returned completely unpadded. So the one person Stage 1 was built for — the one with an existing sheet — was structurally guaranteed to never see it, no matter how the deploy behaved. **Fix:** capacity is now derived as `max(whatever was saved, the current floor)` on EVERY load, both axes — never a one-time migration flag, so a FUTURE floor increase (Stage 4's larger pro-forma) heals every existing sheet the same way with no new code. Reuses the existing `ensureColumnCount` (already used by paste/fill) rather than inventing a second "grow to N columns" rule. Existing cell/format data is untouched — padding only ever APPENDS new blank columns after the ones already holding real data; nothing is renumbered, truncated, or moved. 5 new unit tests in `modelSheetModel.test.js` (an 8×200 pre-Stage-1 blob migrates to 26×1000; existing cell data at old ids/rows survives untouched; an already-wide sheet is never truncated back down; padded columns get fresh non-colliding ids; migrating twice is idempotent) — all pass, plus the full existing 61-test suite for the file still passes (66 total).
- **Defect 2 — AUDIT-FIRST CORRECTION, stated plainly rather than silently built over: the brief's claim that "Planyr does not have this feature" (build-version/stale-bundle detection) is FALSE.** Read the actual code before touching anything, per AUDIT-FIRST. `src/app/buildSkew.js` + `UpdateBanner` in `Shell.jsx` is a mature, already-shipped, already-WIRED mechanism (B1373, hardened by B881667) — the build bakes `__BUILD_ID__`, publishes it at `/version.json` (served `no-store`, confirmed live), and a poll (every 15 min) plus focus/visibilitychange listeners compare it against what this tab is running, showing a dismissible "A newer version of Planyr is available — Reload" strip when they differ. **Also independently confirmed the cache-header half of the brief's ask was already correct**, not a new fix: `public/_headers` already sets `index.html` to `Cache-Control: no-cache` (must-revalidate) and `/assets/*` to `public, max-age=31536000, immutable` — exactly the split the brief asked for, shipped under B221/B1373. **Live-verified against the actual production deploy, not assumed:** fetched `https://planyr.io/` and `https://planyr.io/version.json` directly — both serve the current `origin/main` HEAD's build id, and the deploy pipeline itself is not currently exhibiting any propagation lag. The one genuine, addressable gap found: the mechanism's first check fires **20 seconds after boot** — long enough that someone who opens the app specifically to check "did my change ship" and looks within that window (exactly what both reported incidents describe) would never see the banner even on a truly stale tab. Tightened `SKEW_FIRST_CHECK_MS` from 20s to 3s — still comfortably past first paint (one small fetch, not a competing download), but fast enough to answer the actual question someone is asking when they open the tab to look. 18/18 existing `buildSkew.test.js` tests still pass unchanged (none pin the exact delay value).
- **What this does NOT claim:** it does not explain with certainty why either reported incident happened (a genuinely stale/long-lived browser tab predating the deploy is the mechanism buildSkew already targets and should have caught via its poll/focus listeners; a transient CDN edge-propagation window in the seconds right after a deploy is a different, largely unavoidable cause no app code can fully close) — only that the mechanism itself was verified sound, live, and is now faster to speak up.
