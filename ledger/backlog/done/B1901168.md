### B1901168 — Notes toolbar dropdowns opened behind the note page `[Notes]` (bug) #notes #ui  *(Owner chat block, minutes after PR #1850 (B1895536-B1895544) deployed, "NEW-1" — "open any note, click the font chip, the size chip, the ¶ style button... the menu opens but is painted UNDER the grey canvas and the white note page." Minted **B1901168** from this branch's reserved block B1901168–B1901183 against freshly-fetched `origin/main` be1271b. DEDUPE-FIRST — searched Open/⏳Verify/Done/Done-archive for "toolbar clip", "overflow", "popover" + "notes": no prior item covers this regression, which the toolbar rebuild itself introduced hours earlier. Net-new.)*

`[x]` **ROOT CAUSE, confirmed by diffing against the pre-rebuild file rather than assumed.** `NoteToolbar.jsx`'s row (`barStyle`) used to set `overflowX: "auto"` only `...(narrow ? {...} : null)` — phone width only. The rebuild (B1895544/NEW-9, for the compact-fold's own horizontal scroll) made it **unconditional**, on every width. Every one of the row's eight popovers (font, size, paragraph style, spacing, text colour, highlight, the "+" insert menu, table/link/callout) renders `position: absolute` inside a `position: relative` trigger span that lives INSIDE that now-always-clipping row, so each menu was cropped to the row's own thin box the instant it extended past it — reported as painting "under the canvas," which is what a hard CSS crop looks like once the rest of the page paints where the menu used to be. Confirmed live: with the fix reverted, `elementFromPoint` at an open menu's own centre resolves to the canvas/page underneath it, not the menu.
`[x]` **FIX — the same escape the toolbar's own tooltip already proved live.** `usePopoverClampLeft` (one shared hook, called from all eight popovers) is rebuilt as `usePopoverAnchor(open, wrapRef)`: instead of `position: absolute` clamped only on `left`, it computes `position: fixed` coordinates from the trigger's own `getBoundingClientRect()` — laid out against the viewport, not the scrolling row, so no ancestor's `overflow` can crop it and no ancestor's stacking level can bury it. Re-measured live via the same `ResizeObserver` pattern the old hook used (the table-size grid's own width still grows while dragging), plus a `scroll` listener so a still-open menu tracks the row's own horizontal scroll rather than drifting from its trigger.
`[x]` **The module tab row's Export ▾ menu (`Notes.jsx`'s `NotesHeaderTools`) had the identical defect, from a different, pre-existing cause — checked because the brief asked to check every popover, not just the one clicked.** `AppHeader.jsx`'s toolbar-zone `overflow: hidden` (existing, desktop-only, unrelated to this PR) had simply never had a popover to crop before — Notes never supplied `toolbarContent` until B1895537. Fixed with the identical `position: fixed`-from-`getBoundingClientRect()` technique, inlined locally (not imported from `NoteToolbar.jsx`, which is a separate lazy chunk).
`[x]` **The zoom pill's percentage menu (`NoteEditor.jsx`) was checked and is NOT affected** — it renders as a sibling of the clipped canvas viewport, inside the mat's own unclipped `position: relative` wrapper, so nothing crops it. Verified live rather than assumed (see below).
