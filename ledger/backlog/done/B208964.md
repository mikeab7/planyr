`[x]` **✅ DONE — shipped 2026-08-06 (sandbox-verified).** For most of ~30 seconds the rail showed rows literally labelled "Sheet 1" through "Sheet 30" and a header reading "30 SHEETS · 49 PAGES", which later settled to "21 SHEETS · 49 PAGES".
- Verify: sandbox
- Origin: filed 2026-08-06 from chat
- **Cause.** `orderedMeta` fabricates an empty record for every page not yet scanned, `groups` is a grouping OF that, and `sheetLabel` falls through to the string `Sheet ${n}`. So both the headline number and the row names were computed over pages that had not been read — the "30" was never a fact, and it did not "settle", it was replaced by the first real number.
- **THE FIX — the rail states what it knows and nothing else.** Until the read completes it reports the one count it actually has (`49 pages · reading 31/49`), lists pages FLAT, and draws an unnumbered skeleton bar where a name has not been read — never an invented one. Read pages show their real label immediately, and every row (skeleton included) is clickable from the first frame, so navigation never waits on the read. The grouped view, and the sheet count, arrive when the grouping is real.
- **Guards.** e2e **review-sheet-rail-and-zoom** samples the rail continuously from first pixels until the read completes (under 4× CPU throttle, so the reading state is a real window) and asserts the invariant at EVERY sample — no "N sheets" claim while reading, and no row matching `^Sheet \d+$` — then that the real count appears and no skeleton survives. A second spec proves a skeleton row still navigates. Mutation-checked: times out on the old build, which never leaves the reading state honest.
