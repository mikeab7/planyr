`[x]` **ROOT CAUSE, confirmed by reproducing the report headlessly against the real running app before touching any code.** `buildingNumbers(els)` (`lib/siteModel.js`) is stateless and purely derived: it reserves every building's EXPLICIT `buildingNumber` first, then fills every remaining building with the smallest still-free number, in placement order. A plan where nobody has ever touched the Properties panel has NO explicit numbers at all, so every building's displayed number is implicit. The Properties panel's free-number path (`attemptBuildingNumber` in `SitePlanner.jsx`) stamped only the ONE building being edited — correct in isolation — but the moment that stamp existed, the NEXT `buildingNumbers()` recompute re-ran the implicit fill for every OTHER still-unstamped building from scratch. Renumbering building 1 (implicit "1") away to a free number 9 vacates slot 1; the implicit fill then greedily reassigns 1 to building 2 (previously "2") and 2 to building 3 (previously "3") — the exact cascade reported, and it is not specific to the lowest building; any vacated slot below other unstamped buildings reproduces it.
`[x]` **THE FIX — `renumberBuilding` (`lib/siteModel.js`) now freezes every OTHER implicitly-numbered building whose computed display number would otherwise move, at its PRE-edit value, in the same pass as the edit.** It computes `before = buildingNumbers(list)`, resolves the caller's own edit (plain stamp / swap / shift, unchanged from B1768384), then recomputes `after = buildingNumbers(next)` and stamps an explicit `buildingNumber` (equal to its own `before` value) onto any other still-implicit building whose number differs between the two. Proven to need only ONE pass rather than an iterative fixpoint: `before` is already a non-conflicting complete numbering, so re-reserving an unaffected building's own old number can never unseat a different building that already recomputed correctly to its own old value under the same tentative reservation set — reasoned through and confirmed by the swap/shift/gap unit tests below, all of which still pass unchanged. `attemptBuildingNumber`'s free-number path (previously a second, duplicate inline stamp — `setEls(src.map(...))`) now delegates to `renumberBuilding` instead of re-implementing it, so the UI and the pure function can never disagree again.
`[x]` **Unit tests updated/added** (`test/siteModel.test.js`): the existing "a free number is a plain stamp" case now asserts the untouched building's DISPLAYED number is preserved (previously it only asserted the raw element object was untouched, which is exactly what let the display-level bug through undetected); a new case reproduces the reported repro shape directly (three sequential buildings, lowest one moved to a free number, the other two must hold 2/3). All existing swap/shift/gap-widening cases pass unchanged — the freeze is a no-op whenever nothing would otherwise have moved.
`[x]` **E2E regression coverage, real browser, real app, logged out** (`e2e/building-number-panel.spec.js`): a new case draws three buildings and reproduces the exact reported shape end to end through the real Properties panel; the existing case's own assertions (which had encoded the pre-fix cascade as "expected" — building 2 reading "1" after building 1 moved to 5) are corrected to the fixed behavior (building 2 keeps "2"; the downstream swap/shift numbers it exercises are corrected to match) and still pass in full.
