- Verify: sandbox
- **⛔ HE GUESSED THE CAUSE AND WAS RIGHT ABOUT ITS SHAPE** — *"check the drag does not silently drop the selection on pointerdown."* Close: the selection was never dropped, the group drag was never **reached**. `beginGroupDrag` exists and is wired to the MAT's press handler, but the grip calls `preventDefault()` on `pointerdown`, which suppresses the compatibility `mousedown` the mat listens for. So grabbing a box **by its grip** — the one control built for moving it — was the single path the group drag could not see, and marquee-select was pointless for the thing people select for.
- **WHAT LANDED:** the grip reads the live selection **from the DOM** (`[data-selected="1"]`, the same attribute the stylesheet paints the ring with, so the boxes that move are exactly the boxes he can see are selected) and moves the whole set through the existing `moveSelection` rule and `moveNoteAnchors` command — ONE delta for the set, ONE undo frame.
- **MEASURED:** three boxes, all three moved by **90,50 · 90,50 · 90,50** — the same delta, so the arrangement is preserved exactly — and one Ctrl+Z returned all three.
- **⛔ AND AN INSTRUMENT FAILURE WORTH RECORDING, because it produced a confident false finding about working code:** `page.mouse.click` accepts `button`/`clickCount`/`delay` and **silently ignores `modifiers`** (that option belongs to `locator.click`). Every Shift+click replaced the selection instead of adding to it, one box ended up selected, and the harness reported *"the group drag moves only one box"*. An option a driver quietly drops is indistinguishable from a feature that does not work.
