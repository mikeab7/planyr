- **THE CAUSE, named rather than hidden: a prior session's BRIEF, not a bug.** B559376 (this repo, three days earlier) instructed that session to give Complete "its own button and its own distinct key." That put a third control in the footer — redundant, since the Complete pill directly above already reaches the identical outcome one click away through Update Successors (pick Complete on the pill, press Update Successors — same result) — and it broke the footer's visual balance doing it. That was a product decision, and it was never the owner's to begin with; he made it explicitly this session by asking for the revert.
- **WHAT WAS REMOVED, precisely.** The footer button (`data-successor-apply="complete"`, "Mark Complete"), its dedicated Ctrl/Cmd+Enter branch in the modal's `onKeyDown`, and the three values that existed only to support them (`applyComplete()`, `canComplete`, `readyIds`) — all dead once the button and key are gone, so all four are deleted rather than left unreachable. **The Complete CAPABILITY is untouched**: the per-row Complete pill still exists, and Enter / "Update Successors" still applies whatever's picked, exactly as it did for the other three pill values before B559376 and exactly as B559376 itself left that specific path (Enter's own line — `if (e.key==='Enter' && changeCount>0) apply();` — is byte-for-byte unchanged).
- **Ctrl/Cmd+Enter — decided explicitly, not left half-wired: REMOVED, not kept.** The brief allowed either call. Reasoning: the binding's own code comment, verbatim at the time, said it existed "wired to a DIFFERENT control (the 'Mark Complete' button) and a DIFFERENT key" — it was purpose-built as that button's keyboard twin, never an independent feature. With the button gone, keeping it would leave an accelerator with no on-screen affordance, no tooltip explaining it (the tooltip lived on the now-deleted button), and semantics that diverge from every visible control on this modal (it force-completed EVERY Ready-to-Start row regardless of individual pill picks — the pill+Enter path only ever completes what's explicitly picked). A hidden shortcut whose behaviour disagrees with the visible UI is worse than no shortcut. It is now fully gone — a Ctrl+Enter press falls through to the exact same plain-Enter `apply()` line Enter already used (still just applies `pending`, never force-completes), proven live in `ui-audit/verify-successor-complete.mjs` A4.
