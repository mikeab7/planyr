- **ROOT CAUSE, traced through Leaflet's own source (`node_modules/leaflet/dist/leaflet-src.js` + `leaflet.css`), not assumed from the screenshot.** `GridLayer._tileReady` stamps `tile.loaded` on EVERY outcome — success or error — which is what stops Leaflet's own grid update from ever asking for that tile again. It adds the `leaflet-tile-loaded` class — the ONE thing `.leaflet-tile { visibility: hidden }` / `.leaflet-tile-loaded { visibility: inherit }` (leaflet.css) ever un-hides — **only when the load did not error.** `withTileRetry` (`layers.js`) gives an errored tile two quick retries (~1.5 s total, via `tileerror`) and then stops listening entirely. A tile whose retries ALSO fail (a rate limit, a DNS hiccup, a cold host — nothing exotic) is therefore **invisible forever**, and Leaflet itself will never revisit it: `.leaflet-container`'s own flat, hardcoded light-grey background shows through the gap — a borderless, textless, spinner-less square, exactly tile-sized. On a STATIC camera (the dashboard map, not being panned — exactly the owner's described state) nothing ever gives Leaflet a reason to ask for that tile again, so it can sit there indefinitely, matching "still there 45 seconds later" (and would still be there at 45 minutes). Candidate 1 (a released offscreen canvas) was checked and ruled out for this surface: `releaseCanvas.js`'s 16 call sites are all offscreen work canvases (PDF/DXF rasterisation, OCR, export encoding) released after their pixels are consumed, per the module's own documented contract — the dashboard aerial has no offscreen canvas in its paint path at all, it is plain `<img>` tiles.
- **THE FIX, two halves, both required by the item and both shipped.** **(a) A real fix, extending the tile-memory tier (`tileLifecycle.js`'s existing 4 jobs → a 5th, `armBlankTileHeal`/`sweepBlankTiles`; the pure decision in `tileBudget.js`'s new `stuckTiles`/`STUCK_TILE_GRACE_MS`).** A periodic (2.5 s) sweep of a tile layer's retained tiles finds any that are still `current` (part of the view) and still missing `leaflet-tile-loaded` past a 5 s grace period (generous — an ordinary fetch settles in well under a second, so this never interrupts a merely-slow tile) and forces a fresh, cache-busted `src` reassignment, re-entering Leaflet's own `load`/`error` handlers so a successful reload is indistinguishable from an ordinary one. **(b) Generic self-heal, regardless of cause** — the sweep asks only "is this retained tile painting nothing after a generous grace period", never why; it would catch a future bug in this same class exactly as it catches the one found here. It is deliberately scoped honestly, not oversold: it covers the Leaflet `<img>` tile-grid mechanism (the one this report's mechanism actually is), not a different painting technology like an offscreen `<canvas>` release (see the adjacent-cases note below).
- **WIRED ONTO BOTH of the two Leaflet basemap surfaces the app has — the dashboard finder AND the Site Planner's own canvas — because both build their tile layers through the identical `withTileRetry` pattern and are therefore equally exposed.** `MapFinder.jsx`: the imagery layer and the labels overlay (both already capped via `boundTileCache`/NEW-6) each get `armBlankTileHeal`, detached alongside their existing cap on layer teardown. `SitePlanner.jsx`: the coarse backfill layer (`bf`) and the retina detail layer (`t`) each get it too; because that basemap effect tears down INLINE (no `return () => {}` cleanup of its own) rather than via a returned cleanup, the interval-based heal (unlike the existing `on("load"/"moveend")` listeners, which go inert the instant the layer stops receiving events) had to be **explicitly detached on the outer whole-map-teardown path too** (`geoMapRef`'s own effect), not just the inline source-change branch — a `setInterval` left unarmed on origin change or unmount would otherwise poll a dead layer forever. Both are new findings from actually building this, not assumed safe.
- **INSTRUMENTATION.** Every heal fires `reportClientEvent("map-tile-blank-self-heal", ...)` (the existing `event:` channel into `public.client_errors`, `clientErrors.js`) carrying `layerId`, the tile's grid `coords` (x/y/z), its on-screen `rect` (`getBoundingClientRect`, rounded), the live `zoom`, and `blankMs` (how long it sat unpainted before this heal) — every field the item asked for. Shipped even without a naturally-occurring production repro in hand, so a recurrence is diagnosable from data rather than another screenshot.
- **ADJACENT CASES, checked and reported plainly, per the item's own explicit ask.** **Site Planner's own map canvas: YES, same defect, same fix, now shipped identically** (see above — it shares the exact `withTileRetry`/leaflet.css mechanism, so it was equally exposed and is now equally covered). **The Review (Document Review) drawing surface: a DIFFERENT rendering mechanism, checked and NOT covered by this fix.** It rasterises PDF/DXF onto a `<canvas>` via pdf.js (`doc-review/lib/pdf.js`), not a Leaflet tile grid — `.leaflet-tile`'s `visibility:hidden`/`leaflet-tile-loaded` pair and `.leaflet-container`'s grey background do not exist there at all, so the specific mechanism this fix targets cannot occur on that surface. `renderInto`'s own `isStale()` guard deliberately leaves the canvas UNTOUCHED (never blanks it) when a render is superseded — a different, already-safer-by-design shape than the bug reported here. No evidence of an analogous "blank and never recovers" failure was found there, but no equivalent self-heal instrument was built for it either — a full audit of the Review canvas pipeline is a separate, larger undertaking and is honestly out of scope for this specific report rather than silently claimed as covered.
