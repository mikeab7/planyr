- **What was wrong.** The first point of a measurement (and of a Line markup) snaps onto a nearby parcel boundary on purpose, so a setback measurement can begin on the property line. Its tolerance was a pure screen distance with **no world cap**: about two feet at a working zoom, and roughly **70 ft at the overview zoom real layout is done at**. So a click could be pulled tens of feet onto a property line with nothing on screen to say so — from the seat, indistinguishable from *"my point landed five, ten, fifteen feet from where I clicked."* Caught by the B1141 harness, which reported a 4.5 ft east pull as if it were a transform error; it is not, it is this.
- **Fix.** `lib/edgeConstrain.js` now owns the tolerance: `edgeLockTolFt(ppf) = min(EDGE_LOCK_PX / ppf, EDGE_LOCK_MAX_FT)` — screen tolerance, capped in the world, the same idiom the road-connect magnet already uses. Both call sites move to it (the snap itself and the Shift-lock angle recovery, which must agree or the lock would be recovered from a point that wasn't snapped). Holding **Alt** still bypasses the snap entirely. The **Split** tool's separate boundary snap is deliberately left uncapped: a split has to land ON the line, so being pulled there is the intent, not a surprise.
- **Tests.** `test/pointerRegistration.test.js` — a working zoom is the plain screen tolerance; the overview zoom is capped (with the pre-fix reach asserted at >80 ft, so the guard has teeth); a zero/negative/NaN scale can never yield a nonsense tolerance.
- **Sandbox evidence.** `npm test` 6364 green · lint 0 errors · build green · the constants moved into the pure lib so the cap is unit-tested rather than buried in `SitePlanner.jsx`.
