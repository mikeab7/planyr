- **(a) THE FIELD, storage.** `xsection.rowDesignFt` — a new, optional key on the road element's existing `xsection` object (`lib/roadCrossSection.js`). Deliberately NOT named `rowW`/`rowWidth`/anything close: `rowW` already names an unrelated TABLE ROW WIDTH in `AppHeader`/`headerCenterFit.js`, and `rowWidth(xsection)` is the pre-existing DERIVED band-total function this item does not replace — a name near either would read as the same concept and isn't. **PRESENCE IS THE SIGNAL** (`designatedRowFt(xsection)`), never a numeric comparison against the band total: a road with no `rowDesignFt` at all has never had a ROW designated, and every caller (dialog, canvas, Properties) gates on `designatedRowFt(...) != null` — so a designated ROW that happens to exactly equal the modeled bands (a real, valid case: every foot of the legal ROW is accounted for by drawn bands) still reads as genuinely designated, not as "nothing to show." `makeXSection(bands, rowDesignFt)` omits the key entirely (never writes `null`/`0`/`NaN`) when the value isn't a real positive number, and `xsectionFromRoad(el)` carries an already-designated ROW through unchanged when the dialog re-opens on that road — never silently dropped.
- **(b) THE DIALOG FIELD.** A new "Right-of-way width (ft)" row beneath the summary line, defaulting to the current band total (so an untouched field commits nothing) and editable upward. The summary line grows two new spans, shown only once a real ROW is designated: **Designated ROW `<N>`′** and **ROW margin `<(designated−modeled)/2>`′ each side**. `X` in that margin formula is the FULL modeled band total (`rowWidth`, which already includes any explicit outside-curb sidewalk/parkway/ditch band), never curb-to-curb alone — an explicit parkway band is already accounted-for ROW, not margin stacked on top of it, and this is also why the field defaults to the band total (an untouched default then reads as zero margin, not a mystery leftover).
- **⛔ (b), THE REAL BUG THIS SESSION FOUND WHILE BUILDING IT — A DEFAULT THAT LOOKS COMMITTED CAN SILENTLY REFUSE TO COMMIT.** Both the dialog's ROW field (`BandWidthInput`) and the Properties panel's ROW field (`NumInput`) only call `onCommit` when the typed value differs from the current `value` PROP — correct for every other field in this app, because their `value` IS the true persisted model value, so retyping the same digits really is a no-op. The ROW field's `value` is NOT that: it's `designatedRowFt(xsection) ?? Math.round(rowWidth(xsection))` — a computed DEFAULT shown when nothing is designated yet. The realistic case this dispatch itself supplies triggers it exactly: a 68′ boulevard + two 16′ parkways models to precisely 100′, the field pre-fills "100," and typing the same "100" to explicitly designate it hit `next === value` and **silently did nothing** — no error, no commit, the field still reads "100" either way. Caught by the live-verify script itself (the first run reported `Designated ROW: null` after typing exactly the dispatch's own numbers), not by inspection. **Fixed at both call sites** with an opt-in `forceCommit` prop (`BandWidthInput` in `RoadCrossSectionDialog.jsx`; `NumInput` in `SitePlanner.jsx`) plus a `dirtyRef` that tracks a real keystroke, so a genuinely untouched blur still costs nothing, but a field the user actually typed into commits even when the digits match the shown default. Every other caller of both components (dozens, across this codebase) is untouched — `forceCommit` defaults `false` and is passed only at these two ROW call sites.
- **(c)/(d) CANVAS — the "should be shown" half.** The ROW draws as two thin dashed boundary lines, one each side, offset from the road's own TRIMMED dense centerline (`roadDenseCenterline`, the exact geometry the pavement ribbon and the within-curb bands are already built from) by `±rowDesignFt/2` via the same `offsetPolyline` used everywhere else in this feature — so it curves, arcs and trims identically to the ribbon, never a separate straight-line approximation. An inline "`N`′ R.O.W." label rides the midpoint, styled like the existing width-dimension callout (same font/scale/halo idiom — `stroke="#fff"` white halo, matching that pre-existing label's own hardcoded halo exactly, the one deliberate raw-hex exception in this diff) in a neutral tone rather than the dimension's red, so the two are never mistaken for one control. Gated on `rowMarginFt(xsection) != null` (never drawn when nothing is designated, and never drawn when the modeled bands EXCEED the designated ROW — see (g)) and on the new View ▾ toggle (below).
- **(e) LAYERS/VIEW TOGGLE.** `settings.showRowLines` (new, default `true`, read via `!== false` so a project saved before this key existed still shows the lines) joins the `showGrid`/`showDims` family in the View ▾ menu's "Detail" section (`ViewMenu.jsx`) — same checkbox shape, same section, same persistence mechanism.
