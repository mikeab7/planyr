- **THE ONE RESOLVER, confirmed by source read, not assumed.** `resolveDoubleClickTarget`/`gestureAnchorTarget` (`lib/featureTarget.js`) are consulted ONLY from `onBgDouble` (the native `dblclick` fallback) and the two read-only diagnostic hooks — never from any single-click or plain-right-click path; a full-file audit of every call site confirms this (pinned in `test/featureTarget.test.js`'s new "picker is wired into the canvas's own capture-phase press handler" suite). `featureContextAction` is the right-click twin, and before this item it had exactly ONE legitimate forward (a selected annotation deliberately sent behind the plan, reachable from wherever it now paints — `onElContext`'s narrow, already-shipped exception). This item adds its second and third uses, both to the SAME function, never a new one: the handle-layer's unhandled-right-click fallback, and the Alt-picker's right-click twin.

- **FIX 1 — the acreage badge selects its parcel on left-click.** `startAcChip` now calls `setSel({ kind: "parcel", id })` (+ `setCombineSel([])`) before arming the drag, mirroring every other drag-starter on this canvas (`startMoveEl`/`startMoveParcel`). Right-click was already correct (B1539888/PR #1654, 2026-09-11).

- **FIX 2 — every element's own label is a direct-dispatch click target, not just the pond's.** The pond label was already pointer-enabled with its own click/right-click/double-click handling (B875); every OTHER label relied on `pointer-events:none` fallthrough, which is correct only as long as the label happens to sit inside its own shape — `labelFitLadder`'s `outside-with-leader` rung can push ANY element's label off its own footprint onto a neighbour's (the reported case: a building's name/SF label). Generalised `isPondLabel` → `labelInteractive` (`tool === "select" && !!d.el && !d.added`) so every label now carries `data-feature`, `pointerEvents: auto`, and forwards click/right-click/double-click to its OWN `d.el.id` via a closure — correct by construction regardless of where it's drawn, closing the whole class rather than patching the one reported instance (CHROME-NEVER-EATS-A-PRESS clause 5's stated preference).

- **FIX 3 — the handle layer forwards an unhandled right-click to whatever is selected, closing the class B806082 fixed one grip at a time.** None of the resize/rotate/vertex grips, the setback chip, or the parcel edge-length label carried their own `onContextMenu` (only `onPointerDown`, for dragging) — and because the whole handle layer renders as a top-level sibling rather than nested inside any one feature's own `<g>`, an unhandled right-click there doesn't bubble to that feature's menu the way it would from inside the feature's own body. It bubbled all the way to the canvas root's plain `onContextMenu`, opening the empty-canvas menu (Zoom to fit / Paste / Export…) — CHROME-NEVER-EATS-A-PRESS's right-click shape. One line on `<g data-handle-layer="1">`: `onContextMenu={(e) => { if (sel) featureContextAction(sel, e); }}` — every grip renders only while something is selected, so `sel` is always the right answer when nothing more specific already stopped the event. Callout tip/elbow/width grips already had their own precise per-leader `onContextMenu` (B806082) and are unaffected — their own handler still wins the race.

- **⛔ THE ALT AMENDMENT — established what exists FIRST, then extended it in the SAME function, never a second path.** A canvas-wide "reach behind" mechanism already existed and was NOT built from scratch: **B548822 (Alt+CLICK, left button only)** — `handleStackPick`, wired into the root's `onPointerDownCapture` — already resolved to the top of the hit stack exactly like a plain press, and a repeated Alt+click at the same point stepped one deeper, wrapping at the bottom (`lib/featureTarget.js`'s `stackAtPoint`/`nextPickIndex`). A SEPARATE Alt+HOVER reveal-list (`B845585`) also exists and is untouched. **What did not exist: Alt+RIGHT-CLICK.** Fixed by extracting the shared gating+cycling logic out of `handleStackPick` into one new function, `resolveAltPick(e)`, and adding its right-click twin, `handleStackPickContext(e)`, wired into the root's `onContextMenuCapture` (ahead of the vertex-edit capture handler, mirroring how Alt already wins ahead of it on the pointerdown side) — dispatching through `featureContextAction`, the SAME per-family menu-opener `onElContext`'s one legitimate forward already uses. **ONE shared cycle position (`stackPickRef`) for both buttons**, so a left-click pick and a right-click pick at the same point can never disagree, and alternating buttons mid-cycle continues the SAME sequence rather than resetting it (proven live — see the harness below).
  - **Modifier-collision check, as asked, before binding anything:** Alt is already read in three other places on this canvas — the drag/placement snap-bypass (`altSnapOffRef`, read only once a drag has already armed, so it cannot collide with a fresh press being resolved before any drag exists) — no collision; Alt+Z for callout autosize (different key entirely) — no collision; and the setback chip's own `onEdit(fp, e.altKey, key)` (Alt+click picks the nearest SEGMENT of a grouped run instead of the whole run) — **a real, but PRE-EXISTING and narrow collision, found by this audit, not introduced by this item:** `handleStackPick`'s capture-phase Alt-check runs before the chip's own bubble handler and would claim the press whenever the chip happens to sit over a real feature underneath (a building, paving, etc. — common wherever the setback ring runs close to a building), leaving the chip's own segment-override unreachable there. **This is reasoned from source, not confirmed live this session** (fixture geometry for a setback-chip-over-a-building repro didn't come together in the time available) — flagged here rather than silently left, per the owner's explicit instruction, and NOT fixed as part of this item (STANDING RULE #3 — a different, pre-existing bug, unrelated to what this item was dispatched to fix; B548822's left-click Alt-picker predates this session unchanged). Smallest proposed resolution, if picked up later: have `resolveAltPick` bail out (return `null`) when the actual DOM node under the point is inside a control that already declares its own Alt handling (e.g. a new `data-alt-owned` marker on the setback chip's own `<g>`), rather than reaching for a different modifier or overriding the chip's existing meaning.
  - **Discoverability — the ordinary way this app already teaches a modifier (a tool-button tooltip), not a new mechanism.** The Select tool's own `hint` string already documented "hold Alt to bypass [snap]" but was never actually wired as a tooltip on the Select button itself (its sibling Marquee button already does this) — fixed the same oversight and added the reach-behind sentence to the same hint: *"something buried behind another object?
