### B1991041 — Renaming a brand-new (never-drawn) project failed: "The rename didn't match any project in your account" `[Site / project switcher]` (bug) #site-planner #persistence  *(Owner block 2026-09-30. Repro measured live: "+ New project" then Rename → rpc/rename_site_group 200 but matched no row, toast, name reverted; no sites row existed for smunhw2pxvka. Minted **B1991041 / V1416129** from the same block. DEDUPE-FIRST — searched Open/Verify/Done for "rename didn't match", "new project rename": the rename RPC family (B1048400/B1266592) fixed the cloud-side write, never the lazy-creation gap; net-new.)*

`[x]` **ROOT CAUSE.** Project creation is deliberately lazy (owner constraint 5), so a new project has no local plan and no `sites` row until its first real write; `storage.renameSiteGroup` iterated zero local plans and sent the RPC, which updates by group and matched nothing.
`[x]` **FIX — a rename IS a real write, so it materialises the project.** `renameSiteGroup` now creates the row first when the group has no local plan — signed-out: a minimal local record carrying the new name; signed-in: the existing idempotent, deleted-refusing `ensureProjectRow` (which leaves a project the cloud already has, but this device hasn't pulled, untouched) — then renames as before. Guarded against re-entry. Both entry points (switcher row menu; the in-plan header path through `renameProjectFromHeader`) go through it, the shared names store shows the new name everywhere at once, and it survives a reload. **Empty-project decision:** a project nobody names or draws in still vanishes (lazy creation stays); one that was RENAMED is now a saved project and no longer disappears — the rename is the user's statement that it matters. The `renameProjectChecked` pending-name map is cleared once the persisted store owns the name.
`[x]` **Red-proof + acceptance.** Two new cases in `e2e/names-matrix.spec.js` ("NEW-2 — renaming a brand-new project"): switcher row menu, and the in-plan header path, each on a never-drawn project created through "+ New project" — both FAIL on current main (name stays unstored, `null`) and PASS with the fix; the row-menu case also reloads.
- Owner product constraints check: **constraint 5 (lazy project creation) is preserved** — nothing is created by "New project" itself; only a rename (a real write) materialises the row.
- Verify: live — **V1416129** (`Blocker: auth`: the signed-in cloud path, `ensureProjectRow` → push → RPC).

`[x]` **2026-10-08 LIVE SIGNED-IN CHECK FOUND A REAL DEFECT IN THE FIRST FIX — fixed here.** Driving V1416129 on planyr.io as the test account (build `e29a76f`, which contains #1892) the new-project rename PASSED in some runs and FAILED in others (breadcrumb showed the new name, but the cloud row never landed and a reload said "That link points at a project this account doesn't have open here"). Cause, found with a network trace on a slow day (each Supabase call 4–9 s from the sandbox; row landed 1.5 s → 27 s after the rename): `renameSiteGroup` went through `ensureProjectRow`, which makes a **network round trip (the deleted-project check) BEFORE it saves anything locally**, so for the seconds that took, the new name existed only on screen and a reload or closed tab lost the project and the name **silently** — worst on a slow connection (a phone). **Fix:** local-first — the local record is written synchronously in the same tick as the typed name, then pushed (`pushSiteToCloud`), then the group rename runs; a failed push keeps the local record and returns a failure (loud, never a silent success). **Red-proof:** `test/renameNewProjectLocalFirst.test.js` (cloud mocked to hang) fails on the deployed version at "the project must exist on this device the instant the name is typed" and passes on the fix. Known limit, same as every `ensureProjectRow`-materialised project: a project created this way carries no default share-team stamp (private is the safe direction); if a default team should apply, that is a separate item.
`[x]` **A SECOND FINDING, about the harness not the product:** a harness that HARD-deletes its throwaway rows invites resurrection — three hard-deleted projects came back minutes later because another signed-in browser on the shared test account still held them in its local cache with no trash marker to honour. The app only ever trashes (the database also refuses to hard-delete a live row). `ui-audit/verify-rename-signed-in.mjs` therefore **trashes and stops**.

**Closed 2026-10-08 — disposition for an owner-reported symptom: REPRODUCED AND FIXED.** Live signed-in pass V1416129 (builds `dfce41b`, `701e78a`): new-project rename, reload, and a reload ~1 s after the rename all keep the project; cloud row still arrives. Harness: `ui-audit/verify-rename-signed-in.mjs` (trash-only cleanup).
