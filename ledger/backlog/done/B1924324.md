### B1924324 — Uploading a site plan with "No project" leaves it with no card anywhere, and orphans a tracked record `[Site Planner / site-plans]` (bug) #site-planner #ui #comps #persistence  *(Owner live-test on planyr.io, 2026-09-22, PR #1785/merged 52032a0. Map, Records rail, "+ Site plan", choose a file, leave Project on "No project", "Place on map": the overlay draws on the map and a tracked "Market record" site is minted (id shaped like `trkmuc2pobsk8124t`, site = the doc title), but the rail goes back to the comps list and the plan has no card anywhere — no way to Adjust/crop/lock/delete it except by separately logging a comp on the same parcel (which happens to match the tracked record via location). Also, after the plan and comp are deleted, the tracked record stays live, orphaned. Minted **B1924324** from this branch's reserved block. DEDUPE-FIRST — no prior item covers this; net-new.)*

`[x]` **AUDIT-FIRST — root cause traced to a visibility gate with only one input.** `SitePlansSection.jsx`'s whole card (`showEmbeddedCard = !!focusedProjectId && !flow`) renders NOTHING unless `focusedProjectId` is truthy, and that prop was wired ONLY from a currently-open comp (`focusedComp?.projectId`) in `MapFinder.jsx`. A fresh "No project" upload mints its tracked site ASYNCHRONOUSLY (`reload()`'s own fire-and-forget resolve sweep, `resolveOverlaySite` → `resolveOrCreateTrackedSiteForOverlay`), and nothing that resolution ever reaches `MapFinder` to focus — so with no comp open, the card the resting-state design already has (it isn't a missing feature, it's an unreachable one) never shows.
`[x]` **FIX, Part A — resolve the tracked site SYNCHRONOUSLY and hand the id up, instead of relying on the fire-and-forget sweep.** `SitePlansSection.jsx`'s `confirmPage()` now, for a genuinely fresh upload with no project chosen, calls the SAME `resolveOverlaySite`/`patchAndReload` the sweep already uses, but inline and awaited — marking `resolveAttemptedRef` first so the sweep never double-resolves it — then reports the resolved id to a new `onOverlayProjectResolved` prop. `MapFinder.jsx` holds it in a new `focusedTrackedProjectId` piece of state and composes it into the existing prop as `focusedComp?.projectId ?? focusedTrackedProjectId ?? null` — a comp's own projectId still wins whenever one is open, unchanged. The result: right after "Place on map," the Records rail shows THIS plan's own card, Adjust reachable, with no comp involved.
`[x]` **A real side effect this exposed, and fixed rather than left as a known flash.** `SitePlansSection.jsx` already resets `adjustOpen` to `false` on every `focusedProjectId` change (B1310208 — closing a PREVIOUS plan's panel when switching to a different one). Since Part A's fix changes `focusedProjectId` in the same batch `confirmPage` opens the panel in, that effect fired right after and closed it again — a visible open-then-instantly-close flash. Fixed with `justOpenedOverlayIdRef`, naming the one overlay that effect must not act against on the very next `focusedProjectId` change it itself caused. Mutation-proven: reverting the guard reproduces the flash and the new harness's "already open" check goes red.
`[x]` **FIX, Part B — an auto-created tracked site is retired once its last plan AND last comp are both gone, matching the comps-side precedent exactly, including WHEN it fires.** New `countLiveOverlaysForProject` (`sitePlanOverlayStore.js`, mirrors `countLiveCompsForProject`). `SitePlansSection.jsx`'s `purgeForever()` (permanent delete) now checks both counts and, when zero, calls the existing `binOrphanedTrackedSite` — same as `CompsPanel.jsx`'s own `purgeForever` tidy-up. **Deliberately NOT wired into ordinary soft-delete (`remove()`)**, for the identical reason the comps-side precedent already documents: a soft-deleted overlay is restorable for 30 days, and `countLiveOverlaysForProject` already excludes it from the live count, so retiring the tracked site at soft-delete time would strand a later restore with no site left to reattach to.
`[x]` **Part C — the specific orphaned record from the live test.** Checked via the Supabase MCP: `trkmuc2pobsk8124t` (`role:"tracked"`, site "ZZ-CLAUDE-TEST-polycrop") already carries `deleted_at` (2026-09-24, three days before this session started, ahead of any Part B mechanism existing) — already retired by an earlier process, nothing left to do.
