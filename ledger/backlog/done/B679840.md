`✅` **Done — root-caused, fixed, and proven with a real debounced-autosave + localStorage round trip in headless Chromium this session. Verify: sandbox.**
- Verify: sandbox — this is a logged-out, no-GIS persistence check (ATTEMPT-BEFORE-YOU-PARK: draw → undo → reload is fully driveable here, including the debounced-autosave timing itself), so it was driven rather than parked. No live-GIS/auth/real-data dependency. No `V#` was minted.
- **Root cause.** The debounced autosave effect in `SitePlanner.jsx` has always skipped saving a still-blank, never-touched "Start blank" plan — the guard exists so opening a fresh blank plan and immediately leaving doesn't clutter storage with an empty record. The guard read `if (isBlankSite({ parcels, els, measures, callouts, markups, underlay, sheetOverlays }) && !deletedIds.length) return;` with no scoping: it fired on ANY blank state, including a plan that already has a saved, non-empty record on disk and is reverting to blank because the owner deliberately drew something and then hit Ctrl+Z. The canvas correctly showed the object gone; the autosave effect silently no-opped instead of writing the now-blank state over the stale saved record, so the old record — with the "undone" object still in it — sat untouched on disk and came back on the next reload.
- **The fix.** `fresh` (`!loadSite(siteId)` — true only when this plan has no existing saved record yet) already existed further down the same effect for an unrelated purpose (telling `App` to list a brand-new site); it's now computed earlier and the blank-skip guard is scoped to it: `if (fresh && isBlankSite(...) && !deletedIds.length) return;`. A plan with no prior save is still skipped while blank (the original intent, untouched); a plan that already has a saved record is never skipped, so an undo-to-blank writes through and the stale record can't survive.
- **Live-driven proof (headless Chromium, real debounced autosave + real `localStorage`, not a source read).** Seeded a plan, drew a callout on it (nothing else on the plan — the exact minimal repro), let it autosave, undid the callout (canvas confirmed empty), reloaded, and confirmed the callout does NOT come back and the saved record reads blank. Control case run alongside: a genuinely untouched "Start blank" plan (never drawn on) still produces no storage record after the same wait — confirming the fix is a no-op for the case the guard was originally written to protect, not a removal of it.
- **How this was found.** Surfaced by the NEW-4 interaction sweep (see the sweep's own summary item below), not by a direct owner report — undo history is memory-only and correctly does not survive a reload, so most of the sweep's undo checks ran (deliberately) BEFORE reload; this one repro needed the object to be the plan's ONLY content so the blank-skip guard's misfire had something to hide behind. Two false leads chased and refuted along the way, kept here so they're not re-chased: (1) undo appearing to do nothing at all across a reload is NOT a bug — undo history (`histRef`) is session-scoped by design and reloading a page is expected to clear it, same as any editor; (2) a synthetic-instrumentation pass (temporary `window.__DBG_HIST`-gated logging in `pushHistory`/`undo`, added and then fully reverted — diffed clean against a pre-instrumentation backup) confirmed undo itself was firing correctly and popping the right frame; the defect was entirely downstream, in autosave's write-skip decision.
