- **What shipped.** `siteModel.js`'s `buildingNumbers(els)` (B122) now honors an optional, persisted `el.buildingNumber` override: it's a RESERVATION (reserved first, in placement order, over every explicit number), and every building WITHOUT one still fills in around it from the smallest number not already reserved — so an untouched plan renders byte-identical to before this shipped. Two new pure helpers: `buildingNumberHolder(els, n, excludeId)` (who currently holds `n`) and `renumberBuilding(els, id, n, mode)` (`mode: "swap"` trades two buildings' numbers; `mode: "shift"` gives `id` the number and bumps every building numbered `n` or above by one — both computed as ONE pass over the current numbers and applied via a single `setEls`, so no two buildings are ever — even momentarily — shown holding the same number).
- The Properties panel's SELECTED · BUILDING section (`SitePlanner.jsx`, the `isBuilding(selEl)` branch) gains a "Building number" field directly above FOOTPRINT, backed by a new dedicated `BuildingNumberField` control (not the shared `NumInput` — a taken number must reach the caller for Swap/Shift/Cancel rather than silently commit or silently revert). A free number commits on Enter/blur with no confirmation; a taken number blocks the plain commit and shows an inline "That number belongs to Building N" banner with **Swap with Building N** / **Shift N and up by one** / **Cancel**. The on-canvas label stays display-only, exactly as scoped — no click-to-edit there, no drag-to-reorder Buildings list, no canvas renumber mode (the two mocked directions explicitly NOT built, per the brief's own scope cut).
- Guard: integers only (non-digit keystrokes filtered at the input itself), no 0, no negative; gaps left by a Shift (or by typing a number well past the current count) are never auto-compacted.
- **Two real bugs found and fixed by the live browser check, not by unit tests — the reason this shipped with an e2e spec rather than unit coverage alone.** (1) The canvas's own `onMouseDown` deliberately `preventDefault()`s outside a text field (so a canvas drag never starts a text selection), which also suppresses the browser's normal focus-shift-on-click-elsewhere — so double-clicking a DIFFERENT building right after an Enter-commit (which leaves the field focused on purpose, matching every other inline editor in this panel) never fired a blur, and the field kept showing the PREVIOUS building's number. Fixed by binding the field to the selected building's `id` and resetting its edit-latch the instant that `id` changes, rather than relying on a blur this app's own canvas can silently withhold. (2) Escape's revert called `.blur()`, and since a React state update is not synchronous, the resulting `onBlur` fired before the revert had applied and re-committed the STALE (about-to-be-reverted) draft into the model. Fixed by not blurring on Escape — matching the shared `NumInput`'s own Escape convention, which also lets Escape correctly bubble up to close the whole inspector (B1125's "guaranteed escape hatch"), exactly like every other field in this panel.
- **VERIFIED, headless, logged out (`e2e/building-number-panel.spec.js`, new):** draws two buildings, opens Properties, and drives — a free number committing with no confirmation; a taken number's conflict banner naming the right holder; Swap trading exactly two numbers; Shift bumping exactly the buildings at/above the target; Cancel reverting the field and leaving the model untouched; the 0/negative guard; the non-digit-keystroke filter; and Escape's interaction with the inspector's own escape hatch — asserting after every step that no two buildings ever carry the same `buildingNumber`.
