`[x]` **SHIPPED.** Root cause confirmed exactly as the report's own hypothesis: `CompEntryGrid.jsx`'s `onGridKeyDown` handles a single printable keydown on a selected-but-not-editing cell by calling `beginEdit(selection.row, selection.col, e.key, false)`, which seeds React state with `e.key` and — via the `editing` `useLayoutEffect` — focuses the freshly-mounted `<input>` SYNCHRONOUSLY, before this handler returns. Every OTHER branch in the same function (Tab, Enter, arrows, Delete/Backspace, F2, Ctrl+Z/D) calls `e.preventDefault()` first; this one didn't. With the keydown's default action left unprevented, the browser's own native character-insertion then fires against whatever element now has focus — the just-mounted, just-focused input already holding the seeded character — landing the identical keystroke a second time. Fix: one line, `e.preventDefault();` added ahead of the `beginEdit(...)` call, matching every sibling branch — chosen over "seed with '' and let the native keystroke land naturally" because it doesn't depend on browser-specific focus/caret timing (this exact file's history is a long list of regressions from relying on native focus/blur race timing) and needs no change to `beginEdit`'s existing seeding contract.
- **Every affected cell class checked, not just Size** — the fix is in the ONE shared keydown handler, not per-column code (`SheetCell`'s generic `<input>` branch is identical for every `kind` except `"select"`, which never receives the typed seed at all, and the `compDate` branch, which is the same input wiring plus a "Tdy" button). Live-verified: Size (number), Title (text), Executed (date — the report's own literal repro case), and Notes (flexKey text column) all now take exactly one character per keystroke; the click-to-edit control path (mount-first, then type) is provably untouched by this change since it never reaches `onGridKeyDown`'s type-to-edit branch (`editing` is already truthy).
- **Both entry paths verified** — click-then-Escape (selected, not editing) AND arrow-navigation-from-a-neighbour both reproduced the bug pre-fix and are both clean post-fix. **Caret position verified** — typing two keystrokes in sequence ("4" then "5") lands "45", not "445" or "54"; `selectionStart` reads at the end of the input after the seeded character, confirmed by direct read, not inferred.
