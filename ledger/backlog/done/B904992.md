- **⛔ FOUND AND FIXED A REAL HAZARD NOT IN THE ORIGINAL SPEC, MEASURED DIRECTLY: a git merge driver runs BEFORE git checks out anything the merge changes.** git's recursive/ort strategy computes the whole merged tree in memory (including invoking custom drivers) and only writes the result to the working tree — and even writes `MERGE_HEAD` itself — as its LAST step. An instrumented driver invocation proved this: `src/` on disk held only whichever branch was already checked out, "theirs"' newly-added file was completely absent, and `.git/MERGE_HEAD` did not exist yet — for a merge that went on to auto-complete with zero conflicts. A naive driver that just re-ran `build-map.mjs` in place therefore produced a MAP.md silently missing whichever files the OTHER side added, with NO conflict shown — exactly the "silently wrong" class LOUD-FAILURE exists to catch, and it would have hit the dominant real-world case (two PRs each adding an unrelated file) every time.
- **THE FIX IS TWO LAYERS, not one:** (1) `scripts/merge-driver-ledgers.mjs` — the actual driver, mid-merge, necessarily a partial view: seeds the union of both sides' hand-authored descriptions (reusing `resolve-ledgers.mjs`'s own `seedGenerated`/`GENERATED`/`lostDescriptions`, now parameterised by `repo` rather than re-derived) and re-runs the real generator against whatever the working tree currently holds — good enough to avoid a shown conflict and to get the B384432 description-preservation case right (that check is unaffected by file-set incompleteness, since it only compares descriptions for paths present in the result). (2) `scripts/post-merge-regen.mjs`, run from a NEW `.githooks/post-merge` hook — fires only once git has resolved every path with zero conflicts anywhere and the commit is already made, which is exactly the point (also confirmed empirically) where the working tree is complete; it re-runs the same unmodified generators there and re-stages the result if it differs from what the driver produced. `post-merge`, not `pre-merge-commit`: also measured directly that `git commit --amend` from inside `pre-merge-commit` (or from `post-merge` itself) fails with "You are in the middle of a merge" — git has not cleared its own merge bookkeeping at that point — so the backstop can only STAGE the correction (`git add`), not fold it into the merge commit; that staged fix shows immediately as `git status` returns and is one more commit (or an amend, now safe once `git merge` has actually returned) away. A merge with a genuine, separate conflict elsewhere never reaches either layer automatically — the pre-existing, documented Definition-of-Done workflow (regenerate by hand before committing) already covers that case.
- **INSTALLATION:** both the driver's local git config (`merge.planyr-ledger.driver`/`.name`) and the `post-merge` hook are wired by `scripts/install-hooks.mjs` (`installMergeDriver`/`mergeDriverPlan`, and `post-merge` simply joined `REQUIRED_HOOKS` alongside the existing `pre-push` mint-gate hook) — same self-install-from-`npm install`-`prepare`, idempotent, never-clobbers-a-foreign-value, never-fails-`npm install`, always-loud-when-not-armed guarantees as the mint gate already had. `--check` fails (exit 1) if either is missing, naming which.
