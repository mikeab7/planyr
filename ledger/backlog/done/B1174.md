- **THE REPORT.** Draw an area measurement, double-click its label chip: nothing. Double-clicking the geometry works.
- **AUDIT-FIRST — the diagnosis is CONFIRMED exactly as written.** `startMeasChip` was the only handler on the label chip and it never called `isDoubleTap` — it selected and armed a drag, nothing else. It did not even write `lastTapRef`, so the gesture was completely unarmed on that element. There is no id mismatch: `isDoubleTap` had 8 call sites and the chip was not one of them.
- **WHY IT IS A REGRESSION, and the mechanism worth keeping in mind.** #866 REPLACED the old label. The old one was a `pointerEvents="none"` `<text>` at the polygon centroid, and an area's grab layer is a transparent FILLED polygon covering the whole interior — so a double-click on the old label fell THROUGH to the fill and reached `startMoveMeasure`. #866 put a pointer-enabled chip on that same spot, painted AFTER the hit path so it wins the hit test (deliberately, so its own drag would not be swallowed — that ordering has its own assertion), with a handler that had no double-tap branch. Same click, now a dead end.
- **BOTH CASES FIXED, as instructed.** Line/polyline measurements were a PRE-EXISTING gap rather than a regression — their old label sat outside the stroke's hit band and very likely never worked — and one `chipNode` serves every mode, so the single branch covers all of them. Both are driven in the browser.
- **THE FIX, placed as diagnosed.** The double-tap branch sits after `if (!m) return;` and BEFORE the lock guard, because `startMoveMeasure` opens Properties for a locked measurement too and the two surfaces must agree. It keys on the bare `m.id`, so a press on the chip pairs with a press on the shape and vice versa. Returning early also skips the `pushHistory()` the chip press would otherwise push as a no-op undo frame.
- **THE GUARD — this is the point of the item, and it was widened rather than trusted.** `test/measureWiring.test.js` already asserted double-click-opens-Properties and stayed green through this regression, because it source-scraped `startMoveMeasure` ONLY. **B1151 recorded that guard as protection against exactly this class and it did not protect.** It now DISCOVERS the surfaces from the render — every `onPointerDown` bound inside the measurement block — instead of naming one, so a new surface shipped without the gesture goes red on arrival. The generalisation is structural, never a name list: a handler that selects a SUB-PART (it writes `setSelVtx({…})`) is a vertex grip, which is a handle on an already-selected object rather than a way to reach the object, and no vertex handler anywhere in the planner reconstructs the double-tap — that invariant is itself asserted, so the exclusion cannot quietly rot into an excuse.
- **THE WIDENED GUARD IMMEDIATELY FOUND A THIRD SURFACE** the report did not mention — `startMeasureVertex` — and classified it correctly rather than either failing spuriously or ignoring it. That is the behaviour the widening was for.
