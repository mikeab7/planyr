### B2174224 — Dragging a docked left panel wider shrank the whole drawing once the map pane got narrow `[Site Planner / canvas]` (bug) #site-planner #ui  *(owner chat block 2026-10-06, NEW-1: "as I resize the left menu, it literally shrinks everything else on the site." Goose Creek / Phase II - 1.2M, Land → Parcels docked, Windows Chrome. Minted from this branch's reserved block. DEDUPE-FIRST: not B837/B821 (those are a panel switch flashing/jumping the basemap — the left-edge pan compensation, which held throughout this one); no prior item on a pane-width-driven scale.)*
`[x]` **✅ live (V1587744 PASSED 2026-10-06, planyr.io build 1b6bf18, which contains merge 62ba9f5 / #2119).** Disposition (STANDING RULE #2): **reproduced and fixed.**
- **Root cause (measured, not inferred).** The canvas SVG is `width/height 100%` with `viewBox="0 0 size.w size.h"` and the default `preserveAspectRatio` (`xMidYMid meet`). `size` was FLOORED at 320 × 360 in six places (`Math.max(320, r.width)`), so once the map pane fell under 320 CSS px wide the viewBox outgrew the element and the browser scaled the ENTIRE drawing down, proportionally to the pane: screen scale **0.79 at 252 px, 0.475 at 152, 0.16 at 52**, with `view.ppf` — and therefore the scale-bar label — unchanged, exactly the owner's "same 0/250/500 ft bar, everything smaller". The same floor permanently shrank the drawing on any window whose canvas is under 360 tall (0.83 at 1280×380). The Leaflet aerial did NOT scale with it (it is a sibling, not inside the SVG), so the drawing also slid off its registration with the imagery.
- **Why the previous chat could not reproduce it (WRONG-CASE).** It ran at 1191 px wide, where the 620-px panel maximum leaves a 343-px pane — just above the floor. The variable was the window's CSS width (a laptop, OS display scaling or browser zoom all shrink it), not the panel or its dock state. Chrome (panel text, rail, header) never scaled on any build; "everything" was the map.
- **Fix.** New pure `lib/canvasBox.js`: the canvas box IS the measured rect (floor only at 1 px, to keep it positive); every `setSize` goes through `nextCanvasSize`. The floor only ever existed to dress up a never-laid-out container, and every framing site already refuses a degenerate raw rect itself (B1234400 / B1574432), so nothing relied on it. `fit()` and the zoom-to-selection framing now use `framePad`, which shrinks the fixed margin on a very narrow pane rather than asking for a negative drawable width.
- **Sweep run (`ui-audit/verify-panel-resize-scale.mjs`, real grip drag 240 → 420 → 620 → 240):** windows 1920×1080 (known-good arm), 1191×521, 1100×700, 1000×650, 900×600, 1280×380; every other left-rail panel (Analysis, Drainage, Yield, Properties, References, Standards) at the widest panel on the two narrowest windows. Each reading asserts screen scale 1, viewBox = element box, ppf unchanged, the largest drawn building's size and position unchanged, a basemap tile's size and position unchanged, and panel-header / Tools-rail heading / rail-tab heights unchanged. **Fixed build: 36 readings, 0 failing. Pre-fix build (`--expect-red`): red at 1100, 1000, 900 and 1280×380, green at 1920 and 1191** (which is the non-reproduction, explained). Unit: `test/canvasBox.test.js` (pure box + red-proof replay + source guard against a floor coming back).
- **Adjacent surfaces checked:** floating panels portal out of layout and never narrow the canvas; the right Tools rail is fixed-width; Doc Review's sheet rail already compensates against the measured edge (B838); the Notes page scaling to its pane is that module's intended paper behaviour. A source scan found no other interactive surface that floors a measured box into its viewBox.
