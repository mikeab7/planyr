### B315 — Undo (Ctrl+Z) unreliable after moving a building `[Site Planner]` (bug)  *(arrived as coworker-chat "NEW-1" 2026-06-21; renumbered B310→B313→**B315** as a very hot `main` twice consumed the number — B310/B311 parcel click-vs-drag + B312 auto-filing, then B313/B314 multi-tab + optimistic-concurrency)*
`[x]` **Fixed + headless-verified 2026-06-21 (branch `claude/ecstatic-ritchie-ihzkym`).** Moving a building then pressing Ctrl+Z now reverts the **entire** move in one step, every time (was: sometimes nothing, sometimes a partial revert).
- **Root cause (confirmed by reading, NOT guessed — the brief's hypothesis #2, the race):** the drag-move transaction boundary was already correct — `startMove`/`startMoveParcel`/`startGroupMove` push history **once** at drag-start, nothing during the drag, nothing on pointer-up (so hypothesis #1, per-frame pushes, did **not** apply). The defect was that `stateRef` — the single source both for the snapshot pushed onto the undo stack AND for the baseline `undo()` compares against (the B32 no-op dedup `histKey(stateRef.current)` check) — was updated in a **passive `useEffect` (no deps)**. A ref written in a passive effect lags the committed render by a paint, so a quick undo↔drag sequence could snapshot/compare a **stale** state → revert to the wrong frame (partial) or skip the frame in the dedup loop (does nothing). Timing-dependent ⇒ intermittent, matching the fuzzy repro.
- **Fix:** (1) `stateRef.current` is now assigned **during render** instead of in a passive effect, so `pushHistory`/`undo`/`redo` always read the TRUE current state — the race window is gone. (2) Extracted the stack + dedup into a **pure, unit-tested** module `lib/history.js` (`createHistoryStack({ keyOf })` → push/undo/redo/drop/canUndo/canRedo), matching the `stitchGeom.js` precedent; `undo`/`redo` take the live state **explicitly**, so the stale-ref class of bug can't recur. (3) **Interrupted-drag edge case** (brief's list): Esc / lost-focus / pointer-cancel **mid-move** now reverts to the pre-drag snapshot stashed on `drag.current` and drops the dangling frame (`cancelActiveMove` in `abortGesture`), so a cancelled drag leaves no half-recorded command.
- **Edge cases covered + verified:** one drag = one undo (full revert); redo restores; two moves = two undos (one each); multi-select/group move = one push = one undo (geometry-agnostic stack); independent transactions don't clobber each other (a move-undo doesn't touch an unrelated vertex edit); Esc-mid-drag cancels cleanly.
- **Verified:** lint 0 · **full suite green** (11 new in `test/history.test.js`, incl. a deterministic repro of the stale-baseline failure mode) · build green. Headless on the built app (`ui-audit/verify-b315.mjs`, chromium-1194, logged-out): drag a building 300px → **one Ctrl+Z snaps it fully back, Δ=0.0px** (not partial); redo; two-moves-two-undos; Esc-mid-drag revert; **0 JS errors**.
> **Dedup:** net-new. **Related but distinct from B32 (done)** — B32 stopped no-op edits from polluting the stack (the *dedup* the `while`-loop does); B315 is the *stale-baseline race* that made even a clean move-frame revert wrong/skipped. NOT a duplicate of any open item; no open item covered undo-after-move. Kept as ONE item (the brief said split only if the diagnosis turned out to be redo- or multi-select-specific — it wasn't; the race affects all undo, redo + multi-select already work as separate transactions).
