- **THE MECHANISM, MEASURED RATHER THAN GUESSED.** `trashEntries` sorts **newest first** on `deletedAt`, a millisecond stamp, and the `binnedThree` fixture bins three pages in a tight loop — so which entry is `[0]` is decided by how fast the machine is. Forcing the clock forward one millisecond between the three deletions, with nothing else changed, moves the answer: **all three in one millisecond → `sort` is stable → `[0]` is `"a"`; three distinct stamps → `[0]` is `"c"`.** The assertion `expect(liveIds(stale)).toEqual(["a"])` was therefore only ever true on a fast run. CI drew the slow case and reported `[ 'c' ]`.
- **⛔ IT IS PRE-EXISTING ON `main`, and that is worth stating plainly** — the identical line is at `test/notesBinPurge.test.js:183` on `origin/main`, and the branch it blocked touches no Notes code. It was found because it happened to fail under an unrelated PR, which is exactly how a latent flake surfaces.
- **THE FIX — name the entry you mean.** `entryForPage(tree, pageId)` looks the bin entry up BY the page it holds. The test's subject was never *which* entry (it is "a stale client restored one of them, and the merge refuses it"), so indexing a time-sorted list was expressing something it did not mean. Rule recorded at the helper: **index into a clock-sorted list only when the ORDER is the thing under test.**
- **THE GUARD FORCES THE CASE RATHER THAN HOPING FOR IT.** A new test spins the clock to give the three deletions distinct stamps, asserts that precondition really holds, then asserts BOTH halves in one place: the old `[0]` really does pick `"c"` under it, and the named lookup still means `"a"`. A run on a fast machine covers the same-millisecond tie for free, so between them both tie-break outcomes are exercised on every run.
