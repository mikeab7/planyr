- **STEEL-MAN, done before committing to the mechanism, as asked.** Drag-and-drop is genuinely hard to get right across a long, partially-collapsed, virtualized list, and it does NOT actually solve the owner's stated scenario as well as it first appears to: this codebase's entire selection model (`selRange`) is a single contiguous rectangle — there is no ctrl-click or other discontiguous multi-select anywhere in it (documented already, above `indentSelection`) — so a set of SCATTERED tasks (his literal situation: 12 permitting/entitlement rows created at different times, sitting at different points in the list) can never be grabbed in one gesture, by drag OR by any bulk selection mechanism, regardless of what UI sits on top. A **"Move to…" command** — pick the destination by NAME from a searchable list, invoked once per scattered task — closes his actual scenario end-to-end: it needs no aiming, no scrolling to keep both ends of the move on screen at once, and it works identically whether the destination is expanded, collapsed, or off screen. **Verdict: ship BOTH, Move-to first.** Drag is still worth having — the day-to-day case ("nudge this task up two slots," "put this one inside that group I can see") is common and drag is the natural tool for it, and the owner explicitly named it — but Move-to is what actually gathers 12 scattered tasks into a folder, which is what he asked for.
- **THE SHARED PRIMITIVE.** New pure `moveSelectionToDestination(tasks, selectedIds, destParentId, insertAfterId)` (`public/sequence/index.html`, byte-identical mirror in `ui-audit/stress/schedule-tree-ops.mjs`, drift-guarded the same way B645360 hardened indent/outdent's mirror) generalizes `indentSelection`'s block rule — "reparent only the block's ROOT rows (a selected row whose parent is also selected is left untouched)" — from "the row above, at the topmost row's own level" to an ARBITRARY destination parent + sibling position. Reparenting only the roots is what carries the rest of the block along for free: non-root selected rows AND any hidden/collapsed descendants outside the selection never have their `parentId` touched, and `sortByVisualOrder` rebuilds the whole tree purely from `parentId` — so a moved PARENT always takes its whole subtree, with **zero special-case code for "does it have children."** Refuses (returns `null`) a drop into the moved block's own descendant (cycle guard, walks the ORIGINAL tree) and a genuine no-op (dropped back exactly where it started, same parents + same relative order for every row — not just the moved ones).
- **(A) Drag-and-drop.** A small grip (`⠿`, Tabler `ti-grip-vertical`) in the ID column, real `page.mouse`-driven in every test (never a synthetic `dispatchEvent` — SYNTHETIC-KEYS-DONT-EDIT's sibling caution about untrusted events not propagating the way a real gesture does). Drop zones, read from where the cursor sits inside the hovered row: top third = insert BEFORE it (same parent), bottom third = insert AFTER it (same parent), middle third = reparent as its LAST CHILD — the ONLY way to target a COLLAPSED row's children at all, since you cannot see inside it to aim between them. Dropping into a collapsed group **auto-expands it** (built into the primitive itself, so drag and Move-to both get it for free) — the moved block is immediately visible right where it landed, which is how the owner can tell it worked without needing to see inside the group first. Honors the WHOLE active row-selection when the grabbed row is part of one, not just the grabbed row — resolved via the SAME `structuralTargets` App-level closure indent/outdent/delete already share, not a parallel notion of "what moved."
  - **Zero `setData` calls during the drag.** Every mousemove-driven repaint (the insertion line, the drop-target highlight, auto-scroll near the viewport edges) is an IMPERATIVE DOM write through refs on an internal `requestAnimationFrame` loop — never `setState`, never touches React at all — so the row list is re-rendered **zero times** for the whole gesture, however long it lasts or however far it scrolls. Measured live against a ~540-row fixture (matching the owner's real 529-task plan) with a `MutationObserver` watching the rows container through a sustained auto-scroll: **zero** `childList` mutations (no row DOM node added/removed/reordered) until the single drop-triggered commit. `moveRows` (the one call that reaches `setData`) fires from exactly one place — the mouse-up handler — never from the per-frame paint path; a source-pin test asserts this structurally (every `moveRows(` call site in `startRowDrag` lives inside `onUp`, none in the paint/tick/move functions) and a live mutation (wiring a commit into the per-frame loop, simulating a B1121-shaped regression) is proven to break the single-undo-step guarantee below.
  - **A real bug was found and fixed building this**, not shipped with it: the grip's first implementation covered the WHOLE id cell (`inset:0`), invisible until `:hover` — but `:hover` is true for the entire duration of a mousedown (the cursor always enters an element before it can press it), so gating interactivity on hover did not protect ordinary clicks at all: it silently ate every mousedown in the ID column, breaking the pre-existing row-range-select drag. Caught by a diagnostic script reproducing the exact CHROME-NEVER-EATS-A-PRESS shape (chrome painted over a feature's own body swallowing the press meant for that body). Fixed by narrowing the grip to an 8px strip at the cell's left edge, permanently interactive, opacity-only on hover — it no longer overlaps where a click aiming at the row number lands, and the pre-existing selection drag was reproven working (range badge + blue highlight both fire again) before re-testing the move feature itself.
- **(B) "Move to…" command.** New `MoveToModal`, reachable from the row context menu ("Move to…", between Outdent and the clipboard group) — a searchable, keyboard-navigable list of every task in the project (by name, indented by depth, walked WITHOUT the `isExpanded` gate so a collapsed destination is still searchable and pickable) plus a "— Top level —" pseudo-entry, with the moved block's own descendants excluded from the candidate list (same cycle guard as the primitive). Commits through `moveSelectionByIds` with the ids FROZEN at the moment the menu item was clicked, not a live re-resolved selection — so the picker can't silently retarget if anything about the selection changed while it was open. Appends as the LAST child of the chosen destination and auto-expands it, identical semantics to a drag "into" drop.
- **(C) MEASURED, then fixed: Ctrl+C/X/V and the row context menu's Cut/Copy/Paste.** Stated precisely, per surface, before changing anything — **single cell**: operated on the WHOLE anchor row's subtree (not the cell), since there is no per-cell clipboard in this app. **A cell range** (multiple columns, one row): identical — the column span was never consulted. **A full-row selection** (one row, ID column): identical, correctly a no-op distinction since the range was exactly one row anyway. **A genuine multi-row selection**: this is where it broke — Ctrl+C/X and the menu's Cut/Copy operated on `selectedId` ALONE (the drag/shift-click ANCHOR), completely ignoring every other row in the range, with **no error and no indication anything was dropped**. A 6-row selection copied exactly one row's subtree. Paste then inserted only that one subtree. This is precisely the shape STANDING RULE calls "a half-working paste is worse than none" — it LOOKED like it operated on the selection. **Fixed the same way as indent/outdent/delete**: `copyTaskById`/`cutTaskById` now take an array and resolve `rootsOfSelection` (a selected parent + its own selected child collapse to ONE subtree, not two — same "root = parent not itself selected" rule the move primitive and `indentSelection` both use); `pasteTaskAfter` reparents EVERY pasted root to the paste target's parent (was: one hardcoded `sourceRootId`), keyed off a new `sourceRootIds` array on the clipboard (an old-shaped clipboard with a lone `sourceRootId` still works via a fallback, so nothing already in a user's clipboard at reload breaks). All four entry points (Ctrl+C, Ctrl+X, the menu's Cut, the menu's Copy) now resolve `structuralTargets(anchor)` first, identically to indent/outdent.
