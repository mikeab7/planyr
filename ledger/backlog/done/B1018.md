- **Three distinct holes, all closed.** (1) **Tombstones were client-local and never server-side** — `planarfit:sites:deltomb:v1:<uid>` lives in one browser's localStorage and is never replicated, so every other client was structurally entitled to resurrect. (2) **The deleting client disarmed itself at the worst moment** — `mergePulledSites` did `if (!cloudIds.has(id)) { tombClear.push(id); continue; }`, discarding its only evidence of the delete the instant the cloud confirmed removal, i.e. right before client B's re-push arrived; that is why the resurrection was permanent rather than a one-time flicker. (3) **`saveSite` ignored the durable tombstone** — it gated only on the per-tab in-memory `recentlyDeleted` Set and never consulted `readSiteTombs()`, so a second tab in the SAME browser (or the same tab after a reload) could re-create a deleted row locally.
- **Fix — soft-delete `sites`, the pattern B792 already shipped for `doc_reviews`.** New `src/workspaces/site-planner/db/sites_soft_delete.sql` adds `sites.deleted_at` + two partial indexes (the bin listing, and a live-rows index so every read's new `deleted_at is null` stays fast); RLS deliberately unchanged and reviewed — soft delete rides UPDATE (owner **or** any team member, matching B792's recoverable-trash semantics) while the permanent purge still rides the stricter DELETE policy (owner/team-admin). **Applied to production via MCP this session and confirmed** (`deleted_at` column + `sites_deleted_at_idx` + `sites_live_updated_at_idx` all present). `cloudDelete` becomes `UPDATE … SET deleted_at = now()`, keeping B372's `.select("id")` zero-row honesty and the `reportClientEvent` telemetry; `cloudHardDelete` is split out for the purge + the pre-migration degrade; `cloudRestore` un-bins. `cloudList` filters `deleted_at is null` at every fallback tier, and — the actual fix — `pullCloud` additionally fetches `cloudDeletedRows` and hands `mergePulledSites` the server's deleted id set, so **"the cloud is missing this row" becomes "the cloud says this row is deleted"**, a fact every client reads. `toPush` excludes it and heal-the-split can never resurrect. **B124 is intact**: a genuinely local-only, never-pushed site carries no tombstone and is not server-deleted, so it still heals (unit-locked).
- **LOUD-FAILURE on the new fetch.** If the deleted-id fetch itself fails we cannot tell "never landed" from "deleted", so the cloud-absent half of heal-the-split is **suspended for that pull** (nothing local is dropped; the heal simply waits) and a `cloud-read-failed` telemetry event fires. A pre-migration DB reports `supported:false` and everything degrades to today's hard delete.
- **TOMBSTONE-DELETES, independently of the migration.** `saveSite` now checks `readSiteTombs(activeUser)` alongside `recentlyDeleted` (hole 3), and the durable tombstone **survives a 30-day grace window** (`SITE_TOMB_GRACE_MS`, matching the retention) instead of clearing the moment the cloud confirms (hole 2) — so even a pre-migration peer's resurrection gets **re-killed rather than adopted**. A server-reported delete also writes a local tombstone on the receiving client (`tombAdd`), so a still-mounted planner's late flush can't re-create it before the next pull.
- **Elements survive (no cascade fires) → a real Recently deleted → Restore bin.** New store API (`listDeletedProjects` / `restoreDeletedProject` / `purgeDeletedProject` / `purgeExpiredDeletedProjects`, re-exported through `shared/projects/projects.js`) and a **"↺ Recently deleted · N"** section in the shared project switcher (`ProjectBreadcrumb`) with per-project **Restore** and a confirm-gated **Delete forever** — the only user-facing hard delete. The bin groups plans into PROJECTS (a project is a site group), matching how delete is offered. A lazy 30-day purge runs when the bin is listed. Because the delete was soft, **restore returns the project WHOLE**, not the gutted shell the bug produced. The delete confirms in both surfaces (breadcrumb + `MapFinder`) now tell the honest new story instead of the no-longer-true "This can't be undone."
