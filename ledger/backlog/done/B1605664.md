**⛔ THE CONTRADICTION THE BRIEF ASKED TO BE RECONCILED FIRST — the harness and the owner were both telling the truth about different boxes.** Round 1's fix was a `transform: translateY(...)` on `dom`, the ProseMirror body. `dom` lives INSIDE `note-sheet`, and `note-sheet` is the page a person sees: the white surface, the border, and the two height grips that sit on its edges. Round 1's own probe, quoted in its write-up above ("top 267→367, bottom fixed at 704"), is the same `note-body` rect — honest, and about the wrong box. **The owner's stated rule-out — `getComputedStyle` reporting `transform: none` on the sheet, its parent and its grandparent — is confirmed and is NOT refuted: the transform is on the sheet's CHILD, which those three reads could not see. It is applied, and it does persist across the commit (`matrix(1, 0, 0, 1, 0, 39.89)` after release); it was never the direction or the lifetime that was wrong, only the element.** Round 1's own root cause — `scrollTop` cannot go negative and a note page opens at 0, so scroll cannot represent a top-edge shrink — is UNCHANGED and still correct; it is the thing this round designs around, exactly as the brief instructed.

**THE FIX: a layout offset on the PAGE, not a paint offset on the text.** `heightTopPadRef` (+ a new `sheetTopPad` render mirror, written through one `writeTopPad` helper so ref and render can never disagree) now feeds `note-sheet`'s own `margin-top`. The page's height still comes from `dom.style.minHeight`, so shrinking by `S` and pushing the page down by `S` holds the bottom edge exactly still — `bottom = top + height`, `(T + S) + (H − S) = T + H` — while the top edge moves 1:1 with the pointer. ⛔ A margin is safe HERE and was not on `dom`: round 1 rejected `margin-top` because `dom`'s own top margin collapses with the title band's `marginBottom` (measured 16px short every time), and `note-sheet` is a FLEX ITEM of `note-mat` (`display: flex; flexDirection: column`), where margins never collapse with anything. It is also the one offset that survives `zoom`: the sheet's margin and the body's `minHeight` are scaled by the same zoom, so the two cancel at every level. Because the sheet is React-owned, the offset is React state — the same reason `sheetGrowWidth` exists for the width feature, and the reason round 1's "NO REACT STATE NEEDED HERE, UNLIKE WIDTH" comment was the tell that it was writing to the wrong element.

**THE RULE IS NOW PURE AND ONE LINE, NOT TWO BRANCHES.** `topEdgeCompensation` (`lib/notesPageHeight.js`) answers both directions: growing HANDS BACK whatever gap an earlier shrink opened before it spends a single pixel of scroll, so a shrink-then-regrow round trip lands exactly back at rest with no leftover gap above the page and no leftover scroll under it. Two independent branches would accumulate both, and the drift only shows on the third or fourth gesture — the kind nobody reports as a bug. `heightPadOwnerRef` stops the offset going stale: it records the committed `pageHeight` the gap belongs to, every height drag on either edge re-stamps it (so "drag the top, then drag the bottom" composes instead of jumping), and any other route to a different height — undo, redo, a sync from another device, Fit to content — drops the gap and re-anchors the page at the top of the mat.

**⛔ WHY THE GAP IS KEPT AFTER RELEASE.** Clearing it on commit would yank the page back up by `S` the instant the mouse comes up, which IS the reported bug one frame later. With the mat already at `scrollTop === 0` there is nothing above the page to scroll into, so real space opening above it is the only way the top edge can move down at all — the honest consequence of the owner's own stated expectation. That space is ordinary scrollable grey, and a reload (which restores neither scroll position nor this offset) settles at the app's usual top-anchored rest position with the same stored height, unchanged from round 1.
