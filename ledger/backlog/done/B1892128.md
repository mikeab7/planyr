`[x]` **AUDIT-FIRST — the dispatch's own framing ("sorts long tasks by duration and keeps the smallest") describes the NET EFFECT of two separate, individually-plausible pieces of code, not a literal sort call, and finding that composition is what the fix actually required.** `perfRecorder.js`'s `capture()` (line ~286) already sorts `tasks` **worst-first** before capping to 24 — `.sort((a, b) => _tasks.dur[b] - _tasks.dur[a])`, "the biggest blocks are the ones worth the characters" — which is correct and untouched. The bug is entirely downstream, in `perfCapture.js`'s `encodeCapture()`: its `shedTasks` helper (added by B1317824, "TASKS NOW TRIM OLDEST-FIRST") drops `tasks[0]` on the explicit assumption that index 0 is the OLDEST task, mirroring how the frame track is trimmed. That assumption was never true for the task table — it arrives duration-descending, not chronological — so dropping the front of the array discarded the BIGGEST tasks first, leaving only the small ones that happened to survive at the tail. Confirmed against B1317824's and B846385's own regression tests (`test/perfRecorder.test.js`): both existing fixtures build `tasks` with duration **ascending** by index (`60 + i * 90`), the opposite of what the real recorder produces, which is exactly why neither caught this — a textbook WRONG-CASE instance (the fixture's incidental ordering happened to make front-eviction look like oldest-eviction).
`[x]` **FIXED — `shedTasks` now sheds from the TAIL of the array, not the front, in both call sites (the `TASK_FLOOR`-bounded stage and the final all-the-way-to-zero stage share the one helper).** Since the array is already worst-first, the smallest durations sit at the end; shedding from there keeps the kept set as exactly the biggest N tasks, which is the entire reason the producer sorted them that way. `perfCapture.js`'s header comment for this shedding stage, and the earlier top-of-file history paragraph describing the B1317824 order as "oldest-first … dropping the earliest evidence, keeping the most recent," are both corrected in place with a dated addendum rather than silently rewritten, per this file's own layered-correction convention.
