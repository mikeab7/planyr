- **THE DATA MODEL.** `o.crop = { x, y, w, h }` in IMAGE PIXELS (the same unit as the existing `imgW`/`imgH`), additive to the `sheetOverlays` record — the persisted raster (`src`/`storageKey`/`idbKey`) is **never touched**, so widening or clearing the crop later recovers exactly the original picture with no re-import. Sparse, matching every other overlay/settings flag in this codebase: no `crop` key at all = the full image, and a crop that normalizes back to covering the whole image collapses to `null` rather than persisting a no-op rect (`overlayCrop.normalizeCrop`).
- **THE DISPLAY MECHANISM — literally what was asked for.** `SitePlanner.jsx`'s `renderSheetOverlay` renders an SVG `<clipPath>` (a `<rect>` sized/positioned via the new pure `cropClipRectScreen`) and applies it to the placed `<image>`'s `clip-path` attribute, ONLY when `hasCrop(o)` — an uncropped overlay renders byte-identically to before this feature (proven: a source-guard test asserts the `<image>`'s `href`/box are untouched, and the live check below confirms no `<clipPath>` node exists for an uncropped overlay). The persisted raster (`o.src`, and the transient hi-res zoom raster `hiresById[o.id]`) are both left as the FULL image; only the DISPLAY is clipped, which is what non-destructive means here.
- **THE PANEL UI.** Four feet-based edge-trim fields (Left/Top/Right/Bottom) in the References panel, available for both PDF-sheet and plain-image overlays (not gated on `o.sheet`), converting to/from the image-px `crop` rect via `overlayCrop.cropTrimFeet`/`cropFromTrimFeet` — this app is feet-everywhere-internal at the UI boundary, never raw pixels. Commits through the SAME `patchOverlay` helper Opacity/Rotate/Width already use (one undo frame per edit session via `onFocus → pushHistory()`, live typing otherwise). A "Reset crop" action (visible only while cropped) clears the field entirely — reversible in one click, no re-import.
- **PDF-PARITY (the one LIVE-VERIFY-class candidate here) — DRIVEN, not argued from source.** `exportSheet.js`'s `buildExportSvg` clones the live `<svg>` wholesale (the same "an export is a document, not a screenshot" mechanism this repo's other overlay features already rely on for parity — B131/B654/B461's z-order/lock/knockout all ride the same clone), and the export's blob→persisted-src href swap (`inlineImages`) sets `href` in place without touching any other attribute — so the `<clipPath>` + its `clip-path` reference on the `<image>` were expected to survive into the export automatically, with zero new plumbing in `exportSheet.js`. **Confirmed, not assumed:** the live check below calls the real E2E `window.__plannerExportSvg()` hook (the same one B719408/measure-export-lod use) after applying a crop and asserts the returned sheet HTML carries the SAME `clipPath` id and the SAME `clip-path="url(#…)"` reference on the exported `<image>`. - **RASTERISATION COST — WHAT WAS SHIPPED, AND WHAT WAS DELIBERATELY NOT, stated so a later session doesn't assume more than was built (see `overlayCrop.js`'s own header for the full derivation).** A clipped-out region is never painted to the framebuffer by the browser's own compositor, so a heavily-cropped overlay genuinely costs less to paint/composite on every pan and zoom, and that saving carries into the export via the same clone — this is real, not hand-waved.
