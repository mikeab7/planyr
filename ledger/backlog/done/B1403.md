- **WHY THIS IS WORSE THAN SLOW.** ArcGIS answers any query with at most the layer's `maxRecordCount` and sets `exceededTransferLimit` when it had more to give. esri-leaflet's `featureLayer` does not page, so the map drew an authoritative-looking parcel layer with an unknown number of lots simply **not there to click** — and said nothing. A lot the owner needs can be missing from a map that looks complete.
- **THE AUDIT, over every parcel fetch path rather than the one the report came through:** the vector GIS engine (`vectorLayers.js`) and the nightly snapshot builder both already page on the server's own flag and are **untouched**; the point paths (`queryAtPoint` / `identifyAtPoint`) are single-point intersects and cannot reach a record cap; the `/export` image path is rendered server-side and returns no flag to read. The DISPLAY path was the one unchecked consumer, and it is the one that cannot page.
- **SO IT SAYS SO.** `parcelTruncation.js` (a new pure module — split out of `parcelDisplay.js`, which imports Leaflet and therefore cannot be unit-tested) answers "did this come back cut short?" in **every shape a real service returns the flag** (top-level `exceededTransferLimit`, GeoJSON `properties.exceededTransferLimit`, and `transferLimitExceeded`), and produces one honest, non-blocking notice naming the cap and what to do: *"That parcel service capped this view at 2,000 lots — some outlines here are missing. Zoom in to see them all; clicking a lot still adds it."* Wired to the display layer's `requestsuccess`.
- **B1401 also removes most of the OCCASIONS for it** — a county on its own endpoint answers a view-sized bbox well inside `maxRecordCount` — but the notice stays, because the composite is still every county's outage fallback and Waller's primary.
