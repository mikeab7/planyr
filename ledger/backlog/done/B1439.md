### B1439 — Switching plans leaves the plan you left behind alive in the renderer `[Site Planner / Map]` (bug) #site-planner #perf #persistence  *(found 2026-08-06 by the B1436 probe's plan-switch axis. **Filed deliberately, NOT fixed** — one A→B→A round trip is a suspect, not a conviction, and B1434's own rule is "do not ship a fix you cannot demonstrate on the probe." Minted **B1439 / V717** LATE via `--against-main`. DEDUPE-FIRST — searched Open + ⏳ Verify + Done across `detached`, `teardown`, `release`, `releaseLayer`, `unmount`, `B1121`, `B1161`, `B1331`, `B1433`: **B1433** measured detached DOM at ZERO from V8's own `detachedness` flag — but only across INTERACTION on one plan, never across a plan SWITCH, which is a different lifecycle entirely; **B1161** is MapFinder's second Leaflet map, a different object. Net-new.)*
`[x]` **✅ FOURTH ATTEMPT (2026-08-07) — RESOLVED, AND THE ANSWER IS THAT THERE IS NO PRODUCT BUG. The leak was the measuring harness's own undisposed `ElementHandle`. Fix + regression guard shipped. Everything below the FOURTH ATTEMPT block is the superseded record of attempts 1–3.**
- Verify: live
- Origin: found 2026-08-06 by `ui-audit/session-axes.mjs --axes plans`

Listeners are released every time (+0.3 to +2.7%); the ATTACHED node counts come back to where they started every time, so the residue is entirely in nodes the renderer is holding that the document no longer contains.
- **WHY IT IS STILL NOT CONVICTED, stated rather than implied.** `rendererNodes` counts every node the renderer is keeping alive, which includes nodes held only by a JS reference — that is a weaker claim than "detached DOM", and the honest counter-evidence is **B1433's ZERO detached nodes read from V8's own `detachedness` flag** (measured across interaction on one plan, which does not cover a switch). Each run above is also ONE round trip on a fresh load, so this shows a switch leaves a residue; it does **not** yet show the residue COMPOUNDS across several switches in one session, which is the version of the question that matters for the owner's symptom.
- **WHAT WOULD SETTLE IT, and both halves are cheap:** (1) a full heap snapshot through `ui-audit/lib/heapSnapshot.mjs`'s detachedness reader at A₀ and again at A₁ — a non-zero count with a class name on it turns this from a signature into a mechanism; (2) three round trips inside ONE page load (a small harness change) to see whether it compounds. If it compounds, this is a genuine per-switch leak and it feeds straight into the one row the **B1435** audit could not answer — whether major-GC pause time scales with the live set on a 278 MB tab.
- **WHY IT MATTERS TO THE OWNER'S SYMPTOM.** Plan/revision switching is one of the axes that rises through his session and resets on reload — the exact shape of *"reload and it's quick; a minute or two later it's lagging."*
- **⏱ SECOND ATTEMPT — `docs/PERF-PLAN-SWITCH.md`, instrument `ui-audit/diagnose-plan-switch.mjs`.** The item asked for "one real attempt … if it still cannot be named, say so plainly and record what the second attempt ruled out, so a third does not start from zero." Four things are settled that were open, and one is not.
  1. **IT IS NOT THE HARNESS.** Every probe here sets `window.__PLANYR_E2E`, arming four `window.__planner*` hooks that were never nulled on unmount — a genuine candidate for the whole signature. The `--no-e2e` control runs the identical cycle without them and leaks **IDENTICALLY**: 7,026 detached nodes, 1,173.4 KB, `rendererNodes` +326.2%, `jsEventListeners` +55.1%, on both arms. **B1439 is a product bug.**
  2. **THE DETACHED DOM IS REAL, and B1433's zero does not cover this.** From V8's own `detachedness` flag: **0 → 2,342 nodes / 391.1 KB** across one A→B→A, while every attached counter returns exactly. B1433 measured zero across INTERACTION on one plan — a different lifecycle.
  3. **IT COMPOUNDS — the version of the question B1439 said mattered.** ×1 → 2,342 nodes / +108.7% `rendererNodes`; ×3 → **7,026 nodes / 1,173 KB / +326.2%**, heap +37%. **Linear at ~2,342 nodes and ~106 listeners per round trip, released never.** Nothing plateaus, so this is not "the previous plan is held until the next replaces it" — every plan opened in a session is still there. It is the only thing measured anywhere in the speed program that grows **without bound inside one session**, which is the exact shape of the owner's report.
  4. **WHAT IS HELD is the WHOLE previous `SitePlanner` tree, not just its canvas** — 78 detached `<svg>` roots (the rail's inline icons), `<button data-rail-tab="standards">`, `<button data-rail-tab="references">`, the panel divs, and 1,187 `SVGRectElement`.
  5. **HALF-NAMED, and the half that is named is new.** Two holder classes, from a proper reverse-graph search: a **bound function** (`native_bind`) holding the overlay's file `<input>` as its third bound argument, and a plain **`Array`** holding a detached `<div>` — from either root the whole tree is reachable by ordinary DOM edges. **No source line**, because there is no `.bind(` in `src/` taking a DOM node (the one site-planner match is `fetch.bind(globalThis)`). **⛔ So no fix is shipped — B1434's rule.**
  - **Two methodological corrections are recorded, because each produced a confident WRONG answer first.** (a) The **shortest retaining path is the wrong question** for a detached node: every DOM wrapper is one edge from V8's handle table, so `(GC roots) → (Traced handles) → node` is always available and never distinguishes a leak from a live element — the first run returned exactly that for every class. (b) **A `native` node is not a holder either**: Blink hangs `SVGAnimatedLength` / `CSSStyleDeclaration` / `Text` / `InternalNode` off every element and those are NOT flagged detached, so "the first non-detached retainer" answered *the element's own width attribute*. `holderOf` traverses THROUGH both and reports only a JS-side holder — or refuses, with a stated reason.
  - **RULED OUT, so a third attempt starts here:** not the harness (1) · **not a listener left on a long-lived target** — `DOMDebugger.getEventListeners` on `window` and `document`, with the registering script position on every row, is **net +0 on both**, so the ~106 listeners/cycle are on the detached nodes themselves and are a CONSEQUENCE, not the cause · **not a missing `removeEventListener`/`disconnect()`/`clearInterval` in app code** — an exhaustive sweep of `site-planner/**`, `shared/**` and `app/**` for all seven asymmetry classes found ZERO (every module-level registry returns an unsubscribe and every consumer uses it) · **not Leaflet** (`leafletContainers` and `leafletTiles` return exactly; `releaseLayer` intact) · **not `window.__planner*`**, though those four hooks WERE a real retention path and are **nulled on unmount as of this dispatch** so no future measurement is taken through them.
  - **WHERE A THIRD ATTEMPT SHOULD START:** the `Array` holder — a plain JS array with a detached `<div>` at index 1, the cheapest thing left to identify and certainly ours or a dependency's rather than an engine artifact. The tool to do it with now exists (`holderOf` + `retainerIndex`, 21 unit tests).
- **Tests added by the second attempt.** `test/heapSnapshot.test.js` grows the edge-walking half: `to_node` is a BYTE OFFSET not a node index · an `element`/`hidden` edge's name is an ARRAY INDEX not a string-table offset · every retainer is recorded, not just the first in node order · `holderOf` names the first non-detached NON-NATIVE holder and REFUSES to invent one when every retainer is detached, native or a handle table.

- **⛔ FOURTH ATTEMPT (2026-08-07) — CLOSED. `docs/PERF-PLAN-SWITCH.md` §12–§16.** The mechanism is
  named, proven by making the leak conditional, fixed, and guarded.
  - **THE CAUSE IS ONE IGNORED RETURN VALUE IN THE INSTRUMENT**, not a line of app code:
    `await page.waitForSelector('[data-testid="planner-canvas"]')`, called after every route change
    by every harness in this family. `waitForSelector` **returns an ElementHandle**, which is a
    strong V8 global handle in the inspector's object group; Playwright never disposes it and
    ignoring the return value does not either. A Blink `Node` holds its **PARENT** strongly, so one
    undisposed handle on the canvas `<svg>` pinned the whole detached shell above it. It accounts for
    the quantities exactly: ~1,171 nodes is one app shell, ×2 per round trip is the 2,342, ×3 cycles
    is the 7,026, and it is linear because one handle is stranded per switch.
  - **PROVEN CONDITIONALLY** — two arms, one line apart. Handle ignored: `0 → 3,377` detached,
    `rendererNodes 2,378 → 6,112`, listeners `577 → 736`. Handle **disposed**: `0 → 0` detached,
    `rendererNodes 2,379 → 2,379`, listeners `578 → 578`. **Flat on every counter B1439 was filed on.**
  - **HOW IT WAS NAMED — one heap rule §8 had backwards.** §8 refused to traverse handle tables, so
    it could only ever conclude "nothing live points into the island". The right rule is *skip WEAK
    edges*, not *skip handle tables* — a `weak:` edge does not retain, which is why §8's six
    crossings explained nothing, while an inspector-side retention IS a strong handle-table edge.
    Re-run that way the entire island has **exactly two** strong crossings, both
    `(Global handles) ──internal:N / DevTools console──▶ SVGSVGElement`. One per switch.
  - **ALSO RULED OUT, all null results, all recorded (§14):** §9's step 1 **animations** —
    `getAnimations()` is 0 before AND after, and switching mid-flight vs switching only once the page
    is provably animation-free leaks identically (2,342 each) · §9's step 3 **listeners beyond
    window/document** — `getEventListeners` at `depth:-1` over the whole live tree, **net +0** ·
    **observers / ranges / focus** — constructors wrapped before app code, 0 observers left observing
    a detached element, no stale range, `activeElement` = BODY · **conservative stack pinning**, which
    nearly became a fourth wrong answer: a forced purge drains 2,343 → 1 while 13 `collectGarbage`
    calls do nothing, but both natural allocation pressure AND a precise cache-neutral
    `gc({execution:'async'})` move it not at all, so the retention was real and the purge freed it by
    releasing the inspector's object group.
  - **SHIPPED.** `ui-audit/lib/waitRelease.mjs` (disposes in a `finally`; deliberately never returns
    the handle) · the contaminated harnesses fixed — `diagnose-plan-switch.mjs`,
    **`session-axes.mjs`** (its `switchPlan` stranded one per switch, so **its plans-axis memory
    numbers were measuring this defect** — including the `rendererNodes +93.9%` reading this item was
    filed from, now retired) and `interaction-degradation.mjs` · the **regression guard**
    `ui-audit/verify-plan-switch-release.mjs` (`npm run perf:planswitch`), measured green at guarded
    `0 → 0` detached / `rendererNodes 2378 → 2378` with its control arm dirty at `0 → 1035`.
  - **THE GUARD CANNOT ROT GREEN**, which is the point given three attempts hid from ordinary checks:
    it runs a second arm that strands a handle **on purpose**, and if that arm comes back clean it
    FAILS as *not observing* rather than passing; and it refuses to report unless the plan switch is
    proven by the drawn-element count changing. Tests: `test/planSwitchRelease.test.js` (the pure
    verdict table incl. both anti-rot cases) and `test/harnessHandles.test.js` (static: a script that
    measures retention may not call bare `page.waitForSelector`; the file list is derived from what
    each script does, and the test asserts that list is non-empty).
  - **⚠ WHAT THIS DOES NOT EXPLAIN, said plainly.** B1439 was the only confirmed defect matching the
    owner's *"reload is quick, a minute or two later it's lagging"*, and it is now retired — **that
    symptom is unexplained again**, and nothing here addresses it. The memory readings that pointed
    at plan switching came through the contaminated harness and **need re-taking**. See **B1121**.
  - **METHODOLOGICAL LESSON — the fourth in this family** (§4a's two, §6's one): *the instrument's own
    protocol handles are part of the measured heap.* §1 asked exactly the right question and built
    `--no-e2e` to answer it, but varied the app-side `__PLANYR_E2E` hooks rather than the
    harness-side handles. Clearing one candidate is not clearing the instrument.
