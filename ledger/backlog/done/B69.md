### B69 — Paving "+" over-increments from a single-loaded bay `[Site Planner]` (bug)
`[x]` Repro: start from the ~42–47′ paving cross-section (one parking row + one drive aisle — a single-loaded bay = parking on one side of the aisle only) and click "+". **Observed:** it added two parking rows plus another drive aisle (a full double-loaded module). **Expected:** "+" adds exactly one parking row — from a single-loaded bay it converts to double-loaded (parking both sides of the existing aisle, ~60–65′); a new drive aisle is inserted only once the current aisle is already double-loaded; each click steps by one row, never a two-row module. (Filed from a parallel chat as provisional "NEW-1"; minted **B69** here — B67/B68 were already taken on `main`.)
> Done 2026-06-15 (branch `claude/nice-wozniak-2k2v9c`). **Root cause:** `growParking` stepped depth by a whole `stallDepth+aisle` band per click, but the renderer/counter (`carStalls`) re-flows the field into *double-loaded modules* (2 rows share 1 aisle), so a single band of added depth re-striped into ~2 extra rows + an aisle — the jump the report saw. (Distinct from the already-fixed B29/B59, which were per-element `cfg` plumbing in the same area, not the increment model.) **Fix:** two pure helpers — `parkDepthForRows(n)= n·stallDepth + ⌈n/2⌉·aisle` and its inverse `parkRowsForDepth(h)` — model double-loading explicitly; `growParking` now reads the current row count and sets the depth for `n±1`, so the increment alternates +stallDepth (single→double-loads the last aisle) / +stallDepth+aisle (adds a new aisle) exactly as specced. `setParkCfg`, `splitParkingRows`, `canShrink`, and the two "Split into rows" `≥2` gates were moved onto the same row model so depth↔rows stays consistent; the "+" button/tooltip relabelled "＋ Row" / "Add one parking row" (was "Row + aisle"). Verified: 42→60→102→120→162 (rows 1→2→3→4→5, +18/+42/+18/+42), round-trip `rows↔depth` clean for n=1..8; build + tests pass.
