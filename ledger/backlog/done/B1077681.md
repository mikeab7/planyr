`[x]` **SHIPPED THIS SESSION — hypothesis confirmed, then fixed at the root rather than patched.** Root cause matched his hypothesis exactly: `docToText` discards all node structure by design (it's the search-index flatten), so a table and the same words as running paragraphs produce byte-identical output, and the old word-diff (`diffNoteText`/`sideOps`) had nothing left to distinguish.
- **The fix is architectural, not a patch onto the flatten.** `lib/notesRedline.js` gained `buildComparison(revisedDoc, originalDoc)`, which runs the SAME block-alignment LCS the unified redline already uses (`buildRedline`'s engine, refactored into a shared `computeFlat` so the two views can never disagree) and additionally derives `panes.newer`/`panes.older` — two independent, fully-formatted block trees: the newer document's own shape (kept blocks + insertions) and the older document's own shape (kept blocks + deletions). `ConflictSideBySide.jsx` now renders each pane through the SAME `NoteRedline` component the unified view uses (rather than a second, separate rendering path), so a table renders as a table, a picture as a picture, in BOTH views — real structure survives, and the two panes can only look alike when the documents genuinely do.
- **The reassurance he should hear, checked rather than assumed, per the brief's own instruction not to assert it without confirming.** Where the sole difference between two versions is a table converted to the same words as plain text, the INFORMATION is identical either way — confirmed structurally (the block alignment matches the table's cell text against the paragraphs' text at the word level) — so neither choice loses data, only formatting differs. This is now visible directly in the panel itself (the redline shows the table's real removed content sitting right next to the paragraphs' added content, so a reader can see the words are the same) rather than asserted in chat.
