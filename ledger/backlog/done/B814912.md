- **ROOT CAUSE (a), confirmed by reading, not guessing.** `STATUS_TOKENS.dead` (`shared/ui/statusTokens.js`) carried `hideByDefault: true` — a flag `MapFinder.jsx` honored at two render sites (the map pin/zoomed-plan render, and the KMZ export) with `if (status === "dead" && !statusFilter.has("dead")) return;`. A Dead site rendered on the map ONLY when the user proactively clicked the "Dead" status filter chip — otherwise it was omitted outright, from both the pins and the KMZ export, with no indication anything was hidden. (The "Your sites" LIST panel was NOT affected by this flag — a dead site was always still listed there, just filed under a "Dead" section that's COLLAPSED by default, matching "Complete." That's left as-is: reasonable, one click away, not what "disappeared entirely" describes.)
- **THE FIX.** Removed `hideByDefault` from `STATUS_TOKENS.dead` and both of `MapFinder.jsx`'s `status === "dead" && !statusFilter.has("dead")` gates. A Dead site now renders exactly like every other status, subject only to the ordinary chip filter — it still recedes visually (smallest tier, dimmest opacity, gray ✕ glyph, per the EXISTING B433/B434 salience rules, untouched) but is never omitted. The status-chip filter itself is unchanged and still works (clicking "Dead" still isolates it).
- **THE UNDO (b).** `SitePlannerApp.jsx`'s `setSiteStatus` now captures the prior status before writing, and — when the status actually changed — pushes a toast (`“<site>” marked <Status>.` + an **Undo** button that calls `setSiteStatus` back to the prior value) via the app's existing shared toast primitive (`shared/ui/Toast.jsx`, B673's sync-conflict toast — reused rather than duplicated: `role="status"` announced, auto-dismissing with hover-hold, an explicit action button, exactly the "loud but non-blocking, offers an action" shape this exact bug needs). Rendered at the `SitePlannerApp` level (outside both the Map/Plan mode divs) so it survives a mode switch before its own timer elapses. Ctrl+Z itself was NOT wired to cover this (that stack lives entirely inside the `SitePlanner` canvas component and structurally cannot see a Map-level header write) — the toast is the "obvious, working undo" the report asks for instead of a silent, misleading no-op.
