- **CHECKED FIRST, per the brief's explicit instruction not to steal Alt from an existing shortcut.** Every existing `altKey` use in `SitePlanner.jsx`: Alt+Z (physical KeyZ) autosizes a text box/callout — different key, no conflict. Alt+click (no Shift/Ctrl/Meta) already cycles one level deeper into the hit stack at a point (`handleStackPick`, B548822) — a CLICK gesture; this feature is a HOVER gesture (no click needed to see the list), so the two coexist: holding Alt shows the list, and a click that lands on the canvas itself (not on the list, which is a separate floating overlay) still cycles the old way. Alt held during a drag-place bypasses grid snap (`altSnapOffRef`) — reads `e.altKey` on its own pointer events, untouched, and this feature is gated to `tool === "select"` so it never shows during a placement drag anyway.
- **THE MECHANISM.** A `keydown`/`keyup`/`pointermove` listener (mounted once, gated on `tool === "select"`, no menu open, and not while a text field is focused) computes `stackAtPoint(document.elementsFromPoint(x,y))` — the SAME ordered, deduped, chrome-skipping stack reader `handleStackPick` and the priority-rule already use, never a re-derivation — and renders a small floating list (a portal, not the shared `ContextMenu` component, since this is hover-driven and must carry no dismiss backdrop that would block the canvas underneath). Each entry is labeled the way a user would name it (`Building N` via `buildingNumbers`, `<stall depth>′ Trailer Parking`, `<pond name> <acreage> AC` via the same `pondDisplayNameFor`/`pondAreaLabelLine` the on-canvas label uses, else the plain type label). Hovering an entry highlights it on the map by reading the ALREADY-PAINTED DOM node's own `getBoundingClientRect()` (`data-feature="<kind>:<id>"`, the same key `featureStack` resolves) rather than re-deriving its screen geometry. Clicking an entry (or Enter, with Up/Down moving the highlight) calls `setSel(entry.target)` — `target` is already in the exact shape `sel` expects, the same shape `handleStackPick` already writes. Alt release or Escape dismisses; empty canvas computes zero entries and renders nothing (no empty box).
- **VERIFIED.** `e2e/markup-behind-building.spec.js`'s new NEW-2 describe block (4 tests, real Chromium): the picker names both the covering building and the behind-band markup topmost-first, picking the markup selects it WITHOUT moving it (still behind the plan), the covering element's own menu is then reachable again via the unchanged priority rule and its cross-band toggle brings the markup back in front, and hovering a feature with nothing behind it shows exactly one entry while empty canvas shows none. `ui-audit/verify-markup-over-building.mjs` re-run against the owner's real Bain plan (21/21): at a real overlap point the actual stack is FIVE deep (two road pieces, the markup, two parcels) — the picker reports all five correctly, topmost-first, richer than the simpler synthetic fixture and exactly the "reach a completely covered feature" case the brief asked for.
