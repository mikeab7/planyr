- **WHAT ACTUALLY DRIVES THE PICTURE, established before writing anything (per the brief's own "read this first").** Read `DashboardTopoBackground.jsx` in full: there is **no scroll-driven motion anywhere** — the canvas is `position:fixed` to the viewport and never reads a scroll offset. The ONLY user-input driver is the cursor: a localized bulge in the ambient noise field near the pointer (the "highlight"). The field's own large-scale drift runs on pure elapsed time (`t += 0.0000625`/frame), independent of any input — that's DEPTH, already correctly slow (three prior items tuned it) and untouched by this one.
- **FOLLOW and DEPTH already existed as unnamed inline magic numbers** (`d2 < 9` / `S * 1.6` for the cursor's reach/strength; `t += 0.0000625` for the depth-of-field time rate) — now named (`FOLLOW_RADIUS2`, `FOLLOW_STRENGTH`, `DEPTH_RATE`) in a new small pure module, `lib/topoMotion.js`, with the SAME values (a pure rename, no behavior change to either).
- **SETTLE was genuinely missing, confirmed by reading the code, not assumed.** The raw cursor TARGET (`ptr.tx`/`ptr.ty`) was already set directly from `clientX`/`clientY` — instant, lockstep. What eases toward that target (`ptr.x`/`ptr.y`/`ptr.s`) already existed too, as three duplicated inline lerp lines at 0.11 (position) / 0.065 (intensity) — but MEASURED against the ask: at 60fps that reaches ~90% of a sudden jump in about 20 frames (~330ms), which reads as "tracks the cursor," not "trails behind it." **The fix is `easeToward` (new, pure, unit-tested) replacing those three inline lines, at new, genuinely slower constants — `SETTLE_POS 0.045` / `SETTLE_STRENGTH 0.03`** (roughly half the old rate, ~45–50 frames / ~750–800ms to 90%).
- **WHY THESE NUMBERS READ AS "LAG," NOT "SLUGGISH" OR "SEASICK" — the brief's own explicit ask, answered rather than asserted.** A lerp toward a FIXED target cannot overshoot or oscillate — it only ever approaches monotonically — so there is no mechanism by which slowing it further could look "seasick" (that needs an unstable/oscillating system); it can only ever read as more or less lag. "Sluggish" was the real risk worth weighing, and the headless mechanism proof below shows the highlight visibly leaves the OLD point and visibly arrives at the NEW one within under a second, not several — a deliberate beat, not a stall.
- **prefers-reduced-motion: YES, respected — unchanged, reconfirmed directly.** The whole per-frame loop (including the new `easeToward` calls) only runs inside the existing `rAF` loop, which `prefers-reduced-motion: reduce` (and a coarse/touch pointer) already skip entirely, rendering exactly one static frame — this item adds no new gate, the existing one already covers it. Reconfirmed with a fresh headless pass (two `toDataURL()` reads 900ms apart, byte-identical) rather than only citing prior sessions' passes on this file.
- **MECHANISM PROOF (not a screenshot vibe-check) — `ui-audit/verify-dashboard-topo-settle.mjs`.** Samples the canvas's own drawn pixel color (`getImageData`, averaged over a real box wide enough to catch several contour-line segments — a single pixel is nearly always fully transparent, since the highlight composites with `source-atop` and only tints existing ink) at two far-apart points before and after a sudden cursor jump: the OLD point still carries most of its tint immediately after the jump; the NEW point has NOT snapped to full tint immediately; both migrate monotonically (no oscillation, confirming the "can't be seasick" reasoning above) over the following ~1.6s; the NEW point reaches a strong tint once settled and the OLD point fades back down.
