DEDUPE-FIRST — searched Open/⏳Verify/Done for "ScrollChevron", "row1Edges", "chevron drift": B1343201/B917073 (Done) built the show/hide mechanism this bug lives inside but never measured the chevron's own on-screen position across a scroll. Net-new.)*

`[x]` **ROOT-CAUSED AND FIXED THIS SESSION.** `ScrollChevron` (the phone-only tappable arrow that pages Row 1's breadcrumb strip and Row 2's module-tab strip when either genuinely overflows) was rendered as a DIRECT CHILD of the very `<div>` that both scrolls (`overflow-x:auto`) AND is its `position:absolute` containing block. A `position:absolute` descendant of a scrolling element is part of that element's own scrollable content in the browser's rendering model — it does NOT stay pinned to the element's visible viewport, it scrolls along with everything else inside the box, even though its `right`/`left` offset is computed against the (unscrolled) padding box. That mismatch is exactly the reported symptom: as the row scrolled right, the chevron (laid out at a fixed point in the row's *content* coordinate space) visually slid left relative to the viewport instead of staying pinned to the true edge, and the "always still points right" read was the same drift making the control land somewhere other than the edge it was meant to mark.
- **THE FIX.** Wrapped each of the three scrolling rows (Row 1's `rowRef`, and both of Row 2's `toolbarCenter`-present / absent branches, which share `row2Ref`) in a small, non-scrolling `position:relative` wrapper `<div>` and moved the `ScrollChevron` calls to be children of that wrapper — siblings of the scrolling row, not descendants of it. CSS resolves `position:absolute` against the NEAREST positioned ancestor, so the chevrons now pin against the wrapper (which never scrolls) instead of the row. `rowRef`/`row2Ref` KEEP their own pre-existing `position:relative` unchanged — nothing else about the row's layout, mask, or measurement refs moved; only the two chevron render sites did. Zero behavior change for the row's own content, the edge-fade mask (`row1Mask`/`row2Mask`, still applied only to the row, so the chevron — now outside it — is no longer implicitly faded by it either, which is a correctness improvement, not a visual regression: the fade exists to soften the CONTENT near the edge, not to dim a tappable control sitting on top of it), or the centered content (Row 1's jurisdiction badge, Row 2's Schedule center group) that still legitimately positions against the row itself in the one mode (`!narrow`) where it uses `position:absolute` at all.
- **MUTATION-PROVEN.** Extended the existing live harness `ui-audit/verify-header-touch-targets.mjs` (NEW-2 section) with a direct repro: set the row's `scrollLeft` to two different values (1 and roughly half its overflow) and compare the right chevron's measured distance from the row's own right edge at both — `git stash`-ing only the `AppHeader.jsx` fix and re-running against the unmodified pre-fix source reproduces the defect exactly (`a=3, b=40` — a 37px drift for a 37px scroll delta, i.e. the chevron moved in lockstep with the content instead of staying still); restoring the fix brings it back to `Math.abs(a-b) <= 1`. Full harness run post-fix: 63/63 checks green (up from the pre-existing 62, the one new check included), across the full adjacent-case matrix (touch targets, active-tab visibility, breadcrumb middle-truncation, live resize, both rows together) — no regression anywhere else the harness already covered.
