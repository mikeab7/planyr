`[x]` Merged the phone-only "‹ Notes" back link into the top of the compact formatting toolbar's own row instead of giving it a full-width band of its own.
- Verify: sandbox — a static layout/DOM change, fully provable headless under real iPhone-13 emulation with no auth/live-GIS/real-data/timing dependency; not a LIVE-VERIFY class.
- **THE DEFECT, exactly as reported and counted from his screenshot.** Drilling into a page on a phone stacked FOUR bands of chrome before the note title: (1) the app header, (2) the module tab row, (3) a new full-width band containing nothing but "‹ Notes", (4) the compact formatting toolbar. Band 3 bought one small link at the cost of an entire row — measured at 54px of the ~181px of chrome sitting above the title on a 390pt-wide screen.
- **THE FIX.** Band 3 is deleted outright. "‹ Notes" now renders as the FIRST item inside `NoteToolbar`'s own primary row (`NoteToolbar.jsx`), `position: sticky; left: 0` (wrapped with its divider in one flex item, `data-testid="notes-toolbar-back-pinned"`) so it stays put while the rest of the row scrolls sideways underneath it — no second scroll container needed, the row's existing `overflowX: auto` is untouched. It shares the row's 44px `big` control sizing, so it adds no height of its own (the row measures 55px either way) and never squeezes the formatting controls below 44px. `onBack` is a new prop threaded `Notes.jsx` → `NoteEditor.jsx` → `NoteToolbar.jsx`, passed only while `narrow` (`undefined` on desktop, where nothing renders and the toolbar's DOM is byte-identical to before — diffed directly, confirmed). The bin-"peek" reader (reading a binned note without restoring it) doesn't use this toolbar as its top chrome — it renders one read-only `NoteEditor` (and toolbar) PER PAGE in the cascade, so pinning Back there would duplicate it once per page — so its own existing single-row status bar ("Reading “X” from the bin…") gets the same merged-in Back link instead, narrow-only, same `backToList` handler. Both paths delete band 3; neither adds a second one.
- **MEASURED, not eyeballed — the exact numbers this item's own guard checks.** Pre-fix: `note-title` top = 181px, gap between the module tab row's bottom edge and the toolbar's top edge = 54px (band 3's own height). Post-fix: `note-title` top = 128px (53px less chrome above the title), gap = 1px (border only — nothing sits between the tab row and the toolbar any more).
- **THE ADJACENT CASE, checked rather than assumed.** Searched every other workspace for the same "list ↔ detail drill-in with a phone Back control" shape before deciding whether to extract a shared component now. `useNarrow()` (the shared 760px breakpoint hook this fix reuses) is used in exactly three places: Notes (this fix), `ModelApp.jsx`, and `FoodMap.jsx` — but the latter two only compact their OWN single-pane toolbar at narrow width (icon-only Undo/Redo, a narrower format picker); neither has a list+detail split or a Back control of any kind. Library — the one candidate the brief named — is currently a single, ALWAYS-two-pane view (folder tree rail + file list, unified since B662) with **no narrow-mode handling at all** (`grep useNarrow` in `src/workspaces/library/` returns nothing); it neither has this pattern nor is any in-flight backlog/roadmap item building one. **Conclusion: the pattern is not being repeated anywhere else today, so no shared "pinned mobile back" component was extracted** — building one now against a single real caller would be exactly the premature abstraction this repo's own engineering rules warn against. If Library (or anything else) later grows its own phone drill-in, extract `NoteToolbar`'s `backControl` shape (the sticky-span-plus-divider pattern) into `shared/ui/` at that point, not before. Library's own total absence of phone-width handling is a separate, real gap — not filed here, since it's a different symptom (no compaction at all, not a back-button chrome cost) and out of this item's scope; worth a session of its own if Michael wants Library usable on a phone.
