### B2244016 — A teammate opening a shared plan erased the owner's overlay pointers (an RLS refusal was healed as "file missing") `[Site Planner / persistence]` (bug) #site-planner #persistence #security #sync
`[x]` Shipped (NEW-1 of the 2026-10-11 sharing block, guard first, in its own PR as the brief required).
- **The mechanism, proven rather than suspected.** Supabase Storage answers an object the caller's RLS refuses with the same 400 "Object not found" as a genuinely missing one (`overlayStorage.classifyStorageError` maps both to "missing"). The rehydrate loop (`SitePlanner.jsx`, B785/B719777) then wrote `{ storageKey: null, storageMissing: true }` onto the record — inside `sites.data`, which a teammate may write on a shared plan (2026-08-09 decision). No storage policy let a teammate read a Site-tab overlay file in another account's folder, so simply OPENING the owner's shared plan erased the pointer in the owner's own plan.
- **It already happened (read-only census of production, 2026-10-11).** 13 overlay records carry `storageMissing: true`; all 13 are on shared plans. **12 of them still have their object in the bucket** (found by the overlay id the key embeds): Goose Creek ×6 owner plans + 1 teammate plan (all naming the one Master Site Plan PDF), Bain ×2 owner plans + 1 teammate plan, Richfield ×2 (teammate plan). The 13th (Woods Road `smsrrlk9u576`) is the genuine 2026-08-13 deletion and was healed correctly. **Nothing was repaired** — Goose Creek and Bain are off-limits to sessions; the restore is an owner decision (OWNER-TODO, `site-planner/db/overlay_pointer_restore_proposal.sql`, read-only by default).
- **Fix.** `lib/overlayHeal.js`: a heal is persisted ONLY for a confirmed-missing object in the reader's OWN folder (the own-folder policy always admits it, so there "not found" really means gone). Any other folder, no uid, or a malformed/path-trick key records the new terminal reason `denied` ("shared file not readable from this account · click to retry") and leaves the record untouched.
