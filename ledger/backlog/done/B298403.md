`[x]` **✅ DONE 2026-08-09 — normalised at every read and every write, the two production rows migrated, and a server-side trigger so the class cannot come back.**
- Verify: sandbox — unit-tested here, and the production migration was applied and re-queried in the same session (40 `harris`, 0 `Harris`).
- Origin: filed 2026-08-09 from chat; shipped the same session.
- **THE REPRO, CONFIRMED AGAINST PRODUCTION.** `select county, count(*) from public.sites group by 1` returned **38 `harris` and 2 `Harris`** (capital H, last written 2026-07-04) — and both the `county` COLUMN and the serialized model's `data->>'county'` carried the capital. `county` is used as an OBJECT KEY throughout (`COUNTIES_MAP[county]`, `COUNTY_DISTRICT[county]`, `defaultJurForCounty(county)`, `statewideFallbackFor(county)`, and now the baked-flood-tile archive pick), so those two plans missed every one of them.
- **⛔ WHY IT WAS INVISIBLE, WHICH IS THE WORST PART.** A missing object key is `undefined`, not a throw — and **every one of those call sites has a `|| fallback`**, so the miss rendered as a confident wrong answer. `defaultJurForCounty("Harris")` returned `"generic"` instead of `"coh"`, i.e. those two Harris plans were quietly using generic easement rules instead of City of Houston's. No banner, no dot, no telemetry. This is precisely the LOUD-FAILURE class.
- **⛔ THE FIX IS AT THE MAPS, NOT AT THE CALL SITES, and that is deliberate.** Patching call sites one at a time is HOW this class existed: `defaultFloodJurForCounty` already lower-cased and `defaultJurForCounty`, in a sibling module, did not. So `shared/gis/countyKeys.js` wraps the county-keyed config maps themselves (`COUNTIES`, `COUNTIES_MAP`, `JURISDICTION_LAYERS`, the two statewide county-name tables, `SNAPSHOT_COUNTIES`) in a normalising accessor — **no lookup can miss, including one written next year by someone who never reads this item.** `Object.keys` / `entries` / `in` all behave exactly as before; only a key absent under its literal spelling but present under its normalised one changes.
- **⛔ WHITESPACE IS REMOVED, NOT TURNED INTO AN UNDERSCORE, and that is a decision about THIS vocabulary.** The underscore in a routing key is a STATE PREFIX separator (`co_larimer`), never a word separator — this app keys the two-word counties `fortbend` and `sanjacinto`, run together. So `"Fort Bend"` normalises to `fortbend`; mapping the space to `_` would produce `fort_bend`, a key that exists nowhere, and would silently reintroduce the exact miss being closed. (The first version of the normaliser did that, and the test caught it.)
- **THE WRITE SIDE TOO, at three gates.** `createSiteModel` (the funnel every record passes through — a localStorage load, a cloud row, an import, every save-merge) · `cloudSync.siteRowFor` (the last gate before the `county` column, for a header-only path that never round-trips the model) · and a **server-side `BEFORE INSERT OR UPDATE` trigger**, so an import, a hand-edited row, a client that predates this fix, or a psql session cannot recreate it.
- **THE MIGRATION, APPLIED.** `db/sites_county_normalize.sql` — an immutable `public.norm_county_key(text)` mirroring the JS, the two rows fixed in **both** the column and the jsonb blob (normalising the column alone would leave the model still holding `Harris` on the next open, which is the lookup that was failing), and the trigger. **It is a TRIGGER, not a CHECK constraint, on purpose:** a CHECK would REJECT a mixed-case write, turning a silent wrong answer into a hard save failure for the user; normalising is the behaviour actually wanted, because the key means the same thing either way. **`updated_at` is deliberately NOT bumped even on the rows it changes** — it is the CAS input the optimistic-concurrency layer compares against, and a housekeeping rewrite that moved it would hand every open tab a spurious "changed in another session" conflict on a field the user never touched. Re-queried after applying: **40 `harris`, 0 `Harris`.**
- **A NICE SIDE-EFFECT WORTH RECORDING:** the repo's own e2e fixture `e2e/fixtures/sites/dense-testfit.fixture.json` carried `"county": "Harris"` and regenerated to `"harris"` on the next `node scripts/build-fixtures.mjs`. The bug was in the test corpus too.
- **GUARD.** `test/countyKeys.test.js` (36) — the normaliser, the map/set wrappers, and the brief's own acceptance test (*"a mixed-case county key still resolves its source set"*) asserted against the **REAL config maps**, not a fixture, because the bug was never in a normaliser — it was in the maps not using one. Both write gates are pinned by value.
