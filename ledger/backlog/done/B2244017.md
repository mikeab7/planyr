### B2244017 — Sharing a project shares its overlays and comps: anyone who can open a shared plan can see and load every overlay on it `[Site Planner / sitePlans / comps / database]` (bug) #site-planner #comps #security #auth
`[x]` Shipped (NEW-1 of the 2026-10-11 sharing block; owner constraint #21). Owner, 2026-10-11: *"if I share a site with someone, they should have access to all the overlays that I have as a default."* 2026-10-05: *"if I have a project … and there's like comps attached to it or overlays, those should all be visible."* Reviews deliberately unchanged (still undecided — OWNER-TODO).
- **Measured before building (production, read-only).** Site-tab overlay files live under the uploader's folder; the bucket's read policies were own-folder, `can_read_shared_review_file` (review sources) and `can_read_shared_site_plan_raster` (Map/Comps rasters by their own `team_id`). None covered a `sheetOverlays` file, so a teammate on a shared plan saw the records and every image failed — which also drove B2244016's pointer erasure.
- **Fix — additive SELECT policies, derived, no row rewritten** (`site-planner/db/project_follow_sharing.sql`, applied 2026-10-11). (1) `can_read_shared_site_overlay_file`: readable when the caller can read a LIVE plan naming that exact key AND the key's origin plan exists, is readable by the caller, and its uploader is that plan's owner or on its team. Same predicate as the plans table's own SELECT policy, so "can see the plan" and "can load its overlays" cannot disagree; a binned plan grants nothing. (2) `can_read_via_project(project_id, row_owner)`: Map/Comps overlays and comps are readable by anyone who can read a live plan of the project (group of the referenced plan, plans owned by the project's owner) — and only if the row's owner also holds that plan. (3) `can_read_project_site_plan_raster`: the raster of such an overlay, bound to the overlay owner's folder. No `team_id` changed; `guard_team_share` untouched; unshared stays private.
- **Adversarial review (subagent), findings + responses:** #1 HIGH plan-id squatting (client-chosen `sites.id` matching a purged origin folder) → uploader bound to the origin plan; #2 MEDIUM purged-origin fallback let a teammate expose the owner's orphaned files → fallback removed (0 live shared keys rely on it); #3 LOW id-existence oracle → closed by #2; #4/#5 LOW fail-safe "visible but not loadable" for a sibling copy from a private plan / a teammate-uploaded file truly gone → left, reads "denied, retry"; #6 heal guard only stops ACCIDENTAL erasure (an editor can always edit) → by design; #7 comps follow the whole project group → intended (sharing is per project); #8 perf negligible. Plus B2244018 (two pre-existing forgeries found on the way).
