DEDUPE-FIRST — searched Open + ⏳ Verify + Done across `siteRouteChunks`, `prefetch`, `lazy`, `boot`, `rasterIdentifyLazy`, `featureHoverAttach`: **B1041** removed the boot-time idle PREFETCH (a different mechanism — an explicit warm call), **B1130/B1131** created these very splits, **B1163** is the harness's allowlist defect, **B1064** owns the byte total. Nothing covers these chunks being fetched at mount despite the split. Net-new.)*
- `floodZoneCopy` · `rasterIdentifyMap` · `rasterIdentify` · `featureHover` · `terrainLayers` — the five modules B1130/B1131 deliberately moved OFF the boot path to get back inside the bundle ceilings — are **requested during boot anyway**. Measured on a fresh load of the reference plan with **no gesture at all** and four seconds of idle: all five are already in flight. The same list appears whether the harness snapshots before or after its scripted gestures, and `lazyChunksAfterBoot` measures **empty**, so this is not the instrument's timing.
- The static analysis is CLEAN and stays clean — `bundle.siteRouteChunks` is 7, and the manifest shows no static edge from the boot path. This is a RUNTIME `import()`, which is exactly the class the runtime half of the harness exists to catch, and it is catching it.
- CDP initiator traces put all five behind React effects running at mount (`SitePlannerApp`), not behind a user action. The likely mechanism: a layer that is ON by default at mount drives `syncOverlayLayers` → the hover/identify attach → the dynamic import. If so the split still holds for a user who turns everything off, and buys nothing for the default case, which is every user.
- **Why this matters beyond tidiness:** B1130's own justification for raising a ceiling was that these modules had been moved off the boot path. If they load at boot anyway, that justification does not hold as stated.
- Fix shape: defer the hover/identify attach until the first hover over a layer that needs it (the `rasterIdentifyLazy` pattern already does this correctly for the raster half — `ensureRasterHover` builds on first need). Keep the honest "not yet" first-rest behaviour.
- Guard already in place: `runtime.siteRouteChunks` in `ui-audit/perf-harness.mjs` FAILS on this today, by name. Do not widen the allowlist to make it pass.
`[~]` **SHIPPED 2026-07-31 — FOUR of the five are gone. The fifth is not an accident and is flagged below.**
- **FIXED — `floodZoneCopy`.** `LayerPanel` imported it from a bare `[]` mount effect, and the map finder's panel mounts at boot on a desktop width even while the planner is the visible workspace. It now loads when there is something for it to say (`floodContext?.flood?.state`), which is EXACT rather than a heuristic: `femaZoneVerdict` returns null for anything without `flood.state`, so every case now skipped rendered nothing anyway.
- **FIXED — `rasterIdentifyMap` + `rasterIdentify` + `featureHover`.** All three came from ONE call: `attachRasterIdentifyLazy` in `MapFinder`'s map-setup effect, which kicked off the import at mount (`featureHover` is their shared dependency, not a fourth trigger — CDP initiator traces, not inference). It now arms on the first `pointermove` / `pointerdown` / `wheel` over the map container, the `ensureRasterHover` pattern the planner half of this feature already used correctly. No behavioural gap: the identify only ever answers after the cursor RESTS, and the chunk lands within the first move of a hover.
- **PROOF, on the build where it reproduces every time:** idle page, no gesture, six seconds — before: `featureHover floodZoneCopy rasterIdentify rasterIdentifyMap terrainLayers` all in flight; after: none of the four.
- **⚠ IT IS A BOOT-ORDER RACE, not a constant.** On a fast build the finder's Leaflet map is sometimes never created before the planner takes over, and the four are never fetched at all; on a slow one they always are. It is therefore **worst on a slow machine, which is the owner's machine.** The instrument that was supposed to catch it had the same race and could silently pass — **B1358**.
- **⛔ NOT FIXED — `terrainLayers`, and this is a PRODUCT DECISION, not an oversight.** It is pulled by `checkDrainage({ auto: true })`, the **load-time drainage revalidation B860 deliberately designed**, firing on a timer after load on a plan with no cached snapshot. So it is on the boot path BY DESIGN, and B1130's "moved off the boot path" was only ever true for a plan that already has a fresh drainage snapshot. **The allowlist was NOT widened** and the guard stays red on it. What shipped instead is a **timing** change, not a behaviour one: a LOAD-kind auto-check now additionally waits for a genuinely idle main thread (`requestIdleCallback` with a hard 4 s timeout, so B874's "the attempt ALWAYS fires" invariant is preserved exactly). The 1,200 ms delay was chosen as "after boot", and on a 4x-throttled profile boot is not finished at 1,200 ms — time-to-first-drag measures ~4.4–7 s. **Michael's call:** should the drainage facts pass run automatically on load at all, given it costs a chunk plus several GIS fetches during the window he describes as sluggish? **Logged on `OWNER-TODO.md` as the one decision this item is waiting on** — the item stays Open until he answers, and it is a taste call about the first few seconds of opening a plan, not a defect. **⚠ SUPERSEDED 2026-08-06 — HE ANSWERED IT: manual only, shipped as B1442. Do not read the sentence before this one as an open question, and do not put it back on his list.** See the two blocks at the end of this item.
