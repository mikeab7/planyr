### B2584496 — Schedule grid: on a selected / hovered row the line under the frozen ID and Task cells looks different from the rest of the row (thinner and greyer vs heavier and bluer) `[Scheduler]` (bug) #scheduler #ui  *(owner chat block NEW-1, 2026-11-03, from a screenshot of Grand Port / Groundbreaking Path, Schedule › Grid, planyr.io; a Needs Attn. row selected by clicking its Dur cell. AMENDS B2623536 / PR #2792 (marker crosses ID and Task) and keeps B2618896 / #2790 (fills run edge to edge). Same symptom family as B2279024 and B2623536; filed under a new B# at the dispatcher's instruction, cross-referenced.)*
`[ ]` **MERGED — V2033552 PENDING (a live check on the deployed build is the closure; see the Verify line).**
- **What he saw.** "The task column gets a weird outline that doesn't match the rest of the cells." Expected: one continuous line, identical in colour, weight and vertical position, ID through Task and on to the right, no visible change at the Task / Start boundary.
- **Reproduced first (build 879a557), and what it is.** The existing painted harness (`verify-grid-filler-row-marker`, 63/63 green) could not see it: it reads ONE pixel per edge, at device pixel ratio 1, with the Start cell clicked. Reading the whole edge at several ratios: **the marker pixel itself is the same colour on every cell; the grid-line pixels BESIDE it differ.** The line is a `::before` in each cell and the grid line is each cell's own border; a frozen (sticky, opaque) cell rasterises that border differently from a plain one wherever the device pixel ratio is FRACTIONAL (browser zoom 125 / 150 / 175 %). At ratios 1 and 2 the row is byte-identical (ΔE00 0.00), which is why it is nearly invisible at lower zoom. On the unfixed page: ID / Task differ from a date cell by up to ΔE00 2.8 on a single pixel row, the frozen right-hand Health cell by up to 5.8; the repo's blurred "perceived" bar is MET (0.66), so a blurred metric alone cannot see it — the single-pixel bar is the one that does.
- **Hypotheses MEASURED AND REFUTED, so nobody re-hunts them.** (1) Stickiness alone: forcing every cell to `position:relative` left ID / Task different. (2) The frozen cells' opaque fill alone: a transparent fill fixed ratio 1.5 only, not 1.25. (3) z-index / the fill's gradient layer: no change. (4) A fractional vertical origin of the scroller or rows: snapping row tops to whole device pixels changed nothing to the decimal (Chrome already snaps them). (5) Clipping the fill to the padding box: made it worse.
- **Fix (`public/sequence/index.html`).** The marker is now ONE `::after` on the ROW (hover, selected task row, focused "+ New task"), `z-index: 6` — over the sticky ID / Task / Health cells (5), under the sticky header (10). Same 1px #94a3b8 line in the same place as before; plus a `box-shadow` that re-draws the grid line (`var(--bd)`, the same colour) in the pixel above and below it, so those pixels come from this one element on every cell. At fractional ratios the band is 2 px deep (2.5 px at 150 % and 250 %, empirical, re-measured by the harness); whole ratios keep 1 px. A row inside a multi-row range keeps only the marker (`:has(> [data-cell-in-range])` → no band) so the range's blue shared edge is not turned grey. The per-cell `::before` rules are gone; the markup is unchanged. Alternatives tried and rejected: a marker drawn ON the grid lines (`top:-1px`) hid the first row's top line under the header and turned range edges grey; an inside marker with no band left ID / Task at the old difference.
- **Sandbox proof (red/green).** NEW `ui-audit/verify-grid-row-marker-uniform.mjs`: real Chromium contexts at a true device scale factor (0.8 · 1 · 1.25 · 1.5 · 1.75 · 2 · 2.5 by default; any list via `DPRS=`), the owner's case (Needs Attn. row, Dur clicked) plus plain / Complete / summary / first / blank / "+ New task" rows, hovered and selected, scrollLeft 0 and 300; a strip of the top and bottom edge under ID, Task and a date cell must agree on EVERY pixel to CIEDE2000 1.0 (the just-noticeable difference, fixed before any candidate was measured) and meet the repo's detail ≤ 6 / perceived ≤ 1.0 bars; known-good + negative arms and a scale guard VOID the run rather than score it. **Unfixed page: 1/25 at every fractional ratio (0.8: 1/13), 25/25 at 1 and 2. Fixed page: 13/13 at 0.8, 25/25 at 1, 1.25, 1.33, 1.5, 1.67, 1.75, 2, 2.25, 2.5, 3.** The honest residual: ratio 1.1 and the owner's own 2.15 each leave ONE state (a pixel at ΔE00 1.15 against the 1.0 bar; 23/25), so it is "at the threshold of visible", not zero, at those two ratios — see the Follow-up. The harness's frame-mean limit (0.10) is deliberately not used: it is defined for whole frames and is meaningless on a 20 × 6 pixel strip. CI half: `test/scheduleRowMarkerOneElement.test.js` (structure + the harness's own guarantees); `scheduleRowOutline`, `scheduleGridStrip`, `scheduleRowMarkerFillerRows` rewritten to the row-level structure. Existing painted harnesses on the fixed page: `verify-grid-filler-row-marker` 63/63, `verify-grid-row-outline` 158/158, `verify-grid-strip` 39/39 (its "is this row lit" read now looks at the row's `::after`), `verify-grid-full-lines` 229/229.
- **Follow-up, owned here and not dropped.** The residual single-pixel ΔE00 1.15 at ratios 1.1 and 2.15 is the neighbouring row's frozen-cell fill edge, a raster property of a sticky layer, not of the marker. Closing it to zero would mean the frozen columns stop being per-cell sticky layers (a frozen pane), which is a grid architecture change and is NOT done here.
