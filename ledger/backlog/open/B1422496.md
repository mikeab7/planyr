**THE DESIGN CHOICE, stated plainly (task step 1).** Picked **Option 1 — append automatically, in a sensible slot** — over a "N new cards available" affordance or a full catalog-version scheme. Reasoning: a card is entirely self-explanatory once it's on screen (it has its own title and content — nothing about it needs a banner to make sense), so the affordance route would just be extra chrome for something the card itself already communicates; and Michael's own complaint was literally "I never saw it," which auto-append answers directly with zero new UI. **What it does to a user mid-session:** nothing, until their next visit. The layout (and its reconciliation) loads once per Dashboard mount (`Dashboard.jsx`'s own `useEffect(..., [userId])` — this predates this fix); a card that ships while someone already has the Dashboard open appears the next time they open or reload it, the same way any other deployed change here needs a reload to be seen (see this repo's own chunk-hash staleness note in `CLAUDE.md`'s Workflow section) — not a new gap this fix introduces.

**HOW IT WORKS.** `dashboardLayout.js` gains a `dismissed` concept — the list of catalog cards an account has deliberately removed — alongside the existing `layout` array, persisted as a sibling key (`dashboardDismissedCards`) in the same `profiles.prefs` jsonb row `dashboardLayout` already lives in (no new migration, same pattern the file already used for `dashboardLayout` itself). `newCatalogCards(layout, dismissed)` is every `CARD_DEFS` key that is **neither currently placed nor dismissed** — DEFAULT_ORDER for a deterministic, sensible append order; `appendNewCatalogCards` adds each one via the *same* `addCard` a manual "Add a card" click already uses (own default size, appended below whatever's on the grid), so an auto-reconciled card behaves identically to one the user added themselves and **existing cards' x/y/w/h are never touched.** `dashboardPrefs.js`'s `loadDashboardLayout` runs this reconciliation on every load (cloud row AND the signed-out localStorage mirror), before the layout ever reaches `Dashboard.jsx` state — the existing 900ms-debounced save effect (unchanged) then persists the appended card back on its own, no new plumbing needed. Removing a card (`Dashboard.jsx`'s `onRemove`) now also calls `dismissCard`; re-adding one from the picker calls `undismissCard`, so a later removal is a fresh, freely-reachable decision rather than reusing a stale record; Reset layout clears `dismissed` entirely (matches its own full-catalog result).

**HOW A REMOVED CARD IS TOLD APART FROM A NEVER-SEEN ONE (task step 3).** By that persisted `dismissed` list, keyed by the card's own stable `CARD_DEFS` key — the same key-stability guarantee `compsSummary`'s own code comment already relies on ("the KEY stays `compsSummary`... so every account's already-saved layout keeps placing this card without a migration") cuts both ways: a stable key is what makes a stable removal decision possible. The one place this needed real care is **bootstrap** — an account saved before this shipped has no `dismissed` list at all, and defaulting that to *empty* would treat every already-missing catalog card as brand new and silently resurrect anything that account had ever removed, which is exactly what rule 3 forbids, with no way to tell, from the layout alone, which historical absence was a removal and which was a miss. So `normalizeDismissed(raw, layout)` bootstraps the OPPOSITE way: `raw === undefined`/`null` (never recorded) seeds `dismissed` as *every* catalog card currently missing from that layout — i.e., a legacy layout is left exactly as it was the moment this first runs for that account, not retroactively changed. From that point on, `dashboardDismissedCards` is a real, explicit, persisted list (written on every subsequent save, even when empty), so **every card added to the catalog after this ships is new to every account, and reaches every saved layout the same way, indefinitely.** The honest cost of that bootstrap: this fix does not itself retroactively re-add the four already-shipped cards to any OTHER pre-existing legacy account (Michael's own account needed no such rescue — it already holds all ten, added by hand before this shipped) — attempting to guess which of an account's already-missing cards were "never seen" vs. "removed on purpose" is exactly the guess rule 3 says must never be made in the resurrecting direction.
