- **HIS READING, which is the whole diagnosis.** Same point (673,414), nothing selected, `grips === 0` in both states — only the stack differs: after touching the POND, `target el:e79463haroul`, stack `["el:e79463haroul"]`; after touching the STUB, `target parcel:e79379lfxyni`, stack `["parcel:e79379lfxyni", "el:e79463haroul"]`. **The parcel does not move above the stub — IT ENTERS. The stub is still there, second, unchanged.**
- **⛔ AND IT IS NOT THE DOM, which he ruled out directly:** the stub's node is index 99 of 521 in BOTH states, computed `pointerEvents` is `"auto"` on the node AND its parent in BOTH, same total node count. Not paint order, not re-parenting, not a pointer-events flip on the stub. **The parcel BECOMES hit-testable.**
- **THE CAUSE.** The acreage badge renders `pointerEvents={draggable ? "auto" : "none"}` where `draggable = tool === "select" && hoverChipId === pc.id`. **`hoverChipId` is a HOVER latch** — B1327/NEW-4 moved the gate from selection to hover precisely so the badge could be dragged (the selection gate was unreachable: the badge sits at `polylabel`, on top of a building, so pressing it selected the building and the lot never became selected). But **a cursor resting on a point is exactly what a cursor does between the two presses of a double-click.** So the badge arms itself mid-gesture, and because it paints after the element bands it wins the hit test — over a feature smaller than its own chrome, there is nothing else to win it. That also explains every discriminator: the pond click **moves the cursor away** and disarms it; a six-second wait does not, because the cursor never moved.
- **THE FIX — the badge is a GRIP, so it is identity-transparent, exactly like the handle layer.** New `data-chrome` marker (`lib/featureTarget.js` `CHROME_ATTR`), flagged by `stackEntries` alongside `data-handle-layer`, so the resolver looks THROUGH it. **DELIVERY IS UNTOUCHED:** the badge keeps its own `pointerEvents`, its own `onPointerDown` and its own drag — only "which feature was double-clicked" changes, the same B233153 rule one layer out. The lot is still reachable by its own body underneath, so double-clicking a lot still opens the Parcel panel.
- **REPRODUCED, then proven both ways.** Sandbox fixture: a lot whose `polylabel` puts its badge on a 6-px road stub. Pre-fix the stack reads `["parcel:zzlot", "el:zzstub"]` and the gesture selects the lot; post-fix both gestures read `["el:zzstub"]` and open Properties. **The audit row he predicted goes RED on cf4f77b** and names the cause in its own message — *"with the cursor merely hovering, this point resolves to parcel:zzlot1 instead"*.
- **THE GUARD — a HOVER-ARMED-CHROME invariant, run for every feature.** Park the cursor on the probe point, let it arm whatever it arms, and re-ask the resolver: it must still name this feature. **Nothing in the suite read the DOM after a plain HOVER before** — every other check reads after a click, which is why this was invisible.
