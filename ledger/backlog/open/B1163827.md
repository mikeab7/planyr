- **ROOT CAUSE, confirmed by reading the exact source (a dedicated research pass, not guessed) — THREE genuinely disjoint stores, none of which write or invalidate each other:**
  1. `gisCache["analysis:flood:<ringsSig>"]` (`lib/siteAnalysis.js`'s `analyzeSource`, `cache.swr`) — Analysis panel ONLY. 7-day TTL. Keyed on a per-ring intersect signature. Its `ageMs` is the "1m ago" the Analysis panel shows.
  2. `gisCache["vec:fema:<bbox>"]` (`lib/vectorLayers.js`'s `vectorKey`, called from `checkDrainage` at `SitePlanner.jsx`) — the Yield/drainage panel's own FETCH cache. 30-day TTL. Keyed on a bbox of active parcels/fill elements — a DIFFERENT key shape hitting the SAME NFHL layer 28, that never warms or invalidates entry #1 or vice versa.
  3. `settings.drainage.lastCheck` (persisted in the SITE MODEL, autosaved to Supabase — `SitePlanner.jsx`'s `slimDrainageContext`/`hydrateDrainageContext`, `lib/detentionRules.js`) — this is the ONLY thing the Yield header's own "checked/stale/age" readout (`floodChecked`/`floodAgeMs`) actually reads. Its `checkedAt` is the "30d ago" the Yield header shows. Nothing in `runSiteAnalysis` (the Analysis panel's engine) ever writes to this record, and nothing in `checkDrainage` ever writes an `analysis:` cache key — so running the Analysis panel's screen cannot make the Yield header any fresher, BY CONSTRUCTION, no matter how recently it fetched.
- **WHY THIS IS GENUINELY TOO LARGE FOR THIS SESSION, not a convenience judgment:** unifying these three requires either (a) making `checkDrainage`'s flood fetch consult/seed from Analysis's `analysis:flood:<ringsSig>` cache entry when it's fresh (which needs reconciling two DIFFERENT query shapes — a per-ring intersect vs. a bbox pull — and confirming the ring-based answer actually carries what the BUILDING-level mitigation math needs, which it may not: Yield needs raw zone GEOMETRY for footprint intersection, Analysis only needs a boolean per-ring verdict), or (b) making `settings.drainage.lastCheck`'s freshness readout also consult Analysis's cache timestamp and take the newer of the two for DISPLAY purposes (safer, but still needs careful handling of the "is the underlying DATA the same, or just coincidentally both fresh" question — a state Analysis fetched with different geometry inputs is not necessarily the SAME answer Yield needs). Either shape touches the heavily-guarded drainage/mitigation engine this repo's own `CLAUDE.md` documents at length (`pondLedger.js`, `detentionRules.js`, `floodplainMitigation.js` — real financial/engineering numbers a real construction project is priced against) and needs dedicated live verification against a real project, which this session's remaining budget (already spent on B1163824-B1163828 in the same block) does not allow to do safely.
- **A PLAN, so this isn't a bare stop:** (1) pick ONE shared "last flood fetch" timestamp source — likely promote `settings.drainage.lastCheck`-style persistence to also be written by `runSiteAnalysis` whenever it fetches, OR extract a single shared "site flood freshness" reader both panels call; (2) decide whether Yield's drainage fetch can OUTRIGHT SKIP a re-fetch when Analysis's same-geometry entry is fresh (saves a redundant NFHL call) or should merely display the OLDER of its own state and Analysis's, being explicit that "fresher elsewhere" doesn't mean "this panel's specific query is answered"; (3) live-verify on a real project (Goose Creek Plan II is the standing repro) that running ONE panel's re-check visibly updates the OTHER panel's freshness line without a full page reload.
