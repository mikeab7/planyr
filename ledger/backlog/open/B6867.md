- Verify: live

- **NOTHING IS BYPASSED AND NOTHING IS DISABLED.** The required check stays required; no PR is merged whose build has not actually passed. Every one of the seven was failing `check-mint` on a real (if wrongly-specified) rule — so the fix is to correct the rule, not to wave the PRs through.
- **⚠ CORRECTED THE SAME SESSION, AND THE CORRECTION IS THE USEFUL PART. The first version of this item said "no rebase is needed — one re-trigger each". That is WRONG, and it was TESTED rather than assumed, which is the only reason it was caught.** All four re-runs (#931, #932, #933, #934) fired within minutes of B6866 reaching main and **all four failed again**, with the message `B9001 is at or below the claimed high-water mark B209509` — wording the corrected gate **no longer contains**. Proof, not inference: **a re-run replays the merge commit the run was created against; it does NOT recompute `refs/pull/<n>/merge` against main's current tip.** So a re-run faithfully reproduces the old failure and reads as "the fix didn't work", when the fix was simply never in the tree being built. This is the same class of error as Stage B in B6864 — a mechanism assumed from how it *ought* to behave rather than measured — and it survived one round of review here before the test refuted it.
- **WHAT EACH STUCK PR ACTUALLY NEEDS IS A NEW PUSH.** Any new commit makes GitHub recompute the merge ref against main's tip, and that build runs the corrected gate. Prefer `git fetch origin main && git merge origin/main` over an empty commit — it also puts the corrected `check-mint.mjs` into the branch, so the pre-push hook and CI agree. Expect a `BACKLOG.md` conflict (main's copy moved); resolve by keeping both sides' items and **renumber nothing**. Then **wait out the ~30-minute lag before concluding anything** — a PR reading `Expected` for the first half hour is normal. That last sentence is the one that would have prevented six renumbers.
