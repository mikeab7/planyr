**WHY IT IS HIDDEN, not just how to show it — investigated at length, and reported honestly rather than guessed at.** The mechanism's own two safety valves — (1) the layout effect succeeds the instant `active` is true, the document is visible, and the container has a real box, and (2) failing that, an UNCONDITIONAL 1.5s watchdog that does not even check the container — mean `framingCommitted` can only stay `false` past 1.5 seconds while `active` and `document.visibilityState === "visible"` are NOT continuously true for that whole window (the owner's own ancestor-visibility measurement rules out the coarse CSS `display:none` cases, though not a `React` prop value disagreeing with them). The dispatch's own leading hypothesis — the sub-pixel transform suggesting "hidden during a map-registration settle" — was checked and is **not what is happening**: that transform (`regShift.dx/dy`) comes from an entirely separate, pre-existing registration effect that runs independently of `framingCommitted` and was already computing real values, meaning the rest of the component's effects were running normally; only this one flag never flipped.

- **A real, provable code weakness was found and fixed as defense-in-depth, though NOT confirmed as the exact trigger:** `SitePlannerApp.jsx`'s `applyUser` — the function that runs the signed-in cloud pull + resume + `loadEpoch` bump this whole mechanism rides on — de-duplicates repeat auth events by comparing against `prevUid.current`, but only WROTE that marker at the very end of a long multi-`await` function. `@supabase/auth-js`'s own `GoTrueClient` (installed version 2.108.1, read directly from `node_modules`) can legitimately deliver more than one auth event for the same resumed session close together — `_emitInitialSession` fires the instant a NEW listener subscribes, independently of `_recoverAndRefresh`'s own later `SIGNED_IN` broadcast for a session that does not need a token refresh. A second such event arriving before the first call's end-of-function marker write landed read the dedup guard as "not a duplicate" and could re-run the whole pull+resume+`setLoadEpoch` sequence, force-remounting the keyed planner (``${activeSiteId}:${loadEpoch}``) a second time mid-boot — exactly the mechanism 453623a's own commit message names as this bug's trigger, just with a path to fire MORE than once. **Fixed:** the marker is now stamped synchronously, immediately after the dedup check passes, before any `await`.
