`[x]` **MEASURED ON PRODUCTION** (owner's signed-in Chrome, window backgrounded at the OS level, two readings hours apart on two different served chunks — `SitePlannerApp-D8RPy4VN.js` and `-yp5pQfwb.js` — with the chunk hash read in the same observation as the result): canvas computed `visibility: visible`, aerial imagery painting across it, `data-view-ppf/-offx/-offy` = `0.35 / 60 / 60` (the `useState` boot default), and all three `[data-el-id]` elements at `x 1195..1405` against a canvas box of `x 54..1023` — **every element outside the canvas**. `elementFromPoint` at an element's own centre returns `null`. `[x]` **Reproduced in the sandbox** at 1280×900 on a 66-element fixture, on reverted `main` AND on pre-`453623a`, byte-identical: hidden boot → ppf `0.35` off `(60,60)`, elements at `x -350..-205` etc., all `inView: false`. Foregrounded cold load on the same builds → plan on screen, ppf `0.1064540557003681`, hit-testable. **Hidden-boot only.**

`[x]` **ROOT CAUSE:** `SitePlanner.jsx`'s `fitReq` effect asks `mayFrame(..., { visible: isVisible() })`, which correctly returns `document-hidden` and correctly treats it as a "not yet" — but the retry is `requestAnimationFrame(poll)`, and rAF is suspended in a hidden tab (the owner's own diagnostic measured **zero rAF callbacks in 6295 ms**). A retry that only runs once the tab is already foregrounded cannot recover a tab that is not. This is the rAF-chained deadline the original dispatch brief hypothesised — on the retry path, not the watchdog.

- **The fix, and what it must NOT be:** do not re-introduce `framingCommitted` or any hide-until-ready gate (see `docs/incidents/B1594320-CANVAS-VISIBILITY-OUTAGE.md`, which requires a remount-surviving ceiling and a signed-in live pass first). The minimal forward fix is to stop using "is the tab frontmost" as a proxy for "is the container measurable" — the raw rect answers that directly — and to drive the retry off `visibilitychange`/`pageshow`/`focus` plus a wall clock rather than off rAF.

`[x]` **FIXED — two changes in `SitePlanner.jsx`'s `fitReq` effect, no hide-until-ready gate.**
1. **"Is the tab frontmost" is not the readiness question — "is there a real box" is.** The container is read directly and a raw non-degenerate rect (`r.width > 1 && r.height > 1`) is the verdict, replacing `visible: isVisible()`. `getBoundingClientRect()` is layout-accurate in a tab that is merely not frontmost — production measured a real **969×408** while hidden, and later **x 54..1023 / y 56..464**. What B1234400 actually caught was a container that had NEVER BEEN LAID OUT, reporting a degenerate box that the `Math.max(320, …)` floor then dressed up as a plausible 320×360; the raw-rect test refuses exactly that, directly. **Keeping the proxy is what forced reliance on a rescue at all.** `fit` regained its optional freshly-measured `box` argument so the framing is computed from the box just read, never from the placeholder `size` state.
2. **The retry runs on wake events and a bounded wall clock, never on rAF** — `visibilitychange`, `pageshow` (bfcache restore) and `focus` re-ask directly, plus a bounded `setInterval`. Nothing between boot and framing can be suspended by a throttled frame loop.

`mayFrame`'s OWNERSHIP check is untouched and the ticket still travels to the execution, so a user gesture during any of this still cancels the framing exactly as before.

`[x]` **VERIFIED.** `verify-boot-framing.mjs` — hidden arm now `ppf=0.0831` off `(283.9, 340.2)`, `elementFromPoint` resolves to the element, all **before the arm foregrounds anything**; exit 0 (it exits 1 against the unfixed build with production's exact readings).
