- **⛔ WHAT THIS IS BOUND TO, ANSWERED DIRECTLY, BECAUSE IT IS THE QUESTION THE ESCALATION TURNED ON.** The brief asked for a handle on the real Leaflet map instance with every view mutator patched (`setView`, `setZoom`, `zoomIn/Out`, `setZoomAround`, `fitBounds`, `flyTo`, `flyToBounds`, `panTo`, `panBy`, `invalidateSize`). **That was NOT done, and it is not a fallback to a DOM proxy either — it is a third thing, and the reason is a measured property of this codebase rather than a preference.** The instrument binds to the app's own `setView`, capturing a real `new Error().stack` at every call plus the view before and after. **Leaflet is not a second opinion here: the planner creates it with `dragging: false, scrollWheelZoom: false, doubleClickZoom: false, boxZoom: false, keyboard: false, touchZoom: false, tap: false` — it cannot originate a view change at all**, and every `map.setView`/`map.panBy` in the file is downstream of the app `view` state this recorder already sits on. Patching it would have produced a fourth instrument reading a mirror. **No DOM-derived proxy is used for any verdict in this item** — not the scale bar, not tile `z`, not `getBoundingClientRect`. Every number here comes from the app's own state transitions.
- **⛔ WHY THE TWO PREVIOUS LIVE PROBES READ NOTHING, and it is structural rather than bad luck — this is the finding that unblocked the whole hunt.** Two attempts to observe this on the owner's own browser both came back empty: one polled `.leaflet-control-scale-line` across a cold load and read 20 mi on all 95 samples **including during a deliberate trusted wheel-scroll**; the other polled the first `img.leaflet-tile`'s `z` path segment and read z10 on all 110 samples, same story. Neither registered a zoom that was actually performed. **THE PLANNER'S ZOOM IS NOT LEAFLET'S ZOOM.** The user's view is an app-level transform (`view = { ppf, offX, offY }`) and the Leaflet basemap is a SLAVE that mirrors it — moved for most gestures with `map.panBy` at a FIXED Leaflet zoom level and re-based to a new level only past ~0.75 levels of drift (the B933 anti-flash core). So a whole pinch can run, the drawing can scale on screen, and both the scale bar and the tile `z` can hold their value the entire time. **A DOM proxy derived from the basemap cannot see this at all.** Bind to the object that decides.
- **What shipped.** `src/workspaces/site-planner/lib/viewChangeRecorder.js` (new, pure) — every `setView` with the view before and after, the classification (zoom/pan/no-op), the real call stack, the document's visibility, and **whether a TRUSTED user gesture authorised it** — alongside ONE timeline of `visibilitychange` · `pageshow`/`pagehide` (naming a back/forward-cache restore) · `freeze`/`resume` · `focus`/`blur` · `online`/`offline` · the planner's own mount/unmount · long tasks · animation-frame gaps · resource loads settling · and framings the gate suppressed. Each change carries what arrived in the second before it. `window.__plannerViewChanges()` returns the snapshot.
- **⛔ ARMABLE ON HIS PHONE, which is the only place the defect lives** (FOREGROUND-OR-VOID clause 5 / B280403): gated the `diagArm.js` way — read at CALL time, armed with `?planyrDiag=1` and no console. Unarmed it allocates nothing. **READ-ONLY, and the boundary is not negotiable:** it listens and reads `PerformanceObserver` entries; it patches no global. `window.fetch` was the obvious way to watch requests settle and is deliberately NOT patched — arming may never gate anything that mutates.
- **⛔ IT CREDITS ONLY `isTrusted` EVENTS.** A synthetic `WheelEvent` is recorded as `gesture:untrusted` and every change it causes reads as UNREQUESTED — so a probe cannot launder its own writes into "the user did it" (SYNTHETIC-KEYS-DONT-EDIT, applied to the input half).
- **⛔ AND THE INSTRUMENT CAUGHT ITSELF LYING, TWICE, WHICH IS THE PART WORTH KEEPING.** (a) On its own first teeth run at 20x CPU throttling, one wheel gesture's frame-coalesced flush landed on the far side of a **912 ms long task**, aged out of the attribution window, and was filed as an UNREQUESTED zoom — a clean, plausible, entirely false violation against a build that did not have the bug. The window now measures time the main thread was **AVAILABLE**, discounting long-task time: the app in that gap is not idle, it is blocked, and a gesture whose own flush is still queued has not stopped being that gesture. (Same mistake `lib/doubleTap.js` already records one layer up, where 307 ms of queueing ate a 350 ms budget.) (b) The harness first defined a violation as an unrequested change after the **LAST** gesture change, so a reframe landing BETWEEN two notches — which is the reported in→out→in symptom — was invisible; it reported a clean 0/10 on a build the fixed one was demonstrably suppressing 8 framings on. Both are pinned by tests.
