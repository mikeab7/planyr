**THE MODEL: ONE STORED NUMBER, TWO ENTRY POINTS.** A page's width lives as a single ProseMirror **doc attribute**, `pageWidth` (`null` = Fit to content · a number = a pinned sheet width in the same px unit `SHEET_MAX_WIDTH` already uses · the literal string `"full"` = fill the pane) — the exact mechanism `density` already uses (`notesExtensions.js`'s `addGlobalAttributes`/`setDocAttribute`), reused rather than re-argued: it rides storage, sync, print and export for free, and needs no tree schema, no `migratePageNode` entry and no cloud-merge change. New pure module `src/workspaces/notes/lib/notesPageWidth.js` (`PAGE_WIDTH_PRESETS`, `resolvePinnedBaseWidth`, `resolvePresetPx`, `dragWidthFromDelta`, `pageWidthLabel`/`pageWidthPresetId`) — 23 unit tests, `test/notesPageWidth.test.js`. The page menu's `NoteToolbar.jsx` control (a `FormatMenu`, the same listbox `Block style`/`Font size`/`Line spacing` already use) sits beside Zoom/History/Print/Markdown — "things you do TO the page." Presets: Narrow 440 · Normal 580 (matching the unpinned default exactly, so picking it is a REAL, persistent pin, not a same-numbers no-op) · Wide 900 · Full width (resolved against the live pane at render time, not frozen at click time, so it tracks a later window resize).

**THE FLOOR RULE, exactly as asked: a pin is a floor, never a cap.** Content wider than the pin still pushes the sheet wider — a table too wide for a Narrow-pinned page keeps growing the page past 440, and a Wide-pinned page with only a sentence on it still renders at 900 rather than shrinking to fit the text. Mechanically, `NoteEditor.jsx`'s existing page-growth measurement effect (NOTES-PAGE-GROWTH/NOTES-FREE-PLACEMENT) already computes `contentW = Math.max(<the unpinned 580 baseline>, needX)` for an overhanging box or table; the pin's only change is substituting its own baseline in that ONE `Math.max`, so real content overflow keeps winning exactly as it already did against the unpinned 580.

**⛔ THE BUG THIS SESSION FOUND IN ITS OWN FIRST DRAFT, THE SAME SPECIES NOTES-PAGE-GROWTH's ROUND 2a ALREADY NAMED AND REJECTED, ARRIVING THROUGH A NEW DOOR.** The first implementation fed the pin straight into `naturalSheetWidth` — the SAME baseline `matPadX` (the page's left gutter) is centred against. Measured live: committing a right-edge drag from 580→780 jumped the page's LEFT EDGE 100px left in the same instant — half the width gained, the exact "centring splits the new width across both edges" signature that item's history already has a name for. Fixed by keeping `naturalSheetWidth`/`matPadX` **pin-independent** (computed from the constant 580, exactly as before) and giving the pin its OWN baseline (`pinnedPageWidth`) that feeds only `sheetGrowWidth` — the SAME additive, already-proven, already-scroll-compensated mechanism an overhanging box or table already uses, which is what makes the left edge provably unable to move because of a pin, the same way it already cannot move because of ordinary content growth.

**A SECOND BUG THE SAME FIX PASS FOUND: A DRAG'S OWN FLOOR WAS ITS OWN STARTING WIDTH.** The live-drag preview originally floored its target width against the CURRENT `sheetGrowWidth` state — which already includes whatever pin is active — so narrowing an existing pin silently did nothing (dragged to 780, tried to drag back to 630, stayed at 780). Fixed with a second ref (`widthContentFloorRef`), refreshed by every real measurement pass, holding ONLY the genuine box/table-overflow floor with the pin subtracted back out — proven by the harness's own "drag it back" case (§6).

**THE DRAG GESTURE, Word/Docs-style, both edges, opposite edge holds.** Two 14px hit strips straddle the sheet's own left/right border (visible only on hover/drag — the #1508 lesson named in the brief: an invisible 9×14px grip shipped once already and was reported "super buggy"). A RIGHT-edge drag trivially holds the left edge (growth has only ever extended rightward in this codebase). A LEFT-edge drag reuses the identical rightward growth internally but ALSO scrolls the mat by the exact amount the width grew, so the two numbers moving together make the RIGHT edge hold on screen while the grip under the pointer tracks the LEFT edge — proven to hold within a few px of rounding noise (§7). The live preview bypasses the full DOM-querying measurement effect entirely (guarded by `widthDragRef`, so its own `ResizeObserver` cannot fight a live drag with a stale, uncommitted attribute) and commits via ONE `setNotePageWidth` call on release — one undo step regardless of drag distance (§4), and a plain click with no movement writes nothing (§8, matching B391073's standing rule for a box).

**PRINT — the width pin folds into the SAME `growPx` `buildPrintDocument` already computes for an overhanging box or table (`notesPrint.js`'s new `pageWidthPinExtentPx`), not a second mechanism.** A numeric pin (Narrow/Normal/Wide, or a completed drag) widens the printed sheet past its ordinary 190mm exactly like a wide table already does (§10). **"Full width" deliberately does NOT widen paper** — it means "fill my monitor," which has no print equivalent, so a Full-pinned page prints at the ordinary width unless its content genuinely needs more (§11) — stated here rather than left as a silent asymmetry.

**A WINDOW NARROWER THAN THE PINNED WIDTH (§9) behaves exactly like an already-overflowing table does on a narrow window (verify-notes-table-columns.mjs's own §9): the pin is not silently overridden — the page stays the width chosen and the outer pane scrolls sideways to reach it. Fit to content, unaffected, still shrinks to a narrow window with no forced overflow, exactly as it always has** — only an explicit pin opts a page out of that.

**ADJACENT CASES, all checked live:** every preset and Fit to content, including after a manual drag and after another preset (§2); a pinned-narrow page whose table is wider than the pin still grows (§3); a pinned-wide page whose content is short still stays wide (§3b); undo/redo of a width change as one step (§4); reload persistence for a preset AND for a completed drag, either edge (§5/§6/§7); a plain click on a grip commits nothing (§8); a window narrower than the pin (§9); PDF-PARITY via the real Print button, both a numeric pin and Full width (§10/§11). **Secondary ask (a draggable bottom edge for a page taller than its content) did NOT fall out cheaply — a text box's height is already a fixed product decision ("a text box's height is its words," B391073/notesBoxResize.js's `handlesFor`) that would need its own owner conversation, so it is not built here** rather than guessed at.
