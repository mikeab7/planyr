`[x]` **FIXED THIS SESSION.**
- Verify: sandbox — a real cloud round-trip through a mocked Supabase client (the same technique `test/notesTreeWriteThrough.test.js` and `test/notesTwoClientConflict.test.js` already use), plus a source-level mutation check, cover this completely; nothing here needs a live/signed-in browser.

**ROOT CAUSE — traced through the actual code, not re-derived.** `Notes.jsx`'s `handleAddPage`/`handleAddSubpage` put a new node straight into the tree via `addPage`, then called `persistTree`, which writes the tree locally and schedules a cloud push **on its own clock**. Nothing wrote the page's BODY at that moment unless a template was picked (`B1020931`'s `writePage(r.pageId, tpl.buildDoc())`). The body is otherwise written for the first time only from `NoteEditor.jsx`'s `onUpdate` handler — which fires once per keystroke, 600ms-debounced, and only once the user actually types. `notesStore.js`'s `sync.pages` (the set `pushPending` reads to decide what needs pushing to `notes_pages`) is marked dirty **only** by `writePage`, so a page nobody ever typed into never entered it. **This is not a failed write — it is a write that was never attempted.** A page created and then abandoned (tab closed, user distracted, or simply never typed into before clicking elsewhere) leaves a tree entry with literally nothing wired to ever create its body, for as long as the page goes untouched — which for Michael's orphan was 12+ hours and counting. The 7-of-8 control cases got a body only because he happened to type into them within a couple of seconds of creating them.

**THE FIX — order, not a retry.** `notesStore.js` gets a new exported `createPage(baseTree, opts, seedDoc)`: it calls `addPage` then **immediately, synchronously writes the body** (via the existing `writePage` seam) before returning the mutated tree to the caller. `Notes.jsx`'s two creation handlers now go through it exclusively — `addPage` is no longer called directly from the workspace at all (the source guard in `test/notesModule.test.js` that pins every tree-mutator call site to read the live tree was updated from `"addPage("` to `"createPage("` accordingly). A body write that fails (a real local-storage failure) returns `{ ok: false }`, and both handlers now refuse to persist the tree or navigate to the new page in that case — so a storage failure can never stand in for "never typed into" and leave the same kind of phantom entry; the failure is already surfaced by the existing `onNotesStorageError` banner (`fail()` inside `writePage` itself), so no new banner was needed. A page with no template now starts with the exact same blank document (`{type:"doc",content:[{type:"paragraph"}]}`, identical to `EMPTY_DOC` — `isEmptyDoc` in `notesCloud.js` treats them the same) that a template-seeded page has always gotten immediately.

**ITEM 4 — THE 17 ROWLESS TOMBSTONES, and whether `tombs` needs pruning.** Checked the actual code (`notesModel.js`) rather than assuming: `tombs` is **not** unpruned. `withTombstones` already drops any tombstone older than `TOMB_RETENTION_DAYS` (400 days) every time a new one is added — deliberately far longer than the bin's own 30-day window, "because the job of a tombstone is to outlive every copy of the thing it buried" (a device asleep for months must still be told, the day it wakes, that a delete was real — see `B357011`/`B364016`/`B391072`, three separate resurrection bugs from getting this exact tradeoff wrong). Michael's 59 tombs entries are all well under 400 days old, so none have been pruned yet — "tombs only grows" was an accurate observation of an account that hasn't hit the horizon, not evidence that no horizon exists. **The 17 rowless tombstones are not a separate defect — they are residue of this very bug**: a page created, abandoned bodiless (the old behaviour), then binned and purged before ever getting a body has nothing to mark `purged_at` on, but its tombstone is still doing its real job, which is blocking a stale device's tree-union from resurrecting the *tree entry* (never mind the row). **Decision: no additional pruning beyond the existing 400-day mechanism.** A tombstone's job is about the tree structure, not about whether a `notes_pages` row exists behind it, so "rowless" is not a signal that it's safe to drop early — and this codebase has three prior incidents of a tombstone-safety shortcut causing a real resurrection. The cost being weighed against that risk is a few dozen `{id, at}` pairs (kilobytes, not a real storage or performance problem). Going forward, this fix means a tombstone will always name a row that existed (even if empty) rather than a row that was never attempted.
