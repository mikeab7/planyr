### B1360 — The wheel zoom cannot reach 30 fps without taking the VIEW out of every coordinate `[Site Planner / UI]` (task) #site-planner #perf #ui  *(filed 2026-07-31 as the honest residue of the phase-2 speed block, whose stated target was a 33 ms wheel-zoom median at 4x throttle. **NOT reachable in that block, and said so loudly rather than reported as progress.** Minted via `--against-main`. DEDUPE-FIRST — searched Open + ⏳ Verify + Done across `memo`, `reconcil`, `transform`, `LOD`, `f2p`, `worldToScreen`, `B1345`, `B1352`: **B1345** cut how much there is to reconcile, **B1352** put a boundary around it. Neither changes the fact below, and this is a different KIND of change from either. Net-new.)*
- **THE MEASURED FACT.** `f2p` is `worldToScreen(view, …)`, so every element's pixel geometry is a function of the view. A pan or a wheel zoom therefore changes the rendered output of **every element**, and no memo can bail: `ElNode`'s memo (B1352) misses on 100% of elements during a view gesture **by construction**, which is why B1352 moved the number by less than the noise floor. Attribution of a zoom frame at 4x throttle: **script ~72%**, recalc-style ~8%, layout ~6%, paint/raster residual ~13%. There is no single item inside that 72% worth 5×.
- **THE ONLY SHAPE THAT GETS THERE** is a representation change: draw the plan in a view-INDEPENDENT space and let the view be an SVG group transform, so a gesture writes one attribute instead of re-emitting ~1,200 host elements. Then B1352's boundary becomes the mechanism by which nothing re-renders.
- **WHY IT IS NOT A ONE-SESSION CHANGE, stated so the size is not rediscovered:** stroke widths, label sizes and every LOD gate in this renderer are functions of `ppf` and would scale with the group unless individually counter-scaled; the pixel bar is byte-identical (B1345's standard); and the canvas has many sibling layers (parcels, markups, measurements, handles, GIS bands, furniture) which would all have to move together or visibly detach mid-gesture — the exact failure B1122 exists to prevent.
- **A PAN, unlike a zoom, has an EXACT version of this** (a pan is a pure translation at constant `ppf`, and a translate composes exactly), so it could land first and independently. The pan median is already 16.8 ms; its **p90 is 133 ms**, which is what that would fix.

`[~]` **AMENDED 2026-08-06 (speed program phase 3, NEW-3) — THE COSTED ROUTE TO 33 ms. No code; the dispatch asked for the plan, and the plan's honest conclusion is that the target is reachable for a PAN and is a multi-session component split for a WHEEL ZOOM.**
- **Derived from the profile already taken, re-run with source-map naming rather than re-derived.** A wheel frame at 4× throttle, panel closed, 3 interleaved reps: **script ~65% · recalc-style ~9% · layout ~8% · paint/raster residual ~15%**, and inside the script half: V8 `(program)` 25% · `setAttribute` 11% · the registration layout effect 11% (**B1359**) · react-dom + jsx-runtime ~12% · number formatting 3.3% · `getBoundingClientRect` 1.2% · label layout 1.1% · `renderElPx` 1.0% · roadNetwork 1.1% · Clipper 0.8%. **679 DOM mutation records per commit.**
- **CONSTRAINTS THAT BOUND THE PLAN, stated so no increment is costed against a cheaper bar than it has to clear:**
  - Canvas / WebGL are **rejected**, with reasons that are structural rather than aesthetic: `buildExportSvg` CLONES the live SVG, 54 of 65 e2e specs read `planner-canvas`, 39 `data-*` names are the test contract, and the accessibility tree is the SVG.
  - The B65 ghost buffer, retina, and drawing quantity are **off the table** (owner constraint: capping retained memory is authorised, a downgrade of drawing quality or quantity is not).
  - Anything that changes the picture must clear the **B1345 pixel bar**: byte-identical, or one unit of 255 on one channel.
- **THE INCREMENTS, in the order they would land:**

  | # | change | predicted | risk | what it would break |
  |---:|---|---|---|---|
  | 1 | **PAN as a group `translate`** — draw in a view-independent space for translation only; a pan writes ONE attribute instead of re-emitting ~1,200 host elements | pan p90 **133 ms → ~20 ms**; pan median already 16.8 ms | **medium** | hit-testing must add the offset; the basemap registration transform must compose with it; `data-view-offx/offy` must keep being written (harness + e2e contract). A translation cannot change any LOD gate or stroke width, so the picture is exact by construction — this is the increment whose pixel bar is free |
  | 2 | **ZOOM as a group `scale` between rungs** — re-emit geometry only when the scale crosses a threshold or the gesture settles | wheel median **~250 ms → ~40–60 ms** (the only increment that is worth a multiple) | **high** | every stroke width, label size and LOD gate is a function of `ppf` and would scale with the group. Counter-scaling strokes is `vector-effect`; counter-scaling text and re-deciding LOD is per-element work, which is the cost being removed. **Mid-gesture the picture would differ from the shipped one — the pixel bar has to be re-stated for "during a gesture" or this cannot ship** |
  | 3 | **The registration layout effect's forced layout** (B1359) | **8–11%** of the frame | medium | the drawing↔basemap weld; not verifiable in this sandbox |
  | 4 | **Memoise the panel's number formatting** (3.3% closed / 5.2% docked) | **2–4%** | low | nothing user-visible; the strings are pure functions of values that mostly do not change per frame |
  | 5 | **Cache the tile scan** in `tileRef` instead of re-querying every tile every run | **1–2%** here, more on a machine where tiles actually load | low | the "deepest z wins" rule exists to avoid sampling the coarse backfill layer — it must become structural (skip that layer) rather than a max-scan |
- **THE ARITHMETIC, said plainly: increments 3–5 sum to roughly 12–17%, which takes a 250 ms frame to about 210 ms. The target is 33 ms. Only increments 1 and 2 are worth a multiple, and only increment 2 touches the wheel.**
- **THE SIZE OF INCREMENT 2, so it is not rediscovered as a surprise.** It is a component split, not an optimisation: the canvas has many sibling layers (parcels, markups, measurements, handles, GIS bands, furniture) which must move together or visibly detach mid-gesture (the exact failure B1122 exists to prevent); `f2p` is threaded through every renderer; and the counter-scaling policy above is a product decision about what the plan looks like DURING a gesture, which is the owner's call and not an engineering one. **Estimate: increment 1 is one focused session with its own live verification; increment 2 is a multi-session project with a design decision at the front of it.** An honest "not this quarter" is a legitimate answer to it.
