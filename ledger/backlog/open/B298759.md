### B298759 — Version history is DEVICE-LOCAL, so losing the machine loses the history `[Notes]` (feature) #notes #persistence #sync  *(filed 2026-08-09 alongside B298754, which shipped the feature. This is the half that did NOT ship, stated as an item rather than left implied.)*
`[ ]` **Not shipped — a stated limit of B298754, filed on the day it shipped so it cannot be discovered later as a surprise.**
- Verify: sandbox
- Origin: filed 2026-08-09 from chat, as the named gap in NEW-3.
- **WHAT IS TRUE TODAY.** B298754 keeps a page's earlier versions in **IndexedDB on the machine you are sitting at**. It covers the risk the owner named — *"a note somebody mangled"* — including the two-window case, because THIS device snapshots what it holds before the sibling window's copy arrives. What it does not cover is losing the device: a new laptop signs in to the notes but to none of their history.
- **WHY IT SHIPPED THAT WAY, and it was a decision rather than an omission.** Syncing history needs a `notes_page_versions` table, a fourth entry in the sync plan, its own purge cascade and its own conflict story against a **server-owned `rev`** — and the brief's own instruction was to *cooperate with the existing cloud sync rather than fight it*. Device-local needs no schema change and cannot fight anything. Shipping the 90% that answers the stated risk beat shipping nothing this session.
- **WHAT IT WOULD TAKE.** One table (`user_id, page_id, at, reason, pinned, doc`), own-row RLS, and a fifth branch in `refreshNotesSync` that pushes rows the server has not seen and pulls the page's history when the panel is opened. Retention already exists and is pure (`planRetention`), so the server side is a mirror of a decision that is already made and tested.
- **THE HONEST ALTERNATIVE, if this is never wanted:** say so and the panel's own line — *"History is kept on this computer."* — becomes the whole of the answer. It is already on screen, so nobody can be surprised by it.
