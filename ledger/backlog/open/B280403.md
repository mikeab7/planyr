- **The gap, in his words and it is exact.** `__plannerHitWhy` is gated on `window.__PLANYR_E2E`, which is FALSE in production — **so as shipped it could not diagnose the owner's live session, which is the only place the bug exists.** He got in by setting the flag by hand and then forcing a `SitePlanner` remount by switching plans and switching back, because the hook's effect has `[]` deps and reads the flag at mount. **That worked, and it is folklore, not a feature:** it requires knowing the dependency array.
- **THE FIX, two halves.** The gate is read at **CALL time**, not at mount — the hooks are installed unconditionally and answer `null` until armed, so arming can never require a remount. And there is a way in that needs no console and no source dive: **`?planyrDiag=1`** on the URL, which **latches into `sessionStorage`** so an in-app plan switch (the planner navigates by hash) does not disarm it mid-diagnosis. `window.__PLANYR_E2E` still works, so every existing harness is untouched.
- **⛔ THE SAFETY BOUNDARY, and it is the whole argument:** arming exposes READ-ONLY resolution diagnostics — what a double-click at a point would address, and the facts behind that answer. It writes nothing, changes no behaviour, and is SESSION-scoped so it cannot leak into a later visit. **It is not a debug mode and must never gate anything that mutates.** Pure half in `lib/diagArm.js`, so the rule is testable without a browser.
