- **THE FACT.** There are exactly **two** Web Workers in this repo — `lib/terrainWorker.js` and `lib/dxf/dxfWorker.js`. The `offsetInward` path is not one of them. `clipper-lib` (a runtime dependency) runs its polygon offsetting on the thread that draws the screen, reached from `pondOffset.js`, `inwardBerm.js`, `pondGeom.js` and `pondStageModel.js`.
- **WHY MEMOISATION IS NOT THE END OF IT, in the owner's framing and it is correct.** B236592 cut the CALL COUNT by ~99% (275,184 `offsetInward` calls in one pan). It did not move a single millisecond off the main thread, so **the next bad input reintroduces the whole problem** — a pond with a denser ring, a larger plan, a new caller. A memo bounds frequency; it does not bound worst case.
- **⛔ WHY IT DOES NOT SHIP BLIND, AND THE ARBITER IS NAMED.** This math sizes the owner's **detention basins for permitting**. Any move off-thread must be **byte-identical**, and the arbiter is **`test/pondStorageGoldenMaster.test.js`** — **78 tests, exact equality, no tolerance anywhere** (verified green on this branch, 8.9 s). Its own header states the bar: *"the stored volumes did not move. Not close. EQUAL."* **No engineering number may be changed to make anything pass.** A failing golden-master assertion is a failed port, never a threshold to revisit.
- **THE ASYNC RIPPLE, SCOPED HONESTLY — this is the real cost of the item and the reason it is not small.** A worker boundary makes a currently-synchronous answer a promise, and the callers are in the RENDER PATH:
  - `pondStageModel` / `pondSplitFor` / `usablePondVolume` / `bandedStorage` are read **synchronously from the render body** (the `pondLedgerEntries` build, `SitePlanner.jsx` ~L10533 — see **B221763**). A promise there means the panel must render a PENDING state, which is a **product** change: the yield/pond panel would show "computing" where it now shows a number.
  - **PANEL-BREVITY and honesty collide here** and the resolution has to be decided before any code: a pending detention volume must not read as a computed zero, and it must not add a line to the default view.
  - **PDF-PARITY** applies — the export path reads the same numbers and must not be allowed to race a pending result.
  - The pond LABEL FIT (**B221761**) and the drainage facts pass sit downstream of the same geometry.
- **THE SHAPE THAT AVOIDS MOST OF THAT, recorded as the candidate rather than the decision:** keep a synchronous LAST-GOOD result (the memo B236592 already maintains) and let the worker refresh it, so the render body always has a number and the pending state is a staleness marker rather than a blank. Whether that is acceptable for a permitting number is the owner's call, not an implementation detail — **and it is the one question this item must not answer on its own.**
