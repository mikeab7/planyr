`[x]` **SHIPPED (hardened).** Added a real CSS rule, `.rbtn[aria-expanded="true"]:not(.on) { background: var(--hover-chrome) !important; border-color: var(--chrome-muted) !important; }` (`src/index.css`, right after the existing `.rbtn` hover rules), independent of the JS-driven inline `rbtn(active, open)` background/border wash already on `main`. `[aria-expanded="true"]` is a fact every `AnchoredMenu` trigger on this rail already publishes correctly; `:not(.on)` keeps it from ever fighting the orange active-tool fill (which stays inline-only). `!important` is required — a plain-specificity rule can never beat an inline style, so without it this rule could only ever agree with a working inline value, never actually stand in for a broken one, which is the entire point of a second, redundant mechanism.
- Verify: sandbox — logged-out, no external GIS, driven headless against a fresh build.
- **Strengthened `ui-audit/verify-rail-menu-consistency.mjs`'s NEW-1 section to match the owner's own methodology exactly**: a full `getComputedStyle` snapshot (every property, not a hand-picked few) of both the main row and the caret button, before and after a real click, diffed key-for-key, across all six rail triggers (previously only Parcel tools was checked, and only for one property). Fixed two bugs found while rewriting it: a locator that ambiguously matched both the main button and the caret (both accessible-name "Parcel tools"), and two assertions silently reading `undefined` because `CSSStyleDeclaration` iteration yields hyphenated property names (`background-color`) not the camelCase DOM property (`backgroundColor`) — both passing vacuously before the fix.
- **Mutation-checked, per the owner's explicit instruction, three ways — not just "delete the rule and confirm it fails":** (1) disabled only the new CSS rule → test still passes, because the pre-existing inline JS mechanism alone still produces a real computed-style diff (proves the CSS rule is a genuine backup, not the only thing working); (2) disabled only the two inline JS terms (`background`/`border`, the mechanism the owner's live test reported as producing zero diff) → test still passes, because the new CSS rule alone now carries the open-state highlight (this is the case that specifically protects against whatever caused the owner's observed failure); (3) disabled BOTH the inline JS terms and the new CSS rule → the test correctly goes red on all six triggers, with the exact symptom the owner reported (`(no properties changed)`), proving the test is not vacuous. All three mutations were reverted and a clean final run confirmed `✓ ALL PASS` before shipping.
