**THE HAZARD, stated as the owner did.** B1358128 (×2)'s fix means the id now arrives, so the delete now goes out. But `deleteSite` removed the record from `planarfit:sites:cloud:<uid>` and called `writeSites()` **before** asking the cloud, then handed the caller the cloud promise. So any REJECTED write — offline, an RLS/ownership mismatch, a team member deleting a teammate's shared project, a 5xx — left the project already gone locally while its row sat untouched in Postgres. Same visible outcome as the bug just fixed, reached a completely different way, and still live after that fix.

**THE FIX.** Order is now **tombstone → ask the server → remove locally only on a confirmed removal**. Three details carry the weight:
- **The tombstone still goes FIRST** — it is what stops an in-flight autosave resurrecting the row during the round trip (B372/B757), and it has to be armed before the network call, not after.
- **It is ROLLED BACK on a failed delete.** A project still on screen because its delete failed must remain editable and savable; leaving a tombstone would poison `saveSite`'s resurrection guard for that id — the exact permanent poisoning **B1202176** recorded from the other direction. A failed delete leaves nothing behind.
- **`removed: 0` is TWO different answers and must not be conflated**, or this fix trades one data lie for a worse bug. It means either *"the server refused / cannot see this row"* (real failure — keep the project) or *"the server has no such row at all"* (a plan that only ever lived on this device — nothing to confirm, and refusing would strand it on screen permanently **undeletable**). One extra `cloudCheckDeleted` round trip on that rare path decides; an inconclusive answer keeps the project, because the safe direction is always to keep. An already-binned row still matches `.eq("id", …)`, so an ordinary delete never pays for this.
- Raster eviction moved inside the confirmed path — a delete that did not happen must not throw away that plan's cached images. Logged-out and `tombstone:false` paths are unchanged (no server to ask). Every caller already awaited this promise before refreshing its list, so nothing else moved.

**⛔ AND AN INSTRUMENT FINDING WORTH MORE THAN THE FIX: THE BROWSER HARNESS CANNOT SEE THIS BUG, AND THREE ARMS WRITTEN FOR IT ALL READ GREEN ON THE BROKEN CODE.** Written first, then measured against the old ordering deliberately restored: *"is it still in the picker"*, *"is it still there after a reload"*, and the database-row check ALL passed on the defect. The reason is that opening the picker runs `reconcileProjects()`, which re-pulls from a database that is still serving the row it refused to delete — **the re-pull HEALS the wrongly-erased local list before any assertion can see it.** Those arms were deleted rather than shipped; a check that passes on the defect is worse than no check (DRIVER-SCROLL-IS-NOT-APP-SCROLL §6). What survives in the harness is only the arm that is genuinely discriminating (the row really is alive server-side after a refused delete) plus a written note recording the negative result, so the next session does not spend the same hour rediscovering it.
- **That masking is also the answer to why this was frightening rather than merely wrong**, and it is now the sharpest test in the file: the healing re-pull is defeated by a durable tombstone — which the OLD ordering left behind on a failed delete. Tombstone + erased local list is what turns *"vanished"* into *"vanished for good, on this device, across reloads"*, which is the Richfield shape. `test/deleteConfirmedBeforeLocal.test.js` asserts the whole chain through the real `mergePulledSites`: after a rejected delete there is no tombstone, so the next pull brings the project back.

**RED-PROOF, three mutations, each isolating a different half:** restore the old ordering → 3 cases red (kept-visible, RLS-refusal, inconclusive-check) · drop the `serverHadNoRow` probe → 1 case red (a local-only plan is stranded, permanently undeletable — the bug the naive version of this fix would have introduced) · drop the tombstone rollback → 2 cases red (savability, and the healing pull). `test/siteSoftDelete.test.js`'s two tombstone cases now `await` the delete, and say why in the file.
