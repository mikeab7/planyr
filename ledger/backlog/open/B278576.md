- **THE MECHANISM.** #963 taught the resolver to look THROUGH the handle layer, which answers *"what is beneath this grip"*. It does not answer *"what is this GESTURE about"*, and those are the same question only while the feature is bigger than the chrome it summons. A 6×12 body wearing a 12 px endpoint handle inside a 15×22 handle box has **no pixel left uncovered** once it is selected, so press 2 can only resolve to whatever lies under the chrome — and there, that is a different road.
- **THE FIX — the rule the owner proposed, taken literally: while a double-click is in flight, the feature press 1 selected WINS the hit test at that point.** `lib/featureTarget.js` gains `gestureAnchorTarget`, gated on the NATIVE double-click's own budgets (`pairsWithLastTap`, i.e. `DBLTAP_MS`/`DBLTAP_PX` — borrowed, never a second copy, so the anchor and the pair cannot disagree about what a double-click IS). It is asked FIRST and wins OUTRIGHT: a tie-break rule still loses to whatever the stack puts on top, which is the failure. One press outside the window or 15 px away is not a gesture and resolves off the stack exactly as before. **Identification only — no grip's `pointerEvents` or `onPointerDown` changed, and a vertex still drags.**
- **The two facts the anchor needs, each from its one honest source.** `lastPressRef` — WHERE and WHEN the last press landed, stamped in the **CAPTURE phase at the canvas root**, because reading the double-tap record would only ever see presses that reached a feature's own handler and a press EATEN BY CHROME is exactly the case being closed. `gestureAnchorRef` — WHICH feature that press selected, stamped in a layout effect on `sel`. **Press 1 keeps the anchor for the whole gesture:** a selection change that pairs with the anchor already held is ignored, so chrome that steals press 2 and selects something else cannot hand the gesture to itself.
- **THE SECOND SYMPTOM, and the honest answer on it.** The owner asked that the panel-closing half be filed separately IF it has a separate cause. **It does not, as far as this session could measure** — no sandbox configuration reproduced a double-click CLOSING an open panel, and with the anchor in place press 2 addresses the stub, so `featureDoubleAction` opens the inspector and there is no state left in which the gesture shuts it. It is guarded anyway rather than argued: **every feature** in the audit now double-clicks a SECOND time with the panel already open and requires it to survive, and the e2e spec pins the same thing on the tiny stub. That assertion is the only one in the file that starts from a non-empty state, which is why nothing caught it before.
