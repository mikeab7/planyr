### B1883840 (×2) — Notes reload bounces to first page (visibility guard race condition) `[Notes]` (bug) #notes #persistence  *(Claude Code dispatch block, "NEW-1," 2026-09-25 — repro: open Notes on a project with multiple pages, click to a non-first page, reload the browser; expected the same page stays open, actual it bounces back to the first page every time. **Recurrence: 2026-09-25** — the original fix (below, shipped 2026-09-24) added the read/write storage seam and wired every navigation path through it, and its own unit tests (`test/notesActivePage.test.js`) were genuinely green, but it never drove an actual mount-and-reload of the real `Notes.jsx` component against a real multi-page tree — exactly the LIVE-VERIFY gap a timing/race defect exploits. Per the Recurrence rule (B636) this reopens the ORIGINAL number rather than minting a new one — same symptom, same file, same feature.)*

`[x]` **ORIGINAL FIX (2026-09-24, unchanged, still correct as far as it went).** See the two `[x]` bullets below this line for the shipped `readActivePageId`/`writeActivePageId` storage seam — that mechanism is sound and untouched by today's fix.
`[x]` **ROOT CAUSE, exactly as dispatched.** `activePageId` in `Notes.jsx` is plain React state (`useState(null)`) with nothing in `lib/notesStore.js` ever recording which page was open — the mount effect unconditionally called `setActivePageId(firstPageId(loaded))` on every load, so a reload (or a scope/account switch) always landed on the tree's first page regardless of where the user actually was.
`[x]` **FIX.** Added `readActivePageId(scope)` / `writeActivePageId(pageId, scope)` to `lib/notesStore.js` — one localStorage blob per scope (`planyr:notes:activePage:v1:<scope>`, the new `ACTIVE_PAGE_KEY_BASE` in `lib/notesKeys.js`), following the exact shape of the existing `readNoteView`/`writeNoteView` and `readIgnoredDuplicates`/`ignoreDuplicate` pairs: a failed read/write is a silent no-op at the old first-page default, never a banner (a device preference, not data). `Notes.jsx`'s mount effect now reads the stored id and uses it when it still names a page in the freshly-loaded tree, falling back to `firstPageId(loaded)` exactly as before otherwise. Every OTHER place that navigates to a page — the cloud-seed `onTree` callback, the visibility guard that keeps the open page inside the current project/org scope, `handleAddPage`/`handleAddSubpage`/`handleCopyPage`/`handleDelete`/`handleRestore`/`handleOpenFinding`, the rail's page/search-hit/task click handlers, and Quick Open's pick handler — now writes through via a new stable `goToPage(id)` wrapper (or writes through inline where the id has to be resolved inside a functional state update), so the stored id always matches the page actually on screen. `noteIntent` (the Dashboard's "since you were last here" cross-workspace open request) still takes priority over the stored page — its own effect runs after the mount effect settles the tree and unconditionally overrides, and now also writes through so a subsequent reload keeps the intent's page rather than reverting to whatever was stored before it.
`[x]` **RECURRENCE ROOT CAUSE (2026-09-25), an effect-ordering RACE the original fix's own unit tests could not see.** The visibility-guard effect ("keep the open page inside the visible set", `Notes.jsx`, was line 761) and the mount effect above both fire in the SAME passive-effect pass on the FIRST render, off that render's stale closure: `tree = emptyTree()`, `activePageId = null` (the two `useState` initial values). Declaration order puts the mount effect first — it calls `setTree(loaded)` and `setActivePageId(storedPageId)`, but these are queued state updates, not yet committed. The visibility-guard effect runs NEXT in the same pass, still reading the STALE `tree`/`activePageId` from render 1: `pagesInScope(emptyTree(), …)` returns no roots, `!activePageId` is true, so it calls `goToPage(roots[0]?.id || null)` → `goToPage(null)` → `writeActivePageId(null)`, which **removes** the just-read stored page id from `localStorage` before the mount effect's own resolved value has ever committed. All the queued updates then flush as one re-render (`tree = loaded`, `activePageId = null` — the guard's `setActivePageId(null)` was called after the mount effect's own `setActivePageId`, so it wins). The guard's dependency array (`tree`, `activePageId`) changed, so it fires again: now `tree` has pages and `activePageId` is `null`, so `!activePageId` is true again and it lands on `roots[0]?.id` — the tree's first page — which it then writes back to storage, permanently overwriting the correct id. Confirmed live by driving the actual mount/reload sequence in a real browser (not by reasoning about the effect order): red on unmodified code, green on the fix (see below).
`[x]` **RECURRENCE FIX.** One line: the visibility-guard effect returns early while `tree.pages.length === 0` — a tree that has not finished loading yet is not evidence the active page is invisible. A not-yet-hydrated tree can never legitimately conclude "nothing is visible"; the effect's dependency array already re-runs it the instant `tree`/`activePageId` settle to their real values, so nothing is lost by skipping the empty-tree pass. Considered and rejected: a `treeLoaded` boolean (redundant with `tree.pages.length`) and a ref-based "skip the first run" guard (refs update synchronously but the mount effect's `setState` calls do not, so a ref would still read `true` while state was stale — reproduces the exact bug it's meant to prevent).
`[x]` **Verification — driven against the REAL component, not just the pure store functions (the gap that let this recur).** New headless harness `ui-audit/verify-notes-reload-active-page.mjs`: seeds a real three-page tree, opens the app, clicks the second (non-first) page, reloads twice, and asserts the SAME page stays open both times (plus a third page, so this isn't special-cased to index 1) — reading both the rendered title/selected-row state AND the raw `localStorage` value on every check. **Red-proven**: run against the untouched pre-fix code (`git stash` on just this file) it reproduces the exact reported symptom — 4/9 checks fail, every reload bounces to "Coordination" (the first page), matching Michael's report verbatim. **Green with the fix**: 9/9 pass. `test/notesActivePage.test.js` (the original 5 store-level tests) and `test/notesModule.test.js` (222 tests) still pass unchanged — this fix touches only the component's effect ordering, not the storage seam. `npm run lint` — 0 errors on the touched file.
