`[x]` **SHIPPED — and then CORRECTED. Read the correction first; the first fix was the wrong end of the problem and is reverted.**
- **Recurrence: 2026-08-13 — owner researched the three options rather than picking one, and none of them was right.** Verbatim: *"THE DEFECT IS THE ERROR STATE, NOT THE FOCUS RING. Orange-red is Planyr's brand accent — it is on the Select tool, the 'Select parcels: on' pill, everywhere. A field you are typing in glowing in the accent colour is normal and correct, and restyling every text box in the app is a large visible change to fix something that is not the cause."* He is right, and the shipped restyle is **reverted**: `--focus-border` is gone, `--focus-ring` / `--focus-ring-soft` are back to their accent-derived values byte-for-byte, and the focused input's border reads `var(--accent)` again. A guard test now fails the build if a separate focus colour reappears.
- **⛔ WHAT THE FIRST PASS GOT RIGHT AND WHAT IT GOT WRONG.** Right: nothing was rejecting his input (that finding stands, unchanged and re-verified). Wrong: it read the accent-vs-danger ΔE00 of ~14 as *the focus ring is impersonating an error* and moved focus. The accent IS the brand; the real fault is that **this app had no invalid state whatsoever** — an unusable value was reported by nothing at all: no colour, no icon, no message. **That is a WCAG 1.4.1 (Use of Color) failure in its own right, independent of the bug that surfaced it**, and — per Deque's guidance — a bare coloured border would not have satisfied it either, because the user must be able to tell WHICH field is wrong and WHAT is wrong with it.
- **WHAT SHIPS NOW.** A rejected value carries **four** cues, with colour last: a **short text message** naming the problem (*"Smallest allowed is 1"*) · **`aria-describedby`** tying that message to the input so a screen reader is handed it · an **icon** · and a border that differs from focus in **WEIGHT (2px vs 1px) as well as hue**, so the two never read alike before the words are read. A bare accent ring with no message is then unambiguous: you are simply typing.
- **PANEL-BREVITY:** the message is ONE line, ≤ 60 chars, and exists ONLY while there is something to say — every panel's default view is byte-identical. `panel-copy-budget --check` before and after: **all regions within budget, unchanged** (the note is not static copy and never renders at rest).
- Verify: sandbox — proven on the RENDERED element in both themes (ATTEMPT-BEFORE-YOU-PARK: this is a logged-out UI check and was driven here, not filed as pending).
- Origin: filed 2026-08-13 from chat.
- **⛔ SAY IT PLAINLY: NOTHING WAS REJECTING HIS INPUT.** Driven every way it can be driven on his own Depth field — select-all-and-type · clear-with-Backspace-and-type · type-a-partial-and-Tab-away · type-and-click-away — **the field took the value every single time** (613 → 500, → 5, → 450, all committed to the model). There was no validation, no revert, no blocked keystroke. The screenshot he sent showed Depth outlined in red and Length normal because **Depth was FOCUSED and Length was not.**
- **THE MEASUREMENT.** The focused-input border was `--accent` (#C2410C light / #F26B3A dark) with a soft accent halo. Against this app's own error colour `--danger` (#E24B4A / #F2706F) that is **ΔE00 14.4 (light) and 13.4 (dark)** by the repo's own CIEDE2000. A plainly different hue measures ~49 on the same scale. Red universally means rejected, so **a focused field was an error message.**
- **⛔ SUPERSEDED — the blue-focus fix described here was REVERTED (see the correction above).** It is left in the record because the blast radius it measured is the reason the revert mattered: those are BARE ELEMENT SELECTORS in `src/index.css` reaching **~194 inputs, selects and textareas** across Site Planner (138), Review (14), Notes (15), Library (11) and shared chrome (16), plus the Scheduler's own 66 — one edit restyling every text box in the product.
- **AND `--danger` NOW HAS A REAL STATE TO MEAN.** There was no invalid state in this control at all, which is why the focus ring was the only red on screen. `NumInput` now refuses a genuinely unusable value (unparseable · below `min` · above `max`) — and ⛔ **an EMPTY field is never an error**, because clearing it is the first half of retyping it and flagging that instant would recreate the exact impression this removes.
- **⛔ COLOUR IS NEVER THE ONLY CUE** (owner requirement — blue-vs-red is precisely the pair a red-green colour-blind reader cannot separate). Four independent signals: **`aria-invalid="true"`** on the input · **`aria-errormessage`** carrying the reason · a visible **⚠ glyph** whose accessible name is *"Invalid: Smallest allowed is 1"* · and the colour, last.
- **⛔ THE DEFECT THAT ONLY THE ON-SCREEN CHECK COULD SEE, and the reason the owner was right to demand it.** The first cut set every token correctly, put `aria-invalid` on the element and rendered the ⚠ — **and the border stayed blue.** `!important` does not arbitrate between two `!important` declarations; SPECIFICITY does, and the focus rule's three `:not()` arguments (0,4,1) out-specify a bare `input[aria-invalid]:focus` (0,2,1) wherever it sits in the file. A stylesheet reading would have passed it.
