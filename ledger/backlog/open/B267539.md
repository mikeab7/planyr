- **THE FAILURE.** `test/pondViewIndependence.test.js` › *"a single inward offset is not superlinear in vertex count"* went red on CI with `expected 17.674 to be less than 8.464`. Nothing in the branch touches `pondViewIndependence.test.js`, `pondOffset.js` or `pondStageModel.js` — its last change was #947 the previous day.
- **⛔ THE MEASUREMENT, WHICH IS THE WHOLE ITEM.** Each arm was timed **once**, over 20 iterations, landing both in the **1–10 ms** band where timer granularity and JIT state dominate. On ONE IDLE MACHINE the single-sample ratio spanned **0.23× … 8.81×** against a **6×** bound — while the TRUE cost ratio, taken as a minimum over repeats, is **1.84×**. The algorithm was never near the bound; the sampling was.
- **AND A SECOND, SUBTLER BUG IN THE SAME LINE: the bound is a function of the baseline.** `max(small, 1) × 6` means a baseline that happens to measure FAST **tightens** the gate. That is backwards — a lucky-fast baseline should never make the test harder to pass — and it is exactly what happened on CI, where `small` came in at 1.41 ms and set the bar at 8.46 ms.
- **THE FIX — the measurement only; the assertion is byte-for-byte unchanged.** Both arms are sampled **repeatedly and INTERLEAVED**, each keeping its **MINIMUM**, at a higher iteration count. Min is the right statistic for *"how fast can this go"*: a scheduler steal, a GC or a noisy neighbour can only ever **add** time, never subtract it, so the minimum is the least-contaminated estimate and one clean sample out of seven suffices. Interleaving stops a machine that drifts mid-run from biasing one arm against the other.
- **⛔ THE CLEANEST PROOF CAME FROM CI ITSELF, AND IT IS BETTER THAN ANY BENCH: THREE CONSECUTIVE RUNS OF A BYTE-IDENTICAL TREE DISAGREED.** PR #957 ran `Build` on `aa8c041f` → **success**, then on `7bbccf67` → **FAILURE**, then on `92cbc26c` → success. **`7bbccf67` is an EMPTY commit on top of `aa8c041f`** (`git diff aa8c041f 7bbccf67` is empty — it was a `--allow-empty` CI nudge). Same tree, same runner image, opposite verdicts, minutes apart. A guard whose answer changes with nothing but the weather is not measuring the code.
- **A/B, MEASURED UNDER THE CONTENTION THAT PRODUCED THE FAILURE (3× CPU load), 40 trials each on healthy code:** old sampling **2/40 false failures**; new sampling **0/40**. Green on six consecutive idle runs and four consecutive loaded runs.
- **⛔ AND A PRE-EXISTING WEAKNESS THIS FOUND, RECORDED RATHER THAN QUIETLY LEFT OR QUIETLY "FIXED".** The 6× bound's SENSITIVITY is weaker than its comment implies. A deliberately planted O(n²) pairwise vertex scan — the shape a self-intersection guard arriving on this path would have — only reaches **~3.4×** at this ring size (**12 vertices against 192**), because at that size `offsetInward` is dominated by fixed clipper overhead. **The bound was NOT changed**: tightening a threshold on the strength of one sandbox, against a CI runner this session cannot measure, would trade a proven flake for an unproven one, and loosening it would be worse. The honest reading is written into the test: this guard proves no quadratic term large enough to change the cost CLASS has arrived — it does not prove none exists. Sharpening it wants a bigger ring or a direct exponent fit, and that is a deliberate follow-on, not a silent edit.
- **THE GENERAL RULE IT RE-CONFIRMS.** `CLAUDE.md` already says this repo has been *"bitten four times in two days by guards that measured how long something took instead of how many times it happened"* — and the sibling test one line above this one says it outright: *"The COUNT of clipper executes, not the time … a machine that happens to be busy cannot [fail here]."* This test could not take that advice, because the question *"is one call superlinear in n?"* has no invocation count to count. When time is genuinely the only observable, **the sampling has to earn it**: repeat, interleave, take the minimum, and keep every arm clear of timer granularity.
