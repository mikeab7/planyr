- **THE PREMISE, and it was a good one:** the symptom (appears only after interaction, clears on reload, ~278 MB tab) fits a compositor/raster problem, and a JS CPU profile — every instrument the speed program had — would never see it. So the browser side was measured explicitly.
- **⛔ THE BLOCKER THAT HAS ENDED EVERY MEMORY INVESTIGATION IN THIS REPO IS NOW REMOVED.** Every external tile host is unreachable here, so Leaflet created its tile `<img>` elements but **nothing ever decoded** — no bitmap, no texture upload. `ui-audit/lib/fakeTile.mjs` now serves a real, decodable PNG for every tile request (`--fake-tiles`), so Chromium does the actual work: decode, bitmap allocation, texture upload, compositing, eviction. **Every tile's bytes are UNIQUE by construction** — Chromium caches decoded images by content, so one shared fixture would have meant ONE decoded bitmap shared N ways and a tile cache that looked free. That false negative is the exact failure this file exists to avoid, and it is unit-tested (`test/fakeTile.test.js`, including a real CRC walk of the PNG chunks — a malformed PNG fires `error` instead of `load` and would silently reproduce the blocked-host run it replaced).
- **(a) COMPOSITOR LAYERS AND RASTER MEMORY — measured, FLAT.** Read from CDP `LayerTree`, not inferred. With imagery absent: **7 layers**, flat 0 → 1000. With tiles decoding at dpr 1: **43 → 45**. At **dpr 2: 112 → 114**, raster proxy **35.62 → 36.12 MB**. Layers are numerous — and they do not multiply with interaction.
- **(b) RETAINED vs GARBAGE — CLASSIFIED, which is what the item said mattered most.** The owner measured the heap climbing 35 → 114 MB over 600 gestures without forcing GC and could not tell garbage from retention. Forced-GC readings plus full heap snapshots at both ends: **retained heap grows 0.9–2.1 KB per gesture and PLATEAUS** (16.96 → 17.33 → 17.48 MB over the last 850 gestures). The snapshot diff is **+0.75 to +1.46 MB total**, and **every top class is a JIT artifact** — `[code]`, `system / TrustedByteArray [code]`, `system / WeakArrayList`, instruction streams. That is V8 compiling hot functions: self-limiting, and the opposite of a leak. **No application object class appears anywhere in the growth list.** So the owner's ~130 KB/gesture was **garbage, not retention**.
- **(c) DETACHED DOM — REFUTED OUTRIGHT, and not by a proxy.** `lib/heapSnapshot.mjs` reads V8's own per-node `detachedness` flag: **0 detached nodes, 0 KB**, in all three regimes. (The probe also carries a `detachedApprox` counter — renderer-wide nodes minus attached nodes — which is an UPPER BOUND that also catches shadow and adopted trees, so it can clear a suspect but never convict one. The snapshot is the answer; the counter is the cheap screen. The parser **refuses to quote a detached figure at all** from a snapshot with no detachedness column, because a zero meaning "not measured" is exactly the reassuring number that must never be printed.)
- **(d) TOTAL INTERACTIONS vs SINCE-LAST-IDLE — neither.** The `idle` control arm holds time-since-load, probe count and GC opportunity equal at zero gestures. Cost is flat on both axes; there is no cleanup that never runs, because there is nothing accumulating for it to run on.
- **(e) THE B65 GHOST AND THE TILE CACHE — bounded, and now demonstrated rather than reasoned about.** **7,943 tiles were served, decoded and uploaded** across 1,000 retina gestures and **107 were retained at the end** (105 at N=0). At dpr 1: **6,084 served, 38 retained**. Leaflet's pruning plus `capTileCache` / `boundTileCache` are doing exactly their job. No eviction, teardown or lifetime change is warranted, and none is made — the authorisation to cap retained memory is not a licence to cap something that is already flat.
- **THE OWNER'S "LEAFLET TILE RETENTION LOOKS WRONG" IS EXPLAINED, AND IT IS NOT A LEAK.** He saw ~164 tiles on a fresh load. Measured here: **36 at dpr 1, 105 at dpr 2** on the identical scene. The multiplier is `detectRetina` — on a HiDPI display Leaflet fetches one zoom level DEEPER, roughly four times the tiles for the same ground, which is the sharp-aerial trade `lib/tileBudget.js` `retinaForZoom` makes deliberately and which the owner's standing constraint protects. 36 × ~4 ≈ 144, against his 164. **The count is high by design and it is FLAT with pan/zoom count** (+2 over a thousand gestures).
- **⚠ WHAT THIS STILL CANNOT SETTLE, stated rather than implied.** The tile BYTES are synthetic and the network is local: real imagery over a real connection is a different load (transfer, cache pressure, decode of far more varied content), and this reference plan is a floor, not a match, for the owner's heaviest signed-in plans. What is now proven is the MECHANISM — decode, bitmap, texture, eviction — not the magnitude on his machine. `Blocker: real-data`.
