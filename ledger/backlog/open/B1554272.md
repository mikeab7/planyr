- Verify: sandbox — reproduced and fixed in a headless, signed-out Chromium session (ATTEMPT-BEFORE-YOU-PARK: no auth, no external GIS, fully Claude-doable) with a real mouse drag through `columnResizing`'s own mousedown handler (SYNTHETIC-KEYS-DONT-EDIT's mouse analogue — a programmatic Range/event proves nothing here). `ui-audit/verify-notes-table-columns.mjs`, 32/32 checks across 11 cases.

**ROOT CAUSE, MEASURED NOT GUESSED.** `@tiptap/extension-table` (ProseMirror's own `columnResizing`) writes a resized column's width onto THAT column alone — `updateColumnWidth` in `@tiptap/pm/tables` rewrites exactly one column's `colwidth` attrs, confirmed by reading the library source. "Pairwise compensation" is not something ProseMirror does to the document. The squeeze is a RENDERING artifact one level up: the table's own node view only sets an explicit `table.style.width` (the sum of its columns) when EVERY column already carries an explicit width — the moment even one column is still unset, it falls back to `min-width` only and clears `width`, and under `table-layout: fixed` a column that has never been given an explicit width gets whatever is LEFT of the container's width after the explicit columns are subtracted. Once two columns are dragged wide, the untouched ones are squeezed toward Tiptap's own default floor (`cellMinWidth: 25`, about one character per line) — exactly Michael's "AHJ / Permit / Number" report.

**THE FIX — every column of a touched table always carries an explicit width, so the browser has nothing left to reconcile against the sheet.** New pure module `src/workspaces/notes/lib/notesTableWidth.js`: `normalizedColumnWidths(widths)` defaults an unset column to `TABLE_DEFAULT_COL_WIDTH` (160) and floors anything below `TABLE_COL_MIN_WIDTH` (100) — `null` (no change) the moment a table is untouched or already normalized, so an ordinary freshly-inserted table keeps its existing, un-reported-as-broken "divide the available width evenly" behaviour. `src/workspaces/notes/lib/notesTableColumns.js` is the editor-side half: `applyTableColumnNormalization(doc, tr)` walks every table (via `TableMap`, correctly handling colspan/rowspan/multi-row) and writes the normalized widths back. **Two defences, not one** (mirrors `notesExtensions.js`'s own `noteSpacingBlockSize` shape for the identical reason): (a) an `appendTransaction` plugin on `NoteTableColumns`, so a resize's own repair rides the SAME undo step as the resize (see B1554273's undo note below); (b) `normalizeTableColumnWidths()`, a command called once on editor MOUNT (never on every doc change) for the on-load recovery case `appendTransaction` cannot reach. `NoteEditor.jsx`'s `EDITOR_CSS`/`notesPrint.js`'s `PRINT_CSS` both drop `width: 100%` from `table` (the rule that pinned a table's total width to the text column in the first place — `table-layout: fixed` stays, since that's what makes an explicit column width honoured exactly).

**THE SHEET GROWS, REUSING THE EXISTING PATH — no second growth mechanism, per the owner's own instruction.** `NoteEditor.jsx`'s page-growth measurement effect (already used for a box placed past the right margin, `anchorExtentX`) now also measures each `<table>`'s own rendered right edge and folds it into the SAME `anchorExtentX` call. `notesPrint.js`'s `pageTableExtentPx` mirrors it purely (off the stored `colwidth` attrs, no DOM) so the printed sheet grows too — PDF-PARITY, driven through the real toolbar Print button in the harness (§10), not just the pure builder.

**A SECOND, INDEPENDENT BUG FOUND VERIFYING THE OWNER'S OWN "undo/redo of a resize as a single step" CASE, ALSO FIXED THIS SESSION:** `Table`'s own `addNodeView()` returns `null` whenever `resizable: true`, so the table's `<colgroup><col>` elements are patched ONLY by the live-drag preview — any colwidth change that doesn't come from a drag (an undo, a redo, this item's own repair) left the `<col>` elements showing the OLD widths forever, even though the STORED document was correct (proven by reading `editor.getJSON()` directly: `colwidth` genuinely reverted to `null`, while the rendered table looked unchanged). A SECOND, independent bug in the library's own `updateColumns` compounded it: it only ever sets the ONE CSS property (`width` or `min-width`) the current state wants and never clears the other, so a column reverting to unset kept a stale `width:` alongside a freshly-set `min-width:`, and `width` wins. Fixed with `NoteTableView` (`notesTableColumns.js`) — a corrected mirror of the library's own exported `TableView`, used unconditionally via `NoteTable = Table.extend({ addNodeView() {...} })` in `notesExtensions.js`, so `update()` runs on every transaction, drag included, and both CSS properties are decided every time rather than only the one currently relevant.

**ADJACENT CASES, checked live (`ui-audit/verify-notes-table-columns.mjs`):** widen the first / a middle / the last column (§2/§6/§9); narrow a column back down, well above the floor, siblings undisturbed (§11a); a table already comfortably within the ordinary sheet width never grows it (§11b); two tables on one page, one wide (explicit) and one untouched — the untouched one is unaffected by its sibling (§7); a table nested in a bullet list (§6); a table inside a `noteAnchor` box placed outside the text column (§8); undo/redo of a resize as ONE step (§5, both the resize AND the auto-filled siblings revert/reapply together); reload persistence for the repair, the drag, and the floor (§1/§2); the whole set at a window narrower than the sheet — the OUTER pane scrolls rather than the page clipping (§9); PDF-PARITY via the real Print button (§10). **Markdown export was not additionally driven live** — `docToMarkdown`'s table renderer reads only cell text, never `colwidth`, and the table schema itself is unchanged by this item, so it is unaffected by construction; not re-verified beyond the existing exporter guard in `test/notesModule.test.js`.
