### B463922 (×3) — Schedule grid: clicking/collapsing/undoing/switching views throws the view somewhere else `[Schedule]` (bug) #scheduler #ui #view  *(owner chat block, 2026-09-16, verbatim: "there's a million ways that I press something on the schedule and it jumps me to somewhere else in the schedule... sometimes I'll open something and it'll take me to somewhere completely different." Recurrence: 2026-09-17 — a chat dispatch had already reproduced four distinct mechanisms headlessly on `main` @ `d61e57c` (real wheel scrolling, `visibleClick`, a patched `scrollTop` setter) and prototyped a fix; this session applied, hardened, red-proofed and shipped it, and found + fixed a fifth. Reopened from Done per the recurrence rule — not a new number.)*

`[x]` **FIVE DISTINCT DEFECTS IN `GridView`/`GanttView` (`public/sequence/index.html`), ALL FIXED THIS SESSION AND MUTATION-PROVEN (every new scenario measured failing on the pre-fix build, then passing after).**
- Verify: sandbox — every scenario reproduces and is asserted headlessly against the app's own baked-in demo data (real wheel scrolling, real clicks via `visibleClick`/driver-scroll-safe helpers, a patched `scrollTop` setter witnessing real app writes) via `ui-audit/verify-grid-row-hold.mjs`. No auth, no cloud, no real-project-data path is load-bearing for any of the five fixes.
- **A — a tasks-only change (collapse) while the selection sits off screen chased it back anyway.** The passive "keep selectedId visible" `useEffect` (deps `[selectedId, selectedColIdx, tasks]`) re-ran on EVERY `tasks` identity change — collapse, undo, a cloud merge, a recompute, a Gantt drag, a status change, anything — and force-scrolled to `selectedId` whenever it judged the row off screen, with no memory of whether the SELECTION itself had actually moved. Clicking a row near the top, scrolling far away, then collapsing an unrelated group elsewhere threw the view back near the stale selection.
- **B — same mechanism, general case.** Bug A's own repro used a collapse; the real trigger is ANY `tasks`-identity change while the selection is off screen — proved separately with an undo (Ctrl+Z).
- **C — clicking (or double-clicking into) the topmost fully-visible row nudged the view up to one header height.** The same effect's `rowTop = idx * ROW_H` omitted `TL_H` (the sticky header's height), used only for the boundary check the immediately-preceding B463922 (×2) anchor effect already gets right (`TL_H + idx*ROW_H`) — so a row that was already fully visible, just under the header, read as "above the visible top" and got an unwanted 15–30px nudge. The goToFocus landing effect and the review-target-scroll effect had the identical omission; fixed in both.
- **D — a Grid/Split/Gantt view switch reset the pane to the top.** `<ErrorBoundary key={data.view}>` (App's render) remounts the whole Grid/Split/Gantt subtree on every view switch, and neither `GridView` nor `GanttView` remembered its own scroll position across a remount.
- **E — a dashboard/report jump (`goToFocus`) replayed on a LATER, unrelated remount.** App never cleared the `goToFocus` token after `GridView` landed on it, so any SUBSEQUENT remount (another view switch, a phone-breakpoint stack remount) was a brand-new effect instance that ran on mount regardless of whether its deps "changed," and replayed the jump to what was by then an unrelated row.
- **THE FIX, per bug:**
  - A/B — a `chasedSelRef` tracks the previously-seen `{selectedId, selectedColIdx}`; the passive effect now chases unconditionally only when the selection ITSELF moved (arrow keys, Tab, a fresh click, a dashboard/successor-prompt jump — unchanged). On a tasks-only change it chases ONLY when the selected row was already on screen before the change — a `selChaseAllowedRef`, set by the pre-existing B463922 anchor `useLayoutEffect` (which, in the SAME commit, already determines exactly this while computing its own anchor) so the two effects can't disagree. A row that was genuinely off screen is never dragged back.
  - C — added the missing `TL_H` to all three formulas.
  - D — two module-scope per-project `Map`s (`GRID_SCROLL_MEMO`, `GANTT_SCROLL_MEMO`, keyed on `proj.id`) restored via a `useLayoutEffect` on mount (skipped while a `goToFocus` jump is pending, so a deliberate jump always wins) and updated on every scroll. Per-project, not per-mount, so it also covers switching between two schedules under the same view without a remount. `GanttView`'s scroll container gained a `data-gantt-scroll="1"` hook (parity with `GridView`'s existing `data-grid-scroll="1"`) for this and for testability.
  - E — `goToFocus` is cleared (functional update, guarded on its `n` token) once the landing scroll is actually WRITTEN, inside the `setTimeout` callback — **not synchronously at the top of the effect**: an earlier version of this fix cleared it synchronously, which re-renders App with a new `goToFocus` reference before the scheduled scroll fires, and a dependency change on that SAME effect runs its cleanup first (`clearTimeout`), silently canceling the landing before it ever happened. Caught by the harness itself (scenario E initially failed with the landing position reading as a stale memo restore, not the jump target) before it could ship broken.
- **MUTATION-PROVEN, all five, against the true pre-fix source** (`git stash` the `public/sequence/index.html` diff only, keep the extended harness): A/B/D/E fail outright pre-fix (off-screen selection chased back, undo drags the view, both view-switch scenarios reset to 0px or lose the Gantt container, the report jump replays 5838px→912px). **C needed two harness corrections to actually exercise the bug** rather than pass by accident, both are the point, not incidental: (1) the buggy formula only misfires in a narrow ~30px band (one to two header-heights down) — picking "the topmost visible row" at an arbitrary scroll position mostly missed that band entirely, so the check has to place a row's on-screen top precisely inside it; (2) the "click a different row first" setup step was itself using a plain, unchecked click that could reach an off-screen row and trigger Playwright's own actionability auto-scroll — the exact **DRIVER-SCROLL-IS-NOT-APP-SCROLL** trap this repo already has a named rule about, this time inside the NEW test, not the product. Both corrected; C then failed pre-fix (15px nudge, budget ±2) and passes post-fix. Full run, post-fix: `PASS — every anchor held its place on screen within ±2px, every step changed the model, and the selection never wandered.`
