- **BUG 1 (the one actually asked for) — `handleClick`'s cache fallback only fired when the snapshot happened to already be the DISPLAYED map layer, which is true for Waller (its only live source is the image-only statewide layer, so `preferSnapshotForDisplay` always prefers the cache for display) but was never true for Chambers, which has its own live CAD (CCAD, since B787) and so keeps that live layer as the display until it fails. `optimisticHitAt` (the pre-existing fallback's data source) reads only the currently-DISPLAYED layer's features — so on a Chambers click during an outage, it found nothing, even though the Drive snapshot had already loaded successfully into memory and `selectParcelAt` (the ADDRESS-SEARCH selection path) already had a working, independent fallback (`snapshotHitAt`) that queries the loaded snapshot directly regardless of what's on screen. `handleClick` (the direct MAP-CLICK path) just never called it. Fixed: `handleClick`'s no-hits branch now also tries `snapshotHitAt(latlng.lng, latlng.lat)` whenever live truly didn't answer (`res.responded === 0`), the same lookup the search path already used — so a raw click on the map resolves against the cache exactly like a searched address does.
  - **Also wired the DISPLAY side, not just the click:** a real county's live outline layer going down (`markDown`, the existing 8s hang-guard / `requesterror` handler) now promotes the Drive snapshot to the on-map DISPLAY too (`showSnapshotDisplay`, shared with the pre-existing image-only-source branch), and a snapshot that finishes loading AFTER the live layer already gave up is picked up by the existing `onSnapshotChange` listener (extended to also promote on a now-known-down county, tracked in a new `downDisplaysRef` — the deterministic "this county's live layer already gave up" signal `markDown` itself owns, not `sourceHealth.js`'s 3-consecutive-failure click breaker, which answers a different question and stays closed for minutes after the display already failed).
- **BUG 2 (found while diagnosing — a real server-side defect, not diagnosed by the owner but load-bearing for BUG 1's fix to work in production): the `/api/parcel-cache` endpoint shipped its stored Drive bytes RAW-GZIP with a manually-set `content-encoding: gzip` header, expecting the browser to gunzip it transparently.** Cowork's own live measurement against production confirmed it does not — the body handed to `res.json()` is still gzip-compressed and the call throws, silently swallowed by `parcelSnapshot.js`'s `refreshFromDrive` (`catch (_) { return; }`), so the in-memory snapshot never populated in a real browser even though `?meta=1` reported `cached:true` (exactly what Cowork measured — server healthy, full endpoint 200, but the FeatureCollection never actually usable without a manual `DecompressionStream` workaround). Fixed in `functions/api/parcel-cache/_handler.js`: the handler now decompresses the stored gzip bytes SERVER-SIDE (Web Streams `DecompressionStream("gzip")`, available in both the Cloudflare Pages Functions runtime and Node) and returns plain, already-decoded GeoJSON with no `content-encoding` header — Cloudflare's own edge still compresses the larger plain-text body transparently for the wire when the request's `Accept-Encoding` allows it, so this costs no real bandwidth, it just removes the unreliable manual double-encoding. `test/parcelCacheHandler.test.js` rewritten to build fixtures with real `zlib.gzipSync` (was arbitrary bytes, which never exercised real gzip framing) and asserts the response is decompressed with no `content-encoding` header, plus a new case for corrupt/legacy stored bytes (404, never throws).
