### B1359 — The drawing↔basemap registration layout effect is the largest named item in a zoom frame `[Site Planner / UI]` (task) #site-planner #perf #ui  *(found 2026-07-31 by `ui-audit/diagnose-zoom-cost.mjs --profile`, the instrument built for the phase-2 speed block. **Filed deliberately, NOT fixed** — it is a change to the code B1122 / B1141 / B1189 have each already had to correct, and the effect's own comment names the change as deliberately unshipped; it needs its own verification and its own item. Minted via `--against-main`. DEDUPE-FIRST — searched Open + ⏳ Verify + Done across `regShift`, `registration`, `mapLock`, `B1122`, `B1141`, `B1142`, `B1189`: **B1122** moved the write into a layout effect, **B1141/B1142** made the shift measured rather than assumed, **B1189** stopped it re-running on state identity. Every one of those is about the effect being CORRECT; none is about it being expensive. Net-new.)*
- A CPU sample profile across a 40-event wheel gesture at 4x throttle puts the registration layout effect at **9.2% of all script self-time** with the inspector closed and **12%** with it docked — the largest single named entry after V8's own unattributed `(program)` bucket. `setAttribute` and a synchronous `getBoundingClientRect` inside it account for several points more.
- Its own source comment already names the fix: *"The larger win — taking `regShift` out of React state entirely and writing both transforms — DELIBERATELY unshipped."* That is still the shape.
- **⛔ Read `B1122` / `B1141` / `B1189` before touching it.** It is load-bearing for the drawing sitting on the imagery, it must stay pre-paint (VIEWPORT-STABLE), and it has taken the planner down once (B1189's fifty-render abort).

`[~]` **AMENDED 2026-08-06 (speed program phase 3, NEW-2) — the MECHANISM is now measured, one half of phase 2's diagnosis is REFUTED, and the fix is deliberately NOT shipped. Nothing in the render path changed.**
- **The instrument got better first.** `ui-audit/diagnose-zoom-cost.mjs --profile` now resolves its frames through the build's source maps (shared with the boot timeline's reader), and a new `--profile-tree <substring>` opens a named frame up into its own call tree. Phase 2 could say "the registration layout effect is 9.2% of script"; it could not say which line, what it called, or where the time went inside it.
- **CONFIRMED, and it is the largest single app frame in a zoom profile.** Interleaved A/B, 3 reps each way at 4× throttle (closed · Yield docked · closed · …): the effect (`SitePlanner.jsx` → the `useLayoutEffect` at line 2751) measures **11.3% of script self-time closed and 13.1% docked**, in absolute terms **1,471 ms → 1,776 ms across a 40-event gesture (+21%)**, with the two arms' ranges NOT overlapping (closed 1,383–1,586 · docked 1,690–1,957).
- **REFUTED — `setAttribute` does NOT rise with a panel docked.** Phase 2 recorded 4.9% → 8%; measured again here it goes the other way, **1,480 ms → 1,312 ms (11.4% → 10.0%)**, with the arms' ranges heavily overlapped. Half of phase 2's stated mechanism does not reproduce. (What DOES rise on the panel arm besides the effect: number formatting, 3.3% → 5.2% — the panel re-formats its numbers every frame.)
- **⚠ AND THE HEADLINE ITSELF IS INCONCLUSIVE TODAY.** The +20% panel-open frame penalty phase 2 reported comes out **+6.7% (closed median 250 ms · docked 267 ms) against a ±6.6% noise floor measured on the closed arm's own repeats** — it does not clear its floor. The mechanism below is confirmed; the headline it was meant to explain is not, on this machine on this day. Both are reported rather than the convenient one.
- **WHY IT COSTS — a FORCED SYNCHRONOUS LAYOUT, not the state dispatch.** The effect reads `wrap.clientWidth` / `wrap.clientHeight` (and, in the tile branch, `getBoundingClientRect`) *inside a layout effect*, i.e. immediately after React has mutated the DOM — so every run flushes a full layout of the just-dirtied tree. Chrome's own counters make the case quantitatively: **`LayoutCount` is flat between the arms (97–110 closed · 91–100 docked) while `LayoutDuration` rises 881 ms → 1,276 ms (+45%)**, with every docked rep above every closed rep. The effect's own self time rises by **+305 ms** while layout rises by **+395 ms** — the same money. The panel does not make the effect run more often; it makes each forced layout more expensive, because there is 142 nodes more to lay out. **That is what the "+20% panel penalty" is.**
- Its children are minor by comparison: the tile scan 136 ms, the commit path 199 ms, everything else under 20 ms.
- **THE FIX THAT WOULD WORK, costed and NOT taken this session.** `cw`/`ch` exist only to decide `sizeChanged`. React already knows every input that can change them (`size`, `geoOverscan`), so the synchronous read can be gated to the frames where a resize is *possible* and skipped entirely on a pure view gesture — the measurement is unchanged wherever it is taken, which is the property that protects the weld. Predicted saving **≈8–11% of a zoom frame**, and most of the panel-open penalty with it.
- **WHY IT IS NOT SHIPPED HERE, plainly: THIS SANDBOX CANNOT VERIFY THE WELD.** Every external tile host is blocked, so `tileRef()` never finds a loaded tile and the registration falls to its projection fallback on every run — the exact path the change would alter is the one that cannot be exercised. Shipping a change to the effect that B1122 / B1141 / B1189 each had to correct, un-verifiable, on a predicted saving, is the trade this program exists to refuse. It needs a session with a live basemap (V710).
