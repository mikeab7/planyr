### B917 — Share entry points, unified project-level dialog, and read-only client (viewer) mode `[Global / UI]` (feature) #ui #infra #auth  — depends on B916  *(owner-dropped 2026-07-21 as "NEW-3", top-of-queue; minted **B917**. Uses the B915 ContextMenu primitive.)*
`[ ]` Two problems: sharing is only reachable from the map-pin right-click, and the app assumes every user can edit everything — there is **no viewer state**. This item adds the surfaces + the read-only mode on top of B916's schema/RLS.
- Verify: **live** — depends on B916 (⛔ same `auth` blocker: the read-only lockdown + "shared with you" distinction + cross-module gaps need two signed-in accounts to confirm). Ships AFTER B916's schema is live-verified. Not shippable-and-verified this session.
- Origin: filed 2026-07-21 from chat ("NEW-3").
- **DEDUPE-FIRST:** relatives (not dups) — **B464/B465** (read-only/locked-TAB persistence signal — a DIFFERENT read-only: single-writer lock, not a viewer grant), **B455** (conflict/at-risk lockout). This is a *permission-driven* viewer mode, distinct from the tab-lock class.
- **Primary surface:** a persistent **Share** button in the project header bar of **every** module (Site Planner, Schedule, Document Review, Cost Estimating, future Notes).
- **Also reachable from:** the map-pin right-click (existing — CONVERTED from the current one-click team-grant to opening this dialog) and the project list / Library row right-click. All via the **B915 `ContextMenu`** primitive.
- **Unified dialog contents:** project name; an explicit **"Private"** state when there are zero grants; a **"Who has access"** list (grantee, role, "All modules" or "3 of 5"); an add row (existing user or team → module checkboxes, all checked by default); revoke. **Contextual open:** launching from inside a module pre-highlights that module in the checklist but still shows the FULL project-level dialog — no module-only shortcut that grants without showing complete access.
- **Read-only client (viewer) mode (new work):** when a viewer opens a shared project, EVERY edit affordance across all modules — drag handles, markup tools, task-edit fields, layer edits — is **disabled or hidden, not merely rejected server-side after the fact.** RLS is the enforcement backstop; the UI must not let a viewer attempt an edit guaranteed to fail. (Threaded as a `canEdit`/`viewer` capability from the grant down through each module's editing surfaces.)
- **Cross-module access gaps:** if a grant excludes a module that another visible module references (e.g. a Schedule task links a Doc Review sheet), show an explicit **"you don't have access to this module"** state — never a broken/dead link.
- **Blocked-this-session note:** the dialog + viewer-mode wiring is real UI work that can be built, but it is **meaningless to ship without B916's schema live + verified** (a viewer mode with no grants to read, and no verified revoke, is untestable and unsafe). So it parks here behind B916; the plan + surfaces are fully specced above for the follow-on session that has the owner's 2nd account. → **V388 in `VERIFICATION.md`**.
