**ROOT CAUSE — one line, and neither previous fix was near it.** Pressing a row in the switcher's per-row Rename/Delete menu **closed the switcher dropdown underneath it**, and the switcher's `[open]` effect clears both `menuFor` (which project the row menu is about) and `editingId` (the inline rename editor) whenever the dropdown closes. The Delete row's own state update ran in the SAME React batch, immediately after, and did `setMenuFor((m) => ({ ...m, confirm: true }))` — spreading the just-nulled `m`. **`{ ...null, confirm: true }` is truthy**, so the menu did not close: it re-rendered its confirmation step with the project ERASED. Everything downstream then operated on `undefined`.

**WHY IT LOOKED LIKE A SUCCESS, which is the whole reason it survived two fixes.** `doDelete(undefined)` → `deleteProject(undefined)` → `deleteSiteGroup(undefined)`: `loadPlansOfGroup(undefined)` matches nothing, the B1303824 empty-cache fallback then declines to ask the cloud (there is no group id to ask about), and the call resolved **`{ ok: true, removed: 0 }` — zero network traffic, no error, nothing thrown**. The notes move still ran (that is the `notes_trees.rev` bump the owner caught), the dialog closed, and the app routed home. Nothing in the code ever asked the database to delete anything, exactly as the brief predicted.

**WHY THE DROPDOWN CLOSED — a comment that quietly stopped being true.** `ProjectBreadcrumb.jsx` asserted that the row menu is *"a SECOND portal layer above the dropdown's click-away backdrop, so clicking inside it never closes the parent dropdown."* That was true of the **backdrop** it was written for: a rendered `position:fixed; inset:0` layer at a higher z-index physically absorbed the press. **B1106256 replaced that backdrop with a document-level capture `mousedown` listener** — for its own good reasons (a backdrop is a hit-test target and was swallowing real presses) — and a document listener has no geometry: every press inside a second portal reads as "outside". The comment was never updated, so the property looked guaranteed and was not.

**THE FIX, three layers.**
1. **The class fix.** New `shared/ui/menuLayers.js`: every portal menu declares its stacking layer (`data-menu-layer`), and `AnchoredMenu`'s dismissal stands down for a press inside a **strictly higher** layer. Strictly higher matters — a sibling menu at the same level must still dismiss, which is what keeps "open one menu, click another trigger" working (asserted as its own e2e case, and it stays green under the red-proof below). `ContextMenu` stamps both its backdrop and its panel. This closes the class, not the instance: any menu opened above an `AnchoredMenu` anywhere in the app inherits it.
2. **A lost target closes the menu, it never survives as a partial one.** `setMenuFor((m) => (m ? { ...m, confirm: true } : null))`, both directions.
3. **LOUD-FAILURE at both ends.** `doDelete`/`commitRename` refuse a missing id, say so in plain words, and file telemetry (`project-delete-no-target` / `project-rename-no-target`); `deleteSiteGroup(falsy)` and `deleteProject(falsy)` now return `{ ok:false }` with `delete-no-group-id` telemetry instead of a clean-looking `{ ok:true, removed:0 }`. A REAL id that names nothing still reports the honest `ok:true, removed:0` — the two cases stay distinct, and that distinction is its own test.

**AND THE SEPARATE, REAL DEFECT UNDERNEATH IT — the Schedule module deleted the wrong thing.** Even with a correctly resolved id, `doDelete` handed a controlled row to the bridge and **returned**: `planar:nav-delete` removes the embedded app's SCHEDULE and never touches `public.sites`. So "Delete project" in the Schedule module could only ever have deleted a schedule — the project stayed, everywhere, forever. That is the owner's sentence in as many words ("why does it even offer that ability"). Now: a row the site registry knows is a **project**, and is deleted as one, with its linked schedule carried along; only a schedule-only pseudo-project (Pursuits / Operations, which no `sites` row describes) is bridge-only. Rename had the mirror defect — `unionProjectLists` displays the REGISTRY copy of a linked project, so renaming only the schedule left the visible row unchanged.

**⛔ THE INSTRUMENT GAP, which is the reason this was invisible to a repo with 15,800 tests (WRONG-CASE).** Every existing project-delete check drives the app **logged out** and asserts `localStorage` — `verify-b439-b440-project-manage.mjs` does exactly that, and it passes on the broken build, because the local half of the delete always worked. The half that matters when signed in is a write to `rest/v1/sites`, and **nothing in this repo could observe it**: this sandbox's proxy CORS-blocks the Supabase auth handshake (the standing `Blocker: auth` behind ~80 parked checks), so no harness here has ever been signed in. New: `ui-audit/lib/stubSupabase.mjs` (a faithful PostgREST/auth stand-in — it honours the query, not just the path; an early version that answered every GET with "all rows" made the Recently-deleted bin believe every live project was binned and hard-delete them, a failure invented entirely by the instrument) and `ui-audit/verify-signed-in-project-delete.mjs`, which drives the real signed-in app and asserts the row actually moved. It carries a **KNOWN-GOOD ARM** that fails the run if it never sees ordinary `sites` traffic at all, because a probe that cannot see the app talking to the database cannot report that one write is missing. `verify-b439-b440-project-manage.mjs` was ALSO found dead at boot on unmodified main (it waited on `button[title^="All projects —"]`, a title the crumb no longer carries, and booted to the Dashboard, which has no crumb) — repaired here; **eight other harnesses share that stale selector and are filed as B1361682, not fixed.**
