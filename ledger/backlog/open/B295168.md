### B295168 — The site-route chunk guard snapshots AFTER its own gesture, so it reports input-driven chunks as boot-path ones `[Infra / Testing]` (bug) #infra #testing #perf  *(found 2026-08-06 while closing out B1349's owner gate — the guard was still red on `terrainLayers` after B1442 removed the only trigger this repo had recorded for it, and the discrepancy turned out to be the instrument. Minted **B295168** via `git fetch origin main && npm run next-id -- --against-main`. DEDUPE-FIRST — searched Open + ⏳ Verify + Done across `siteRouteChunks`, `bootChunks`, `BOOT_SETTLE_MS`, `lazyChunksAfterBoot`, `B1163`, `B1344`, `B1349`, `B1358`, `B1431`: **B1358** fixed this metric's RACE (the snapshot was taken before React's mount effects had fired, so a fast machine reported clean) and its 4 s settle window is still correct and still load-bearing; **B1163** is the allowlist's own defect; **B1349** owns the chunks the guard names. None of them is about WHERE in the run the snapshot is taken relative to the harness's own pointer. Net-new, and deliberately NOT a B1358 recurrence — B1358's fix holds and this is a second, independent way the same number can mean something other than what it says.)*
- **THE DEFECT.** `ui-audit/perf-harness.mjs` defines `siteRouteChunks` as "which JS chunks a PLAIN SITE ROUTE fetched — the boot path", and takes the snapshot **after** the time-to-first-drag gesture plus a 4 s settle. That gesture moves the mouse across the canvas. So any chunk a POINTER MOVE can pull lands in a list whose name and whose failure message (*"Something is warming a route-irrelevant workspace at boot again"*) both say boot.
- **PROVEN, on `main` at `1d2f31a`, with the reference plan seeded:** idle page, **no mouse, no click, eight seconds** → `terrainLayers` is **absent**. One mouse move over the canvas → `terrainLayers` arrives (the cursor ground-elevation readout, `useGroundElevation` → `terrainLazy.loadTerrain()`). The harness reports it as a boot chunk in both worlds.
- **WHY IT MATTERS BEYOND TIDINESS:** it cost B1349 a false red for a defect that was genuinely fixed, and the next reader's obvious move — widening the allowlist — would have hidden a real regression on the six chunks that ARE on the idle path.
- **FIX SHAPE, and why it is not a one-line move.** The snapshot cannot simply move earlier: B1358's settle exists because a boot-path `import()` fired from a mount effect is only in the list if it has been REQUESTED by the moment of the read, and that is machine-speed dependent. The honest shape is **two page loads in one run** — one that gestures immediately (time-to-first-drag) and one that never receives input at all (the chunk guard, after its settle) — or an initiator-aware split reporting `chunksBeforeFirstInput` / `chunksAfterFirstInput` as two named numbers. Either changes what a guard other sessions read, so it wants its own before/after rather than a drive-by edit.
- **⛔ Until it is fixed, do NOT widen `bundle.siteRouteAllowlist` to quiet it** — the six genuinely-at-boot names on B1349 are what it is correctly catching.
