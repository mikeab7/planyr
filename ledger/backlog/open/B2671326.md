### B2671326 — Schedule page still carries a hand-typed Supabase URL and anon key (`page/main.jsx`, cloud IIFE) `[Scheduler]` (refactor) #scheduler #supabase #infra  *(audit batch J3 follow-up, 2026-11-24)*
`[ ]` **🔲 Open — design needed, not a quick edit.** J3 asked the page to use the shared Supabase client and drop the typed-in URL/key. Not done in J3 because the page is a STANDALONE bundle (the committed `public/sequence/page.js`, loaded by an iframe and by ~25 harnesses that each run their own static server), so it cannot read the app's build-time env (`VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY`) and any config it needs at runtime has to be injected into `index.html` by EVERY server that serves it. The anon key is public by design (RLS is the protection); this is housekeeping, not an exposure.
Proposed design: (1) the page reads `window.__PLANYR_SUPABASE__ = { url, anon }` and, if absent, builds a client against an unreachable URL so the existing "Cloud unreachable — offline copy" banner shows (LOUD-FAILURE, never silent); (2) the Vite dev middleware and the production `minify-sequence-page` step inject it from env into `/sequence/index.html`; (3) `ui-audit/lib/scheduleStandalone.mjs` injects the same for harnesses, and every harness that starts its own server for `/sequence/` is moved onto `bootSchedule` or gets the same inject (list: `grep -l "sequence" ui-audit/*.mjs | xargs grep -l createServer`); (4) then bundle `@supabase/supabase-js` from npm and delete `public/sequence/vendor/supabase.js`. Keep `window.__sb` and the storage-key compatibility.
