### B2154049 — `POST /api/auth/e2e-session` (the test-account sign-in route every session relies on) answers 502 for long stretches — measured ~17:50–18:55 UTC and again at ~19:00 UTC on 2026-10-06 `[Infra / verification]` (bug, HIGH for the sweep) #testing #infra  *(AUTH-SWEEP 2: 3 of the last 4 agents could not sign in at all; earlier agents saw intermittent 502 under parallel load)*
`/version.json` stays 200 while the route 502s, and a wrong key correctly answers 404, so the route is deployed and configured but its upstream call (Supabase admin/session mint) fails or the Worker errors. Candidates: Worker CPU/subrequest limit under many parallel sign-ins; upstream rate-limit on the test account; back-to-back deploys. **Needs a look at the Cloudflare Pages Functions logs for that route** (Michael or a session with log access). **Stopping rule:** 20 consecutive sign-ins in a row succeed, and the route retries/backs off server-side instead of returning a bare 502.

**2026-10-11 (this session) — cause + fix, pending the live 20-in-a-row.** Measured first: 8 serial calls at a gentle pace all answered 200 (0.35–1.3 s), so the route is healthy when idle — the 502s were NOT a steady fault. What the code did: every upstream failure (generate_link non-OK, verify non-OK, a thrown timeout/network error) collapsed into a bare `502` with the reason discarded, and there was no retry, so ONE transient upstream blip (a 5xx/429 from Supabase admin `generate_link`, or the ~3 min a Pages deploy is in flight) failed the whole sign-in with nothing to diagnose; and every check minted a brand-new magic link, which is the load that coincided with the stretches. The exact historical upstream status is not recoverable (Supabase log retention here is 24 h; the 10-06/10-08 windows are gone) — so this is a hardening, stated as such, not a proven single root cause.
Fix: `functions/api/auth/e2e-session.js` retries network errors / timeouts / 429 / 5xx up to 3 attempts with backoff, and on final failure answers 502 with `stage`, `upstream_status`, a sanitised `upstream_error` (token-shaped runs masked, 200 chars) and `attempts` — no secrets; every security invariant unchanged (POST only, no CORS, 404 without the key, constant-time compare, both account pins). `ui-audit/lib/signedInSession.mjs` caches the test account's session (0600 file, `E2E_SESSION_CACHE` or tmpdir), reuses and refreshes it via `setSession`, and calls the route only when there is no usable cache; route failures print stage + upstream reason. Tests: `test/e2eSessionRoute.test.js` (+7), `test/signedInSessionCache.test.js`.
**Stopping rule (unchanged):** 20 consecutive helper sign-ins with zero 502s after deploy → close.
