`[ ]` **Observed:** repeated multi-second tab-unresponsive stalls while the Review module reads a dropped PDF's title block on import, and during statewide-parcel selection / map zoom over a new area. Didn't fail a test, but it's a real responsiveness issue (and slowed the signed-in pass).
- Verify: live
- **Recurrence: 2026-08-06 — owner repro (chat block "NEW-5", speed half; DEDUPE-FIRST fold — same module, same ~30 s, same named cause).** *"Opening a drawing takes about 30 seconds… 30 seconds is the bug behind the bug. Profile the open path and fix what is actually slow, and report the attribution."* Grand Port > All files > "2026.06.23 Grand Port - Architectural", 49 pages; the real names (FM101, A101, A110, A201–A227) appeared only at the very end. The DISPLAY half of that report — the fabricated "30 SHEETS" count and the "Sheet 1…Sheet 30" row labels — is its own new item, **B208964**, and shipped; this is the speed half, which lands here.
  - **What was measured, and how.** A synthetic 49-page D-size set (2592×1728, ~220 drawn objects/sheet, a readable title block), dropped into the real built app in headless Chromium, timed from the drop to (a) first pixels and (b) every rail row carrying a read label. Three samples each, at 6× CPU throttle to stand in for a heavier real set on a real machine. Harness kept at `scratchpad` scale — this is an attribution, not a new committed instrument.
  - **The one cost I could attribute and remove: the per-page COMMIT, not the per-page read.** `applyMeta` called `setSheetMeta` once per page. Each of those is a full re-render of a 2,500-line component, and each re-runs `refineSheetTitles` + `groupSheets` over the WHOLE set — so an n-page document cost n renders and O(n²) grouping, on the main thread the user is trying to pan and click on. Batching the reads on a 250 ms flush (token-guarded, with a final flush so the tail lands at once) collapses n commits to a handful and changes not one label a human eye would notice.
  - **RESULT (median of 3, 6× throttle): time to a fully-read rail 8,195 ms → 5,847 ms, −29%.** First pixels 1,662 → 1,494 ms (inside the run-to-run spread — unchanged, and correctly so: nothing on the raster path was touched). Unthrottled, 49 pages: 2,636 → 1,683 ms.
  - **⛔ WHAT THIS DOES NOT CLAIM.** I could not reproduce 30 seconds. My heaviest synthetic set reads in ~2.6 s unthrottled and ~8.2 s at 6×, so his real CAD set — real embedded fonts, real vector density, possibly scanned pages taking the OCR path — is heavier than anything I could generate, and the −29% is a share of a smaller number than his. **The remaining cost is dominated by `extractPageItems` itself** (pdf.js `getPage` + `getTextContent`, once per page), which is the actual reading work and is exactly what the "Cause" line above named in June. **The next lever is unchanged and unshipped: move the vector title-block read into a Web Worker** (OCR already is, B352). That is this item's remaining work.
