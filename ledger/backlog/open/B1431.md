- **EVERY CANDIDATE IN THE DISPATCH, MEASURED — five of the six are small or absent:**
  - **(a) THE FOUR-SECOND COINCIDENCE — REFUTED, and it is a coincidence.** Control arm `no-drainage` seeds `settings.drainage.autoFacts = false`, which is exactly what `drainAutoEnabled` reads; the arm demonstrably fires (GIS requests during boot drop **75 → 34**). Two independent interleaved A/B runs, 3 reps each: run 1 **−1.6%** against a ±6.1% floor (INCONCLUSIVE), run 2 **−13.5%** against a ±9.6% floor (clears it). **Pooled, 6 boots per arm: baseline median 7,744 ms (7,420–8,370) vs 7,224 ms (6,772–7,445) — about −0.5 s, with the two ranges overlapping.** So the load-time drainage pass is worth a few hundred milliseconds, NOT four seconds. The arithmetic settles the coincidence on its own: B1349's idle callback is armed **after a 1,200 ms timer** with a 4,000 ms ceiling, so it can only fire between 1.2 s and 5.2 s — and with it disabled the boot still measures ~7 s with the **same shape** (first-paint → canvas 2,851 ms vs 3,573 ms). Phase 2 did NOT move this cost somewhere else; it is not this cost.
  - **(b) parcel-snapshot hydration from IndexedDB — NOT FOUND HERE, and the reason is stated rather than hidden.** All model work together (`Model load & normalisation`) is **465 ms / 5.8%**, and this scenario is a fresh profile with **no stored snapshot to hydrate**, so the durable side is unexercised. Its ceiling in this run is that 465 ms; sizing it properly needs a scenario seeded with a cached county snapshot, which does not exist yet.
  - **(c) the element-sync seed + `normalizeBondedChildren` / `normalizeStrandedZones` / `rowsToModel` — inside that same 465 ms row**, and 163 ms of it lands before first paint. Not the four seconds.
  - **(d) the first roadNet dissolve + pondContours — REAL and the largest named app cost: Clipper 534 ms + site geometry 238 ms = 772 ms (9.5%)**, essentially all of it inside the first-paint → canvas-exists segment (Clipper alone is 491 ms of that 3,573 ms). - **WHAT IS ACTUALLY IN THE FOUR SECONDS, in one sentence: the planner's FIRST RENDER (3.6 s, 100% busy — `SitePlanner.jsx` 968 ms · React 812 ms · Clipper 491 ms) and then THREE MORE SECONDS OF CONTINUED RE-RENDERING after the canvas is already drawn** (V8 390 ms · React 281 ms · `SitePlanner.jsx` 210 ms · Leaflet 190 ms in the first of those two segments, and the same shape in the second). The app does not stop working when it looks finished.
- **WHAT TO ATTACK, with a predicted saving each — proposals, not decisions:**
  1. **The post-draw tail (≈3.0 s, 38% of time-to-first-drag).** Nothing should be re-rendering the whole planner for three seconds after the canvas is drawn. Attribute it further with the same instrument (the boot-order of the map mount / layer sync / overscan settle are the named suspects). **Caveat that has to be settled first:** 350 basemap tile requests are BLOCKED in this sandbox, and failed-request handling is inside this window — a run on a live network could look different. Predicted saving unknown until attributed; largest addressable block by far.
  2. **The road dissolve off the first-paint critical path (Clipper 534 ms).** Predicted **≈400–500 ms**. ⚠ Deferring it changes the FIRST FRAME's picture (roads unwelded for a beat), so it is bound by the B1345 pixel bar; persisting the dissolve across a reload is the version that is not.
  3. **Parse / compile, 1,659 ms (20.5%).** The only lever is fewer boot-path bytes (B1064 / B1130 territory). A 20% cut ≈ **330 ms**.
  4. **The first React commit, 1,587 ms.** ~1,000 canvas nodes on first mount; deferring non-canvas chrome to after first interaction. Predicted **100–300 ms**, and it is the riskiest of the four for what the user sees.
  5. **The load-time drainage pass, ≈0.5 s** — already an owner decision on **B1349**, now with a measured price against it.
- **⚠ TWO LIMITS ON EVERY NUMBER ABOVE.** (i) The last two spine segments include the harness's own CDP round trips for the press and the drag; the page was 98% busy through them, so the lag is real in kind, but the millisecond figure is instrument-shaped. (ii) Source-map naming needs `npx vite build --sourcemap`; without it the run degrades to chunk granularity and says so.
