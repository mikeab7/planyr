### B400177 — The box width handle resized against a STALE left edge, so resizing a box you had moved gave the wrong width `[Notes]` (bug) #notes #ui  *(found 2026-08-13 by driving the control with a real mouse, after the owner reported it as "PRESENT but not behaviour-verified by me — my synthetic drag does not register on this build". Net-new.)*
`[ ]` **⛔ SHIPPED, and it is a defect in code this cohort shipped one round earlier.**
- Verify: sandbox (`ui-audit/verify-notes-box-drag.mjs`, 43/43)
- **THE MECHANISM.** A ProseMirror node view is built once; its `update(next)` re-styles the element but **never rebinds the closure's `node`**, so `node.attrs` describes the box as it was when the view was BUILT. The width handle computed against `num(node.attrs.x)`. Resize a box you had already dragged and the width was measured from its OLD left edge: on a ten-box page, a drag asking for **90 more** produced **34 less**.
- **AND A SECOND, SMALLER ONE FOUND BY THE SAME PASS.** The box's right edge JUMPED to the pointer on grab, so asking for 90 gave 86 — a silent re-seat, which is precisely what the move drag's own comment forbids. The handle now keeps its grab offset the way the move drag keeps `grabX`. Exact to the pixel afterwards: asked 90, got 90; at zoom, asked 72, got 72.
- **THE DEAD FIELDS ARE GONE, not left unused.** The move drag's `from` object still carried `x`/`y` read from the same stale `node.attrs`; nothing read them, which makes them a trap for whoever edits this next.
- **WHAT THIS SAYS ABOUT THE PREVIOUS ROUND.** The control was shipped with a test that found it in the DOM and never drove it. "The button is there" and "the button works" are different claims, and only the second one is worth making. The harness now drives it with a real mouse in both directions, asserts the box does not MOVE while it resizes, and reloads to prove the width is stored rather than styled.
