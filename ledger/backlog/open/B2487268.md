`[x]` **(a) Does the Notes UI offer trash/restore?** Yes. Delete is a SOFT delete into a 30-day Bin: `Notes.jsx` `deleteNode` (tree) + `markPagesBinned` (cloud rows get `deleted_at`, body kept). The rail's third view is the Bin with **Restore** (`handleRestore` → `markPagesRestored`), a read-only "Read it" peek, **Delete forever** (`handlePurge`), "clear the empty ones" (`handlePurgeEmpties`) and "empty the bin" (`handlePurgeAll`). A binned entry older than the window is purged for real on the next Notes load (`expiredTrashIds` → `purgePages`).
`[x]` **(b) Which path sets `purged_at` at delete time?** None does. `purged_at` is set in exactly one place, `notesCloud.purgePagesCloud`, which writes `{doc:null, purged_at: stamp, deleted_at: stamp}` — **the SAME stamp into both columns, overwriting the original bin time.** So the 201 rows with `purged_at = deleted_at` and a NULL doc are *exactly what every purge produces*, not evidence the content was destroyed at the instant of deletion; the real delete time is gone, so the data cannot say whether a row sat in the Bin first. Callers of that function: Delete forever, "clear empties" (sixteen of one real account's twenty-one bin rows were empty notes), "empty the bin", the 30-day expiry, and the interrupted-purge finishers (`plan.purge`, `plan.repurge`). **The 26 rows that kept their doc with `purged_at` NULL (all `e2e@planyr.test`, deleted 2026-10-05→10-11) are the Bin working as designed** — soft-deleted, body intact, still inside the 30 days; not a second code path, and consistent with the e2e harness binning rather than purging.
`[ ]` **The decision only Michael can make — two contracts, no pick made here:** (1) **Delete means gone, and the UI says so** — keep today's behaviour but stop overwriting `deleted_at` on purge so the record shows when each page was deleted, and word the Bin/Delete-forever confirmations plainly. (2) **A retention window with prove-then-destroy** — keep the Bin, but make a purge refuse unless the page has been binned the full window (and say so), the way the Library purge now proves before it destroys (B2487264). Neither changes data already purged; those bodies are unrecoverable from this table either way.
