- **WHAT WAS ESTABLISHED THIS SESSION, so the next one starts from measurement rather than from scratch:**
  - **⛔ THE OWNER'S QUESTION ABOUT THE EXISTING CLOCK CONTROL IS ANSWERED, AND THE ANSWER IS "EXTEND THE SHELL, NOT THE DATA".** There IS a clock: `HistoryIcon` → **Version history**, and it is a row in the **Plans ▾ header menu**, not in the map control cluster (the canvas cluster is Undo / Redo / Zoom-to-fit only). Its data is `storage.js`'s `planarfit:sites:history:v1` — a ring of **15 whole-plan snapshots, per DEVICE**, `{ at, buildings, summary, sig }`, never pushed to the cloud, **with no actor and no operation**. So it is the wrong grain and the wrong scope for a plan-activity feed: reuse the dialog chrome and the menu affordance, source the list from the rows, and do NOT try to widen the version ring.
  - **A PER-TAB SESSION ID ALREADY EXISTS AND SHOULD BE PROMOTED, NOT MINTED.** `elementJournal.journalSessionId()` is `sessionStorage`-backed — per TAB, surviving a reload, which is exactly the lifetime `actor_session_id` needs. (Two weaker candidates exist and should not be used: `randomIdSalt()` at `SitePlanner.jsx` is per-page-load and already baked into element ids, and `multiTab.js`'s `tabId` is per-realm and shared by every workspace header in one tab.)
  - **`updated_by` / `deleted_by` ARE NOT DECORATIVE — the owner's word, and it is worth correcting.** They are stamped server-side from `auth.uid()` on all five write statements and are load-bearing today: `elementSync.foreignAuthor()` reads them for own-echo suppression (B1116) and for the conflict-toast name resolver. The gap is real but narrower than stated: they carry an ACCOUNT, and both live sessions authenticate as the same account, so they cannot answer "was that my other tab". **Session granularity is what is missing, not attribution.**
  - **THE MERGE ALREADY LANDS IN ONE BATCH, incidentally rather than by design.** `mergeParcels` does `setParcels(...)` + `tombstone(goneIds)` in one React handler, so the autosave diff produces the deletes and the create in one `commit_elements` call. It is NOT atomic (`batchSpansAssembly` is about bonded buildings, and parcels are not), and nothing marks the three ops as one logical act. So `op_id` + `op_kind:"merge"` is a labelling change on a batch that is already whole — which is the cheap half.
  - **`reconcile` already carries a `direct` flag** (real user touch vs cascade relayout) — the closest existing thing to an `op_kind`, and the natural seam to widen.
- **THE PLAN, in the order it should be built:**
  1. **Envelope on the wire.** Extend `opFor` (`elementSync.js`) with `op_id` / `op_kind` / `actor_session_id` / `client_ts`; a 5-arg `commit_elements` overload; **columns on `site_elements`, not a separate `operations` table** — the rows are already the record, a side table would be a second copy of a fact the rows can carry (the mistake the `group_rev` column would have been), and every read path already selects from this one table. Follow the `site_elements_assembly_id.sql` precedent for the DDL and the `elementApi` PGRST202 latch precedent so an unapplied migration degrades instead of failing.
  2. **One op per user-visible action.** Mint the `op_id` where the gesture is (`pushHistory` is already the one-per-action seam) and thread it through the diff, so a merge's deletes and create share it.
  3. **Presence names names.** `ch.track({ uid, name })` gains `sessionId`; `presencePill` keys names by session and marks which is ME.
  4. **Activity view**, reusing the Version-history dialog shell, reading grouped ops.
  5. **Undo ownership.** `history.js` frames gain a meta sidecar (`push(current, meta)`); Undo names what it will undo and refuses / requires explicit confirmation when the top frame is not this session's.
- **SCOPE FENCE, from the owner verbatim: no full CRDT, no audit-log UI, no per-keystroke history.** The bar is that a human or agent looking at the plan five minutes later can answer "who did this, and what were they doing" without reading the database.
