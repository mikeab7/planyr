**ITEM 1 — IS THE EMPTY PROJECT MEANT TO BE LOCAL-ONLY? YES, AND IT ALREADY WAS DELIBERATE — this is not a new decision, it's confirmed against an existing one.** `SitePlannerApp.jsx`'s `newBlankSite()` (the "+ New project" handler with no address/parcel picked) writes NOTHING — no `saveSite()` call at all, no `public.sites` row, no local plan record — until the plan's first real edit; its own header says so verbatim ("a blank site that's never edited should never be saved"). This is exactly the root `/CLAUDE.md` → **Owner product constraints** entry 5: *"Project creation is deliberately LAZY. Never create a `sites` row for every abandoned 'New project' click — the row is materialized only by a module's first real write"* (2026-09-05, citing B1160480/B1202176). The CONTROL project in the report (`smtuc8z2x9w0`) got its row immediately because it was created WITH an address/parcel — that's the OTHER branch of `newBlankSite`/`newSiteFromMap`, which writes immediately because "an anchor is a fact worth keeping even before anything is drawn." So the write path works; the two empty shells are the deliberately-lazy path working exactly as designed, not a persistence bug.

**BUT THE BRIEF'S OWN RULE APPLIES: since it's deliberate, the UI must stop presenting it as a saved project — and it was.** A never-saved project has no local plan record, so it can only ever appear in the project switcher via `withCurrentProject`'s synthetic "the project you're standing in" placeholder (`projectModel.js`) — it never shows up in `listProjects()`, the real on-device/cloud registry. Yet the dropdown's delete confirmation (`ProjectBreadcrumb.jsx`) said, unconditionally, for every project: *"Delete X? It moves to Recently deleted — you can restore it for 30 days."* For a project with nothing anywhere to move, that promise is false — and the owner's separate report ("delete does nothing … Recently-deleted count doesn't move") is exactly what happens when a user believes that promise and then sees it not come true. **Fixed:** a new pure decision, `hasSavedProjectRecord(id, registryProjects)` (`projectModel.js`), asks whether an id is actually present in the real registry (never a list already unioned with the synthetic placeholder, which would always answer true for the one case this exists to catch). `ProjectBreadcrumb.jsx`'s confirmation now reads honestly for such a project — *"X hasn't been saved yet — there's nothing on the server (or this device) to delete. Closing it just leaves it behind; it won't be in Recently deleted."* — with the action button reading **Close** instead of **Delete**. A genuinely saved project (the overwhelming common case, and every existing e2e/ui-audit fixture) is completely unaffected: same "moves to Recently deleted" copy, same "Delete" button, proven below.
