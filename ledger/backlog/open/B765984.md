- **BOTH removed, not just export, and here's why the import mattered more.** The import's own tooltip admitted it "replaces the current canvas" with no confirmation dialog anywhere in its path — a destructive whole-plan overwrite one row below a harmless PNG download, in a project that has already had a real data-loss incident (57 of 95 elements wiped on a real plan, `BACKLOG-DONE.md`). An import with no way to produce its own input file is also just dead weight once export is gone. Removing this pair is a safety win, not only decluttering.
- **AUDITED FIRST, per the task's own instruction: is the serialiser shared with autosave / plan duplicate / templates / the Library?** No. `exportJSON` (in `lib/exportSheet.js`) built its own standalone `Blob` from the live collections and was called from nowhere but this menu button. `importJSONFile` (in `SitePlanner.jsx`) parsed a dropped file through `createSiteModel` — the SAME model funnel autosave/cloud-save/duplicate/Library all use — but it was the ONLY caller that fed it a user-picked file; autosave, `duplicatePlan`, and the Library's file browser all call `createSiteModel`/`storage.js` directly on already-in-memory or already-fetched data, never through this import path. So `createSiteModel` (the shared funnel) was left completely untouched — only the menu entries and their two dedicated functions were removed.
- **What was removed:** the two `<button>` menu items and the hidden `<input type="file">` in the File ▾ menu (`SitePlanner.jsx`); `importJSONFile` + its `importRef` (`SitePlanner.jsx`); the `exportJSON` wrapper (`SitePlanner.jsx`) and the underlying `exportJSON` function + its entry in the returned API (`lib/exportSheet.js`).
