### B603841 — MasterView's health-cell renderer has no `|| HEALTH.gray` fallback (crashes on an unknown health key) `[Scheduler]` (bug) #scheduler #ui  *(self-discovered 2026-08-17 while mutation-testing B603840's Automatic-clear guard — NOT an owner report. DEDUPE-FIRST — searched Open/⏳ Verify/Done for `HEALTH.gray`, `MasterView` crash, `dispHealth`: no prior item.)*
`🔲` **Open — found, filed, NOT fixed (out of scope for the item that found it, per its own "smallest correct change" brief).**
- Verify: sandbox
- **THE DEFECT.** MasterView's `renderCell`, case `"health"`, reads `const h = HEALTH[dispHealth];` with no fallback — every OTHER `HEALTH[...]` lookup in this file guards it (`HEALTH[value] || HEALTH.gray`). If `dispHealth` is ever a key `HEALTH` doesn't recognize, `h` is `undefined` and the very next line (`h.dot`) throws, taking down MasterView's whole render (caught by the app's `ErrorBoundary`, so the failure is a broken Dashboard tab, not a blank page — still a real crash).
- **HOW IT WAS FOUND — and this is the ONLY confirmed trigger.** A deliberately-broken build (testing B603840, `--mutate-automatic-grid`) let the internal sentinel string `"__auto__"` leak into a task's stored `.health` field — something the real, unmutated code can never do (the sentinel is always intercepted before it reaches storage). This trigger is NOT reachable in production; it exists only inside that mutation test.
- ~~**THE REAL, REACHABLE TRIGGER:** a task holding a CUSTOM health status (`data.settings.customHealth`) that the user later renames or deletes from Standards. `HEALTH` is rebuilt from `customHealth` on every settings change (`rebuildHEALTH`); a task's stored `.health` is not migrated when a custom status disappears, so any task still carrying the old key would hit this exact crash the next time MasterView renders it.~~
- **⛔ CORRECTION (2026-08-17, same day, before this item was ever picked up) — the struck claim above is WRONG and was filed without checking the deletion code first.** The delete-a-custom-status path is **already guarded**: `removeOption` (`public/sequence/index.html` ~line 8246) reassigns every task still carrying the status being deleted to `"gray"` **before** removing it from `customHealth`, specifically to prevent this exact crash — its own comment says so verbatim (`"...so no view dereferences a now-missing HEALTH key and crashes (B1)"`). So that is not the reachable path either. **No genuinely reachable real-product trigger has been found, and none has been ruled out — this is UNPROVEN in both directions.** Recommendation: leave filed, do NOT dispatch, until someone actually finds a real path in (a multi-device/sync race around a status deletion is the one untested candidate, not confirmed).
- **STOPPING RULE:** closes when MasterView's health-cell lookup guards the same way every other `HEALTH[...]` read in this file already does (`HEALTH[dispHealth] || HEALTH.gray`) — that fix is cheap and safe regardless of whether a real trigger is ever found — **or** when a genuinely reachable real-product trigger is found and confirmed, whichever comes first. A repro via `removeOption`'s delete path is NOT a valid closing test (see correction above); anyone attempting one will find it already passes for the wrong reason.
