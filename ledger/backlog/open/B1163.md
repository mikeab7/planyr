`[ ]` **Open — deliberately unfixed.** The runtime harness's `siteRouteChunks` assertion walks the chunks the browser actually FETCHED — dynamic imports included — and tests them against the STATIC allowlist. So it names `rasterIdentifyMap`, `rasterIdentify`, `featureHover` and `terrainLayers` as intruders when all four are lazy **by design**, and it reports a breach on every run. Confirmed again 2026-07-30 during the B1157 work: `✗ runtime.siteRouteChunks — UNEXPECTED CHUNK(S) FETCHED ON A SITE ROUTE: rasterIdentifyMap, rasterIdentify, featureHover, terrainLayers`.
- Verify: sandbox
- Origin: filed 2026-07-30 from chat
- **Why nothing is red.** This half of the harness is not CI-gated (only `perf-bundle-audit.mjs` is), so the false breach costs nothing today except that anyone running the runtime harness has to know to ignore one line — which is how a guard stops being read at all.
- **Why it was left alone.** Loosening a guard nobody has diagnosed is how guards die. The right fix needs a decision this item does not pre-empt: either the allowlist grows a *dynamic* section (naming the chunks that MAY be lazily fetched on a Site route, so a genuinely new boot-path import is still caught), or the assertion is narrowed to statically-imported chunks only and the lazy set is checked separately. The first keeps the NEW-9 prefetch regression catchable; the second is simpler and catches less.
- **Related:** the deterministic `bundle.siteRouteAllowlist` check in `perf-bundle-audit.mjs` is a *different* assertion over the static manifest and is working correctly — it caught a real new chunk during the B1160 work and was honoured rather than raised.
