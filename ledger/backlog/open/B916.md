### B916 — Project sharing model: one grant per grantee, module-visibility mask, viewer-only v1 `[Backend / Sharing]` (feature) #infra #auth #persistence  *(owner-dropped 2026-07-21 as "NEW-2", top-of-queue; minted **B916** via `npm run next-id -- --against-main`. Schema/RLS DRAFT written this session — see below.)*
`[ ]` A more granular sharing model than today's team-based share: the unit of sharing is the **project**, a grant is **(project → grantee)** where grantee is a user OR a team, exactly one live grant per (project, grantee), and each grant carries a **module-visibility mask** (which modules the grantee can see) rather than sharing everything. Default on share = every module the grantor can see; uncheck to redact. **v1 role = viewer only.**
- Verify: **live** — **⛔ BLOCKER: `auth` + concurrency.** This is a security-critical RLS change on REAL user data whose core acceptance ("**revoke is immediate and verified** — re-run the access check post-revoke and confirm it returns `false`, crash-severity if it doesn't") can ONLY be confirmed with **two signed-in accounts** in the live app. The sandbox blocks Supabase sign-in (proxy CORS) and has no second account, so this **cannot be shipped-and-verified in one session** and is NOT auto-applied to production — see "What's blocked" below. This is the STANDING-RULE-#1 "too large / hard-blocker → raise with a plan, don't ship half" case, flagged loudly.
- Origin: filed 2026-07-21 from chat ("NEW-2").
- **DEDUPE-FIRST (searched Open / ⏳ Verify / Done for shar*, grant, team, RLS, access, viewer):** related but NOT a dup of **B406** (the EXISTING team-workspace share — whole-project `sites.team_id`, all-or-nothing, teammate-can-edit) or **B714** (the B406 model's share-reverts bug). NEW-2 is a *new, additive, finer-grained* model (per-grantee, per-module mask, viewer-only) that sits ALONGSIDE the team model, not a rewrite of it — a `team_id`-shared project keeps working; a `project_shares` grant is a second, independent path. When both cover the same (project, user), access is the UNION (either grants read). **Design note flagged for the owner:** whether `project_shares` eventually SUPERSEDES `team_id` sharing is a product call to make later — v1 just adds it without touching the team path.
- **Schema (DRAFT written this session → `src/workspaces/site-planner/db/project_shares.sql`, NOT yet applied):** `project_shares` (id, project_id, grantee_type `user`|`team`, grantee_id, role, **modules text[]**, created_by, created_at, revoked_at) with a partial-unique index enforcing exactly ONE live (`revoked_at IS NULL`) grant per (project, grantee); `teams` / `team_members` (reuse the B406 tables if present, else create); `share_events` audit log (who granted/revoked what, when). **`modules` is a `text[]` of module keys, not boolean columns** — adding a future module (e.g. `notes`) is a data change, not a schema+policy rewrite.
- **RLS (one helper, called from every table):** a single SECURITY-DEFINER SQL function **`has_project_access(project_id, module, min_role) → boolean`** — true when the caller owns the project, OR has a live `project_shares` grant whose `modules @> {module}` and role ≥ `min_role`, OR (union) a live team share. Every project-scoped table's SELECT policy becomes a **one-line call** to it with that table's own module key. (Draft policies for `sites` / `doc_reviews` included in the SQL file, commented as illustrative until the live pass.)
- **Non-negotiables (all in the DRAFT):** default **private** (a new project = zero grants); **no god-mode / cross-user admin read**; **revoke is immediate + verified** (post-revoke access check must return false — the live gate); every grant/revoke **undoable as one step**; a failed share write **surfaces loudly** (LOUD-FAILURE — never optimistic-only UI). v1 grantee scope = **existing accounts only** (no invite-by-email flow yet — that's a separate follow-on: needs pending accounts + invite emails + an accept-flow, scoped once this lands).
- **Out of scope v1:** anonymous/public links; invite-by-email for non-accounts; commenter role (implies a per-module comments system that doesn't exist — a dead checkbox without it); editor role (blob-level cloud save makes two editors silent last-write-wins data loss until the per-element `site_elements` sync migration ships); element-level ACLs inside a module.
- **Grantee experience:** shared projects appear on the grantee's map with a visible "shared with you" distinction and are filterable.
