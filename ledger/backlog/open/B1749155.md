`[ ]` **Repro (confirmed live this session, not guessed):** a side-parking (employee parking) field bonded to a building via `sideParkSide`, positioned off the wall's centred span default — however it got there, including a plain drag of the field's BODY along the wall — carries no `sideParkFit` stamp unless the LAST thing that touched it was specifically an along-wall edge-drag or the properties-panel Length input (the only two gestures that call `relayoutWallKids`/`sideParkAlongRun` with `pinFrom` set to that field). The very next assembly-integrity pass — which runs ambiently on load and after any other edit via `assemblyGuard`/`assemblyIntegrity`/`normalizeBondedChildren` (`lib/siteModel.js`'s `normalizeHostRuns`, `pinAllowed: false` by construction for that seam) — reads the field as "unstamped, off the span default" and resets its along-wall position and run back toward the wall's centred default, per the deliberate "no stamp ⇒ default" policy (dogEar.js NEW-2). **The gap: a plain MOVE of the field's body is a real, available canvas gesture (`d.mode === "move"` in `SitePlanner.jsx`, the generic per-element drag translate) and it never calls anything that stamps `sideParkFit` — so a user who repositions an employee-parking field by dragging it (rather than by trimming an edge) can never make that reposition survive the next heal.** Confirmed directly: constructing a field at a valid, on-wall, off-centre position (matching exactly what a plain move would leave behind) and merely reloading the plan — with ZERO further interaction — snaps it back to centred/full-span.
- Expected: repositioning a side-parking field along its wall by dragging its body should persist through the next reload/edit, the same way trimming its length via an edge-drag already does.
- Likely fix shape (not yet implemented — this is a diagnosis, not a plan to follow blindly): on pointer-up of a `mode: "move"` drag whose grabbed element carries `sideParkSide`, call the same `relayoutWallKids(..., { pinFrom: el.id })` the resize path already uses, so the field's NEW along-wall position gets exactly the same "is this off the default → stamp it" treatment a resize gets. Needs care: `d.mode === "move"` is the single shared handler for EVERY draggable element kind (buildings, markups, roads, …), so the side-park-specific stamping must be gated tightly (only fires for an element with `sideParkSide`, only on the FINAL committed position, not per-frame) to avoid adding cost or side effects to the general move path this repo's own `dragGate.js`/`click-never-moves` guards are built to keep clean.
