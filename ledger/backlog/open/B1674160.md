`[x]` **IMPLEMENTED AND SANDBOX-VERIFIED.** Repro (measured on deployed build 533ef3f, chunk `SitePlannerApp-BdTHtd59.js`, a throwaway duplicate plan, a callout selected): the label-gutter cell's `getBoundingClientRect().left` read 79.66 in a single Field row, 79.66 in a paired PairedField row, and **81.66** in the FILL/LINE PairedFieldHead row above them — the header rendered 325.8 CSS px wide where every other row in the same panel rendered 329.8, and the FILL header text started at 151.65 while the fill-column controls beneath it start at 149.66.
- **Root cause.** `PairedFieldHead` (`SitePlanner.jsx`, alongside `Field`/`PairedField`/`StdSubLabel`) set inline `margin: "10px 2px 7px"` — a three-part shorthand whose middle (horizontal) term was meant to be `0`; every other row in these panels sets `marginBottom` only, with no horizontal margin at all. `StdSubLabel` (the plain single-column sub-heading used above e.g. "Parcel line"/"Setback line" in the Standards → Parcels panel) carried the byte-identical stray margin and is fixed alongside it — same defect, same shorthand typo, a different function.
- **Vertical rhythm is preserved on purpose** — only the horizontal `2px` term changed, to `margin: "10px 0 7px"` on both. The `10px`-above/`7px`-below spacing that separates a header from the group above it is unchanged.
- **Because `PairedFieldHead` is the ONE shared component, the fix lands on every panel that uses it at once** — confirmed live, not assumed: re-verified the text box/callout panel (Chromium + real WebKit, both objects, 5 size/orientation combos) and the Standards → Parcels panel (which combines `StdSubLabel` + `PairedFieldHead` + `Field` + `PairedField` in one screen — the parcel-line/setback-line sub-headings, the Outline|Fill header, and every field row all now read the identical left edge, 80px, in a headless Chromium run). The same component also serves markup, measurement, easement, the shared Properties section, the pond Appearance group, Standards → Measurements, and the multi-selection style panel — no separate fix was needed for any of them because none of them carries its own copy of this styling.
- **GUARD, mutation-proven.** A prior alignment check (`ui-audit/verify-callout-outline-style.mjs`) measured a real rendered box, but only across `[data-field-group="1"]` elements — and `PairedFieldHead` never carried that attribute (it marks a value-entry row for the keyboard-scope latch; a plain header holds no input), so the check silently measured **zero** header rows and reported "one left edge" while the header itself sat off by 2px. Both `Field`/`PairedField` (alongside their existing `data-field-group`) and `PairedFieldHead` (alone) now also carry `data-row-align="1"`, a marker that exists ONLY to let an alignment check find every row KIND including the header; the harness now measures via that marker instead, and separately asserts the header row is actually present in what it measured (so this specific blind spot can't recur silently). Verified the guard has teeth the way this repo requires: reverted the header's margin to the old `2px` value, rebuilt, and the check went red (`edges seen: 80,82`) — reapplied the fix, rebuilt, and it went green (`edges seen: 80`) again.
