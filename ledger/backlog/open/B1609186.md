**THE DEFECT.** `scripts/verification-queue-audit.mjs --check` compares today's stale-pending count against a committed snapshot (`scripts/verification-queue-ceiling.json`). "Stale" means *the newest date in the item's block is more than 60 days old* — a function of the CALENDAR, not of any diff. So the count rises on its own, with nobody changing anything, and the moment it passes the recorded ceiling the gate reds out on every PR into `main` at once. Measured history of the ceiling: **0 → 7 (2026-09-11) → 10 (2026-09-12) → 13 (2026-09-15)**, three refreshes in four days, each one a repo-wide block discovered by whichever session happened to run the gate next. A ratchet on a clock has no fixed point.

**WHAT WAS DONE NOW, AND WHY IT IS NOT A FIX.** This session re-ran `--write-ceiling` (staleCeiling 10 → 13), which is the maintenance step the script's own header documents for exactly this drift and the same remedy `4594c83d` used. It unblocks the repo and it acknowledges an already-true count — no item was resolved, silenced, or re-dated, and `noBlockerCeiling` is untouched at 155. But it buys days, not a fix, and the next session pays the same tax.

**PROPOSED FIX (not implemented here).** Judge the gate against the BASE REF rather than a committed snapshot, the way the bundle gate already does: compute the stale/no-Blocker counts on `origin/main`'s own `VERIFICATION.md` **as of the same `now`**, and fail only if THIS branch's diff makes them worse. Calendar drift then moves both arms equally and can never fail anyone; a session that parks a new no-Blocker or newly-stale item still goes red immediately. That also deletes the snapshot file and the "remember to refresh it" ritual entirely.

**THE 13 STALE ITEMS ARE NOT SANDBOX-CLOSABLE, which is why "just close them" is not the answer either.** V6 (a sub-frame white flash — needs a human eye or a video capture), V285/V286/V287/V289/V291/V292/V293 (signed-in production + real project data), V301/V303/V304, V329/V330 (a real slow/blocked tile host, and live Esri/USGS endpoints the sandbox egress blocks). Every one names a real wall in prose; they trip `noBlocker` only because they describe it in a sentence rather than with the literal `Blocker: <kind>` tag. Tagging them would improve THAT metric and would not move `stale` at all, which is date-based only.
