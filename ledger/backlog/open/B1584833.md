`[ ]` `rename_site_group.sql`'s `p_renamed_at bigint` parameter is supplied by the CLIENT (`cloudRenameGroup` sends `Number(renamedAt) || Date.now()`, computed on the user's own machine). A device whose clock runs meaningfully behind the server can therefore push a rename that is timestamped *older* than it actually happened. Today's guard (`sites_preserve_rename_stamp`) only checks for the PRESENCE of a real stamp, so this is latent; NEW-1 (a 2026-09-12 companion dispatch) is changing that guard to a RECENCY comparison, and B1584832's backfill seeds 87 previously-unstamped rows from their own `updated_at` — under a recency guard, a genuinely later rename from a clock-skewed device could lose to one of those backfilled values, silently reproducing the exact "my rename didn't stick" symptom this whole family of fixes exists to prevent.
- Verify: sandbox — a unit/mutation test proving the RPC's stamp no longer depends on client-supplied time is sufficient; no live click-through needed.
- The fix named by the dispatch, and almost certainly the right one: stamp `p_renamed_at` SERVER-SIDE inside `rename_site_group` (`now()`), removing the client clock as a source of truth entirely — the same "collapse to one source of truth" instinct NEW-3 (a sibling 2026-09-12 dispatch) is applying elsewhere in this same family.
- **Why this is its own item and wasn't folded into B1584832:** `rename_site_group` is the LIVE PRIMARY rename path (B1568880) — every real user rename goes through it right now. Its client half (`storage.js`'s `renameSiteGroup`) computes `at` once and writes the SAME value to local storage synchronously *before* the cloud call even starts ("ONE stamp for the whole rename," per that function's own header) — so making the RPC mint its own `now()` desynchronizes the local and cloud copies of every future rename unless the client is also changed to adopt whatever stamp the RPC actually used (e.g. read it back off the RPC's return row before finalizing the local write, or accept a small always-present drift between the two copies and confirm nothing depends on them matching exactly). That's real client-side follow-through on a live, frequently-used write path — it deserves its own scoped change with its own tests, not a rider on a data backfill.
