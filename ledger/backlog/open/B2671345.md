### B2671345 — Emailed sign-in code: cap wrong guesses per account (Planyr-issued code, burned after 5 misses)
🔲 Open · #auth #security · Verify: live
Found by the adversarial review of PR 3103 (AI agent access). Today the 6-digit code is Supabase's own email OTP, checked by
`supabase.auth.verifyOtp` straight from the browser with the anon key: no per-account miss counter, only Supabase's per-IP
verify limit, and the code shares the link's 1-hour life. Each wrong typed code also costs two verify calls (type `email`,
then the `magiclink` fallback), so the per-IP budget drains twice as fast.
Fix (reviewer's proposal): leave Supabase's `email_otp` out of the mail; mail a Planyr-issued 6-digit code stored as an HMAC
(same HMAC email key the mail caps use) with a miss counter. A Planyr function burns it after 5 misses and redeems a good one
server-side into Supabase's `hashed_token` (verifyOtp token_hash), so the browser never guesses against Supabase directly.
Consider a 10 to 15 minute code life while the link keeps its hour. Drop the double verify call in the same change.
Closure: on planyr.io, 5 wrong codes then the right one is refused and says to send a new code; a fresh code signs in.
