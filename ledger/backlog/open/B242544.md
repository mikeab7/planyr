**AUDIT FIRST — the brief named four candidate causes and it was NONE OF THEM.** Each was measured on the real DOM rather than reasoned about, and each was refuted: **(a)** the flexbox `min-height: auto` trap — refuted, every element in the chain already carried `minHeight: 0`; **(b)** an ancestor clipping with `overflow: hidden` — present (the card, for its rounded corners; the map pane) but not the cause, they clip a box that should never have been that tall; **(c)** the scroll container being the wrong element — refuted, the scroll box was written correctly with `flex: 1; minHeight: 0; overflowY: auto`; **(d)** the brief's STRONG CANDIDATE, the wheel-zoom handler eating the gesture — refuted by reading it: `SitePlanner.jsx`'s non-passive wheel listener already opens with `if (e.target.closest("[data-wheelscroll]")) return;` and the Layers card already carries that attribute. **Every module involved was correct in isolation.** The defect existed only in the resolved cascade.

**The actual cause, measured.** The card row between the positioned container and the cards had `maxHeight: "100%"` and therefore a height of `auto`. A percentage `max-height` resolves against the containing block's height **only when that height is definite**; against a content-driven one it computes to `none`. So the Layers card's own `maxHeight: "100%"` silently became no limit at all, the card grew to its full content height, and the scroll box — correctly written — never overflowed and so never scrolled. Measured on a 1280×600 viewport: **the card stood 1568px inside a 500px slot, and the last of 27 rows sat 641px below the bottom of the window.** The fix is one word — `height` instead of `maxHeight` on that row — which makes the percentage resolvable and re-arms every descendant's `maxHeight: "100%"`.
- **It failed at EVERY realistic height, not only short ones** (the brief asked). Because the card resolved to its content height regardless of the room offered, the shortfall scaled with the viewport rather than shrinking: 1000/800/700/600px tall all failed. All four are asserted so a fix that only works with plenty of room cannot pass.
- **It was the panel BODY, not a nested group** (the brief asked). One scroll box, one missing precondition.
- **`pointerEvents` had to move in the same edit, or the fix trades a scroll bug for a dead map.** That row is only as tall as its content today; a full-height version still claiming pointer events would lay an invisible click-eating strip down the right of the map wherever the cards are not — worst with both collapsed. The row is now transparent to the pointer and each card claims its own presses back. Asserted directly: with both cards collapsed, a press 200px below them lands on the canvas.
- **The other side panels do NOT have this bug, and the reason is instructive.** Checked rather than assumed: `FloatingPanel` gets a definite `maxHeight: min(72vh, 620px)` on a `position: fixed` card, and the docked left-rail panels (Properties / Standards / Notes / Yield) sit in a rail whose height is definite from the shell. Both resolve their percentages fine. The shared ancestor that needed fixing had exactly one broken descendant chain, so the fix is in one place — not four, and not a shared abstraction invented for a problem only one surface has.
- **⛔ NO FURNITURE ADDED** (the brief's constraint): no scrollbar chrome, no collapse-all, no virtualization. Three CSS properties on one element, plus the pointer-events consequence.

**⛔ THE PART WORTH REMEMBERING: B1423 INTRODUCED THIS, AND BOTH OF ITS SCROLL GUARDS WENT GREEN ON IT.** B1423 built this flex column and claimed "group headers stick so you can still tell which group you are in after scrolling." Its spec (`e2e/layers-panel-legibility.spec.js`) was re-run against a deliberately re-broken build for this item and **all four specs passed**. Two of them are scroll guards and each rotted green a different way:
- The sticky-header guard proves the list scrolled — but only after **writing the missing precondition in itself**: `scroller.style.maxHeight = "180px"; scroller.style.height = "180px"`. That injected `height` is precisely the definite height the real cascade lacked. **A guard that supplies the precondition whose absence is the bug can never detect it.**
- The "many more than four rows" guard counts rows inside the scroller's rectangle and asserts ≥ 10. On the defect the scroller was 1537px tall, so **all 27 rows were "inside" it** and the check passed emphatically — measuring "rows visible without scrolling" against a box that had grown past the window.
- The new spec avoids both traps by asserting only properties the user can observe: `scrollHeight` vs `clientHeight` on the untouched element, and **a real wheel gesture** rather than `scrollIntoView` (written with `scrollIntoView` the last-row test also passed on the bug — it walks up and scrolls any ancestor that will move, including ones the user cannot reach). The wheel gesture doubles as the standing check on candidate (d).
