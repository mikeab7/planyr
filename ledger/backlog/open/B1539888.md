### B1539888 — Right-click on the parcel acreage label opened the BUILDING's menu instead of the label's own — a label's hit region must belong to the object it describes, always `[Site Planner / selection]` (bug) #site-planner #ui #selection #parcel  *(owner chat block 2026-09-11, arrived as NEW-1, with screenshots: on a plan where the parcel acreage label sits over a building footprint (443'×135' with dock zones top/bottom), right-clicking "Parcel 1 20.xx AC" opened the BUILDING's context menu — Reshape…, Bump-outs, Dock Zones, Arrange, Properties…, Copy, Duplicate, Lock, Align rotation…, Attach to…, Delete — with "Hide acreage label" nowhere in it. Minted **B1539888 / V1105584** LATE via `git fetch origin main && npm run next-id -- --against-main`, from this branch's reserved block B1539888–B1539903 · V1105584–V1105599 against `origin/main` d8f6bc8; code, tests and commits keep the provisional `NEW-1` label. **DEDUPE-FIRST — searched Open / ⏳ Verify / Done across `acreage badge`, `onChipContext`, `Hide acreage label`, `data-chrome`, `resolveDoubleClickTarget`, `chrome`, `right-click`, `B280402`, `B316865`, `B1327`, `B233153`, `B278576`:** this is the mechanism's FOURTH appearance and the direct consequence of the THIRD. **B1327** gated the badge on selection, then hover, so it could be dragged. **B280402** made the badge `data-chrome` — identity-transparent for the DOUBLE-CLICK resolver only — after it ate a double-click meant for the pond underneath. **B316865** (⏳ Verify, never confirmed live — see its amendment below) then made the RIGHT-CLICK handler ask that same resolver and forward the press to whatever the resolver found, to fix the mirror-image complaint (right-clicking his pond, with the badge merely resting over it, opened the parcel's menu). That forwarding is exactly what THIS report hits: `polylabel` deliberately anchors the badge on the developed middle of a lot (B1186), so "something real is under it" is the ORDINARY case on any built-out parcel, not the rare one B316865 was built around — forwarding made the badge's own menu practically unreachable everywhere the owner actually works. **This item REMOVES B316865's forward entirely** rather than patching it a fifth time; see B316865's own entry, amended below, for why that is a deliberate reversal of ITS fix and not a defect in it.)*
`[x]` **SHIPPED.** `onChipContext` (`SitePlanner.jsx`) no longer asks `resolveDoubleClickTarget`/`hitStackAt` or forwards to `featureContextAction` — it opens the parcel's own menu unconditionally, the same direct-dispatch shape every OTHER label on the canvas already used (the pond label's `onContextMenu={(e) => onElContext(e, d.el.id)}`, the parcel boundary's `onContextMenu={(e) => onParcelContext(e, pc.id)}`, etc.) — none of which ever forwarded to whatever they happened to sit over. The rule, stated once for every label the canvas draws: **a label's hit region belongs to the object it describes; a label painted above an element must also test above it.** The acreage badge's hover-gated hit box already matched this exactly — `parcelChips` builds it as the literal rect the pill paints (`box: boxOf(c.x, c.y, boxW, boxH)`, the same `boxW`/`boxH` the `<rect>` draws) — so reaching the handler at all already meant the cursor was genuinely on the opaque, drawn label with nothing of the object beneath it visible at that pixel; there was no ambiguity left for a resolver to settle.
- Verify: sandbox — reproduced and fixed headless (Chromium, no auth/GIS/real-data needed): a seeded plan with a 443'×135' building carrying dock zones top/bottom, badge landing squarely on it. - **THE HAZARD, as reported.** The menu that opened leads with Reshape… and ends with Delete, none of it acting on the label the cursor was actually over — a misdirected menu on a Delete is how someone destroys a building while trying to tidy a label. Treated as a canvas hit-testing correctness bug, not a cosmetic one.
