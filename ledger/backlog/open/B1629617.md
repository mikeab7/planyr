### B1629617 — `comps` has no optimistic-concurrency guard at all — a stale edit-form save silently overwrites every field `[Shared / Comps]` (bug) #persistence #comps  *(filed by B1629616's concurrency audit, 2026-09-15. Minted **B1629617** from this branch's reserved block. DEDUPE-FIRST — no prior item on `comps` concurrency; net-new.)*
`[ ]` `public.comps` carries no `version`/`rev` column, and `compsStore.js`'s `updateComp(id, comp)` runs `supabase.from("comps").update(compToRow(comp)).eq("id", id)` — `compToRow` serializes every column of the in-memory draft (comp type, date, title, notes, the whole anchor, every land/building/lease field), never a diff, and there is no compare-and-swap of any kind. `compsStore.js`'s own header claims this is fine because "comps don't have cloudSync.js's multi-tab autosave race" — measured against the actual UI (`CompsPanel.jsx`'s single-comp edit form, an explicit Save button after a form can sit open indefinitely) this claim does not hold: the owner runs two machines and leaves tabs open for days, and a comp edit form opened from a stale snapshot on one of them will, on Save, overwrite every field of the current row with that snapshot's stale values — including any field someone changed on the other machine in the interim. This is a true lost-update risk, not a theoretical one.
- Verify: sandbox
- Fix shape (measured, not yet built): add `version integer not null default 1` to `public.comps` (mirrors `optimistic_concurrency.sql`'s shape for `sites`/`doc_reviews`), and route `updateComp`/`insertComp` (`compsStore.js`) through `shared/cloud/optimisticUpsert.js`'s `casUpsert`/`degradeUpsert` — `comps`' PK is a plain single `id` column (`conflictTarget` defaults correctly, no composite-key work needed like `model_sheets` required). `CompsPanel.jsx`'s `save()` needs to carry and update the draft's `version`; a conflict should surface the same "reload before saving" prompt `sites`/`doc_reviews` already use. `insertComps` (the bulk paste-grid path) inserts brand-new rows only, so it is unaffected — a fresh row starts at `version: 1` regardless of caller.
