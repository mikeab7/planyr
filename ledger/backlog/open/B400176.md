- **HIS REPORT.** Rename a loose page from "Untitled page" to "PROBE13 TITLE". The stored tree updated immediately and correctly, **and the rail stopped showing the note at all** — only "Recovered — …" remained. A reload put it back in the right place. His caveat, stated plainly and correctly: he drove it with a synthetic `input` event, so the re-render path might not be the real one. What made it worth chasing anyway is the **asymmetry** — the commit path ran while the list did not update.
- **REPRODUCED WITH `page.keyboard`, and the caveat was not the story.** `ui-audit/verify-notes-rename-live.mjs`, three assertions, two window sizes including his short one. After typing a new name: the screen read **"PROBE13 TITLE"** and the STORED tree read **"Untitled page"**. After making a new page: the rail had **three** notes and the stored tree had **two**. 11/15 before, **15/15** after.
- **THE CAUSE — TWO READERS OF ONE TREE, READING DIFFERENT COPIES.** The rail renders from React state; the cloud sync reads `localStorage`. `persistTree` wrote the stored copy on a **400 ms debounce**, and the sync does not merely READ that copy, it decides from it:
  - `seed()` asks `sync.treeDirty` — only true once `writeTree` has run — to decide whether this device owes anything. Inside the window it is FALSE, so the seed concludes this device is clean and **adopts the account's tree wholesale**, a tree that cannot contain an edit this device has not written down yet. It hands that back through `onTree`, which is the row leaving the rail.
  - `pushPending` pushes `readTreeRaw()`, so an edit made in the window is not merely late to the account — it is **skipped**.
  - A page that exists only in memory is therefore one sync tick away from never having existed. That is the version of the failure that matches what he SAW.
- **THE FIX, and it is a correctness rule rather than a performance one: THE STORED TREE IS NEVER STALER THAN THE SCREEN.** `persistTree` writes through. The debounce bought nothing — the write it delayed is LOCAL, and the network push is debounced separately inside `writeTree` (`schedulePush`), unchanged — so removing it adds no traffic.
- **THE COST IS MEASURED, NOT ASSUMED** (`ui-audit/measure-tree-write.mjs`, budget chosen before the run: 2 ms/keystroke against a 16.7 ms frame). His notebook today: **0.007 ms** median. Ten times his: **0.052 ms**. Fifty times his (500 notes × 5 subpages, 500 binned, 352 KB): **1.167 ms**. The debounce was protecting a rename from seven-millionths of a second.
- **AND THE SAME DEFECT ONE LAYER UP, fixed in the same pass.** Every tree mutator was a `useCallback` closing over the render's `tree`, so an edit made after the store replaced the tree underneath us wrote the older copy back over the newer. **Two of the sixteen already read the ref and fourteen did not** — exactly the split that survives review. All sixteen now go through `treeNow()`, which also makes the rail's handlers referentially stable instead of rebuilt on every keystroke of a rename.
- **GUARDS, both mutation-proven.** `test/notesTreeWriteThrough.test.js` — 11 cases through TWO REAL STORE INSTANCES against an in-memory server that owns `rev` like the deployed trigger: the loss DEMONSTRATED (so the cost is on the record, not asserted), then rename / new page / move / delete each surviving a seed, plus ten interleaved write-then-sync rounds with the other computer editing between each. `test/notesModule.test.js` adds the source guard — no timer between `persistTree` and the disk, `TREE_SAVE_MS` gone rather than unused, and every one of nine mutators reading `treeNow()`. Reverting one mutator to the render's copy turns it red with the exact call named.
- **WHY A SOURCE GUARD AS WELL AS A BEHAVIOURAL ONE.** A reintroduced timer looks correct to every test that waits a moment before reading, which is nearly all of them. The shape is what rots quietly, so the shape is what is pinned.
