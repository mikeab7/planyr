- Verify: sandbox — per ATTEMPT-BEFORE-YOU-PARK, drove the exact reported sequence headlessly (logged out, no GIS/auth needed) rather than parking it for a signed-in pass; see the live proof below.
- **AUDIT-FIRST: what the missing doc's title claims ("routes by DOM focus rather than canvas selection") is not what the shipped B464048 system does** — it already routes by a LATCH tracking the user's last real canvas-vs-chrome touch, not by raw focus, and undo/redo are already `scope:"app"` (always allowed except while literally typing in a text field). Rather than re-diagnose a fix that was already shipped and independently verified 56/56 in `test/keyContract.test.js`, this session searched for a DIFFERENT way the reported symptom could still occur despite that system.
- **THE FOUND DEFECT: four `onKeyDown` handlers called `e.stopPropagation()` UNCONDITIONALLY, before checking which key was pressed** — `ParcelRecordPanel.jsx`'s two record fields, `SetLocationDialog.jsx`'s address search box, the "Add by address" field, and — the one that matters most, because it is the single most-used free-text control on the canvas — the callout/text-box editor (every plan with any callout or text box reaches it). A `window`-level bubble-phase listener (the planner's `onKey`, where keyScope/keyContract actually live) never sees a key stopped upstream, for ANY reason, whatever the shared router would have decided. That is a SECOND, undocumented, per-component keyboard-routing decision — exactly the "routes around the one place this app decides who owns the keyboard" failure mode named in the task, even though the specific missing-doc diagnosis could not be confirmed.
- **THE FIX IS THE SAME SHAPE IN ALL FOUR PLACES: stop only the key(s) the component actually answers itself** (Enter to commit, Escape to cancel/revert, Alt+Z to autosize) **and let everything else bubble.** This is safe by construction, not by luck: `keyScope`'s FIELD scope already refuses every plan-mutating shortcut while a text control is genuinely focused (`keyScopeVerdict`'s `if (scope === SCOPE.FIELD) return { allow: false, … }` — checked BEFORE the "app"-scope carve-out, so even Ctrl+Z stays correctly blocked while truly typing), so nothing here needed a second copy of that rule. The only behavior this changes is the case where one of these controls holds focus PAST the point a shortcut is pressed — which is exactly the class of bug B464048 exists to close, arriving through a door that system could not see because the event never reached it.
- **LIVE PROOF, driven headless against the real running app on a fresh "Start blank" plan (no sign-in, no GIS):** drew a building, moved it (one canvas action), then armed the Callout tool, placed one, typed "hello world" — and, critically, clicked DIRECTLY ON THE BUILDING to select it, never pressing Enter or Escape (the exact "believes he's left the box" sequence from the report). Confirmed `document.activeElement` moved to `BODY` (not the textarea) and the callout's `<textarea>` unmounted. Pressed Ctrl+Z **once**: the callout ("hello world") was removed from the canvas — proof the keystroke reached the app's global undo instead of being silently absorbed by the (no-longer-focused, but formerly `stopPropagation`-guarded) callout editor. Before this fix, the same sequence would have left that keystroke unable to even reach the window listener.
- **MACHINE-ENFORCED so it cannot regress:** `test/keyContract.test.js` gained a source sweep (`BANNED` regex) over the whole site-planner workspace that fails the build if `onKeyDown={...}` ever again calls `stopPropagation()` before its first `if`, plus a mutation-proof (the exact pre-fix shape is asserted to MATCH the banned pattern, so the guard is proven to bite before proving the fix clears it).
