## Lazy per-state layer files (batch K stage 1, B2671306)
The 14 per-state layer files (state/county `…Layers` modules) load ON DEMAND (`lib/lazyLayerFiles.js`, loader in `lib/layers.js`, React hooks `lib/useLayerRegistry.js`). An unloaded layer is still a known id (`isLayerId`, generated `lazyLayerIndex.generated.js`) so saved settings are never pruned; new layer in one of those files → `npm run layer-index`. Never import one statically from eager code (guarded by the lazyLayerRegistry test).

## Lazy per-state county parcel tables (batch K stage 2, B2671306)
The 19 per-state county tables (`alabamaParcels.js` … `kyParcels.js`, key prefix `<st>_`) load ON DEMAND through `lib/parcelStateTables.js` (the slim eager index: `PARCEL_STATE_FILES`, `LAZY_ROW_ORDER`) and merge into `COUNTIES` / `COUNTIES_MAP` via `registerParcelState` in `counties.js`, at their ORIGINAL key position (candidate order and tie-breaks read it). **"Not loaded yet" is never "no data":** until a state's rows are in, `countyIdentity` answers `pending` (reason `parcel-tables`), `displaySourcesForView` takes its pending path un-memoized, a missed `COUNTIES["ky_…"]` read kicks the load, and `ensureCountyGeometryAt` / `countyKeyForNameLoaded` / `lookupParcels` wait for it; `onParcelTablesLoaded` re-runs the map, the planner and (via `useParcelTablesVersion`) React readers. A saved county key is never rewritten while its table loads; a failed load is loud and retried. The admin coverage map calls `loadAllParcelStates()`. Unit suites keep every row synchronously through the `parcelTablesPreload.js` alias (the vitest config alias onto the test-helpers preload-all module). New state file → add it to `parcelStateTables.js`; the repo-root parcelStateTables test fails until the index, the row order and the pre-split baseline fixture agree. Never import a table file statically from eager code; a lazy row may not carry a URL-keyed registry flag (statewide / identifyOnly / pointViaEnvelope / dedupeBy / pointWhere / cityScoped) without extending `refreshLazyDerived`.

## GIS source packs (batch K stage 3, B2671306)
the shared GIS registry module (`sources`) is now only the EAGER CORE of the GIS source registry (rows jurisdiction / Site Analysis / detention / the always-on layers read at load). Every other row lives in a pack file (`sources<Colorado|Georgia|Tennessee|Mississippi|Florida|Ok|HoustonMetro|TxCityZoning|SugarLand|FortBend|Nashville|NashvilleBuffers|Rutherford|RegistryOnly>`) that the shared pack loader (`sourcePacks`) merges INTO THE SAME `GIS_SOURCES` object (`registerSourcePack`, original key order restored) before the lazy layer file that reads it runs — `lazyLayerFiles` entries carry `packs: [...]` and their loader awaits them. ⛔ A pack key read early throws a message naming its pack (`gisSource`), a failed pack load rejects + console.errors and retries, and an eager module must never read a pack key (the repo-root sourcePacks test sweeps for it, compares the all-loaded registry with its baseline fixture, and loads every layer file with nothing preloaded). Adding a row: eager core only if an eager module reads it at load, else the pack of the layer file that reads it; then `npm run source-pack-index`. Node scripts that audit pack rows import `sourcesAll` (shared/gis) (full registry), never the app.
