- **`lib/numEditBox.js` + `components/NumEditField.jsx` (NEW-1) — the canvas's ONE inline numeric
  editor, and the rule that it may never be bigger than the control it edits.** Clicking a setback
  chip turns THAT CHIP into the field: same footprint, same type scale, same corner, and the static
  chip is suppressed while its editor is open, so the number can never be on screen twice. The
  editor is SHARED (road width · element dimension · overlay trace length · aerial calibration); a
  caller with no chip gets the FLOATING fallback — same styling, brought to chip scale, OFFSET off

  contour hover label); **(c)** `input[type=number]` spinners are suppressed app-wide in the
  global stylesheet (repo-root `src/`) and replaced by ArrowUp/ArrowDown — the UA chevrons are bigger than the digits on a pill this size.

## Diagnostics and version history are their own hooks (audit batch G4)
The planner's `window.__planner*` read-only diagnostic / E2E hooks (view changes, layers, hit target, foreign overlays, grading readout and drive, perf, fit, identify result, parcel outlines, road network, export sheet) are ONE hook, `lib/usePlannerDiagnostics.js`, called once from the component with the values they read; each keeps its call-time gate (`isDiagArmed` / `__PLANYR_E2E`) and cleanup. The Version history dialog's state, the Activity tab fetch and open/restore are `lib/useVersionHistory.js`. Neither imports back from `SitePlanner.jsx`. Tests: `plannerDiagnosticsHook` in the repo-root `test/` folder.

## The pond block of the Properties inspector is `components/PondInspector.jsx` (audit batch G5)
Was a 1,500-line IIFE inside SitePlanner's main return; now a module-scope `memo` component (`@planner-extract`, listed in `test/helpers/plannerSource.js`, exempt in `DRAWING_SURFACE_FILES` like the other moved pieces). Every planner value it reads arrives as a prop, named exactly as it was in the component, so the body is byte-for-byte the old one. Note: `memo` only skips a re-render when props are referentially stable; most handlers are still rebuilt each render, so this step is a seam, not yet a speed-up (the profile step decides what is next).

## The markup blocks of the Properties inspector are `components/MarkupInspector.jsx` (audit batch G5b)
Three module-scope `memo` components moved verbatim out of SitePlanner's main return: `EasementInspector`, `NeutralMarkupInspector` (line, polyline, rectangle, ellipse, polygon, cloud) and `MarkupStyleInspector` (the remaining deed-encumbrance kind). The `!multiStyleable && selMarkup && kind…` guards stay in SitePlanner; every other value arrives as a same-named prop. Source-scan tests that sliced the old inline text now slice on the `export const …Inspector` markers (`calloutPanelLayoutA`).

## Building/road headers and the other top-level inspector blocks are components (audit batch G5c)
`components/InspectorHeaders.jsx` holds `BuildingInspectorHeader` and `RoadInspectorHeader`; `components/ElementInspectors.jsx` holds `DockLayerInspector`, `MultiStyleInspector`, `CalloutInspector`, `MeasureInspector` and `DriveInRampInspector`. All are module-scope `memo` components moved verbatim from SitePlanner's main return, with every planner value passed as a same-named prop and the guards left in SitePlanner. The deeper building and road bodies (the sections below the header, rendered through `renderElAppearance` and the inline element sections) are still in SitePlanner: they are interleaved with shared per-type conditionals and are a separate step.
